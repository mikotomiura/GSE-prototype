## 1. ⚠️★★★ 主結果: **L3 は Stop。計器がこのコホートに存在しない**

**`hook_health` 行は 63 ファイル中 1 行も存在しない**（実測・全行種を数えた）。

| 事実 | 出所 |
|---|---|
| Phase1 コホートの記録期間: **2026-07-04 〜 2026-07-24** | 本実験で実測（全レコードの時刻範囲） |
| `src-tauri/src/input/liveness.rs` の追加コミット: **2026-08-09** | `git log --diff-filter=A`（`feat(hook): キーボードフックの silent death を検知して記録する`） |

→ ★★★ **計器は収集が終わった 16 日後に作られた。**
**`starved_ms` による沈黙の 2 成分分解は、このコホートには原理的に適用できない。**

⚠️★★★ **これは事前登録どおりの Stop であって、失敗ではない**（`preregistration.md §7`）。
★ しかも「測れなかった」の**中身が特定できた** —— 「データが薄い」でも「信号が無い」でもなく、
**「計器がこのコホートより後に作られた」**である。

### 1.1 ⚠️ この失敗は「Tier 0 の `keys`/`bs_keys` が旧ログに無い」と**同型**である

`personalization-and-online-learning.md §5.2` 逐語:

> ⚠️ **旧 NDJSON には本フィールドが無い**ので、`--metrics` 経路では欠測が `0` に倒れる
> （「実測 0 打」と区別できない）。解析側は対象ログが Tier 0 配線以降かを別途確認すること。

★ 本実験は `keys`/`bs_keys` については**この注意に従って回避した**（`key` 行から数え直した）が、
⚠️ **`hook_health` については同じ検査をしていなかった**。
→ ★ **教訓: 「既存ログにある」は *現行コードが出す* の意味であって、*対象コホートにある* の意味ではない。**

### 1.2 ★ 実装が黙って嘘をつきかけた（★ 修正済み・テストで固定）

初版は「`hook_health` 行が無い」を **「入力皆無だった」** として集計し、
`<100` 窓について **`void = 0.680`** と報告していた。⚠️ **存在しない所見を作っていた。**

→ ★ **`unknown` を `void` から分離**し、`analyze.py` の Stop も
`stop_kind = "instrument_absent"` として「計器が無い」と「presence が観測されなかった」を区別した。
★ 自己検査 **S1c** がこの挙動を固定している（計器の無い合成ログで `void == 0` を要求）。

## 2. ★★★ L1 / L2（model-free）— `§0` の問いへの答えはここにある

⚠️ **L3 が Stop しても、測った量は残る。** 以下はモデルを一切当てていない。

### 2.1 窓の切り方が上流と同一であることの確認

| 量 | 本実験 | 上流 `cv-gate-null` | 一致 |
|---|---|---|---|
| 5 分窓の総数 | **617** | 617 | ★ |
| `keydown < 100` の窓 | **235（38.09%）** | 235（38.09%） | ★ |
| 被験者別の除外率 | 0.219 / 0.017 / 0.422 / 0.605 / 0.580 | 21.9% / 1.7% / 42.2% / 60.5% / 58.0% | ★ |

★ `selftest` S1b が窓ごとの keydown 数を `block_variance.window_counts()` と
**完全一致**することを機械検査している ＝ **窓の切り方を再発明していないことの構造的証明**。

### 2.2 ★★★ 5 分窓の時間内訳 — 「打鍵が薄い窓」で時間は何に使われていたか

★ 「沈黙」= **≥30 秒の無打鍵区間**。「先頭」= 計測開始から最初の打鍵まで（★ §2.4 参照）。

| 窓の種類 | n | 沈黙（本体） | 先頭 | **計** | keydown 中央値 |
|---|---:|---:|---:|---:|---:|
| 全窓 | 617 | 0.503 | 0.071 | **0.574** | 205 |
| `≥100`（適格） | 382 | 0.395 | 0.014 | **0.408** | 370 |
| **`<100`（除外）** | 235 | 0.680 | 0.164 | ⚠️ **0.843** | 0 |
| うち **0 打鍵** | 123 | 0.561 | 0.258 | **0.819** | 0 |
| うち **1–99 打鍵** | 112 | 0.810 | 0.060 | ★ **0.870** | 27.5 |

★★★ **読み取れること**:

1. ⚠️★★★ **適格性ゲートで除外される 235 窓では、時間の 84.3% が ≥30 秒の沈黙である。**
   → ★ **「打鍵が少ない窓」は「ゆっくり打っている窓」ではなく「ほとんど打っていない窓」である。**
2. ★★★ **`1–99` 打鍵の窓が最も沈黙が長い（87.0%）** —— ゼロ打鍵窓（81.9%）**より長い**。
   ⚠️ `cv-gate-null §3-4 (b)` が「H0 の 4.7〜19.9 倍の余分な質量がある」と特定したのが
   まさにこの `1–99` 帯である。→ ★ **その帯の正体は「時間の 87% が長い沈黙で、
   残り 13% に 27.5 打が詰まっている」窓**だと分かった。
3. ⚠️ **適格な `≥100` 窓ですら時間の 40.8% が ≥30 秒の沈黙**である。
   → ★ **沈黙は「除外される窓の特徴」ではなく、作業一般の性質**である。
4. ★ 被験者別の `<100` 窓の沈黙割合: P010 0.866 / P012 0.913 / P013 0.941 / P014 0.770
   （⚠️ P011 は `<100` 窓が 1 個で沈黙 0.000 ＝ **実質的に情報が無い**）。
   → ★ **「打鍵が薄い窓」の中身は 4 名で一貫している。**

### 2.3 沈黙ギャップの分布

| | n | 中央値 | p90 | 最大 |
|---|---:|---:|---:|---:|
| 本体（打鍵に挟まれた） | **776**（うち打ち切り 25） | 64.4 s | 251.1 s | **39.7 分** |
| 先頭（計測開始→初打鍵） | 34 | 107.3 s | — | **68.4 分** |

★ **沈黙の総量 = 31.0 時間**。

### 2.4 ⚠️ 「計測開始前の窓が 38% を汚染している」という疑いは**否定された**

★ 実装中に「ゼロ打鍵窓の沈黙割合が 56.1% しかない」という物理的に不自然な値が出たので追跡した。

| 検証 | 結果 |
|---|---|
| `session_start` 行が無いファイル | **0 / 63** |
| `t0` → 最初の `session_start` のずれ | 中央値 **5.1 秒** / p90 50.7 秒（5 分超は **3/63**） |
| **計測開始より前の `key` 行** | ★ **0 件** |

→ ★★★ **上流の 617 窓 / 38.09% は「計測前の時間」で汚染されていない。**

⚠️ **不自然さの原因は本実験の実装側だった** —— 「計測開始 → 最初の打鍵」の区間
（`session_start` は既に押されている）を沈黙に数えていなかった。
★ この区間を **`leading_gaps`（34 本・中央値 107.3 秒・最大 68.4 分）** として別枠で計上した。
⚠️★ **初版の本文は「中央値 180 秒・最大 97 分」と書いていたが、これは別量**
（`t0` から最初の *採用* 打鍵までを全 57 セッションで測った値）であり、
`results/` の実測（107.3 秒 / 68.4 分）と一致しない。→ **results から再計算した値に置換した**
（`verify-before-claiming` / code-reviewer MEDIUM）。
→ ★ **「先頭」列として別枠で加算し、含む/含まないの両方を報告する形に直した**
（⚠️ 片方だけ報告すると、都合のよい方を選べてしまうため）。

## 3. ⚠️★★★ 限界（★ 隠さない）

1. ⚠️★★★ **本実験の主目的（在席×非打鍵 / 入力皆無 の弁別）は 1 ミリも達成していない。**
   ★ 得られたのは「沈黙がどれだけあるか」までであり、**その沈黙の中身は依然として不明**である。
   ⚠️ `cv-gate-null §5-4` 逐語「**「ゼロ打鍵窓＝離席/非打鍵作業」は解釈であって観測ではない**」は
   **そのまま生きている**。
2. ⚠️ **30 秒未満の沈黙は対象外**（`lib.rs:2923` の間引きに合わせた閾値）。
   → **micro 帯（2–15 秒 = [P121] の「局所思考」）について本実験は何も言わない。**
3. ⚠️ **n = 5・全セッション `task_kind = argumentative`（分散ゼロ）。**
   → ★ **「個人差か実タスク差か」は本データでは原理的に切り分けられない**（ADR-011 D7）。
4. ⚠️ **P011 は `<100` 窓が 1 個しか無く、判定に情報を与えていない。**
   ★ `cv-gate-null §5-6` が同じ参加者について「**実質 4 名の結果である**」としたのと同じ状況。
5. ⚠️ **「沈黙」は content-free な打鍵の不在であって、離席・熟考・非打鍵作業を区別しない。**
6. ⚠️ **探索トラックであり確証主張に使わない**（ゲート未適用）。

## 4. ★★★ 結論と含意

### 4.1 事前登録の合格基準に対する回答

`preregistration.md §6` の 3 条件は **1 つも評価に至らなかった**（L3 が Stop したため）。
→ ★ **「情報があった」とは書かない。「情報が無かった」とも書かない。測っていない。**

### 4.2 ★ それでも確定したこと

1. ★★★ **適格性ゲートが落とす 235 窓は、時間の 84.3% が ≥30 秒の沈黙である。**
   → ⚠️ **「打鍵が薄い窓を測る」とは「長い沈黙の中身を割る」ことに他ならない。**
   ★ これは `docs/mhd` 系の裁定（Tier 1–2 の目的を「精度」から「沈黙区間を割ること」へ
   置き直した）を**実測で裏づける**。
2. ★★★ **その素材（`starved_ms`）は現行コードには存在するが、Phase1 コホートには存在しない。**
   → ★ **この解析が実際に回るのは、`liveness.rs` 導入（2026-08-09）以降に収集したログである。**
   ⚠️ **G1 のログには `hook_health` が載っている**（`validate_blocks.py:494` 逐語
   「アプリが `hook_health` 行を出すようになったので、ここで**機械判定**する」）。
   → ★★★ **本実験のパイプラインは、G1 コホートに対してはそのまま走る。**

### 4.3 ⚠️ handoff の推測に対する判定

`_handoff §3` の「安く届きそうな経路」1 は逐語で
「**`liveness.rs` が既に OS 全体の最終入力時刻（マウス含む）を取っている**…
**content-free に切り出せる素材が既にある**」と書いていた。

→ ⚠️★★★ **半分正しく、半分誤りだった**:

| | 判定 |
|---|---|
| 「素材が既にある」（現行コード） | ★ **正しい**。`starved_ms` の意味論は本実験が実測で確認した（`liveness.rs:86-103` の 3 分岐） |
| 「既存ログから切り出せる」（Phase1） | ⚠️ **誤り**。**Phase1 コホートには `hook_health` 行が 1 行も無い** |

★ handoff 自身が「⚠️ **ただし repo にこの用途の設計記述は無い。新規の設計判断になる**」と
但し書きしていた点は妥当だった。
