## 1. ★ ブロックの切り方 — **(a) 1 ブロック = 1 セッション**（確定）

**各ブロックごとに GSE アプリを起動し、ブロック終了で停止する。1 ブロック = NDJSON 1 ファイル。**

### なぜ (a) か（(b) 通し録り＋オフライン分割を却下した理由）

| 観点 | (a) 1 ブロック = 1 セッション | (b) 通しで録りオフライン分割 |
|---|---|---|
| **取り違えの影響範囲** | ★ ファイルが物理的に分かれる。時刻を 1 つ間違えても**そのブロックだけ**壊れる | ★ **分割時刻が 1 つずれると以降の全ブロックのラベルがずれる**（10 ブロックが連鎖して壊れる） |
| **特徴量の汚染** | ★ セッション開始で `FeatureExtractor::reset()` が走るので、**30 秒ローリング窓が前ブロックを引きずらない** | 各ブロック冒頭 30 秒が**前ブロック＋休憩の沈黙**で汚染される |
| **時刻の扱い** | 匿名化が `t` を**セッション開始相対 ms** にするので、ブロック内相対時刻がそのまま得られる | ブロック境界を絶対時刻で管理し続ける必要がある |
| **コード変更** | 不要（通常の起動／停止だけ） | 不要 |
| **手間** | アプリ起動 10 回（ブロック間の 1 分休憩に収まる） | 起動 1 回 |
| **失敗モード** | 起動忘れ → **そのブロックのログが無い**（=技術的欠損として §3.6 の既存規則で扱える） | 分割ミス → **気づかないままラベルが入れ替わる**（検出できない） |

> ★ **決め手は「気づけるか」である。** (b) の失敗は**沈黙して間違った結果を出す**が、
> (a) の失敗は**ファイルが無いという形で必ず露見する**。

### 手順

1. ブロック開始の直前にアプリを起動し、「開始する」を押す。
2. ブロック終了（5 分）でアプリを停止する。
3. 生成された NDJSON のファイル名を**そのまま**記録用紙の該当行に転記する（§2）。
4. ⚠️ **休憩中にアプリを動かしたままにしない。** 休憩の打鍵がブロックに混入する。

### 1.1 ★★ アプリの起動方法（**毎ブロック同じ**・`preregistration.md §5.4`）

> ⚠️ ★ **`GSE_DISABLE_PROBES=1` を立てずに起動してはならない。**
> `§2.6` は「アプリ内プローブを使わない」と凍結しているが、**アプリは放っておくと出す**。
> 5 分ブロックあたりの発火確率は **57%（第 1 週モード）**。しかも `§3.6` が
> **ブロックの事後除外を禁じている**ので、汚染されたブロックは**後から落とせない**。

### ★★ launcher を使う（手で打たない）

★ **起動のたびに毎回必要**である（1 ブロック = 1 セッションなのでアプリを 10 回起動する）。
毎回手で打つと、10 回のうち 1 回抜ける。**本 repo に launcher を用意してある**:

| OS | 使うもの | 中身 |
|---|---|---|
| **macOS** | `launch-g1-macos.command`（ダブルクリック） | 既存インスタンスを quit → `GSE_DISABLE_PROBES=1 open -a gse-next` |
| **Windows** | `launch-g1-windows.bat`（ダブルクリック） | `taskkill` → `set GSE_DISABLE_PROBES=1` → `start gse-next.exe` |

> ### ⚠️ 手で打つ場合に間違えやすい 2 点（2026-08-03 実測で確認）
>
> 1. ★ **アプリ名は `gse-next` である**（`tauri.conf.json` の `productName`）。
>    `open -a GSE` / `GSE.exe` では**起動しない**。
>    Windows で配っているのは **portable の `gse-next.exe`**（v0.1.22 にインストーラは無い）。

>    → **その回の環境変数が適用されない。** 前ブロックのアプリを必ず終了させてから起動する。
>    （残っていると打鍵が 2 本の NDJSON に混ざる問題も同時に起きる。）
>
> ✅ ★ `VAR=1 open -a <App>` の形で環境変数がアプリに届くことは **macOS 26.5.2 で実測確認済み**。
> ⚠️ ただし **`ps eww` では検証できない**（macOS は他プロセスの環境変数を出さない。`PATH` すら見えない）。
> **その方法で「渡っていない」と判断してはならない。**

### 2.3 ★ 取り違え防止の 4 段構え

1. **転記は 1 方向だけ**: `assign.py` の出力 → 記録用紙。逆方向（記録用紙から割付を再構成）はしない。
2. ★ **課題文はブロック開始直前に、そのブロックのファイルだけを開く**（§1.2 / §4 の台本）。
   ⚠️ **次のブロックのファイルを先に開かない**（★ **提示順**は `§2.12` が伏せると宣言している）。
   （紙で 1 枚ずつ渡す旧運用は 2026-08-03 に廃止した。1 ファイル = 1 ブロックが同じ役割を担う。）
3. ★ **ブロック長をログから検算する**（実施当日中に必ずやる）:

   ```bash
   python3 analyze.py --verify-blocks --dataset ~/gse-dataset --subject P015
   ```

   各 NDJSON の「最初の keydown 〜 最後の keydown」の長さを出力する。
   **5 分ブロックなら 4:00〜5:00 に収まるはず**。大きく外れたら起動／停止の取り違えを疑う。
   `--verify-blocks` は**ラベルを一切読まない**（条件を見ずに長さだけ見る）ので、
   これを走らせても解析結果を見たことにならない。
4. ★ **打鍵数を用紙に転記する**（同コマンドが出力する）。
   `preregistration.md §2.9` の適格性ゲート（≥100 打鍵）を**当日その場で確認できる**。
   ⚠️ 下回っていても**その場でやり直さない**（やり直しは条件を見た後の介入になる）。記録だけする。

## 5. ★ 課題文を研究者本人が読まずに使う手順（パイロット用）

パイロットは**研究者本人が被験者**になる（`preregistration.md §2.8`）。完全な盲検は不可能である
——**課題文の作成者だから**である。それでも露出を最小化する:

1. **課題文を作った日と、パイロットを回す日を分ける**（最低 1 日空ける）。
2. ★ 生成した `pages/<ID>/blockNN.html` を**当日まで開かない**。画面で読み返さない。
3. パイロット当日は**ブロック開始 1 分前**に、そのブロックのファイルだけを開く（§4.2 と同じ）。
4. ★ **ファイル名は `blockNN.html` で条件も題材も含まない**ので、開くまで
   HI / LO のどちらかは分からない（`build_task_pages.py` の `leak_check` が保証する）。
5. ⚠️ ★ **これは盲検ではない。** 作成者は内容を覚えている。
   **報告に「パイロットは盲検化できていない」と明記する**（`preregistration.md §2.8`）。
   だからこそ**パイロットデータは確証標本に入れない**。

### 5.1 ★★ P-1 を 2 端末で回す（研究者判断 2026-08-03 = G-1 / G-4）

**Windows 11 と macOS で 1 回ずつ、計 2 回**の P-1 を回す。

```bash
# 1 回目（Windows・topic01）
python3 assign.py --pilot --pilot-label win --json > blocks/PILOT-win.json
# 2 回目（macOS・topic02）
python3 assign.py --pilot --pilot-label mac --pilot-topic 2 --json > blocks/PILOT-mac.json
python3 validate_blocks.py     # ★ 実施前は「まだ実施していない」note だけが出て緑
```

| 回 | OS | 題材 | 被験者 ID | 割付ファイル | NDJSON の置き場 |
|---|---|---|---|---|---|
| **1 回目** | **Windows 11** | `topic01` | `PILOT-win` | `blocks/PILOT-win.json` | `~/gse-dataset/raw/PILOT-win/` |
| **2 回目** | **macOS** | `topic02` | `PILOT-mac` | `blocks/PILOT-mac.json` | `~/gse-dataset/raw/PILOT-mac/` |

> ### ★ なぜ P-1 だけ被験者 ID を `PILOT-*` にするのか
>
> `§2.0` の「P-ID を Phase1 と共有する」は **確証標本の被験者**についての決定である。
> ★ **パイロットは研究者本人であり、確証標本に入らない**（`preregistration.md §2.8`）ので、
> Phase1 のロスターから採番する必要が無い。
> 分けることで実務上の利点が 2 つある:
>
> 1. `validate_blocks.py` は **ファイル名 == `subject`** を要求する。2 回分の割付を置くには
>    `subject` が分かれている必要がある（同名だと**上書きされる**）。
> 2. `analyze.py --verify-blocks --subject <ID>` は `raw/<ID>/*.ndjson` を**全部**読む。
>    Phase1 の較正セッションと同じディレクトリに置くと**混ざって数えられる**。

- ★ **題材を必ず変える。** 同じ題材だと 2 回目は 1 回目で HI / LO の**両方を書き終えている**ので
  内容を完全に知った状態になり、P-1 の目的（**5 分で十分な打鍵が出るか**）の答えが
  **速く書けるほうへ歪む**。
- ★ **Windows を先にする。** `ime_dwell_med` が取れる設計どおりの **14 特徴**で、
  まず主たる答えを取る（macOS は構造的に欠測し実質 13 特徴・`preregistration.md §5.1`）。
- ★ **同日に回すなら 60 分以上空ける**か、**翌日**にする。
  P-1 は打鍵量の測定なので、連続実施の疲労が測定を歪める。
- ★ **どちらの回も `env.md` に OS・題材・実施順を記録する**（`§5.1-4` の報告義務）。
- ⚠️ 条件の提示順（`LO` / `HI` のどちらが先か）は**両回で同じ**である
  （`assign.py` の `rng_for` キーが `"PILOT"` 固定のため）。
  P-1 は判定しないので順序の統制は不要で、**揃っているほうが 2 回の比較を素直にする**。

### 6.1 ★ `HMM_VERSION` の刻印手順（`reproducibility-discipline`）

★ **2026-08-05 更新**: `config.json` の `reproducibility.hmm_version` は
**macOS 回（`PILOT-mac`・2026-08-04 実施）の実測値 `0.3.0` を刻印済み**である。
⚠️ ★ **残りは Windows 回（`PILOT-win`・未実施）**。

> ### ⚠️★★ Windows 回を刻印する前に必ずやること
>
> 1. `config.json` の `reproducibility.hmm_version` の**現在値を読む**（= macOS 回の値）
> 2. Windows 回の NDJSON の `meta` 行の値と**突き合わせる**
> 3. ★ **一致 → そのまま**／⚠️ **不一致 → 上書きせず、両方の値と OS を `env.md` に残す**
>    （2 回の P-1 が別の HMM で回ったことになる。★ **黙って新しい方に揃えない**）
>
> ⚠️ ★ `hmm_version` は**文字列 1 個**しか持てず、この規律を構造的に強制していない。
> ★ **人が守るしかない箇所なので、手順の側に書いてある。**

★ **誰がいつ何を書くかを決めておく**（後から思い出せない）:

| いつ | 誰が | 何を |
|---|---|---|
| **実施当日・開始前**（最初のブロックより前） | 実験者 | 実施に使う**そのビルド**の `HMM_VERSION` を確認する（★ 取り方は下記） |

| **解析の前** | 実験者 | `config.json` の `reproducibility.hmm_version` を同じ値に書き換え、コミットする |

#### ★★ `HMM_VERSION` の取り方 — **NDJSON の 1 行目に載っている**

`logger.rs:917` がセッション開始時に `{"type":"meta","session_start":…,"hmm_version":"<semver>"}`
を書く。値は `engine::HMM_VERSION` 定数なので、★ **実際に走ったバイナリの値そのもの**である。

⚠️ ★ **ワイルドカードのまま読まない。** `head -1 gse_*.ndjson | head -1` は複数ファイルがあると
`==> gse_….ndjson <==` という**ファイル名ヘッダを返す**（★ **JSON ですらない**。実測で確認した）。
→ ★ **対象を 1 本に確定してから読む**:

```bash
# macOS — ★ 最新の 1 本を選び、対象を表示してから読む
f=$(ls -t ~/Documents/GSE-sessions/gse_*.ndjson | head -1); echo "対象: $f"; head -1 "$f"
# → {"type":"meta","session_start":…,"hmm_version":"0.3.0"}
```

```powershell
# Windows (PowerShell) — ⚠️ ★ 未実測（Windows 実機が無い）。macOS 版だけ実測済み
$f = Get-ChildItem $env:USERPROFILE\Documents\GSE-sessions\gse_*.ndjson |
     Sort-Object LastWriteTime -Descending | Select-Object -First 1
$f.FullName; Get-Content $f.FullName -TotalCount 1
```

★ **repo の `engine.rs` を読んで代用しない。** 配布バイナリは `v0.1.22` のタグ時点のもので、
`main` の現在値と一致する保証がない（`env.md` は「参考: `main` の `engine.rs` は `0.3.0`」と
**参考値**であることを明示している）。

⚠️ ★ **「開始前に」という要求とは順序が食い違う**（1 行目が出るのはブロック 1 を起動した後）。
→ ★ **ブロック 1 を起動した直後**（打ち始める前）に読めばよい。**そのビルドの実測値**であり、
起動前に別経路で見るより確かである。

#### ★★ ブロック直後の 30 秒チェック（⚠️ **2026-08-04 の事故を受けて追加**）

⚠️ ★ **launcher を通さずに起動するとプローブが発火する**（`lib.rs:1938`。実機初回で実際に起きた）。
`validate_blocks.py --dataset` は**全ブロックを終えて dataset へ送った後**にしか回らないので、

⚠️ ★ **`grep -c` は 0 件でも `0` を出力する**（実測）。★ **「何も出なければ OK」ではない。
