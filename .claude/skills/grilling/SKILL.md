# grilling

## 実行モデル
**Opus** で実行する（`/model opus`）。理由: ここで閉じる判断分岐は「やり直しが効かない」。
ゴールの取り違えは、後続の issue-slicing と loop 実行全体を「間違った方向に効率よく」走らせる
だけで、verify では検出できない (`docs/loop-engineering.md` モデル割当ポリシー準拠)。

## 位置づけ (WHY)
- ループ工学は「短い・検証可能・記録可能なゴール」を前提に初めて機能する。
- そのゴールを製造するのがこの skill。曖昧なゴールのままループを回すことは、
  間違った方向への効率的な loopmaxxing にしかならない。
- したがって grill は **ループの前に・タスクにつき 1 回・main チェックアウトで** 走らせる。
  worktree の中で走らせない (ゴールは全 worktree で共有される単一の真実であり、
  worktree ごとに再確定すると分岐する)。
- grill の後段は `to-prd` → `to-issues` (このプロジェクトでは `issue-slicing` skill) に接続する。
  grill はゴールを確定するだけで、issue には分解しない。

## 方針 (固定リストを使わない)
- 固定の質問リストを順に聞くのではなく、**直前の回答から次の曖昧点・矛盾・未定義語を検出し掘る**。
- 毎回、次の 3 つを問い続ける:
  - なぜそれで良いと言えるか (根拠)
  - どうなったら done か (exit code / test 名で言えるか)
  - 何を Out にするか (スコープ外の明示)
- **判断分岐 (if A then X else Y の未確定) が残る限り終わらない。** 1 問で切り上げない。
- ユーザーが「わからない」「任せる」と答えても、それを判断分岐が閉じた合図にしない。
  代替案を 2〜3 出し、トレードオフを示した上で選ばせる (推測で埋めない)。
- 確定した内容は **その場で** `docs/glossary.md` に inline 追記する (揮発させない)。
  下した意思決定は該当タスクの `.steering/[task]/decisions.md` に
  「決定 / 理由 / 却下案」の 3 項で記録する (`.steering/_template/decisions.md` の書式)。

## 終了条件 (すべて満たすまで終わらない)
- [ ] 未解決の判断分岐が 0 (if/else の分岐が残っていない)
- [ ] 曖昧語が `docs/glossary.md` に定義済み (新規に使った用語を含む)
- [ ] ゴールが exit code / test 名 / 具体的な観測可能条件で Done/Stop を言える形になっている
- [ ] スコープ外 (Out) が明示されている
- [ ] 下した意思決定が `.steering/[task]/decisions.md` に記録されている

## 出力
- 検証可能なゴール記述 (Done/Stop が exit code / test 名で言える形)
- 確定用語 (glossary.md への追記差分)
- 決定事項 (decisions.md への追記差分)

この出力を受けて `to-prd` (このプロジェクトでは grill 結果をそのまま要件として)
→ `to-issues` (`issue-slicing` skill) が縦切り issue 群を生成する。

## 良い例 / 悪い例
- ✅ 「p_stuck の閾値は 0.70 のままで良いか」→「わからない」→「0.60/0.70/0.80 で外れ値検出の
  再現率がどう変わるか実測してから決めますか、それとも既存値を踏襲しますか」と分岐を提示し選ばせる
- ✅ 「較正」という語を初出で使った時点で glossary.md に定義を追記してから会話を続ける
- ❌ 5 問の固定リストを順番に聞いて、答えが曖昧でも次の問いに進む
- ❌ 「良い感じにお願いします」を額面通り受け取り、判断分岐を推測で埋めて grill を終える
- ❌ 確定した用語を glossary.md に書かず、会話の中だけに留める (次セッションで揮発する)

## 関連する他の Skill
- `issue-slicing` — grill で確定したゴールを縦切り issue 群に分解する後段 (Opus)
- `implementation-workflow` — grill を経ない通常の実装タスクの共通骨格
