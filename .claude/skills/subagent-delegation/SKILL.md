# サブエージェントへの渡し方

## このスキルの目的

⚠️★★★ **subagent の失敗はほぼ全部「渡し方」で起きている。**
★ 能力不足ではなく、**範囲が書かれていない / 締切が無い / model が合っていない /
戻り値を検算していない**の 4 つに集約される。本 Skill はその 4 つを毎回閉じる。

⚠️ **subagent は「安い並列」ではない。** 起動した瞬間に、
★ こちらの文脈は**プロンプトに書いたぶんしか渡らず**、
★ 向こうの作業は**見えず**、★ 戻ってくるのは**要約だけ**である。
→ ⚠️ **2 つの取りこぼし（渡し忘れ・報告漏れ）が起き、どちらも気づけない。**

## ルール 1: model は **一次を見る**。写さない・惰性で明示しない **[SSOT] [一次]**

★ 単一真実源は `docs/loop-engineering.md:60-76`。逐語:

> **やり直しが効かない判断は Opus / やり直しが効く作業は Sonnet / 判断を含まない実行は Haiku。**

⚠️★★★ **値をここに写さない。** ★ `loop-engineering.md:79` 逐語
「この表は `.claude/agents/*.md` の frontmatter `model:` と一致させる（**L7 が drift を検出する**）」。
→ ⚠️ 本 Skill に写すと **drift 検出の外にある 3 つ目の複製**になる。

| 何を知りたいか | どこを見るか |
|---|---|
| **その agent に渡る model** | ★ **`.claude/agents/<name>.md` の `model:`（一次）** |
| **役割ごとの方針** | ★ `docs/loop-engineering.md:60-77`（SSOT） |

### ⚠️ `model` を明示するのは「いつ」か **[一次]**

★ 2026-09-20 に実測した結果、**定義済み agent 12 本はすべて frontmatter に `model:` を持つ**
（`code-reviewer`=opus ／ `file-finder`=sonnet ／ `test-runner`=haiku ほか）。
→ ★ **定義済みの相手に投げるときは、既定が正しく効く。**

| 相手 / 状況 | 明示するか |
|---|---|
| ⚠️ `general-purpose` など **定義ファイルを持たない相手** | **必ず明示する**（★ 親から継承されうる） |
| ★ 既定と**違う** model を使いたいとき | **明示する**（⚠️ 理由も書く） |
| ★ 定義済み agent に既定どおり投げるとき | **書かなくてよい**（⚠️ 誤って `code-reviewer`=opus を下げうる） |

⚠️ **設計判断そのものを subagent に渡さない。** 表で Opus が割り当たっているのは
**レビュー（見逃しコスト）**であって、**裁定**ではない。★ 裁定はメインが持つ。

## ルール 2: **範囲と禁止事項**を書く（★ 書かないと暴走する）**[実地]**

⚠️★★★ **2026-09-20 に 25 分ハングさせた**
（`.steering/_handoff/next-session-g1-preconditions-verification.md:85`）。
★ 原因は「レビューして」とだけ書き、**どこまで見てよいか**を書かなかったこと。

→ ★ レビュー系に渡すときは、**次の 5 つを必ず書く**:

1. **範囲**: 「**コミット済みの範囲だけ**」（★ 下記の定型で書く）
2. **作業ツリーを触らない**（★ read-only であること）
3. **隔離クローンを作らない**（⚠️ 勝手に clone すると時間が溶ける）
4. **長い検査を回さない**（★ 「`--selftest` は 1 分以上かかるので実行しない」のように名指しで）
5. **締切**（★ 「**N 分で結論を出す**」「読み切れなかった範囲は *読んでいない* と書く」）

⚠️ **5 が最も効く。** ★ 締切が無いと subagent は**網羅を目指して止まらない**。

### ★ 範囲の定型（⚠️ **2 版ある。取り違えると対象がゼロになる**）

**(a) コミット済みの範囲をレビューする**（★ `/finish-task` の完了レビュー・PR 前）

```
対象は `<base>..<head>` の N ファイルだけです（主対象: <path1> / <path2>）。
それ以外のファイル・他のコミット・作業ツリーの未コミット変更は対象外です。
```

**(b) 未コミットの変更をレビューする**（★ `/review-changes` は
`review-changes.md:26` 逐語「**`git diff HEAD` の内容をレビュー**」＝ **未コミットが対象**）

```
対象は **起動時点の `git diff HEAD`** の N ファイルだけです（主対象: <path1> / <path2>）。
★ 起動後、メインは作業ツリーを変更しません。
それ以外のファイル・他のコミットは対象外です。
```

⚠️★★★ **(a) の文面を `/review-changes` に貼ると、対象が 1 件も残らない。**
★ **どちらの範囲指定を使うか**は、下の「レビューの型」の表で決める。

★ 対象の数え方（⚠️ `git show` は**単一コミットしか出ない**）:

| 範囲 | メインが叩くもの |
|---|---|
| 単一コミット | `git show <sha> --stat` |
| 複数コミット | `git diff --stat <base>..<head>` |
| 未コミット | `git diff --stat HEAD` |

⚠️★★★ **相手が知り得ないものは、全部メインが先に埋める。**
★ subagent は**範囲外を読めない**ので、範囲の外にある情報は**構造的に選べない**。
→ ⚠️ 丸投げすると、相手は**推測で埋めたうえで要件を満たしたように見せる**。

★ メインが先に確かめて名指しするもの（⚠️ 2026-09-20 の検証で 3 つとも詰まった）:

| 何 | どう確かめるか | ⚠️ 丸投げの形（禁止） |
|---|---|---|
| **対象ファイル名** | ★ 上の「対象の数え方」の表の**どれかをメインが叩く** | 「まず自分で `git show` して確認して」 |
| **参照先 Skill** | ★ ファイル名から決める（`.rs` → `rust-standards` ／ `analysis/` → `architecture-rules` ／ `logger.rs`・`hook.rs` → `data-privacy`） | 「内容に応じた該当 Skill を参照して」 |
| **回してはいけない検査の名前** | ★ そのタスクで何が重いかを**メインが知っている** | 「長い検査は回さないで」（★ 何が長いか相手は知らない） |

> ⚠️ **検証で実際に出た言い訳**（2026-09-20・iteration 2）: 「この新モジュール固有の重い処理を
> 知らないため、一般的な `cargo test --workspace` を代替に挙げた。**的外れの可能性がある**」。
> → ★ **相手は正しく困っている。埋めるのはメインの仕事である。**

### ★ 締切の目安（⚠️ 実測が無いときの出発点）

| 仕事 | 目安 |
|---|---|
| レビュー（`code-reviewer` / `security-checker`） | **10〜15 分** |
| 探索・影響調査（`file-finder` / `impact-analyzer`） | **5〜10 分** |
| 検証・集計（`test-runner` / `log-analyzer`） | **5 分** |

★ **同種の実測があるならそれを基準にする**
（★ 本 repo の実測: レビュー 2 本が **5.4 分 / 6.7 分**で完走し、両者とも「読んでいない範囲」を
自己申告した —— `.steering/20260920-subagent-delegation-skill/verification.md`）。
⚠️ 目安は**上限**であって、予算ではない。★ 早く返るのが正しい。

### ★ レビューの型は 2 つある（⚠️ 混同しない）

| 型 | 何を起動するか | いつ |
|---|---|---|
| **作業中の点検** | `code-reviewer` ＋ `security-checker` を**並列** | ★ 実装の区切り・自分で確かめたい時 |
| **タスク完了時** | 上に加えて **`/cross-review`（Codex との独立 2 系統）が必須** | ★ `/finish-task` Step 3（`CLAUDE.md`） |

⚠️ **「レビューして」と言われただけでは Codex 側まで回さない。**
★ 完了処理かどうかで決まる（⚠️ 迷ったら**どちらの型か**を先に確かめる）。

> ⚠️★★★ **25 分ハングの中身**: ★ レビュー中に**作業ツリーが並行更新された**のを見た
> `code-reviewer` が、⚠️ **隔離クローンを作りに行き**、Bash 呼び出しでハングして
> **結果を 1 行も返さなかった**（★ トークンは消費済み）。
> ★ 同じ変更に上の 5 点を明記して再実行したら **5 分半で完走**した。**差はプロンプトだけ**である。

★ あわせて守る:

- ⚠️ **並列レビュー中は作業ツリーを変更しない**（★ 変えるなら先にコミットしてから起動する）。
- ★ **既に出ている指摘と対応済みの内容を列挙し、再掲を求めない**（⚠️ 同じ指摘で 2 度払わない）。
- ★ **停滞の見分け方**: `~/.claude/projects/<proj>/<session>/subagents/agent-<id>.jsonl` の
  **最終 timestamp が伸びていなければハング**。→ 止める（⚠️ **手段名は未確認** ——
  `TaskStop` と記録されているが、repo 内に他の用例が 1 件も無い）。
  ⚠️★★★ そのとき完了報告には **「結果が無い」と書く**。★ **「指摘なし」と書かない**
  （⚠️ 両者は正反対の意味である）。

## ルール 3: 並列は **1 メッセージで**まとめて投げる **[SSOT]**

★ `CLAUDE.md` §4 逐語「**独立した調査・レビューは 1 メッセージで並列に投げる**」。

- ★ **独立でないものを並列にしない**（⚠️ 片方の結果が他方の入力なら直列）。
- ⚠️ **同じファイルを触る agent を並列にしない**（★ read-only なら可）。
- ⚠️ **投げた仕事を自分でもやらない**（★ 二重に払う）。待つ。

## ルール 4: **入れ子で起動しない** **[一次] [実地]**

⚠️★★★ **2026-09-19 に、これで止まった。**
★ 一次は `.steering/20260919-ssot-sr-systematic-review/deviations.md:13`。逐語:

> 段 2 を全件に回したところ、**並列のサブエージェントが入れ子で 20 本以上に増え、
> 月の利用上限に 2 回当たって全停止した**

★ **20 本以上**という数が要点である。→ ⚠️ **並列数と総本数はメインが決める**
（★ 相手に「何本まで」と委ねない）。★ 例: `/literature-review` Step 4 の `evidence-axis-judge` は
1 ラウンドに初回 3 本（軸ごとに 1 本・上限 6 本）、欠けの補いと読み違えの再判定はそれぞれ軸ごとに 1 本までと、コマンドの側で決めてある。★ 操作系に渡すプロンプトには
**「サブエージェントを起動しない（入れ子にしない）」と明記する。**

★ **波及**（⚠️ 止まること自体より、止まった後のほうが高くつく）:
`.steering/20260919-ssot-sr-systematic-review/results.md:40` —— 中断後にやり直した subagent が
**protocol から外れた**。→ ★ **中断はそれ自体が汚染源**である。

⚠️ **上限は入れ子でなくても当たる**（★ 別例・混同しない）:
`.steering/20260914-mhd-feature-offline-tiers/decisions.md:1033` —— Opus の `code-reviewer` が
**HTTP 429** で途中終了した。→ ★ 重い agent を**同時に何本も置かない**。

★ 2026-09-20 に `.claude/agents/*.md` の `tools:` を実測した結果、
**`Task` を持つのは `loop-worker` だけ**（12 本中 1 本）である。
→ ★ **他の 11 本は構造的に subagent を起動できない。**

### ★ どの相手に「入れ子禁止」を書くか（⚠️ 毎回書くものではない）

| 相手 | 書くか | 理由 |
|---|---|---|
| ⚠️ `general-purpose` など **定義ファイルを持たない汎用 agent** | **必ず書く** | ★ `tools` が絞られておらず**構造的に止まらない**（★ 2026-09-19 に入れ子を起こしたのはこの経路） |
| ⚠️ `loop-worker` | **必ず書く** | ★ 唯一 `Task` を持つ定義済み agent |
| ★ 上記以外の定義済み agent（`code-reviewer` / `security-checker` ほか 10 本） | **書かなくてよい** | ★ `tools:` に `Task` が無く**構造的に不可能**。⚠️ 書いても害は無いが、**禁止事項の行数を増やすと締切の行が埋もれる** |

⚠️ **並列数と総本数はメインが決める**（★ 相手に「何本まで」と委ねない）。

⚠️★★★ **ただし文書が食い違っている**: `.claude/commands/cross-review.md` Step 5 は逐語で
「`cross-reviewer` 内部で: 1. `code-reviewer` を **Task で並列起動**」と書くが、
★ `.claude/agents/cross-reviewer.md` の `tools:` は `Read, Bash, Glob, Grep` で **`Task` が無い**。
→ ⚠️ **その内部動作は実行不可能である。**
★ **実体としての `/cross-review` は、メインが `code-reviewer` と Codex を別々に起動する形**で回す。
（★ 起票済み: `.steering/20260920-subagent-delegation-skill/decisions.md` 判断 6）

## ルール 5: **自分でやったほうが速い仕事を渡さない** ⚠️ **[未記録]**

★ 渡す判断の目安:

| 渡す | 自分でやる |
|---|---|
| 複数ファイル横断の探索（`file-finder` / `impact-analyzer`） | ★ **探す場所が既に分かっている** 1〜2 回の grep |
| 独立に並行できる調査が 2 本以上ある | 数回のツール呼び出しで終わる確認 |
| 出力が大量で、要約だけ欲しい（`test-runner` / `log-analyzer`） | ⚠️ **一次資料を自分で読む必要がある**確認（`verify-before-claiming`） |

⚠️★★★ **一次で確かめる仕事を subagent に代行させない。**
★ 戻ってくるのは要約で、⚠️ **「読んでいない範囲」が見えない**。
→ ★ 断定の根拠にする資料は、**メインが自分で開く**。
★ 判定を独立にするために渡す場合（`/literature-review` Step 4 の `evidence-axis-judge`）は別の仕事である:
逐語の照合はメインが済ませ、相手には照合済みの一次テキストを渡して**判定だけ**を返させる。
⚠️ そのときメインは返ってきた判定を書き換えない（書き換えると独立にした意味が消える）。異議は判定と並べて書く。

## ルール 6: 戻ってきた報告を **そのまま信じない** **[実地]**

⚠️ subagent の報告は **model の出力**であって、実行結果ではない。

- ★ **指摘は一次で裏取りしてから反映する**（`verify-before-claiming` ルール 1）。
  > ★ 本セッションの実測: `code-reviewer` / `security-checker` / Codex の計 **22 件**を
  > すべて一次で確かめ、**1 件は偽陽性**（Codex が 2 巡とも同じ誤りを出した）だった。
- ★ **「done」を自己申告で受け取らない**（`docs/loop-engineering.md` の
  「`issue_done` は必ず `loop-watchdog` の客観再検証を通す」と同じ規律）。
- ⚠️ **自分の仮説を渡すと、確認されて返ってくる。** ★ 独立した読みが欲しいときは
  **コードを渡し、結論は渡さない**。

## ルール 7: **書けない brief は、渡せない仕事** ⚠️ **[未記録]**

★ brief に書くのは次の 4 つだけでよい:

1. **ゴール**（★ 何が返ってきたら成功か）
2. **既に除外したこと**（⚠️ 書かないと同じ道を辿り直す）
3. **読むべきファイル / docs**（★ 貼るのではなく**指す**）
4. **範囲・禁止事項・締切**（ルール 2）

⚠️ **これが書けないなら、渡せるほど自分が理解していない。** ★ 先に自分で調べる。
