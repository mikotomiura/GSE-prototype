# サブエージェントへの渡し方

## このスキルの目的

⚠️★★★ **subagent の失敗はほぼ全部「渡し方」で起きている。**
★ 能力不足ではなく、**範囲が書かれていない / 締切が無い / model が合っていない /
戻り値を検算していない**の 4 つに集約される。本 Skill はその 4 つを毎回閉じる。

⚠️ **subagent は「安い並列」ではない。** 起動した瞬間に、
★ こちらの文脈は**プロンプトに書いたぶんしか渡らず**、
★ 向こうの作業は**見えず**、★ 戻ってくるのは**要約だけ**である。
→ ⚠️ **2 つの取りこぼし（渡し忘れ・報告漏れ）が起き、どちらも気づけない。**

## ルール 1: model を明示する **[SSOT]**

★ 単一真実源は `docs/loop-engineering.md:60-76`。逐語:

> **やり直しが効かない判断は Opus / やり直しが効く作業は Sonnet / 判断を含まない実行は Haiku。**

★ 同表から subagent に関わる行（⚠️ **ここで再定義しない。表が動いたら表に従う**）:

| 役割 | model |
|---|---|
| survey（探索・影響調査） | **Sonnet** |
| issue 実装（worker） | **Sonnet** |
| 統合レビュー（`code-reviewer` / `security-checker`） | **Opus** |
| verify 実行（`test-runner`） | **Haiku** |
| 監視（`loop-watchdog`） | **Haiku** |

⚠️ **[未記録]** ★ **`model` は毎回明示する。** 既定に任せない。
→ ★ 既定は親から継承されうるので、⚠️ **探索に Opus が流れてコストが跳ねる**。

⚠️ **設計判断そのものを subagent に渡さない。** 表で Opus が割り当たっているのは
**レビュー（見逃しコスト）**であって、**裁定**ではない。★ 裁定はメインが持つ。

## ルール 2: **範囲と禁止事項**を書く（★ 書かないと暴走する）**[実地]**

⚠️★★★ **2026-09-20 に 25 分ハングさせた**
（`.steering/_handoff/next-session-g1-preconditions-verification.md:85`）。
★ 原因は「レビューして」とだけ書き、**どこまで見てよいか**を書かなかったこと。

→ ★ レビュー系に渡すときは、**次の 5 つを必ず書く**:

1. **範囲**: 「**コミット済みの範囲だけ**」（★ `git show <sha> --stat` の N ファイル、と具体で書く）
2. **作業ツリーを触らない**（★ read-only であること）
3. **隔離クローンを作らない**（⚠️ 勝手に clone すると時間が溶ける）
4. **長い検査を回さない**（★ 「`--selftest` は 1 分以上かかるので実行しない」のように名指しで）
5. **締切**（★ 「**N 分で結論を出す**」「読み切れなかった範囲は *読んでいない* と書く」）

⚠️ **5 が最も効く。** ★ 締切が無いと subagent は**網羅を目指して止まらない**。

> ⚠️★★★ **25 分ハングの中身**: ★ レビュー中に**作業ツリーが並行更新された**のを見た
> `code-reviewer` が、⚠️ **隔離クローンを作りに行き**、Bash 呼び出しでハングして
> **結果を 1 行も返さなかった**（★ トークンは消費済み）。
> ★ 同じ変更に上の 5 点を明記して再実行したら **5 分半で完走**した。**差はプロンプトだけ**である。

★ あわせて守る:

- ⚠️ **並列レビュー中は作業ツリーを変更しない**（★ 変えるなら先にコミットしてから起動する）。
- ★ **既に出ている指摘と対応済みの内容を列挙し、再掲を求めない**（⚠️ 同じ指摘で 2 度払わない）。
- ★ **停滞の見分け方**: `~/.claude/projects/<proj>/<session>/subagents/agent-<id>.jsonl` の
  **最終 timestamp が伸びていなければハング**。→ `TaskStop` で止める。
  ⚠️★★★ そのとき完了報告には **「結果が無い」と書く**。★ **「指摘なし」と書かない**
  （⚠️ 両者は正反対の意味である）。

> ★ **本セッションの実測（2026-09-20）**: 上の 5 つを書いて `code-reviewer` と
> `security-checker` を並列起動したところ、**5.4 分 / 6.7 分で完了**し、
> 両者とも「読んでいない範囲」を自己申告して返した。

## ルール 3: 並列は **1 メッセージで**まとめて投げる **[SSOT]**

★ `CLAUDE.md` §4 逐語「**独立した調査・レビューは 1 メッセージで並列に投げる**」。

- ★ **独立でないものを並列にしない**（⚠️ 片方の結果が他方の入力なら直列）。
- ⚠️ **同じファイルを触る agent を並列にしない**（★ read-only なら可）。
- ⚠️ **投げた仕事を自分でもやらない**（★ 二重に払う）。待つ。

## ルール 4: **入れ子で起動しない** **[一次] [実地]**

⚠️★★★ **2026-09-19 に、これで止まった。** ★ 体系的レビューのふるい分けを任せた agent が
**入れ子でさらに subagent を起動**し、⚠️ **月の利用上限に 2 回当たって全停止**した。

- `.steering/20260919-theory-ssot-promotion/design.md:42` 逐語「SR は段 2 を『結論が確定した
  時点で打ち切る』形へ（逸脱 2・**利用上限に 2 回当たったため**）」
- `.steering/20260919-ssot-sr-systematic-review/results.md:40`（★ 中断後にやり直した agent が
  protocol から外れた ＝ **中断はそれ自体が汚染源**である）
- `.steering/20260914-mhd-feature-offline-tiers/decisions.md:1033`（★ `code-reviewer` が **HTTP 429** で途中終了）

→ ⚠️ **並列数と総本数はメインが決める。** ★ 操作系に渡すプロンプトには
**「サブエージェントを起動しない（入れ子にしない）」と明記する。**

★ 2026-09-20 に `.claude/agents/*.md` の `tools:` を実測した結果、
**`Task` を持つのは `loop-worker` だけ**（12 本中 1 本）である。
→ ★ **他の 11 本は構造的に subagent を起動できない。**
⚠️ ただし `general-purpose` など**定義ファイルを持たない汎用 agent は構造的に止まらない**
（★ 2026-09-19 に入れ子を起こしたのはこの経路）。→ **プロンプトで止める。**

⚠️★★★ **ただし文書が食い違っている**: `.claude/commands/cross-review.md` Step 5 は逐語で
「`cross-reviewer` 内部で: 1. `code-reviewer` を **Task で並列起動**」と書くが、
★ `.claude/agents/cross-reviewer.md` の `tools:` は `Read, Bash, Glob, Grep` で **`Task` が無い**。
→ ⚠️ **その内部動作は実行不可能である。**
★ **実体としての `/cross-review` は、メインが `code-reviewer` と Codex を別々に起動する形**で回す。
（★ 起票済み: `.steering/20260920-subagent-delegation-skill/decisions.md` 判断 6）

## ルール 5: **自分でやったほうが速い仕事を渡さない** ⚠️ **[未記録]**

★ 渡す判断の目安:

| 渡す | 自分でやる |
|---|---|
| 複数ファイル横断の探索（`file-finder` / `impact-analyzer`） | ★ **探す場所が既に分かっている** 1〜2 回の grep |
| 独立に並行できる調査が 2 本以上ある | 数回のツール呼び出しで終わる確認 |
| 出力が大量で、要約だけ欲しい（`test-runner` / `log-analyzer`） | ⚠️ **一次資料を自分で読む必要がある**確認（`verify-before-claiming`） |

⚠️★★★ **一次で確かめる仕事を subagent に代行させない。**
★ 戻ってくるのは要約で、⚠️ **「読んでいない範囲」が見えない**。
→ ★ 断定の根拠にする資料は、**メインが自分で開く**。

## ルール 6: 戻ってきた報告を **そのまま信じない** **[実地]**

⚠️ subagent の報告は **model の出力**であって、実行結果ではない。

- ★ **指摘は一次で裏取りしてから反映する**（`verify-before-claiming` ルール 1）。
  > ★ 本セッションの実測: `code-reviewer` / `security-checker` / Codex の計 **22 件**を
  > すべて一次で確かめ、**1 件は偽陽性**（Codex が 2 巡とも同じ誤りを出した）だった。
- ★ **「done」を自己申告で受け取らない**（`docs/loop-engineering.md` の
  「`issue_done` は必ず `loop-watchdog` の客観再検証を通す」と同じ規律）。
- ⚠️ **自分の仮説を渡すと、確認されて返ってくる。** ★ 独立した読みが欲しいときは
  **コードを渡し、結論は渡さない**。

## ルール 7: **書けない brief は、渡せない仕事** ⚠️ **[未記録]**

★ brief に書くのは次の 4 つだけでよい:

1. **ゴール**（★ 何が返ってきたら成功か）
2. **既に除外したこと**（⚠️ 書かないと同じ道を辿り直す）
3. **読むべきファイル / docs**（★ 貼るのではなく**指す**）
4. **範囲・禁止事項・締切**（ルール 2）

⚠️ **これが書けないなら、渡せるほど自分が理解していない。** ★ 先に自分で調べる。

## チェックリスト（★ 起動の直前に通す）

- [ ] `model` を**明示**したか（★ 既定に流していないか）
- [ ] **範囲**を「コミット済みの N ファイル」のように**具体**で書いたか
- [ ] **禁止事項 4 つ**（作業ツリー / クローン / 長い検査 / 一次の代行）を書いたか
- [ ] **締切**（N 分）と「読んでいない範囲は *読んでいない* と書く」を入れたか
- [ ] 独立なものだけを**1 メッセージで**並列にしたか
- [ ] ⚠️ 投げた仕事を**自分でも**やろうとしていないか
- [ ] 戻ってきたら**一次で裏取り**する段取りになっているか

## ⚠️ よくある抜け穴

| 抜け穴 | 直し方 |
|---|---|
| 「レビューして」とだけ書く | ★ 範囲・禁止・締切の 5 点を貼る（ルール 2） |
| `model` を省いて既定に任せる | ★ 毎回書く。探索に Opus を流さない |
| 一次確認を代行させる | ★ メインが開く（要約では「読んでいない範囲」が消える） |
| 報告の指摘をそのまま実装する | ★ 一次で裏取り。⚠️ 偽陽性は実際に出る |
| 迷ったら投げる | ⚠️ **迷ったら投げない**（★ 数回の grep なら自分で） |
