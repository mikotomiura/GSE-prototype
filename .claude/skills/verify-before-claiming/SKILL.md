# 主張する前に確かめる

## このスキルの目的

★ **このプロジェクトで繰り返し起きている失敗は「主張と実体のずれ」である。**
事前登録が禁じたものをツールが出していた (E-6 / E-7)、docstring が約束したことを実装が破っていた
(`/cross-review` HIGH)、ゲートが検査しているつもりで何も検査していなかった
(`run.sh [5]` の silent pass)。**同じ構造が、私 (エージェント) の発言にも起きる。**

本 Skill は **断定の前に一次資料へ降りる**手順を強制する。

## 適用範囲

### 適用する
- 事実の断定（「〜は不要」「〜になる」「〜は既知」「〜済み」）
- 削除・簡略化の提案（アセット / コード / ドキュメント / 設定）
- ★ **設計裁定・ADR・仕様の確定**（⚠️ **2026-09-13 追加** —— ★ ここで 2 回踏み抜いた。→ ルール 7 / 8）
- 挙動の説明（CI・ビルド・スクリプト・フラグ）

### 適用しない
- 明示的に「仮説として」「未確認だが」と断ったうえでの見立て
- ユーザー自身が事実として述べたこと（★ ただし下記ルール 4 を見ること）

---

## 主要なルール

### ルール 1: 出所を格付けし、**一次資料まで降りる**

| 格 | 何 | 扱い |
|---|---|---|
| **一次** | コード / 設定ファイル / 実行ログ / 実測値 / CI の実際の run | ★ **これだけが根拠になる** |
| 二次 | docs / README / コメント | **主張ではなく仮説**。一次と食い違ったら一次が正 |
| 三次 | memory / 過去の steering / 引き継ぎ / **自分の以前の発言** | ★ **根拠にしてはならない**。当たりを付けるためだけに使う |

> ⚠️ ★ **memory は「書かれた時点の真実」であって現在の真実ではない。**
> 実例: 「private repo は Actions 分数枯渇で即 fail する」という memory を根拠に CI を説明したが、
> `ci.yml` は **2026-08-01 に macOS を self-hosted へ移していた**（`runs-on: [self-hosted, gse-mac]`）。
> 1 行 grep すれば分かることを、記憶で答えて誤情報を出した。

### ルール 2: 「不要 / 冗長 / 使われていない」と言う前に **消費者を探す**

★ **生産者側だけ見て「重複だから不要」と言わない。** そのファイル・バイナリ・設定を
**誰が読む / 実行する / ダウンロードするか**を grep で洗い出す。

```bash
# 例: あるバイナリを消してよいか
grep -rn "gse-submit" --include='*.rs' --include='*.sh' --include='*.bat' \
  --include='*.command' --include='*.md' --include='*.yml' . | grep -v node_modules
```

> ⚠️ 実例: 「mac の `gse-submit` は dmg に同梱されているから冗長」と断定したが、
> `scripts/submit/提出する_mac.command` が **同じフォルダの `./gse-submit` を実行**しており、
> `docs/participant-setup-guide.md` の「方法2」がそれを案内していた。
> **`.app` の中身（生産者側）だけ確認して、ランチャと手順書（消費者側）を見ていなかった。**

**消費者の探し方**（どれか 1 つでは足りない）:
1. コードからの参照（`grep` — 拡張子を絞りすぎない。`.bat` / `.command` / `.yml` を忘れる）
2. **ドキュメントからの参照**（被験者・研究者への手順書は契約である）
3. CI / スクリプトからの参照
4. ★ **運用の実績**（下記ルール 3）

### ルール 3: ★ **実績 > 設計上の想定**

設計文書に「フォールバックとして用意した」と書いてあっても、
**実運用で使われなかったなら、それは実績として扱う**。

> 実例: 「方法2 は現役だから残すべき」と主張したが、研究者から
> 「Phase1 は Windows=`gse-next.exe`+`gse-submit.exe`、mac=dmg のみで完了した」という
> **実績**が示され、主張は否定された。★ **設計意図は実績に負ける。**

⚠️ 逆向きも成り立つ: **実績が無い＝安全**ではない。「まだ 1 回も走っていない経路」は
**壊れていることが判明していないだけ**である（例: `--verify-blocks` は P-1 が初実行）。
「実績が無い」ことを**明示する**（"未実行である" と書く）。

### ルール 4: ユーザーの指摘は **確認のきっかけ**であって、即座の同意でも反論でもない

- ユーザーが「〜では？」と言ったら、★ **まず一次資料を見に行く**。
- 一次資料が支持したら **明確に訂正する**（言い訳を足さない）。
- 一次資料が支持しなかったら **証拠を示して差し戻す**（黙って従うと実害が出る）。
  実例: 「Windows の `gse-submit.exe` も不要では」に対し、`lib.rs:845 run_submit_blocking` が
  **exe と同階層の `gse-submit.exe` を要求する**ことを示して差し戻した。削っていたら提出が壊れていた。

### ルール 5: 「赤になる / 緑になる」は **走らせてから言う**

チェックの結果を予測しない。`bash run.sh` / `--selftest` / `cargo test` を**実際に実行**して報告する。

> ⚠️ 実例: 引き継ぎメモは「`src-tauri/` に触るので `run.sh [5]` が赤になる」と書いていたが、
> 実体は `git status` を見るだけで **コミットした瞬間に黙って緑に戻る** silent pass だった。
> **予測を信じずに読んだから見つかった。**

### ルール 5b: ★ **検査を書いたら、検査自体を 3 状態で試す**

「正常なら緑」だけ試して満足しない。**正常 / 不在 / 壊れている**の 3 つを実際に作って通す。

> ⚠️ 実例（本 Skill 作成と同じセッションで 3 件出た）:
> 1. `--help` が **`ExitCode::from(1)`** を返す CLI に対し `if cmd --help; then OK` と書き、
>    **正常なバイナリを「実行できない」と誤判定**した（`unpack.rs` を読んで判明）。
> 2. 直したつもりで `cmd --help | grep -q usage` にしたら、**`set -o pipefail` 下では
>    `--help` の exit 1 がパイプライン全体を 1 にする**ため、また誤判定した。
>    → 出力を変数に取ってから中身を見る形に変えた。
> 3. ★ **検査結果の測り方自体を間違えた**: `script | tail -2; echo $?` は
>    **`tail` の終了コード**を見ていた。→ リダイレクトしてから `$?` を取る。

⚠️ ★ **「exit 0 なら成功」は前提であって事実ではない。** その CLI が何を返すかを**ソースで確かめる**。

### ルール 6: 主張を書いたら、**その主張を検査するものを一緒に置く**

docstring・README・事前登録に「〜しない」「〜である」と書いたら、
★ **それを検査する回帰テスト / grep / selftest を同じコミットで足す。**

- 例: 「条件ラベルを画面に出さない」→ 壊れた入力を複数通し、出力に禁止語が出ないことを selftest で固定
- 例: 「文書と実装は同じ版」→ `selftest` が `config.json` の `revision.version` と定数を突き合わせる
- ⚠️ ★ **その検査自体が空回りしていないか**も確かめる（「FAIL が 1 件も出ていなければ赤」を入れる）

### ルール 7: ★★★ 一次資料を **部分読み**で代表させない

★ **「一次資料に降りた」ことと「一次資料を読んだ」ことは別である。**
⚠️ 長い資料の **1 節だけ**読んで、その資料全体の立場を代表させない。

> ⚠️★★★ **実例（2026-09-13・ADR-030）**: `.idea` の文献サーヴェイ **551 行**のうち
> **§6.1（Tier 表・約 25 行）だけ**を読んで特徴量の枠を確定した。
> ★ 同じメモの **§3.2**（チャネルを増やしても効かない）/ **§4**（Tier ごとの証拠地図）/
> **§4.1**（強い反証 5 件）/ **§5**（方法論）/ **§17**（個人化・tuning の既存の実体名）が
> **設計判断を直接動かす内容**を持っていたのに、1 行も見ていなかった。
> ⚠️ 併記された 3 本目の一次資料（roadmap 356 行）は **一度も開かなかった**。

**手順**（★ 長い一次資料を引くとき）:

1. ★ **まず `grep -n "^## \|^### "` で見出しを全部出す。** ⚠️ 節を 1 つ名指しされても、他を見ないで済ませない。
2. ★ **「自分の結論に反する節」を先に探す**（⚠️ 反証・限界・未解決・却下の節）。
3. ★ **引用元の資料が複数指定されていたら、全部の見出しは見る**（★ 読む深さは配分してよい）。
4. ⚠️ **読んでいない範囲は「読んでいない」と書く**（★ 黙って代表させない）。

### ルール 8: ★★★ 「核心 / 本質を押さえた」と言う前に、**より広い版**を探す

⚠️ **狭い版の問題を解いて、広い版も解いたかのように書かない。**
★ 同じ語（循環・重複・漏れ・不整合…）で、**自分が解いたものより一段広い主張が資料に無いか**を必ず探す。

> ⚠️★★★ **実例（同日・同じ ADR）**: 「既存トリガは推定器の出力（`p_stuck`）を使うので **循環**する」と
> 指摘し、これを **「本 ADR の核心」**と自称した。
> ★ しかし同じ一次資料の別節が逐語で「**行動だけで criterion を作ると循環する**」と書いており、
> ⚠️ **自分が書いた定義（打鍵ログだけで作る）がまさにその広い版に該当していた。**
> → ★ **狭い循環を閉じて「核心」と称し、広い循環には触れていなかった。**

**手順**:

1. ★ 解いた問題を**一語で言い直す**（例: 「循環」）。
2. ★ その語で**一次資料を全文 grep する**（⚠️ 自分が読んだ節だけでなく）。
3. ★ 出てきた中に**自分の解より広い主張**があれば、**(a) 解く** か **(b) 限界として明記**する。
   ⚠️ **黙って狭い版だけを提示しない。**
4. ⚠️ **「核心」「本質」「これで閉じた」は、3 を通してからでないと書かない。**

## チェックリスト（断定の直前に通す）

- [ ] この主張の根拠は **一次資料**か？ memory / 過去の発言に頼っていないか
- [ ] 「不要」と言うなら、**消費者を grep で洗った**か（`.bat` / `.command` / `.yml` / docs を含めたか）
- [ ] **運用の実績**を確認したか（使われたのか / 一度も走っていないのか）
- [ ] チェックの結果を**予測**していないか（走らせたか）
- [ ] 削除・変更するなら、**それを参照している docs を同じ版に揃えた**か
- [ ] 新しく書いた主張に、**それを検査するもの**を付けたか
- [ ] 確認できていないことを「確認した」と書いていないか（**未確認は未確認と書く**）
- [ ] ★ 長い一次資料を **見出しレベルで一度見渡した**か（⚠️ 1 節だけで代表させていないか・ルール 7）
- [ ] ★ 「核心 / 閉じた」と書くなら、**同じ語でより広い主張が無いか全文 grep した**か（ルール 8）

## ⚠️ よくある抜け穴

| 抜け穴 | 直し方 |
|---|---|
| grep の拡張子を絞りすぎる | `.bat` `.command` `.ps1` `.yml` `.gs` `.md` を忘れない |
| 生産者側だけ見る | 「誰が使うか」を必ず 1 回は探す |
| docs を一次資料と誤認する | docs は**約束**であって実体ではない。実体はコード |
| 「たぶん動く」を「動く」と書く | 走らせる。走らせられないなら**そう書く** |
| ★ 指定された節だけ読んで資料全体を代表させる | **見出しを全部出す**。反証・限界・未解決の節を先に読む（ルール 7） |
| ★ 狭い版を解いて「核心」と称する | 解いた問題を**一語で言い直して全文 grep**（ルール 8） |
| ★ 新しい語を発明する | ⚠️ **資料に既に実体名があることが多い**（例: `warmup_count` を `n_min` と書いた）。**先に grep する** |
| ユーザーの発言を根拠に断定を上書きする | ユーザーの**実績報告**は一次資料。**推測**は仮説（区別する） |
