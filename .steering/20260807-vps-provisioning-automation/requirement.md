# Phase1.5 / Phase2 の課題ページ配布を随時自動化する（設計）

⚠️ ★ **このタスクは設計だけ**である。実装は Phase1.5 の着手時に別タスクで行う。

## 背景

G1（2026-08-07）で、被験者への配布は **半自動** までしか行けなかった。
詰まった場所は 3 つで、引き継ぎ (`_handoff/next-session-prompt-g1-provisioning-and-vps.md` §3) は
これをそのまま設計の出発点にせよと書いている。

| 段階 | G1 で詰まった理由 |
|---|---|
| 割付 (`assign.py`) | GAS は Python を実行できない。⚠️ JS で書き直すと**凍結された科学的手続きの実装が 2 つ**になる |
| Drive へ配置 | ローカルに Drive 資格情報が無い |
| ★ フォルダの共有 | ⚠️ **MCP に権限設定 API が無い**ので手作業（★ ここが実際に一番重い） |

★ **実測の重さ**: 2026-08-07 時点で、被験者 15 人ぶんの配布に要る人手は
「Drive へドラッグ 1 回」＋「**フォルダを 1 つずつ共有 15 回**」である。
⚠️ 共有は 1 回でも取り違えると `decisions.md` D-7 の fail-open（親を共有 → 全被験者分が見える）に
直結するので、回数がそのまま事故確率になる。

★ 割付が決定的であることは実測済み（`SEED` + P-ID の純関数。P001 を再生成して byte 一致を確認）。
→ ⚠️ **「先に用意する」と「登録後に用意する」で結果は一致する。** 自動化しても科学的な差は生じない。

## ゴール

Phase1.5 / Phase2 で、**被験者が登録してから課題ページが手元に届くまでに人手が挟まらない**こと。
具体的には次の 4 つが人手ゼロで回ること:

1. その P-ID の割付を **`assign.py` そのもの**で作る（★ 実装を 2 つにしない）
2. 課題ページを生成して Drive の被験者別フォルダへ置く
3. ★ **そのフォルダだけ**を「リンクを知っている全員（閲覧者）」にする
4. 上げたものを **byte で照合**し、⚠️ 合わなければ**共有しない・URL を出さない**

## スコープ

### 含むもの
- 資格情報の種類と置き場（★ どの OAuth スコープで、誰として動くか）
- 起動方式（★ 登録に同期して叩くのか、定期的に収束させるのか）
- 冪等性と fail-closed の規律（⚠️ 既存の割付を上書きしない・照合が赤なら共有しない）
- ★ VPS が本当に要る境目はどこか（＝ 段階分け）

### 含まないもの
- ⚠️ **アプリのビルド**。配るのは CI のリリース成果物だけ（`build-ci-and-pilot-distribution`）
- ⚠️ 受け口 (`GSE_G1_Submit.gs`) の変更。あれは `.age` の受領であって配布ではない
- ⚠️ `preregistration.md §3.1/§3.2/§3.4/§3.5/§3.6` の変更
- ⚠️ `schema_dto.rs` の変更
- G1 本番の運用そのもの（★ G1 は今回作った `prepare-subjects.sh` ＋ 手作業で回す）

## 受け入れ条件（設計として）

- [ ] ★ 「VPS が要る理由」が、詰まり 3 つのうち**どれに効くか**で説明されている
      （⚠️ 3 つ全部を VPS のせいにしない）
- [ ] 割付の実装が 1 つのままである道筋が示されている
- [ ] ⚠️ 共有が**フォルダ単位**であり、親を継承させる設計に戻っていない
- [ ] ⚠️ 検証が赤のときに**配らない**経路が設計に含まれている
- [ ] 資格情報の種類が、**個人 Gmail アカウントで実際に成立する**方式で選ばれている
      （★ ここは引き継ぎの前提を 1 つ訂正している。`design.md` D-2 参照）
- [ ] ★ 実装前に潰すべき**未検証の前提**が spike として列挙されている
