# 設計判断 — 課題ページ配布の随時自動化

## D-1: VPS は「随時性」だけを買う。手作業 15 回を消すのは資格情報である

**判断**: Stage 1（ローカル + Drive API）と Stage 2（VPS で収束器）に割り、**Stage 1 を先に出す**。

**根拠**: 引き継ぎが挙げた 3 つの詰まり（Python が動かない / 資格情報が無い / 権限 API が無い）を
1 つずつ見ると、⚠️ **VPS が効くのは 1 つも無い**。Python は研究者の Mac で今日実際に動いた
（`prepare-subjects.sh` が 15 人ぶんを生成した）。資格情報と `permissions.create` は場所を問わない。
VPS が足すのは「研究者の Mac が落ちていても動く」ことだけである。

**⚠️ 却下した案**: 「まず VPS を立てて全部そこに寄せる」。
★ 一番重い手作業（共有 15 回）の解決が、一番重いインフラ作業に人質に取られる。

## D-2: サービスアカウントではなく OAuth ユーザー資格情報を使う

**判断**: インストール済みアプリの OAuth（リフレッシュトークン）で **研究者本人として**動かす。
スコープは `drive.file` を第一候補にする。

**根拠**: ⚠️ ★ 引き継ぎの「サービスアカウントで API 直叩き」は**個人 Gmail では素直に成立しない**。
サービスアカウントが作ったファイルはサービスアカウントが所有し、
共有ドライブ（Google Workspace の機能）の外では容量を持たない。
`mmiura.network@gmail.com` は consumer アカウントなので、共有ドライブもドメイン全体の委任も使えない。

**⚠️ 引き継ぎとの差分**: ここは引き継ぎの前提を**訂正している**。
★ ただし方向（API を直に叩く・`permissions.create` で共有を自動化する）は変えていない。

**★ 残る不確かさ**: `drive.file` が「アプリが作っていない既存の親フォルダの下に子を作る」ことを
許すかどうかを実測していない（`design.md` spike-1）。⚠️ ここは推測のまま実装に入らない。

## D-3: 登録に同期して叩かない（push でなく収束器）

**判断**: 5 分周期の収束器が「ロスターの全 P-ID ＋ 次の K 人」を用意済みの状態へ寄せる。

**根拠**:
1. ⚠️ 配布処理（10 枚のアップロード＋権限設定）を登録の応答時間にぶら下げると、
   タイムアウトで **「登録は済んだのにフォルダは無い」** という最も直りにくい中間状態が残る。
2. ★ 収束器は冪等が構造で保証される。2 回叩かれても・途中で落ちても次の周回で正しい状態へ寄る。
3. ⚠️★★ **（撤回）「共有を誤って外した場合に自己修復する」を利点として挙げていたが、これは危険だった。**
   → D-7 を参照。desired state に「非共有」を表現できるようにするまで、収束器で共有を管理してはならない。
4. ★★ **GAS を 1 行も変えずに済む。** `g1MaterialsUrlForPid_` は親の下から
   **名前 (P-ID) で引く**設計で、誰が置いたかを問わない。
   ⚠️ この疎結合は 2026-08-07 に偶然そうなったのではなく、
   「研究者が先回りして置いておけば 1 通で渡せる」という設計判断（`Form_G1/README.md`）の帰結である。
   ★ 自動化はその「先回りする人」を機械に置き換えるだけになる。

**⚠️ 却下した案**: `onG1ConsentSubmit` から VPS を叩いて URL を受け取る。
★ 一見「完全 on-demand」に見えるが、上の 1 の中間状態を作る。

## D-4: 照合が緑になるまで共有しない（★ 順序を逆にしない）

**判断**: `permissions.create` は **byte 照合が通ったあとにだけ**呼ぶ。

**根拠**: ⚠️ 共有を先にすると、壊れたページ・別人のページが**見える状態**で存在する時間ができる。
★ Drive は更新・削除の取り返しがつきにくいので、この窓を作らない。
`verify-drive-upload.py` の rc=1 が「配らない」に直結する現行の規律をそのまま持ち越す。

**★ テストで守る**: 「照合が赤 → 共有まで進まない」を単体テストの本丸に置く（`design.md` テスト戦略）。

## D-5: 手作業版のスクリプトを消さない

**判断**: `prepare-subjects.sh` / `make-upload-manifest.sh` / `verify-drive-upload.py` を残す。

**根拠**: ★ 資格情報が失効した・ネットワークが無い・Drive API が塞がれた、のいずれでも
**被験者に配れる退路**が要る。⚠️ さらに `verify-drive-upload.py` は `provision.py` の照合ロジックの
**正解（参照実装）**でもあり、両者の食い違いはバグの検出になる。

## D-6: 自動化を G1 本番に差し込まない

**判断**: G1 は今日作った半自動版（`prepare-subjects.sh` ＋ 手作業のドラッグと共有）で最後まで回す。

**根拠**: ⚠️ 実施の途中で経路を変えると、割付の来歴が「手作業ぶん」と「自動ぶん」に分かれる。
★ 割付は決定的なので**結果は同じ**だが、`reproducibility-discipline` の観点では
「どちらの経路で作ったか」が記録に残らないほうが問題である。

## ⚠️★★ D-7: 収束器の desired state に「非共有」を表現できるようにする（同意撤回の担保）

**判断**: 収束器は「共有されている」を唯一の正としない。★ **対象から外す宣言**（ロスターの
`撤回/除外` 列 / `blocks/<ID>.json` の tombstone）を入力に持ち、それが立っていたら
**共有を外した状態へ寄せる**。表現できない状態は収束器で管理しない。

**根拠（⚠️ D-3 の根拠③として書いた「自己修復」を撤回する）**:
初版の設計は「共有を誤って外しても次の周回で戻る」を**利点**として挙げていた。
⚠️ しかしこれは、**研究者が意図して共有を外す**経路をまるごと潰す:

- 被験者が**同意を撤回**した（`consent.md` はいつでも撤回できると約束している）
- 誤った相手にリンクを配ってしまい**緊急に止めたい**
- 実施が終わったので**公開を畳みたい**

いずれの場合も、研究者が Drive で共有を外す → ★ **5 分後に `permissions.create(type=anyone)`
で再公開される**。⚠️ しかも `checkMaterialsProvisioning()` は「共有済み = ✅」と読むので、
**緑に見える**。人が止める手段が設計に無かった。

★ 一般化: **収束器は「あるべき状態」を宣言できる範囲でしか使ってはならない。**
「止めたい」を宣言できないなら、その軸は収束器の管轄外である。

**⚠️ 実装時に必ず**: 撤回フラグが立った P-ID について「共有が外れていること」を
確かめるテストを、共有する側のテストと**対にして**書く（片側だけだと fail-open に気づけない）。

## D-8: VPS には P-ID しか渡さない（実名↔メール対応表を到達範囲に置かない）

**判断**: 収束器の入力は **P-ID の配列だけ**。Sheets API でロスターを直接読まない。
GAS が `g1RosterParticipantIds_()` の出力だけを書いた JSON（または専用シート）を経由させる。

**根拠**: ⚠️ Phase1 の「参加者ロスター」は **氏名・メール** の列を持つ（実名↔P-ID 対応表そのもの）。
VPS に置く長命リフレッシュトークンに Sheets スコープを与えると、
★ **VPS の侵害 = `data-privacy` の「実名↔P-ID 対応表」と「実アドレス」の漏洩**になる。
さらに Sheets スコープは `drive.file`（非機微）では読めないので、
⚠️ D-2 が売りにしたスコープの狭さが実装時に**必ず**崩れる。

★ 初版は `decisions.md`「未決」に正しい代案を書きながら、
**`design.md` 本文は Sheets API 前提のまま**だった。⚠️ 実装者が読むのは本文である。
→ 未決に置かず、ここで確定させる。
