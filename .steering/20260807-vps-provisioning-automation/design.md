# 設計 — 課題ページ配布の随時自動化

## ★★ 核心の見立て（⚠️ 引き継ぎの前提を 1 つ組み替えている）

引き継ぎは 3 つの詰まりを **VPS で解く**と書いている。⚠️ しかし詰まりを 1 つずつ見ると、
**VPS が効くのは 1 つだけ**である。

| 詰まり | 本当に足りないもの | VPS が要るか |
|---|---|---|
| GAS は Python を実行できない | ★ **Python が動く場所**。研究者の Mac で `assign.py` は今日実際に動いた | ❌ 要らない |
| ローカルに Drive 資格情報が無い | ★ **Drive API の資格情報**。取れば Mac からでも叩ける | ❌ 要らない |
| MCP に権限設定 API が無い | ★ **Drive API の `permissions.create`**。資格情報があれば呼べる | ❌ 要らない |
| （引き継ぎに書かれていない 4 つ目）**研究者の Mac は常時起動していない** | ★ **常時動く場所** | ✅ **ここだけ** |

→ ★ **VPS が足すのは「随時性」だけ**である。**手作業 15 回を消すのは資格情報**であって VPS ではない。
⚠️ ここを取り違えると、VPS を立てるまで手作業が続く（＝ 一番重い部分の解決が最も遠い依存に人質に取られる）。

## 実装アプローチ — 2 段階に割る

### Stage 1: `provision.py`（★ 研究者の Mac で動く。VPS 不要）

```
provision.py --range P006 P020
  1. blocks/<ID>.json が無ければ assign.py --json で作る（★ 有れば触らない）
  2. validate_blocks.py（⚠️ 赤なら 1 枚も上げない）
  3. build_task_pages.py
  4. Drive: 親の下に <ID> フォルダを作る（無ければ）
  5. Drive: blockNN.html を上げる（⚠️ 既にあれば byte を見て、違えば消してから上げ直す）
  6. ★ 照合（Drive の fileSize vs 手元）— ⚠️ 赤ならここで止まる
  7. ★ 緑のときだけ そのフォルダに permissions.create (type=anyone, role=reader)
```

★ 1〜3 は **`prepare-subjects.sh` と同じ規律**（既存の割付を上書きしない・validate が赤なら作らない）を
Python に移すだけである。⚠️ 4〜7 が新しい部分。

**これだけで手作業 15 回が 0 回になる。** ⚠️ 随時性は無い（研究者が叩いたときに動く）。

### Stage 2: 同じ `provision.py` を VPS に置き、**収束器 (reconciler) として回す**

```
5 分ごと:
  ロスターを読む（Sheets API）
  → 実在する全 P-ID ＋ 次の K 人 について、
     フォルダが「ある・中身が合っている・共有されている」状態へ寄せる
  → 既にその状態なら何もしない
```

⚠️ ★ **登録リクエストに同期して叩く設計（push）を採らない。** 理由:

1. ★ **応答時間に配布処理をぶら下げない。** 10 枚のアップロード＋権限設定は数秒〜十数秒かかる。
   ⚠️ GAS の `UrlFetchApp` がタイムアウトすると、**登録は済んだのにフォルダは無い**という
   一番始末の悪い中間状態が残る。
2. ★ **冪等が構造で保証される。** 収束器は「あるべき状態」を宣言するだけなので、
   2 回叩かれても・途中で落ちても、次の周回で正しい状態に寄る。
3. ★ **自己修復する。** 共有を誤って外した／フォルダを消した、が次の周回で戻る。
4. ★★ **GAS を 1 行も変えずに済む。** 既存の `g1MaterialsUrlForPid_` は
   **親の下から名前 (P-ID) でフォルダを引く**設計であり、誰が置いたかを問わない。
   さらに `g1MaterialsFolderProblem_`（ガード 7）が「親の下にあるか・名前が一致するか・
   共有されているか」を送信前に確かめる。⚠️ **配布側と送信側が既に疎結合になっている。**

★ 「収束器」は本プロジェクトの既存語彙である（`src-tauri/src/reconcile.rs` が
`.age` の再送・取りこぼし回収を同じ形でやっている）。⚠️ 新しい概念を持ち込まない。

## ⚠️★ 資格情報 — 引き継ぎの「サービスアカウント」を訂正する

引き継ぎ §3 は「サービスアカウントで API 直叩き」と書いている。
⚠️ ★ **個人 Gmail (`mmiura.network@gmail.com`) では、この方式は素直に成立しない。**

- サービスアカウントが作ったファイルは **サービスアカウント自身が所有者**になる。
- ⚠️ サービスアカウントは（Workspace の共有ドライブの外では）**自分の Drive 容量を持たない**。
- 回避策の「共有ドライブ」「ドメイン全体の委任」は **Google Workspace の機能**であり、
  個人 Gmail では使えない。

→ ★ **OAuth のユーザー資格情報（インストール済みアプリ + リフレッシュトークン）を使う。**
研究者本人として動くので、所有者も容量も研究者のものになり、既存フォルダの構造をそのまま使える。

**スコープは `https://www.googleapis.com/auth/drive.file` を第一候補にする。**
★ 「このアプリが作った・開いたファイルだけ」に限られる非機微スコープなので、
⚠️ 資格情報が漏れても **研究者の Drive 全体は読まれない**。
（`drive` フルスコープは機微スコープで、審査と 7 日でのトークン失効の話がついて回る。）

⚠️ ★ **未検証の前提** → 下の spike-1 で潰す。

## 影響範囲

- ★ 被験者から見た体験は**変わらない**（同じ URL・同じ 1 通のメール）。
- ★ 割付の科学的手続きは**変わらない**。`assign.py` と `SEED` を触らない。
  ⚠️ 決定的なので、手作業で作った既存の `blocks/<ID>.json` と自動生成分は一致する（実測済み）。
- ⚠️ **G1 本番には入れない。** G1 は今日の半自動版で回す。
  ★ 自動化を実施中に差し込むと、割付の来歴が「手作業ぶん」と「自動ぶん」で分かれる。

## 既存パターンとの整合性

- ★ **fail-closed**: `make-distribution.sh` / `make-common-app-zip.sh` / `prepare-subjects.sh` と同じく、
  「作らずに止まる・赤なら配らない」を守る。⚠️ 「とりあえず上げて後で直す」をしない
  （Drive の更新・削除は取り返しがつきにくい）。
- ★ **上げたら照合する**: `verify-drive-upload.py` のロジックをそのまま関数として持つ。
  ⚠️ 照合は **名前 + byte 数**まで。★ SHA まで確かめたことにしない（Drive の一覧は
  `fileSize` しか返さない — 2026-08-07 に実測）。
- ★ **収束器**: `reconcile.rs` と同じ「宣言した状態へ寄せる」形。

## テスト戦略

- **単体**: `drive_client.py` を偽 API（`prepare-subjects.sh` のテストと同じく、応答を差し替える）で
  ⚠️ **陽性対照込み**で回す。★ 「全部止める」ガードが緑にならないようにする。
  - 正常: 15 人ぶんが作られ、共有され、照合が緑
  - ★ 照合が赤: **共有まで進まない**（⚠️ ここが本丸。順序が逆だと fail-open）
  - 既に正しい状態: **API 呼び出しが 0 回**（冪等）
  - 部分アップロード（8/10 枚）: 赤で止まり、共有しない
  - ⚠️ 別被験者のページが紛れている: 「余分」で赤
  - 権限設定だけ失敗: 次の周回で回復する
- **統合（spike）**: 実 Drive の**捨てフォルダ**に対して 1 人ぶんを通す。
  ⚠️ 本番の親フォルダで試さない。
- **回帰**: `node Form_G1/materials_autosend_test.cjs`（★ GAS を変えないので落ちないはず＝
  落ちたら「変えないつもりで変えた」ことの検出になる）。

## ⚠️★ 実装前に潰す spike（★ ここが未検証の前提）

| # | 確かめること | 外れたときの代替 |
|---|---|---|
| spike-1 | ★ `drive.file` スコープで、**アプリが作っていない既存の親フォルダの下に**子フォルダを作れるか | 作れなければ ★ **親フォルダもアプリに作らせる**（新しい親を 1 つ作り、以後その配下で完結させる）。⚠️ 親は制限付きのままにする |
| spike-2 | `permissions.create(type=anyone, role=reader)` が個人 Gmail の Drive で通るか（組織ポリシーで塞がれていないか） | 塞がれていれば ★ **被験者のメールアドレス個別共有** (`type=user`) に落とす。⚠️ 匿名性の設計に影響するので `data-privacy` を先に読む |
| spike-3 | リフレッシュトークンが**何日もつか**（公開状態が「本番」なら無期限のはず） | 短命なら ★ 失効を**検出して止める**（⚠️ 黙って共有せずに進まない）＋ 研究者へ通知 |
| spike-4 | Drive にアップロードした HTML が **`text/html` のまま**で、Google 形式に変換されないか | ★ 既に実測で対策済み（`disableConversionToGoogleType`）。API 側の同等指定を確かめる |

## ⚠️★ 設計に持ち込んではいけないもの（引き継ぎ §3 より・全部そのまま生きている）

1. ★ 割付を「梱包のついでに」走らせない。⚠️ 取り違えると「同じ人に 2 通りの割付」が黙って生まれる
2. ★ アプリを手元／VPS でビルドしない。配るのは CI のリリース成果物だけ
3. ⚠️ `g1-submit.json`（共有シークレット）を public な場所・追跡ファイルに置かない
4. ⚠️ NDJSON 生ログ・キーストローク内容を外部へ送らない（`data-privacy`）
5. ★ 親フォルダを共有にして継承させる設計へ戻さない（D-7 の fail-open）
