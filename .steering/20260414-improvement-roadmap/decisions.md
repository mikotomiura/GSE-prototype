# 重要な設計判断の記録

本ロードマップ策定過程での主要な判断と根拠を記録する。

---

## 判断 1: /reimagine プロセスを適用した

**判断**: 単純な技術改善ロードマップ作成であっても、`/reimagine` の「破壊と構築」プロセスを挟み、v1 / v2 / 採用版（ハイブリッド）の 3 段構成で意思決定した。

**根拠**:
- 元ロードマップ（`GSE_改善分析_開発ロードマップ.md`）は筆者自身の思考の延長にあり、確証バイアスが入る恐れがあった
- v1 を先に書いた時点で「基盤先行」という教科書的切り方に流れていた
- v2 を独立生成したことで「介入価値駆動」「リプレイ CLI を背骨に」という別軸の最適解が浮上した
- 両者の強みを統合したハイブリッドがどちらの単独案よりも強い結果になった

**影響**: Phase 0 の中心がテスト基盤からリプレイ CLI に移り、工数対効果が改善した。

---

## 判断 2: セッションリプレイ CLI をテスト基盤の中心に据えた

**判断**: ユニットテスト / 統合テスト / 回帰テスト / GT 評価 / パラメータチューニング / リグレッション検知を **リプレイ CLI 1 本で兼ねる** 設計とした。

**根拠**:
- 単一ユーザー（開発者自身）用プロトタイプでは、本格的なテストピラミッドは費用対効果が悪い
- ゴールデン NDJSON → `FeatSnapshot` の byte-equal 比較が、実質的にすべての回帰保護を提供する
- GT 評価（混同行列）も同じ CLI の別サブコマンドで実現できる
- `analysis/` モジュールが Tauri 依存を持たない純粋 Rust であることが、この設計を容易にしている

**代替案**: 伝統的なユニットテスト + 統合テスト + E2E テスト の 3 層構造。
**却下理由**: テスト実装の工数が大きく、リプレイ CLI の方が包括的。ただし薄いユニット層は併存させる（原則 B）。

---

## 判断 3: 沈黙パスの二重構造を統一しない

**判断**: `lib.rs:662-667`（バッファあり沈黙パス: F6 開始 8s / F3 開始 10s）と `features.rs:242-251`（合成パス: F6 開始 10s / F3 開始 15s）の閾値差を **統一せず、明示的な 3 状態機構（Typing / Transition / Silence）としてコメントリネーム + `docs/architecture.md` で文書化** にとどめる。

**根拠**:
- 統一リファクタは新バグを生むリスクが、統合による保守利益を上回る
- 既に動作しているゴールデン挙動があり、統一による微妙な挙動変化が意図通りか検証困難
- 「3 状態」として明示化すれば可読性の問題は解決し、意図も伝わる
- コード削減自体を目的化しない

**代替案**: 共通ヘルパー関数への抽出。
**却下理由**: 各パスは EWMA α の扱い（`update` vs `update_silence`）と F5 加算タイミングも異なる。抽出しても条件分岐だらけの関数になり、可読性は改善しない。

---

## 判断 4: パラメータ外部化を却下

**判断**: 遷移行列・放出行列・β 値・EWMA α 等を JSON/TOML 等の外部ファイルに出さず、Rust 定数のまま維持する。代わりに `// TUNE:` マーカーコメントで全チューニング箇所を grep 可能にする。

**根拠**:
- GSE は単一ユーザー向けプロトタイプ。外部化で読み書きするのは同じ人間
- Rust 定数は型安全 + コメント併記 + Git 履歴でトレーサビリティ十分
- 外部化するとパースエラーハンドリングや整合性チェックのコードを自前で書く必要がある
- 外部化の唯一の正当な動機（ML 重みとの統一管理）は、LR 重みを Rust 定数として手貼りすることで消える

**代替案**: TOML 設定ファイルからの読み込み。
**却下理由**: 純損失。Rust コンパイルは速く（`cargo check` は秒単位）、開発フローで再コンパイルが大きな摩擦にならない。

---

## 判断 5: Synthetic Friction の閾値判定を φ 正規化後の値で行う

**判断**: 元ロードマップが提案した「F3 ≥ 0.15 かつ F6 ≥ 0.15」の生値閾値を **φ 正規化後の値**（`φ(F3) ≥ 0.30` かつ `φ(F6) ≥ 0.20`）に変更して採用する。

**根拠**:
- 生値 0.15 は β 依存の意味を持ち、β_coding（0.06/0.08）と β_writing（0.10/0.12）でゲート挙動が大きく異なる
  - β_coding 下では F3=0.15 → φ=0.75（ほぼ発動しない）
  - β_writing 下では F3=0.15 → φ=0.25（頻繁に発動）
- φ 正規化後は「相対摩擦度」として意味が一貫する
- 閾値の絶対値（0.30 / 0.20）は Phase 1 の GT データで校正する（提案値は初期値）

**代替案**: 生値のまま β ごとに異なる閾値を用意する。
**却下理由**: パラメータが倍増し保守コストが上がる。φ 正規化で自動スケールする設計の方がシンプル。

---

## 判断 6: LR を「入れる / 入れない」の判断ゲートとして Phase 3 を定義

**判断**: Phase 3 は「LR を導入する Phase」ではなく **「LR を導入すべきかデータで判断する Phase」** と定義。No-Go（入れない）判断も正当な成果として扱う。

**根拠**:
- データ量が 50 セッション程度では LR の改善幅が 5% 前後に留まる可能性が高い
- 「LR 統合」というタスクを先に決めてから判定するのは確証バイアス
- 「HMM のみで十分」という結論は学術的にも未踏提案的にも価値がある
- HMM と LR を AND で組み合わせる（置換ではなく補強）設計により、Go の場合もリスクを抑制

**代替案**: LR 統合を前提に設計。
**却下理由**: データが示す結論と設計意図が食い違った場合、設計を捨てるコストが大きい。判断ゲートとして設計することで、どちらの結論でも無駄にならない。

---

## 判断 7: XGBoost / CNN 段階をスコープ外とした

**判断**: 元ロードマップの Stage 3 (XGBoost) / Stage 4 (1D-CNN/TCN) を本ロードマップから **完全に除外**。

**根拠**:
- 100-500 セッションではツリーアンサンブル / CNN の過学習リスクが大きい
- Rust へのデプロイ手段が確立されていない（`xgboost-rs` はメンテ停止、ONNX Runtime は ~50MB で過剰）
- LR で効果が出なければ、より複雑なモデルで効果が出る保証もない
- 「Stage 4 のために今年中に生イベント列フォーマットを確定」というロードマップ記載の準備作業は妥当だが、実装は 500+ セッション蓄積後

**代替案**: Phase 4 以降のオプション Phase として残す。
**却下理由**: ロードマップに残すと「やるべきタスク」として認識され、優先順位を歪める。「今はやらない」と明示した方が焦点が絞れる。

---

## 判断 8: Lv3 Thought Scaffold を Phase 4 に残した（v2 と異なる選択）

**判断**: v2 は Lv3 をスコープ外にしたが、ハイブリッドでは Phase 4 として残す。ただし **前提条件として「Phase 2a で Stuck precision 改善が確認されている」** を置く。

**根拠**:
- 介入の多段性（Lv1 → Lv2 → Lv3）は GSE の核心的なコンセプト設計
- 固定テキスト 20 問は純フロントエンドで実装コストが小さい（S 規模）
- 未踏 2027 提案で「介入の多段性」を見せる材料として有用
- 「precision が上がる前に介入種類を増やさない」という v2 の懸念は、前提条件で緩和できる

**代替案**: v2 通りスコープ外。
**却下理由**: Lv3 の実装コスト自体は小さく、前提条件を満たせば十分な価値がある。

## 判断 9: 遡及ラベリング UI を Phase 1 で作らない（v2 の選択を採用）

**判断**: 元ロードマップの GT Level 1（遡及ラベリング）を Phase 1 では実装せず、リアルタイム GT ボタンのみを先行。

**根拠**:
- 遡及ラベリングには記憶バイアスが入る
- 専用 UI（タイムライン表示 + 区間選択）の実装コストが大きい
- リアルタイム GT で十分なデータが集まる可能性が高い
- NDJSON を直接目視する方が早い場合が多い

**代替案**: Phase 1 で両方実装。
**却下理由**: 工数対効果が悪い。Phase 1 完了時点で再評価する。

## 判断 10: macOS の IME 追加特徴量を明示的に保留

**判断**: Phase 2b の IME Shadow Features は Windows のみ実装し、macOS は明示的に保留する。

**根拠**:
- macOS の IME 状態取得は TCC 権限・GCD dispatch_sync 制約があり実装コストが大きい
- Phase 2b はシャドーモードでデータ収集のみ。まず Windows で価値を検証してから macOS に展開するのが合理的
- Phase 3 の LR で IME 特徴量に価値があると判明したら、そこで初めて macOS 版の優先度が上がる

**代替案**: クロスプラットフォーム完全性のため両方実装。
**却下理由**: 価値未証明段階で両プラットフォームに工数を使うのは非効率。

## 判断 11: EWMA α 系定数をモジュール定数として抽出しない（2026-04-14 追記）

**判断**: `EWMA_ALPHA_NORMAL = 0.3` / `EWMA_ALPHA_SILENCE_EARLY = 0.15` / `HYSTERESIS_ALPHA_NORMAL = 0.40` 等、compute 経路で使用される α 系の値を**モジュール定数として抽出しない**。`// TUNE:` マーカーコメントでの列挙可能性のみ確保する。

**根拠**:
- IEEE 754 浮動小数点演算で `1.0 - 0.3 ≠ 0.7`（bit パターンが異なる）。
  - 実測: `0.3` の IEEE 754 表現は `0.2999999999999999888977...`、`1.0 - 0.3 = 0.7000000000000000111...`、リテラル `0.7` は `0.6999999999999999555...`
- `0.3 * raw + 0.7 * prev` を `ALPHA * raw + (1.0 - ALPHA) * prev` に置換すると、compute 経路の結果が ULP レベルで変わる
- GSE はゴールデンセッションログとの byte-equal 比較を Phase 0 の回帰保護の中心に据える（原則 A: Replay-as-Truth）設計
- リファクタで浮動小数点結果がずれると、すべてのゴールデンスナップショットが失効する
- `// TUNE:` マーカーでの grep 可能性が確保されれば、実用上「チューニングポイントを列挙する」目的は達成される

**代替案**: `const ALPHA: f64 = 0.3; ewma = ALPHA * raw + (1.0 - ALPHA) * prev;` と書く（抽出）。
**却下理由**: bit 非同値性により既存挙動が変わる。リファクタの「振る舞い保存」原則に反する。

**影響範囲**:
- 抽出した定数: `INITIAL_PROBS` / `INITIAL_AXES_EWMA` / `BACKSPACE_PENALTY_THRESHOLD`（いずれもリテラル assignment で bit 同値を保証）
- 抽出しなかった定数: 通常 EWMA α=0.3、沈黙 EWMA α=0.15/0.18/0.25、ヒステリシス α=0.40/0.60
- 方針は `engine.rs` 冒頭のヘッダコメントに明文化済み

## 判断 12: loop_step.rs は analysis/ → logger 依存を避け、中立記録型を返す（2026-04-15 追記）

**判断**: P0-1 `analysis/loop_step.rs` の `StepOutput` は `logger::LogEntry` を直接含めず、`KeyRecord` / `FeatSnapshot` / `ImeStateRecord` の中立な記録型ベクタを返す。`lib.rs` 側で `LogEntry` へ変換して送信する。

**根拠**:
- `architecture-rules` ルール 6「循環参照禁止」: 依存方向は `lib.rs → analysis` / `lib.rs → logger` の Y 字で、`analysis → logger` は禁止。
- design.md §0.1 の当初案 `log_entries: Vec<LogEntry>` はこのルールに抵触する。
- 中立記録型は `gse-replay` CLI (P0-4) でも直接再利用でき、`logger::LogEntry` への依存を replay 側でも避けられる。
- `FeatSnapshot` はゴールデンスナップショット (P0-10) の JSON 比較対象にもなるため、`serde::Serialize` を付与できる位置（`analysis/`）に置くほうが自然。

**代替案**: `LogEntry` を `logger` から `lib.rs` 直下もしくは新規 `types` モジュールに移す。
**却下理由**: 既存コード広域への破壊的変更。中立記録型を別建てする方が局所的。

## 判断 13: step() は Instant を捨て u64 ms で時刻管理する（2026-04-15 追記）

**判断**: `AnalysisState` は `last_event_time_ms: u64` / `next_engine_update_ms: u64` を持ち、`step(..., now_ms: u64, ...)` として呼び出す。`lib.rs` 側は `Instant` 基準時刻を保持し差分を ms に変換する。

**根拠**:
- P0-4 `gse-replay` CLI は NDJSON の `t` (ms) しか持たず、`Instant` を再現できない。replay と production で同一の時刻表現を使うのが原則 A (Replay-as-Truth) の要請。
- `elapsed() > Duration::from_secs(10)` の境界は ms 精度で等価 (`diff_ms > 10_000`)。
- `as_secs_f64()` は `(diff_ms as f64) / 1000.0` で再現可能。サブ ms 誤差は存在するが、P0-10 でスナップショットを新規生成するため既存挙動との byte-equal 問題は発生しない（新しい baseline として固定される）。

**代替案**: `now: Instant` をそのまま渡し、ms 変換は LogEntry::Feat の timestamp 生成のみに限定 (impact-analyzer 推奨案)。
**却下理由**: replay 側が Instant を合成できないため、production コードと replay コードで時刻計算経路が分岐する。これはまさに loop_step 抽出の目的（同一関数で動かす）を損なう。

## 判断 14: AnalysisState.pressed_keys は cross-platform で保持する（2026-04-15 追記）

**判断**: Windows 専用のキーリピート検出に使う `pressed_keys: HashSet<u32>` を、`AnalysisState` のフィールドとしては `#[cfg(target_os = "windows")]` を付けず全プラットフォームで保持する。使用する分岐（Press/Release での insert/remove）のみ `#[cfg(windows)]` でガードする。

**根拠**:
- `#[cfg(...)]` をフィールドに付けると、構造体コンストラクタ・mem::take・Debug 実装・テストコードの各所で `#[cfg]` 分岐が必要になり、cfg 伝播の破綻でコンパイルエラーが頻出する（impact-analyzer リスク 3）。
- 未使用 `HashSet` のメモリオーバーヘッドは数十バイトで無視できる。
- `gse-replay` CLI は OS に依存せず同じ state 型を使えるため、replay 再現性の観点でもメリットがある。

**代替案**: `#[cfg(target_os = "windows")] pub pressed_keys: HashSet<u32>` のフィールド cfg 分岐。
**却下理由**: 保守負荷が大きい割に得るものが少ない（数十バイトのメモリ節約）。

## 判断 15: code-reviewer HIGH 2 件のうち 1 件を意図的に適用しない（2026-04-15 追記）

**判断**: P0-1/P0-2 リファクタ後の code-reviewer レビューで以下 2 件の HIGH 指摘を受けた:

1. `lib.rs` の `now_ms()` 呼び出しを `tick_now` 変数化する → **適用した**（コスメ改善）
2. `step()` が `input=None + gate 未到達` で busy-wait する可能性 → **適用しない**

HIGH 2 を適用しない根拠:
- `crossbeam_channel::recv_timeout(Err(Timeout))` は指定した timeout の全期間を必ず待機してから返る（spurious wakeup なし）。
- そのため `input=None` が返った時点で `now_ms ≈ current + remaining_ms = next_engine_update_ms`。`step()` 内の gate 条件 `now_ms < next_engine_update_ms` は false となり、gate は必ず発火する。
- 「input=None + gate 未到達」という組合せは発生しない。busy-wait リスクは理論上存在しない。
- 旧コードは `timeout.max(Duration::from_millis(1))` で下限 1ms を設定しており、新コードも同じ。振る舞い等価。

レビュアーの推奨案（`max(5)` への引き上げ）を適用すると latency 特性が変わり、「振る舞い不変」のリファクタ原則に反する。よって適用しない。

**影響**: リファクタは振る舞い保存。ゴールデンスナップショット (P0-10) 生成時に挙動等価を byte-equal で最終検証する。
