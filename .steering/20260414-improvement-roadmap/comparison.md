# v1 vs v2 比較 — 採用案選択のための整理

## 共通する結論

| 項目 | 両案の共通判断 |
|------|---------------|
| XGBoost (Stage 3) | **却下**（データ不足・Rust デプロイ手段なし） |
| GT プロトコル | **採用 / 最優先** |
| Synthetic Friction 再設計 | **採用**（GT データで閾値校正後） |
| Lv1/Lv2 既存挙動の保護 | **採用**（方法は異なる） |
| XGBoost / CNN 段階は現時点スコープ外 | **却下** |

## 主要な相違点

| 観点 | v1 | v2 | 分岐の本質 |
|------|----|----|------------|
| **Phase 0 の主軸** | テスト基盤（ユニット・統合・スナップショット） | **セッションリプレイ CLI**（テストを包含） | 「テストが先」vs「測定軸が先」 |
| **沈黙パスの二重構造** | **統一する**（閾値整合） | **統一しない**（リネーム + ドキュメント化のみ） | 「コード削減は善」vs「統合リスク > 保守利益」 |
| **パラメータ外部化** | 「欠落タスク」として重視（JSON/TOML 設定化を示唆） | **却下**（Rust 定数 + `// TUNE:` マーカー） | 「再コンパイル不要」vs「型安全 + Git 履歴で十分」 |
| **遡及ラベリング UI** | 言及なし（Level 1 はコード外扱い） | **Phase 1 では作らない**（リアルタイム GT のみ） | 「2 系統で収集」vs「最小手段で十分」 |
| **LR 統合の位置づけ** | Phase 3B で導入。重みを Rust 定数として埋め込み | Phase 3 は「**LR を入れるべきかの判断ゲート**」。入れない結論も対等 | 「LR は採用前提」vs「データで採否判断」 |
| **Lv3 Thought Scaffold** | Phase 4 で採用 | **却下（スコープ外）**。介入 precision が上がる前に種類を増やさない | 介入の「幅」を広げるか「質」を上げるか |
| **IME 追加特徴量の位置** | Phase 3A（ML 統合と同 Phase） | **Phase 2b として Phase 1 並列化**（シャドーモードで GT 待ち不要） | スケジュール最適化の焦点 |
| **macOS の IME 追加特徴量** | 明示なし（暗黙に対象） | **明示的に保留**（TCC・dispatch_sync コストが価値を超える） | クロスプラットフォーム完全性の重み |
| **HMM と LR の関係** | HMM 出力を LR 出力で置き換え（Go 判定時） | **HMM 出力と LR 出力の AND で介入発火**（HMM を残す） | 「置換」vs「補強」 |
| **Stuck 回復時間** | Phase 1 の独立タスクに分離（`recovery_time.py`） | GT ボタンに `recovered_at` を同梱（独立タスク不要） | タスク粒度の違い |
| **スケジュール合計** | 明示せず（各 Phase で 1-6 週） | **7〜8.5 週** を明示 | コミットメント度 |

## 哲学的な違い

| 軸 | v1 | v2 |
|----|----|----|
| 設計スタイル | **工学的正統派** — テスト → リファクタ → 新機能の順序 | **プロダクト最小主義** — 測定軸と介入価値から逆算 |
| 重視するリスク | 既存機能の意図しない破壊 | 投資の空振り（使われない基盤への工数浪費） |
| 「未踏2027 提案準備」への寄与 | 複数軸のデータ（HMM + LR + IME）を揃える | 「介入判断の precision が測れる」という根拠を 1 つ確実に作る |

## 選択の判断材料

### v1 を選ぶべき場合
- テスト基盤・パラメータ外部化が将来的な共同開発や長期運用を想定して必要
- IME 追加特徴量を macOS でも揃えたい
- ML 統合を「計画済み」として提案に載せたい

### v2 を選ぶべき場合
- 単一ユーザーのプロトタイプである現実を受け入れ、工数を最小化したい
- 「何をやらないか」を明示的に決めて工程を短縮したい（7〜8.5 週で Phase 3 まで）
- ML よりもまず「介入判断の precision を測れる状態」に到達することを優先
- 沈黙パスの統合リファクタを「挙動保存を優先して見送る」判断を許容できる

### ハイブリッド案（第 3 の選択肢）
- Phase 0 の **背骨は v2 のリプレイ CLI**（テストとリプレイを統合、パラメータ外部化は却下）
- Phase 1-2 は **v2 の並列化戦略**（Phase 2b を Phase 1 並列で進める）
- **LR は v2 の「判断ゲート」姿勢**（入れない選択肢を対等に扱う）
- ただし **テストは v1 の薄い層**を維持（φ, calculate_features, make_silence_observation のユニット + スナップショット）
- 遡及ラベリング UI は v2 のとおり後回し
- **Lv3 Thought Scaffold は Phase 4 として残す**（v1 の立場。ただし Go/No-Go は「介入 precision ≥ 閾値」で条件付け）
- macOS IME は v2 のとおり保留

---

## 推奨

**ハイブリッド案（v2 ベース + v1 のテスト層）** を推奨。理由:

1. **v2 のリプレイ CLI 背骨** は工数対効果が圧倒的に高い（テスト・GT 評価・チューニング・回帰検知を 1 ツールで兼ねる）
2. **v1 の薄いテスト層** は Phase 0 で 1 日あれば追加でき、リプレイ CLI が壊れたときの最後の砦になる
3. **v2 のパラメータ外部化却下** は単一ユーザー前提では正しい
4. **v2 の並列化戦略**（Phase 2b）はスケジュール短縮に直結
5. **Lv3 は Phase 4 に残す**（未踏 2027 提案で「介入の多段性」を見せる材料として有用）
6. **LR は判断ゲート姿勢**（v2）で、「入れない」も記録可能な成果とする

次のステップ: ユーザーに v1 / v2 / ハイブリッド のいずれを採用するか選択してもらい、採用版を `design.md`（最終版）にリネームして `tasklist.md` を起こす。
