# 設計判断: `IME_ACTIVE` の Ordering

## 判断 1: **7 箇所を一度に**閉じる (⚠️ 片側修正をしない)

- ★ mac が 判断 5b で踏んだ罠を繰り返さない ——
  **store だけ `Release` にしても読み手が `Relaxed` なら happens-before は成立しない**。
- ⚠️ 片側だけの修正は「直したつもりで**何も保証していない**」＝ silent no-op であり、
  ★ **「規則に合わせた」という記録だけが残る**のが最も悪い。
- → ★ store 4 箇所 / load 3 箇所を**同一コミットで**閉じた。

## 判断 2: フックコールバック内 (`hook_windows.rs:603`) も `Acquire` にしてよい

- ★ 共通-1 の禁止リストは **Mutex / ブロッキング send / I/O / ヒープ確保 / ログ / sleep** であり、
  ⚠️ **atomic load は入っていない** (★ 共通-1 はむしろ「Atomic 操作 + channel send **のみ**」と定める)。
- ★ `Acquire` load は **x86-64 では `Relaxed` と同一命令**でフェンスを生まない。
  → ⚠️ コールバックのレイテンシ要件に影響しない。
- ⚠️ **ここを `Relaxed` のまま残す方が危険である** —— ★ 共通-2 が名指しで対を要求しており、
  例外にする根拠がどこにも無い。

## 判断 3: ⚠️★★★ **回帰テストを足す** (★ mac は実測しただけだった)

- ⚠️ mac は `IME_OPEN` を閉じたあと「実測して 0 件」と記録したが、
  ★ **実測はその時点の写像にすぎず、次に書く人を止めない**。
  → ⚠️ 現にその**同じ日**に `IME_ACTIVE` が 7 箇所 `Relaxed` のままだと判明している。
- **決定**: `capabilities.rs` と同じ様式で **ソースの実物**を `include_str!` で走査する
  (`guarded_atomics_never_use_weak_ordering`)。
- ★ **型では表せない**理由: 共通-2 の規則は「**どの変数か**」に依存する
  (⚠️ `LAST_KEY_MS` / `CONSECUTIVE_TAP_FAILURES` は `Relaxed` で**正しい**)。
  → `AtomicBool` という型は両者を区別しない。

### ⚠️★★★ 判断 3a: **`#[cfg]` を付けない**

- ★ 文字列として読むので、`hook_windows.rs` が **1 行もコンパイルされない macOS でも中身を検査できる**。
- ⚠️ `#[cfg]` を付けると**相手側 OS の CI が素通り**し、
  ★ **今回まさに起きた「片 OS でしか見ていない」状態に戻る**。
  (★ `docs/agent-shared.md`: 「OS ごとに規則が違うロジックは両 OS に対のテストを置く」)

### ★ 判断 3b: 針を `concat!` で割る

- ⚠️ **本ファイル自身も走査対象**なので、割らないと**テストのリテラルが自分に引っかかる**。
- ★ コードにその理由をコメントで残した (⚠️ 後から「なぜ分かりにくく書くのか」と直されないように)。

### ★ 判断 3c: コメント行は除外する (⚠️ 既知の限界)

- ⚠️ 規則を説明する文章そのものが引っかかるため。
- ★ **「落ちすぎない」方向の限界**であり、⚠️ **実コードの見落としは生まない**。
  (★ `capabilities.rs` が「過大側に振れるが見落とす方向ではない」と書いたのと同型の判断。
   ★ 本件は向きが逆なので、⚠️ **限界を doc に明記**した)

## 判断 4: ⚠️ **変異テストで赤を実測してから**完了とする

- ⚠️★★★ **「足したら緑だった」は検査が効いている証拠にならない。**
  ★ **走査対象のファイルを列挙し忘れれば**「緑」になる。
  ⚠️ (訂正: 初版は「パスを 1 文字間違えても緑」と書いたが**誤り** —— `include_str!` は
  パスが違えば**コンパイルエラー**になる。★ 実在する silent pass は「列挙漏れ」の方である。
  → ★ 後述の 判断 6 で `read_dir` の自動走査に置き換えた)
- ★ **実測** (2026-09-12): `hook_windows.rs:603` を `Relaxed` に戻すと

  ```
  hook-constraints 共通-2 違反: 保護対象の static に弱い Ordering が使われている。
  input/hook_windows.rs:603 | if is_press && IME_ACTIVE.load(Ordering::Relaxed) {
  test result: FAILED. 0 passed; 1 failed
  ```

  ★ **行番号と該当行を名指しで返す**ことまで確認し、復元後は緑に戻ることも確認した。

## 判断 5: `HMM_VERSION` は bump しない

- ★ `Release` / `Acquire` は `Relaxed` より**強い**制約であり、**緩めていない**。
- ⚠️ (訂正: 初版の「観測される値の系列は変わらない」は**強すぎた** —— ★ 本当に何も変わらないなら
  本修正は no-op である。正確には **replay は単一スレッドなのでゴールデンは不変**／
  live では**可視性が改善する方向にのみ**変わりうるが、★ **HMM のモデル定義は不変**、である)。
- ★ ゴールデン **6 fixture / 226 snapshot が byte-equal** (⚠️ replay は単一スレッドなので
  そもそも Ordering を踏まない —— ★ **この回帰は「変えていないこと」しか言えない**点に注意)。

## ⚠️ スコープ外 (★ 意図的に触らない)

| 事項 | 理由 |
|---|---|
| 起票 10① (`macos_vk_to_vk` の素通しアーム) | ★ mac が 判断 6 / 研究者裁定 S-1 で「**VK 分布が変わりうるので混ぜない**」と裁定済み |
| `LAST_KEY_MS` 等の `Relaxed` | ★ 共通-2 が**明示的に `Relaxed` で正しい**としている |
| R-2 / R-3 / R-4 / R-5 | ⚠️ 引き継ぎに残したままの研究者判断 |

# レビュー後の判断 (code-reviewer / security-checker を並列実行した結果)

★ security-checker は **CRITICAL / HIGH ともに無し**。
⚠️ code-reviewer が **HIGH を 1 件**返し、**その指摘が正しかったので直した**。
★ MEDIUM 2 件は**両者が独立に同じものを指摘**しており、信頼度が高いので両方塞いだ。

## 判断 6: ⚠️★★★ **HIGH —— `Release` store の位置が逆で、リリースが空振りしていた**

- **指摘**: `hook_windows.rs` の IME_SHOW 分岐は `IME_ACTIVE.store(true, Release)` を
  **先頭**に置いており、その後に `IME_COMPOSITION_START_MS` / `IME_CANDIDATE_NAV_COUNT` /
  `IME_SHADOW_ABANDON` の `Relaxed` store が続く。
  ⚠️★★★ **`Release` store が公開するのは「それより前」の書き込みだけ**なので、
  読み手 (`hook_callback` の `Acquire` load) が `true` を観測しても
  **後続の 3 つが見えている保証は一切ない**。
- ⚠️★★★ **これは本タスクが避けようとした当の状態である** ——
  「規則には合っているが happens-before を確立していない」。
  ★ 私は 判断 1 で「片側修正をしない」と書きながら、**順序の側で同じ罠を踏んでいた**。
- ★ **一次資料で裏を取った**: もう一人の書き手 `ime_windows.rs::apply_fold_action` は
  **payload → `IME_ACTIVE.store(true, Release)`** の順で書いており、
  ⚠️ コメントに「**先行する 3 つの Relaxed store を分析スレッド側の Acquire 読みに対して
  可視化する**」と明記されている。
  ★ さらに同ファイルの doc が言う「更新順は `win_event_callback` と**同じ形**」は、
  ⚠️ **この修正で初めて真になった**。
- **対応**: SHOW 分岐の `IME_ACTIVE.store(true, Release)` を **payload の後**へ移した。
  ★ 実害は shadow 系メトリクスに限られる (⚠️ 読み手が古い `NAV_COUNT` に加算し、
  直後の 0 リセットで消える) が、⚠️ **順序を直さなければ Release を付けた意味が無い**。

## 判断 7: ⚠️★★★ **MEDIUM —— 針が「裸の `Relaxed`」を素通ししていた** (★ 両者が独立に指摘)

- **指摘**: 針が `concat!("Ordering::", "Relaxed")` の完全一致だったので、
  `use std::sync::atomic::Ordering::Relaxed;` を書けば `IME_ACTIVE.load(Relaxed)` は**検出されない**。
- ⚠️★★★ **仮定の話ではない** —— ★ `lib.rs:3210` (**`emit_ime_shadow` の中**、
  まさに IME shadow の atomics を触る関数) と `lib.rs:5513` が**既にこの import 形式**を使っている。
  → ⚠️ **回避経路が走査対象ファイルの中に先に存在していた。**
- **対応**: 針を **`Relaxed`** に緩めた (★ 保護対象名との AND なので誤検出は増えない)。

## 判断 8: MEDIUM —— **ファイルのハードコード列挙をやめた** (★ 両者が独立に指摘)

- ⚠️ 列挙だと**新しいファイルが黙って検査の外に出る**。
  ★ それは本テストが批判している「実測はその時点の写像にすぎない」という弱点を
  **1 段上に残しただけ**である。
- **対応**: `env!("CARGO_MANIFEST_DIR")` + `read_dir` の再帰走査に置き換えた。
- ★ 併せて **空振り検知**を足した: 走査ファイル数が 20 未満なら落とす／
  保護対象の名前を 1 つも見つけられなければ落とす。
  ⚠️★★★ **0 件でも `violations.is_empty()` は緑になる** —— それは
  「検査したが無かった」ではなく**「検査していない」**であり、**最も危険な緑**である。

## 判断 9: ⚠️ `;` 区切りは**過検出して使い物にならなかった** (★ 実測して設計を変えた)

- ★ レビュー指摘 (複数行に折られた呼び出しを取りこぼす) を受けて
  「行 → `;` 区切りのステートメント」に変えたところ、⚠️ **正しい `Acquire` のコードが 2 件赤になった**。
  - `hook_windows.rs`: `if is_press && IME_ACTIVE.load(Acquire) {` の**ブロック本体**に入っている
    無関係な `NAV_COUNT.fetch_add(.., Relaxed)` と同居した。
  - `ime_compose.rs`: 構造体リテラル内で `active: IME_ACTIVE.load(Acquire)` と
    `nav: IME_COMPOSE_NAV.load(Relaxed)` が同居した。
- ⚠️★★★ **常時赤の検査はいずれ消される。** ★ 「落ちすぎる方向だから安全」は
  **検査が生き残る場合にしか成り立たない**。
- **対応**: **保護対象名の直後の `( .. )` の中だけ**を括弧の深さを数えて切り出す方式にした。
  ★ 複数行は「行コメント除去 → 1 本に連結」で吸収されるので、両方を同時に満たせる。

## 判断 10: ★ 変異テストを **3 形態**でやり直した (⚠️ 1 つは検証になっていなかった)

| 変異 | 結果 |
|---|---|
| A: `Ordering::Relaxed` (従来形) | ✅ **FAILED** (赤) |
| B: 裸の `Relaxed` (⚠️ **import ごと**注入) | ✅ **FAILED** (赤)・`input/hook_windows.rs \| IME_ACTIVE(…Relaxed…)` |
| C: rustfmt が折った複数行 | ✅ **FAILED** (赤) |
| 復元後 | ✅ ok |

- ⚠️★★★ **B は最初、出力が 1 行も出なかった** —— ★ `Relaxed` が import されておらず
  **コンパイルエラーになっただけ**で、**針の検証になっていなかった**。
  → ★ `use std::sync::atomic::Ordering::Relaxed;` を**一緒に注入して**やり直した。
  ⚠️ 「赤になった」だけでは**何が赤にしたのか**を確かめたことにならない。
