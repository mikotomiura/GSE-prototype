## 判断 1: 潜在状態の定式化 — 状態数を今決めない（★ `/reimagine` 適用箇所）

- **判断日時**: 2026-08-01
- **背景**: 引き継ぎ #6 / §SSOT-(A)。doc#2 §4.1 の 4 状態
  `Progress / Stagnation / ExternalizationPressure / Receptivity` は 5 点で破綻している
  （相互排他でない / Receptivity に放出モデルが書けない / ExternalizationPressure が状態か傾向か未決で
  §0 と循環 / `WorkStateEstimate` への写像が未定義 / 「4」の根拠が無い）。
  さらに Receptivity は既存 SSOT では Layer 5 の概念で、ADR-007 が「分解維持」を採択済み。
  同じ語が Layer 4 と Layer 5 に並立すると **ADR-007 の決定が静かに無効になる**。

### 初回案（生成 → **破棄**）

引き継ぎ §SSOT-(A) の代案そのまま:

> 潜在状態は相互排他で放出が分かれる作業モードに限る
> （`Progressing / Stalled / Externalizing` — それぞれ打鍵継続 / 無音・修正ループ /
> 外部化イベントと放出が対応する）。

**破棄した理由**: `requirement.md` だけを見て再生成したとき、この案自身が
**§SSOT-(A)-5 の批判（「3 状態は手で選んだ状態だった。3 → 4 にしただけでは同じ轍」）を
4 → 3 の向きで繰り返している**ことに気づいた。状態数を手で選ぶという操作は同じで、
数が 1 つ減っただけである。(A)-5 が本当に要求しているのは「状態数を変えること」ではなく
**「状態モデルがデータ中の何かに対応していることを検査可能にすること」**。

### 再生成案（★採用）

**潜在状態の層を「ontology」から「head の実装詳細」へ降格し、状態数を今決めない。**

1. **Layer 4 の出力を先に固定する**（ここだけ確定させる）:
   `WorkStateEstimate` に `self_directed_recovery_risk`（+ 専用 `uncertainty`）を **additive に追加**する
   （ADR-005 の additive 原則）。これは**推定器の内部構造と独立に定義できる観測可能な予測量**である。
2. **正となる推定器は stateless baseline**: `p_recovery = sigmoid(bias + w·context)`。
   潜在状態を一切持たない。
3. **潜在状態モデル（3 モード HMM / online EM）は候補 head に降格**し、
   **採用ゲート**（held-out の recovery 予測で baseline を上回る勝ち幅 ＋ 退化検出
   ＝ 状態占有エントロピー / 最小占有率 / seed 間ラベル安定性）を通過した時にだけ採用する。
4. `ExternalizationPressure` は状態でなく **recovery risk の構成要素（特徴）**。
5. `Receptivity` は **Layer 5 に戻す**（ADR-007 の分解維持を維持）。

- **選択肢**:
  - A: 状態数を決めない（stateless baseline を正とし、状態モデルは勝ち幅で採否）★採用
  - B: 3 モード（Progressing / Stalled / Externalizing）を今確定する（＝破棄した初回案）
  - C: doc#2 の 4 状態を修正（Receptivity だけ外して 3 状態に）して採る
- **採用**: A（ユーザー裁定 2026-08-01）
- **理由**:
  1. **Phase1 の実測が「状態数は今の binding constraint ではない」と言っている**。doc#1 §7.2 は
     「φ は単調変換なので C-index をほぼ変えない ＝ β を直しても生の特徴量に無い信号は作れない」を
     実データで確認した。同じ論法が潜在状態にも効く——**情報を持たない観測の上に状態構造を載せても
     事後分布は情報を持たない**。効くのは観測空間（externalization / pause 分布 / focus 復帰）を
     広げることと目的変数を変えることであって、状態の数ではない。
  2. B / C は「なぜその数か」に答えられないまま SSOT に入る。A は答えを**実験に委ねる**形にして、
     答えられないことを SSOT で断定しない。
  3. doc#1 §7.3 優先3（Codex #7「D 以外のベースラインを先に置き、D の複雑さに対する勝ち幅を測れ」）と
     構造的に同じ要求であり、2 本のメモが独立に同じ方向を指している。
  4. コストがゼロ。今は設計のみで実装しないため、状態数を保留しても失うものが無い。
- **トレードオフ**: 「GSE の潜在状態は何か」という問いに現時点で答えを持たない文書になる。
  未踏 PM 等への説明では「4 状態です」より弱く聞こえうる。
  → 統合設計文書ではこれを **弱さでなく方法論上の強み**（採用ゲートを事前に宣言した反証可能な設計）
  として書く。
- **影響範囲**: ADR-009 の Decision 本体。`WorkStateEstimate` の additive 拡張（Epic 2/5）。
  doc#2 §4.1 / §8 Phase 2 の書き換え。
- **見直しタイミング**: 採用ゲートを通る状態モデルが 1 つでも出たとき（そのとき ADR-009 を
  superseding する ADR を書く）。または観測空間の拡張後も recovery 予測が baseline で偶然水準のとき
  （そのときは軸自体の反証＝統合設計文書 §8 の反証ゲート G1 へ）。

## 判断 2: online EM を Phase 4 へ降格する（不一致 #2）

- **背景**: doc#1 §3-D は online EM を「**本命候補**」と書き、doc#2 §0/§8 は「初期実装の中心ではない」
  として Phase 4 へ降格した。doc#2 が doc#1 を上書きしているが、**降格の理由が書かれていない**。
- **選択肢**:
  - A: doc#1 に戻し online EM を本命として設計する
  - B: Phase 4 へ降格（doc#2 の判断を追認するが、理由を明文化する）★採用
  - C: 完全に棄却する
- **採用**: B
- **理由**: 降格の理由は「重いから」でも「難しいから」でもない。**3 つの前提が揃っていないため
  現時点では評価不能**だからである:
  1. **目的変数が未確定だった**（`progress_proxy` / recovery の operational definition が無い）。
     何に対して「良い潜在状態」なのかが定義されていなければ EM の当たり外れを判定できない。
  2. **比較対象（baseline）が無い**。doc#1 §7.3 優先3 / Codex #7 の指摘そのもの。
  3. **識別可能性の問題が未解決**（doc#1 §4.3）。教師なし EM はクラスタを作るが Stuck は作らない。
     半教師ありアンカーに使う予定だったラベルは、**Phase1 でまさに枯渇した**
     （probe 枯渇・P013 の straight-lining・GATE3 DataInsufficient）。
     アンカーの供給が壊れている状態で意味固定に頼る設計は成立しない。
  → よって「本命を降格した」のではなく **「前提が揃うまで評価できないので順序を後ろに置いた」**。
  判断 1 の採用ゲートを通れば Phase 4 で復活しうる。
- **トレードオフ**: 新規性の主張（doc#1 §6「content-free 制約下での潜在状態オンライン推定」）が
  当面使えない。→ 統合設計文書では新規性を **閉ループ較正（介入のランダム化が較正の教師になる）** と
  **行動由来ラベルによる label supply の解決**の側に置き直す。
- **見直しタイミング**: Phase 1-3 完了後（doc#2 §8 Phase 4 の条件と同じ）。

## 判断 4: PreReg-5 の衝突は「詭弁か否か」でなく「情報の出所」で切る（不一致 #4）

- **背景**: doc#1 §5-a / §8-1 が「『正規化層は測定器の一部なので適応可』は**詭弁ではないか**」と自問し、
  未解決のまま残っていた。PreReg-5 は「評価期間中の閾値・パラメータ調整は**禁止**」（forking paths 排除）。
- **採用**: 「測定器の一部だから適応してよい」という**レトリックは採らない**。
  代わりに **情報の出所**を基準にする:
  > **評価期間のデータが 1 バイトも推定に入らないなら PreReg-5 と両立する。入るなら破る。**
  これは Codex #1（doc#1 §9-1）の 3 条件切り分けと同じ operational な基準であり、
  `cold_start` / `past_session_adapted`（評価開始前に凍結）は両立、
  `within_session_adaptive` は**両立しない**（＝探索的結果としてのみ報告）。
- **理由**: 「測定器か意味層か」は**層の名前**の話であり、forking paths の有無を決めない。
  実際に問題になるのは「評価期間の分布を見てスケールを学ぶ」という**情報の流れ**（広義の
  test-time adaptation）であって、その層を何と呼ぶかではない。よって自問への答えは
  **「詭弁である。ただし切り分けたい実体は存在し、正しい切り口は情報の出所である」**。
- **スコープ**: `preregistration-v0.3.md` は**凍結・変更しない**。統合設計文書 §7.2 に
  「次バージョンで宣言すべきこと」を書くに留める。

## 判断 5: ADR-006 は拡張せず、新 ADR が参照する（不一致 #5）

- **背景**: doc#1 §3-C は「head が持つものを β だけでなく **criterion と写像係数**まで広げる拡張」と書く。
  ADR-006 の改訂か、新 ADR か。
- **選択肢**: A: ADR-006 を改訂して所有物を広げる / B: 新 ADR が ADR-006 を前提として参照する★採用
- **採用**: B
- **理由**:
  1. ADR-006 は **Accepted**（枠組み C ＋ 下位決定 #2/#3 まで確定）であり、スコープは
     「task_kind → head/β の配線」に閉じている。既に確定した ADR を後から広げると、
     **どこまでが 2026-07-24 の研究者判断だったのかが判別できなくなる**。
  2. 追加される所有物（criterion＝目的変数 / 写像係数 / 個人プロファイル）は β と**性質が違う**。
     β は母集団定数でオフライン決定、写像係数と profile は**オンライン更新される個人状態**であり、
     replay 決定性・PreReg-5・同意/削除 UI という β には無い制約が付く。同じ ADR に混ぜると

  3. 引き継ぎ「やらないこと」が ADR-006 の再検討を明示的にスコープ外にしている。
- **帰結**: ADR-006 は**無変更**。ADR-008 が「ADR-006 の枠組み C を前提に、head の所有物を
  β から {criterion, 写像係数, profile} へ拡張する」と Context に書き、ADR-006 側は触らない。

## 判断 6: 個人化ナッジ（doc#2 §2.1-F）は「抑制方向のみ」採る（前提 B-1）

- **背景**: doc#2 §2.1-F は個人化ナッジ（どの形式・強度・タイミングで出すか）を採用候補に置くが、
  `[V40]`（assistance 系 d=0.22 → 補正後 **0.01**, BF01≈9）に一言も触れていない。
  `gse-v2-overview.md §5` は「Motivation Generator を標準実装しない」と既に書いている。
  `.idea` の中なら私見で済むが、昇格すると **SSOT 同士が矛盾する**。
- **選択肢**:
  - A: **抑制方向のみ個人化**★採用
  - B: 採る（[V40] への反論を SSOT に書く）
  - C: Deferred（Gate D/H のデータ待ち）
- **採用**: A（ユーザー裁定 2026-08-01）
- **理由**: `[V40]` が否定したのは **assistance 系＝説得力を上げる方向**である。
  個人化の対象を 2 つに割ると:
  - **説得方向**（どの文面・形式で促すか）＝ assistance 系そのもの → **採らない**。
  - **抑制方向**（いつ**出さない**か・強度上限）→ [V40] の否定対象外であり、
    `[V43]`（受動観測の行動指標が受容性を予測・自己申告は予測しない）が**支持する**方向。

  すなわち **個人化は「よりうまく説得するため」ではなく「より確実に黙るため」に使う**。
- **トレードオフ**: 介入の効果最大化の余地を自ら捨てる。ただし [V40] 下でその余地の期待値は
  ほぼゼロ（補正後 d≈0.01）であり、失うものは小さい。

## 判断 7: 引用の是正方針（前提 B-2 / B-3 / B-4 / C）

- **背景**: doc#2 の外部 9 本は `docs/references.md` に **1 本も未登録**（citation-ssot 違反）。
  加えて A・D・E は行動経済学が無くても導ける（装飾的引用）、§2.1-C は無引用主張、
  KTO の引用が技術的に働いていない。
- **採用**: **9 本すべて採番する。ただし「採らない理由」の出典としても採番してよい**とする。
  - 採らない候補（Ellsberg / CPT-RL / Personalized Nudging）も、本文で**明示的に棄却する文**の
    出典として inline `[n]` を持つ。これは citation-ssot ルール 6（active 行に使用箇所がある）を満たす。
  - **KTO [V54]**: 「KTO 的」と名乗るのをやめる。借りているのは
    「二値の desirable/undesirable フィードバックと非対称効用から学習する」という**枠組みだけ**で、
    KTO 固有の実装（言語モデルの生成ポリシー・参照分布・生成尤度）に対応するものは GSE に無い。
    §5 の `utility = gain − λ·cost` は素の非対称損失である、と書く。
  - **Tversky-Kahneman 1991 [P29]**: 参照点依存の**概念的出所**として残すが、GSE で実際に効いているのは
    標準的な cost-sensitive decision theory（非対称損失）であることを明記する。
  - **Ellsberg 1961 [P30]**: 「ユーザーの ambiguity aversion を推定しない」という**棄却の出典**として使う。
    採用根拠（uncertainty gating）は既存 SSOT（`domain-adapter-boundary.md §原則`）に既にあり、
    行動経済学を必要としない。
  - **§2.1-C の無引用主張**: [V55]（CPT-RL）ではなく **[V56]**（Sukumar et al. 2022・遅延報酬 MDP を
    個人ごとにフィットしインセンティブを最適化）が該当する研究例。採番して inline を付ける。
- **理由**: 装飾的な引用は「理論に接地している」と読まれるため危険（引き継ぎ B-2）。
  一方で「引用を消す」と、なぜ検討して棄却したのかの記録が失われる。
  **棄却の出典として残す**のが両方を満たす。

## 判断 8: `progress_proxy` の operational definition（前提 E）

- **背景**: doc#2 §11-2 が「`progress_proxy` を本文なしでどう検証するか」を未解決と自認している。
  **目的変数の定義が未確定のまま軸を再定義するのは順序が逆**。
- **採用**: 3 層で閉じる（詳細は統合設計文書 §3.3）。
  1. **定義**: 個人×task_kind×phase 基準で正規化した**純産出の持続**
     ＝ 窓内の（挿入 − 削除）打鍵数を個人基準で正規化し、**T 秒以内に取り消されないこと**を条件とする。
     content-free（打鍵数と時間のみ・本文非保存）。
  2. **`self_directed_recovery` のラベル**: stall onset から H 分以内に、
     **観測された外部化イベント（paste）を挟まずに** progress_proxy が個人基準を超えて回復すること。
     focus 喪失・アプリ切替は**打ち切り（censoring）指標**として別に記録する
     （content-free 制約下では検索等の外部化が観測できないため。これは隠さず限界として書く）。
  3. **妥当性の検証**: Phase1 の実測が既に部分的な裏付けを持つ——単純な `keys`→Q2（前進感）の
     個人内 C-index は 0.615 / 0.600 / 0.657 / 0.676（P014 のみ 0.368）であり、
     **打鍵数ベースの産出量は現行 5 特徴量のどれよりも Q2 をよく順序付けている**（doc#1 §1.5）。
     つまり産出ベースの progress_proxy は「効くはず」ではなく**既存データ内で最も強い信号**に接地している。
- **理由**: これが X 軸を摩擦（偶然水準）から recovery（産出・前進側）へ動かす**実証的な動機**でもある。
  doc#2 は §0 で軸を再定義したが、なぜその方向かの実証的根拠を doc#1 §1.2/§1.5 から持ってきていなかった。
- **限界（明記する）**: P014 の 0.368 は写像係数の符号反転の実例であり、progress_proxy にも
  個人適応が要ることを同時に示している。また C-index 0.60 台は「弱いが一貫」であって強い信号ではない。

## 判断 11: ICC の訂正をどう本文に反映するか

- **背景**: doc#1 §3-B は「ICC が 0.06〜0.16 と低いことは強めに縮約すべき根拠になる」と書き、
  doc#2 §4.2 の partial pooling の強さがそれに乗っている。しかし `.idea` の
  0.060/0.055/0.159/0.156 は **ICC ではなく η² = SSB/SST** だった
  （PR #83・`experiments/20260801-signal-diagnostics/notes.md` §2-C）。
  正しい ICC(1) は 0.080/0.073/0.204/0.200、LOO 範囲 0.050–0.302。
- **採用**: 統合設計文書では**点推定を引かず**「概ね 0.05–0.30、被験者 5 名で不確実性大」と書く。
  `.idea` の 4 値は引かない。加えて Codex 指摘（doc#1 §9-4）の
  「『個人差』と解釈したものが実は作業種別差かもしれない」を併記する。
- **理由**: 方向（個人差は小さい → 個人適応は写像係数側）は変わらないが、
  **縮約の強さを数値で正当化する根拠としては弱くなった**。partial pooling の強度を
  ICC の点推定に紐づけて書くと、後で ICC が動いたときに設計判断が宙に浮く。
  → 縮約強度は「ICC がこの値だから」ではなく **「n が小さいから CV で選ぶ」**に接地し直す。
