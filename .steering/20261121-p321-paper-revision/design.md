# design — p321-paper-revision（v2・/reimagine の再生成案）

> v2 は、v1（`design-v1.md`）を見ていない Opus の汎用エージェントに、requirement.md・decisions.md（判断 1〜11）・attack-me round 1 の verdict・論文用リポジトリ・JSS の規程の逐語（v1 §0 と同じ事実）だけを渡して書かせた（2026-11-21・約 2 分）。読んだ範囲の自己申告: 全文 = requirement・decisions・verdict・`main.tex`・`build.sh`・`run.sh`・`NOTES.md`・`README.md`・`DATA.md` ／ 一部 = `config.json`（先頭 40 行）・`analysis/*.py`（関数名と grep）・`make_results.py`（関数の一覧）・`metrics.json`（先頭）。何も実行していない。以下はその案を私がまとめたもの。

## 0. 前提（v1 から引き継ぐ）
- JSS の規程の一次の事実と、その出典（URL・逐語）は `design-v1.md` §0 を正とする。ここには写さない（二重に持たない）。
- K の具体: D1 の元データは CC BY 4.0（`DATA.md`・"shown on both figshare item pages"）なので、派生表は帰属表示をつければ出せる見込み。figshare のページは S3 で Chrome で読み直す。元データにはセッションごとの公開動画とリポジトリの URL が入っているので、派生表は episode 単位の符号と時刻だけにする（URL・配信者の名前・セッションの識別子は入れない）。
- `NOTES.md:39` の "the author's other project" は消し、「前の名前が引用のキーに似ていた」とだけ書く（研究者の選択・2026-11-21）。タグ `submission-2026-09-29` の版は公開済みなので、そのまま残る。

## 要旨
- 待ち時間の長い照会を 0 日目に出し、その 2 週間に解析と本文を並行で進める。返事は、最後に RQ4 の 1 節へ差し込むだけで済む形にする。
- 進める順は「枠 → 数 → 名前 → 本文 → 外枠の文」。まず文言を 1 字も変えずに JSS の枠（elsarticle）へ移す。次に凍結の外の補助解析を「追加だけ」で足す。そのあと用語をそろえ、本文は内側の節から書き直す。要旨・結論・Highlights・題は最後に書く。
- 本文を `body.tex` に切り出し、雑誌ごとの枠（`main-jss.tex`）から読み込む。JSS も査読の依頼が 20 件に届くと査読に回さない。そのときは枠だけ替えて IST へ出す。
- 受け入れは `build.sh` と自己検査で機械的に判定する（規程の数値・禁止する文言・旧い値の不変）。

## 1. アプローチ
1. **枠の移行を内容の改訂から切り離す**: `main.tex` を `body.tex`（本文）と `main-jss.tex`（elsarticle の 1 段組・author-year）に分ける。`build.sh` の Springer の zip とハッシュの検査は、elsarticle の照合に替える。この段では本文の差分を 0 にし、見た目と頁数（36 頁未満）だけを確かめる。書式の崩れと内容の誤りが、同じ差分に混ざらないようにするため。
2. **補助解析は凍結した節を変えずに足す**: `config.json` に新しい節 `post_review_additions`（日付・理由・verdict の記号）を作り、`NOTES.md` に Deviation 8 として記録する。足すのは次の 6 つ。
   - 打ち切りの感度分析: DF3 を除く／DF3 と DF5 を除く／D2 の研究期間の終わりを除く
   - 区間 [R0′, R0]
   - D1 の k・開発者ごとの分布・DF3 がセッションの最後の episode か
   - 時間で重みをつけた版と長さ（M）
   - P1TA を参照に数えない感度分析（I）
   - 補助の区間（判断 9）

   凍結した節は、`submission-2026-09-29` の版のハッシュを定数として持ち、`analyze.py --selftest` で一致を確かめる。
3. **名前は先に辞書を作る**: R0・R0′・R1 と 3 つの effect について、表示名・記号・避ける語の表を decisions.md に置く。研究者が決めたら一括で置き換える。`metrics.json` のキーは外部の契約なので変えず、表示名だけを替える。
4. **本文は内側から外側へ書く**: 方法・結果 → 考察（受け手別の提言・2×2 表）→ 関連研究（B の検索の結果・F）→ 序論・貢献（L）→ 結論・要旨・Highlights・題。

## 5. テスト
- `build.sh` が exit 1 で止まる検査:
  - 要旨が 250 語以内（`\R` を展開した後）
  - Highlights が 3〜5 本・各 85 字以内
  - キーワードが 1〜7
  - PDF が 36 頁未満
  - 生成 AI の申告の節が文献表の直前にある
  - 禁止する文言が無い（"over-states"・"every number in this paper"・"frozen before results were computed"・内部の名前）
  - 要旨の符号の句が `metrics.json` の符号と合う
- `make_results.py --selftest`: 新しい質的な主張ごとに、偽の metrics で止まることを確かめる（陰性対照）。
- `analyze.py --selftest`: 凍結した節のハッシュの一致 ／ 旧い `metrics.json` の全フィールドが同じ値で残る ／ 打ち切りの感度分析を合成データで再現できる ／ 派生表から主の値を再計算すると一致する。
- 変異: 検査ごとに 1 回わざと破り、止まることを確かめてから戻す。
- 閉じ方: tasklist の A〜M と minor の各行が「直した箇所」か「直さない理由」を持つことを grep で数える。
- 人の検査: S7 の通読・round 2（fatal 0・major 0、または研究者が採否を決める）・`/cross-review` の裁定。

## 6. v2 が挙げた判断への懸念（案の外）
1. 判断 11: JSS も依頼が 20 件に届けば査読に回さない → 枠の分離（IST へ替えやすく）と推薦の査読者で備える。
2. 判断 2: 「DF3 を除く」（2/77 = 2.6pp・打ち切りとしての扱い）と「DF3 を解決に数え直す」（[R0′, R0] の端点）は別の量 → 本文で名前を分ける。
3. 判断 9: 分子の効果は構成上 0 以上 → 境界の上で情報を持たない区間になりうる。「補助の区間は役に立たない」も結論として選べるようにする。
4. 判断 5: 照会の前に journal 版の数字を一次で確かめる（verdict §4 の注意）→ S0 を最優先に。
5. 生成 AI: いまの原稿は "The assistant drafted and revised this manuscript" と書いている。JSS が求める「著者が全体を編集・翻案した」を満たすには、S7 の通読と手入れが前提になる。
6. 公開物: `NOTES.md:39` に "the author's other project" がある（名前は出していない・タグの版にも 2 か所ある＝公開済み）→ 残すか研究者に確かめる（私が grep で確かめた）。
