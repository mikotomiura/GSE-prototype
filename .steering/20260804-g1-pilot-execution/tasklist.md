## 2026-08-04 — Drive への配置で **私が block01.html を壊した**

**見た目の問題ではない。** この正規表現が壊れると `countChars` のフォールバックが変わり、
**T-2 で実測した「JS 11 / Python 11 の一致」が崩れる**（`preregistration.md §3.5` の産出量報告に効く）。

### 教訓 — 前セッションの規則は正しかった

「**Drive MCP でファイルを送るときは 1 ファイルずつ上げてサイズを照合する**」という規則を立てた。

私は本日その **診断**（zip が破損している）を訂正した。**しかし規則そのものは別問題であり、

### 送信経路の性質（実測でわかったこと）

| 中身 | textContent 経由 |
|---|---|
| エスケープ列・制御文字を**含まない**（`launch-g1-macos.command`） | バイト一致 |
| `\uXXXX` などのエスケープ列を**含む**（`block01.html`） | 化ける |

→ **「一度うまくいった」を経路の保証と読まない。** 中身によって結果が変わる。

### 解決 — `base64Content` を使えばバイト一致する（実測）

`textContent` をやめ、`base64 < file | tr -d '\n'` の出力を `base64Content` に渡したところ、
**解釈が一切挟まらず完全一致**した:

| ファイル | ローカル | Drive | |
|---|---|---|---|
| `block02.html` | 6,858 | **6,858** | 一致 |
| `block03.html` | 6,642 | **6,642** | 一致 |
| `block04.html` | 7,268 | **7,268** | 一致 |

- 送信量は raw の 4/3（例: 7,268 B → 9,692 字）。**数百 KB までは実用的**
- **MB 級は不可能**（`.dmg` は 6 MB → base64 約 8 MB）→ drag & drop
- `block01.html` は **壊れた方を消してから**上げる（同名重複を作らないため）
