- **理由**: 確証実施をどちらの OS で回すかを P-1 の結果で決められる。P-1 は判定しないので
  実施回数を増やしても事前登録に抵触しない。
- **トレードオフ**: 所要が 23 分 × 2 になる。★ **題材の重複問題が発生する**（→ G-4 で解決）。
- **影響範囲**: `env.md`（記入枠を 2 回分）／ `protocol.md §5.1` ／ `assign.py`（G-4）
- **見直し**: P-1 の結果で OS 差が実務上問題にならないと分かったら、確証は片方でよい。

## 判断 G-5: 課題文は 1 枚ずつ維持。冊子化するのは**手引きのほう**

- **背景**: 「課題文を 1 つの冊子にまとめたほうが被験者はやりやすいのでは」という提案。
- **選択肢**: A=課題文を全面冊子化 ／ B=P-1 だけ冊子 ／ ★ **C=1 枚ずつ維持＋手引きを冊子化**
- **採用**: **C**
- **理由**: ★ **被験者が一度に見るのは常に 1 枚**なので、冊子にしても被験者側の利点が無い。
  一方で失うものが 3 つある:
  1. ★ **先のブロックの課題文を読めてしまう** → 事前に構想でき、打鍵量の測定が歪む
     （＝ P-1 の目的そのもの）。
  2. ★ **課題の型が露出する**。`participant-guide.md` は「資料 1 本の要約 / 資料 3 本の統合」
     という taxonomy を**意図的に伏せている**（実験者向け注記に明記）。冊子で全題材が並ぶと
     型が一目で分かり、強制比較（`§2.6`）が「体験」ではなく「型」で答えられてしまう。
  3. `protocol.md §2.3-2`（複数枚を手元に置かない）と `§5`（パイロットの封筒運用）が壊れる。
- **代わりにやったこと**: `participant-guide.md` に表紙と目次を付けて**冊子体裁**にした。
  まとめる価値があるのはこちらである（当日ずっと手元に置くもの）。

## 判断 G-6: 課題文に「架空」明示。**出典はデブリーフで開示**

- **背景**: 「参考文献も公開されていることを明示したい」という提案。
- **★ 実測で分かった問題**: 課題文には**どこにも「架空です」と書かれていなかった**
  （`topic01_lo.md` 全文で確認）。一方 `materials/sources.md` は
  「課題文の数値を事実として引用してはならない」と明記している。
  → **被験者が架空の統計を事実として持ち帰る**状態だった。
- **選択肢**: A=課題文に出典を併記 ／ B=同意文書で宣言 ／
  ★ **C=課題文に「架空」1 行＋デブリーフで出典開示**
- **採用**: **C**
- **理由**:
  - A は ★ **数値が架空なのに出典を並べると「この数字には出典がある」と誤認させる**。
    加えて読解量が題材ごとに変わり `§2.2` の ±5% 制約に影響する。
  - B は題材の内容に触れるとブロック前の予備知識に差が出る。
  - C なら実験中の統制を一切変えずに、透明性と誤情報防止の両方を満たす。
- **★ 実装上の確認**: `validate_materials.py` は `## 資料 N` セクションだけを数えるので、
  **教示末尾への追記は ±5% 制約に影響しない**（実測: 追記後も `topic01` lo=468 / hi=473 で不変）。
  文言は LO / HI で同一なので**条件差も作らない**。`copy.md` は架空の統計を含まないため対象外。
- **副次的効果**: デブリーフに ★ **口外しないお願い**（`debrief.md §5`）を入れた。
  8 題材は全被験者に共通なので、内容が伝わると次の被験者が事前知識を持つ。

## 判断 I-1: `validate_blocks.py` の「実施前」を fail から note へ

- **★ 発見**: `protocol.md §6` は「**前日まで**: `assign.py --json > blocks/P0xx.json` を作り、
  `validate_blocks.py` が緑（実施前は『未記入』の note だけが出る）」と要求している。
  ⚠️ **しかし実装は、file 未記入をすべて fail にしていた**ので、
  前日に割付を置くと**必ず赤**になり、`run.sh` まで赤くなる（`run.sh` は blocks があると
  `validate_blocks.py` を走らせ、失敗を `bad` にする）。★ 文書の要求が達成不可能だった。
- **選択肢**: A=protocol の記述を「前日は赤で正常」に変える ／
  ★ **B=実装を直す** ／ C=割付をサブディレクトリに置いて `run.sh` から隠す
- **採用**: **B**
- **理由**: A は「赤いのが正常」という状態を作り、**本当の赤を見逃す**ようになる。
  C は検査を回避するだけで前日チェックの価値が得られない。
- **★ 緩めすぎない設計**: **全ブロックが未記入なら「未実施」note**、
  **一部だけ未記入なら fail のまま**（そこが本当の記入漏れ事故である）。
  この 2 状態を `validate_blocks.py --selftest` に恒久的な検査として追加した
  （「実施前（全ブロック未記入）は緑」「★ 一部だけ記入は記入漏れとして赤」）。実測で両方確認済み。
- **⚠️ ★ 自己レビューで見つけた欠陥と、その修正**:
  この格下げによって **`--dataset` を付けても「実施後に file 列を丸ごと転記し忘れた」ケースが
  緑を通る**ようになっていた（`check_dataset` は `if not f: continue` で未記入を黙って飛ばすため）。
  ⚠️ 変更前は「file 無し」が常に fail だったので、この事故は捕まっていた。**検出力を落としていた。**
  → `check_dataset` に「★ **dataset に NDJSON が実在するのに file が 1 つも無い = 転記漏れ**」を
  fail として追加し、無ければ「未実施」note に留めるようにした。
  ★ **この検査が空回りしていないことも実測で確認**した（ガードを一時的に無効化すると
  selftest が赤になる）。第 5 版の教訓「回帰テストが空回りしていないかを検査する」と同じ型。

## 判断 I-3: launcher を repo に置く（`scripts/` ではなく実験ディレクトリ配下）

- **理由**: G1 実施専用であり、`scripts/` の被験者配布物（Phase1 系）と混ざると配り間違える。
- **★ 実測で潰した落とし穴 2 つ**:
  1. **アプリ名は `gse-next`**（`productName`）。`open -a GSE` / `GSE.exe` では起動しない。

     launcher が先に quit / taskkill する。
- **★ 検証の教訓**: `VAR=1 open -a <App>` が環境変数を渡すかを最初 `ps eww` で測ったが、
  ⚠️ **macOS は他プロセスの環境変数を出さない**（`PATH` すら 0 件）ため、この手法では
  「渡っていない」と誤結論しかけた。**環境変数を書き出すテスト用 .app を作って測り直し**、
  3 方式とも渡ることを確認した（`verify-before-claiming`: 検査手法自体の健全性を確かめる）。
- **Windows 版**: ★ **BOM ＋ CRLF ＋ `chcp 65001` を日本語より前**に置いた
  （Phase1 の participant launcher 文字化けの再発防止）。実測で BOM あり・裸の LF 0 を確認。
