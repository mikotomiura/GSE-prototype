# 重要な設計判断

## 判断 1: タスクの範囲（2026-10-30・研究者の回答）

- **採用**: 直す前後の比べまで。GSE の CPU の内訳の洗い出しと軽くする設計は別タスク。
- **却下**: 洗い出しまで含める／測らずに直すだけ。
- **理由**: 修正の PR を小さく保つ。

## 判断 2: テストの作り方（2026-10-30・研究者の回答 2 回）

- **採用**: 待ちの計算を `FlushClock`（時刻を引数で受ける小さな構造体）に切り出して単体テスト 3 本。加えて、code-reviewer の MEDIUM（単体テストはループからの呼び方の回帰を捕まえない）を受け、実際のロガーを動かしてループの周回数を数えるテスト `paused_logger_does_not_spin_past_flush_deadline` を足した。
- **周回数の数え方**: ロガーの個体ごとに `#[cfg(test)]` の `Arc<AtomicU64>` を持たせる。グローバルの数え上げは、並行して走るほかの logger のテストと混ざるので使わない。製品のビルドには入らない。
- **しきい値**: 200 周。周回数は届いた行の数と期限の回数で決まり、時間の揺れに左右されない（CI が遅くても増えない）。
- **変異で確かめた**: 元のバグに戻すと 383,764 周、ループから `on_tick` の呼び出しを消すと 373,319 周で赤。
- **トレードオフ**: テストに 6.5 秒かかる（並行で走るので全体の待ちは延びにくい）。

## 判断 3: 期限の判断をループの先頭に移した（設計の承認・2026-10-30）

- 先頭に置くと、一時停止中に行を落とす `continue` の道も期限の判断を通る。
- 正確に書くと、空回りを止める本体は「期限が来たら書いた行が無くても時計を進める」ほうで、判断を末尾に残しても、キューが空になった `Timeout` の周回で時計が進むので空回りは続かない（`continue` の道で余分に回るのは 1 周程度）。code-reviewer の「末尾に戻すと空回りが戻る」は言い過ぎで、変異 2 は「呼び出しを消す」で確かめた。先頭に置いたのは、判断を 1 か所にまとめて道ごとの違いを考えずに済ませるため。
- flush の時刻は変わらない（末尾で判断していたものを、次の周回の先頭で判断する。その間に待ちは入らない）。`End` と `Disconnected` はループを抜けた後の `writer.flush()` が従来どおり拾う。

## 判断 4: 長い空白の後の最初の行の書き出し（意図した変化・code-reviewer の LOW）

- 直す前は、長く何も書かなかった後に最初に来た行は、期限を過ぎていたのでその場で flush されていた（`last_flush` が古いまま残っていたため）。直した後は、次の期限まで最大 5 秒待つ。
- 「書いた行は最大 5 秒で書き出す」の約束の内側。落ちたときに失いうる範囲は、ほかの行と同じ最大 5 秒になる。

## 判断 5: O1 の配る版（2026-10-30・研究者の回答）

- **採用**: 配布物（v0.1.40）は差し替えず、次に版を切るときに修正を入れる。`docs/o1-distribution-tag.md` の v0.1.40 の節に注意を足した。
- **却下**: すぐ v0.1.41 を切る／被験者への案内だけ。
- **理由**: 一時停止中だけの欠陥で、記録の内容に影響しない。版を切り直すと配布の検算・Drive の差し替え・再送付が要る。
- **見直しタイミング**: 被験者が一時停止を長く使っている・電池や発熱の苦情が来たとき。

## 判断 6: 開発版の「停止中」では再現しなかった

- 直す前の開発版（非 O1・開始前の「停止中」）は 1.60%／0.75% で、空回りは起きなかった。この状態でも 1 秒ごとに `feat` が書かれていて `dirty` が立つため。試作の枝の run7 でなぜ `feat` が出ていなかったかは確かめていない（範囲外）。
- 一時停止は開始後のダッシュボードにしか出ないので、実機での確かめはロガーを実際に動かすテストに置き換えた（results.md の 2）。実機の開発版で一時停止中の CPU を測るのは、次に O1 の版を切るときの実機確認で行う。
