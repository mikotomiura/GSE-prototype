# decisions — G1 配布の自動化

## D-1: 配布の形 = アプリ共通 ＋ 課題文だけ被験者別

**決定**: Drive 上は次の 3 本立てにする。

```
GSE_ユーザー検証_G1_アプリダウンロードリンク/   (1FDkU52n9EXO92TzCieivexg7WKsXHkFP)
  G1_実施用_Windows/    ← 共通。exe×2 / bat / pubkey.txt / g1.mode / g1-submit.json
  G1_実施用_macOS/      ← 共通。dmg / g1.mode / g1-submit.json / README_先に読む.txt
  課題ページ_被験者別/
    <P-ID>/  block01..NN.html   ← 被験者ごと。★ シークレットを含まない
```

**理由**:
1. ★ **P-ID は配布物に焼き込まれていない**ので、アプリ本体を共通にしても
   `.age` の被験者分離は壊れない。分離を担っているのは被験者がアプリに入力する P-ID である。
   - `src-tauri/src/submission.rs:165` — `format!("{participant}_block{block:02}_{stem}.age")`
   - `src-tauri/src/submission.rs:143` `g1_start_gate` — G1 モードで妥当な ID が無ければ開始不可
     (`submission.rs:414-419` にテスト: `None`/空/`../etc`/`P 12` は err、`P012` は ok)
   - `src/App.tsx:499-521, 756-766` — 入力欄と「開始する」の gate（現行 main で健在）
   - `src-tauri/src/lib.rs:1113` — 保存値 (`~/.gse/g1_participant_id`) を読むだけ。生成はしない
2. 被験者別フォルダに `g1-submit.json`（共有シークレット）の複製が増えない
3. 被験者ごとに新規アップロードが要るのは `block*.html`（9KB 前後 × 8〜10 枚）だけになる。
   ★ 10MB の exe/dmg を MCP の base64 で通すのは非現実的なので、これは実現可能性の条件でもある

**却下案**:
- **被験者ごとに丸ごと 1 フォルダ**: 被験者のダウンロードが 1 回で済むが、
  ⚠️ シークレットの複製が人数分増える。バイナリは `copy_file` でサーバ側複製でき
  コストは低いが、露出面が増える側の設計である。

**代償（受け入れる）**: 被験者のダウンロードが 2 回になる。→ README の書き換えが要る（D-4）。

## D-2: 共有範囲 = 現状維持（リンクを知っている全員）

**決定**: `anyone: reader` のまま。被験者ごとの個別招待はしない。

**理由**: Drive の**権限設定 API が MCP に無い**ため、個別招待にするとフォルダ 1 つにつき
Drive 画面で 1 回手作業が発生し、「手作業を減らす」という本タスクの目的と逆向きになる。

**⚠️ 残る露出（記録しておく）**: `g1-submit.json` は共通フォルダにあり `anyone: reader` である。
リンクが漏れると第三者が受け口へ偽の記録を投げられる（`GSE_G1_Submit.gs:129` の
`secretMatches_` を通ってしまう）。中身は pubkey 暗号なので読めないが、フォルダは汚れる。
→ 根を潰す設計（受け口側を P-ID ベース検証にする等）は**別タスク**。

## D-3: 事前資料メール = 完全自動（時間トリガー）

**決定**: 「G1 実施トラッキング」に配布 URL の列を足し、研究者が URL を貼ったら
時間トリガーが拾って送る。

**理由**: 関数セレクタが引数を渡せない以上、3 引数関数は研究者がラッパーを手書きしないと
実行できない。URL を 1 か所に貼る形にすれば入力は 1 回で済み、実行操作が消える。

**⚠️ 送信は取り消せない**ので、次の 4 つを fail-closed で付ける（ユーザー確認は取っていない。
いずれも一方向にしか効かない安全弁なので既定で入れる）:

1. **URL 形式検査** — `https://drive.google.com/` で始まること
2. **冪等** — 「課題文リンク送信日」が空の行だけに送る
3. **1 回の発火あたりの人数上限** — 既定 3 人。列の貼り間違いが一斉送信になる事故を頑健に抑える
4. **キルスイッチ** — Script Properties 1 値でトリガー送信を即時停止

## D-4: macOS README から落ちた 3 指示を復活させる

**決定**: `dist-readme-macos.txt` を分割配布に合わせて書き直し、
`§2.13` / `§2.14-2` 由来の 3 指示は**残す**。

**理由**: 2026-08-07 に Drive へ上がった README（3,105 B）はローカル生成物（3,470 B）から
「【5】課題のページ」節がまるごと欠けていた（byte diff で確認）。落ちていたのは:

- 「block01 → block02 … 番号の順に 1 つだけ開く」= `§2.13`
- 「先にページを開いてから開始を押す（開いた時点から 5 分）」= `§2.14-6` が事後実測する当のもの
- 「次の回のページを先に開かない」= `§2.14-2`「在宅では提示順を伏せられない」への唯一の手続き的抑止

★ 在宅実施ではこれが実験者の統制の代わりなので、落としたままにできない。

## D-6: cross-review で足したガード 2 本と後始末（2026-08-07）

`/cross-review`（Claude code-reviewer + Codex）の指摘を **4 件すべて採用**した。
★ どれも「メール送信は取り消せない」領域で、既存 4 ガードの**外側**にあった。

| # | 指摘元 | 何 | 直し方 |
|---|---|---|---|
| 1 | ★ Codex 単独 | `LockService` が無い。トリガーの重なり／手動実行との衝突で「送信日が空」を 2 つの実行が同時に見て**同じ人に 2 通**行く | 収集〜記録を `LockService` で囲む。取れなければ何もしない |
| 2 | 両者一致 | URL ガードは**形式**しか見ず、**宛先の正しさ**を見ていない | ガード 5 を追加。同じ URL が 2 人以上に貼られていたら送らない（★ 送信済みの行も数に入れる） |
| 3 | Claude 単独 | `sendTaskMaterialsEmail` は送信日の書き込み失敗を握りつぶす。人が 1 件ずつ呼んでいた頃はログで気づけたが、★ トリガー化でその人間のチェックが消えた → **次の発火で再送**される | 送信後に送信日を**読み直し**、空なら補って書く。それも駄目なら備考に出す |
| 4 | Claude 単独 | `make-upload-manifest.sh` の glob が 0 件のときリテラルのまま残り、**原因を取り違えさせるエラー**になる | `shopt -s nullglob` |

★ 1 と 4 は**実測で裏を取ってから**直した:
- `LockService` は `onG1ConsentSubmit`（`GSE_G1_Form_Builder.gs:1736`）で既に使われている = 新関数だけ欠けていた
- bash の glob 非展開は `for f in <空dir>/block*.html` で `f=<dir>/block*.html` になることを実測

⚠️ ★ **副産物**: ガード 5 を足したらテスト「1 回の上限」が赤になった。
4 人に**同じ URL** を渡すテストデータだったためで、**ガードが正しく働いた**。
テスト側を実態（被験者ごとに別フォルダ = 別 URL）に直した。

## D-7: 被験者別の親を**非公開**に戻し、フォルダ実体の検査（ガード 7）を足す

**決定**（2026-08-07・ユーザー指摘を受けて D-1/D-2 を一部改める）:
`G1_課題ページ_被験者別`（`1qhl28IDeh-19upuZf_YxPwwdq_d9xVcI`）を**制限付き（非公開）**にし、
被験者フォルダを 1 つずつ「リンクを知っている全員（閲覧者）」にする。

**きっかけ**: ユーザーの「そのP0xxなどが他のユーザーにも映る感じに今なってない？」

⚠️★ **私の誤り**: README と `.idea` に
「**Drive は子リンクから親へ遡れないので、直リンクだけなら他は見えない**」と書いていたが、
これは **実測せずに書いた断定**だった。撤回した（`verify-before-claiming`）。

**実測できたこと / できなかったこと**:
- ✅ 匿名 GET した子フォルダの初期 HTML に親 ID も親フォルダ名も出ない（親 ID 出現 0 回）
- ❌ ログアウト状態の Drive UI で親へ遡れるかは**別アカウントが無く試せていない**
  （Drive は JS で後からデータを取るので、初期 HTML は証明にならない）

**判断の根拠を差し替えた**: 遡れるかどうかに依存しない、確実な事実で決めた。
★ 親がリンク共有だと、被験者へ送る URL を**親のほうにした 1 回**で全員分が渡る = **fail-open**。
親が非公開なら同じ取り違えは「アクセス権が必要です」で止まる = **fail-closed**。
⚠️ 親リンクは `.idea/短縮版リンク集.md` にも載っているので、取り違えの経路は実在する。

**代償と、その受け皿**: 被験者ごとに共有操作が 1 回増える（Drive の権限設定 API は MCP に無い）。
★ **共有し忘れると「届いたが開けない」**という新しい失敗経路が生まれるので、
`g1MaterialsFolderProblem_`（ガード 7）を足して Drive の実体を検査する:

| 止める事故 | 検査 |
|---|---|
| ★★ 親フォルダの URL を貼った | ID が `G1_MATERIALS_PARENT_ID` と一致 |
| ★ 別の被験者のフォルダ | フォルダ名 ≠ P-ID |
| 置き場所違い | 親が `G1_MATERIALS_PARENT_ID` でない |
| ⚠️ **共有し忘れ** | `getSharingAccess()` が `ANYONE_WITH_LINK`/`ANYONE` でない |
| 消された / ID 違い | `getFolderById` が投げる |

⚠️ ★ **DriveApp のスコープが増える**ので、`.gs` 貼り直し後の初回実行で再承認が要る。
承認するまで自動送信は走らない（安全側）。
⚠️ ★ フォルダを作り直したら `G1_MATERIALS_PARENT_ID` も直すこと。

## D-8: 受付メールにアプリのリンクを入れ、トラッキング表の導出列を自動集計する

**きっかけ**（2026-08-07・ユーザーが G1-C を実際に回して発見）:
「アプリ自体のダウンロードリンクが無い / 課題文フォルダのリンク提供も無い /
実施予定日・実施日などの記述は不要では / スプシの記述の自動化ができていない」

### D-8a: 受付メールにアプリのリンクを入れる（★ 本当の欠落だった）

★ 入れない理由が無かった。アプリは**全員共通**で、`§2.12` が伏せると宣言した項目
（題材・課題の型・難易度・条件名・提示順・他人の割付）を **1 つも開示しない**。
⚠️ 2 便に分けた理由（`g1RegisterAckBody_` のコメント）は「割付がまだ無い」「題材名が提示順を示唆する」で、
★ **どちらもアプリには当てはまらない**。分割の理由を課題ページ以外にも広げてしまっていた。

⚠️ ★ 早く渡すことに実質的な意味がある: macOS は初回に入力監視の許可 → 開き直しが要るので、
当日その場で詰まると **1 回きりの実施機会**（`§2.3` は分割を許さない）を潰しかねない。

### D-8b: 事前資料メールの「閲覧のみ」を撤回

⚠️ ★ 本文は「■ 資料（閲覧のみ）」と書いていたが、**実態と食い違っていた**。
`§2.14`（第 9 版）で無人在宅を正規の実施形態にした時点で、被験者は `blockNN.html` を
手元に持って自分で開く（`§2.13`）。→ ダウンロードして**アプリのフォルダに移す**手順に書き換えた。

⚠️ ★ これは私が作った食い違いではなく、`§2.12`（閲覧のみで開示する）と `§2.14`（在宅）の
**preregistration 側の緊張**である。メールで取り繕う問題ではないので、事実を書くほうに倒した。
`§2.12` 自身も「防ぎ切ることを前提にしない」と書いている。

### D-8c: 導出列の自動集計（`refreshG1RunSheet`）

⚠️ ★ 20 列のうち自動で埋まるのは 3 列だけだった（`P-ID` / `課題文リンク送信日` / `備考`）。
★ **「写すだけの列」= どこかに真実源がある列**を機械が埋める:

| 列 | 真実源 |
|---|---|
| `G1-C 同意` | 行の存在そのもの（行は提出でしか作られない） |
| `G1-M 回答数(/7)` | G1-M の回答（被験者IDごとのブロック番号の異なり数） |
| `G1-S 回答` | G1-S の回答 |
| `完了ブロック数(/10)` | 受け口の `.age`（`P0XX_blockNN_…` の異なる NN の数） |
| `実施日` | 同上（最も早い `gse_YYYYMMDD`）。⚠️ **空のときだけ**書く |

⚠️★★ **判定に関わる列は 1 つも触らない**。`実施形態` `配置(A/B)` `撤回/除外` `verify-blocks 実施`
`validate_blocks 緑` `gse-dataset 送付` は**人の判断**であり、`§3.6` は事後除外を禁じている。
★ 機械が埋めると「判断したことになってしまう」ので、ここは自動化してはならない。

### D-8d: 列の要否 — ★ `実施形態` は消せない

| 列 | 判定 | 根拠 |
|---|---|---|
| `実施形態` | ⚠️★★ **消せない** | `§2.14-3` の報告義務（来所 n / 在宅 n を必ず併記）。★ 保存先がここしか無い。2026-08-04 の cross-review で Codex が指摘して足した列である |
| `実施日` | ★ **残す**（自動で埋まるようにした） | `§2.14-6` の逸脱事後検出の起点 |
| `HMM_VERSION` / `配置(A/B)` / `verify-blocks 実施` / `gse-dataset 送付` | 残す | preregistration に 7〜11 件の言及があり、運用の契約に組み込まれている |
| `実施予定日` | ⚠️ **消してよい**（事前登録に言及なし・日程はメールに書かない運用） | ただし記録スキーマの変更なので**今回は触らない**。消すなら `migrateRunSheetAddUrlColumn` と同型の移行関数を書くこと |
