# 重要な設計判断

## 判断 1: `--cleanup` の失敗を **非 0** で返す（★ 契約変更）

- **判断日時**: 2026-09-21
- **背景**: 起票 18 の核心は「撤去できていないのに **exit 0 / `cleanup 完了`**」である。
  ★ 報告文だけ直して exit 0 のままにすると、⚠️ **スクリプトから呼んだ側には依然として嘘が伝わる**。
- **選択肢**:
  - A: 文言だけ直し、exit 0 は維持する（★ 後方互換）
  - B: 撤去できなかったものが 1 件でもあれば **exit 1**
- **採用**: **B**
- **理由**: ★ 2026-09-21 に repo 全体を grep し、**`--cleanup` の呼び出し元は人間だけ**であることを
  確認した（⚠️ `scripts/loop-run.sh:204` は復旧手順を**文言で案内している**だけで実行していない）。
  → ★ 自動経路を壊さずに fail-loud にできる。
- **トレードオフ**: ⚠️ 「未 merge のブランチが残る」正常な運用でも非 0 になる。
  → ★ だから**メッセージで `git branch -D` を案内する**（★ 黙って `-D` はしない = 判断 2）。
- **影響範囲**: `scripts/loop-spawn.sh` の `--cleanup` 分岐のみ。
- **見直しタイミング**: ★ `--cleanup` を自動経路（モードC 等）から呼ぶようになったとき。

## 判断 2: 残っているものを **黙って強制削除しない**

- **判断日時**: 2026-09-21
- **背景**: 「撤去できない」を消す最短経路は `git branch -D` と `rm -rf` である。
- **採用**: ★ **`-d` まで / `rm` はしない**。撤去できなければ**報告して人に渡す**。
- **理由**: ★ 先例がある —— `loop-spawn.sh` の `abort_worktree` は逐語
  「⚠️★★★ **`-D` を無条件で使わない**（★ Codex /cross-review 1 巡目 MEDIUM）」を持ち、
  **作成時の commit から動いていないときだけ**消す設計になっている。
  ⚠️ `--cleanup` は**人が merge 後に叩く**ので、未 merge ＝ 想定外の状態であり、
  ★ そこで消すと**作業を黙って捨てる**。
- **トレードオフ**: ⚠️ 手作業が 1 回増える。★ ただし失われるものが無い側に倒した。

## 判断 3: 一致規則を **branch ∪ path** にし、前方一致に区切り `-` を要求する

- **判断日時**: 2026-09-21
- **背景**: 起票 18 の直し方 1 は「パスでも引く」。★ 実装中に**別の穴**が見つかった ——
  旧 `$0 ~ ("loop/" id)` は **awk の正規表現の部分一致**なので、
  ⚠️ `--cleanup 005` が `loop/0055-t` にも当たる（★ 実測: 旧実装は 2 本ヒットし、
  複数行を 1 引数に渡して `git worktree remove` が失敗 → **どちらも撤去できず** exit 0）。
- **採用**: `loop/<id>` **完全一致** ∪ `loop/<id>-` **前方一致**（path 側も同型）。
- **理由**: ★ `scripts/loop-run.sh:201` の `ensure_branch` が既に
  `"loop/$id"|"loop/$id-"*` という**同じ規則**を持っている（★ 規則を 2 つに増やさない）。
  ★ 完全一致も許すのは、`--cleanup 001-issue` のように `<id>-<short>` を丸ごと渡す運用が
  実在するため（`.steering/_handoff/next-session-issue001-pause-const-arbitration.md:123` 逐語）。
- **影響範囲**: ⚠️ **挙動が変わる**: これまで巻き込んでいた別 id を巻き込まなくなる（★ 意図した変更）。

## 判断 4: 残存ディレクトリの網は「**処理したものだけ**除外する」

- **判断日時**: 2026-09-21
- **背景**: 最初の実装は「登録に残っているものは報告済みなので除外」としていた。
  ⚠️ これだと**一致規則が退行して worktree を拾えなくなったとき**、
  ★ 登録に在るという理由で除外され、**黙って「完了」に化ける**（＝ 起票 18 の再来）。
- **採用**: ★ 上のループで**実際に触った basename** だけを除外し、それ以外は報告して `left` に数える。
- **理由**: ★ 一致規則そのものが壊れたときに鳴る**最後の網**が要る。
  ⚠️ 実際、変異テスト（path 系統を潰す）では**この網だけが非 0 を出している**（2026-09-21 に実測）。
- **トレードオフ**: ★ 網は `../wt/` 直下しか見ないので、**worktree を別の場所へ移された形は拾えない**
  （⚠️ 拾えないことを隠さない）。

## 判断 5: 撤去の確認に **フルパス比較を使わない**

- **判断日時**: 2026-09-21
- **背景**: ⚠️ git-bash で実測（2026-09-21）: `git worktree list` は `C:/wt/…` を、
  bash の `pwd` は `/c/wt/…` を返す。★ 同じ worktree が**別の文字列**になる。
- **採用**: ★ **basename で突き合わせる**（★ 既存の stale 検出も basename 比較を使っている）。
  ⚠️ フルパス比較は「git の出力同士」に限る。
- **影響範囲**: ★ この規則が退行すると **ubuntu では緑のまま Windows だけ壊れる**
  → ★ だから CI は **両 OS に配線**した（`docs/agent-shared.md` の「OS ごとに対のテスト」）。

## 判断 6: 検査で `grep -q` をパイプの終端に置かない

- **判断日時**: 2026-09-21
- **背景**: `set -o pipefail` 下で `... | grep -q` は、★ **一致した瞬間に grep が終了**して
  上流へ SIGPIPE が飛び、⚠️ **パイプライン全体が非 0** になりうる。
  → ★ 「一致したのに『していない』と読む」＝ **検査が静かに反転する**。
- **採用**: ★ `grep -c`（全部読む）＋ 件数比較、または改行を番兵にした `case` 完全一致。
- **影響範囲**: `scripts/loop-spawn.sh` の `contains_line` / `scripts/loop-spawn-cleanup-test.sh` の `wt_has`。

## 判断 7: `repo_root` は **main worktree** から解決する（★ `--show-toplevel` を使わない）

- **判断日時**: 2026-09-21（★ `code-reviewer` HIGH → **メインが独立に再現**して確認）
- **背景**: ⚠️ `git rev-parse --show-toplevel` は **linked worktree の中では worktree 自身**を返す。
  ★ 実測（使い捨て repo）:

  ```text
  $ (cd $T/wt/repo-002-t && bash $T/repo/scripts/loop-spawn.sh --cleanup 002)
  loop-spawn: ★ branch 撤去: loop/002-t
  loop-spawn: cleanup 完了 issue 002 (worktree 0 件 / branch 1 件 を撤去)   ← ⚠️ rc=0
  $ git -C $T/repo worktree list
  .../wt/repo-002-t  [deviated]      ← ★ 残っている
  ```

  → ⚠️★★★ **本タスクが契約にした「撤去できていないのに完了と書かない」が破れていた。**
  ★ 原因は 1 つだが**壊れ方が 3 段**である: `repo_name` が `<repo>-<id>-<short>` に化けるため
  (1) path 系統が永久に当たらない (2) main checkout ガードが**本物の main を守らない**
  (3) 残存 dir の網が存在しないパスを見る。
- **選択肢**:
  - A: **main worktree を解決して、そこで処理する**
  - B: fail-closed —— `--git-dir` と `--git-common-dir` が違えば「main checkout から実行してください」と `die`
- **採用**: **A**
- **理由**: ★ `git worktree list --porcelain` は **main worktree を必ず先頭に出す**ので確実に取れる。
  ⚠️ B は「worktree に居るまま別 id を片付ける」という正当な操作まで拒否する。
  ★ A なら `--cleanup` だけでなく **spawn 経路も正しくなる**（⚠️ worktree の中から spawn すると
  `../wt/<worktree名>-…` という入れ子ができる形も同時に塞がる）。
- **トレードオフ**: ★ 起動位置によって処理対象が動くので、**移動したことを stderr に明示**する。
- **影響範囲**: `scripts/loop-spawn.sh` の全経路（★ `--cleanup` / spawn / `--no-exec`）。

## 判断 8: id を **文字集合で検証**する（⚠️ glob を `git branch --list` へ通さない）

- **判断日時**: 2026-09-21（★ `security-checker` MEDIUM）
- **背景**: ⚠️ `git branch --list` の引数は **fnmatch パターン**である。
  → `--cleanup '*'` は `loop/*` / `loop/*-*` に化け、★ **merge 済みの `loop/*` が全部 `-d` の対象**になる。
  ⚠️ 一方 worktree 側は `==` / `index()` の **literal 比較**なので 1 件も当たらない。
  → ★★★ **両系統の広さが非対称**（branch だけ全部消え、worktree は 1 件も消えない）。
- **採用**: ★ `[A-Za-z0-9._-]` のみ許可・`-` 始まり禁止。それ以外は `die`。
- **理由**: ★ 1 行で 3 つ閉じる —— (a) glob の拡大 (b) `..` / `/` で `../wt/` の外を指す形
  (c) `awk -v` がエスケープ列を解釈して**シェル側の glob と awk 側の一致文字列がずれる**形。
- **トレードオフ**: ⚠️ 記号を含む id を将来使えない。★ 実在の id（`001` / `zzz` / `001-issue`）はすべて通る。

## 判断 9: **未コミット変更がある worktree は撤去しない**

- **判断日時**: 2026-09-21（★ `security-checker` MEDIUM）
- **背景**: ⚠️ 旧実装は `git worktree remove` が失敗したら **無条件に `--force`** を撃ち、
  しかも出力を `/dev/null` に捨てていた。★ 本タスクで一致規則を **path 系統へ広げた**ので、
  ⚠️ `--force` が届く範囲も広がった。★ 起票 10 の「逸脱した worktree」は
  **worker が別ブランチで作業した跡**＝未コミット変更が載っている可能性が最も高い対象である。
- **採用**: ★ `git -C <wt> status --porcelain` が非空なら **撤去せず** `left` に数えて人へ渡す。
  ⚠️ `--force` へ落ちるときは **stderr に 1 行出す**（★ 黙らない）。
- **理由**: ★ 判断 2（`-D` を使わない）と**同じ理屈**である。⚠️ branch 側だけ自制して
  worktree 側が無条件に強制削除するのは筋が通らない。
- **トレードオフ**: ⚠️ 「撤去できない」が増える。★ ただし**失われるものが無い側**に倒した。

## 判断 10: ⚠️ `check` job の `permissions:` は**本タスクで触らない**

- **判断日時**: 2026-09-21（★ `security-checker` LOW-5）
- **背景**: ★ `frontend-check` は `permissions: contents: read` を明示しているが、
  ⚠️ 新 step を足した `check` job には無く、リポジトリ既定の `GITHUB_TOKEN` 権限が渡る。
- **採用**: ⚠️ **本タスクでは変更しない。★ 起票 24 として登録する。**
- **理由**: ★ **本コミットが作った穴ではない**（既存条件）。
  ⚠️ `check` job は release 経路も担うので、権限を絞ると**別の job が無言で壊れうる**。
  → ★ 影響範囲の確認（release / tag 経路）を伴う**独立したタスク**にする。

## 判断 11: path 系統は **`../wt/` 直下に限る**（★ basename 一致だけでは広すぎた）

- **判断日時**: 2026-09-21（★ `/cross-review` 1 巡目の指摘で足したテストが**実害を検出**した）
- **背景**: ⚠️ Codex は「撤去**確認**が basename なので誤爆しうる」と指摘した。
  ★ それを確かめるテスト（別パスに同名 worktree を置く）を書いたところ、
  ⚠️★★★ **確認だけでなく *一致規則そのもの* が広すぎた** ——
  `--cleanup 013` が `../other/<repo>-013-t`（★ 別の場所・`loop/*` でもない枝）を**実際に撤去した**。
- **採用**: ★ path 系統に **`<repo_root の親>/wt/` 直下であること**を追加条件にする
  （⚠️ `repo_root` は git 由来なので、文字列の組み立てで表記が揃う）。
- **理由**: ★ 本スクリプトが作る worktree は**必ず `../wt/` 直下**である（`wtdir` の定義）。
  ⚠️ 名前が合うだけで撤去すると、**人が別の目的で置いた worktree を壊す**。
- **トレードオフ**: ⚠️ **置き場を移された worktree は path 系統で拾えない**
  （★ branch 系統が `loop/<id>` なら拾う。⚠️ 両方外れたものは拾えない —— 判断 4 の限界と同じ）。
- ★ **副産物**: 撤去の**確認**も basename → パス比較へ直した（⚠️ 比べる両辺とも git の出力である）。

## 判断 12: ⚠️ Codex の「HIGH: pipefail が無い」は **誤検出**だった（★ 一次で確認）

- **判断日時**: 2026-09-21
- **内容**: Codex は逐語「ファイル先頭に `set -uo pipefail` しかない」として
  `wts="$(... | awk ...)" || die` を fail-open と判定した。
- ⚠️★★★ **一次では `scripts/loop-spawn.sh:8` が `set -euo pipefail` である。**
  ★ `set -euo pipefail` 下で `v="$( (exit 3) | awk '{print}' )" || echo …` を走らせ、
  **`||` が発火すること**を実測した。→ ★ **指摘は成立しない。**
  ⚠️ `set -uo pipefail` なのは **テスト側**（`loop-spawn-cleanup-test.sh:30`）であり、
  ★ Codex は 2 ファイルを取り違えたと見られる。
- ★ **記録する理由**: ⚠️ 次に同じ指摘が来たときに**また調べ直さないため**。
