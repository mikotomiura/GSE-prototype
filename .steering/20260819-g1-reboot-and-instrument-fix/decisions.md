## 判断 1: 本セッションの実装範囲は **ADR-013 → G-1 の両方**

- **判断日時**: 2026-08-19 (grill)
- **背景**: リブート決定により「G1 実施中だから `src-tauri/` に触れない」制約 (ADR-013 §Context-3 / D5) が
  外れた。停止期間をそのまま実装窓に使えるが、範囲を先に決めないと `HMM_VERSION` / ゴールデン 6 本 /
  schema parity / 両 OS の対のテストの負荷が読めない。
- **選択肢**:
  - A: ADR-013 → G-1 の両方
  - B: ADR-013 のみ (G-1 は設計まで)
  - C: 設計のみ
  - D: 全部 (+ App.tsx lock 解除の実装)
- **採用**: **A**
- **理由**: handoff §9 の順序 (**ADR-013 実装 → G-1 修正 → 検証 → 凍結 → 募集 → 収集開始**) を
  1 セッションで満たす最短経路。⚠️ **収集開始より後に計器を直すと、本タスク群の動機である
  「計器がコホートを跨げなかった」失敗 (既に 2 件) を 3 件目として自分で作る**。
  D を採らないのは、lock 解除が判断 5 (宣言の扱い) に依存し、かつ `scope_fit` 未実装のまま
  **観測不能な交絡**を通常運用に入れてしまうため。
- **トレードオフ**: App.tsx lock 解除が本セッションでは進まない (方針の凍結のみ)。
- **影響範囲**: `src-tauri/src/{lib.rs,logger.rs,schema_dto.rs,input/liveness.rs}` / `schema/current.json`
- **見直しタイミング**: `HMM_VERSION` を上げないとゴールデンが緑にならない場合 (= additive でない証拠)

## 判断 4: 中断ブロックは提出のブロック**番号を消費させる** (提出番号 = 試行の連番)

- **判断日時**: 2026-08-19 (grill)
- **背景**: ⚠️ handoff §2 は「`G1_BLOCKS_STARTED` の増やし方を必ず設計に含めること。ここが崩れると
  提出のブロック番号がずれる」と書いていたが、**実測ではそうなっていない**:
  提出のブロック番号は `reconcile.rs:236 next_block_number` が **`.age` 名と `manifest.jsonl` の
  最大値 + 1** (ディスク突き合わせ) で決めており、`G1_BLOCKS_STARTED` は**ローテート要否
  (`blocks_started > 0`) だけ**を決める (`submission.rs:23` 逐語「**永続カウンタを作らない**」)。
  → ★ 実際に立つ分岐は「**閉じてから開く**と中断分が `.age` 化して番号を 1 つ消費する」ことである。
- **選択肢**:
  - A: 消費させる (提出番号 = 試行の連番)
  - B: `manifest.jsonl` に中断印を additive に付ける
  - C: 中断分は `.age` にしない
- **採用**: **A**
- **理由**: 実装ゼロで、`submission.rs` の設計思想 (**数えるのではなく突き合わせる**) を 1 文字も
  変えない。C は handoff §2 の採用理由「**失敗した試行も別ファイルとして残る (★ 捨てない)**」に反し、
  中断の事実自体が観測データである (P010 block07 の解析はそれで成立した)。
  B は `manifest.jsonl` のスキーマと提出側の検査を同時に触ることになり、本リブートの範囲を超える。
- **トレードオフ**: ⚠️ 提出物の連番は「プロトコルのブロック番号」ではなく「**試行の連番**」になる。
  研究者は `manifest.jsonl` と NDJSON の中身で対応を復元する (★ P010 block07 と**同型の作業**が残る)。
  → ★ **この非対応を `protocol.md` / `data.md` に明記して、後から驚かないようにする。**
- **影響範囲**: `experiments/20260801-controlled-friction-task/{protocol.md,data.md}` (記述のみ)
- **見直しタイミング**: 中断が常態化した場合 (★ そのとき B へ上げる)

## 判断 5: 宣言 (`task_kind`) は **ADR-010 D3 の写し** — routing のみに使い、正しくさせようとしない

- **判断日時**: 2026-08-19 (grill)
- **背景**: `task-adaptation-and-scope-gating.md §2.1` 逐語「**UI ロックは宣言する能力を奪うだけで、
  実際の作業を拘束しない → 交絡は除去されたのではなく不可視化された**」。
  lock を外す段で宣言をどう扱うかを決めないと、外した瞬間に方針が空白になる。
- **選択肢**:
  - A: ADR-010 D3 の写し (宣言は routing のみ・観測は `scope_fit` のみ・融合しない)
  - B: `scope_fit` 実装まで lock を外さない
  - C: 宣言自体を廃止する
- **採用**: **A**
- **理由**: ★ **新しい原則を持ち込まない**。既存決定 (ADR-010 D3) の写しで済む。
  宣言が外れることを前提にし、検出は `scope_fit` で `evidence_quality` を下げる形に後置する。
  B は ADR-006 の 2a/2b (2026-08-18 実装済み) が引き続き 1 度も効かない状態を延長し、
  `scope_fit` の定数が R-F1 (較正プロトコル) からしか出ない以上、判断 3 により**待ちが長い**。
  C は ADR-006 で配線済みの head 切替を殺し、Phase1 の `session_meta` の連続性も切る。
- **トレードオフ**: ⚠️ **lock を外してから `scope_fit` が入るまでの期間は、宣言が外れても検出できない。**
  → ★ その期間のセッションは「宣言は観測ではない」と明記して扱う。
- **影響範囲**: `src/App.tsx` (将来) / `docs/architecture/task-adaptation-and-scope-gating.md` /
  ADR-010 (Proposed のまま。★ 本判断は ADR-010 を先取りするものではなく、**その写しを lock 解除に適用する**という運用判断)
- **見直しタイミング**: `scope_fit` 実装時 (ADR-010 の採用ゲート通過時)

## 判断 8: `!was_active` は**外さず**、`was_active` 側に別経路を足す

- **判断日時**: 2026-08-19 (設計)
- **背景**: handoff §2 逐語「⚠️★★★ **`!was_active` を単純に外してはならない**」。その条件が置かれた
  理由は `lib.rs:2004-2007` 逐語「`record_session_meta` 失敗時の文言は**明示的に再押下を促す**ので、
  無条件に数えると**孤児ファイルが 1 本増える** (code-review HIGH)」。
- **選択肢**:
  - A: `!was_active` の枝はそのまま (新規ブロック) / `was_active` の枝に「閉じてから開く」を足す
  - B: `!was_active` を外して無条件にローテート
- **採用**: **A**
- **理由**: ⚠️ 上の code-review HIGH は**「数える」ことへの指摘**であり、「閉じてから開く」は
  数える話ではない。→ 分けて書けば両立する。★ ただし **`record_session_meta` 失敗後の再押下**も
  `was_active == true` で入ってくるので、⚠️ **この経路では前セッションが「打鍵ゼロで閉じられる」**
  ことになる (孤児ファイルが 1 本残る)。
  ⚠️★★★ **【2026-08-19 訂正・判断 12】ここに書いた「提出側の `has_any_data_row` が
  二重化として効いており `.age` 化されないので提出は汚れない」は *誤り* である。**
  ★ 実測すると同関数が読み飛ばすのは `meta` / `hook_health` / `ime_state` **だけ**で、
  **`session_start` 行があるファイルは `true` を返す** → **提出され、番号を 1 つ消費する**。
  ★ handoff §2 の同趣旨の記述をそのまま採ったのが原因である。
  → ★ **判断 12** で、`record_session_meta` 失敗後の再押下では**ログを 1 行も書かない**ようにした。
- **トレードオフ**: 中断ファイルが増える。判断 4 のとおり番号は消費される。
- **影響範囲**: `src-tauri/src/lib.rs` (`start_session`)
- **見直しタイミング**: `has_any_data_row` の緩和規則を変えるとき

## 判断 9: 容量ガードは **G1 モードのときだけ**掛ける

- **判断日時**: 2026-08-19 (実装中の自己レビューで発見)
- **背景**: 「触る前に断る」ガード (判断 1 / design v2 §1.1) を `start_session` の先頭に置いたが、
  ⚠️ **無条件だと通常運用にも掛かる**。通常運用では従来 `let _ = tx.try_send(SessionStart)` で
  **失敗を握りつぶして開始していた**ので、★ **これまで開始できていた場面で開始できなくなる**。
- **選択肢**:
  - A: G1 モードのときだけ検査する
  - B: 無条件に検査する (通常運用も fail-loud にする)
  - C: 必要スロット数を経路ごとに変える (G1=2 / 通常=1)
- **採用**: **A**
- **理由**: ⚠️ ガードの目的は「`Rotate` + `SessionStart` の 2 通が**途中で切れる**」ことの防止であり、
  ★ **通常運用は `Rotate` を送らないのでその失敗様式が存在しない**。
  B は挙動の変更であり、研究者決定 #2「リブートの範囲は計器＋運用」の外に出る
  (⚠️ B のほうが望ましいという議論は成り立つが、**本タスクで決めることではない**)。
  C は A と同じ効果を回りくどく書くだけである。
- **トレードオフ**: ⚠️ 通常運用では、channel が満杯のとき **`session_start` 行が黙って落ちる**
  従来の挙動が残る (★ 既知の穴として据え置く)。
- **影響範囲**: `src-tauri/src/lib.rs` (`start_session` 冒頭)
- **見直しタイミング**: 通常運用も fail-loud にすると決めたとき (★ 別タスクで裁く)

## 判断 10: `swap` を**ログのロックの中**へ移す (同時押下の交錯を閉じる)

- **判断日時**: 2026-08-19 (実装後の自己レビューで発見)
- **背景**: ⚠️★★★ 「開始する」は**送信中に disabled にならない**ので、2 回続けて押すと
  `start_session` が**並行に走りうる**。`session_active.swap` は「どちらが新規か」を決めるが、
  ⚠️ **ログへ書く順序までは決めない**。→ 次の交錯が残っていた:
  `A(新規) swap → B(再押下) swap → **B が先に log ロックを取ってローテート** →
  B が SessionStart → **その後 A が SessionStart**` ＝ ⚠️ **新ファイルに `session_start` 2 本**
  （★ **P010 block07 と同じ形**であり、G-1 修正の目的そのものを取り逃がす）。
- **選択肢**:
  - A: `swap` を `log.lock()` の**中**へ移す
  - B: `session_active` とは別に「開始処理中」フラグを足して排他する
  - C: フロント (`App.tsx`) でボタンを disabled にする
- **採用**: **A**
- **理由**: ★ 「誰が新規か」と「何を書くか」が**同一のロックの下で**決まるので、
  押した順に `file1 → (閉じる) → file2` と**必ず 1 本ずつ**になる。新しい状態を足さない。
  B は状態が増え、⚠️ 失敗経路でのリセット漏れが新しい穴になる。
  C は ⚠️ **バックエンド側の保証にならない** (DevTools から直接 invoke できる。
  `g1_start_gate` を二重ゲートにしたのと同じ理由)。
- **⚠️ ロック順序の確認**: `intervention` → `log` の順で取る箇所が既にある
  (`force_wall_decision` 周辺・`lib.rs:546-549`)。→ ★ **`latest_feat` / `intervention` の更新は
  `log.lock()` より前に置いたまま**にし、入れ子にしない (反転させない)。
- **トレードオフ**: ⚠️ `swap` が `latest_feat` / `intervention` のリセットより**後**になる。
  ★ 「reset を `session_active = true` より前に」という元の不変条件は**保たれている**
  (むしろ余裕が増える)。
- **影響範囲**: `src-tauri/src/lib.rs` (`start_session`)
- **見直しタイミング**: `start_session` に新しい共有状態を足すとき (★ ロック順序を再確認する)

## 判断 11: `capabilities` に **第 3 群 `config_gated`** を足す (ADR-013 の改訂)

- **判断日時**: 2026-08-19 (code-reviewer HIGH)
- **背景**: ⚠️★★★ 初版実装は `probe_assignment` / `realtime_label` /

- **選択肢**:
  - A: 第 3 群 `config_gated` を足す (ADR-013 D1 を改訂)
  - B: 当該 4 行種を `threshold_gated` へ移す (ADR は無改訂)
  - C: `unconditional()` を `g1_mode` / `intervention_enabled` の**実値**で組み立てる
- **採用**: **A**
- **理由**: ★ 「0 行が何を意味するか」は **閾値**と**設定**で理由が違うので、
  群を分けたほうが解析側が正しく読める。B は動くが「閾値ゲート」という名前が嘘になる。
  ⚠️ C は **`meta` を書く時点で `intervention_enabled` が未確定**
  （`record_session_meta` は `start_session` の**後**）なので**成立しない**。
- **トレードオフ**: ⚠️ **Accepted な ADR-013 D1 の形を変えた**（2 群 → 3 群）。
  → ★ ADR に改訂節を書き、**なぜ 2 群では自己矛盾するか**を残した（口頭で済ませない）。
  ★ 旧ログには本キーが無いので `Option`（`required` に入れない = additive）。
- **影響範囲**: `capabilities.rs` / `schema_dto.rs` / `schema/current.json` / ADR-013 D1
- **見直しタイミング**: 新しい設定ゲートを足すとき (★ その行種を `config_gated` へ入れる)

## 判断 12: `record_session_meta` 失敗後の再押下では **ログを 1 行も書かない**

- **判断日時**: 2026-08-19 (code-reviewer HIGH)
- **背景**: ⚠️★★★ **判断 8 の前提が誤っていた。**
  判断 8 は「孤児ファイルが増えても提出側の `has_any_data_row` が二重化として効いている」
  （handoff §2 の記述をそのまま採った）としたが、★ **実測すると成り立たない**:
  `packaging.rs` の同関数が読み飛ばすのは **`meta` / `hook_health` / `ime_state` だけ**で、
  ⚠️ **`session_start` 行があるファイルは `true` を返す** → `.age` に包まれ、**提出され、
  ブロック番号を 1 つ消費する**。
  → ★ `RotateForRestart` が meta 再送の押下でも発火すると、
  **旧 code-review HIGH が防いでいた孤児ファイルが本当に戻る**。
- **選択肢**:
  - A: 握手フラグ (`SESSION_META_RECORDED`) で「二度押し」と「meta 再送」を分け、
    後者では**ローテートも `session_start` も行わない**
  - B: 経過時間で分ける (`now - SESSION_START_MS >= 30_000` のときだけ restart 扱い)
  - C: 現状維持 (孤児を許容する)
- **採用**: **A**
- **理由**: ★ **判定の根拠が「時間」ではなく「握手が済んだか」そのもの**なので、閾値を持たない。
  ⚠️ B は 30 秒という新しい魔法数を増やし、遅い端末で誤判定する。

  **`Ok` を返す直前**の 1 箇所、落とすのは「新しいブロックを実際に始める」1 箇所だけに限定した。

- **見直しタイミング**: フロントが `record_session_meta` を呼ばない経路を足すとき

## 判断 13: ブロック境界の検出は **`SESSION_START_MS` の変化**で見る (`session_active` の縁ではなく)

- **判断日時**: 2026-08-19 (Codex HIGH・`/cross-review`)
- **背景**: ⚠️★★★ **判断 12 で入れた修正自体に穴があった。**
  ブロック境界で `dropped_at_last_line` と `MicroStarveWindow` を揃える処理を
  `if session_active && !prev_session_active` で書いていたが、
  ★ **`RotateForRestart`（実行中の再押下）は `session_active` を `true` のまま維持する**ので、
  ⚠️ **G-1 で新設したまさにその経路でだけ発火しない**。
  → 計器の状態が**旧ファイルから新ファイルへ持ち越され**、
  `dropped_delta` / `starve_window` が**ファイル境界をまたいだ値**になる
  ＝ ★ **`dropped_delta` を足して消そうとした誤帰属そのもの**。
- **選択肢**:
  - A: `SESSION_START_MS` の変化を見る（純関数 `liveness::is_new_block_epoch`）
  - B: ローテート専用のエポックカウンタ (`LOG_EPOCH: AtomicU64`) を新設する
  - C: `session_active` を一瞬 false にしてから true に戻す
- **採用**: **A**
- **理由**: ★ `SESSION_START_MS` は **通常のブロック開始 (`0 → t`) でも実行中の再押下
  (`t1 → t2`) でも必ず動く**（`lib.rs` が `start_session` の成功経路で毎回 `now` を格納する）。
  → **新しい状態を 1 つも足さずに**両方を捉えられる。
  B は同じ情報を二重に持つ。⚠️ C は分析スレッドが false を観測して
  **前セッションの沈黙が混入する**（`lib.rs` の可視性順序コメントが禁じている形）。
- **トレードオフ**: ⚠️ `SESSION_START_MS` の意味に「計器のエポック」という第 2 の役割が乗る。
  → ★ 純関数 `is_new_block_epoch` に切り出し、**再押下ケースをテストで固定**した。
- **影響範囲**: `src-tauri/src/lib.rs` (監視スレッド) / `src-tauri/src/input/liveness.rs`
- **見直しタイミング**: `SESSION_START_MS` の更新箇所を増やすとき
