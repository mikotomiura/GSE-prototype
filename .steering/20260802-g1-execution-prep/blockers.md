## B-1 ★★ アプリのランダムプローブが G1 ブロック中に発火する

### 何が問題か

`preregistration.md §2.6` は「**アプリ内プローブを使わない**」と凍結している
（`probe_scheduler.rs` は凍結対象で、主観は紙／外部フォームの強制比較で取る）。
しかし **アプリは研究者の意図と無関係にプローブを出す**。

`D-1`（1 ブロック = 1 セッション）により**ブロックごとにアプリを再起動**するため、
プローブのスケジューラは **ブロックごとに作り直される**（`lib.rs:1995` 付近・新セッション検出で
`ProbeScheduler::from_seed(seed, config, session_start)`）。すなわち **毎ブロック抽選し直す**。

### 調査結果（案 A =「コード変更ゼロで止める」は**成立しない**）

起動モードは `App.tsx` の週セレクタが唯一の真実源で、**2 つしかない**:

| モード | 介入 (Nudge/Wall) | プローブ設定 | 5 分ブロックでの発火確率（設定からの計算） |
|---|---|---|---|
| **第1週 (blind 較正)** | ★ **発火しない**（`INTERVENTION_ENABLED=false` → `safe_default()`・`lib.rs:473`） | `ProbeConfig::calibration()`<br>λ=1回/6分・gap 3分・max_gap 10分 | ★ `1−exp(−5/6)` ≈ **57%**<br>10 ブロックで期待 5〜6 回 |
| **第2週 (介入)** | **発火する** | `ProbeConfig::default()`<br>λ=2回/30分・gap 6分・max_gap 22分 | `1−exp(−5/15)` ≈ **28%**<br>10 ブロックで期待 2〜3 回 |

★ **介入を止められる唯一のモードが、プローブを最も密にする。**
どちらを選んでも**プローブは止まらない**。

⚠️ 上表の確率は**設定から計算した見込みであり実測ではない**。P-1 で実測すること。

### 何が壊れるか

1. `§2.6`（アプリ内プローブを使わない）と**正面から衝突する**。
2. ポップアップが課題を中断し、**そのブロックの打鍵を汚染する**。
3. ⚠️ `§3.6` は「ブロックを事後に除外しない（技術的なログ欠損のみ）」と凍結しているので、
   **汚染されたブロックを後から落とせない**。

### 選択肢（★ 研究者判断）

| | 案 | 帰結 |
|---|---|---|
| **A** | コード変更ゼロで止める | ★ **不成立**（上記の調査結果） |
| **B** | 発火を前提に `protocol.md` へ手順を書く（出たら答えずに閉じ、記録用紙に発火を記録する） | 打鍵汚染は残る。`§3.6` との整合を説明する必要がある。発火の有無をブロック水準で報告する義務を `§5` に足すことになる |
| **C** | env フラグ等でプローブを無効化する | ★ **コード変更を伴い `run.sh` [5]（`src-tauri/` `src/` 非接触）に抵触する**。G1 の「コード変更ゼロで実施できる」という前提を崩す |

★ 現時点の私の見立ては **C が本命**（B は汚染が残るうえ `§3.6` との整合説明が厄介）。
ただし C は G1 の設計前提を崩すので、**研究者が決めること**。

### 参考（別件・既に解決済み）

Windows の overlay クリック奪取バグは **PR #63 / `330dcdf` で真因特定・修正済み**
（「idle 残存」ではなく**カード表示中の透明余白**が真因だった）。
残っているのは Windows dev 機での最終確認のみ。**B-1 とは別問題**。

## B-2 ★ 操作チェックの分母が薄く、1 問で合否が反転しうる

### 何が問題か

`§2.6` は「**分母は異条件ペア（HI vs LO の比較）のみ**、HI が『詰まった』と選ばれる割合 **≥70%**」
と凍結している。同条件ペア（HI-HI / LO-LO）は情報を持たないので外す、という理屈自体は正しい。

しかし**分母の大きさが割付に依存する**。強制比較は G1 ブロック 3〜9 の直後に 7 回取るので、
隣接ペアは 7 組。HI4/LO4 を 8 ブロックに並べたときの**隣接不一致ペア数の期待値は 4**
（`7 × (2·4·4)/(8·7) = 4`）。取りうる範囲は 1〜7。

| 分母 | 70% を満たすのに必要な数 |
|---|---|
| 7 | 5/7 (71%) |
| 4（期待値） | **3/4 (75%)** ← 2/4 = 50% で不合格 |
| 3 | ★ **3/3 (100%)** ← 2/3 = 66.7% で不合格 |
| 1 | 1/1 |

★ すなわち **1 問の揺れで操作チェックの合否が反転しうる**。
そして操作チェックが落ちると `§3.4` により **打鍵の結果を一切解釈できない**
（`analyze.py` が `MANIPULATION_CHECK_FAILED` を返す）。

### なぜパイロットで確かめられないか

⚠️ `§2.8` により **P-1 では強制比較の鎖が成立しないので取らない**
（HI/LO の対が 1 組しかない）。したがって **この計器の実効性はパイロットで検証できない**。

### 選択肢（★ 研究者判断・いずれも事前登録の改訂を伴う）

| | 案 | 触る節 |
|---|---|---|
| **a** | 現状維持（分母が小さくなるリスクを承知で凍結） | なし |
| **b** | 無作為化に「隣接異条件ペアが最低 N 組できる」制約を足す | `§2.3`（ブロック順序の無作為化） |
| **c** | 分母が小さいときの扱い（例: 分母 < N なら操作チェックを判定に使わず記述に降格）を事前宣言する | `§2.6` |

⚠️ **b は無作為化の制約なので、C(8,4)=70 の全数列挙という並べ替え検定の前提に影響しないかを
必ず確かめること**（ラベルの並べ替えは検定側で全数列挙するので、実施順序の制約とは独立のはず。
ただし「実際に出した順序」が帰無分布の一部でなくなる意味はないか、確認が要る）。
