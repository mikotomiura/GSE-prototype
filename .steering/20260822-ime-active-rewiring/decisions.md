# 重要な設計判断

## 判断 1: `IME_ACTIVE` を EnumWindows 経路へ配線し直さない (B 不成立)

- **判断日時**: 2026-08-22
- **背景**:
  `IME_ACTIVE` を `true` にするのは `hook_windows.rs` の WinEvent コールバック 1 か所だけで、
  そこが実機で 1 件も発火しない (60 秒 × 3 回で `EVENT_OBJECT_IME_SHOW/HIDE/CHANGE` すべて 0)。
  一方 `is_candidate_window_open()` は EnumWindows 経路を持っており「動いているように見えた」。
  → **働く検出器が無効化用にしか繋がっておらず、データを産む側が死んだ経路に繋がっている**
  という配線の非対称を直せるか、が本タスクの問いだった。
- **選択肢**:
  - A: EnumWindows 経路を `IME_ACTIVE` の正の駆動源にする (handoff §2.2 の想定案)
  - B: 何もしない。`IME_ACTIVE` は「取れない」と結論し `config_gated` 据え置き
  - C: 診断B で見つかった `SHOW Windows.UI.Core.CoreWindow` (20 件) を新しい駆動源にする
- **採用**: **B**
- **理由**:
  ⚠️★★★ **A は実測で潰れた。** EnumWindows 経路は 60 秒 × 2 回で
  **検出 0/2400 (0.0%)・立ち上がり 0**、本番相当の 100ms 間引きでも **0/600**。
  ⚠️★★★ **さらに 3 回目で本番の完全な述語 `is_candidate_window_open()`
  (WinEvent `||` EnumWindows `||` UIA) を直接測り、これも 0/2400・立ち上がり 0 だった。**
  ★ **UIA 経路の寄与は 0 回**（「本番 true かつ EnumWindows false」が 1 度も無い）。
  → ★ **3 経路すべてが閉じている**ことを実測で確認済みである。
  可視トップレベル窓のセンサスに**一過性のクラスが 1 件も無く**、窓レベル `HIDE` も 0 件。
  → **候補 UI がトップレベル窓として可視化されない**ため、`EnumWindows`
  (トップレベル窓しか列挙しない) では構造的に捕まえられない。
  ★ handoff §2.1 の gate が「検出しないなら B は成立しない」と事前に定めており、それに従った。
- **トレードオフ**: 何を諦めたか
  - ⚠️ `ime_shadow` (dwell / nav / abandon) は **0 行のまま**である。
  - ★ ただし `capabilities` が `config_gated` なので、0 行は「信号が無かった」ではなく
    **「判定不能」**と読まれる。→ ⚠️ **偽の結論にはならない** (これが ADR-013 の要点)。
- **影響範囲**: `lib.rs` の IME Monitor は**変更しない**。`capabilities` も**変更しない**。
  本番の挙動は 1 バイトも変わっていない。
- **見直しタイミング**:
  ★ 別の IME / 別のアプリ / 別の Windows ビルドでは上がりうる。
  ⚠️ 被験者環境が変わったら**再測定**する (プローブは残してある)。
  ⚠️★★★ **その際はセンサス出力を repo / gse-dataset に貼る前にレビューする**
  —— ★ 可視クラス名の一覧は**被験者のアプリ利用状況の指紋**になる
  (`findings-enumwindows-probe.md §6.2`・security review MEDIUM)。

## 判断 2: 診断B の `Windows.UI.Core.CoreWindow` を採用しない

- **判断日時**: 2026-08-22
- **背景**: 窓レベルの `EVENT_OBJECT_SHOW` が `Windows.UI.Core.CoreWindow` に対し 20 件飛んでいた。
  ★ **これまで一度も計測されていなかった窓口**であり、`IME_ACTIVE` の新しい駆動源になりうる。
- **選択肢**:
  - A: これを駆動源として実装する
  - B: 記録に残し、証拠が揃うまで採用しない
- **採用**: **B**
- **理由** (★ 3 つとも独立に致命的):
  1. ⚠️ **非対称**: `SHOW` 20 に対し窓レベル `HIDE` は **0 件**。
     → **`dwell_ms` が計算できない**。`ime_dwell_med` は dwell が本体なので、目的を満たさない。
  2. ⚠️★★★ **クラス名が汎用すぎる**: Start メニュー・通知トースト・任意の UWP が同じクラス。
     → 過去に「常時可視クラスを含めて**分析が永久停止**」した事故
     (`ime_windows.rs` の回帰テスト `excludes_language_bar_and_imm32_system_window`) と**同型**。
  3. ⚠️ **`hook-constraints` Win-1 違反**: 本番の WinEvent コールバックで `GetClassNameW` を
     呼ぶことになる (許可は Atomic + `try_send` のみ)。
- **トレードオフ**: ⚠️ 収集開始前にしか入れられない改修を 1 つ見送った。
  ★ ただし 20 件が本当に IME 候補 UI かは**未確認**であり (PID を見れば分かるが、
  プローブは意図的に PID を取らない)、**仮定のまま配線する方が危険**である。
- **影響範囲**: なし (実装していない)。
- **見直しタイミング**: ★ 研究者が「この窓口を追う」と判断した場合。
  ⚠️ その場合は最低限 (a) SHOW/HIDE の対称性、(b) 候補 UI 由来かの同定、
  (c) Win-1 準拠の設計 (HWND を `try_send` → 別スレッドで解決) の 3 つを先に閉じること。

## 判断 3: `is_ime_candidate_window_visible` を `pub` にした

- **判断日時**: 2026-08-22
- **背景**: プローブから本番の検出関数を測る必要があった。
- **選択肢**:
  - A: プローブ側に EnumWindows ロジックを複製する
  - B: 本番関数の可視性を `pub` に上げ、プローブから直接呼ぶ
- **採用**: **B**
- **理由**: ⚠️★★★ **A は「複製の方が動いた」という無意味な計測になる。**
  本番経路の可否を答えるには**本番の関数そのもの**を叩くしかない。
  ★ 変えたのは可視性だけで、シグネチャも中身も 1 行も変えていない。
- **トレードオフ**: ⚠️ lib の公開 API が 1 つ増えた (利用者は example のみ)。
- **影響範囲**: `input/ime.rs` の再エクスポート 1 行。本番の呼び出し経路は不変。
- **見直しタイミング**: プローブを捨てるとき。
