# 未踏提出文書に「検証の仕掛けの到達点」を書く

## 背景

前セッション (2026-09-03, `.steering/20260903-mitou-doc-consistency-fixes/`) の引き継ぎより。

提案書 §5 は「**測定設計が成立しなかった実測を原因分析へ戻せること**」を腕前の中身にしている。
ところが、その原因分析を可能にした装置が 1 つも書かれていない。
Phase1 で「主観プローブの負荷 / データ不足 / 信号不足」を分離できたのは、
`gse-replay` でゴールデンを再実行でき、`capabilities.rs` が
「測れて無かった 0 行」と「計器が無かった 0 行」を区別して刻んでいたからである。
装置が書かれていないと、あの原因分析は「言い訳」と区別がつかない。

もう一点。二つの収集レジームのうち、**自然作業の長期記録**が 4 文書で実質 1 回しか出てこない
(2026-09-03 実測。詳細資料 L43 の 1 箇所のみ)。配備 runbook・提出パイプライン
(`submission.rs` / `packaging.rs` / `reconcile.rs`) に実体があるのに文書上ほぼ存在しない。

### 内部呼称の扱い (最初に守ること)

`G1` / `O1` は社内の符牒であり審査員には通じない。実測 (2026-09-03、本セッションで再検証済み):

| 文書 | `G1` | `O1` |
|---|---|---|
| 詳細資料 | 0 件 | 0 件 |
| 技術設計書 | 1 件 (L628) | 0 件 |
| 検証レポート | 2 件 (L31 / L62) | 0 件 |

詳細資料は既に実体名で書いている (「統制実験」3 回 /「統制タスク」3 回 /
「自然作業の長期記録」1 回)。**この語彙に揃える。**

| 内部 | 提出文書での書き方 | 実体 |
|---|---|---|
| G1 (R1) | 統制実験 / 統制タスク | 高摩擦・低摩擦を実験者が操作し、条件ラベルを criterion にする。入力先を固定する |
| O1 (R3-a) | 自然作業の長期記録 | 普段の作業を普段どおり。入力先を固定せず、アプリ横断で常駐して記録する |

## ゴール

1. 詳細資料 §4【検証ワークフロー】の直後に **250〜350 字**を足す
   (§5 腕前節ではない。検証節に置けば「この検証計画が実行可能である根拠」になる)。
2. 実体の厚い記述は**検証レポート側**へ置く (文書の分担: 詳細資料＝概要 / 補足資料＝具体)。
3. 技術設計書 1 件・検証レポート 2 件の裸の `G1` を処理する。
4. 追記後に**提出経路 (Google Drive) でページ数を実測**し、10 ページ規約内であることを確認する。

## やってはいけないこと (前セッションで実際に踏んだ)

- **数の列挙**。未踏の審査は工数ではなく設計判断を見る。数を並べると「よく作り込んでいる学生」になり、
  §5 が積み上げた「測れなかったことを認められる」という像を薄める。
- **未実装のものを実装済みに読ませる**。2026-09-03 にまさにこれをやった
  (security-checker M-2: セキュア入力欄の記録抑止の「未実装」但し書きを消して実装済みに読める状態にした)。
