# Issue 002: 削除の最小幅を入口で保証し、削除区間の内側に onset が立つ穴を塞ぐ
verify_level: recheck

## Goal

`delete_time_range` が **最小幅未満の区間を受けたら最小幅まで広げて消す**ようにし、
**「削除 UI の最小幅 > `hole_gap_ms`」を定数比較の検査で固定する**（★ 陽性対照つき）。

## Background

★ ADR-030 **D8 (b-2)** は「1Hz の `feat` 列に穴がある区間では、条件 B の連続を切る」と定め、
⚠️ **被験者が削除を求めた位置に onset が立つこと**を防いでいる。

⚠️★★★ **ところが穴の判定は `隣接差 > hole_gap_ms` である**（`.steering/20260914-mhd-feature-offline-tiers/blockers.md`
**起票 15**・2026-09-18 の `security-checker` L1・**実測**）:

> ★ **feat 行が 1 本だけ欠けた場合（差がちょうど 2000ms）は区間が切れない。**
> ★ 1 秒おきの feat 行の中で `[30,900, 31,500]` を削除すると消える feat 行は 1 本で、
> **元に無い onset が丸ごと削除区間の内側に出た**。

★ **現行 UI からは到達不能**（実測・2026-09-21）:
`src/components/RecordingControls.tsx` の削除入力は **`datetime-local`（秒なし）** なので、
幅は 0 か **60,000 ms 以上**になる。

⚠️★★★ **しかし `delete_time_range`（`src-tauri/src/lib.rs:1426`）は任意の ms を受ける** ——
実測した検査は **`from_ms > to_ms` の拒否だけ**である:

```rust
if from_ms > to_ms {
    return Err("開始時刻が終了時刻より後になっています。".to_string());
}
```

→ ★ **秒単位の削除 UI を足した時点で実際に起きる**（★ テスト・外部ツールからも到達できる）。

### ★ 研究者裁定（2026-09-21・`decisions.md` 判断 8）

ADR-030 **補訂 1 項目 5** は固定の仕方を (a) 定数比較の検査 / (b) 入口で拒否または広げる の
**どちらかを実装タスクで決める**としていた。→ ★ **(b) 広げて消す ＋ (a) 検査の両方**を採る。

- ★ **広げる向きは終端側**（`to_ms = from_ms + MIN_REDACTION_WIDTH_MS`）——
  `from_ms` は被験者が「**ここから**消したい」と言った点なので動かさない。
  ⚠️ 対称に広げると**指定していない過去**が消える。
- ⚠️ **拒否は採らない** —— ★ 補訂 1 項目 5 逐語「★ **削除は広げる側に倒す。被験者への約束は
  『その時間帯が消える』ことである**」。被験者が「消してくれ」と言ったのに消えないのは約束違反。

⚠️★★★ **被験者向け文書は契約である。** 広げる旨を UI 文言と `docs/o1-deletion-ledger.md` に書く。
