# decisions — `IME_ACTIVE` cloak 経路への配線替え (2026-08-23)

## D-1: クラス絞りは **完全一致 `"IME"`**

**決定**: cloak/uncloak を `IME_ACTIVE` に流すのは、ウィンドウクラスが
**完全一致 `"IME"`** (IMM32 のシステムウィンドウ) のときだけ。

**理由**: 実測 (findings §16.1) では 3 クラスとも「打鍵から遠い cloak = 0」で、
false positive の点では区別がつかなかった。★ 決め手は**名前が IME 固有かどうか**である。

| クラス | 実測 | 判定 |
|---|---|---|
| `IME` | cloak 18 / 遠い 0 / dwell 中央 701ms | ★ **採用** |
| `Xaml_WindowedPopupClass` | cloak 9 / 遠い 0 | ⚠️ 却下 |
| `ApplicationFrameWindow` | cloak 9 / 遠い 0 | ⚠️ 却下 |

⚠️ 後 2 者は**汎用クラス**である (ツールチップ・メニュー・フライアウト / 全 UWP のホスト)。
★ 60 秒の計測でたまたま候補 UI しか出なかっただけで、
**被験者が別のアプリを使えばツールチップ 1 個で誤検知する**。
★ `IME` の「1 変換 = 2 周期」は畳めば済むが、汎用クラスの誤検知は畳んでも消えない。

**却下案**: 「`IME` かつ候補 UI の AND を取る」(引き継ぎ §2.3 案 3)。
⚠️ 2 クラスの cloak が**必ず同時に来る保証が無く**、片方だけ来た場合に取りこぼす。
★ 実測でも `IME` 18 : 候補 UI 9 と**件数が違う**ので、AND は 1 変換の一部しか拾わない。

**⚠️ 既存の `is_ime_candidate_class_name` との関係**: あちらは完全一致 `"IME"` を
*明示的に除外*しているが、**矛盾しない。判定軸が違う**
(可視性 vs cloak 遷移。`IME` 窓は常時可視だが静止時は cloak 遷移しない)。
★ **別関数 `is_ime_cloak_class` として実装し、既存のテストは 1 行も触っていない。**

## D-2: 2 周期の畳み込みは **HWND 別の集合 + ギャップ debounce の 2 段**

**決定**: `CloakFold` が (1) HWND 別の集合 (2) `FOLD_GAP_MS` の debounce の両方を持つ。

**理由**: 実測は「1 変換 = `IME` クラス 2 周期」までしか言っておらず、⚠️ その 2 周期が
**(a) 同じ窓の連続 2 往復**なのか **(b) 別々の窓の重なり**なのかを**見ていない**。
→ ★ どちらでも壊れないように両方入れる。

- 集合 → (b) 重なりを 1 区間に融合する (引き継ぎ §2.4「pending 単一スロット」問題の解)
- debounce → (a) 連続 2 往復を 1 行に畳む

**却下案**: 「`Xaml_WindowedPopupClass` を使えば 1:1 だから畳み込み不要」(引き継ぎ §2.3 案 2)。
⚠️ D-1 の理由で却下 (汎用クラス)。

**⚠️★★★ 2026-08-23 の実測で前提が変わった (★ それでも 2 段を残す)**

★ 実測 D で **「1 変換 = 2 周期」は誤読**と判明した ——
`ApplicationFrameWindow` / `Xaml_WindowedPopupClass` / `IME`×2 の **4 窓が
同じミリ秒で同時に** cloak/uncloak しており、2 : 1 : 1 の正体は
**「`IME` クラスの窓が 2 個ある」**ことだった (findings §4.2)。
→ ★ 畳むべきは **(b) 重なり**であり、**HWND 別の集合**がそれを処理する。

⚠️ debounce の当初の存在理由 (連続 2 往復) は消えたが、**0 にはしない** ——
★ 1 変換の途中に出る**短い明滅** (別計測で 116ms の可視区間を観測) を吸収するため。

**`FOLD_GAP_MS` = 150 ms** (★ 実測で決めた。⚠️ 勘ではない):

| debounce | 行 | ⚠️ 判定 |
|---|---|---|
| 0〜250 ms | **12** | ★ 変換回数と一致 |
| 300 ms | 11 | ⚠️ 最小ギャップ **308ms** を跨いで融合 |
| 400 ms | 9 (+打切 1) | ⚠️ 壊れる |

★ 候補が隠れている区間の最小 = **308ms** に対し **約 2 倍の余裕**を取り、
★ debounce 中も `IME_ACTIVE` が立つので**水増しを 1 変換 150ms に抑える**。
⚠️ 境界は回帰テスト `too_large_a_debounce_merges_separate_conversions` で固定。

## D-3: ⚠️★★★ **辺の向き** — 引き継ぎに無かった論点を足した

**問題**: 引き継ぎ §2 と findings §15.5 は「`CLOAKED`/`UNCLOAKED` で駆動する」とだけ書き、
⚠️ **どちらの辺が「候補ウィンドウが見えている」なのかを一度も確かめていない。**

★ これは飾りではない:

| 仮定 | `ime_dwell` が測るもの |
|---|---|
| `CLOAKED` = 候補表示 (★ 旧 v0.1.27 の仮定) | 候補ウィンドウの滞在時間 |
| `UNCLOAKED` = 候補表示 (★ DWM の素直な意味論) | ⚠️★★★ **変換と変換のあいだ** |

⚠️ **件数はどちらでも同じに見える** (cloak = uncloak = n)。★ 順序か実状態を見ないと決まらない。

**決定**: `candidate_shown_from_cloak(cloaked) = !cloaked` (DWM の意味論に従う)。
★ **1 関数に閉じ込め、回帰テスト `shown_means_not_cloaked` で固定**した。
→ ⚠️ 将来向きを変えるなら、変えるのはその 1 行とテストだけで済む。

**★★★ 2026-08-23 の実測で確定 (実測G)**: ⚠️ **推測ではなく実測で裏が取れた。**

★ 遷移した窓そのものを 250ms ごとに DWM へ問い合わせ、打鍵からの距離で分けたところ、
**変換していないとき (打鍵から 4 秒以上) は 3 クラスとも 100% cloaked**
(`IME` 30/30・他 15/15。⚠️ uncloaked のサンプルは**ゼロ**)。
→ ★ **cloaked が平常状態** = 候補は見えていない → ★★★ **`UNCLOAKED` = 候補表示。**
→ ★ **実装の向きは正しい。** ⚠️ **旧 v0.1.27 の仮定 (`CLOAKED` = 表示) は逆だった。**

⚠️ **途中で私は逆の結論に傾いた。訂正の経緯を findings §4.1.1 に残した**
(★ 実測 E の「静止時 104/108 が uncloaked」は**変換に関与しない別の窓**を見ていた)。

**実装上の保険**: resolver は届いた辺の名前を信じず、
**`DwmGetWindowAttribute(DWMWA_CLOAKED)` で OS に現在状態を聞き直す**
(⚠️ `WINEVENT_OUTOFCONTEXT` の配送は非同期で、届いた時点の実状態と食い違いうる)。

## D-4: 2 経路の**排他** (`LEGACY_IME_EVENT_MS` + recency)

**決定**: 文書化された `EVENT_OBJECT_IME_*`(0x8027-29) が **直近 60 秒に飛んでいる端末では、
cloak 経路は一切手を出さない**。

**理由**: 両方が `IME_COMPOSITION_START_MS` / `IME_SHADOW_*` を書くと**書き手が 2 人**になる。
⚠️ この repo が過去に踏んだ事故 (無関係な窓の cloak で `IME_ACTIVE` が立つ) の型そのもの。
★ 優先順位を固定すれば、他の IME / OS ビルドで 0x8027-29 が飛ぶ場合に
**壊れる方向ではなく正しい方 (文書化された経路) が勝つ**。

**⚠️ 初版は不可逆ラッチ (`AtomicBool`) だった。レビューで潰した** ——
★ それだと**無関係なアプリが 0x8027 を 1 件上げただけで、プロセス寿命の残り全部で
cloak 経路が無言で停止する**。⚠️ その端末で `ime_shadow` が 0 行に戻っても、解析側は
「変換しなかった」と「黙った」を**区別できない** (★ この repo が繰り返してきた事故の型)。
→ ★ **最終到達時刻 + `legacy_path_is_driving()` の recency 判定 (窓 60 秒)** に置換し、
切替時に `tracing::warn!` を 1 回出す。

**⚠️ 譲るときは atomics に一切触らない** (★ cross-review 重大)。
初版は「自分が立てた `IME_ACTIVE` は自分で下ろす」としていたが、
⚠️ **`AtomicBool` に所有者は書かれていない** —— 直前に legacy が立てた `true` を
潰して legacy 側の pause と dwell 計測を壊しうる。★ 残った `true` は
`lib.rs` の safety valve が設計どおり回収する。

⚠️★ **ただし D-10 で valve を 8 秒 → 25 秒に伸ばしたので、
残留しうる時間の上限も 8 秒 → 25 秒に伸びた** (2026-08-23・cross-review 両者一致)。
★ 許容する: **pause を外したので残留しても推論は止まらず**、影響は
`ime_state.active` の解釈が最大 25 秒ぶん汚れることに限られる。
⚠️ **解析時にこの上限を知っている必要がある。**

## D-5: ⚠️★★★ `is_stale_winevent_active` を `legacy_path` で絞る

**決定**: stale 判定を `legacy_path && winevent && !enum && !uia` に変更した
(★ 既存 4 テストは `legacy_path=true` で意味を保ったまま維持。新規 1 本を追加)。

**理由**: ⚠️ **これを直さないと A は動かない。**
★ この判定の前提は「本当に候補が出ているなら EnumWindows か UIA が裏を取れるはずだ」だが、
⚠️ **実測で裏取りは構造的に 0** (EnumWindows 0/2400・UIA 0)。
→ ★ cloak 経路の世界では式が「**常に stale**」に退化し、
`IME_ACTIVE=true` を立てた 100ms 後に必ず折られ、**`ime_shadow` は 1 行も出ない**。

⚠️ **fail-stuck の防止は失われていない**: `lib.rs` の 8 秒 safety valve と
`CloakFold::MAX_SESSION_MS` (**6 秒**) が別々に効く。

★ **6 秒にした理由** (⚠️ 8 秒に揃えない): 揃えると `lib.rs` の valve と**競走**し、
あちらが先に発火すると **1 回の変換で `ime_shadow` が 2 行**出る
(★ valve の stale 経路が 1 行 → その直後に fold の `End` が `READY` を立てて 2 行目)。
⚠️ `const _: () = assert!(MAX_SESSION_MS + 1_000 <= 8_000)` で**コンパイル時に固定**した。

★ **打ち切りは行を出さない**: `FoldAction::End { forced: true }` のときは
`IME_SHADOW_READY` を立てず `IME_COMPOSITION_START_MS` も 0 に戻す。
⚠️ そうしないと **`dwell_ms` = 上限そのものの行**が本物の変換と区別できない形で
NDJSON に入り、`ime_dwell_med` を計器由来の値で汚す。
★ **1 行失う方が、偽の dwell を 1 行足すより安全である。**

## D-6: `IME_OPEN` は **触らない**

**決定**: cloak 経路は `IME_ACTIVE` と IME Shadow の atomics だけを書き、
`IME_OPEN` (日本語モードか英数か) には**一切触れない**。

**理由**: `IME_OPEN` には別の正しい持ち主が居る (`VK_DBE_*` キー + `ImmGetOpenStatus` ポーリング)。
⚠️★★★ 旧実装が「無関係な窓の cloak で `IME_OPEN` まで立てていた」のが、
2026-08-21 に見つかった計器不良そのものである。★ 同じ誤りを繰り返さない。

## D-7: WinEvent は**範囲を広げず 2 本目を張る**

**決定**: 既存の `0x8027..=0x8029` はそのまま、`0x8017..=0x8018` に **2 本目**を張る。

**理由**: `eventMin`/`eventMax` は単一の連続区間しか取れず、両者は連続していない。
⚠️ 広げて `0x8017..=0x8029` にすると、間の `EVENT_OBJECT_TEXTSELECTIONCHANGED`(0x8020) など
**高頻度イベントが全部届く** (★ 同じ 60 秒に 298 件飛んでいた実測がある)。
★ 2 本目なら購読するイベント ID は **2 個だけ**。→ 負荷を実測するまでもなく桁で違う。

## D-8: `capabilities` は **`config_gated` 据え置き**

**決定**: `ime_shadow` は `config_gated` のまま。⚠️ `unconditional` へは戻さない。

**理由**: ★ 行は出るようになったが、
1. ⚠️ **1 台・1 アプリでしか確認していない** (被験者環境での再現は未検証)
2. ⚠️ cloak が飛ぶのは**候補ウィンドウが出るとき**であって、ローマ字入力中ではない
   → ★ 「変換しない打ち方」の被験者では 0 行になりうる
3. ⚠️ macOS には送出元が構造的に無い

→ ★ **0 行は依然「判定不能」であって「信号が無かった」ではない。**

★ 両 OS が初めて同じ量になるが、⚠️ Mac セッションが要り収集開始が遅れる。→ 研究者が却下。

## D-10: ⚠️★★★ **`IME_ACTIVE` で推論を止めない (記録のみ)** — 研究者判断 2026-08-23

**決定**: `lib.rs` の IME Monitor と `analysis/loop_step.rs` の**両方**から
`engine.set_paused()` を外す。★ `ime_shadow` の**記録は続ける**。

### ⚠️ なぜ引き継ぎ §3.2 の方針を覆したのか

★ 引き継ぎは「pause を設計どおりに復活させる」ことを A の目的の 1 つに挙げ、
その代償を **「打鍵時間の 15〜20%」** と見積もっていた。
⚠️★★★ **その見積りは、信号を「候補リスト表示」だと誤解した上でのものだった。**

★ 自然な打鍵 60 秒 (打鍵 281) の実測で、uncloaked 区間の長さは:

```
6464 / 5714 / 5004 / 3456 / 6974 / 3279 / 1574 / 363 / 267 / 203 / 133 / 88 ms
```

⚠️ **候補リストを眺めている時間ではない。** ★ 実測 G でも打鍵中のサンプルの
**69% が uncloaked**。→ ★★★ **この信号は「IME 変換セッション全体」
(ローマ字入力の開始 〜 確定) を覆う。**

| ★ 実測 | 値 |
|---|---|
| 自然な打鍵での pause 率 (上限 20s) | **55.9〜60.4%** |
| ⚠️ 実データ fixture `phase1_ime_heavy` | ★★★ **推論窓の 94% が消えていた** (6 / 98) |

→ ⚠️★★★ **設計意図 (「候補選択中の打鍵で推定を汚さない」) は正しいが、
手に入る信号はそれより遥かに広い。** ★ そのまま pause に使うと**過剰適用**になり、
**G1 の主タスク (日本語論述) の較正データを半分以上捨てる**。

### ★ 決めたこと / 却下したこと

| 案 | 判定 |
|---|---|
| **記録のみ・pause しない** | ★ **採用** |
| 設計どおり pause する | ⚠️ 却下 (推定窓 −57%) |
| pause するが上限を短く | ⚠️ 却下 (「長い変換だけ部分的に止める」は意味の説明がつかない) |

### ⚠️ 実装上の帰結

1. ★ **replay 経路も同時に外す** —— `loop_step.rs` の `LoopInput::ImeActivate` は
   NDJSON の `ime_state.active` から pause を再構成していた。
   ⚠️ 片方だけ外すと **live と replay が食い違い Replay-as-Truth が壊れる**。
   ★ バリアント自体は残した (将来戻すならここ、という位置を保つ)。
2. ⚠️★★★ **`HMM_VERSION` を 0.4.0 → 0.5.0 に bump した。**
   ★ 同じ入力 NDJSON から出る `FeatSnapshot` 列が変わるため
   (⚠️ 据え置くと「同じ版で 2 つの挙動」が存在することになる)。
3. ★ ゴールデン再生成は **`phase1_ime_heavy` の 1 本だけ** (6 → 98)。
   ⚠️ 他の 5 本は `active:true` を含まないので **byte-equal のまま**。
   ★ この fixture の `active` は**旧 (v0.1.27) の壊れた駆動**で記録された値なので、
   ⚠️ **94% は「旧 pause が食っていた量」であって新実装の予測値ではない。**
4. ★ `lib.rs` の safety valve を **8 秒 → 25 秒**、`MAX_SESSION_MS` を **6 秒 → 20 秒**。
   ⚠️ 6 秒は**実データを切っていた** (13 セッション中 3 本が打ち切られ、行が消えていた)。
   ★ pause を外したので、長く立ちっぱなしでも推論は止まらない。

**⚠️ 未決 — 研究者判断が要る**:
