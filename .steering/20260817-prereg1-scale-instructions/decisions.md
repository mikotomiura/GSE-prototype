## D-6: 中点 (3) の扱い — 「不一致のまま」+「初期値を撤廃」+「本番との切り分けを明示」

**決定**:
1. 採点上、**3 は想定象限を答えたことにならない** (現行規則を維持)
2. ただし**スライダーに初期値を持たせない**。両軸を操作するまで次へ進めない
3. 教示文では「3 は不一致」とは**書かない**。代わりに
   「**この 8 つの場面はどちらか一方に寄っています。迷ったら、より近いほうへ振ってください**」
   と書く
4. テスト終了時に「**本番のプローブでは、どちらとも言えない状態も正当な回答です**」と明示する

**理由**:
- (1) を変えると「想定象限を答えた」の意味が崩れる。凍結逐語の解釈を保つ

  この分離がないと straight-lining の検出そのものが成立しない
- (3) で「3 は不正解」と直接教えると被験者は中点を避けるようになり、
  **本番の Q1/Q2 の回答分布が歪む**。`synthesis.md` §2 **L5「計測・提示それ自体が行動を変える」**
  (独立 5 出典・[P77]/[P124]) に直撃する
- (4) は (3) の残留反応性を打ち消すための明示的な枠外し。L5 への軽減策として設計に織り込む

**却下案**:
- **4 件法 (中点なし) にする** → 理解テストと本番で尺度が変わる。
  [V83] の 3 脅威のうち「**尺度の場当たり変換**」そのものになる。**却下**
- **順序採点 (問間の q1 の大小だけ見る)** → 中心化傾向に強いが、
  凍結逐語「6 問以上が**想定象限**」は問ごとの象限判定を要求しており、**条件変更に当たる**。却下

逆に言えば現行の器は「読まずに真ん中を置く」以外の失敗モードを捕捉できない。

## D-11: 教示文に**合否条件を書かない** (実測で撤回した)

**決定**: 「8 問中 6 問がそろわなければ説明を書き直して再施行します」という告知を
教示文に**入れない**。

**理由**: `empirical-prompt-tuning` の実測 (`tuning-log.md` §2)。この 1 行を入れたところ、
- 誠実なペルソナ (S-A) が**出題構成を推測して答えを配分し始めた**

## D-13: 「値」と「触れたか」を別 state に分ける (自己レビューで見つけた競合)

**決定**: `q1: number | null` を `q1Value: number` ＋ `q1Touched: boolean` の 2 つに分ける。
`onPointerUp` / `onKeyUp` は **`Touched` だけを立て、値には触らない**。
値の確定は `onChange` だけが行う。

**理由**: 最初の実装は「未操作 = `null`、描画時に `?? 3`」で、`onPointerUp` が
`commitIfUntouched(value, setValue)` を呼んで `value === null` なら 3 を書き込んでいた。
⚠️ **`onChange` の直後に `onPointerUp` が古いクロージャの `null` を読むと、
被験者が選んだ値を既定値 3 で上書きする**。
React 18 は discrete event を同期 flush するので実際には起きにくいが、
**「起きにくい」に測定器の正しさを預けない**。値を常に `number` に保てば、
2 つのハンドラがどちらの順序で発火しても被験者の入力が壊れない。

**副作用**: `changes` が 1 だけ多く数えられる場合がある (`onChange` と `onPointerUp` の
両方が `Touched` を立てる経路)。⚠️ **`changes` は行動メタであってゲートではない**ので
無害と判断した。値の正しさと引き換えにしない。

**却下案**: `setValue` を関数形 (`prev => prev ?? 3`) にする。
→ `changes` の増分を関数の中で数えることになり、StrictMode の二重呼び出しで壊れる。

## D-14: ⚠️★★★ 採点は「最後の 1 施行」に限る — 完了ガードが作った穴を塞ぐ

**決定**: `score_vignettes_internal` は全回答を合算せず、`vignette_id` の再出現で
**施行 (attempt) に切って最後の 1 施行だけを採点**する (`split_attempts`)。
`VignetteRecord` に `vignette_id` を追加し、`VignetteScore` に `attempts` を追加した。

**理由**: ⚠️ **D-10 の完了ガード (`total >= 8`) が、それ自体で新しい穴を作っていた**
（`code-reviewer` HIGH 指摘。一次で確認済み）。
`score_vignettes_internal` は全セッションの vignette を `flat_map` で合算するため、
**4/8 で落ちた被験者が同じ成績で再受験すると `total = 16` / `matched = 8` になり、
`total >= 8 && matched >= 6` を満たして合格する**。
しかも `VignetteTest.tsx` の結果画面が「6/8 未満。…**再度受けることを推奨します**」と
再受験を明示的に促しており、**到達可能な経路**である。

⚠️ **PreReg-1 は再施行を明示的に許している**（「不合格時は教示文を作り直して再施行する」）。
禁じるべきは再施行ではなく**合算**である。

**却下案**: 「直近 8 件」で切る。
→ 中断した施行（例 4 問）の直後に完走した施行（8 問）が来ると、
**直近 8 件が 2 つの施行にまたがる**。`vignette_id` で切れば混ざらない。
この経路も `vignette_retake_is_scored_per_attempt_not_summed` で検査している。

**教訓**: ⚠️ **ガードを 1 つ足したら、それが別の穴を開けていないかを確かめる。**
今回は「未実施と不合格を分ける」ために足した `total` の下限が、
上限を塞いでいないことに気づいていなかった。

## D-17: キーボード操作は `onKeyUp` ではなく `onKeyDown` ＋ キー限定

**決定**: スライダーの「触れた」検出を `onKeyDown` に移し、
`ArrowLeft/Right/Up/Down` / `Home` / `End` / `PageUp` / `PageDown` に限定する。
`onPointerCancel` も同じハンドラに繋ぐ。

**理由**: `code-reviewer` HIGH 指摘。⚠️ **`onKeyUp` はキーを離した時点で
フォーカスがある要素で発火する**。Tab はキーダウンでフォーカスが移るため、
**keyup は移動先のスライダー上で起きる** → 触っていないのに「3 を選んだ」ことになり、
**本改修の核心（未操作と 3 の分離）がキーボード操作で完全に無効化されていた**。

**補足**: キーボードで 3 を選ぶ導線は残っている（3 → ArrowRight → 4 → ArrowLeft → 3）。
また値の境界（1 で ArrowLeft）でも `onKeyDown` が「触れた」を拾う。

## D-19: 未記録 (`None`) と 0 を分ける

**決定**: `VignetteRecord.elapsed_ms` / `changes` を `Option` にする。

**理由**: ⚠️ 2026-08-17 より前のログには本フィールドが無い。`#[serde(default)]` で
`0` に潰すと、**旧データが一律「0 ms で即答」= straight-lining 疑いに見える**。
`None` は「記録されていない」であって「0 ms で答えた」ではない。
pretty 出力でも `n/a` と表示し、旧 fixture (`calib_subject_s1.ndjson`) で実測確認した。

**却下案**: `#[serde(default)]` で 0 にする（実装が短い）。
→ ⚠️ **この誤読こそが本タスクの発端と同型**である
（`vignette.total = 0` を「不合格」と読んだのと同じ、「欠測を値として扱う」誤り）。
同じ型の間違いを、それを直しているタスクの中で作らない。
