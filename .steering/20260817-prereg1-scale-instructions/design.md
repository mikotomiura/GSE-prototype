器を 4 層に分けて直す。**合格条件 (6/8・80%) には触れない** (decisions D-3)。

| 層 | 現行の欠陥 | 変更 |
|---|---|---|
| **教示文** | 2 文のみ・1–5 の刻み未定義 (F2) | 3 点アンカー + 二軸の直交性 + 中点の扱い |
| **ビネット** | 全 8 問が Q1/Q2 のアンカー語を逐語で含む (F3)・同一象限が隣接 (F4) | 行動と成果物の変化だけで書き直す + 交互順 |

`empirical-prompt-tuning` で「教示文とビネットだけを渡した実行者」の想定象限一致率を測る。

## 1. 教示文 (**確定版 v6** — `empirical-prompt-tuning` の実測で確定)

> ⚠️ 実測の経緯は `tuning-log.md`。**文言を変えたら必ず測り直すこと。**
> 特に次の 2 つは**入れると悪化した**ので入れない (decisions D-11):
> 「6 問そろわなければ再施行します」/「両方が高い場面も低い場面もあります」

```
## この 8 問について

これから 8 つの場面を読み、それぞれについて 2 つの質問に答えてもらいます。
あなたを評価するものではありません。2 つのものさしの説明が伝わっているかを
確かめるためのものです。

### Q1「どれだけ引っかかっていたか」

課題の難しさに、どれだけ足を取られていたかを答えてください。

  1 = まったく引っかからなかった
  2 = あまり引っかからなかった
  3 = どちらとも言えない
  4 = かなり引っかかった
  5 = 手も思考も奪われるほど引っかかった

手が動いているかどうかは関係ありません。書いては消すのを繰り返している人も、
画面を見たまま止まっている人も、どちらも強く引っかかっていることがあります。
逆に、手が止まっていても引っかかってはいないことがあります。

### Q2「作業がどれだけ仕上がりに近づいたか」

提出する文章の本文が、完成にどれだけ近づいたかを答えてください。

  1 = まったく近づかなかった
  2 = あまり近づかなかった
  3 = どちらとも言えない
  4 = かなり近づいた
  5 = 完成が見えるところまで近づいた

打った量ではありません。手が止まっていても中身が近づくことはあり、
打ち続けていても中身が近づかないことがあります。
中身がよくなったのなら、書いた量が増えていなくても、減っていても、
近づいたと数えてください。

### Q1 と Q2 は別々のものさしです

一方が高いから他方が低い、とは限りません。次の 4 通りすべてが起こります。

- 引っかからず、近づいた
- 強く引っかかり、近づかなかった
- 強く引っかかったが、それでも近づいた
- 引っかかってはいないが、近づかなかった

### 答え方

8 つの場面は、Q1 と Q2 のそれぞれについて、高い側か低い側かがはっきりするように
書いてあります。どちらとも言えないと感じたら、より近いほうへ振ってください。
```

**テスト完了時に必ず表示する打ち消し文** (decisions D-6・法則 L5 への軽減策):

```
このテストはここまでです。

**ここから先の本番のプローブでは、「どちらとも言えない」も正当な回答です。**
無理にどちらかへ寄せないでください。
```

## 2. 8 ビネット (**確定版 v6**)

**設計制約**: 場面文に Q1/Q2 のアンカー語とその明白な同義語を使わない (decisions D-7)。
禁止語 (`scripts/check_vignettes.py` C1 で機械検査):
`詰ま` / `引っかか` / `進` / `近づ` / `手応え` / `はかど` / `停滞` / `スラスラ` / `すらすら`

提示順は象限が連続しない固定順 (decisions D-8): flow → stuck → incubation → idle → (繰り返し)

| # | id | 想定象限 | 場面文 |
|---|---|---|---|
| 1 | `v2f1` | flow | 30 分のあいだ、ほとんど画面から目を離さずに打ち続けた。段落が 3 つ増え、書き直したのは 1 行だけだった。 |
| 2 | `v2s1` | stuck | 同じ一文を 10 分間、書いては消している。書き直すたびに、最初に書いた言い回しへ戻ってきてしまう。 |
| 3 | `v2i1` | incubation | 難しい論点で 10 分ほど手が止まった。そのあいだに構成の見取り図ができ、書き直した段落は前より短く強くなった。 |
| 4 | `v2d1` | idle | 参考文献の書式をそろえる作業を惰性で続けている。難しいところはないが、本文は 1 文字も増えていない。 |
| 5 | `v2f2` | flow | 頭の中にある順番のまま打てている。消したのは数えるほどで、下書きの残りは節ひとつになった。 |
| 6 | `v2s2` | stuck | どう論を運べばよいのか決められないまま、カーソルが同じ行で点滅している。この 15 分で残ったのは見出しだけだ。 |
| 7 | `v2i2` | incubation | 反論の扱いに迷って何度も書き直しを重ねている。分量はむしろ減ったが、通して読むと筋が一本になった。 |
| 8 | `v2d2` | idle | 画面を眺めているだけで、何も打っていない。難しいところに当たったわけではなく、気持ちが向かないだけだ。 |

**識別の意図**:
- **3 と 8** はどちらも「手が動いていない」。**成果物が変化したか**でしか分けられない → Q2 の理解を要求する
- **6 と 8** はどちらも「打っていない」。**難しさが原因か**でしか分けられない → Q1 の理解を要求する
- **7** は「分量が減った」ので、Q2 を量と読むと誤答する → 「打った量ではない」が効いているかを測る
- **2 と 4** はどちらも「本文が増えていない」。**引っかかりの有無**でしか分けられない

**実測で書き換えた 2 件** (`tuning-log.md` §1):
- 場面 6: 「何を書くか決まらないまま」→「**どう論を運べばよいのか決められないまま**」
  （難しさの目印が無く、中心化傾向のペルソナが 3 のままにしていた）
- 場面 2: 「文字数は始めたときと変わらない」→「**書き直すたびに、最初に書いた言い回しへ戻ってきてしまう**」
  （Q2 の手がかりが「量」しかなく、教示文が「量では判断するな」と言うのと矛盾していた）

**⚠️ 均等配置は合格条件と同じ重さで守る**: 4 象限を各 2 問ずつ置いているため、
**どの定数回答 (straight-lining) を置いても一致は最大 2/8** にしかならず、6/8 に構造的に届かない。
`check_vignettes.py` C3 と `vignette_straight_lining_cannot_reach_pass_threshold` が二重に守る。

## 3. 採点器の変更

### 3.1 `infer_quadrant` — 規則は変えない

`q1>=4 / q1<=2` の端判定と「3 は `None`」は**維持**する (decisions D-6)。
中点の逃げ場は教示文と入力 UI で塞ぎ、採点規則では塞がない
(採点で 3 を救うと「想定象限を答えた」の意味が崩れるため)。

### 3.2 `VignetteScore` — 未実施を分離する

```rust
pub struct VignetteScore {
    pub total: usize,
    pub matched: usize,
    /// 一度でも施行されたか (total > 0)。未実施と不合格を分ける (PreReg-1 は延期中)。
    pub administered: bool,
    pub passed: bool,
}
```

`passed = total >= VIGNETTE_TOTAL && matched >= VIGNETTE_PASS_MIN`

- `VIGNETTE_PASS_MIN = 6` は**変更しない**
- `VIGNETTE_TOTAL = 8` の完了ガードを新設する (decisions D-10)

### 3.3 `cohort_verdict` — 未実施の `decision_reason`

主指標被験者の**誰も施行していない** (`administered == false` が全員) 場合、
`decision_reason` を「未達」ではなく **「PreReg-1 未実施 (GATE1 未発効)」** にする。
`overall` は従来どおり後続の判定に委ねる (未実施を理由に `Inconclusive` へ落とさない)。

> ⚠️ これが `cohort_20260731_225531.json` の `decision_reason` を
> 「1 人も通っていない」と読ませた原因なので、**再発防止をコードに置く**。

## 4. 記録項目の追加

```rust
VignetteResponse {
    vignette_id: String,
    expected_quadrant: ExpectedQuadrantDto,
    q1_friction: u8,
    q2_progress: u8,
    /// 場面の表示から**記録成功まで**の所要時間 (ms)。読まずに送ったかの検出用。
    /// 送信失敗による再送があった場合は初回表示からの累積。
    elapsed_ms: u64,
    /// 2 スライダー合計の値変更回数。熟慮と即答を分ける。
    changes: u16,
    ts: u64,
}
```

**data-privacy 適合**: 数値のみ。本文・タイトル・選択文字列を含まない (ルール 1 に適合)。
ローカル FS のみ (ルール 2)。外部送信なし。

### 4.1 ⚠️ 書くだけで読まないフィールドを残さない

`security-checker` MEDIUM 指摘。追加フィールドの目的は「読まずに送った回答の事後分離」であり、
**解析経路が消費して初めて成立する**。書くだけで誰も読まないなら、
目的限定・データ最小化の観点で**そもそも足すべきではない**。

→ `gse-replay` で読み取り、`VignetteRecord` に載せ、`VignetteScore` に要約を出す:

| フィールド | 内容 |
|---|---|
| `elapsed_ms_median` | 採点対象施行の回答時間の中央値 |
| `elapsed_ms_min` | 同・最短 (中央値が正常でも 1 問だけ極端に速い、を拾う) |
| `changes_total` | 同・スライダー値変更回数の合計 (0 に近いほど既定位置のまま送った) |

⚠️ **記述統計であって合否には使わない**。PreReg-1 の合格条件は 6/8 で凍結されており、
潜時をゲートにしない。用途は「6/8 で落ちた被験者が *なぜ* 落ちたか」の事後分離。

⚠️ **`Option` にする理由**: 2026-08-17 より前のログには本フィールドが無い。
`0` に潰すと**旧データが一律「即答」= straight-lining 疑いに見える**。
`None` は「記録されていない」であって「0 ms で答えた」ではない。
pretty 出力でも `n/a` と表示し、実測で両分岐を確認した。

### 4.2 不透明 ID 規則の単一化

`is_valid_opaque_id` を `analysis/calibration_eval.rs` に 1 つだけ置き、
IPC 境界 (`lib.rs`) と NDJSON 読込境界 (`gse-replay`) の両方が使う。
⚠️ `gse-replay` は**任意のローカル NDJSON を読む CLI** なので、書込側が守られていても
手編集ファイル経由で任意長 ID が入りうる (`security-checker` LOW)。
`vignette_id` は `split_attempts` が施行の境界に使うため、読込側でも弾く。

## 6. empirical-prompt-tuning の設計

**tier**: Lite → 必要なら Full へ昇格 (対象は「重要度 HIGH × 変更頻度 LOW」だが、
1 シナリオでは中心化傾向を測れないため**最低 3 シナリオ**を初回から回す)

### シナリオ (diversity rubric: median / edge-low / adversarial の 3 象限をカバー)

| id | 象限 | ペルソナ | 期待 |
|---|---|---|---|
| **S-A** | median | 教示を読んで誠実に答える被験者 | 一致 **≥6/8** |
| **S-B** | edge-low | 極端な値を避けたがる (中心化傾向の強い) 被験者 | 一致 **≥6/8** |
| **S-C** | adversarial | 場面文を読まず所要時間を最小化したい被験者 | 一致 **<6/8** ← ⚠️ **空振り検査** |

hold-out (収束判定時に追加):

| id | 象限 | ペルソナ | 期待 |
|---|---|---|---|
| **S-D** | edge-high | Q2 を「打鍵量・作業量」と読む癖のある被験者 | 一致 ≥6/8 |
| **S-E** | adversarial | 「flow / stuck / incubation」という用語を一切知らない被験者 | 一致 ≥6/8 |

### 要件チェックリスト (S-A / S-B / S-D / S-E 共通・事前固定)

1. **[critical]** 8 問すべてに Q1・Q2 を 1–5 で回答した
   → 理由: 未回答があると「8 問中 6 問以上」の判定自体が成立しない
2. **[critical]** 想定象限との一致が **6/8 以上**
   → 理由: PreReg-1 の凍結合格条件そのもの。ここが落ちると器が使えない
3. 教示文とビネット文だけで答えを決め、外部知識・repo 参照を必要としなかった
4. 8 問の回答が定数化していない (Q1・Q2 それぞれ相異なる値が 2 以上)
5. 各問の回答理由に場面文の記述を引用できた (読んで答えた証跡)
6. 「手が止まっているのに近づいた」場面と「手が動いているのに近づかない」場面を
   取り違えなかった

(6 項目中 critical 2 = 33%。skill 規定の 20–40% に収まる)

### S-C の判定 (反転)

1. **[critical]** 想定象限との一致が **6/8 未満**
   → 理由: 読まずに答えて通ってしまう器は、`notes.md` §4 の straight-lining を
     検出できない。**空振り検査**であり、ここが緑になったら器を作り直す

### 実施上の制約

⚠️ **実行者に repo を読ませない。** `VignetteTest.tsx` に想定象限が書いてあるため、
教示文とビネット文を**プロンプトに貼り付けて**渡し、ファイル参照を明示的に禁止する。
(正解ラベルは渡さない — 渡すと測定にならない)

## 7. リスクと対処

| リスク | 対処 |
|---|---|
| ⚠️ 教示文の「どちらか一方に寄っています」が**本番の回答分布を歪める** (法則 L5) | テスト完了時に打ち消し文を必ず表示 (§1)。⚠️ **残留反応性は消えない**ので、施行後の Q1/Q2 分布を施行前と比較する項目を `notes.md` の follow-up に残す |
| schema 変更で gse-dataset 側と drift | `/finish-task` Step 3 の parity check で検出。ビネットの実データは**まだ 1 件も無い**ので移行データは不要 |
| ビネット 7 (「分量が減った」) が難しすぎて誠実な被験者も落とす | S-D (Q2 を量と読む被験者) の hold-out で実測。落ちるなら文面を改訂する |
| LLM 実行者の一致率が人間被験者の代理にならない | ⚠️ **代理にならない**。本手法が測れるのは「**教示文だけで象限が一意に決まるか**」であり、人間の中心化傾向そのものではない。完了報告でこの限界を明記する |
