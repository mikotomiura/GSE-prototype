# 重要な設計判断

## 判断 1: 既存の診断パネル (`get_diagnostics`) には足さない

- **判断日時**: 2026-09-11
- **背景**: 当初は「既存の診断パネルに件数を足せばよい」と考えていた。
  ⚠️ **実測したらその前提が誤りだった。**
- **実測**: `src/components/Dashboard.tsx` の診断パネルは **`debugView` で囲まれていない**。
  ★ フックが **20 秒以上**有効にならないときに出るトラブルシュート用で、**被験者にも出る**。
  しかも `Object.entries(diagnostics)` で**全フィールドをそのまま吐く**。
- **選択肢**: A: `DiagnosticInfo` に足して `debugView` で描画を分ける /
  B: 別コマンド・別 DTO・別ブロックにする
- **採用**: **B**
- **理由**:
  - ⚠️ A は `Object.entries` の一括描画を分解する必要があり、★ **将来誰かが戻すと無言で漏れる**。
  - ★ 「放棄回数」は**被験者の振る舞いの数値**であり、較正は**完全ブラインド**が前提。
  - ★ 既存の `debug_force_probe` / `force_nudge` と**同じ二重ゲート**に載せれば前例に従える。
- **トレードオフ**: コマンドが 1 本増える。→ ★ ソース検査テスト 3 本で不変条件を固定した。
- **影響範囲**: `lib.rs` / `Dashboard.tsx` / `App.css`。⚠️ NDJSON と schema は不変。
- **見直しタイミング**: 診断パネル自体を `debugView` で囲む改修が入ったとき。

## 判断 2: カウンタは **logger 側**（実際に書かれた行）で数える

- **判断日時**: 2026-09-11（★ レビュー指摘を受けて**初版から変更**）
- **背景**: 初版は `lib.rs::emit_ime_shadow` の `try_send` 直後で数えていた。
- **⚠️ 何が問題だったか**:
  - ★ それは「**出そうとした回数**」であって「**書かれた行数**」ではない。
  - ⚠️★★★ **被験者が「止める」を押した区間の変換も数えていた** ——
    一時停止ゲートは writer ループの中にあり `ime_shadow` は確実に捨てられるのに、
    カウンタには残って研究者の画面に出る。
    ★ **「止めた区間は痕跡を残さない」(ADR-014 判断 3) が破れる。**
  - ⚠️ チャネル満杯で行が落ちてもカウンタだけ進む。
- **採用**: `logger.rs` の `writeln!` **直後**で数える。ローテートで **0 に戻す**。
- **理由**: ★ 「計器の生存」は**実際に書かれた行**でしか測れない。
  ⚠️ `logger.rs` は `crate::input` を 1 度も参照していなかったので、
  カウンタを `input/hook.rs` に置くと**依存の向きが逆**になる。→ logger が持つのが自然。
- **トレードオフ**: `logger.rs` の書き出し経路に手を入れた（⚠️ requirement の「含まないもの」を
  一部超えた）。→ ★ ただし `ime_shadow` 1 行のみで、他の行種のカウンタは足していない。
- **影響範囲**: `logger.rs` / `lib.rs` / `input/hook.rs`（★ カウンタを撤去）。

## 判断 3: ⚠️★★★ カウンタの順序 —— **初版の主張は誤りだった**

- **判断日時**: 2026-09-11（★ レビューの**実測**で反証された）
- **⚠️ 初版の主張（誤り）**: 「書き手が `abandoned` → `emitted`、読み手が `emitted` → `abandoned`
  の順なら `abandoned <= emitted` が保たれる」
- **⚠️★★★ なぜ誤りか**: ★ 書き手が `abandoned` を**先**に増やす以上、
  **共有状態そのものが `abandoned = emitted + 1` を通る**。
  → ⚠️ **読み手の順序では救えない。**
  ★ レビューが x86-64 で最小再現を作り、**5000 万回中 1034 万回**の違反を実測した
  （最悪 `emitted=4641454 / abandoned=4645163`）。⚠️ ARM（mac 実機）はさらに弱い順序。
- **採用**: ★ **書き手 `EMITTED`(Relaxed) → `ABANDONED`(Release)**、
  **読み手 `ABANDONED`(Acquire) → `EMITTED`(Relaxed)**。
- **理由**: ★ 書き手が `ABANDONED` を増やした時点で `EMITTED` は増え済みなので、
  `ABANDONED` を先に読む読み手からは常に `abandoned <= emitted`。
  ⚠️ `Release`/`Acquire` の対で**可視性**も担保する（`Relaxed` だけでは 2 変数の順序を語れない）。
- **★ 検証**: 旧順序に戻すと回帰テストが**赤**、修正版で**緑**であることを実測した
  （`abandoned_never_exceeds_emitted_under_concurrency`）。
- **⚠️ 教訓**: 初版のテストは**単一スレッド**で `n <= n + 1` を見るだけで**自明に真**であり、
  この欠陥を**取り逃がした**。★ 不変条件のテストは、**壊した実装で赤くなることを確かめる**。

## 判断 4: ⚠️★★★ 順序で守るのをやめ、**2 つの数を 1 語に詰めた**

- **判断日時**: 2026-09-11（★ 判断 3 の修正が**さらに破れた**ため）
- **⚠️ 何が起きたか**: 判断 3 で増分の順序を直したが、**全並列テストでまた赤になった**
  （`abandoned > emitted` を **44 万回**観測）。
- **原因**: ★ **ローテートの `reset` が読み出しの 2 回の `load` の間に挟まる**と、
  `abandoned` が大きいまま `emitted` が 0 に見える。
  ⚠️★★★ **これはテストの都合ではなく本番でも起きうる**
  （★ O1 の日次ローテート / G1 のブロックローテート中に読み出すと再現する）。
- **選択肢**:
  - A: 読み出しを Mutex で囲む
  - B: **2 つの数を 1 つの `AtomicU64` に詰める**（上位 32bit = 書いた数 / 下位 32bit = 放棄）
  - C: テストを「reset 中は許容」に緩める
- **採用**: **B**
- **理由**:
  - ★ B なら **読み・書き・リセットがすべて単一の不可分操作**になり、
    ⚠️ **不変条件が構造的に破れなくなる**（★ 順序の推論そのものが不要になる）。
  - ⚠️ C は**計器の嘘を仕様にする**ので採らない。
  - A は writer 経路（logger スレッド）に Mutex を持ち込む。B のほうが軽く、かつ強い。
- **トレードオフ**: 桁あふれ。★ ただし 1 ファイルに **42 億行**（≒ 250 GB 超）必要で、
  ⚠️ ローテートで 0 に戻るので累積もしない。→ doc に明記した。
- **★ 検証**: 「放棄時に emitted を進めない」壊れ方を注入すると**赤**（198 万回の違反）、
  復元で**緑**。⚠️ 詰め込み後も**テストは空振りしていない**。
- **⚠️ 教訓（2 度目）**: ★ **不変条件を「順序」で守ろうとすると、
  守るべき経路を 1 つ見落とすだけで破れる。** 構造で守れるならそちらを採る。
