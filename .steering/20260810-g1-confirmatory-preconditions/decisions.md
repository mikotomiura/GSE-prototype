# 設計判断（grill 2026-08-10 で確定）

## D-1: P010 は shakedown（確証標本外）

**決定**: `§2.8` に「実参加者による運用確認回 (shakedown)」条項を追加し、P010 をそこに置く。
確証標本には入れない。

**理由**: `§2.4-2` は「**確証データを 1 件も取得する前に** n を凍結する」と定めている。
P010 を確証標本とすると、★ **n の凍結が事後になり optional stopping の疑いを完全には払えない**。
P010 を確証標本外に出せば、⚠️ **`§2.4-2` を満たしたまま**次の被験者から確証標本を始められる。
★ `results/` は空で判定を一度も出していないので、この選択は**結果を見る前**に行われている。

**却下案**:
- **確証標本 1 人目のまま** — `§2.4-2` を満たせなかったことを違反として記録することになる。
  ⚠️ n の凍結が事後になり、以後どの n を選んでも「結果を見てから決めたのでは」が付きまとう。
- ⚠️ `§2.8` の既存パイロット条項に押し込む — 同条項は **研究者本人 1 名**を要件にしており、
  P010 は実参加者なので**そのままでは当てはまらない**。条項の新設が要る。

**⚠️ 代償（隠さない）**: P010 のデータは主判定に使えない。
★ ただし block07 の破れ（`§10-3`）があるので、いずれにせよ扱いに注釈が要るデータだった。

## D-2: n = 3 で凍結

**決定**: `config.json` の `design.n_subjects` に **3** を数値で書く。P010 は含まない（新規 3 名）。

**理由**: `§2.4` は「必要な n は結果の向きで変わり、向きは事前に分からない」としたうえで、
分離できた場合は少ない n で足り、できなかった場合はより多い n が要るとしている。
n=3 は **Fisher 統合が成立する最小の実用域 (n≥2)** であり、実施コスト（1 人 1 時間超・来所）と
の釣り合いで選んだ。

**却下案**:
- **n = 5** — Phase1 と同規模。⚠️ `§2.4` 自身が「power 計算ではなく慣例値だった」と自認して
  **一度取り消した数字**である。採るなら根拠を書き直す必要があり、コストも 1.7 倍。
- **n = 1** — `§3.9` により厳密検定は成立するが、⚠️ counterbalance が成立せず
  題材交絡を排除できない。「その人の特異体質」も排除できない。

**⚠️ 事前に宣言しておく（`§2.4-4/5/6`）**: 3 名の収集が完了するまで確証標本の解析結果を見ない。
★ **「有意になるまで足す」は行わない。** 増減も行わない。

## D-3: 確証標本の SSOT は `config.json`（★ git 管理下）

**決定**: `config.json` に `sample_roster`（`confirmatory` / `pilot` / `shakedown`）を置き、
`analyze.py` は **`confirmatory` にある被験者だけ**を解析する。

**理由**: ⚠️★★ 現在この分類を持つ唯一の場所は `blocks/*.json` だが、
**`blocks/.gitignore` が `*.json` を除外している**（ファイル名にセッション日時が入るため）。
→ ★ **この Mac にしか無く、失えば分類が消え、レビューも履歴も残らない。**
「誰が確証標本か」は研究の主張そのものを決めるので、**追跡可能な場所**に置く。

★ さらに現状 `analyze.py` は `confirmatory` フラグを**一度も見ておらず**、
glob `P*.json` は `PILOT-*.json` まで拾う。⚠️ パイロットが確証解析から外れているのは
「dataset に NDJSON が無いから」であって**コードの保証ではない**。roster はここも同時に塞ぐ。

**却下案**:
- **`blocks/*.json` に `sample` キーを足す** — 追跡されないので上記の理由で不可。
- **両方に書いて照合** — ⚠️ 本日の教訓「**鏡どうしを比べても両方が同じだけずれれば緑**」
  （`notes.md §10-7`）に反する。★ roster を**単一の正**と明記し、二重管理にしない。

## D-4: 凍結解除は「研究者承認」として記録する

**決定**: 第 15 版に「Phase1 GATE3 は判定保留のままだが、研究者承認をもって G1 を開始する」と
明記し、**日付とコミットハッシュ**を残す。実施条件の条文そのものは緩めない。

**理由**: 文書は実施条件を「Phase1 完了 ＋ 研究者承認による凍結解除後」としており、
★ **承認は条文が最初から想定している経路**である。条文を書き換えるより、
**承認したという事実を記録するほうが情報を減らさない**。

**却下案**:
- **実施条件そのものを改訂**（「Phase1 完了」を外す）— ⚠️ 凍結文書の**条件を緩める**変更であり、
  非対称性の議論（何が通りやすくなるか）を伴う。★ 承認の記録で足りるなら払う必要のない代償。
- **Phase1 GATE3 を先に決着させる** — ⚠️ 文書どおりの順序だが、GATE3 の DataInsufficient は
  Q1 の straight-lining が原因で、決着には追加のデータ収集が要る。★ G1 がその分だけ後ろ倒しになる。

⚠️★ **書くべきリスク**: Phase1 の判定が保留のまま G1 を回すので、
★ **G1 の結果が Phase1 の前提に依存していた場合、後から解釈をやり直す必要が生じうる**。
これを第 15 版に明記する。

## D-5: ⚠️ roster に無い割付ファイルを黙って落とさない

**決定**: `analyze.py` は roster のどのリストにも無い被験者を見つけたら**明示的に報告**する
（`silent skip` を作らない）。

**理由**: ★ 「絞る」実装は必ず「黙って落とす」危険を連れてくる。
`silent-failure-in-guard-scripts` の型そのもので、⚠️ **確証標本に入るはずの被験者が
roster への追記漏れで解析から消える**と、結果は緑のまま間違う。
→ ★ 落とした事実と理由を必ず出力し、結果ファイルにも刻む。
