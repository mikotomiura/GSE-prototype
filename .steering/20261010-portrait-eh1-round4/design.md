  - 値 `v` の決め方は PC-cal と同じ。実際の更新ごとに、`[0, 1)` の一様な乱数 `U` と `N` をこの順で必ず 1 つずつ引き、`U < λ` なら `v = q(u)`、そうでなければ `v = N` とする。乱数は `SeedSequence([その回の seed, key_seed & 0xFFFFFFFF, 17])` から引く（17 はほかの用途と重ならない値。形によらず同じ列を使う）。
  - 生成器への入れ方: 更新 `u` の材料に `v` を添える。描くときに、f4 の水準（`raw` では `n4`、`lattice` では `levels["f4"]`）を `v` に置き換える。`lattice` は、置き換えた水準を第 3 回と同じ 3 段の区分とヒステリシス（`delta` = 0.05）に通す。
  - ほかの 3 水準（判断 2・判断 3・判断 4）: f1・f3 は定数 0.5 に固定する。f6 は、`lattice` では定数 0.5 とする。`raw` では、印を描く更新（打鍵のあった更新。中立の後に溜めた更新を描くときも 1 つずつ）ごとに、`[0, 1)` の一様な乱数を 1 つ引いて `n6` とする。乱数は `SeedSequence([その回の seed, key_seed & 0xFFFFFFFF, 18])` から引く（18 はほかの用途と重ならない値。λ・`drift` によらず同じ列で、ラベルにも材料にも依らない）。
    - 理由: 第 3 回の `_step` は印ごとに向きを `heading` で上書きするので、位置は更新ごとの変位ベクトルの和になる。向きが定数だと描き手は画面の隅に張り付き、`frac(k × 0.618…)` の決まった列だと和が有界なので小さな輪に閉じ込められる。一様な乱数なら、壁で切り詰められるランダムウォークになって画面を広く動く（試算は `walk_check.py`・データを読まない: 480 更新で x/y の標準偏差は約 85/50 px。一様に散れば約 92/52 px）。
  - 置き換えないもの（実際の生成器のまま）: 印の数（打鍵のあった秒の数から決まる）・中立の規則（打鍵のあった秒が 60 に達するまでは地を出し、達したら溜めた更新を描く。溜めた更新は、それぞれ自分の `v` で描く）・`raw` の歩き方（歩幅は `n4` から決まる）・`lattice` のセルの順・`diffuse` のぼかし（更新ごと）。打鍵の無い更新では印を描かない（実際の生成器と同じ）。
  - 色は混ぜない（表示の段の色も無い）。漏れは印の大きさ（`raw` の歩幅を含む）だけで運ばれる。
  - λ は形ごとに下見（§3.9）で選び、`config.json` に固定する。
  - **`PCsize0-<形>`**（土台）: λ = 0 の形の PC。本番でも回す。それ自体は緑・赤の判定を受けないが、§3.2 の 3 で、その形の検査器が働くかの条件に使う。
- **神託**: 第 3 回の 6 本（`ORC300`・`ORCgap`・`ORCcum` × 既定・`recent`）をそのまま回す。
- **多値の神託**（`ORCband-<sched>`・2 本・判断 1 の 4）: 土台は第 3 回の神託と同じ `ordinal` ＋ `none`。表示の段だけで、画面を x 方向に 5 等分した縦の帯（各 64 × 180 px）ごとに色を混ぜる。

  - 中立の間（打鍵のあった秒が 60 に達する前）は、第 3 回の神託と同じく地のまま見せる。
- 結果の JSON での名前: `PC1`・`PCcal`・`PCcal0`・`PCsize-<形>`・`PCsize0-<形>`・`ORC300-<sched>`・`ORCgap-<sched>`・`ORCcum-<sched>`・`ORCband-<sched>`。下見の格子は `PCsize-<形>@<λ>`。名前の分類は、接頭辞 `PCsize-`（`@` を含まないもの）・`PCsize0-`・`PCsize-…@`・`ORCband-` を区別して行う（`PCsize` だけの前方一致で分けない）。

## 3. 合否の基準（固定）

判定は、生成器の組ごとに、ラベルごとに **緑 ／ 赤 ／ 判定不能** を出す。全体を 1 つの合否にまとめない。基準の値（0.03）は第 1〜3 回と同じ。

### 3.1 上乗せと区間

- 第 3 回 design §3.1 と同じ（P 240・4 通り・点推定は OOF の AUC の差・セッション単位のブートストラップ 2000 回の 95% 区間・層の中の並べ替え 20 回・層の境界・ラベル単位の NaN と当てはめの失敗は判定不能）。

### 3.2 検査器が働くか（ラベルごと・形ごと）

- **PC1 が働く**・**PC-cal が働く**・**帰無が通る**: 第 3 回 design §3.2 と同じ。帰無は、本番で回すすべての組（8 組・PC1・PC-cal・`PCcal0`・形の PC 4 本・`PCsize0` 4 本・神託 8 本）の論理積とする。
- **形の PC が働く**（形ごと）: 次の 3 つがすべて成り立つ（判断 3）。
  1. `PCsize-<形>` の 4 通りの下限の最大 > 0.03。
  2. `PCsize-<形>` の 4 通りの点推定の最大 ≤ 0.08（1 と 2 は PC-cal と同じ式）。
  3. **土台が基準の下**: 同じラベルの `PCsize0-<形>` の 4 通りの上限の最大 < 0.03（緑と同じ式）。大きさ以外の経路（累積した印の覆い・中立が明ける時刻・描いた更新の番号と、`raw` ではそれで決まる位置・ぼかし）だけで土台が 0.03 以上になる場合に、大きさの漏れを拾えたことを示さないまま「働く」にならないようにする。1 と 3 がそろえば、少なくとも 1 つの攻撃者で、形の PC の区間の下端が土台の区間の上端より上にある（2 つの区間が 0.03 を挟んで分かれる）。AUC の上乗せは足し算で分けられないので、「大きさの漏れの量」としては読まない。
- **形の検査器が働く**（形ごと）: NaN・当てはめの失敗が無く、PC1 が働き、PC-cal が働き、その形の PC が働き、帰無が通る。
- 境界の値は第 3 回 design §3.2 と同じ（0.03 ちょうどの下限は働かない、0.08 ちょうどの点推定は働く、0.10 ちょうどの下限は働かない、0.03 ちょうどの帰無は通らない）。土台の上限が 0.03 ちょうどなら、3 は成り立たない。
- **NaN と当てはめの失敗**は、第 3 回と同じくラベル単位で、すべての形に効く（ブートストラップの抽選はラベルごとに 1 組で全組が共有するので、NaN はラベル単位で起きる。第 3 回 design §3.1）。そのラベルでは `weak_detector`・`weak_shape_pc`・`shape_baseline` を評価せず、付けない（第 3 回と同じ）。
- JSON には、ラベルごとに `pc1_ok`・`pccal_ok`・`null_ok` と、形ごとの `pcsize_ok[<形>]`・`detector_ok[<形>]` を書く。働かない理由は、第 3 回の `nan`・`fit_failed`・`weak_detector`（PC1 か PC-cal が働かない）・`null` に、`weak_shape_pc`（その形の PC の 1 か 2 が成り立たない）と `shape_baseline`（3 が成り立たない）を足す。NaN・当てはめの失敗が無いラベルでは、当てはまる理由をすべて併記する。

### 3.3 E1-3: 形に停滞の情報が残らないか

- ラベルごと（L300・L60・L1800）・組ごとに判定する。
- **判定不能**: その組の形の `detector_ok` が偽。
- それ以外の場合:
  - **緑**: 4 通りの上乗せの 95% 区間の上限の最大 < 0.03。
  - **赤**: 上限の最大 ≥ 0.03。
- **主の判定は L300** である。L60・L1800 は副の判定で、3 つとも報告する。結果を見て主を選び直さない。
- **結果の前の宣言**:
  - **実際の 8 組と神託 6 本の値は、第 3 回で見ている**。合成の記録・seed・計器の該当部分が同じなので、第 4 回でも同じ値になる見込みである（§3.6 で照合する）。第 4 回で新しく分かるのは、形の PC・`PCsize0`・`ORCband` の値と、それによる検査器の条件だけである。この基準は、8 組の値を知った後に書いている。それでも、基準の値（0.03）・組・ラベル・攻撃者は第 3 回から変えておらず、変えたのは検査器の確かめ方を足したことだけである。
  - **帰結**: 第 3 回の L300 では 8 組の上限の最大が +0.003〜+0.009 だった。値が再現すれば、**第 4 回の L300 の 8 組は赤にならない**。L300 の判定が緑になるか判定不能になるかは、その形の PC（と帰無）が働くかどうかだけで決まる。PC が通りやすい作り方を選ぶと緑が増える、という誘因があるので、判断 2〜4 の細部（水準の固定・向きの乱数・乱数のタグ・形ごとの結び方・土台の条件）と §1.4 の定義は、**下見・スモーク・selftest・本番のどの結果を見ても変えない**（§3.7 の「落ちた場合の扱い」）。
  - 下見の土台（λ = 0）が高く、本番で §3.2 の 3 が成り立たない見込みが下見の時点で分かっても、細部・λ の規則・条件は変えない。報告では、`shape_baseline` で判定不能になった形について、下見の土台の値を並べる。
  - 帰無の論理積は 17 本から 27 本に広がるので、第 3 回より判定不能（理由 `null`）になりやすい側に効く。
  - 形の PC が 0.05 に届くかは確かめていない。打鍵の無い更新では印を描かないので、停滞の多い区間ほど描かれる印が少なく、`q` が大きい値ほど画像に現れにくい。`lattice` は大きさを 3 段に量子化するので届きにくいかもしれない。`diffuse` は印をぼかすので、これも届き方が変わる。λ = 1 でも届かなければ（§3.9 の手順 4）、その形の 2 組は判定不能になりうる。**届かなくても、属性・条件・ラベルは変えない**。
  - L60・L1800 は、第 3 回で PC-cal（と L1800 の PC1）が届かなかった。同じ値になる見込みなので、第 4 回でも構成上判定不能になる見込みが高い。λ・条件・ラベルは変えない。
  - 形の PC の λ は L300 だけで合わせる。下見（P 40）と本番（P 240）の値のずれの扱いは、第 3 回 design §3.3 と同じ（どちらに外れても判定不能のまま進み、下見と本番の値を §8 に並べる）。
- 打鍵の有無で決まる量のうち、モデル A が持つもの（窓ごとの打鍵の秒・間隔・`since`・直前 900 s など）は、条件つきの検査では上乗せにならない（第 2 回 design §3.1 と同じ）。モデル A が持たないもの（中立が明けた時刻・描いた更新の番号とヒステリシスの状態・`raw` の位置（変位の累積で決まり、重心に出る）・累積した印の覆い・ぼかしを通した無打鍵の長さ）は上乗せになりうり、そうならないことは確かめていない。形の PC では、これらの経路を `PCsize0` で測り、§3.2 の 3 で受ける。

### 3.4 神託（ラベルごと・神託ごと）

- 第 3 回 design §3.4 と同じ判定を、8 本（第 3 回の 6 本と `ORCband` 2 本）それぞれに当てる。「狭い」の条件の PC-cal は、第 3 回と同じく `pccal_ok` とする（神託はどれも色で運ぶため）。
- 神託の判定は、実際の組の判定（§3.3）を変えない。報告では、組の判定と、その組の scheduler の神託 4 本の判定を並べる。
- 読み方の限定（結果の前に書く。第 3 回 design §3.4 の「どの神託も、更新ごとに運ぶのは 1 つの値」は、`ORCband` については成り立たないので、この節で置き換える）:
  - 神託の判定から言えるのは、**指定した 4 種類の写し方（1 値の 3 本と `ORCband`）と、固定した 4 通りの攻撃者で測った値**までである。「その scheduler を通る経路が 0.03 以上を運べない」とは言わない。
  - `ORCband` は、直前 300 s の停滞を、60 s ずつ 5 つの値として 1 回の更新で運ぶ。ただしこの攻撃者に見えるのは、ほぼ 5 値の多重集合（8 個のビンの色相のヒストグラムに量子化したもの）と、平均の色（5 値の平均 ≈ `q(u)` に近い）だけである。色相 0 と 0.6 の帯は、地からの差がほぼ同じ（約 0.53 と 0.54）なので重心がほとんど動かず、帯の並びの順はほぼ見えない見込みである。したがって `ORCband` が 1 値の `ORC300` より多く当てるとは限らない。各 scheduler の上限の目安は、神託 4 本の上限の最大とする。
  - `ORCcum` の限定は第 3 回 design §3.4 と同じ。

### 3.5 第 3 回との関係と、緑の意味の範囲

- 第 2 回・第 3 回の判定は書き換えない。第 4 回は、検査器の確かめ方に形の PC を足した別の固定である。
- **形の PC が示す範囲**: 打鍵を見ない 60 s の時計で、その形の生成器の、印の大きさの水準（`raw` では歩幅も）に乗せて運ばれる約 0.05 の漏れ（土台が基準の下にあるもの）を、この統計の手順と固定した 4 通りの攻撃者で拾えること、までである。点推定は λ = 0 の土台を含んだ値である。印の位置・明るさ・色相に乗る漏れや、ほかの 3 水準も同時に動く場合を拾う力は確かめていない。`clock60` は 60 s ごとに描き、ぼかすので、更新の間隔と、`diffuse` のぼかしの回数は、既定・`recent` の組と違う。`raw` の向きは一様な乱数で、実際の材料の向きとは違う。
- **まばらな更新の経路について言えること**: 既定・`recent` を通る陽性対照は、この回も無い。この経路については、指定した神託 4 本（1 値の 3 本と `ORCband`）の上限が、固定した攻撃者で 0.03 未満であること（狭い）だけを言う（§3.4 の限定）。
- したがって第 4 回の組の緑は、「上の範囲で働くことを確かめた検査器（色の PC-cal と、その形の大きさの PC）と攻撃者で、0.03 以上の漏れが見つからなかった」までである。組の緑は、同じ scheduler の神託 4 本の判定と並べて読む。親の判断 8 の扱いは研究者が決める（第 3 回の判断 8）。
