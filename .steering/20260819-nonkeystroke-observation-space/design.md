# 設計 (v2) — 非打鍵タスクの観測空間を「実測で」決める

> ⚠️★★★ **本タスクは設計文書だけを作る。`src-tauri/` のコードは 1 バイトも変えない。**
> ★ 「実装」「実施」と書かれた箇所はすべて **別タスク**の対象である。

## 0. 設計の出発点 — 要件から直接引いた 3 つの制約

| # | 要件の逐語 | ★ 設計への拘束 |
|---|---|---|
| 1 | 「**何を入れるか**は dev の推測ではなく…**実測で**決める」 | ★ **候補の順位と採否を人が決めてはならない。** ただし**候補の列挙**と**配線**は人が持つ（ADR-008 D1） |
| 2 | 「打鍵での推論のみでは**また同じ形になる**」 | ★★★ **「同じ形かどうか」は比較しないと言えない。** → **比較対象（打鍵側の基線）を設計に組み込む**のが必須要件であり、飾りではない |
| 3 | 「**計器がコホートを跨げなかった**」が 2 件目 | ★ **収集より先に計器がある**ことを、**人の規律ではなく機械で**強制する（★ 今回の失敗は「規約は書いてあったが適用しなかった」で起きた） |

## 1. 実装アプローチ — ★ 2 段階にし、**1 段目を募集ゼロで回す**

⚠️★★★ **最も重要な設計判断**: 要件が問う「非打鍵タスクの沈黙は何で埋まっているか」のうち、
**総量の問いは、既存の計器で、新規募集ゼロで、いま答えられる。**

### 1.1 なぜそう言えるか（★ 実測・`file:line`）

`src-tauri/src/input/liveness.rs:86-104` の `step()` は次の 3 分岐である:

```rust
if !session_active || hook_event_seen { return Starvation { starved_ms: 0 }; }  // 打鍵でリセット
if !system_input_seen { return prev; }                                          // 入力皆無で凍結
Starvation { starved_ms: prev.starved_ms.saturating_add(tick_ms) }              // それ以外で加算
```

→ ★★★ **`starved_ms` は「打鍵が無い時間のうち、OS が入力（マウス含む）を見ていた累積時間」そのものである。**
★ さらに `lib.rs:2951-2956` の復帰行が **エピソードのピーク**を搬送する。

⚠️ **これは転用ではなく、設計者が明示的に用意した再解釈である**
（ADR-011 D5・`liveness.rs` のテスト `mouse_only_work_is_a_known_false_positive` 逐語
「だから NDJSON には `starved_ms` を載せ、**後から再解釈できる**ようにしてある」）。

→ ★ **すなわち「沈黙のうち何割が *何らかの入力を伴っていたか*」は、
`liveness.rs` 導入（2026-08-09）以降のログなら *追加実装ゼロ* で出る。**

### 1.2 したがって設計はこうなる

```
  Stage 0 ── 募集ゼロ・既存計器・新規収集ゼロ ──────────────────────────
    入力: G1 コホートのログ（★ hook_health を含むことが機械確認済み）
    出す量: ★ 打鍵タスクにおける「沈黙の被覆率」＝ ★★★ 比較の基線（要件 #2）
    副産物: ADR-011 Migration 3b（未了）の消化 ＝ パイプラインの実地検証
              ↓  ★ ここで θ（合格閾値）が データから 決まる。人が選ばない
  Stage 1 ── 形成的コホート・専用計測器 ────────────────────────────────
    入力: 非打鍵タスクを普段行う人 ＋ 同一人物の短い論述ブロック
    出す量: ★ チャネル別の被覆率と限界寄与 ＝ superset の順位
```

★★★ **この順序が v1（いきなり新コホート）より優れている理由**:

| # | 理由 |
|---|---|
| 1 | ⚠️ **募集リソースは G1 の残り 2 名と競合する**。Stage 0 は募集を 1 名も使わない |
| 2 | ★★★ **閾値 θ を人が選ばなくて済む** —— 「打鍵タスクでの被覆率」が基線になるので、
      **「非打鍵でも同じ値なら *まさに同じ形* である」と実測で言える**（要件 #2 への直接の答え） |
| 3 | ★ **Stage 0 が空振りなら Stage 1 を作らない**。⚠️ 「あると便利そうだから全部集める」の反対側に、
      **「実測で不要と分かったから作らない」**を置ける |
| 4 | ★ ADR-011 Migration 3b（**未了**・「コードと自己検査は揃っており、入力を差し替えるだけで動く」）を
      **本設計の一部として消化する**（★ 新しい仕事を増やさない） |

⚠️★★★ **v1 との最大の違い**: v1 は θ を「事前登録で固定する自由パラメータ」にしていた。
★ v2 は **θ をデータから導く**。⚠️ ただし **非打鍵データを見る前に**（Stage 0 は別コホート・別モダリティ）
決まるので、**forking paths を踏まない**。

## 2. Stage 0 の設計（募集ゼロ）

| 項目 | 内容 |
|---|---|
| 入力 | G1 コホートの NDJSON（⚠️ **ローカルに無い**。研究者からの提供が要る） |
| 実装 | ★ 抽出は `experiments/20260819-silence-presence-decomposition/` を**そのまま使う**。⚠️ **被覆率の集計層だけは新規**（事前登録 §2.1 の `被覆率_L-a`） |
| 前処理の必須検査 | ★★★ **対象ログの行種を数える**（`hook_health` が実在するか）。⚠️ **これを最初に置く**（今回の失敗の再発防止） |
| 出す量 | ① 沈黙区間の総時間、② そのうち `starved_ms` が進んでいた時間の割合 ＝ **打鍵タスクの被覆率 `C_write`** |
| ⚠️ 限界 | **G1 は確証標本 1/3 名**。★ **`C_write` は点推定ではなく「幅」として扱う**（全員の値を併記し、範囲で θ を置く） |
| Stop | ⚠️ `hook_health` が G1 にも無い → **Stage 1 の設計前提が崩れる**ので、そこで止めて収集仕様（ADR-013）を先に入れる |

★ **θ の定義**: `θ := max(C_write の全被験者値)` とする。
→ ★★★ **「非打鍵タスクの被覆率が、打鍵タスクの最大値をも超える」** ことを要求する。
⚠️ **これは厳しい側の置き方であり、意図的である** —— 甘い θ は「同じ形」を「違う」と読ませてしまう。

## 3. Stage 1 の設計（形成的コホート）

### 3.1 測る量

```
沈黙区間      := 打鍵イベントが無い連続区間で長さ ≥ 30 秒
                 ★ 30 秒は liveness.rs:64 log_after_ms と揃える
                 ⚠️ 揃える理由は Stage 0 と同じ土俵で読むためであって、
                    30 秒に理論的な意味があるからではない

被覆率(C)     := Σ(チャネル集合 C のイベントが覆った沈黙時間) / Σ(沈黙時間)
限界寄与(c)   := 被覆率(C) − 被覆率(C \ {c})
null 被覆率(c):= そのチャネル自身のイベント率から期待される被覆率（★ 併記必須）
```

⚠️ **「覆った」の定義（`[t−w, t+w]`）の `w` は実データを見る前に凍結する。**

### 3.2 候補チャネル — ★ **取得コストで層別し、安い層から測る**

⚠️★★★ **ゼロから起こさない。** `domain-adapter-boundary.md` §Adapter A/B/C と
`personalization-and-online-learning.md §5.2 (a)` の既存列挙から起こす。

| 層 | チャネル | 取得手段 | ⚠️ content-free |
|---|---|---|---|
| **L-a** | **「何らかの入力があった」の 2 値** | ★ **既存**（`starved_ms`・追加実装ゼロ） | ★ 可 |
| **L-b** | ポインタ移動量 / ボタン押下 / ホイール | 新規フック（別計測器） | ★ 可（**座標を捨て量だけ**持つ） |
| **L-c** | フォーカス遷移**回数** | 新規フック（別計測器） | ★ 可（⚠️ **識別子を保存した瞬間に [P117] の穴**） |
| **L-d** | アプリ内の操作種別 | ⚠️ **プラグイン方式**（Adapter C が警告） | ⚠️ 要設計・**本タスクの次段** |

★★★ **層の順に測り、前の層で θ を超えたら次の層に進まない。**
⚠️ 理由: ADR-008 D1 が禁じた「dev の推測で superset を決める」の裏返しとして、
**「実測で足りたのに、さらに集める」も禁じる**。

⚠️ **列挙から意図的に外したもの（★ 外した記録を残す）**:
アプリ識別子 / ウィンドウタイトル / URL / プロジェクト名 / スクリーンショットの保存
（★ `data-privacy` 禁止事項・**[P117] が落ちた穴**）。

### 3.3 content-free の保ち方 — 3 チャネルを**融合しない**

```
  観測（L-a〜L-c）  ─→ 被覆率の計算            ★ アプリ識別子ゼロ
  宣言（ブロック単位）─→ 「どのタスクの被覆率か」 ★ ラベル付けのみ
  参照（録画）      ─→ 解釈と妥当性検査         ⚠️ 検証用サブサンプルのみ・コード化後に破棄
```

★ 根拠は **ADR-010 D3** 逐語「**宣言は routing のみ、観測は `scope_fit` のみに使う。
融合して「真の task_kind」を作らない**」の写しである（★ **新しい原則を持ち込まない**）。

⚠️★★★ **v1 からの縮小**: 画面録画を**全セッションではなく検証用サブサンプルに限る**。
★ 理由: **被覆率の計算に録画は要らない**（量的指標である）。
録画が要るのは **「被覆＝作業だったか」の妥当性検査**だけである
（⚠️ [P121] の mid 帯「離脱 or 外部資源への相談」と同じ曖昧さが被覆にも残るため）。
→ ★ **同意のハードルと受諾率の低下を、必要な分だけに抑える。**

### 3.4 セッション設計

```text
[warm-up] → [A: 非打鍵タスク] → [B: 短い論述] → [A': 非打鍵タスク]
  破棄       （普段の作業）       ★ 同一人物内の比較    （復帰の確認）
```

- ★ **B を入れる理由は要件 #2 そのもの**。⚠️ B が無いと比較対象が別コホートになり、
  **ADR-011 D7（個人差と実タスク差が切り分けられない）**を自ら踏む。
- ★ 順序は被験者間で **counterbalance**（`§2.3` と同型）。warm-up は破棄。境界をまたぐ窓は除外。
- ⚠️ **要因を掛け合わせない**（`§2.8` 逐語）。論述ブロックは**セッションあたり 1 本**。

### 3.5 合格基準（★ 実データを見る前に凍結）

| 判定 | 条件 |
|---|---|
| **主基準** | 層 L の合同被覆率が **n 名全員**で `θ`（Stage 0 由来）を超える |
| **副基準（必須併記）** | ① **null 被覆率**、② **`C_write`（同一人物の論述ブロック）** の 2 基線 |
| **採否** | チャネル `c` を superset に入れるのは **限界寄与(c) ≥ δ** かつ **null 超過**のとき |
| **Stop-1** | 合同被覆率 < θ → ★ 次の層へ進む（L-a → L-b → L-c） |
| **Stop-2** | ⚠️ **L-c まで進んでも θ 未満** → ★★★ **「非打鍵タスクの沈黙は、この観測空間では埋まらない」と結論し、T3 を future work に戻す**（→ D-11 の改訂を巻き戻す ADR を書く） |
| **⚠️ 逆向きの結論** | ★ **`C_nonkey ≈ C_write` なら「まさに同じ形である」と実測で書く。** ⚠️ **これは失敗ではなく、要件 #2 への答えである** |
| 除外 | warm-up / 境界をまたぐ窓 / 沈黙区間 <20 本の被験者 |

⚠️★★★ **2 基線を必須にする根拠**: [V83] 逐語 **`We cannot replicate models that significantly
improve over the baseline of a majority classifier.`** ＋ `§8` 2026-08-16 決定
「**勝ち幅は 2 つの基線に対して報告する**」。★ これが無いと **[P117] の「偶然 +0.07」を
「有望」と読む誤り**が形式を変えて再発する。

### 3.6 n と期間の下限

**n≥3 名 × 各 ≥3 セッション × 各 ≥30 分、かつ沈黙区間 ≥20 本/人。判定は「全員一致」。**

★ 根拠は **既存先例と同型で、新しい原則を持ち込まない**:
GATE3 の「全員 >0.55」（`§8`）／「≥20 件/人 は floor …単一事例最小 ~15–18点 [V28] と
within-person 信頼性理想 ~70–100機会 [V27] の間」（`§8` 逐語）。

### 3.7 モダリティの選定規則

★ **打鍵密度が薄い順**（CAD → 動画編集 → スライド）に n を満たすまで**降りる**。
⚠️ 降りたら**降りたことを記録する**。★ **一括で始めない**（Adapter C 逐語「まず一アプリに限定」）。

### 3.8 計測器

★ **専用の別計測器**（standalone・GSE 本体と別プロセス）。
出力は **Layer 2 `EventEnvelope` 互換**にして後で本体へ additive に移植できるようにする。
⚠️ `src-tauri/` に触れない・`HMM_VERSION` を動かさない・ゴールデン/schema に触れない。
★ **計測器自身が `capabilities` を刻む**（＝ §4 の規律を最初から満たす）。

## 4. 収集仕様（ADR-013）— ★ **人の規律ではなく機械で強制する**

⚠️★★★ **要件 #3 の核心**: 今回の失敗は「規約が無かった」のではない。
`§5.2` に **「⚠️ 旧 NDJSON には本フィールドが無い」と書いてあったのに `hook_health` には適用しなかった**
（`notes.md §1.1` 逐語）。→ ★ **人が適用し忘れられる形では同じことが起きる。**

### 4.1 穴 C — `capabilities` を **コードから導出**し、テストで固定する

```json
{"type":"meta","session_start":1720000000000,"hmm_version":"0.4.0",
 "app_version":"0.x.y",
 "capabilities":["key","feat","paste","ime","hook_health","starve_window","self_marker","probe"]}
```

★★★ **v1 からの改良**: ⚠️ **手書きの列挙は必ず腐る**
（新しい行種を足したときに `capabilities` の更新を忘れる ＝ **今回と同じ失敗の別形**）。
→ ★ **導出とテストで機械強制する。**

⚠️★★★ **【2026-08-19 訂正 — 本節の初版は誤りだった】**
初版は「**`LogEntry` の variant から導出する**」と書いていたが、⚠️ **これは ADR-013 D2 が
明示的に却下した方式**である。★ 実測により、**`LogEntry::ImeShadow` は両 OS でコンパイルされるが
送出元は `#[cfg(target_os="windows")]` だけ**であり、**macOS で過大申告する**ことが判明した
（＝「計器が無い」を「信号が無い」に化けさせる）。
→ ★★★ **正しくは「このビルドで *送出元* が実在する行種」を `#[cfg]` を効かせて集約する。**
★ **実装仕様の SSOT は `docs/adr/ADR-013-collection-self-description.md` D1〜D3 である。**

★ 解析側の機械判定:

| `capabilities` | 該当行 | ★ 結論 |
|---|---|---|
| ✅ | 0 行 | ★ **信号が無かった**（測れて、無かった） |
| ✅ | ≥1 行 | ★ 通常 |
| ❌ | 0 行 | ⚠️ **計器が無かった** ← ★ 今回の失敗がここ |
| ❌ | ≥1 行 | ⚠️ 宣言のバグ → `app_version` で追跡 |

⚠️ **`hmm_version` では代用できない**（実測: HMM の版であって「何を記録できるか」ではない）。

### 4.2 穴 A — micro 帯は **`hook_health` の意味論を 1 文字も変えずに** 足す

```json
{"type":"starve_window","t":1720000060000,"win_ms":60000,"n_lt30":7,"sum_lt30_ms":4200}
```

★★★ **決定的な利点**: `lib.rs:2924` の出力条件を変えないので、
**≥30 秒トラックの旧ログ（G1 を含む）と新ログが同一意味論のまま比較できる。**
→ ⚠️ **Stage 0 の `C_write` が新ログでも有効なまま**であり、
`experiments/…/env.md` の依存表を壊さない（ADR-011 の再計算が起きない）。
★ ログ量は 1Hz 案の **1/60**。⚠️ 失うのは micro 沈黙の**位置**（本数と合計は残る）。

### 4.3 穴 B — `dropped_delta` を additive に併記

```json
{"type":"hook_health", ..., "dropped":42,"dropped_delta":3}
```

★ `lib.rs:2883-2891` に**既に `prev_dropped` があり差分は `dropped_now` として `tracing` に出ている**（実測）。
→ **搬送 1 行で済む。** ⚠️ 改名（`dropped_total`）は breaking なので採らない。

### 4.4 ⚠️ 入れないと決めるもの（★ 明示的に record する）

| 入れないもの | ⚠️ 理由 |
|---|---|
| 非打鍵モダリティの信号本体を **GSE 本体へ** | ★ **Stage 0/1 の結論待ち**。⚠️ 今入れると **ADR-008 D1 が禁じた「dev の推測で superset を決める」** |
| 1Hz の全 tick 記録 | ⚠️ ログ量・バッテリ。★ 値の大半が 0。窓集計で足りる |
| `dropped` の改名 | ⚠️ breaking。★ 併記で誤読は消える |
| アプリ識別子 / ウィンドウタイトル / URL | ⚠️ `data-privacy` 禁止・**[P117] の穴** |

### 4.5 実装時期

★ **G1 完了後に始め、次コホートの最初のセッション前に終える。**
⚠️★★★ **締切は募集開始ではなく *収集開始* である** —— 本タスクの動機がまさに
「計器がコホートより後に作られた」だからである。
