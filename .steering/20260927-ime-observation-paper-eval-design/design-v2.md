# 設計 v2（/reimagine 1 回目・2026-09-28 — requirement.md だけから再生成）

⚠️ 本書は `/reimagine` が `requirement.md` **だけ**を読んで作った案である（`design-v1.md` は参照していない）。
★ 比較は `design-comparison.md`。★ 確定済みの判断（`decisions.md` 判断 1–13）とぶつかる箇所は比較表で明示する。

## 0. 設計の芯 —— 「何を主張するために、何を測るか」

★ 論文の主張は 1 文に畳める:
**「本文を取らないロガーが、日本語 IME の変換の動態を、書字研究に使える精度で、OS の非対称を明示したまま記録でき、しかも本文をどこまで漏らすかが定量的に分かっている」。**

→ この主張を支える評価は **3 層**に分かれる。v2 はこの 3 層を別々に設計する:

| 層 | 問い | 誰が気にするか |
|---|---|---|
| **L1 事象の一致** | 1 回の変換ごとに、検出・時間・放棄・ナビが IME 自身の状態と一致するか | ツールの作り手・査読者 |
| **L2 測度の一致** | 書字研究者が**実際に計算する集計量**（テキストごとの平均変換時間・放棄率・変換中の時間割合）が一致するか | ★ **BRM の読者**（使うのは集計量） |
| **L3 漏洩** | ログから本文・本文の同定がどこまでできるか | 倫理審査・参加者・査読者 |

⚠️ **L1 だけでは BRM の読者に答えていない。** 事象レベルで 95% 一致でも、誤りが特定の条件（速い打鍵・長い変換）に偏れば集計量は系統的にずれる。→ ★ **L2 を主評価の一つに格上げする**（v2 の最大の変更点）。

## 1. 計器の構成（正解・入力・観測）

### 1.1 三つの記録を同時に取る（三者照合）

```
[シナリオ実行器] ──合成キー──> [OS の IME] ──> [ホストアプリ（前面）]
   │ (a) 意図の記録 = oracle                          │ (b) 正解 = IME 自身の状態（自プロセス内）
   │                                                  │
   └──────────────────────────────> [公開する観測部] ── (c) ImeShadow 行
```

| 記録 | 何か | 役割 |
|---|---|---|
| (a) **oracle** | シナリオ実行器が「何をするつもりだったか」（例: 候補 2 つ目で確定・ESC で取消・矢印 3 回） | ★ **正解の検証だけに使う**。⚠️ 観測部の評価には使わない（macOS の観測部は打鍵推論なので、打鍵由来の oracle で評価すると**循環する**） |
| (b) **正解** | ホストアプリ自身が受け取った IME の状態変化 | ★ 観測部を評価する唯一の基準 |
| (c) **観測** | 公開する観測部の出力 | 評価対象 |

★ **(a)↔(b) の不一致 = 「IME がシナリオの意図どおりに動かなかった」試行**。
→ ⚠️ 捨てずに**件数と型を報告する**（IME の学習・予測候補・タイミングで起きる）。★ 観測部の評価は (b) に対して行うので、(a)↔(b) の不一致試行も (b)↔(c) の評価には含める（除外すると「IME が素直に動いた易しい試行」だけが残る）。

### 1.2 正解の取り方（(b)）

- **macOS**: `NSTextInputClient` を実装した最小のホストアプリ。**全メソッドの呼び出し**を記録する（⚠️ 事前にどれが開始・確定・取消かを決め打ちしない —— 1.4 の Phase 0 で呼び出し列から決める）。
- **Windows**: ★ **TSF 対応のホストアプリを主経路**にする（MS-IME も Google 日本語入力も TSF の IME なので、翻訳層を挟まない）。composition の開始・更新・終了と候補一覧の表示を受ける。★ IMM 互換メッセージで受ける版も作り、Phase 0 で**両者が同じ区間を返すか**を確かめる（食い違えばそれ自体を報告する）。
- ★ **正解ログは content-free にする**: 記録するのは**イベント種別・長さ・時刻だけ**（確定文字列は記録しない）。→ 公開してもコーパスの著作権・漏洩の議論が要らない。★ 照合には長さで足りる。
- ⚠️ どちらも**自プロセス内の観測**であり、他プロセスの composition を覗かない（`docs/agent-shared.md` 制約 7 に触れない）。

### 1.3 ホストアプリを要因にする（★ v2 の追加）

⚠️ 正解が取れるのは自作のホストアプリだけだが、**実際の書字は他のアプリで起きる**。
→ ★ 2 段にする:

| 段 | ホスト | 正解 | 評価 |
|---|---|---|---|
| 主 | 自作ホスト（両 OS） | (b) あり | L1 / L2 のすべて |
| 転移確認 | 実アプリ（macOS = テキストエディット、Windows = メモ帳） | ⚠️ (b) なし | ★ **oracle で数えられる量だけ**（変換の数・放棄の数）＋ `dwell_ms` の**分布**が主と同じかを比べる |

★ Windows の観測部は IME の候補窓のイベントに依るので、**ホストによって候補窓の出方が変わる**可能性がある。→ 転移確認が無いと、査読で「自作アプリだけ」と言われたときに返す材料が無い。

### 1.4 Phase 0 —— 計器そのものの検証（★ 本計測の前・凍結の前）

⚠️ **観測部は走らせない。** ★ 計器（正解・入力・時計）が正しいことだけを確かめる:

1. **呼び出し列の採取**: 全シナリオを各数回流し、(b) の呼び出し列の型を集める → **正解の定義（開始・確定・取消・候補表示）を決める**。
2. **合成入力が届くか**: 合成キーが IME を駆動し、かつ観測部のフックにも届くことを**観測部の生の打鍵行だけ**で確かめる（★ ImeShadow 行は見ない）。
3. **oracle と正解の一致率**を測る（★ 低ければシナリオ・タイミングを直す）。
4. **時計の対応**: 同期マーカーをブロックごとに打ち、正解側と観測側の時刻差の**分布とドリフト**を測る。⚠️ 観測側の時刻は壁時計なので、run 中は時刻同期を止め、跳びを検出したブロックは除外する。

→ ★ Phase 0 の結果（正解の定義・時計誤差の実測）を preregistration に**根拠として書いてから凍結**する。

### 1.5 IME の状態を固定する（★ v2 の追加）

⚠️ **IME は学習する。** 前の試行で選んだ候補が次の試行で先頭に来ると、同じシナリオでも Space の回数・候補の位置が変わり、**試行が独立でなくなる**。

- ★ 学習・予測変換・ユーザー辞書・ライブ変換（macOS）の設定を**要因または固定値として記録**し、ブロックの先頭で**辞書・学習状態をリセット**する（リセットできない IME は「学習の影響を受けうる」と限界に書く）。
- ★ OS / IME の版を記録し、計測中は自動更新を止める。

## 2. 入力の設計

### 2.1 シナリオ（何を起こすか）

★ シナリオは **「変換の結末 × 操作の経路」** の直積から作る（網羅性を構造で担保する）:

| 軸 | 水準 |
|---|---|
| 結末 | 確定 / 取消（候補表示中）/ 取消（候補表示前）/ 全消去 / 打ち切り（20 秒超） |
| 確定の経路 | Enter / 候補を巡回して Enter / 数字キー / マウス / 予測候補 / 変換せずに Enter |
| 途中の操作 | なし / 文節移動（矢印）/ IME を切る / フォーカスを移す |
| 入力モード | ローマ字 / かな（macOS はライブ変換 ON/OFF も） |

→ ★ 全組み合わせではなく、**各水準が少なくとも 1 シナリオに現れる**被覆で 15〜20 本に絞る（被覆表を preregistration に載せる）。

### 2.2 打鍵の速さを要因にする（★ v2 の変更）

⚠️ 「公開された分布からサンプルする」だけでは、**精度が速さにどう依存するか**が見えない。
→ ★ **キー間隔を 3 水準**（遅い・中・速い）の要因にし、**速さ別の精度曲線**を示す。★ 各水準の値は公開の打鍵研究から根拠づける（出典は `[Pn]` で接地）。
★ 加えて **候補を選ぶまでの間**（思考の間）を 0.2 s〜20 s の範囲で振り、`dwell_ms` の誤差と 20 秒打ち切りの境界を見る。

### 2.3 入力文

- ★ **2 つのコーパス**: 青空文庫（著作権切れ・古い文体）と、現代文（ライセンスが再配布を許すもの）。⚠️ 青空文庫だけだと E2 の攻撃者の言語モデル（現代文で学習）と文体がずれ、**漏洩を過小評価する**。
- seed 固定で抽出し、抽出スクリプトと seed を公開する。

### 2.4 試行数の決め方

⚠️ **合成入力には「自然な混合比」が無い。** → ★ 全シナリオを足し合わせた 1 つの精度は、シナリオの配分で**いくらでも動く**。
→ ★ **主推定値はシナリオ別**に出す。★ 全体をまとめるときは**重み（既定 = 均等）を明示**し、「自然な打鍵での精度ではない」と書く。

- ★ 精度目標: シナリオ × 速さ × OS/IME のセルごとに、再現率 0.95 付近で Wilson 95% 半幅 ≈ ±5pt → **n = 75/セル**。
- ★ 所要時間の見積もり: 1 試行 ≈ 8 s として、1 OS/IME あたり 15 シナリオ × 3 速さ × 75 = 3,375 試行 ≈ **7.5 時間**。→ 1 晩 1 セル。
- 転移確認（1.3）は「中」の速さだけ・n = 30/シナリオ。

## 3. 解析計画（L1 / L2 / L3）

### 3.1 L1 事象の一致

- **照合**: 正解の区間と観測の区間を時間の重なりで 1 対 1 に対応づけ、残りを **取り逃し / 偽検出 / 分割 / 併合**に分類する（★ 併合は macOS のマウス確定・数字キー確定で起きると分かっているので、**型ごとに数える**）。
- **指標**: 検出の再現率・適合率（Wilson CI）、`dwell_ms` の誤差（中央絶対誤差 ＋ Bland–Altman）、`abandon` の混同行列と κ、`nav` の一致率。
- ★ **母数の定義を OS ごとに 2 通り**持つ（OS ごとの定義に合わせた正解 / 両 OS 共通の定義の正解）。→ 「定義の違いで何が落ちるか」を示す。

### 3.2 L2 測度の一致（★ v2 で主評価に格上げ）

- ★ 試行を「テキスト」単位（1 文 = 複数の変換）に束ね、書字研究者が使う集計量を正解・観測の両方から計算する:
  テキストごとの**平均変換時間 / 変換の数 / 放棄率 / 変換中の時間割合**。
- ★ 指標: **Bland–Altman（偏りと一致限界）＋ ICC(2,1) の絶対一致**。
- ★ 速さ・シナリオの混合を変えた 2〜3 の「合成テキスト母集団」で、**集計量の偏りが混合比で動くか**を見る。

### 3.3 推定の作法

- ★ **仮説検定ではなく推定**で書く（BRM の統計ガイドライン逐語 "In many scientific investigations the goal of an experiment is to measure the magnitude of an effect with some degree of precision"）。
- ★ 区間: 比率 = Wilson、連続量 = **ブロック単位のクラスタ・ブートストラップ**（同じブロックの試行は IME の状態を共有するので独立でない）。seed 固定。
- ★ **事前に決める除外規則**: 時計の跳び・IME の異常終了・ホストのクラッシュ。★ 除外件数は全部報告する。★ 逸脱は `deviations.md` に記録する。

## 4. E2 —— 本文をどこまで漏らすか（L3）

### 4.1 攻撃者の知識を段で定義する

| 段 | 攻撃者が持つもの |
|---|---|
| K0 | 公開・提出される形のログだけ（`KeyCategory` と時刻、ImeShadow 行） |
| K1 | K0 ＋ 文のジャンル（どのコーパスから来たか） |
| K2 | K0 ＋ **候補文の集合**（閉集合） |

### 4.2 攻撃

- ★ **閉集合の同定（K2）は「シミュレーション攻撃」**で行う: 攻撃者は各候補文を**同じシナリオ生成器に通して予想ログを作り**、観測ログと最も近い候補を選ぶ。⚠️ これが現実的な最強の閉集合攻撃である（ローマ字の長さ・Space・句読点・Enter の位置が決定的に出るため）。K = 10 / 100 / 1000、指標 = 正解率と偶然（1/K）。
- **開集合の復元（K0/K1）**: 言語モデルでカテゴリ列と時刻から本文を推定し、文字誤り率を、ログを見ない事前分布だけのベースラインと比べる。
- ★ **特徴の除去実験**（★ v2 の追加）: 時刻を消す / `Alphabetic` の連続長を消す（窓ごとの件数だけにする）/ 1 秒ビンに粗くする —— のそれぞれで同定率がどれだけ下がるかを測る。→ ★ **「どこまで粗くすれば漏れが減るか」という公開粒度の推奨**を論文に書ける。
- ⚠️ 結果が「同定はかなりできる」でも**そのまま報告する**。★ 攻撃の強さの上限は主張しない（「この攻撃では」と限定する）。

## 5. E3 —— 実行コスト

- ★ **公開する観測部だけ**を単体の常駐プロセスとして両 OS で測る（読者が使うのはそれなので）。
- ★ **作業中 / 無操作の 2 条件**（レート系は活動量で動く）。計器は `experiments/20260903-o1-runtime-cost/` の校正済み版を流用する。
- ★ GSE アプリ全体の既存値は参考として版つきで併記する。⚠️ バッテリーは測らない（限界に書く）。

## 6. 公開する評価一式

- ★ 置き場所: **DOI の付く信頼できるリポジトリ**（Zenodo / OSF）＋ 開発用の公開 repo。
- ★ **観測部のコアは GSE の該当ファイルの「逐語コピー」にし、コピー元の GSE の commit とファイルの SHA-256 を manifest に記録する**。★ 公開 repo の CI が manifest と照合する。
  → ⚠️ GSE 本体の構造（workspace）は変えない（GSE 本体の OSS 公開は未踏採択後）。★ しかし「論文のツール ≠ GSE のツール」という乖離は manifest で検出できる。
- 含める: 観測部（コア ＋ OS ごとの薄いドライバ ＋ 単体ロガー）・両 OS のホストアプリ・シナリオ実行器・Phase 0 の生ログ・本計測の生ログ（content-free）・解析スクリプト・seed / lockfile。
- 含めない: GSE 本体（推定・介入・提出系）・Phase1 / G1 / O1 のデータ。
- ⚠️ ライセンスは研究者判断（★ 少なくとも**非商用の自由利用を許す**もの）。

## 10. テスト戦略（評価系そのものの検査）

1. ★ **パラメータ回復テスト**（★ v2 の追加・最重要）: 正解ログから**既知の誤りを注入した偽の観測ログ**（取り逃し 5% / 分割 3% / 併合 3% / 時間の偏り +20 ms・ばらつき σ = 50 ms）を作り、解析が注入した値を**区間内で回復する**ことを確かめる。⚠️ 「実データで緑」では、解析が誤りを見逃す形で壊れていても気づけない。
2. 照合器の単体テスト（完全一致 / 取り逃し / 偽検出 / 分割 / 併合の 5 型）。
3. ★ 陰性対照: 観測ログを時間方向にずらす・シャッフルすると、一致が**偶然水準まで落ちる**こと。
4. 解析を seed 固定で 2 回走らせてバイト一致。
