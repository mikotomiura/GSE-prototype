# Issue 010: 正解の組み立て —— 呼び出し列から変換セッションを作る（3 つの定義・規則は設定から・oracle との照合・除外）
verify_level: recheck
runs_on: any

## Goal

参照入力欄の `gt/1` と実行器の `oracle/1` から、**正解側の変換セッション**を組み立てる `gt_sessions.py` を作る。
★ 開始・確定・取消・候補窓の**規則は設定（JSON）から読む**（M1 / M5 の較正パイロットで決めて差し替える）。
★ あわせて **oracle ↔ 正解の一致**（IME が意図どおりに動いたか）と、**除外すべき区間**（時計の跳び・ログの途切れ）を出す。

## Background

- design.md §1.2: 単位 = 正解側の 1 変換セッション（開始 = 最初の marked text / STARTCOMPOSITION、終了 = 確定または取消）。⚠️ 母数が OS で違うので正解も 3 通り作る —— `windows_def`（候補窓が出たセッションだけ）/ `macos_def`（かな入力の一区切りすべて）/ `all`（全 composition）。⚠️ macOS では候補窓の表示が取れないので `windows_def` は作れない（design.md §1.1）→ `null` を返す。
- design.md §1.3: `nav` の正解 = **正解側のセッション区間**の中で**実行器が送った矢印キーの数**（oracle の `sent`）。★ 区間を IME 自身から取るので循環しない（判断 10-3）。
- design.md §1.1〔v2〕: oracle ↔ 正解の不一致は「IME が意図どおりに動かなかった試行」。⚠️ 捨てずに件数と型を報告し、観測部の評価には**含める**。
- design.md §1.3: 事前に決める除外規則 = 時計の跳び・IME の異常終了・ホストのクラッシュ。★ 時計の跳びは「隣り合う事象の壁時計の差と単調時計の差のずれ」で検出する（閾値は設定）。
- ⚠️ 2026-09-28 の一次確認: macOS の `unmarkText` は**確定側**、取消の呼び出し列は**文書に無い**。→ 既定の規則は**仮説**であり、M1 で直す。
- ⚠️★★★ 本 issue は**観測側（`obs/1`・ImeShadow）を読まない**（較正パイロットの境界・判断 11）。

## Scope

### In
- `papers/ime-observation/kit/analysis/gt_sessions.py`（新規）
  - `gt_sessions.py --gt <gt> --oracle <oracle> --rules <json> --out <sessions.json>`
  - 規則（`--rules`・`src` ごと）の形（★ キー名はこのとおり）:
    - `start`: セッションを開く事象の条件（例: `{"ev":"set_marked","len_gt":0}` / `{"ev":"start_comp"}` / `{"ev":"tsf_start"}`）
    - `commit`: 確定で閉じる条件の配列（例: `{"ev":"insert_text","len_gt":0}` / `{"ev":"unmark"}` / `{"ev":"end_comp","after_result":true}`）
    - `cancel`: 取消で閉じる条件の配列（例: `{"ev":"set_marked","len_eq":0,"not_followed_by":{"ev":"insert_text","len_gt":0},"within_ms":50}` / `{"ev":"end_comp","after_result":false}`）
    - `candidate`: 候補窓が出たとみなす条件（例: `{"ev":"notify","imn":5}` / `{"ev":"ui_begin","ui_kind":"candidate"}`）。`mac_nstic` は `null`。
    - `clock_jump_ms`: 時計の跳びの閾値。
  - 出力（`sessions.json`）: `{"src":…, "rules_sha256":…, "definitions":{"all":[…],"macos_def":[…],"windows_def":[…]|null}, "oracle_agreement":{…}, "excluded":[…]}`。セッション 1 件 = `{"trial_id", "start_wall_ms", "end_wall_ms", "start_mono_ns", "end_mono_ns", "outcome": "commit"|"cancel"|"open_at_end", "candidate_shown": bool|null, "nav_true": int}`。`trial_id` は oracle の `trial_begin`〜`trial_end` との重なりで決める（重ならなければ `null`）。
  - `oracle_agreement`: 試行ごとに意図（`expect_session` / `abandon` / `commit`）と組み立てたセッションを比べ、一致率と**不一致の型**（「セッションが無い」「取消のはずが確定」「セッションが 2 つ」…）の件数を出す。
  - `excluded`: 時計の跳び・ログが途中で切れた（最後のセッションが閉じていない）区間。
  - `gt_rules.example.json` の既定規則（★ 仮説・M1 / M5 で直す）で動くこと。
  - `--selftest`（目印 `# kit: selftest`）: テストの中で作った事象列（3 つの `src`）で次を確かめる:
    - 基本（開始 → 確定）・取消・候補窓あり / なし・1 試行に 2 セッション・閉じないまま終わる、の 5 型
    - `nav_true` が**区間内の矢印だけ**を数える（区間外の矢印を数えない）
    - `windows_def` が候補窓ありのセッションだけを含み、`mac_nstic` では `null`
    - 時計の跳び（壁時計だけが 5 s 進む）を `excluded` に出す
    - ⚠️ 規則を変えると結果が変わる（規則が本当に読まれている・陰性対照）
    - 同じ入力で出力が**バイト一致**
- `papers/ime-observation/kit/analysis/gt_rules.example.json`（新規）: 3 つの `src` の既定規則（上の例）と `clock_jump_ms: 1000`。
