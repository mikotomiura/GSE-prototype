# 重要な設計判断（auto-context-task-level）

## 判断 1: 置き場（研究者が決定・2026-11-21）

- 決定: タスク名は `auto-context-task-level`。`~/GSE-prototype-auto-context` で、`feature/auto-context-segmentation`（push 済み・PR 未作成）から枝 `feature/auto-context-task-level` を切って重ねる。
- 理由: 2 段目は 1 段目の解析コード（`acs_core.py`・`evaluate.py`・`--features` の `context`）の上に乗る。前の PR のマージを待たずに進められる。
- 却下案: 前の枝を main に入れてから始める（CI を待つ分遅れる）／前の枝にそのまま積む（PR が大きくなる）。
- 注意: PR は前の枝の PR を先にマージし、この枝はその後に main へ向け直す。

## 判断 2: 他の PC（研究者が決定・2026-11-21）

- 決定: 「この Mac で入力が少なく、時々触れるだけ」の様式（前のタスクの task-D にあたる）を 1 つの様式として残し、作業の段で「Mac の外にいる」と読む。他の PC（G-GEAR・職場の PC）の GSE の記録はつながない。
- 理由: 他の PC の記録はこの Mac に 1 本も無い（`~/Documents/GSE-sessions/` は Mac の記録だけ）。つなぐには G-GEAR などで GSE を動かして集め、時刻を合わせる必要があり、別のタスクになる。
- 却下案: 他の PC の記録をつなぐ（記録がたまるまで待つ）／Mac の外の時間をまとめから外す（作業の切り替えの一部を捨てる）。
- 照合の側: 作業の記録（判断 3）に「使った PC」の欄を入れ、Mac の外にいた時間を読み方の確かめに使う。

## 判断 3: 照合の材料（研究者が決定・2026-11-21）

- 決定: 2 つを主にする。
  1. 本人がその場で書く作業の記録（11-22〜11-24 の 3 日）。区間を見せる前に書く。形は「始めた時刻・作業名（自由な一言）・使った PC・後で書いたかの印」。置き場は `experiments/20261121-auto-context-task-level/work/diary.md`（コミットしない）。
  2. git のコミットの repo と時刻。内容は読まず、repo の名前と時刻だけを使う。
- 理由: 宣言はほとんど変わらない（本人の 9 割が `vibe_coding`）。11-19〜11-21 は前回、様式の区間を見せたので、作業の照合には引きずられが入る。その場で書く記録は思い出しのずれが最も小さい。git は本人が書き足さない客観の目安で、他の PC でのコミットも入る。
- 却下案: 出した区間に合う／合わないを付ける（前回の形・見せたものに引きずられる）／まだ見ていない過去の日を思い出す（記憶が薄い）。
- 守ること: 作業の記録を書き終えるまで、11-22 以降の区間を研究者に見せない。書き終えた時刻をこの判断の下に追記する。

## 判断 4: アプリの識別子（研究者が決定・2026-11-21）

- 決定: 今回は取らない。作業の名前の外れ方（様式の割合は同じなのに作業が違う区間の割合など）から、識別子があれば分けられたかを数で見積もり、ここに残す。取るかは結果を見て別のタスクで決める。
- 理由: 取るには計器の変更と data-privacy・ADR-012 D3 の改訂が要る。要るかどうかを先に数で示す。
- 却下案: 取る方向で別タスクを並べて始める。

## 判断 5: 終わりの置き場と /reimagine（研究者が決定・2026-11-21）

- 決定: このタスクは、凍結した基準での判定（本人と O1 の 3 人）と識別子の見積もりまでで終える。論文化の検討は結果を見て別に行う。設計を決めた後、実装の前に /reimagine を 1 回回す。
- 却下案: 論文化の検討まで含める。
