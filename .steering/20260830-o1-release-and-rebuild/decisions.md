# 設計判断と根拠 — O1 リリースと配布物の作り直し

## D-1. `Cargo.lock` の `0.1.29` は **1 箇所しか直さない**

⚠️ 引き継ぎメモは「`src-tauri/Cargo.lock` に **2 箇所**ある（`gse-next` の他にもう 1 つ）」と書き、
「手で 3 ファイルだけ直して lock を放置すると齟齬が出る」と警告していた。

★ 実体を見た結果（一次資料）:

| 行 | パッケージ | 扱い |
|---|---|---|
| `src-tauri/Cargo.lock:1750` | `gse-next` | ✅ 上げる（`cargo check` が自動で追随） |
| `src-tauri/Cargo.lock:3969` | **`schannel`**（第三者クレート・`registry+https://github.com/rust-lang/crates.io-index`） | ❌ **触らない** |

→ ★ 2 箇所目は **偶然バージョン番号が同じだっただけ**の無関係なクレートである。
⚠️ メモの記述をそのまま信じて両方置換していたら `Cargo.lock` を壊していた。

**根拠**: `sed -n '1745,1755p;3964,3974p' src-tauri/Cargo.lock` の実出力。
`cargo check --features package` 完走後の `git diff` が `gse-next` の 1 行だけであることを確認した。

## D-2. `SHARED_SECRET` をローテートした（★ 研究者判断）

**決定**: ローテートする。**理由**（★ コストが実質ゼロである今しか安く直せない）:

- ⚠️ O1 を含むリリースが 1 本も無かった ＝ **有効な secret を持つ配布物が被験者の手元にゼロ**
- ⚠️ 配布フォルダに `o1_submit.json` が `anyone` 公開で生置きされている
- ⚠️ 2026-08-30 に dev が `.steering/` に実 secret の先頭 45 文字を貼った（削除・履歴未混入は確認済み）
- ★ 旧値は手打ちの低エントロピー文字列（60 文字）→ 新値は `openssl rand -base64 32`（44 文字）

**実害の範囲**（★ `GSE_O1_Submit.gs` を読んで確定・推測ではない）:
読み出しは構造的に不可能（`doGet` は `use POST` のみ／`saveWithoutOverwriting_` が上書きを禁止）だが、
⚠️ **書き込みは完全にできる**（`secretMatches_` は共有シークレット一致のみで認可）:
データ捏造（`pubkey.txt` は配布物同梱＝公開情報）と、1 POST 48MB の反復によるクォータ枯渇。

**実施状況**:

| 側 | 誰が | 状態 |
|---|---|---|
| ローカル `Form_O1/o1_submit.json` | Claude | ✅ 差し替え済み（sha256[:12] = `6994e16cdb42`・`.gitignore:100` で追跡外を確認） |
| Apps Script のスクリプトプロパティ | **研究者（手作業）** | ⚠️ **未実施**（Claude からは触れない） |

⚠️ 受信側を変えるまで O1 の送信は全部落ちる。★ 上記のとおり実害は無いが、
**§1-E の実測は受信側の更新が済むまで実施できない**。

### ⚠️★★★ ローテートで**消えない**残余リスク（★ 本セッションで判明・正直に書く）

★ 実測（`make-common-app-zip.sh:475` / `:568`）:

```
cp "$CONFIG" "$M/g1-submit.json"   # ⚠️★ O1 でも名前は g1-submit.json のまま（中身で行き先が決まる）
```

→ ⚠️ **secret は配布 zip の中に焼き込まれる**。★ その zip は `anyone` 公開の Drive フォルダに置く。
→ ★ したがって `SHARED_SECRET` は **「被験者から隠す秘密」ではなく「配布物に同梱される資格情報」**である。

⚠️ **ローテートが直すのは「旧値の無効化」だけ**であって、
「公開リンクを踏んだ誰でも書き込める」という**構造は残る**。
★ 過大評価しないこと —— 直ったのは次の 2 点のみ:

1. Drive に**単体で生置き**された `o1_submit.json`（`anyone / reader` を実測で確認）が無効値になる
2. `.steering/` に貼られた先頭 45 文字が無効値になる

★ 構造的に直すなら「参加者ごとの資格情報」か「書き込みの内容検証」が要るが、
⚠️ **本セッションの範囲外**（★ Phase 検証の途中で受け口の契約を変えるのは高コスト）。

### ★ 派生: Drive 上の単体 `o1_submit.json` は**機能上いらない**

⚠️ 引き継ぎメモは「端末側は `g1-submit.json` を読むので機能上は不要」と書いていた。
★ 一次資料で裏が取れた —— 設定は **zip に焼き込まれて配られる**ので、
被験者が単体ファイルを落とす必要は無い。
→ ★ 置いておく理由が無く、**grep 可能な平文コピーを 1 つ増やしているだけ**である。**削除を推奨する**。

## D-3. ⚠️★★★ 送信 timeout — **測る前に第 3 の上限が見つかった**

### 前提の訂正: 制約は 2 つではなく **3 つ**ある

引き継ぎメモと `.idea/issue.md` は「受け口 `MAX_BYTES` 48MB」と「送信 timeout 180 秒」の
**2 つの矛盾**として問題を立てていた。★ しかし一次資料を当たると **3 つ目がある**:

| # | 制約 | 値 | 出所（★ 一次資料） |
|---|---|---|---|
| 1 | 受け口の本文上限 | 48 MB（base64 64 MB） | `Form_O1/GSE_O1_Submit.gs:151` |
| 2 | 送信側 timeout | **180 秒固定** | `src-tauri/src/reconcile.rs:697` |
| 3 | ⚠️★★★ **Apps Script の実行時間上限** | **6 分 = 360 秒 / 実行** | Google 公式クォータ表（consumer / Workspace とも同値） |

★ **3 は本セッションで初めて確認した**（⚠️ repo 内に記述が無かった。`Form_O1/*.gs` /
`docs/` を grep して 0 件）。

### なぜ 3 が効くのか

`doPost` は本文を受け取ってから **base64 デコード（48MB）＋ `DriveApp` 保存**を行う。
この処理時間は Apps Script の 360 秒に算入される。

→ ⚠️ **クライアント側の timeout をいくら伸ばしても、サーバが 360 秒で殺されるなら届かない。**
★ `MAX_BYTES = 48 MB` は、**転送が間に合っても処理が間に合わない**可能性がある。

⚠️ ただし「転送時間が 360 秒に算入されるか」は**未確認**である
（★ リクエスト本文の受信が script runtime に入るかは公式表からは決まらない）。
→ ★ **これは実測でしか決まらない**（手順 8 の通し確認が、まさにこれを測ることになる）。

### 案の比較（⚠️ 一案に飛びつかない）

| | **案 A: 固定値を大きくする**（例 900 秒） | **案 B: サイズ比例 ＋ 下限/上限** | **案 C: ペイロードを契約に合わせる** |
|---|---|---|---|
| 変更 | `from_secs(180)` → `from_secs(900)` | `Client::builder().timeout()` を外し、`RequestBuilder::timeout()` を **1 リクエストごと**に付ける | `MAX_BYTES` を運べる大きさへ切り下げる／ローテート間隔を日より短くする |
| `MAX_BYTES` 追従 | ❌ 手で追う（★ 上限を変えたら忘れる） | ✅ 自動 | ✅ 定義上一致する |
| 「未知の被験者の回線」への依存 | ⚠️ 残る（★ どんな値でも「全員が収まる」とは言えない） | ⚠️ 減るが消えない（`ASSUMED_BPS` 定数が残る） | ✅ **最も減る**（運ぶ量そのものを小さくする） |
| ⚠️ サーバ 360 秒への対処 | ❌ **できない**（900 秒待ってもサーバが死ぬ） | △ 上限を 360 秒側に置ける | ✅ **本質的に対処**（処理時間そのものが縮む） |
| 実装コスト | 最小 | 小（reqwest 0.13 blocking の `RequestBuilder::timeout` で可能） | ⚠️ 中〜大（ローテート間隔は O1 の「日単位」設計＝ADR に触る） |
| リスク | ⚠️ 被験者の送信が最大 900 秒ブロックされる | 定数の根拠が要る | ⚠️ 分割送信は `saveWithoutOverwriting_` の契約に影響 |

★ **現時点の推奨は B を土台にしつつ、上限を 3（360 秒）から導くこと。**
⚠️ ただし **C を捨てない** —— 3 が効くなら「大きく待つ」ではなく「小さく運ぶ」しか解が無い場面がある。

### ⚠️ 決められないこと（★ 実測が要る）

- 転送時間が Apps Script の 360 秒に算入されるか
- Drive 保存を含む `doPost` の実所要時間（G1 の 207 KB/s は **Drive 保存を含まない**）
- 48MB 上限いっぱいが**そもそもサーバ側で処理し切れるか**

→ ★ 実測は **D-2 の受信側更新が済んでから**。⚠️ それまで `from_secs(180)` は書き換えない
（ゲートは記録票とコードの**両方**を要求するので、数字だけ変えても緑にならない＝正しい設計である）。
