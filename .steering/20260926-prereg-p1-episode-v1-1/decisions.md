## 判断 1: 新版（v1.1）を切る

- **判断日時**: 2026-09-26（研究者裁定）
- **背景**: 凍結文書 §4 #5 の「頻度は下限として読む」は、判断 29／ADR-030 補訂 2 項目 9 が上書きした読み方のまま残っている。§2 の見出し「草案 —— 研究者の承認待ち」も判断 16（承認済み）と食い違う。
- **選択肢**:
  - A: 切る
  - B: 切らない（ADR-030 補訂 2 項目 9 を規範上の置き場とし、凍結文書は 1.0 のまま）
- **採用**: A
- **理由**: B では、P1 の解析者が凍結文書を読むと、上書き済みの読み方を掴む。事前宣言は「P1 で何をどう読むか」の SSOT なので、ADR にしか無い上書きは読者に届かない。実データを見る前なので、今なら forking paths を作らずに閉じられる。
- **トレードオフ**: 版が 1 つ増え、PG-1 の宣言は次の版（v1.2 以降）になる。
- **影響範囲**: `docs/preregistration-p1-episode.md`
- **見直しタイミング**: なし（PG-1 は別の版で扱う）

## 判断 2: 同じファイルの冒頭に宣言ブロックを足し、本文は 1 文字も変えない

- **判断日時**: 2026-09-26（研究者裁定）
- **選択肢**:

  - B: 同じファイルの本文を直し、変更履歴の節を足す
  - C: 別ファイル `…-v1.1.md` を作る
- **採用**: A
- **理由**: `preregistration-v0.3.md` の前例（冒頭の日付付き「バージョンカット宣言／追記」）と同じ作法になる。§0 の凍結規約と引き継ぎの禁止事項（本文を書き換えない）を守れる。`check_prereg_parity.py` は §1・§2.1 の表だけを読むので、検査も JSON の `document` も参照先も変えずに済む。

## 判断 3: 凍結 JSON は `version: 1.0.0` のまま据え置く

- **判断日時**: 2026-09-26（研究者裁定）
- **選択肢**:
  - A: 据え置く（sha もゴールデンも不変・コードの変更なし）
  - B: `1.1.0` に上げる（`replay.rs:4869` の `assert_eq!(dto["prereg_version"], "1.0.0")` を直すことになる＝コードの変更）
- **採用**: A
- **理由**: v1.1 はどの値も変えない。JSON の `version` は**値の版**であり、封筒の `prereg_version` / `prereg_sha256_prefix` は JSON のバイト列から来る（`replay.rs:680` 付近の `sha256_prefix_of_bytes(FROZEN_P1_EPISODE_JSON.as_bytes())`）。値が同じなのに版を上げると、同じ値で出した出力が別の版を名乗ることになる。
- **トレードオフ**: 文書の版（v1.1）と JSON の版（1.0.0）の番号がずれる。→ ブロックで「JSON の版は値の版。v1.1 は値を変えないので 1.0.0 のまま」と明記する。
- **見直しタイミング**: 値を変える版を切るとき（その版で JSON の版を上げる）

## 判断 4: 入れるものは候補 1+2・3・4・6。候補 5（P1-A）は入れない

- **判断日時**: 2026-09-26（研究者裁定）
- **採用**:
  - 1+2: 「併せて出力に載せるもの」に `ime_overlap` を足す。§4 #5 の「下限として読む」を「両方向の誤差がある観測値。Windows に限り下限として読める」へ上書きする（判断 29・補訂 2 項目 9）
  - 3: §3 に「両極の上下界は、極の順序を前提にせず両極の G2 の min / max で取る。`pole_applicable=false` の極は入れない」を足す（補訂 2 項目 4・5／判断 25・28）
  - 4: §2 の見出しの「草案 —— 研究者の承認待ち」を、判断 16（2026-09-21 に 4 件とも承認）で上書きする
  - 6: 探索の各実行では `q` と `warmup_count = ⌈1/(1−q)⌉` を対で指定する（CLI は連動しない。補訂 2 項目 2）。CLI に連動を持たせるかは決めない（P1-F）
- **却下**: 5（P1-A）—— 凍結既定で restart の非退化検査が走らないのは fixture／テストの被覆の問題であり、事前宣言が決める解析パラメータでも読み方でもない。
- **理由**: どれも一次で既に決まっている規則や事実を、P1 の解析者が読む文書へ届けるものであり、新しい値や新しい裁定は足さない（6 は補訂 2 項目 2 が既に「探索の実行者が両方を指定する」と書いている）。

## 判断 6: `/cross-review` 1 巡目の是正（2026-09-26・v1.1 の merge 前なので、同じ版の中で直す。前例: 前タスク判断 20）

- **両系統とも指摘した点（HIGH 扱い）**: (3) の min / max に**どの極の組**を入れるのか、非適用の極を除いた後に何が残るのかが書かれていなかった（Codex P2-1・P2-2／code-reviewer M1・M2）。
  - **是正**: 上下界は**軸ごと**に取る（ポインタ軸 = baseline／pointer_b、修飾キー軸 = baseline／modifier_m_plus）。軸をまたいで 3 実行の min / max を取らない。
    ポインタ軸で極 B が非適用なら**算出不可**と報告し、幅 0 と報告しない。修飾キー軸で極 M+ が `not_applicable` なら「計算した」と書かず（禁止 16）、幅への寄与はゼロ（補訂 2 項目 5）。§4 #4 はこの意味で読むと追補した。
  - ★ 新しい裁定ではない: 軸ごとの 2 極は補訂 2 項目 4・5 の書き方そのもの（どちらも「両極」＝ 軸の中の 2 極）。算出不可は項目 4「値で埋めない」の帰結。2 軸の扱いの違いは判断 26（極 B の 0 行は判定不能）と項目 5（M+ の 0 行は恒等が構造で保証される）の違いから一意に決まる。
  - ⚠️ Codex P2-2 の「baseline と同値を足しても幅は縮まない」は、3 極をまとめて min / max を取る読みを前提にしている。軸ごとの 2 極（baseline と恒等な極 B）なら幅はちょうど 0 になるので、ADR の理由は成り立つ。ただし誤読を招く書き方ではあったので、理由を「測っていない幅が 0 として報告される」へ言い直した。
- **code-reviewer のみ**:
  - L3 採用: 禁止 15 は極 B／極 A だけを扱い、M+ の上位集合の根拠は項目 5・判断 28 である。出典を分け、禁止 15 は逐語（「極 A の部分集合」）に直した。
  - L4 採用: §2 直下の囲み「裁定セッションの草案である（判断 15）」も (4) の上書き対象に含めた。
  - L5 採用: 冒頭の引用ブロックが 2 つに割れていたので、挿入した空行 2 本を `>` にしてつないだ（追加行だけの変更で、本文の削除は 0 のまま）。
  - L6 採用: (5) に除外の判定式（封筒 `config` の `warmup_count` と `⌈1/(1−config.q)⌉` の一致）を足した。
- **Codex のみ**:
  - P2-3（検証が改訂の中心を検証していない）: **一部採用**。parity 検査は値の一致しか見ないのはそのとおりである。ただし v1.1 の規則は将来の解析（タスク D）が従う読み方であり、いま検査できる実装は無い。→ design.md に「D の解析実装で検査するもの」として引き継いだ。
