# 設計 — O1 の配備インフラ ＋ 打鍵の実機確認

## アプローチ

本タスクは **計器を作らない**。作るのは「被験者を 1 人走らせられる状態」にするための
**外界の受け皿**と、その受け皿が壊れていないことを示す**検査**である。

3 本立て:

- **A / B**（実機確認）— ★ 研究者の手が要る。dev は起動・観測・検算に徹する。
- **C**（配備インフラ）— ★ repo 側に置けるものは置き、⚠️ **外界の操作（Apps Script への
  貼り付け・デプロイ・Drive フォルダ作成・フォーム作成）は研究者が手で行う。**
  Apps Script の関数セレクタは自動操作を受け付けないことが実測済みである。

## ★ 本タスクを貫く方針

1. ⚠️★★★ **`docs` / `README` / 引き継ぎメモを一次資料にしない。**
   ★ 外界の状態は `.steering/` の実測記録か実物で確かめる（`verify-before-claiming` ルール 1）。
   → ★ 実際、引き継ぎ §5 の 3 件が古かった（`decisions.md` の検算表）。
2. ⚠️ **緑を根拠にしない。** ★ 検査を書いたら**壊して赤になることを測る**（ルール 5b）。
3. ⚠️ **未確認は未確認と書く。** ★ 「たぶん動く」を「動く」と書かない。

## テスト戦略

| 何を | どう測るか |
|---|---|
| 受け口のガード | `node Form_O1/o1_submit_guard_test.cjs`（★ 実 Drive にも実エンドポイントにも触らない） |
| ⚠️ ガードが空回りしていないか | ★ **変異テスト**（ガードを 1 つずつ壊して赤になるか）を毎回回す |
| ⚠️ 検査自体が空回りしていないか | ★ ケース数の下限（30）／`run.sh` の `guard_count()` が件数を読めること |
| 名前規約の 2 か所整合 | ★ Rust `submission::o1_age_file_name` から導いた名前を**陽性対照**に並べる（実走で生成された stem を含む） |
| サイズ上限 | ★ **実測**（実走 NDJSON → `gse-package` → `.age` のバイト数）から下限を置く |
| 実機の挙動 | ★ 研究者の操作 → NDJSON と `gse-app.log` を dev が検算 |

⚠️ **`cargo` は `src-tauri/` から叩く**（repo 直下に `Cargo.toml` は無い）。
本タスクは `src-tauri/` を変更しないが、`gse-package` のビルドには
`--manifest-path src-tauri/Cargo.toml --features package` が要る。
