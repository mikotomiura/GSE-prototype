## 判断 3: ★★★ E1 連結の具体設計は、実装フェーズで行う（2026-09-19・研究者の指示）

- **研究者の指示（逐語）**: 「**E1の箇所は具体的に設計議論などが実行後での実装フェーズにて実装する形にしましょう**」

  2. `T1c`: `category_bigram_repeat_rate` の式（1 − 種類数 ÷ 総数 か、2 回以上現れる種類の出現の割合か）

  4. `T1d`: E1 の実装順
- ★ **扱い**:
  - ★ E1（4）は研究者の指示どおり、**実装フェーズの設計議論で決める**。
  - ★ `T1c` の 3 点（1〜3）は、**E1 と同じく実装の設計に属すると判断し、同じ扱いにした**（⚠️ レビュー担当の判断。研究者の指示が直接名指ししたのは E1 だけである）。
  - ★ 転記の途中で、`T1c` の未決がもう 1 点見つかった: **走りの最小の長さ**（1 から数えるか 2 から数えるか）。これも同じ扱いにした（issue 004 の U4）。
  - ★ 未決として issue 004 / 006 に転記した。推奨は「推奨（未裁定）」と書き分け、推測で確定させていない。
- ⚠️★★★ **実装フェーズへ渡す論点**（★ 本レビューで見つけ、まだ誰も裁定していない）:
  - **E1 × recovery 未実装**: E1 の規則は「エピソードは転帰か打ち切りでだけ閉じる」である。ところが `recovery`（ADR-029 D2 の `progress_proxy`）は `feat_offline` に未実装であり（2026-09-19 に grep で確認: `src-tauri/src` の該当は注記のみ）、いま閉じられるのは `externalized`（paste）・観測区間の切れ目・打ち切りだけである。
    → ⚠️ **このまま E1 を検出列（`stall_onset`）に入れると、同じ観測区間では最初の onset しか立たない。**
    → レビュー担当の推奨案（未裁定）: 検出列は変えない（断片の検出）。E1 はエピソードへ束ねる別の層として、`recovery` と同時に入れる（ADR-030 Consequences 7z2・[V146] の「検出と束ねを分ける」）。
  - ★ **束ね方に依存しない量**: `restop_ms` / `stable_generation_ms` / 純産出の打鍵数は、E1 でも E2 でも同じ値になる。`r_1` と `s'_1` は同じ観測区間の中の条件 A の辺で決まり、エピソードの窓に依存しないためである。
    → 窓に依存するのは `post_t0_*` と再開の回数だけである。
  - ⚠️ **条件 A の評価は `stall_onset.rs` の非公開関数にある**（`detect_stall_onsets_for_interval`・`net_at_fast`）。issue 006 の Allowed Files（`mod.rs` / `restart.rs`）のままだと、`r` / `s'` を出すには条件 A を再実装するしかなく、定義が二重になる（Codex TASK-PRE 指摘 5 と同型）。
    → 実装フェーズで `stall_onset.rs` から辺の列を `pub(crate)` で出すかを決める（★ Allowed Files の改訂）。
  - ⚠️ **006 の fixture**: `deep_silence.ndjson` は issue 008 以後 onset が立たない（起票 17）→ `stall_onset_observed.ndjson` へ差し替える。
