## 判断 F-1: B-1 = プローブの kill switch は **env 1 本・スレッドを起こさない**

- **判断日**: 2026-08-03（案 C 自体は 2026-08-03 の研究者判断で確定済み。本ラウンドは**実装方法**の判断）
- **背景**: `§2.6` は第 1 版から「アプリ内プローブを使わない」と凍結しているのに、アプリが出す。
  `D-1` で毎ブロック再起動するため**毎ブロック抽選し直す**（5 分あたり 57% / 28%）。
  `§3.6` がブロックの事後除外を禁じているので、**止められるのは実施前だけ**。
- **選択肢**:
  - A: `ProbeScheduler::poll` の戻り値を握り潰す
  - B: ★ **スレッドを起こさない**（env フラグ）
  - C: 起動モードを 3 つ目として追加する（`App.tsx` の週セレクタを拡張）
- **採用**: ★ **B**
- **理由**:
  1. ★ **「発火はしたが黙殺した」状態を残さない。** A だと scheduler は動き続け、
     どこまで進んだのかが曖昧になる。B なら `probe_assignment` も `probe_triggered` も
     **構造的に発生しえない**。
  2. ★ **C は凍結対象に触れる。** 週セレクタは `condition` / `label_pool` / `calibrationMode` /
     `interventionEnabled` を一括決定する単一情報源であり、G1 のために選択肢を足すと
     **Phase1 の較正プロトコルの意味論に手を入れる**ことになる。
  3. ★ **ビルドを分けない。** 被験者配布バイナリが 2 系統になると
     `build-ci-and-pilot-distribution` の運用（CI の本番バイナリを配る）と衝突する。
  4. **既定で無変更**。未設定なら従来どおり起動するので、通常運用のリグレッションが原理的に無い。
- **実装上の担保**:
  - 真値は **`"1"` のみ**（`GSE_DEBUG` と同じ規約）。曖昧な真値解釈を持ち込まない。
  - 純ロジック `probes_disabled_by_env` を `analysis/probe_scheduler.rs` に置き、
    **env 読み取りは `lib.rs`** に置く（`architecture-rules`: `analysis/` は OS/環境に触れない）。
  - ★ **「未設定で無効化しない」を回帰テストに固定した**（`""` / `"0"` / `"true"` / `" 1"` すべて false）。
    ここが緩むと Phase1 / Phase2 のプローブが**黙って全滅する**。
- **トレードオフ**: ★ **毎ブロック env を立てる必要がある**（10 回起動するため）。
  → `protocol.md §1.1` で「ショートカット／launcher に固定する。毎回手で打たない」と明記した。
  ⚠️ **立て忘れはユニットテストでは覆えない**ので、実施後の NDJSON 検査で捕まえる（F-3）。
- **影響範囲**: `preregistration.md` 第 5 版 `§5.4` ／ `config.json` `execution_environment` ／
  `probe_scheduler.rs` ／ `lib.rs` ／ `run.sh [5]` ／ `protocol.md`。

  - ⚠️ ★ **文字数の常時表示はそれ自体が計器である**（産出量を意識させうる）。
    ただし **HI / LO / copy で同一**なので条件差を作らない。`§2.11` に既知の限界として宣言した。
- **影響範囲**: `preregistration.md` 第 5 版 `§2.11` ／ `writing-pad.html` ／

## 判断 F-3: 転記工程に **検証を入れる**（`validate_blocks.py`）。ただし**判定には触れない**

- **判断日**: 2026-08-03
- **背景**: `protocol.md §1` は `D-1` を選んだ決め手を **失敗の可視性**に置いていた
  （「(b) の失敗は沈黙して間違った結果を出すが、(a) の失敗は必ず露見する」）。
  ★ **その思想が転記工程に及んでいなかった**。課題文には `validate_materials.py` があるのに、
  割付ファイルには検証が 1 つも無かった。
- **採用**: ★ **検出専用のスクリプトを新設する**（除外・判定・しきい値を一切持たせない）
- **理由**:
  1. ★ **操作チェックは `§5.3` のとおり「どの分母でも 1 問しか外せない」。**
     すなわち **転記ミス 1 件で合否が反転しうる**。ここは沈黙してはいけない。
  2. ★ **割付は `assign.py` から再生成して突き合わせられる**（決定的なので）。
     `protocol.md §2.3-1` の「転記は 1 方向だけ」を壊さずに検証できる。
  3. ★ **`probe_assignment` 行 0 の検査で、F-1 の立て忘れが客観的に捕まる。**
     `/goal` の自己申告ではなく exit code で決まる（`loop-watchdog` と同じ思想）。
- **★ 意図的に持たせなかったもの**:
  - 除外・被験者の落とし方（`§3.6` / `§2.9` は `analyze.py` の責務）
  - `produced_chars` の合否（**WARN のみ**。桁違いは転記ミスを疑うが、除外はしない）
  - ★ **条件ラベル（HI / LO）の表示**。P-1 は研究者本人が被験者なので、
    検査のたびに条件が見えると盲検が更に崩れる。不一致は「ブロック 5 が割付と違う」とだけ言う
  - ★ **NDJSON ファイル名の出力**（セッション日時が入る）
- **影響範囲**: `validate_blocks.py` ／ `forms_to_blocks.py` ／ `run.sh [4] [6]` ／
  `blocks/README.md` ／ `protocol.md` ／ `data.md`。

## 判断 F-4: `run.sh [5]` は**赤にせず、検査の意図を置き換える**

- **判断日**: 2026-08-03
- **背景**: 引き継ぎは「`src-tauri/` に触るので `run.sh [5]` が赤になる。赤になる理由を文書化せよ」
  と書いていた。★ **調べると、そもそも [5] は主張どおりの検査をしていなかった。**
  `git status --porcelain -- src-tauri src` は**未コミット変更しか見ない**ので、
  **kill switch をコミットした瞬間に黙って緑に戻る**。
- **採用**: ★ **検査の意図を置き換える**（恒久的に赤いチェックを残さない）
  - **旧**: 「G1 はコード変更ゼロで実施できる」→ `src-tauri/` `src/` に変更が無いこと
  - **新**: 「★ **G1 が要求する kill switch が入っている** ＋ それ以外の未コミット変更が無い」
- **理由**:
  1. ★ **恒久的に赤い検査は、赤を無視する習慣を作る。** 「この赤は既知」が積み上がると、
     本当の赤を見落とす。
  2. ★ **新しい検査のほうが強い。** kill switch が失われたら赤になる。
     旧検査は**コミット後に何も検査していなかった**（silent pass）。
  3. 「無関係な未コミット変更で実験を回さない」という有用な性質は**そのまま残している**。
- **⚠️ 記録**: これは `silent-failure-in-guard-scripts` と同型の事故である
  （ゲートが `exit 0` で素通りする）。**検査の主張と検査の実体が食い違っていた。**
- **影響範囲**: `run.sh [5]` ／ `preregistration.md` 第 5 版 `§5-3` の訂正 ／ `env.md`。

## 判断 F-8: **P-ID を Phase1 と共有する**（同じ人＝同じ ID）

- **判断日**: 2026-08-03（研究者判断: 「Phase1 の時の人と ID は連携させる」）
- **採用**: ★ **同じ人には同じ P-ID を使い、採番元を Phase1 のロスター 1 つに固定する**
- **理由**:
  1. **1 人の人間に 2 つの識別子を作らない。** 同一人物のデータが別 ID に分かれると、
     後から突き合わせるための**もう 1 つの対応表**が要る（そこが漏洩点になる）。
  2. ★ **採番を 2 か所でやると必ず衝突する**（別シートを走査しても相手の最大値が見えない）。
     → **G1 側では採番しない**という形でしか一意性を保証できない。
  3. Phase1 参加者は自分の P-ID を知っているので、**G1-C に P-ID 欄を置ける**
     （必須にはしない — 初参加の人は持っていない）。
- **⚠️★ トレードオフ（重要・これが本判断の代償）**:
  G1 は第 1 週（blind 較正）モードで回すので `condition=blind_calibration` /
  `label_pool=calibration_blind` が刻まれ、**Phase1 の較正セッションとラベルが同じ**である（B-4）。
  ★ **これまでは「G1 は P015 以降」という ID 範囲が唯一の切り分けだった。ID を共有するとそれを失う。**
  → 残る分離手段は **2 つだけ**:
  1. `blocks/P0xx.json` の `file` 列（G1 側の解析はここを唯一の入口にするので**逆流は起きない**）
  2. ★ **送付時に G1 であることを明示する** ← **弱い側**。Phase1 側の集計が `label_pool` だけで
     拾うと G1 を巻き込む。**当日終了後の送付を省略・後回しにしない**
  - 最後の保険として **G1 実施日**を管理シートに残す（⚠️ 日付は成果物には出さない・`protocol.md §7`）。
- **★ 事前登録の変更は不要**（実施・データ管理の問題であって判定基準の問題ではない）。
  `§3.1` は**被験者を跨いで学習しない**ので、Phase1 参加者の再参加は解析設計に影響しない。
- **影響範囲**: `Form_G1/GSE_G1_Form_Builder.gs`（採番しない・ロスターを作らない・G1-C に P-ID 欄）／
  `Form_G1/README.md` ／ `protocol.md §2.0` と当日チェックリスト ／ `data.md` の B-4。
