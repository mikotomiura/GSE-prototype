# 結果

## 条件
- 開発版（debug）・`probe/run-dev-o1.sh`（`GSE_O1_MODE=1`・識別子 `com.johnd.gse-next-trim-polling`・HOME と GSE_DATASET は一時フォルダ）。通常運用の確かめは `probe/run-dev-normal.sh`（同じで `GSE_O1_MODE` なし）。
- Mac は電池（49%・放電中）・低電力モードは CPU の内訳のタスクと同じ設定のまま。入力監視の許可が無く、打鍵のフックは動いていない（トレイは HookDown）。
- CPU は `probe/cpu-window.sh`（ps の累積 CPU 時間の 60 秒の差・1 コア = 100%）で、本体と WebKit の子 4 つ（`probe/procs.py`・期待数 4 で確かめた）の合計。
- 呼び出しの回数は一時的な計装 IPC-DIAG（30 秒ごとに `get_cognitive_state` の回数と、`get_intervention_decision` の回数を主窓・overlay に分けて出す）。計装はコミットの前に外した。
- 最小化は `probe/axclick.swift` の minimize（題名 gse-next の主窓だけ）。

## 1. 直す前の呼び出しの回数（30 秒あたり）
- 主窓が見える: `get_cognitive_state` 59・主窓の判定 59（500ms ごと）・overlay の判定 0〜8。overlay は画面外にあり、WebKit がタイマーを間引いている（最初の 30 秒の 8 回の後は 0 回）。
- 主窓を最小化: 主窓は 30 回（1 秒に 1 回）に落ちた。WebKit が隠れた窓のタイマーを間引く。

## 2. CPU（O1 の形・記録中・60 秒 × 2・合計 %）

| 状態 | 直す前 | 取得を全部止めた版（上限の確かめ） | 直した版 |
|---|---|---|---|
| 主窓が見える | 2.66 / 2.38 | 2.01 / 1.99 | 1.96 / 2.41 |
| 主窓を最小化 | 2.27 / 2.59 | | 2.00 / 1.55 |

- 取得を全部止めた版（統合ポーリングの effect を早期 return にした一時的な差し替え・計装の行が 1 つも出ないことで 0 回を確かめた）: 下がるのは約 0.5 ポイント。これが取得を削る効きの上限。CPU の内訳のタスクで「記録中の増分の大部分」と見立てたのは誤りだった（あちらは相関で、因果は確かめていなかった）。
- 取得が 0 でも、本体 0.85〜0.90%・WebContent 0.72〜0.80%・GPU 0.25〜0.40% が残る。
- 直した版の O1: 主窓の `get_cognitive_state` と判定の呼び出しは 0 回（計装の行で確かめた）。見える間は無打鍵の時間だけを取る（計装の対象外）。最小化の間の本体は 0.45 / 0.48%（直す前は 0.78 / 1.03%）。合計の差は 60 秒の窓の揺れ（同じ状態の 2 回で最大 0.9 ポイント）と同じ程度で、効きは小さい。
- 1 回目の直す前・見える状態の測りは、zsh が番号の並びを 1 つの引数で渡して失敗した（測り直した）。最初の上限の確かめは、Vite の差し替え（HMR）が窓に効かず呼び出しが続いていたので捨て、起動し直して測った。

## 3. 通常運用での確かめ（非 O1・第 1 週の既定で「開始する」）

| 最小化 | 20（切り替えの途中）/ 0 | 42（途中）/ 30 | 0 / 0 |

- 最小化で WKWebView の `visibilityState` は hidden になり、表示用の取得は止まった。判定の呼び出しは続いた（介入の判定の時計は止まらない）。
- 既存の振る舞いとして分かったこと: 最小化の間、主窓の判定は 1 秒に 1 回（30 秒で 30 回）に落ちる。直す前の版でも同じ（1 を参照）で、今回の変更によるものではない。介入の判定の時計が窓の見え方で速さを変えることになる。別タスクの候補（判定の時計を Rust へ移す案と関わる）。

## 4. 片付け
- 開発版は 4 回起動した（直す前・上限の確かめ・直した版の O1・直した版の通常運用）。毎回、自分が起動したプロセス（本体・tauri・npm・vite・esbuild・起動のスクリプト）だけを止め、一時フォルダを消した。ポート 1420 は空いている。O1 の収集アプリ（pid 99037）は動いたまま。

## 5. 取得が 0 でも残る約 2% の出どころ（判断 2・コードは直さない）

### sample（直した版・O1 の形・主窓が見える・10 秒）
- WebContent 2 つは 10 秒のほとんどを待ちで過ごし、待ち以外の頂上はどれも 5 回未満に散らばっていた（特定の重い処理は無い）。
- 本体では、JavaScriptCore の掃除（121 回）と、IME の見張りのスレッドの atomic の読み（15 回）が待ち以外で目立つ程度。10 秒の間に短命の CVDisplayLink のスレッドが 11 本生まれていた。画面の描き替えが断続的に起きている印。

### タイマーを止めて測る（`probe/timer-rounds.sh`）
- 一時的な差し替え（コミットしていない）: `src/main.tsx` の import の直後に次を入れ、環境変数 `VITE_PROBE_BLOCK_DELAYS`（`all` か、間隔の並び `1000` など）で指定した間隔の `setInterval` を無効にした。測り終えて外した。
  ```ts
  const probeBlock = import.meta.env.VITE_PROBE_BLOCK_DELAYS as string | undefined;
  if (probeBlock) {
    const blocked = probeBlock === "all" ? null : new Set(probeBlock.split(",").map(Number));
    const orig = window.setInterval.bind(window);
    window.setInterval = ((h: TimerHandler, ms?: number, ...rest: unknown[]) =>
      blocked === null || blocked.has(ms ?? 0) ? 0 : orig(h, ms, ...rest)) as typeof window.setInterval;
  }
  ```
- 差し替えが効いたことは、ダッシュボードの経過秒（SESSION）を AX で読んで確かめた（1 秒ごとを止めた回は 0:00 のまま、止めない回は進む）。
- 直した版・O1 の形・主窓が見える・記録中・60 秒 × 2・合計 %（本体と WebKit の子 4 つ）:

| 止めた間隔 | 合計 | 本体 | WebContent（主窓） |
|---|---|---|---|
| なし | 2.05 / 2.66 | 0.88 / 1.13 | 0.90 / 1.05 |
| 2 秒と 3 秒 | 1.94 / 2.03 | | |
| 1 秒（1 回目） | 1.76 / 0.90 | 0.90 / 0.50 | 0.75 / 0.38 |
| 1 秒（2 回目） | 1.67 / 0.91 | | |
| 500ms と 1 秒 | 0.82 / 0.98 | | |
| 全部 | 0.58 / 0.59 | 0.52 / 0.52 | 0.02 / 0.02 |

- 読めること:
  - 画面のタイマーを全部止めると、WebKit の子はほぼ 0 になり、合計は約 2.3% から 0.6% に下がる。取得が 0 でも残っていた約 2% は、ほぼすべて画面のタイマーによる再描画。
  - 主な使い手は 1 秒ごとのタイマー（止めると 2 回目の窓で約 0.9%）。2 秒（記録の状態の取得）と 3 秒（フックの確かめ・提出の状態）は、止めても揺れの中。
  - 残る 0.5% は本体の Rust のスレッドとトレイなど（CPU の内訳のタスクの表 2 と合う）。
- 1 秒ごとのタイマー（O1 の主窓で動いていたもの）:
  - `Dashboard.tsx:151` の経過秒（SESSION の時計）。毎秒 `setSessionSeconds` で Dashboard 全体が描き直される。
  - `Dashboard.tsx:181` のフックの待ち秒。`hookActive` が false の間だけ動く。今回の開発版は入力監視の許可が無くフックが止まっていたので動いていた。被験者の環境（フックが動く）では止まる。
  - `App.tsx:418` の時計は送信中だけ動き、今回は動いていない。
- 測り方の限界: 今回の測りはすべて、フックが止まった開発版（debug）・電池・低電力モードのもの。被験者の環境で実際に効く 1 秒ごとの再描画は、主に経過秒の時計 1 本と見られる（フックの待ち秒の分だけ、今回の「1 秒」の効きは大きめに出ている）。release のビルド・フックが動く状態では確かめていない。

### 軽くする候補（効きの見込みの大きい順・直すかは研究者が決める）
1. 経過秒の時計を、Dashboard 全体ではなく小さな部品だけが描き直されるようにする（または、O1 では分単位にする）。最大で約 1 ポイント（フックの待ち秒の分を除くともっと小さい）。
2. 500ms の無打鍵の時間の取得（O1 の主窓で残る唯一の取得）を 1 秒にする。小さい。
3. 判定の時計を Rust へ移す（窓の見え方で速さが変わる既存の振る舞いも直る）。効きは小さいが、振る舞いの正しさの面で別タスクの候補。

## 6. 経過秒の時計を小さな部品に切り出す試し（判断 4・捨てた）
- 試した変更: `Dashboard.tsx` の経過秒を `SessionClock` 部品に切り出し、毎秒の描き直しをその部品だけに閉じる（表示は同じ）。code-reviewer・Codex とも HIGH なし。
- 1 回目の比べ（差し替えなし・2 回起動）: 2.13 / 2.89、1.98 / 2.02。直す前（2.05 / 2.66）と変わらない。ただしこの条件では、フックの待ち秒のタイマー（`Dashboard.tsx:181`・フックが止まっている間だけ動く）も 1 秒ごとに Dashboard 全体を描き直すので、効きが隠れる。
- 2 回目の比べ: 待ち秒のタイマーの間隔を一時的に 1001ms に変えて差し替えで止め（被験者の環境と同じく、待ち秒が動かない条件）、切り出す前・後・後・前の順に測った。
  - 切り出す前: 2.27 / 2.39
  - 切り出した後: 2.16 / 2.17、2.27
  - 3 回目の 2 つ目の窓（1.54）と 4 回目（0.18 / 0.17・WebContent 0.00・経過秒が読めない）は、画面が 07:36:16 UTC に消えた後なので捨てた（`pmset -g log` の「Display is turned off」）。
- 読めること: 切り出しの効きは 0.2 ポイント以下で、揺れの中。毎秒の重さは React の描き直しの範囲ではなく、画面の文字が毎秒変わること自体（WebKit の描き替え）から来ていると見られる。1 秒ごとのタイマーを止めると約 1.2 ポイント下がる結果（5）と合う。
- 研究者の選択: 切り出しは捨てる（効きが示せない変更は入れない）。表示を変える案（O1 では経過を分単位にする）は、参加者が見る画面が変わるので、次に画面や配布文書を見直すときの候補にする。
