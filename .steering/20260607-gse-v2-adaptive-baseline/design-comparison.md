# 設計案比較 — adaptive-baseline

## v1 の要旨
β を `CognitiveStateEngine` の内部状態（`Arc<Mutex<BetaState>>`）として抱えさせ、
`update()` 内の副作用で自己学習。ゲート信号はエンジン内部の取り込み前 Stuck 確率
`old_probs[2]`。β 推定は **per-step EWMA**（要件の「窓パーセンタイル」は "F1 が既に
30s 中央値" を理由に簡略化）＋外れ値クランプ。変更はほぼ engine.rs に局所化、churn 小。

## v2 の要旨
β をエンジンから切り離し、**エンジンを `(features, β)→probs` の純関数**化。β の学習は
新規 `ContextBaseline`（`baseline.rs`）が担い、**有界窓 + 低位パーセンタイル/trimmed mean**
で推定（要件に忠実）。受理ゲートはオーケストレーション層（loop_step）で**確定後の報告
p_stuck**＋**N 連続デバウンス**で判定。汚染耐性を窓のパーセンタイル＋デバウンスで二重化。

## 主要な差異

| 観点 | v1 | v2 |
|---|---|---|
| β の所有者 | エンジン内部 (`Arc<Mutex>`) | 外部 `ContextBaseline`、エンジンは純関数 |
| β 推定法 | per-step EWMA + クランプ | 窓パーセンタイル / trimmed mean（要件準拠） |
| ゲート信号 | 取り込み前 `old_probs[2]`（内部信念） | 確定後の報告 p_stuck（最大情報量）＋デバウンス |
| 自己参照 | あり（エンジンが自入力基準を自己書換） | なし（学習と推論を分離） |
| 変更規模 | 小（engine.rs 局所、シグネチャ不変） | 中（新規 file + シグネチャ変更 + loop_step 改修） |
| テスト容易性 | Mutex 状態に依存、やや結合 | 純関数 + 純ロジック window、分離して検証容易 |
| 再現性 | β 固定化に flag 必要 | β=prior 注入で旧 golden と完全一致を保証しやすい |
| 汚染耐性 | ゲート + クランプ（EWMA は全受理値を積分） | ゲート + デバウンス + パーセンタイルが裾を破棄（より強い） |
| 要件忠実度 | 「窓パーセンタイル」を簡略化（逸脱あり） | 明記された推定法をそのまま実装 |
| リスク | 自己参照の収束挙動が読みにくい / churn 小 | シグネチャ変更で呼出側改修必須 / churn 中 |

## 推奨案
**v2（ハイブリッド寄り）** — 理由:

1. **要件忠実**: 要件が名指しした「窓の低位パーセンタイル/trimmed mean」「p_stuck<GATE の
   流暢サンプルのみ」を素直に満たす。v1 はここを per-step EWMA に簡略化し逸脱していた。
2. **再現性規約との相性**: GSE は engine の数値挙動変更を HMM_VERSION + golden で厳格管理する。
   エンジンを純関数化し β を外から注入できる v2 は、β=prior 固定で旧 golden と一致を保証でき、
   回帰検証とロールバックが構造的に容易。
3. **汚染耐性**: 守るべき「生産的苦闘」を基準が飲み込む事故が最大リスク。窓パーセンタイルが
   裾を捨て、デバウンスが苦闘中の凪を弾く v2 は、EWMA + 単発クランプの v1 より防御が厚い。
4. **自己参照の排除**: v1 はエンジンが自分の事前信念で自分の入力基準を書き換える閉ループ。
   学習と推論を分離する v2 の方が挙動が読め、デバッグしやすい。

**v1 から拾う点（ハイブリッド要素）**: warmup を「母集団 prior 流用で起動直後は現状と同一」
とする回帰最小化方針は両案共通で良い。κ=2.0 据え置き＋将来の引数化も踏襲。

**v2 のコスト**: `calculate_latent_axes/update/update_silence` のシグネチャ変更で loop_step の
改修が必要（churn 中）。ただし純関数化の長期的価値（テスト・再現・ロールバック）が上回る。
