# 設計判断記録 — adaptive-baseline

## D-1: β をエンジンの内部状態にせず、エンジンを純関数化する
- **判断**: `CognitiveStateEngine` は β を保持しない。`calculate_latent_axes/update/
  update_silence` が `beta: &BetaSet` を引数で受け取る純関数とする。β の所有・学習は
  新規 `ContextBaseline`（オーケストレーション層 = loop_step の state）が担う。
- **根拠**: (1) GSE は engine の数値挙動変更を `HMM_VERSION` + golden で厳格管理する。
  β を外注入できれば β=prior 固定で旧 golden と一致を保証でき、回帰/ロールバックが容易。
  (2) エンジンが自分の事前信念で自分の入力基準を書き換える自己参照ループを避け、
  挙動を読みやすく・テストしやすくする。
- **棄却案**: v1 の「engine が `Arc<Mutex<BetaState>>` を抱え update() 内副作用で自己学習」。
  churn は小さいが上記 2 点で劣る。

## D-2: 推定は per-step EWMA でなく「有界窓 + パーセンタイル」
- **判断**: context ごとに受理流暢サンプルの有界リングバッファ（W=256）を持ち、
  β = 窓のパーセンタイル。β への追加 EWMA はかけない。
- **根拠**: requirement が明記した推定法。窓のパーセンタイルは裾（外れ値）を構造的に捨て、
  受理した全値を積分する EWMA より汚染に強い。追加 EWMA を避けることで `(1.0−α)` の
  浮動小数再現性フットガン（engine.rs:18-24）も回避。

## D-3: パーセンタイルは特徴量の「向き」で変える（requirement 表現の是正）
- **判断**: friction 方向（高いほど苦闘: F1,F3,F5,F6）は β = 流暢分布の **p60**（上側）。
  engagement 方向（高いほど良い: F4 burst 長）は β = **p35**（下側）。
- **根拠**: requirement は一律「低位パーセンタイル」と書いたが、これは F1 等で誤り。
  φ=(x−β)/(κβ) は x>β で friction が立つ。流暢時 φ≈0 を実現するには friction 指標の
  β は流暢中心〜やや上に置く必要がある（β を低く取ると是正対象の原点バイアスが残る）。
  F4 は逆向き指標で、流暢時に engagement (0.40·φ4) を正に保つため β を下側に置く。
- **未確定**: p60/p35 の具体値は要較正。**codex review の重点叩き対象**（軸セマンティクス整合）。

## D-4: 受理ゲートは「確定後の報告 p_stuck」+ デバウンス、場所は loop_step
- **判断**: 学習サンプルの受理は loop_step で判定。条件 = TypingPath（実打鍵・非silence）
  ∧ reported p_stuck < GATE(0.40) ∧ 直近 N=5 連続流暢。
- **根拠**: エンジン内部の取り込み前信念（old_probs）より、確定後に出力した p_stuck の方が
  情報量が多く意味が明確。デバウンスで苦闘の合間の一瞬の凪を弾き、汚染防御を二重化。
  GATE=0.40 は介入域 NUDGE 0.60 に安全マージンを取った値。

## D-5: warmup は母集団 prior 流用 + 滑らかブレンド
- **判断**: 窓が `W_min=32` 未満は prior（現状の母集団定数）を β とする。充填途中は
  `lerp(prior, learned, n/W_min)` で滑らかに移行。
- **根拠**: 起動直後の挙動を現状と一致させ回帰リスクを最小化。ハード切替の段差を回避。

## D-6: κ=2.0 据え置き、phi は κ 引数化のみ
- **判断**: 比例モデル維持（ユーザー決定）。初版は κ=2.0。`phi` は κ を引数で取れるよう
  シグネチャ変更だけ行い、context 別 κ を将来可能にする。
- **根拠**: 比例モデルなら β を本人値へ動かしても本人比レンジは保たれる。過剰鈍化が
  オフライン検証で出た場合のみ κ を調整。

- バンドモデル = 比例維持 + κ 微調
