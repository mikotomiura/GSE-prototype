## 実装アプローチ

### #1 O1 運用管理シート（提出イベントの追記ログ）

★ 5 本目のスクリプト プロパティ `O1_MGMT_SHEET_ID` を足す。
⚠️ `PHASE1_MGMT_SHEET_ID` を転用しない・改名しない（研究者判断 2026-08-29）。

**タブ**: 「O1 登録ログ」（★ 追記のみ・上書きしない）
**行構成**: 行 1 = 機密バナー / 行 2 = 見出し / 行 3+ = データ（★ ロスターと同じ形）

| 列 | 見出し | 中身 |
|---|---|---|
| A | 記録日時 | ISO 8601（★ スクリプトのタイムゾーン） |
| B | 種別 | `register`（O1-C 提出）※将来 `submit` 等を足せる |
| C | P-ID | ★ 分かっているときだけ。⚠️ 分からなければ空 |
| D | 結果 | `ok` / `blocked` |
| E | 理由 | 理由コード（下記） |
| F | 備考 | ⚠️ **PII を書かない**（行番号 / OS / 件数だけ） |

⚠️★★★ **氏名・メールの列を作らない**（研究者判断 2026-08-29）。
★ マスク済みメールすら置かない —— 削除経路を 2 か所から増やさないため
（`docs/o1-deletion-ledger.md` §5b）。

**理由コード**: `new-pid` / `existing-pid` / `filled-blank-pid` / `no-email` /
`bad-pid-format` / `roster-conflict` / `invalid-pid-in-roster` / `duplicate-email-in-roster` /
`config-error` / `lock-failed` / `dup-pid` / `mail-failed` / `renumbered`

#### ⚠️★★★ fail-open と fail-closed を場所で分ける

| 場面 | 挙動 | 理由 |
|---|---|---|
| **構築時**（`o1ConfigProblems_` / `checkO1FormConfig` / `installO1ConsentTrigger`） | ⚠️ **fail-closed** | ★ 配布**前**に気づかせる。⚠️ 配布後に作ると遡って埋まらない |
| **提出時**（`onO1ConsentSubmit`） | ★ **fail-open** | ⚠️ ログが書けないことで被験者の登録を止めない（★ ログは観測器であってゲートではない） |

#### ⚠️★★★ 2 か所採番を機械で塞ぐ（★ T-23 の一部に効く）

`o1MgmtProblem_(id)` を新設し、次を全部見る:
1. 空 → 問題
2. ⚠️ `rosterSheetId` と**同じ ID** → 問題（★ ログとロスターを同じシートにすると PII が混ざる）
3. ⚠️ `o1IsKnownWrongRoster_(id)` に載っている → 問題
4. ⚠️★★★ **その表に「参加者ロスター」タブがある** → 問題
   （★ 「O1 用のロスターを作った」場合をここで捕まえる。⚠️ 拒否リストでは捕まらない型）

逆向きに `o1OpenRoster_()` でも `rosterSheetId === mgmtSheetId` を拒否する。

### #3 ログ行の上限（★ 既存バグではなく #1 の設計制約）

★ `O1_MGMT_MAX_ROWS = 5000`。⚠️ 超えたら **append をやめて Logger に警告**（fail-open）。
⚠️ **消さない**（append-only の約束を破らない）。
⚠️ G1 の `applyRunValidation_` 型の「行数固定の入力規則」を**このタブに付けない**
（★ 100 行で切れると 101 行目以降が黙って規則なしになる）。

### #4 ロスター内のメール重複

`o1FindInPhase1Roster_` の段 1 を「最初の一致で return」から「**全行を走査して集める**」へ変える。
- 1 件 → 従来どおり
- ⚠️ 2 件以上 → `{conflict: true, reason: "duplicate-email-in-roster", rows: [...]}`
  → ★ 発番も送信もしない（P-ID 重複 `:1614` と**同じ扱い**にする）

⚠️ conflict の文面は理由によって変える（★ 現行は「別のメールが登録されています」固定で、
メール重複には**嘘になる**）。

### #5 プロジェクト跨ぎの二重採番 —— ⚠️ **/reimagine で 2 案を比較してから確定する**

初回案（v1）: **一方的な譲歩（asymmetric yield / self-renumber）**
★ 書いたあとに読み返すのは現行どおりだが、⚠️ **止まる代わりに自分が採番し直す**。
★ 自分の行はメールで特定する（O1 は必ず提出者のメールを持っている）。
⚠️ 受付メールは**採番し直したあと**に送るので、被験者には見えない。
★ G1 を 1 行も触らない（⚠️ G1 実施中に触れないという制約を満たす）。
