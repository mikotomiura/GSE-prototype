## §0 このメモの中心（★ 逐語）

> **GSE は人間の内面を表示する装置ではない。計測された実践の微細な差異を、解読可能な指標ではなく
> 生成する肖像へ変換し、その肖像が必要なときだけ自身の縁を開いて、計測されない身体領域へ
> 作者＝鑑賞者を送り返すメディアアートである。**

骨子 6 命題:
1. 密な作業時系列を数値/状態名でなく**造形素材**として扱う
2. ユーザーをアバターでなく「**変化様式**」の肖像として描く
3. 作品は普段周縁に留まり、必要時は通知でなく**作品自身の形式が開く**
4. 開口はスマホ内の次の課題へ導かず、**画面外の身体**へ向く
5. 身体行為を測定・採点・報酬化せず、**システムが知る権利を手放したまま**再開を待つ
6. 作品鑑賞自体を常時の第二課題にせず、開口の後は媒体が再び注意の外へ退く

```text
密な作業時系列
  -> 機械による限定的な仮説
  -> 非可逆な造形変換
  -> 実践生成肖像
  -> 作品内部の開口
  -> [計測しない身体領域]
  -> 新しい実践としてのみ再接続
```
> 角括弧内は**欠測を埋める対象ではない。作品を成立させる積極的な外部である。**

## §4.1〜4.5 「書き直される境界」の時間的推移

現行の `ground / lattice / sparsity / aperture` 文法を捨てずに「状態記号」から「肖像生成」へ拡張する案。

### §4.1 通常時
- **データがなくても成立する静かな ground** が常にある
- ground の上に**格子または線維状の関係場**がある
- 作業の拍とバーストは**点を増やすのでなく、既存要素どうしの結び方を変える**
- 修正は失敗として**赤くならず**、既存の線を**折り返し、重ね、異なる経路へ書き直す**
- ポーズは穴や死ではなく、**周囲の配置が呼吸できる間**として残る
- ★ **同じ最終 `level` でも、そこへ至った履歴により重層・余白・結合の仕方が異なる**
- 「ユーザーは画面内の物体ではない。**この場が書き直されてきた様式がユーザーの肖像になる**」

### §4.2 摩擦が増えたとき
- ⚠️ **派手さ・赤・警告・嵐を増やさない**（明示的禁止）
- 結合の一部が格子から外れ、**互いの距離が少し不均一になる**
- `stuck` は破壊や罰でなく、**作用できる関係が疎になった構図**として現れる
- ⚠️ **autonomous ground は失われない**（本人の存在・価値が空になる表現を避ける）

### §4.3 invitation が生じたとき
- ⚠️ **別の通知を載せず**、作品の**一辺または輪が一度だけ開く**
- 内側の要素は**スマホ中央へ集まるのでなく、画面外へ続く方向を持つ**
- ⚠️ **開口は点滅・文章・ボタン・カウントダウン・報酬を伴わない**（明示的禁止）
- スマホは「次に操作する対象」でなく、**作業画面と身体空間の間に置かれた閾**になる

### §4.4 開口の後
- ⚠️ **システムは歩いたか、立ったか、休んだかを知らない**（センシングしない）
- 作品は身体行為へ追従せず、**ground の自律運動だけを続ける**
- ⚠️ **無入力の長さに比例した成長・色・空白を作らない**（明示的禁止）
- 復帰しても「成功」として**閉口せず**、新しい作業の作用が**別の方向から加わるだけ**
- その間は「身体回帰の記録」ではなく **「作品が所有しなかった時間」**として扱う

### §4.5 セッションの終わり
- ⚠️ **長期プロフィールを作らない**。セッションの肖像は**消えるか、一枚へ凝縮して閉じる**
- 保存する場合も、**本人向け累計・比較・連続日数へ接続しない**
- 「保存の是非は別途判断する」（**未決**）

## §4.9 推奨する流動エンジン

**第一候補**: **ばね格子 + curl-noise の流れ場 + パリンプセスト状の残像**。
「実際の流体方程式を全面的に解く必要はない」。

| 要素 | 役割 |
|---|---|
| ばね格子 | `lattice / coherence / sparsity / aperture` という**現行文法を保てる** |
| curl-noise | **発散しにくい**滑らかな局所流を安価に作れる |
| 残像テクスチャ（パリンプセスト） | 修正・逡巡・過去の経路を「**消去されない書換え**」として残せる |
| invitation 時 | 一辺の**境界条件を開放**し、一度だけ外向きの流れを作った後に沈静化 |

**却下**:
- 反応拡散シェーダー（「有機的な**静止像**に強い」が用途が合わない）
- GPU 粒子場（「滑らかな運動に強い」が同列比較で除外）
- **Navier–Stokes 型の本格的流体計算** — 「可能だが、**数値発散、端末差、電池、意味制御の難しさ**が増える」。
  ★ 「GSE の作品では『物理的に正しい液体』より、**時間経路を保ったまま意味的に制御できる流動**の方が重要」

## §4.10 「ぬるぬる」と「注意を奪わない」の両立 ★ 実装設計の核

**矛盾に見える理由**: 滑らかで有機的な高フレームレート運動は通常「注意を引く」と結びつけられる。

★ **フレームの滑らかさと運動の強さを分離する**:
> 60 fps で描いても、速度、振幅、コントラスト、全画面移動を小さくすれば、
> 知覚上は滑らかだが低エネルギーな背景にできる。逆に 5 fps でも点滅や大きな状態ジャンプがあれば注意を奪う。

★ **推定周期と描画周期の分離**（逐語）:
```text
GSE の推定・意味更新: 1 Hz または状態変化時だけ
端末へ渡すもの:     新しい目標形態または意味イベント
端末内の描画:         60 fps（可視時のみ）
```

★ **端末内の各形態変数を臨界減衰に近いばねで目標へ寄せる**（逐語）:
```text
velocity += (stiffness * (target - value) - damping * velocity) * dt
value    += velocity * dt
```
- `dt` は**固定刻み（例: 1/60 秒）**で積分し、描画フレームが落ちた場合は **accumulator で追いつく**
- 入力値・速度・反復回数を **clamp** し、**同じ session seed なら同じ意味的構図へ至る**ようにする
- 「これによりネットワークから **60 件/秒を送らなくても**、端末側では連続的に動く」

**注意を捕捉しないための運動規則**（6 項目）:
- 通常時は**低速・小振幅・低い空間周波数**とし、**中心を作らない**
- 状態更新は形を**瞬間移動させず、数秒から数十秒で馴染ませる**
- invitation は常時激しくするのでなく、**局所的な一回の位相変化**にする
- 変化後は**周期的な催促をせず**、開いた構図を**弱く保持**する
- **非表示時は計算を止め**、次の曝露時に**現在形へ再構成**する
- 美しさは維持するが、**収集・完成・希少形・連続記録へ結びつけない**

★ 結論: 「滑らかさを**報酬刺激ではなく**、離散的な推定が人間へ断定として突き刺さらないための
**緩衝材**として位置づけられる。」

## §4.11 計算上・研究上の主な問題（10 項目・全件）

| # | 問題 | なぜ問題か | 解決案 |
|---|---|---|---|
| 1 | **1 Hz と 60 Hz の不一致** | 状態変更のたびに絵が跳ぶ | 目標値だけ更新し、端末内ばね・補間で連続化（§4.10 と同一機構） |
| 2 | **履歴の無限増大** | GPU/メモリ消費、**長期プロフィール化** | 有限の場・有限の残像へ圧縮し、セッション終了時に消す |
| 3 | **数値発散** | 粒子や格子が端末外へ飛ぶ | 固定 timestep、clamp、反復上限、安定な積分法 |
| 4 | **端末差** | 同じデータでも別作品に見える | ★ **pixel parity でなく、結合・疎密・開口の `semantic parity` を試験する**（⚠️ 新概念・未定義の試験手法） |
| 5 | **状態境界の往復** | invitation のような変化が連打される | hysteresis と one-shot impulse を分け、再通知しない |
| 6 | **通信断・再接続** | 古い形へ巻き戻る | `epoch/seq` と現在スナップショットを使い、履歴を再送しない |
| 7 | **個人識別** | 抽象画から**長期的な本人像が固定される** | セッション seed、不可逆圧縮、**安定した人物 ID の不使用** |
| 8 | **推定不確実性** | 精密な絵が精密な真実に見える | （先送り）現状は粗い文法に限定し、将来 `evidence_quality` 導入時に再設計 |
| 9 | **熱・電池** | 背景作品が作業や端末利用を妨げる | 可視時だけ描画、適応 fps、低解像度場、静止 fallback |
| 10 | **馴化・注意捕捉** | 頻繁に確認する**第二の作業**になる | 常態は低エネルギー、開口は一回、⚠️ **視聴時間を成功指標にしない** |

⚠️ 全項目に対応案はあるが、いずれも**未検証の設計方針**で実測・実装の裏付けは無い。

## §4.12 現行チャネルとの境界（メモの自己申告）

現行の表現チャネル契約は `(level, invitation)` の変化時のみ送信し、連続値も 1Hz ストリームも載せない。
★ **この契約のままだと「密な実践データの肖像」ではなく「状態の流動表現」に留まる**、と自己申告。

3 段階に分けている:
- **層 A** = 現行契約のみ（`level`/`invitation` ＋ 端末内 local session seed）
- **層 B / PC リプレイ** = `FeatSnapshot` 短期履歴から完全な Practice Portrait 生成
- **将来拡張** = PC 側で不可逆圧縮した `MorphologyState` の低頻度送信

⚠️★★★ 将来拡張を採る場合は「**wire protocol の実装に紛れ込ませず**、表現上の必要性・
再識別可能性・保持期間・失効を含む**別 ADR と privacy review が必要**」と明記。

## §4.13 スマホ OS 上で可能な範囲

### Android
- **可能**: ライブ壁紙なら描画用 `SurfaceHolder` が与えられ、可視／非表示の通知も受けられるため
  **表示中の連続描画**が実現できる。公式 API も「壁紙は可視時だけ CPU を使うこと」を求めている。
  → 「Android は**低エネルギーな 60 fps 表現の第一実験面**に向く」
- ⚠️ **不可能・未確認**: **ロック画面への適用、AOD 中の可視性、実際の更新頻度は OEM と端末設定の差が残る**。
  `FLAG_LOCK` は存在するが「任意端末で同じ挙動になることを意味しない」。
  AOD で `onVisibilityChanged` がどうなるかは**実機試験を要する**

### iOS
- ⚠️ **不可能**: ロック画面 Widget は「**任意の描画ループを常時所有できない**」。
  Widget extension は画面上にあっても常時実行されず、更新はシステムの **timeline と budget** に従う。
  データ更新時の animation も**最大 2 秒**。ロック画面 Widget は **`vibrant` 表示**になり
  システムが**脱色**して適応させる
- ⚠️ **不可能**: Live Activity も任意の常時 60 fps 面ではなく、通常**最大 8 時間**、
  ロック画面上の保持は**最大 12 時間**
- ★ 結論: 「通常の iOS と App Store 配布を前提に、**ロック画面全体を自前の連続作品へ置換することはできない**。
  アプリを前景表示すれば可能だが、**常に作品へ集中させないという目的と衝突する**」

### ADR-022 との整合判定

★ **完全に整合。新しい制約は追加していない。むしろ ADR-022 の方が大幅に詳細かつ厳密。**

| `.idea §4.13` | ADR-022 の対応箇所 |
|---|---|
| Android ライブ壁紙＝表示中の連続描画が可能 | D1「Android では成立する。ただし画面が点いている間だけ」/ D4 |
| iOS Widget の timeline/budget、animation 最大 2 秒 | D1 理由 1（同一逐語） |
| iOS ロック画面 Widget の `vibrant` / 脱色 | D3（色を主符号にしない根拠として同じ逐語を引用） |
| Live Activity の 8 時間 / 12 時間 | D4（同一の数値・同一の逐語。★ ADR-022 はさらに **push-to-start の alert 必須**という決定的根拠を持つ） |
| Android の OEM 差・AOD 実機確認の要否 | M-7 / M-8（同一の論点を未決として保持） |

⚠️ `.idea` 側は ADR-022 より**情報量が少ない**（Live Activities の alert 強制要件、
glanceable hub の AOSP 既定 OFF、BFU での Android Widget 完全消滅、`directBootAware` 実測など、
ADR-022 が持つ決定的根拠に `.idea` は言及していない）。矛盾は無いが **ADR-022 を前提にした簡略版**、
または独立に到達した同方向の結論と見られる（`.idea` 本文中に ADR-022 への直接参照は無い＝未確認）。

## §4.14 自前システムで越えられるもの／越えられないもの ★ 設計上の不変条件

★ **「自前システム」は単一の「専用アプリ」ではなく 5 段階のスペクトラム**を指す。

| 自前化する範囲 | 解決できること | 解決できないこと・代償 |
|---|---|---|
| 独自描画エンジン | 流動、補間、形態文法、端末内生成 | ⚠️ **iOS のロック画面実行権限は増えない** |
| Android ライブ壁紙／launcher | Android の home 面をかなり所有できる | ⚠️ **secure lock screen と全 OEM の AOD は所有できない** |
| AOSP fork／専用 Android 端末 | OS 面を含む完全な作品制御 | ⚠️ **一般ユーザーのスマホではなく、専用作品端末になる** |
| 外付け ambient display | OS 非対称を避け、常時・周縁・滑らかさを制御できる | ハードウェア制作、携帯性、配布の問題が増える |
| Web/PWA | 配布と試作が容易 | ⚠️ **ロック画面所有と安定した背景連続描画はできない** |

⚠️★★★ **越えられないもの（設計上の不変条件）**:
1. **iOS のロック画面実行権限そのものは、どの自前化の範囲でも増えない**
   （「一般ユーザーの iPhone を使い続ける」前提を外さない限り解けない）
2. **secure lock screen と全 OEM の AOD は Android でも所有できない**
   （ライブ壁紙／launcher の自前化だけでは届かない）
3. 専用端末化すれば技術的には解けるが、代償として **一般ユーザーのスマホでなく専用作品端末になる**
   → **研究対象の生態学的妥当性（日常のスマホ利用に埋め込む前提）を失う**

★ 結論（逐語）:
> 「自前システム」は描画問題を解けるが、**他社 OS の権限モデルそのものは解けない**。
> 同一の連続作品を iOS と Android のロック画面へ出すことが絶対条件なら、
> スマホ OS は主媒体に適さず、専用 Android・AOSP・外付け表示体のいずれかへ研究媒体を移す必要がある。

### ★ 意味的不変性と時間的非対称 / semantic invariance, temporal asymmetry

一方で「**作品の意味を同じにしつつ時間表現だけを OS に合わせるなら成立する**」として提示:

| 媒体 | 時間表現 |
|---|---|
| Android | **continuous fluidity**（可視時に連続する） |
| iOS | **episodic fluidity**（自然に見るたび次の位相が現れ、短い更新 animation で接続する） |
| 層 B ／展示 | 密な履歴を使う完全な 60 fps Practice Portrait |

> **iOS を劣化版として隠すのではなく**、「作品は鑑賞中ずっと動く必要があるのか、
> それとも生活の遭遇間で連続していればよいのか」という**媒体理論上の問い**へ変えられる。
> この非対称性を**欠陥ではなく作品形式の条件**として扱う案が最も強い。
