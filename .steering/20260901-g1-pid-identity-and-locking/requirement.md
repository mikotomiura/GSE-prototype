# G1 の P-ID 採番・本人確認の欠陥を O1 と同じ形に揃える

## 背景

2026-08-31 の調査 (§7) で、⚠️ **O1 で修正済みの欠陥が G1 に未修正のまま残っている**ことが
一次資料で確認された。★ 両者は **Phase1 の参加者ロスターただ 1 つ**を共用しているため、
片方の穴がもう片方のデータ健全性を壊す。

| # | 欠陥 | G1 の実体 | O1 (修正済み) |
|---|---|---|---|
| 1 | **申告 P-ID を検証なしで信用する** | `GSE_G1_Form_Builder.gs:1858` —— `if (pid && rowPid === pid) return {...}` が**メール一致より先**に評価される | `Form_O1/…:989-1029` メール優先 ＋ `conflict` 返却 |
| 2 | **手動採番がロック外** | `:1789-1807` `assignG1ParticipantId` が `LockService` を取らずに `appendRow` | `Form_O1/…:1057-1071` `o1WithRosterLock_` で両経路を包む |
| 3 | **`last > 1`** で 1 行だけのロスターの既存 P-ID を見落とす | `:1775` | `Form_O1/…:957` `last >= 1` |

### ⚠️ #1 が実害になる筋道

★ G1-C の参加者ID欄は自由記入で、フォーム URL は被験者に配られる。
→ 打ち間違い (`P015` → `P016`) でも第三者の申告でも、⚠️ **他人の P-ID を名乗れる**。
★ ロスターが共用なので、⚠️ **G1 経由で名乗った ID が O1 の数週間ぶんの常時打鍵ログと
同じ P-ID 空間に混ざる**。→ A さんから削除要求が来たとき、
`<pid>_o1day*` の削除は「B のデータも消す」か「A のを消し残す」のどちらかになり、
⚠️ **同意文書 §4-3 の「消えます」が履行不能**になる。

### ★ いま顕在化していない理由 (⚠️ 安全だからではない)

G1 は `.steering/20260819-g1-reboot-and-instrument-fix/blockers.md:25` の **D-5 が未クローズ**で
新コホートの収集を止めている。⚠️ **O1 配布と G1 再開が同時に走る局面で実害になる。**

## ゴール

G1 の採番・本人確認を O1 と同水準にし、**二重採番となりすましを機械で検知できる**状態にする。

## スコープ

### 含むもの
- 上表 3 件の是正 (O1 の実装を移植する)
- ⚠️ `conflict` を **Logger ＋ G1 実施トラッキングの「要確認」行**に出す
  (★ O1 は Logger だけ。⚠️ 研究者が実行ログを見に行くまで気づけないため G1 では強める)
- ★ **採番後の重複検知**: `appendRow` の直後にロスターを読み直し、
  自分の P-ID が 2 行以上無いことを確かめる
- 上記を検査する回帰テスト (`Form_G1/guard_test.cjs` に追加、★ 陽性対照つき)

### 含まないもの
- ⚠️★★★ **T-27 (プロジェクト跨ぎの排他)**。★ `LockService.getScriptLock()` は
  **スクリプトプロジェクト単位**なので、別プロジェクトである G1 と O1 のあいだでは
  **原理的に排他できない**。→ ★ 本タスクは「防ぐ」のではなく「**起きたことに気づく**」まで。
  排他そのものは設計判断を伴うので別タスク (`/reimagine` 相当) とする。
- ⚠️ T-21 (実ロスター ID の直書き) / T-15・T-16 (実 Drive ID)。別トラック。
- ⚠️ **D-5 のクローズ** (実 Google フォームへの `migrateConsentForm()` 反映)。
  ★ ブラウザ作業であり研究者の手番。→ 本タスクは repo 側の正本を直すところまで。

## 受け入れ条件

- [ ] `g1FindInPhase1Roster_` が **メール一致を最優先**し、申告 P-ID は
      「その行のメールが空」のときだけ採用する
- [ ] 申告 P-ID の行に別人のメールがあるとき `{conflict: true}` を返し、
      ⚠️ **発番も受付メールも行わない**
- [ ] `conflict` が G1 実施トラッキングの**要確認行**に出る (★ Logger だけにしない)
- [ ] `assignG1ParticipantId` と `onG1ConsentSubmit` の**両方**が同じロックを通る
- [ ] `g1NextParticipantId_` が `last >= 1` で読む
- [ ] 採番直後に重複検知が走り、⚠️ 重複を見つけたら**気づける形**で記録される
- [ ] ⚠️ 追加した検査が**実在の欠陥を捕まえる**ことを陽性対照で確認する
      (★ 修正前のコードを注入して赤になること)
- [ ] `bash experiments/20260801-controlled-friction-task/run.sh` が緑
- [ ] ⚠️ `Form_G1/` に秘密・実 ID を**新たに増やさない**
