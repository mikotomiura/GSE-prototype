## ★ O1 とわざと変えたところ (⚠️ 2 点だけ)

### 1. `conflict` を **シートにも出す** (`g1RecordRosterConflict_`)

⚠️ O1 は `Logger.log` で止めている。★ しかし **研究者が実行ログを見に行くまで誰も気づかない** ——
「警告が出ていない」を「問題が無い」と読ませてしまう
(memory `silent-success-is-not-visible`)。→ 研究者判断 (2026-09-01) で G1 では強める。

⚠️★★ **申告された P-ID の行には書かない。**
★ `conflict` のとき `pid` は**他人のもの**なので、その人のトラッキング行に書くと
⚠️ **無関係な被験者の記録を汚す**。→ 専用行に積む。

#### ⚠️★★★ その専用行の P-ID 列は **空にする**（★ 初版から変えた）

初版は P-ID 欄に `⚠要確認` という印を入れた。「`^P\d+$` に一致しないから安全」と考えたが、
★ **消費者を実際に grep して確かめたら違った**:

| 消費者 | 挙動 | 判定 |
|---|---|---|
| `submissionPids_` (:1069・「**行の真実源**」) | `if (pid && out.indexOf(pid) < 0) out.push(pid)` | ⚠️ **`⚠要確認` を参加者 1 人として数える** |
| `refreshG1RunSheet` (:3406) | `if (!pid) continue` | ⚠️ 空でないので通過 |
| `g1CollectPendingMaterials_` (:3091) | `if (!pid) continue` → その後 `if (!url) continue` | ★ URL が空なので結果的に安全 |
| `g1EnsureRunRow_` (:2031) | 実 P-ID との完全一致 | ★ 一致しないので安全 |

→ ★ **P-ID 列を空にすれば全消費者が自然に除外する**。印は備考の文頭 `⚠★要確認` が担う
（★ 人には見え、機械は数えない）。

⚠️ 実名・メールは書かない (`data-privacy`)。`g1MaskEmail_` を通した形だけ残す。
⚠️ 失敗しても throw しない —— ★ ここで例外を投げると発番の巻き戻しに見える。false を返して**ログには残す**。

### 2. 採番直後の **重複検知** (`g1CountPidRows_`)

⚠️★★★ **T-27 は防げない。** `LockService.getScriptLock()` は**スクリプトプロジェクト単位**で、
G1 と O1 は別プロジェクト (`Form_G1/README.md:134` / `Form_O1/…:34`)。
→ ★ 同じロスターへの「読んで max → 書く」は**プロジェクト跨ぎでは一切排他されない**。

★ 防げない以上、**起きたことに気づける**ようにする: `appendRow` の直後に読み直し、
自分の P-ID が 2 行以上あれば Logger ＋ `⚠要確認` 行に出す。

⚠️ **自動で消したり振り直したりしない。** ★ どちらの行が誰のものかはコードには判断できず、
消すと被験者のデータが迷子になる。→ 研究者に判断させる。

## テスト戦略

`Form_G1/g1_roster_test.cjs` (新設・**29 ケース**) を `run.sh` に配線した。

⚠️ **`[ -f ]` で囲わない。** ★ ファイルが消えたら**黙って飛ばさず赤にする**
(既存の O1 テスト側は `[ -f ]` を使っており、そこは無言スキップの型である)。

### ★ 検査が空回りしていないことの実測

| 対照 | 内容 | 結果 |
|---|---|---|
| 陰性 | 本人 (メール一致) / メール空欄の行 / 2 行以上のロスター / 重複なし | ✅ 全て通る |
| **陽性 (変異注入)** | **M1** なりすまし経路を旧実装に戻す | ✅ 赤 4 件で捕捉 |
| | **M2** `last >= 1` → `last > 1` | ✅ 赤 2 件で捕捉 |
| | **M3** 手動採番のロックを外す | ✅ 赤 7 件で捕捉 |
| | **M4** 重複検知を握りつぶす | ✅ 赤 3 件で捕捉 |
| | **M5** `conflict` を返さず素通りさせる | ✅ 赤 3 件で捕捉 |
| | **M6** P-ID 列に印を書き戻す | ✅ 赤 3 件で捕捉 |

| **配線の陽性対照** | M5 を入れて `run.sh` を走らせる | ✅ **rc=1 / `[FAIL]`** |

### ⚠️★★★ 途中で踏んだ「変異が当たらない」型 (★ 記録する)

**M6 は最初、緑のまま素通りした。**
★ 原因は変異でもコードでもなく **検査の書き方**だった —— 手で組んだシートを
`submissionPids_` に渡していたので、`g1RecordRosterConflict_` が何を書くかを
**1 行も通っていなかった**。⚠️ *「`submissionPids_` の性質」を測っていて、
「conflict 行が数えられないこと」を測っていなかった。*
→ ★ **実際に `g1RecordRosterConflict_` に書かせてから数える**形に直したら捕捉した
(memory `measurement-instrument-false-positives` の「⚠️ 変異が当たらない」型)。

⚠️ さらにその過程で **スタブに `getLastColumn()` が無く**、`runHeaderDiff_` が例外になって
`g1RecordRosterConflict_` が **false を返し続けていた**。★ 無変異でも 2 件赤になって初めて気づいた。
→ ⚠️ もし「書けたか」を assert していなければ、**空回りしたまま緑**になっていた。

★ さらに `run.sh` の `guard_count` は `^全 N ケース期待どおり$` を**行頭アンカー**で読むので、
⚠️ 完了行に空白や絵文字を置くと「件数不明」になる (★ 最初にそれを踏んだので直した)。
→ **何件走ったか分からないまま緑になる**のを防ぐ。
