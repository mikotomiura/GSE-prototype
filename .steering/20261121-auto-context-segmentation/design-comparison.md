## 設計案比較

### v1 の要旨
- Rust が 120 秒の因果窓で文脈の量を集約して出す。窓の長さは封筒の config に出す。
- 解析側では、境界を先に探す。無操作と、前後の窓の差が閾値を超える点を境界にする。
- その後、区間を人ごとに混合ガウスでまとめる。
- 判定は、合成・宣言との照合・循環（状態との NMI）・本人の振り返りの 4 本。

### v2 の要旨
- Rust は 1 秒の tick の中の数だけを出し、窓の引数を持たない。
- 解析側では、60 秒の固定の窓をまとめた後に、最小の滞在長で平滑化する。境界は名前が変わった点として後から出てくる。
- 判定に「本人の中での再現性」（前半で学んだまとめを後半に当てはめる）を足す。
- 循環の検査に「打鍵の多さだけで割れたか」（量の軸だけで再現できるか）を足す。

### 主要な差異
| 観点 | v1 | v2 |
|---|---|---|
| アプローチ | 境界を先に探し、区間をまとめる（2 段） | 窓をまとめて平滑化し、境界は結果として出る（1 段） |
| 調整する値 | 窓・無操作・境界の閾値 `τ_cp`・最短の区間の 4 つ | 窓・最短の滞在長・無操作の 3 つ。`τ_cp` が無い |
| Rust の範囲 | 窓で集約し、config に `context_window_ms` を出す | tick 内の数だけ。config も事前登録も動かない |
| 窓を変えるとき | Rust の引数と出力が変わる | 解析側だけで済む（感度を事前に複数の窓で見られる） |
| 判定 | 合成・宣言・循環（状態）・振り返り | 左に加えて、本人の中での再現性と、打鍵の多さの検査 |
| 宣言の無い人 | 判定できないが増える | 再現性で一部は判定できる |
| 変更規模 | Rust がやや大きい（窓の計算と端の扱い） | Rust は小さい。Python がやや大きい |
| テスト | 窓の端のテストが Rust に要る | Rust は tick の端だけ。平滑化のテストを Python に置く |
| リスク | 境界の閾値 `τ_cp` を決める根拠が薄く、事前登録の前に選びにくい | 平滑化が短い切り替え（3 窓 = 3 分未満）を消す。素早い行き来は区間にならない |

### 推奨案
v2。ただし v1 の 1 点を取り込んだハイブリッドにする。

理由は次のとおり。

- 事前に固定する値が 1 つ減る（`τ_cp` が無い）。実データを見る前に決める値の根拠が、薄いものから減る。
- Rust を tick の数に限ると、窓の長さの感度を解析側だけで事前に決めた複数の値で見られる。P1 の封筒や事前登録も動かさずに済む。
- 本人の中での再現性は、宣言が少ないという今回の出発点の問題に直接効く。ラベルが無くても「偶然のまとまりではない」と言えるため。
- 打鍵の多さの検査は、要件にある循環の検査を、状態との比較だけより強くする。

v1 から取り込む点: v2 の平滑化は、3 分未満の行き来を消す。そこで、v1 の「無操作 `G_idle` で必ず切る」は強制の境界として残す（v2 にもあるが、平滑化で吸収しない規則として明記する）。短い行き来をどれだけ消したかは、notes に数として出す。
