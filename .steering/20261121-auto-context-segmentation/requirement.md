# 作業の区間を自動で切り、本人の中でまとめて名前を付ける（auto-context-segmentation）

## 背景

段 1 を本人で回してみて、研究者は次のことに気づいた。作業を切り替えるたびに宣言（`task_kind`）やラベルを付ける人はほとんどいない。そうなると、宣言に頼った区間の名前は、実際の作業では空のまま残りがちになる。

研究者の案は、打鍵などの観測から区間を裏で自動で分け、区間ごとの傾向を読んで「task-A」のような名前を自動で付けることである。

すでに決まっている制約が 2 つある。

- ADR-010 の代替案 B（観測署名で `task_kind` を推定して re-route する）は却下済みである。D3 は「宣言と観測を融合して真の task_kind を作らない」と決めている。そのため、自動の名前は推定や介入の入力には使わず、研究解析の層に置く。
- 状態の推定に使う 5 特徴量でまとめると、「task-A」が実は Flow の区間だった、という循環が起こりうる。

## ゴール

replay の後のオフライン解析として、次の 2 段を行う。

1. 観測から作業の区間の境界を見つける。
2. 区間を本人の中でまとめて、名前（task-A, task-B, …）を付ける。

そのうえで、この手法が使えるかどうかを、事前に決めた基準で判定する。

## スコープ

### 含むもの

- `gse-replay --features` の特徴行に、フォーカス遷移とポインタの量の列を additive に足す（Rust の計算層・テストつき）。段 1 で配っているアプリの挙動は変えない。
- 境界の検出と、本人内でのまとめ（クラスタリング）を行う解析スクリプトを `experiments/` に置く。reproducibility-discipline に従う。
- まとめに使う特徴は「文脈の量」に限る（`docs/glossary.md`）。5 特徴量は入れない。まとまりが推定状態とどれだけ重なるかは、循環の検査として数える。
- 合成の記録を陽性対照に使う。切り替えの時刻が分かっている記録で、手法が境界を拾えるかを先に見る。合成の記録は実データに混ぜない。
- 実データは本人の段 1 の記録と O1 の被験者の記録の両方を使う（研究者によれば参加者の許可は得ている）。
- 判定の方法は次のとおり。
  - 全員について、`task_kind` の宣言の切り替えや `activity_label` との一致を見る。ラベルは照合にだけ使い、閾値は実データを見る前に決めて記録する。
  - 宣言の無い区間は、本人の分だけ振り返りで補う。
- アプリの識別子が使えたら結果がどれだけ変わるかの見積もりを、`decisions.md` に残す。
- 論文化の検討は、結果を見てから行う（スコープには入れておく）。

### 含まないもの

- 自動の名前を推定・Nudge・介入判定の入力にすること（ADR-010 D3 を改訂しない）。
- 段 1 で配っているアプリの挙動の変更。
- アプリの識別子の記録。計器の変更になり、data-privacy と ADR-032 の判断が要るため、要るかどうかの記録だけ残し、取るなら別のタスクにする。
- 記録や特徴行を外部（Codex を含む外部 LLM）に送ること。これは規約で決まっていて変えられない。`/cross-review` に回すのはコードの diff だけにする。

## 受け入れ条件

- [ ] `--features` に足した列の単体テストが緑（`cargo test --manifest-path src-tauri/Cargo.toml --workspace`）。既存のゴールデンの byte-equal も保たれる。
- [ ] 判定の基準（一致の指標と閾値・循環の検査の閾値）が、実データを処理するコミットより前のコミットに入っている。
- [ ] 合成の陽性対照で、既知の境界を基準どおりに拾えることをスクリプトの終了コードで確かめる。壊した入力（境界を消したもの）で赤になることも確かめる。
- [ ] 本人の段 1 と O1 の実データで、事前の基準による判定（使える／使えない／判定できない）を `experiments/<日付>-auto-context-segmentation/notes.md` に記録する。
- [ ] 本人の振り返りの結果と、アプリの識別子の要否の見積もりを `decisions.md` に残す。
- [ ] 特徴行が共有の門（`scripts/check_no_feature_output.sh`）を通り、リポジトリに入っていない。
