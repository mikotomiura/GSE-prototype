# 設計判断

## D-1: レシートの根拠を「収束器が `.sent` を置いた件数」に固定した

**決定**: バックエンドに `SUBMIT_LAST_SENT_MS` / `SUBMIT_LAST_SENT_COUNT` を置き、
`gse-submit --reconcile` の要約行 `GSE_RECONCILE {"sent":N,…}` が **`N > 0`** のときにだけ書く。

**理由**: `.sent` はアップロードが `Ok(())` を返したときにしか置かれない (`reconcile.rs` §設計核 ③)。
★ 端末側から得られる**最強の証拠**である。

**却下案**:
- 「送信する」を押したら成功表示 → ⚠️★ **偽のレシート**。押下は送信の開始ですらない
  (ブロック実行中なら収束器は見送る)。今回いちばん避けたい形。
- `awaiting_approval` が 0 に減ったら成功表示 → ⚠️ 承認の印を付けただけで減る。送信とは無関係。
- `unsent` が 0 になったら成功表示 → ⚠️ 起動直後 (何も作っていない) と区別できない。

## D-2: `sent == 0` の実行でレシートを消さない

**決定**: `record_sent_if_any` は `sent == 0` / 要約行が読めない場合、**何も書き換えない**。

**理由**: 収束器はアプリ起動のたびに走り、★ **平常時はほぼ毎回 `sent: 0`** である。
0 で上書きすると、⚠️ **本当に送れた直後のレシートが数秒で消える**
(被験者からは「出て、消えた」= 何が起きたか分からない)。
★ この変数が保つのは「**最後に本当に送れたのはいつ・何件か**」であって「直近の実行の結果」ではない。
テスト `only_a_real_send_writes_the_receipt` ④ がこれを仕様として固定している。

## D-3: `sending` は **スレッドの外**で立てる

**決定**: `InFlightGuard::new()` を `thread::spawn` の**前**で呼び、guard をスレッドへ move する。

**理由**: 中で立てると、被験者が「送信する」を押して確認カードが消えてから
スレッドが起きるまでの間に ★ **無表示の窓**ができる。それは今回潰そうとしている沈黙そのもの。
`approve_pending_submissions` は `spawn_reconcile` を呼んでから返るので、
★ フロントが押下直後に読む状態には既に `sending: true` が乗る。

**副次の判断**: 手で `fetch_sub` せず `Drop` に載せた。
⚠️ 戻し忘れると画面が「送信しています…」のまま**永久に固まり**、
しかも未送信警告も (`!sending` gate で) 消えるので ★ **沈黙が悪化する**。
`in_flight_returns_to_zero_even_on_panic` で panic 経路を固定した。

## D-4: 確認待ちが 1 件でもある間はレシートを出さない

**決定**: 表示条件に `awaiting_approval === 0` を入れた。

**理由**: 次のブロックが終わって確認カードが出ている画面にレシートが並ぶと、
⚠️★ **まだ送っていない回のレシート**に読める。隠しておけば、レシートが見えている時の
「この回」は**必ず直近のブロック**を指す。
→ 引き継ぎメモが指定した文言「✅ この回の記録を送信しました」を、
★ **その文言が正しくなる条件を作ることで**採用した (文言を弱めるのではなく)。

⚠️ 一方、**未送信が残っていても**レシートは出す (部分成功)。
「1 件送れた / 1 件残っている」は両方とも事実であり、片方を伏せない。

## D-5: 「全部送れています」は書ける事実だけにした

**決定**: 未送信 0 件・このプロセスで 1 件も送っていない状態の文言は
「✅ 送信を待っている記録はありません。」とした。

**理由**: 起動直後は `.age` が 1 本も無いだけで、⚠️ 「すべて送信済み」とは**言えない**。
★ 肯定形にするために事実を盛らない。1 件でも送れた後は D-1 のレシートが出るので、
肯定形の要件 (要件 §2-3) はそちらで満たす。

## D-6: 送信中だけポーリングを 1 秒に上げた

**決定**: `setInterval(read, sending ? 1000 : 3000)`。

**理由**: 実機で承認 → 完了に 6 秒かかる。3 秒のままだと
★ **送り終わってから最大 3 秒間レシートが出ない**(沈黙が残る)。

⚠️★ **ただしこれは「速くなる」保証ではない** (下記 §検証の落とし穴を参照)。

## ⚠️★ 検証で分かったこと (引き継ぎに残す)

### 背面タブ/背面ウィンドウでは `setInterval` が絞られる

検証中、`document.visibilityState === "hidden"` の間 ★ **3 秒ポーリングが完全に止まった**
(7 秒間で `get_submission_status` が **0 回**。実測)。
Chrome の背面タブスロットリングである。

- ★ 本 UI が読まれるのは**スタート画面**＝被験者が GSE の窓を見ている時なので、実施上は問題にならない。
- ⚠️ ただし **GSE の窓を背面に置いたまま**だと表示の更新が遅れうる。
  これは既存の 3 秒ポーリングにもともと在る性質で、本変更が作ったものではない。
  ★ ブロック境界を JS の `setTimeout` ではなく Rust スレッドに置いてある理由 (`lib.rs` の
  「WebView の背面タイマーはスロットリングされうる」) と**同じ現象**である。

### 輝度差の測定は `background-image` を見ないと嘘になる

★ 素朴に親を遡って `backgroundColor` を合成すると、`.start-button`
(`background: linear-gradient(...)`) が **`cr = 1.00`(＝背景と同色) に化けた**。
⚠️ これは 2026-08-08 の実際の欠陥と**見分けがつかない偽陽性**である。
→ `scripts/tests/submission-receipt-view.html` の測定側で
`backgroundImage !== 'none'` を検出して「測れない」と報告する形に直した。
★ **測定器のほうを疑う**手順を踏まなければ、存在しない欠陥を直しに行くところだった。
