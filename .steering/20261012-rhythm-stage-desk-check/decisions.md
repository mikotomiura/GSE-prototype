## 判断 2: 検査に背景の変化での招待を含めない

## 判断 3: 描画の入力の時間の解像度 —— 秒未満も比べる

- **判断日時**: 2026-10-12（研究者・AskUserQuestion）
- **背景**: 引き継ぎ §3 の 6（`/cross-review` 1 巡目・Codex の指摘）。
- **選択肢**: A 秒ごとの集計だけ（Claude の推奨: EH1 の道具をそのまま使え、打鍵の間隔の列が画面共有に映る `data-privacy` の論点を作らない）／B 秒未満も比べる
- **採用**: B（研究者）
- **含み**:

  - 検査に、秒ごとの集計が同じで打鍵の間隔だけが違う列と、止まりと再開の境界を足す。
  - 秒未満を製品で採るかは別の判断で、研究者が `data-privacy` と合わせて決める（引き継ぎ §3 の 6）。この検査は合成の列だけを使うので、検査そのものは `data-privacy` の対象のデータを作らない。

## 判断 4: 項目 1 の基準のモデルは A_speed（打鍵の有無と速さ）

- **判断日時**: 2026-10-12（研究者・AskUserQuestion・推奨どおり）
- **背景**: EH1 の合成の世界 world v2 は、停滞（STRUGGLE）を打鍵の間隔が遅い（flight の中央値 150 → 320 ms）・訂正が多い（3% → 25%）として作っている（`experiments/20261010-portrait-eh1-round5/config.json` の `_comment_segments_v2`）。EH1 のモデル A は打鍵の有無だけ（`portrait.py` の `presence_features`）。モデル A を基準にすると、速さを写す描画は作りの上で必ず「漏れる」と出る。
- **選択肢**: A_speed を基準に判定（推奨）／A を基準に判定／両方で判定
- **採用**: A_speed（モデル A に速さの量を足したもの）を基準にし、描画が A_speed を超えて停滞を識別できるかで合否を出す。A を基準にした値と、A_speed − A（速さだけで分かる量）は記述で並べる。
- **理由**: 引き継ぎの「打鍵の有無・速さを超えて」に合う。A_speed − A は world v2 の作り方の性質で、ステージの性質ではない。
- **含み**: 合否は「A_speed に入れた速さの要約を超えて」までしか言えない。A_speed に入れなかった速さの側面（窓の中の時間の推移など）を描画が運べば、それは上乗せとして出る（design §3 に書く）。world v2 では速さそのものが停滞を写すので、項目 1 が緑でも「ステージは停滞を写さない」とは言えない（速さを経由して写す。台帳 T1 は閉じない）。

## 判断 5: 写像が読んでよい入力は打鍵の有無と速さだけ

- **判断日時**: 2026-10-12（研究者・AskUserQuestion・推奨どおり）
- **採用**: 写像の入力は、打鍵の有無・打鍵の数・打鍵の間隔に限る（秒ごとでは F1・F4・keys、秒未満では打鍵の時刻）。訂正（F3・F6）と推定（`p_stuck`・X・Y・`level`）は入力にしない。
- **理由**: 訂正は world v2 が停滞を直接埋め込んだ量で、それを写すと作りの上で状態計になる。リズムへの追従という提案の趣旨にも合う。推定を使わないのは親タスクの判断 5 の類比。
- **含み**: 訂正を写す写像は、検査器が漏れを拾えることの「自然な陽性対照」として使う（判定は受けない・design §1.4）。

## 判断 6: 項目 1 の許容の値は 0.03

- **判断日時**: 2026-10-12（研究者・AskUserQuestion・推奨どおり）
- **採用**: 上乗せ（AUC(B) − AUC(A_speed)）の 95% 区間の上限の最大 < 0.03 で緑。EH1 第 1〜5 回と同じ値。陽性対照の強さの条件も EH1 の形（下限の最大 > 0.03・点推定の最大 ≤ 0.08・土台の上限の最大 < 0.03）を写す。

## 判断 7: 攻撃者に見せるのは描画のパラメータの列

- **判断日時**: 2026-10-12（研究者・AskUserQuestion・推奨どおり）
- **採用**: 描画器は作らない。写像の出力（毎フレームの描画のパラメータ）を一定の率で取り、窓ごとに要約して攻撃者に渡す。
- **理由**: 画素に描くと情報は減る側なので、パラメータで漏れが見つからなければ、そのパラメータから描いた画でも見つからない（上界の側）。描画器を作ると、その作り方しだいで結果が変わり、試作の段の判断を先取りする。
- **含み**: 逆は言えない。パラメータで漏れが見つかっても、描いた画で人が読めるとは限らない。

## 判断 8: 固定の前の `/cross-review` 1 巡目の結果と対応（2026-10-12）

- 範囲: `a30ee850` の `design.md`・`decisions.md`（`70113cd5..a30ee850` の 2 ファイル・Codex はパスを限ったラッパー）。Claude（`code-reviewer`）は HIGH 2・MEDIUM 6・LOW 5、Codex は P1 2・P2 3。
- **両者が一致した指摘（1 件）**: 基準 A_speed の AUC が天井に近く、PC1 の「下限 > 0.10」が作りの上で届かない（Claude H1・Codex 5）。一次で確かめた: EH1 第 5 回の `results/v2/material_info.json` で、A の AUC 0.75〜0.82 に F 系列の水準を足した値は 0.98〜0.998（L300 の hgb は 0.825 + 0.173）。world v2 は停滞を打鍵の間隔に埋め込んでいる。→ 研究者の判断 9。
- **判断 7 の理由の訂正**（Codex の指摘 2・研究者に伝える）: 判断 7 の理由に「画素に描くと情報は減る側なので、パラメータで漏れが見つからなければ、そのパラメータから描いた画でも見つからない（上界の側）」と書いたが、これは成り立たない。攻撃者が見るのは列そのものではなく窓ごとの要約 20 と限られた分類器で、要約で失われた時間の型は描いた画に残りうる。情報量の上界（描画の関数は情報を増やさない）と、特定の攻撃者が検出できるか、は別である。判断 7 の決定（描画器を作らずパラメータの列を使う）は変えず、読み方から「描いた画でも見つからない」を外した（design §3.3）。決定の理由として残るのは「描画器を作るとその作り方しだいで結果が変わり、試作の段の判断を先取りする」の方だけである。
- そのほかの対応（すべて当たっていたので直した・design に反映）:
  - 赤の意味（Codex 1）: 上限 ≥ 0.03 は漏れの検出ではない。赤を「0.03 未満と確かめられなかった」と定義し、記述として赤・検出（下限 > 0.03）と赤・未確認に分けた。
  - 止まり方ごとの陽性対照（Codex 3）→ 研究者の判断 10。
  - 解像度の比較に駆動の値の違いが混ざる（Codex 4・Claude M6）: 項目 6 を「2 つの入力の処理の方式の比較」に限り、双子の AUC は 2 方式の差で読む、とした。
  - 帰無の論理積（Claude H2）: PC-corr を外し、土台を入れた（候補 24・PC1・PC-stall 24・PC0 24 の 73 本）。
  - L60 の A_speed の定義（Claude M1）・土台が止まりと再開の時刻を持つかは候補しだい（M2）・「打鍵のある時点」の定義と `rank`・2 方式の PC の見込み（M3）・`gse-replay` の因果を selftest で確かめる（M4・`replay_all.py` の注で tick の秒の対応を一次で確かめた）・記述の量の定義の固定（M5）。
  - LOW: PC-cal を置かない理由（L1）・下見の格子を EH1 と揃える（L2）・`f4` を使わない（L3）・`res=sub` では止まり方がほぼ同じになる見込み（L4）・selftest の閾値（L5）。

## 判断 9: 天井を先に測り、天井なら world v3 を足す

- **判断日時**: 2026-10-12（研究者・AskUserQuestion・推奨どおり）
- **背景**: 判断 8 の一致した指摘。
- **選択肢**: 先に測り、天井なら v3 を足す（推奨）／すぐ v3 を主に／上乗せを伸びしろで正規化／基準を A に戻す
- **採用**: 固定の前に下見 0（`SEED + 1`・P 40・world v2 と v3 の AUC(A)・AUC(A_speed) だけ）を回す。L300 の伸びしろ 1 − AUC(A_speed) が 0.15 以上なら v2、そうでなく v3 が 0.15 以上なら v3 を本番に使う。どちらも届かなければ研究者に戻す（design §3.0）。
- **理由**: 下見 0 は基準のモデルの値だけを見て、描画の候補の値を見ないので、固定の規則に反しない。world v2 のままでは項目 1 が作りの上で判定不能になる見込みが高い。
- **world v3**（Claude が足した作り方・design §1.6・§9 の 8）: STRUGGLE の打鍵の間隔を FLOW と同じにし、world v1 の「訂正の後の間」を戻す。停滞は訂正と、その後の長い間にだけ出る。
- **含み**: v3 を使うと、項目 1 の問いは「速さに出ない停滞（訂正の後の間の型）を、描画が A_speed を超えて運ぶか」になる。v2 と v3 のどちらでも、合成の停滞は打鍵の統計の型で、どの型を停滞とするかの選び方が結果を決める。
