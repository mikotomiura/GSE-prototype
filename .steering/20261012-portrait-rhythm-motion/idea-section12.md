
## 12. 打鍵のリズムで動く背景の「ステージ」（2026-10-12・タスク `portrait-rhythm-motion`）

> 一次は `.steering/20261012-portrait-rhythm-motion/`（ブランチ `docs/portrait-rhythm-motion`）の `decisions.md` 判断 1〜9 と `survey-results.md`（調査 S-RM・出典 [P468]–[P471]・[V283]–[V286]）。本節は要約で、一次ではない。EH0 の案で、ADR ではない。

### 12.1 研究者の提案

- 壁紙を「遅い時間で少し変わる」静止画の更新ではなく、**打鍵のリズムで滑らかにリアルタイムで波打つ**表現にする（時計ではなく打鍵のリズムで動かす）。
- 壁紙という「紙」に固執せず、**デスクトップの背景の層に自前の描画面（ステージ）を置く**と捉える。
- 招待も、右上の図像ではなく背景の変化で身体へ戻ることを促す形にする案。

### 12.2 決めたこと（研究者）

| 論点 | 決定 |
|---|---|
| EH3 との関係（判断 1） | **EH3 の後に回す**。EH3 は今の設計で凍結へ進める。この案は EH4 などの候補 |
| 肖6・判断 5（§11.1）の扱い（判断 3） | **変えない**。壁紙（再着手の面）の規則のまま。ステージは**別の面の候補**で、採るときにその面の規則を新しい判断として起こす |
| 最初の段（判断 4） | **合成の打鍵の列での机上の検査**（EH1 の型・参加者なし）。リアルタイムの写像が停滞・打鍵の有無・速さをどれだけ写すかを測る。試作は作らない |
| 背景での招待（判断 5） | **候補に残す**（Claude の推奨は「図像のまま」だった）。採るときに PC-1・判断 1（§11.1 の分け方）・PC-12・A18 との関係を決める |
| `PS-Q8`（判断 6） | 閉じない。**ステージは D21 の常時リアルタイム表現を「維持する側」の具体案の候補**として、ここで指し示すだけにする |

### 12.3 調査の要点（S-RM・網は粗い）

- **背景の全面が動き続ける表示を作業中に評価した研究は 0 件**。動く壁紙の査読論文も 0 件。近い証拠は割れている: 小さな一画の文字のアニメは主課題を落とさなかった（[P468]）一方、課題に無関係なアニメは知っていても遮断できず慣れは短い（[P469]）、動く妨害の抑制は静的なものより弱い（[P470]）。「滑らかなら静か」を示した文献は無い。常に出ている面は、ADR-026 PC-1 の読みでは常に代償の側に入る。
- **控えめな環境の手がかりは、手がかり無しと変わらなかった**（[P471]）。§3-5 の再着手の面のねらい（驚きに出会う機会）は否定されないが、「背景が穏やかに変われば戻りやすい」は支持されない。
- 本人が表現を状態計として読んだか・表現を動かすために打鍵を変えたかの一次は 0 件 → 机上の検査で先に測る（台帳 T1）。
- **技術**: Windows は非公開の WorkerW に窓を差し込む方式で、24H2 で Lively が中核を書き直した（[V284]）。取り込みからの除外（`WDA_EXCLUDEFROMCAPTURE`）はトップレベルの窓だけで（[V283]）、ステージは画面共有から外せない見込み。本人の壁紙のファイルには触れないので「元の壁紙を書き直す」型の問題は消えるが、explorer の再起動・スリープ・異常終了への手当てが要る（[V285]）。WebView は覆われた窓でアニメーションを止めうる（二次）。Android のライブ壁紙は見えている間だけ CPU を使う作法（[V286]）。
