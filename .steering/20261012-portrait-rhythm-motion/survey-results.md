# 調査 1 ラウンドの結果（S-RM・2026-10-12）

> 4 本のサブエージェント（Sonnet・各 2〜5 分）の報告を、メインが原本で照合した範囲で書く。網は粗い（各 angle で数回の検索）。「0 件」は「この範囲で見つからなかった」の意味である。
> 断定に使った出典はメインが原本で照合した: [P468] [P469] [P470] [P471]（pypdf で全文）・[V283] [V284] [V285] [V286]（取得して逐語を確認）。サブエージェントの報告の写しは `$CLAUDE_JOB_DIR/tmp/survey-*.md`（job が消えると消える）。

## 1. 研究

### 1.1 周辺で動き続ける表示は注意を奪うか（R1 → 衝突 C4・`E-14`）

- **背景の全面が打鍵に合わせて動き続ける表示を、作業中に評価した研究は 0 件**。動く壁紙（animated / live wallpaper）の査読論文も 0 件。
- 近い証拠は割れていて、どれも「小さな一画のアニメ」か「探索課題の妨害刺激」である。
  - 主課題を落とさなかった: [P468] 画面の小さな一画の文字のアニメで、情報探索の主課題（実験 2 は N = 91）。著者は結論で「滑らかで予測できる変化には慣れる」と見立てるが、実験で確かめたものではない。
  - 主課題を落とした: [P469] 課題に無関係なアニメは情報探索を下げ、参加者は知っていても遮断できなかった。慣れは短く、課題をまたぐ干渉を説明しない。Dutta ら（2002・運動を要する主課題で妨害あり・抄録のみで未登録）。
  - 動きは抑えにくい: [P470] 動く目立つ妨害の抑制は、静的な妨害より弱く、立ち上がりが遅い（視覚探索・1 研究）。[P85] 動きは色・形より周辺で検出されやすい（既登録）。
  - 動きの「開始」は注意を捕捉し、動き続けることは捕捉しない、という対比（Abrams & Christ 2003）は、今回は二次の引用でしか読めていない（根拠に使わない）。
- 既決との関係: ADR-026 PC-1・PC-3（代償は出す／出さないと面積で動き、強度では下がらない・[P341] [P343] [P342]）は、離散の通知の実験から来ている。背景の全面が常に「出ている」ステージは、PC-1 の読みでは**常に代償を払う側**に入る。面積は最大である。「滑らかなら静か」とは、どの文献も言っていない（[P468] の見立てだけ）。
- 打鍵のリズムに追従すると、打鍵の始まりと止まりのたびに動きの様子が変わる。これは動きの「開始」に近い変化を、本人の打鍵に合わせて作ることになる（推論・未検証）。

### 1.2 環境の手がかりは再着手を助けるか（R2 → 衝突 C1・面の分担）

- [P471]: 中断の後、目立つ手がかり（赤い矢印）は再開を速めたが、**控えめな環境の手がかりは手がかり無しと変わらなかった**。著者は「環境の手がかりが再開を助けるという案は文献で広く支持されていない」と書く。
- `.idea` §3-4 の再着手の面のねらいは再開を速めることではなく「評価されない驚きに出会う機会」なので、[P471] はねらいを否定しない。ただし「背景が穏やかに変わっていれば戻りやすい」という読みは支持されない。
- 背景の絵を再着手の手がかりとして測った研究は 0 件。

### 1.3 リズムから生成する表現・自己写像（R2 → 衝突 C3・C8）

- 打鍵をリアルタイムに絵にする先行（KeyStrokes・EuroVis 2007）はあるが、本文は読めていない（未登録）。生体信号で動く表現（Heartscape・DeLight ほか）は要約だけ。
- 本人が表現を「自分の状態の計器」として読んだかを直接問うた一次は 0 件。表現を動かすために行動を変えた（ゲーム化）を測った研究も 0 件。
- 携帯の壁紙の花の庭（[P100]・既登録）は好意的に受け取られたが、目標の達成を花で表す設計で、状態を表さない肖像とは別物である。
- → 判断 5 の理由 2・台帳 T1（形が状態計として読まれる）について、文献は答えを持っていない。EH1 の型（合成の列で形と停滞の関係を検査する）で、リアルタイムの写像を先に検査するのが筋である。EH1 では、時計で更新する形でさえ、更新の数が無打鍵の量を写した（相関 0.90〜0.96・判断 12）。リアルタイムに追従すると、更新の数ではなく動きそのものが打鍵の有無と速さを写す。

## 2. 技術とスタック

### 2.1 Windows（T1 → 衝突 C6・C9）

- 方式: Progman に非公開のメッセージ `0x052C` を送り、WorkerW（または Progman）の子に自前の窓を置く（Lively Wallpaper のソースで確認・T1 の報告。行は概算）。Microsoft の公開文書は無い。
- 壊れやすさ:
  - Windows 11 24H2 で背景の窓の構造が変わり、Lively は中核を書き直した（[V284] 逐語 "Core components were fully rewritten to adapt to platform changes introduced in Windows 11 24H2."）。同版で再起動の繰り返しも直した。
  - 24H2 の配布の前に、Microsoft が壁紙をカスタマイズするアプリに互換性の保留をかけた（The Register 2025-04-14・二次）。Insider の版で窓が描かれない・窓の種類で可否が分かれる、の報告（Lively #2074・二次）。27XXX 以降でさらに変わる予告（メンテナ経由・二次）。
  - スリープの後にデスクトップが固まる（Lively #2178・未解決・二次）、アンチウイルスの誤検知（Lively wiki）。
- **画面の取り込みからの除外は、たぶん使えない**: [V283] は `SetWindowDisplayAffinity` の対象を "A handle to the top-level window" とし、子窓（non top-level）への呼び出しは FALSE を返すと書く。デスクトップの層に差し込む窓は Progman / WorkerW の子なので、この API の対象外になる見込みが高い（子にする前に付けた場合の振る舞いは文書に無く、未確認）。→ 引き継ぎ §3 の「ステージなら PC-8・E-13 の露出が下がるかもしれない」は、**Windows では見込みが薄い**。画面共有でステージがどう映るかは未確認（実機で確かめる項目）。
- 元へ戻すこと（R-P8）: ステージは本人の壁紙のファイルに触れないので、窓が消えれば元の壁紙が見える（推論）。Lively は別プロセスの watchdog が親の終了を待ち、子を止めてから `SPI_SETDESKWALLPAPER` で描き直す（[V285]）。→ 「元の壁紙を書き直す」型の問題は構造的に消えるが、代わりに OS の非公開の構造に依存し、explorer の再起動（`TaskbarCreated`）・WorkerW の破棄・表示の変更・スリープとロックへの追従が要る（Lively が全部に手当てを書いている）。
- 負荷: 一次の実測は見つからなかった。前例の方針は「全画面のアプリ・遠隔デスクトップ・電池駆動のときは止める」（Lively wiki）。

### 2.2 macOS（T2）

- デスクトップの層の窓（`kCGDesktopWindowLevel`）と `collectionBehavior`（`.canJoinAllSpaces` `.stationary`）は Apple の文書にある。アイコンの上下・Spaces・全画面・Stage Manager・複数ディスプレイでの実際の振る舞いは未確認（実機で確かめる項目）。
- 取り込みの除外（`sharingType = .none`）は、ScreenCaptureKit で効かない場合がある、という報告が Apple のフォーラムにあり、未解決（二次）。

### 2.3 描く手段（T1・T2）

- Tauri 2 には `set_always_on_bottom`（他の窓の下）・`set_ignore_cursor_events`・`set_content_protected` がある（docs.rs）。ただし「下」はデスクトップの層ではない。差し込むには生の窓のハンドルへの OS 依存の操作が要り、`input/` や `lib.rs` の `#[cfg]` の側に置くことになる（`architecture-rules`・推論）。
- WebView（WebView2 / WKWebView）は、窓が覆われると描画やタイマーを絞る仕組みを持つ（Chromium の遮蔽の追跡・WebKit・二次）。デスクトップの層の窓は常に他の窓に覆われているので、アニメーションが止まる可能性がある（WebView2 での実際は未確認）。Lively の web 壁紙は動いている（二次）。
- 別の描画（wgpu など）は今回は読んでいない。
- 打鍵との境界（設計の論点・T2 の列挙を整理）: フックのコールバックは今のまま Atomic と channel だけ。集計（例: 打鍵の間隔の滑らかな平均）は別スレッドで行い、描画には集計済みの数値の最新値だけを渡す。描画が遅れても欠けてよい（フックに背圧を返さない）。打鍵が止まっている間の減衰を描画側で時間から計算するか、集計側で行うかは論点（引き継ぎ §6 の「止まっている間に特徴量が据え置かれる」と関係する）。

### 2.4 Android（層 A・衝突 C10）

- [V286]: "It is very important that a wallpaper only use CPU while it is visible."。ライブ壁紙は持続アニメーションが置ける（ADR-022）。ただし ADR-022 D1 は、持続振動（A-7）を「iOS で成立せず、Android では画面点灯中のみ＝OS が表現と交絡する」として層 A の第 1 版から外している。
