# decisions

## D1: 層 2（再有効化）と層 3（作り直し）の**両方**を入れる

- **決定**: runloop timer で `CGEventTapIsEnabled` を見て再有効化し、それでも Down が続くなら
  `CFRunLoopStop` で既存の再作成経路を起こす。
- **理由**: ★ 2 つの機序（「tap が disable された」／「runloop が楽をしている」）は
  **別の手段でしか救えない**。⚠️ 2026-09-04 の実測ではどちらだったか**記録が無い**ので、
  片方だけ入れると外す可能性がある。
- **却下案**:
  - ⚠️ 再有効化だけ → **runloop 自体が楽をしていると timer も発火しない**ので手が無い。
  - ⚠️ 作り直しだけ → 毎回 2 秒の空白が出る（★ 軽い手段で済むなら済ませたい）。

## D2: 診断は `tracing` に出す（⚠️ NDJSON スキーマは変えない）

- **決定**: `tap_enabled` / `watchdog_recoveries` を Down のログ行にのみ載せる。
- **理由**: ★ `schema_dto.rs` を触ると `emit_schema` / `schema/current.json` / gse-dataset の
  parity まで波及する。⚠️ 診断 1 個に払う代償として大きい。
  ★ 研究者の機械では `gse-app.log` で「次の 1 回」が決着する。
- **却下案**: NDJSON の `hook_health` に列を足す → ⚠️ 被験者データにも残るが、
  ★ 必要になったら別 PR で足せる（⚠️ 今入れると本 PR の検証範囲が広がりすぎる）。

## D3: `request_reinstall()` は「出せなかった」を `false` で返し続ける

- **決定**: フック未起動 / run loop 未取得なら `false`。⚠️ `true` と偽らない。
- **理由**: ★ ログの `rehook_requested` は**研究者が機序を判断する唯一の手掛かり**である。
  ⚠️ 「呼んだ」を「効いた」と読ませると、2026-09-04 と同じ調査の空回りが起きる
  （memory `silent-success-is-not-visible`）。
- **却下案**: 呼べたら常に `true` → ⚠️ 何も起きていないのに緑に見える。

## D4: 上限 3 回で諦める

- **決定**: `MAX_REHOOK_ATTEMPTS_PER_EPISODE = 3`。
- **理由**: ⚠️ 上限が無いと 1Hz で `CFRunLoopStop` を叩き続ける。★ 1 回だと
  **今回のバグ（出せていないのに済みにする）を再現する**。
- ⚠️ **3 に出典は無い**（★ 恣意的である）。→ ★ 明記して、測った後に動かさない。

## D5: ⚠️★★★ CI では結合テストが **skip されている** —— 門を付けて可視化する

- **実測 (2026-09-05)**: PR #158 の mac self-hosted ジョブで `tests/macos_hook_rehook.rs` は
  **10.5 秒**で終わっていた。★ これは `wait_for_hook(true, 10s)` が空振りして skip した時間である
  (⚠️ 手元で実際に走らせると **12.2〜14.3 秒**)。
  → ★ **CI ランナーのプロセスに Input Monitoring が無い**ので、2 件とも何も検証していない。
- ⚠️★★ **しかも skip はログに残らない** —— `cargo test` は**成功した**テストの
  stdout/stderr を捨てる。→ ★ 「CI が緑」を「検証された」と読めてしまう
  (memory `silent-success-is-not-visible` と同型を、**自分のテストで作っていた**)。
- **決定**: `GSE_REQUIRE_HOOK_TESTS=1` を立てると **skip を失敗に変える**。
  ⚠️ 実機で検証するときは必ず付ける。
- **却下案**:
  - ⚠️ `ci.yml` で常に強制する → ★ CI ランナーの **TCC 状態に CI が依存する**ことになり、
    権限が外れた瞬間に無関係な赤が出る。
  - ⚠️ skip をやめて必ず失敗させる → ★ 権限の無い開発機で `cargo test` が常に赤になる。
- **⚠️ 残る限界**: ★ CI での「skip したこと」自体は**依然としてログに出ない**。
  → ⚠️ **CI 緑は層 2/層 3 の検証にならない**と、ここに書いて残すのが現状の答えである。


## ⚠️★★★ D5 の訂正（2026-09-06）—— **CI では実際に走るようになった**

★ D5 は「CI ランナーのプロセスに Input Monitoring が無いので 2 件とも skip される」と書いたが、
⚠️ **2026-09-06 に状況が変わった。**

| 実測 | ★ 読み |
|---|---|
| ⚠️ PR #162（**docs だけ**）で mac の check が **SIGSEGV** で落ちた | ★ **skip していたら落ちない** → **本当に走っていた** |
| ★ 修正後の run: 09:57:08.4 → 09:57:23.1 ＝ **14.7 秒** | ⚠️ skip の 10 秒待ちではなく、**手元の実測（12〜14 秒）と一致** |
| ★ `request_reinstall_actually_restarts_the_tap` が **2.7 秒** | ★ 再作成の **2 秒待ち**を含む本物の経路 |

→ ★ **層 2 / 層 3 は CI で実際に検証されている**（⚠️ D5 の「CI 緑は検証にならない」は**もう当てはまらない**）。

⚠️★★ **ただし門は残す。** ★ ランナーの TCC 権限は**外れうる**ので、
`GSE_REQUIRE_HOOK_TESTS=1` が無ければ**また黙って skip に戻る**。
→ ★ 「今は走っている」は**今の観測**であって、**保証ではない**。

## ⚠️★★★ D6: `init_hook` に多重起動の門を足した（2026-09-06）

- **決定**: `init_hook` を `bool` を返す門にし、2 回目は**何もせず `false`** を返す。
- **理由**: ⚠️ `hook_macos::start()` は無条件に `thread::spawn` するので、
  2 回呼ぶと **hook スレッドが 2 本**立ち、★ `TAP_PORT` の「同一スレッドで時間的に排他」が
  **破れる**（→ UAF → SIGSEGV）。⚠️ 本番の呼び出しは 1 か所だけだったが、
  **不変条件が「呼び出し規約」でしか守られていなかった**。
- ⚠️ **私のテストがその規約を破っていた** —— 2 件がそれぞれ `init_hook` を呼び、
  `cargo test` が既定で並列に走らせていた。
- **却下案**: テストだけ直す → ⚠️ ★ **不変条件がコードで守られないまま残る**。
