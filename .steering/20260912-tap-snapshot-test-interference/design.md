# design — テスト直列化

## 採る手: ★ **テスト専用の共有 `Mutex` で直列化する**

★ `hook.rs` (プラットフォーム非依存・両テストから届く) に `#[cfg(test)]` の門を置き、
**グローバル `TAP_ENABLED_SNAPSHOT` を読む/書く両方のテスト**が取る。

```rust
#[cfg(test)]
pub(crate) static TAP_SNAPSHOT_TEST_LOCK: std::sync::Mutex<()> = std::sync::Mutex::new(());
```

⚠️ **poison を握りつぶす**: `unwrap_or_else(|p| p.into_inner())`
(★ 片方が panic したら他方も落ちるのは**二重報告**で、原因が読みにくくなるため。
 本 repo の既存コード `lib.rs` の log ロックと同じ作法)。

## ⚠️ 却下した案

| 案 | ⚠️ 却下理由 |
|---|---|
| `serial_test` crate | ★ テスト 2 本のために**依存を増やす**。要件のスコープ外 |
| `--test-threads=1` | ⚠️ **他の 661 件の並列性まで殺す**。CI 時間に直撃 |
| `#[ignore]` | ⚠️★★★ **検査を消すのと同じ**。本 repo の方針 (緑で誤魔化さない) に反する |
| `tap_is_enabled` を純関数に割る | ★ 筋は良いが、⚠️ **公開 API の形を変える**ので影響範囲が広い。別途 |

## ⚠️ 置き場所の判断

★ `hook.rs` の `mod hook_macos;` は**私有**なので、`liveness.rs` から
`hook_macos` の中の static には届かない。→ ★ **門は `hook.rs` に置く**
(⚠️ 守る対象は macOS 固有だが、**取る側が両方から見える**必要がある)。

## テスト戦略

⚠️★★★ **「直したら緑になった」では足りない** —— ★ 元が間欠 (40 回中 7 回) なので、
**修正前後で同じ手順を同じ回数**回して比較する。

- 修正前: **7 / 40 失敗** (実測済み)
- 修正後: **0 / 40** を要求する
