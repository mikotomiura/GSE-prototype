前提として、`docs/portrait-eh3-prereg`（PR #348）が main に merge 済み（`36a1ef0f`）であることを確かめた。
worktree は `C:\wt\portrait-eh3-impl`（`feature/portrait-eh3-impl`・`origin/main` から）。

| # | 問い | 決定 |
|---|---|---|
| 1 | R-1: ADR-035 D1 の内側の制約 ④ と「Nudge を出さず招待だけ」の両立 | **(i) 条件を分けて持つ**。`session_meta` に招待用の研究の条件を別に持つ（EH3 では 招待＝有効・Nudge＝無効）。④ の「研究の条件」を招待の条件として読み、ADR-035 を見直すときに注記する（本文は書き換えない） |
| 2 | R-8: EH3 への参加の同意を「Physical Anchor に opt-in した」とみなすか | **みなす**。別の opt-in は置かない。参加者は全員、有無と時期の範囲をいつでも変えられる（D1）。同意文書に「いつでも止められる」と書く |
| 3 | R-5: 明示の応答を置かないので ADR-033 の「実施時の新 ADR」に当たらないと読むか | **当たらないと読む**。ADR は判断 1 #4（前タスク）のとおり EH3 の後 |

- **推奨の理由（要点）**:
  - #1: (ii) では記録上 `intervention_enabled` が真なのに Nudge が 1 回も出ず、解析で Nudge の条件と招待の条件を取り違える。条件が 2 つとも記録に残るほうが読み違えにくい。
  - #2: 別の opt-in を置くと、opt-in しなかった人は招待の条件を経験せず、前タスク判断 1 #1（両方を測る）が人によって欠ける。
  - #4: R-2・R-7・R-9 の判断が層をまたいで絡むので、issue に切ってループで回すと issue の外の前提が増える。

## 判断 2（2026-10-11・研究者・AskUserQuestion 1 回・2 問・すべて推奨どおり）: 招待の面と日の数え方

| # | 問い | 決定 |
|---|---|---|
| 1 | 招待の PC 面をどこに出すか | **既存の overlay 窓に小図像**。文字の無い固定の大きさの図像を 1 つ、画面の角に出す。押すと説明と設定の窓が開く（その操作は応答として記録しない）。画面共有からは OS の受動的除外（Windows `WDA_EXCLUDEFROMCAPTURE`・macOS `sharingType = none`）で外す。図像の形は後で見本を並べて研究者が選ぶ |
| 2 | 3 ブロック × 5 稼働日の「日」の数え方（R-7 の一部） | **使った日を数える**。現地時刻で早朝 4:00 を区切りとし、打鍵を観測した日を 1 稼働日と数え、5 日たまったら次のブロックへ。条件はその日の最初の起動で決まり、日中は変わらない。曜日の判定は置かない（土日に使えばその日も数える。稿に書く） |

- **推奨の理由（要点）**:
  - #1: 窓の仕組み（クリック透過・画面外への退避）が両 OS で既に動いており、PC-12 を窓の状態で検査できる。トレイは通知領域が隠れていることが多く、招待を経験しない人が出やすい（M-2〜M-4 が測れない）。
  - #2: 休暇や病欠で各条件の曝露が 5 日を割らない。
- **却下案**: タスクトレイのアイコン／専用の小窓／暦の平日で数える。
- **残る点**: 「4:00 区切り」と「打鍵を観測した日」の閾値（打鍵 1 回で足りるか）は design で決める。PC-7（縁に置けば安全とは言えない）により、角に置くことを安全の根拠にしない。

## 判断 3（2026-10-11・研究者・AskUserQuestion 1 回・3 問・すべて推奨どおり）: 収集の器・肖像の終わり・ESM

Step B の調査（file-finder・impact-analyzer）の後に聞いた。一次で確かめた前提: O1 の `o1_mode` は `session_meta` ではなく `meta`（session_start）行にあり、O1 は `session_meta` を書かない（`lib.rs:2434` が拒否）。`is_o1()`/`o1::mode()` は `lib.rs` に 26 箇所。スリープ・ロックの検出は src に 0 件。

| # | 問い | 決定 |
|---|---|---|
| 1 | EH3 の収集の器 | **O1 の器に EH3 の層を載せる**。EH3 の配布物は O1 の収集で動き、`meta` 行に `eh3_mode` と招待の条件を足す。分けるのは配布タグ・参加者 ID の名前空間・sync の振り分け（`eh3_mode` で別のフォルダへ）。O1 の ESM（`activity_label`）は EH3 では切る |
| 2 | 肖像の「終わり」（R-7） | **終了・スリープ・日付の区切り**。アプリ（PC）の終了、OS のスリープの直前の通知、早朝 4:00 の日付の区切りを「終わり」、次の起動・復帰を「始まり」（地から）にする。ロックだけでは区切らない |
| 3 | ESM と日誌（R-6・F-7） | **アプリの外（フォーム）**。アプリに通知の経路を作らない |

- **帰結**:
  - #1 により、判断 1 #1 の「`session_meta` に招待用の研究の条件を持つ」は、`meta` 行に持つ形で実装する（O1 は `session_meta` を書かないため。条件を分けて記録に残すという中身は変えない）。
  - #2 により、昼のスリープでも 1 日に複数の終わりができる（稿に書く）。スリープの直前の通知の OS API を両 OS に足す（`input/` か OS 依存の層）。
  - #3 により、R-6 は「アプリに ESM の通知は無い」で閉じる。
- **却下案**: 独立したモード／終了・長い不在（30 分）・日付の区切り／日付の区切りだけ／アプリの中で ESM を取る。
