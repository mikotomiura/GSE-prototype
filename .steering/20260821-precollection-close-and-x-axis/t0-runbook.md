# T-0 陽性対照ランブック — `starve_window` を実機で 1 回発火させる

## ★ 何を確かめるか (★ 目的を取り違えない)

⚠️★★★ **`starve_window` の実発火は依然として未観測**である
(`20260819-g1-reboot-and-instrument-fix/code-review.md` の最後の 1 行)。

`starve_window` は `capabilities.threshold_gated` に属するので、
★ **0 行は「判定不能」としか読めない** —— つまり**計器が壊れていても気づけない**。
→ ⚠️ **一度も発火を見ないまま収集を始めると、新コホートで 0 行だったときに何も言えない。**

★ したがって本ランブックが検証するのは**純関数ではなく配線**である:

```
フック → CALLBACK_COUNT → liveness::step → MicroStarveWindow::tick
  → LogEntry::StarveWindow → logger → NDJSON の 1 行
```

⚠️ 単体テストはこの鎖の**両端**を検証していない。だから実機で 1 回取る。

## ★ 発火条件 (★ 実装から導いた。推測ではない)

`liveness::step` (`src-tauri/src/input/liveness.rs`) は次で動く:

| 条件 | `starved_ms` |
|---|---|
| `!session_active` または **フックが呼ばれた** | **0 にリセット** |
| **システム入力が無い** (マウスもキーも触っていない) | ★ **凍結** (進まない) |
| システム入力あり **かつ** フック未呼び出し | ★ `+= tick_ms` |

→ ★ **「マウスは動かすが打鍵しない」時間だけが積算される。**

`MicroStarveWindow::tick` は `now == 0 && 0 < prev < 30_000` の tick を
**1 エピソード**として数え、60 秒窓が閉じたときに `n_lt30 >= 1` なら 1 行出す。

## ★ 手順

### 1. アプリを G1 モードで起動する

⚠️ **git-bash ではなく PowerShell** で (Tauri の dev サーバを立てるため):

```powershell
cd C:\GSE-prototype
$env:GSE_G1_MODE = "1"
npm run tauri dev
```

★ 画面に G1 のスタート画面 (参加者 ID 欄) が出れば G1 モードで立っている。
⚠️ **出なければ G1 モードではない** —— `meta` 行が「G1 でない」と告げるので、
そのまま進めても T-0 の陽性対照としては弱い (★ 機構自体は通常運用でも同じだが、
本番と同じ経路で確かめる意味が薄れる)。

### 2. 参加者 ID を入れて「開始する」を押す

★ `P999`（テスト用）を使う。⚠️ **`P015` は使わない**
（提出経路テストの副作用で本番ロスターに実採番済み・焼けた扱い）。

### 3. ★ 陽性対照の操作 (★ 合計 2 分弱)

| # | 何をするか | 秒 |
|---|---|---|
| 1 | ふつうに打鍵する | 〜10 |
| 2 | ★ **打鍵をやめ、マウスだけを動かし続ける** | 〜5 |
| 3 | ★ **キーを 1 つ打つ** (ここでエピソードが閉じる) | — |
| 4 | ★ **2〜3 を、間を空けずに 5 回**繰り返す | 〜40 |
| 5 | ⚠️ **窓が閉じるまで待つ** (通算 60 秒を越えるまで打鍵とマウスを続ける) | 〜70 |

⚠️★★ **注意点**:

- ★ **マウスは「動かし続ける」** —— 1 秒 tick ごとに `GetLastInputInfo` の値が
  変わっていないと starvation が**凍結**して積算されない。小さく円を描き続けるのがよい。
- ⚠️ **1 Hz サンプリングなので 1 秒未満のエピソードは原理的に見えない** (所見 B)。
  → ★ **マウスのみの区間は最低 3〜5 秒**取る。
- ⚠️ **30 秒を越えさせない** —— 越えると `hook_health` (Suspect) 側に移り、
  `starve_window` は**数えない** (2 トラックは閾値できれいに分割される)。
- ★ 窓は**セッション開始から** 60 秒ではなく、`elapsed_ms` の累積が 60 秒に達したとき閉じる。
  → 5) は必ず入れる。**窓が閉じないと 1 行も出ない。**

### 4. ★ アプリを終了する

⚠️ **5 分のブロック自動終了を待たない** (待つと自動提出まで走る)。
★ 90 秒ほど経ったらウィンドウを閉じる。→ `session_end` の無いファイルが残るが、
本件は陽性対照なので問題ない (⚠️ **提出しない**)。

### 5. ★ 値だけを取り出す

```powershell
# 最新のセッションファイルを探す
Get-ChildItem "$env:USERPROFILE\Documents\GSE-sessions\*.ndjson" |
  Sort-Object LastWriteTime -Descending | Select-Object -First 3 Name, LastWriteTime
```

```bash

PYTHONUTF8=1 python "<scratchpad>/t0_extract.py" "<最新の .ndjson>"
```

⚠️★★★ **生 NDJSON を repo に置かない。** ★ 上の出力の**値だけ**を
`t0-result.md` に転記する (`data-privacy`)。

## ★ 受け入れ条件

- [ ] NDJSON に `{"type":"starve_window",...}` が **1 行以上**出た
- [ ] `n_lt30` が繰り返した回数 (5 回) とおおむね一致する
      (⚠️ **下側に偏る**のは仕様・所見 B。3〜5 なら合格)
- [ ] `win_ms` が **60000 前後** (★ 公称ではなく実測値が載る。60000〜62000 程度)
- [ ] ⚠️ `hook_health` の意味論が変わっていない
      (★ 30 秒を越えていないので **0 行が正しい**。出ていたら 30 秒を越えている)
- [ ] ⚠️ `meta.capabilities.threshold_gated` に `starve_window` が入っている
      (★ ADR-013 の宣言が実ビルドに載っていることの確認も兼ねる)

## ⚠️★ 発火しなかった場合

★ **「実装を疑う」側に倒す。** 手順を変えて再試行する:

1. マウスのみ区間を **8 秒**に伸ばす (1 Hz の取りこぼしを潰す)
2. 繰り返しを **8 回**に増やす
3. 窓を確実に閉じるため **合計 90 秒**動かし続ける

★ それでも出なければ **T-1 より先に原因を特定する**
(⚠️ 収集を始めてからでは `§3.6` により直せない)。

★ 切り分けの順序:

| 見るもの | 何が分かるか |
|---|---|
| `meta.capabilities` に `starve_window` があるか | ⚠️ 無ければ**古いビルドで走っている** |
| `key` 行が出ているか | ⚠️ 0 なら**フックが死んでいる** (T-0 以前の問題) |
| `hook_health` 行が出ているか | ★ 出ていれば starvation は積算されている = **窓側の問題** |
| `feat` 行の数 | ★ セッションが本当に active だったか (1 Hz なので秒数と一致するはず) |
