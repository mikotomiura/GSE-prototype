## ⚠️★★ N-1: `realtime_label` は G1 でも止まらない (★ `CONFIG_GATED` の説明が過大)

### ★ 実測 (推測ではない・T-0 のログ)

`meta.g1_mode = "marker"` の G1 セッションに **`realtime_label` が 1 行**出た:

```
{"type":"realtime_label","probe_id":null,"source":"self_marker",
 "q1_friction":5,"q2_progress":1,"answered":true,"skip_reason":"none","latency_ms":0, ...}
```

### ★ 何が食い違っているか

`src-tauri/src/capabilities.rs` の `CONFIG_GATED` は `realtime_label` を載せ、理由に
**「G1 実施中は常に止まる」**（`probes_disabled = disabled_by_env || disabled_by_g1.is_some()`）
と書いている。

⚠️ しかし `realtime_label` の送出元は **2 つ**ある:

| 送出元 | 場所 | G1 で止まるか |
|---|---|---|
| ランダムプローブ (`source: "random_probe"`) | `lib.rs` の `if !probes_disabled` 内 | ★ **止まる** |
| ⚠️ **自己マーカー** (`source: "self_marker"`) | `lib.rs:1838 record_self_marker_inner`（Dashboard ボタン / **D ホットキー**） | ⚠️★★★ **止まらない** |

### ⚠️ 実害の向き (★ 安全側である)

★ **`config_gated` に入れているのは「判定不能」と読ませる宣言**である。
実際には self-marker 経路が生きているので、0 行は本当は
「**参加者が一度も自己申告しなかった**」という**情報**でありうる。

→ ★ **情報を捨てている (過小申告) のであって、ADR-013 が潰そうとした
「計器が無いのを信号が無いに化けさせる (過大申告)」の向きではない。**
⚠️ 危険な向きの誤りではない。

### ⚠️★★★ なぜ直さないか

1. ★ **1 行で終わらない。** `realtime_label` は**送出元ごとに群が違う**ので、
   既存の 3 群のどれに入れても正しくない。⚠️ 直すには
   「**行種**ごとの宣言」を「**行種 × source**ごとの宣言」に広げる必要があり、
   ★ これは `meta` 行の**形を変える構造変更**である。
2. ⚠️★★★ **`meta` の `capabilities` は記録仕様である。** 収集開始前に変えるなら
   schema parity・`emit_schema`・`gse-dataset` 側まで波及する。
   研究者決定 #2「T-0 / T-1 で打ち止め」の線を明確に越える。
3. ★ **結論が動かない。** 上記のとおり誤りの向きが安全側なので、
   G1 の判定にも ADR-012 Stage 0 の投資判断にも影響しない。

### ★ 収集後に拾うときの入口

- 直す場合の最小案: `CONFIG_GATED` の doc コメントに
  「⚠️ `realtime_label` は **`source: "random_probe"` のみ** config_gated」と**書き足す**
  （宣言の形は変えず、読み手の誤読だけを潰す）。
- 本格的に直す場合: 群を「行種 × source」へ広げる ＝ ADR-013 の D1 改訂が要る。

## ⚠️ N-2: セッションファイル名は **UTC**、`t` は epoch (★ 9 時間ずれて見える)

### ★ 実測

T-0 のファイルは `gse_20260820_183006.ndjson` だが、
中身の `session_start` は **2026-08-21 03:30:35 (JST)** である。

### ★ 仕様である (不具合ではない)

`logger.rs:2151 chrono_like_filename()` に逐語で
「**注: 簡易実装のためタイムゾーンは UTC**」と書いてある。

### ⚠️ ただし読み手が転ぶ

★ JST の 00:00〜09:00 に始まったブロックは、**ファイル名だけ前日**になる。
⚠️ 日付でブロックを突き合わせる解析は**ファイル名ではなく `t` を見る**こと。

### ⚠️ なぜ直さないか

★ ファイル名は**識別子であって時刻の記録ではない**（`t` が記録である）。
⚠️ いま名前の規則を変えると、既存 63 ファイル + P010 の並び方と混ざる。
→ ★ **収集開始前に触る価値が無い。** T-2 の解析規約に「`t` を見よ」と書けば足りる。

## ⚠️★★ N-3: `start_session` は同期コマンドなので、最大 1500 ms メインスレッドが止まりうる

### ★ 実測に基づく指摘 (security-checker MEDIUM・2026-08-21)

`src-tauri/src/lib.rs` の `start_session` は `async` でも `#[tauri::command(async)]` でもない。
→ ★ **メインスレッド（イベントループ）上で走る。**

⚠️ 本タスクで足した `lock_block_transition()` が、自動終了スレッドの臨界区間
（`ANALYSIS_IDLE` 待ち・deadline **1500 ms**）と競合すると、**その分イベントループが止まる**
→ ★ Windows で「応答なし」表示になりうる。

⚠️ repo 自身の基準はこれと逆向きである —— `lib.rs` の `gse-submit` 周りには逐語で
「**数百 ms 以上かかり得るため** `async` + `spawn_blocking` で
**IPC/メインスレッド（overlay 制御等のイベントループ）を塞がない**」と書いてある。

### ★ データ欠落は起きない (⚠️ ここは確認済み)

キーボードフックは `input/hook_windows.rs` で**専用スレッド + 自前 `PeekMessageW` ループ**を
回しており、★ **メインスレッドの停止と無関係**である
（⚠️ `LowLevelHooksTimeout` によるフック剥がれの経路にはならない）。

### ⚠️★★★ なぜ直さないか

1. ★ **排他そのものは正しい。** 外すと本タスクが閉じた HIGH 相当の破損が戻る。
2. ⚠️★★★ **`async` 化は通常運用のスレッド挙動を変える。**
   `start_session` は G1 でも通常運用でも通る経路であり、
   ★ 研究者決定 #2「**通常運用の挙動を 1 バイトも変えない**」の線を明確に越える。
3. ★ **起きるのはブロック境界だけ**で、しかも待ちは**有界 (≤ 約 1.5 秒)** である。
   ⚠️ その待ちは「押下を待たせている」のではなく「**押下が壊れないように待たせている**」。

### ★ 収集後に拾うときの入口（★ 安価な順）

- **UI 側**: 押下直後にスピナー / ボタン無効化を出す（⚠️ backend を触らない）
- **backend**: `try_lock` で取れなければ「準備中です」を返す（★ 体感だけを殺す）
- **本格対応**: `start_session` を `async` + `spawn_blocking` にする
  （⚠️ 通常運用の非回帰確認が要る ＝ 収集の後）
