# 設計（Claude の作業）

研究者の判断は decisions.md にある。ここには見本の作り方と、確かめの方法・結果を置く。

## 実物へ持ち込む前の確かめ

### 前提: 背景の窓はマウスを受けない

背景の層の試作（`spike/handmark-stage` の `src-tauri/src/handmark_stage_spike.rs` 冒頭）は、窓がマウスを受けない作りになっている（背後のデスクトップのクリックを奪わないため）。そのため、窓の中の WebView がマウスのイベントを受け取る形は取れない。実物では、Rust の側で入力を読み、表現の窓へ渡す形になる。

### 1. カーソルの位置（macOS）: 権限なしで読める（実測）

- 方法: 権限を持たない ad-hoc 署名の .app（`LSUIElement`・`open -n` で起動し、Claude Code の端末の権限を引き継がない）が、`NSEvent.mouseLocation` を 0.1 秒ごとに 12 秒読む。別のプロセスから `CGWarpMouseCursorPosition` でカーソルを 3 か所へ 2 秒ずつ置き、最後に元へ戻した。
- 権限の状態（.app の中で読んだもの）: `AXIsProcessTrusted()=false`、`CGPreflightListenEventAccess()=false`、`CGPreflightPostEventAccess()=false`。
- 結果: 値が置いた位置を追った（陽性対照）。(200, 200) → y=756、(600, 300) → y=656、(400, 500) → y=456。戻した後は元の位置。y は Cocoa の座標（下が 0）で、主画面の高さ 956 から引いた値になっている。
- 環境: macOS 27.0.1（26A434）、MacBook Air。
- 試しのプログラム: 作業用の Swift（保存していない）。読んだ API・間隔・置いた座標は上のとおり。
- 分かったこと: カーソルの位置には、イベントを取る仕組み（CGEventTap）も TCC の許可も要らない。描画のたびに一点を読むだけで、列を持たずに済む。v3-grading 判断 8 の条件 4 に残っていた「macOS の権限の扱いはまだ確かめていない」は、位置とクリックについてはこれで答えが出た（ホイールは 2 のとおり未確認）。

### 2. クリックとホイール（macOS）

- 方法: 1 と同じ形の権限を持たない .app（`probe2.swift`）が 20 秒動く。(a) `NSEvent.pressedMouseButtons` を 50ms ごとに読み、0 から 0 でない値へ変わった回数を数える。(b) 聞くだけの CGEventTap（`leftMouseDown`・`rightMouseDown`・`scrollWheel`）を作り、届いた数を数える。その間に研究者がデスクトップの空いたところを 3 回クリックした（研究者の実地の操作・2026-10-20）。スクロールは行っていない（研究者に確かめた）。
- 権限の状態: `AXIsProcessTrusted()=false`、`CGPreflightListenEventAccess()=false`。
- 結果:
  - (a) 3 回とも数えた（4.05 秒・10.65 秒・18.25 秒）。
  - (b) tap は作れたが、終わりの時点で無効（`tapIsEnabled=false`）。押下 0 件。いつ無効になったかは見ていない。権限を与えた同じプログラムで届くことを確かめる対照は取っていないので、0 件が権限のせいか、試しのプログラムの不備（run loop・マスク・tap の生存期間）のせいかは分けられない。権限がないと届かないというのは見込みにとどまる。ホイール 0 件はスクロールをしていないので陰性ではない（未確認）。
- 分かったこと:
  - クリックは、権限なしで、押されているボタンを繰り返し読む方法で取れる。いまの O1 の取り方（ADR-014 D4 の mac 側のマスク）を広げずに済む。
  - ホイールには繰り返し読む方法がない。macOS では tap が要り、権限なしでは届かない見込み（押下もホイールも、権限ありの対照を取っていないので見込み）。GSE の本体は打鍵の tap のために許可を持っているが、実物でホイールを使うと、表現の側にもイベントを取る仕組みが入る。
- 限界: 50ms ごとの読みは、50ms より短い押下を取りこぼしうる（トラックパッドのタップでのクリックは短い）。今回の 3 回は取れたが、取りこぼしの率は測っていない。描画の速さ（30〜60 回/秒）で読めば 17〜33ms になる。

### 2b. Windows

- 位置: `GetCursorPos`。クリック: `GetAsyncKeyState(VK_LBUTTON)` などを描画のたびに読む。どちらもフックを使わない。実測はしていない（Mac だけで完結するタスクのため）。
- ホイール: 繰り返し読む方法がない。Raw Input はすでに O1 の `observe_windows.rs` が使っており、Raw Input の受け先は 1 つのプロセスで装置の種類ごとに 1 つの窓なので、表現の側で別に登録すると O1 の受け先を奪う（Microsoft の一次資料の逐語「Only one window per raw input device class may be registered to receive raw input within a process」。`.steering/20260821-workspace-behavior-triage/survey-input-channels.md:342` に引用がある）。O1 の処理から分けて受け取るなら、記録の経路と表現の経路が同じ場所を通ることになり、条件 1 と最もぶつかる。
- まとめ: 位置とクリックは両 OS とも、権限もフックも要らない読み方がある。ホイールは両 OS とも、イベントを取る仕組みを表現の側にも持たせることになる。

### 3. 表現用の値をロガーへ渡さない形（条件 1）

型・境界・振る舞いの 3 層で作る（研究者の判断 9）。壁紙の層の前例（`src-tauri/src/wallpaper.rs:1000` の `person_operations_leave_no_trace_in_the_applog` と `:1013` の `the_wallpaper_layer_cannot_write_records`・R-P9）に倣う。

- 型: 表現の入力の型には `serde::Serialize` も `Debug` も付けない。窓へは専用の関数で、描画に要る値だけを渡す。記録の型 `LogEntry` は `Serialize` を derive しているので、表現の入力の型をそのフィールドに入れるとコンパイルが通らない。`tracing` の `{:?}` でも出せない。型で止められないのは、値をふつうの数（`f64` など）に取り出した後の漏れで、これは次の 2 層で補う（Codex の指摘）。
- 境界: 表現の入力を読むコードを、記録の側と別のモジュールに置く（例: `handmark_input.rs` と OS ごとのファイル）。O1 の `input/observe*.rs` と `analysis/pointer_bin.rs` には手を入れない。
  - テスト 1（構造）: そのモジュールのソース（テストの部分とコメントを除く）が `LogEntry`・`tracing::`・`log_tx`・`POINTER_TX` を含まない。対照として、記録する側のファイル（`lib.rs`）では見つかることも確かめる（R-P9 と同じ）。
  - テスト 2（逆向き）: `logger.rs`・`schema_dto.rs`・`submission.rs` が表現の入力の型の名前を含まない。
  - テスト 3（溜めない・条件 2）: そのモジュールは最後の一点だけを持ち、列を持たない。表現の窓の側は、受け取った値を保存も返送もしない。ソースの文字列検査は、`Vec<`・`VecDeque` だけでは固定長の配列・`HashMap`・リングバッファを通し、TS 側も `localStorage` だけでは `sessionStorage`・IndexedDB・`fetch`・`invoke` を通す。どの語を見るかは実物のタスクで詰める。文字列検査は別名の関数を経由した漏れを見つけられないので、補助として扱う。
- 振る舞い: 入力を与えて表現の側を回し、記録（NDJSON の行・applog）が 1 行も増えないことをテストする（壁紙の層の `person_operations_leave_no_trace_in_the_applog` と同じ形。陽性対照として、わざと記録する版では増えることも見る）。
- 陽性対照: 文字列検査はそれぞれ、検査する文字列を一時的に足した版で赤になることを確かめる（実行時に文字列を組み立てて、対照の文字列を検査対象のファイルに書かない。gate-green-but-artifact-broken の 4 型目）。

### 4. ADR で明示するか

ADR-014 D4 の「入れないもの」の表は、絶対座標を名指ししている（`docs/adr/ADR-014-continuous-natural-work-collection.md` の表）。D4 は O1 の収集の決まりで、表現の側のことは決めていないが、表現の側のコードが絶対座標を読むのを見た人には、D4 に反するように見える。研究者の判断 7 で、実物へ持ち込む前に「表現には使うが記録しない」とその境界（3 の 3 層）を ADR で明示することになった。起票はこのタスクの外（判断 5）。

## 見本

- ファイル: `handmark-nature-multi.html`（版 4 の `20261017-handmark-why-interesting/handmark-nature.html` は触らない）。公開: https://claude.ai/artifact/4FCokjbqZd13PXgVw2MkSg （Version 2 で `/cross-review` の指摘を直した）。
- 版 4 から版 3（自然世界）だけを残し、伏せた見比べの欄と動く量の表示（数値）を外した。打鍵の写し方・基層・霧は版 4 と同じ（強さ 1・判断 8）。打鍵の既定は「止める」にし、本人の入力だけを見られるようにした。
- 写し方（判断 2）:
  - カーソル: 描画のたびに位置を 1 点だけ読み、前の点との差から横の速さを出す（実物で描画のたびに位置を読む形と合わせた）。草の中ほどからの距離が画面の高さの 0.16 倍より近い草だけを、近さの 2 乗の重みで速さの向きへ押す。押しは 0.7 秒で半分に減る。カーソルの跡は描かない。
  - クリック: 押した点から 2 重の輪が広がり 1.6 秒で消える。枠は 6 つで、古いものから上書きする（数が増えない）。作業の窓を重ねたときは窓の下に描く（背景の層なので）。
  - ホイール: 1 回ごとに粒全体の描く位置を縦にずらす（下へ回すと上へ）。ずれは 1 秒で半分に戻る。粒そのものの位置は変えない。舞台の上では、ホイールを切っていてもページをスクロールさせない（入れ切りで舞台のふるまいを変えない）。画素単位は 100 で 1 回ぶんとし ±1 で頭打ちにする。行・ページ単位（`deltaMode` 1・2）は 1 回ぶんにそろえる。
  - クリックは左ボタンだけを使う（右クリックでメニューが出るため）。実物の `pressedMouseButtons` はどのボタンも数えるので、実物でどうするかは持ち込むときに決める。
  - 入力を切ると、その入力の跡（草の押し・波紋・粒のずれ）はすぐ消える。入れ直したときに前の跡は出ない。
  - 「動きを減らす」設定（`prefers-reduced-motion`）では、基層の漂いと粒の流れだけを 0.3 倍にする。跡の減衰と波紋は実時間のまま（`/cross-review` で両者が指摘した: 初版は縮めた dt で減衰させ、草の戻りの半減期が約 2.3 秒に延びていた）。霧も基層なので 0.3 倍になる（入力ではない）。
- 入力ごとに入れたり切ったりできる欄を付けた（判断 8）。
- 確かめ用に、URL に `?probe` を付けたときだけ状態の数を返す口（`window.__probe`）を置いた。溜めない・送らない。返す値に打鍵の時刻の数（`presses`・直近 30 秒ぶん）を含む。

### 確かめ（2026-10-20・`http://127.0.0.1` で配信した Chrome。公開した URL では開いただけ）

7 項目のうち、6 項目は画面（状態の数とスクリーンショット）で、1 項目（4 の霧）はコードの読みで確かめた。合成と書いたものはページの中に JS で入れたイベント、「OS 経由の合成」は拡張機能の `computer` で OS へ入れたイベントで、どちらも人の手の操作ではない。

1. カーソル: 草の帯を左から右へ動かす（合成の pointermove）と、近くの草の押しの最大が 0.74。止めて 1.5 秒で 0.17、4 秒で 0.014 に戻った。対照として霧の帯で動かすと、近くの草の押しは 0（草が無い所では何も動かない）。スクリーンショットでも、動かした帯の草だけが右へ傾いた。
2. クリック: 合成で 8 回押すと、生きている波紋は 6（枠の数）。1.75 秒後に 0。スクリーンショットで輪が見えた。OS 経由の合成のクリック（`computer left_click`）でも 1 つ立った。
3. ホイール: 合成で 5 回回すと粒のずれは画面の高さの -0.11、3.8 秒後に -0.012。OS 経由の合成のホイール（`computer scroll`）でも -0.023 動き、ページはスクロールしなかった。
4. 霧: 描く関数（`fogEdge`）が基層の時間 `drift` だけを使い、入力の値を受け取らないことをコードで確かめた（画面の差では確かめていない）。`drift` は「動きを減らす」設定で遅くなるが、これは入力ではない。
5. 数: どの操作の後も草 270・粒 140・波紋の枠 6 のまま。
6. 数値: 入力から出た数（打った数・動かした量・押した回数）を表示する所は無い。ページにある数字は説明の文の定数（0.16 倍・1.6 秒・幅 1440 など）だけ。
7. 対照（切ると効かない）: カーソル・クリック・ホイールを切って同じ操作をすると、押し 0・波紋 0・ずれは前の残りが減っていくだけだった。

試していないもの: 人の手で動かしたカーソル・クリック・ホイール（研究者が見る段）、OS 経由の合成のカーソルの動き（hover）、「動きを減らす」設定のまま跡の戻りを測ること、研究者の目での見え方（主体感・騒がしさ）、スマホの幅、暗い壁紙・幅 3840 での見え方。

### 直した後の確かめ（2026-10-20・`/cross-review` 1 巡目の直しの後・同じ配信の形）

- カーソルの戻り: 押し 0.73 → 1.5 秒後 0.17（直す前と同じ）。切ると押しは即 0。
- クリック: 右ボタン（`button: 2`）では立たず、左ボタンで 1 つ立つ。切ると生きている波紋は即 0、入れ直しても戻らない。
- ホイール: 行単位（`deltaMode: 1`・`deltaY: 3`）も 1 回ぶんとして粒がずれた（-0.038）。切るとずれは即 0。切っていても `defaultPrevented=true`（舞台の上でページはスクロールしない）。
- 「動きを減らす」: OS の設定はブラウザから切り替えられないので、コードで確かめた。草の押しの減衰（`decay`）は実時間の `dt` を使い、0.3 倍は基層の時間と粒の流れ（`mdt`）にだけ掛かる。設定を入れた画面では確かめていない。
- 出し直し: Version 2。

### カーソルで近くの粒も押す（判断 10）

- 写し方: カーソルの速さを縦横とも出し（前の点と今の点の差だけ）、カーソルから画面の高さの 0.14 倍より近い粒だけを、近さの 2 乗の重みで動いた向きへ押す。粒そのものの位置は変えず、描く位置のずれ（`ox`・`oy`）だけを持つ。ずれは実時間で 0.9 秒ごとに半分に戻り、大きさは画面の高さの 6% で頭打ち。
- 入れ切り: 「カーソルで近くの粒も押す」の欄（カーソルの欄の下）。カーソルの欄を切ると粒も止まる。どちらかを切ると、ずれはすぐ 0 に戻る。
- 確かめ（2026-10-20・`http://127.0.0.1` で配信した Chrome・合成の pointermove）:
  - 霧と粒の帯（舞台の上から 35〜44%）で斜めに動かすと、粒 140 のうち 11 が動き、ずれの最大は画面の高さの 2.1%。1 秒後 1.0%、4 秒後 0.1%。草の押しは 0（草の近くではない）。
  - 対照: 粒の欄だけを切って同じ操作をすると、ずれ 0・動いた粒 0。カーソルの欄を切っても 0。
  - 粒の数は 140 のまま。
  - 見え方: 拡大したスクリーンショットでは、ずれた粒を見分けられなかった。ずれは舞台の上で約 14 CSS px と小さく、撮るまでの間にほぼ戻っていた。押しが弱すぎるかは、動く画面を研究者が見て決める。
- 出し直し: Version 3。
