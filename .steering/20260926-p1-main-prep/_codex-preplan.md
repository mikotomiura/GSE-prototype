## Codex の応答（原文）

提示された資料だけを使い、共有状態・ゲート保証・fold 境界を中心に、優先度順で盲点を整理します。
1. **HIGH｜004・006：PG-1 宣言の保存先が矛盾。**「凍結 JSON は変更禁止」と「新版 JSON に下限を追加」の関係が未定義です。別の宣言ファイルに下限・対象集団・凍結 JSON のハッシュ・分布集計のハッシュを記録する案を検討してください。値の存在だけでなく、型・範囲・対象データとの一致を検証し、不成立なら replay 呼び出しゼロを保証すべきです。

2. **HIGH｜002：射影と拒否条件が接続していない。** `project_pg1` は `overrides` を返さないため、射影だけを使う集計器では非空を拒否できません。読み込み層で検証してから射影する契約が必要です。「onset 以外の改変で byte 同一」は、必須メタデータ検証との区別を明記してください。ソースの禁止語 grep だけでは、別関数経由の転帰参照を防げません。

3. **HIGH｜003：列名検査では retrospective 情報を遮断できない。**「各 Tier を JSON 列」にすると、`stall_onset.ime_overlap` が JSON 内に残る可能性があります。t0 表は許可フィールドから再構成し、再帰的に漏洩を検査する AC が必要です。将来追加される未知フィールドも自動取り込みしない設計が安全です。

4. **HIGH｜005：N=2 とゼロ episode 参加者が未定義。** N=2 では inner k=1 となり、通常の k-fold が成立しません。また episode から参加者を列挙すると、ゼロ件の人が消えて最小件数と ≥L 判定が楽観化します。参加者母集団を sessions から固定し、全 config・極で同じ fold を使うこと、空 fold・全件除外・非適用の扱いを決めてください。

5. **HIGH｜004→005：除外 manifest の信頼境界が弱い。** 実行後に記録するだけでは、不完全出力や後から追加・変更された封筒を選択器が読む危険があります。成功 manifest を最後に確定し、005 は列挙された検証済み成果物だけを読む方式を検討してください。重複 `--set`、欠損極、途中失敗、`0.990` のような等価な q 表記も AC に追加できます。

6. **HIGH｜W2・008：ファイル非交差でも振る舞いは依存。** 002 の実物 replay E2E は、並行する008の変更対象を実行します。各 PR 単独の緑では合流後を保証できません。後続は依存 merge 済み SHA から切り、合流結果で acceptance を再実行してください。008 の比較先も可動の `main` ではなく SHA 固定が必要です。共有 `CARGO_TARGET_DIR` や一時パスの衝突は、設定次第のリスクです〔推測〕。

7. **MEDIUM｜002・003・005：識別子の一意性が不足。** session 名が参加者間で重複可能なら〔推測〕、session_id 単独の manifest 結合は誤結合します。複合キー、manifest・labels の重複拒否、同じ episode への矛盾ラベル、非有限数、複数極間の provenance 不一致を明文化してください。

8. **MEDIUM｜全体：CI が成功してもテスト未実行になり得る。** `test_bounds.py` は共通 discover の対象外で、YAML の文字列検査は実行を保証しません。収集件数の下限と実際の unittest 実行を検証してください。代案として CI 配線と共有 API 契約を先行 issue に集約すると、後続の衝突を減らせますが、統合時の実行確認は別途必要です。
