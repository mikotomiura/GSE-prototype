# 判断の記録

## 判断 1: 直す前の版の実アプリは測らず、診断のテストと O1 の集計で代える

- 決定: 引き継ぎの手順 1（今の版でマウスを 1 分動かした行の数）は、同じプロセスでループの形だけを替えた診断（675 → 0・677 → 677）と、O1 の 3 人の集計（打鍵 4.8 万に対して 424 など）で代える。実際のマウスでの確かめは直した版だけで行った。
- 理由: 診断はループの形以外を揃えた対照で、原因の切り分けとして実アプリより強い。研究者にマウスを動かしてもらう回数を 1 回にできる。
- 却下案: 直す前と後の両方を実アプリで測る（研究者の手間が 2 倍で、得られる情報は診断と重なる）。

## 判断 2: `GetRawInputBuffer` の失敗時は、溜まった `WM_INPUT` を既定処理へ渡して捨てる

- 決定: 失敗したら 1 回だけ `tracing::warn!` し、`WM_INPUT` だけを取り出して `DispatchMessageW`（`DefWindowProcW`）へ渡す。その分は数えない。
- 理由: pump が `WM_INPUT` を取り除かなくなったので、失敗が続くとキューに溜まり、ポインタの行が無言で 0 件になる（今回の症状と同じ）。既定処理へ渡すのは、直す前の版が毎回していたことと同じ後始末。
- 却下案: 何もしない（失敗が続いたときに気づけない）・`DefWindowProcW` を通さずに捨てる（後始末が漏れる）。
