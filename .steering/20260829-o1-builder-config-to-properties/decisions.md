# 設計判断

## D-1: ロスターのキーを `O1_MGMT_SHEET_ID` に改名しない（2026-08-29・研究者判断）

### 問い

★ スクリプト プロパティ 4 件のうち 3 件が `O1_` 接頭辞（`FORM_ID_O1_CONSENT` /
`FORM_ID_O1_SURVEY` / `O1_APP_DOWNLOAD_URL`）なのに、シートだけ `PHASE1_MGMT_SHEET_ID` で
**不揃いに見える**。`O1_MGMT_SHEET_ID` にしてよいか。

### 判断: ★ **改名しない**。ただし O1 固有の管理シートは**別キーで新設する**（案 a）。

### 根拠（★ 一次資料で確認）

⚠️ 接頭辞は「**どのプロジェクトが読むか**」ではなく「**どのプロジェクトの実体か**」を表している。
★ このキーが指すのは O1 の資産ではなく、**Phase1 のロスター**である:

| 実測した使われ方 | 場所 |
|---|---|
| `openById(...).getSheetByName("参加者ロスター")` | `GSE_O1_Form_Builder.gs` `o1OpenRoster_()` |
| ★ **その Phase1 ロスターに行を追記**する（`appendRow`） | `assignO1ParticipantId()` / `onO1ConsentSubmit` |
| ★ 既存参加者を P-ID / メールで引き当て、**既存 ID を再利用**する | `o1FindInPhase1Roster_()` |
| ⚠️ P-ID↔個人の対応表は**ここ 1 か所**（Phase1 / G1 / O1 の共用） | `docs/o1-deletion-ledger.md` §5b（逐語） |

⚠️★★★ **`O1_` を冠すると事故る道が開く。** ★ G1 側に前例があり、
`GSE_G1_MGMT_SHEET_ID` は「**G1 固有の別シート**」を指す（`GSE_G1_Form_Builder.gs:110-111` 逐語:
「Phase1 の `GSE_MGMT_SHEET_ID` とは**別のキー**（別シート）」）。
→ ★ この並びに `O1_MGMT_SHEET_ID` を置くと「O1 にも固有のロスターがある」と読め、
⚠️ 新シートを作って指した瞬間に **2 か所採番**になる。

⚠️ **そして機械では止まらない。** 拒否リスト `o1IsKnownWrongRoster_` が弾けるのは
**既知の古いシート**（`12T8WU4D…`）だけで、★ 新規に作った空シートは**普通に通る**。
新シートは `既存の最大値 + 1` で **P001 から**出るため、実在の P006〜 と衝突し、
⚠️ **別人のデータが 1 つの P-ID に混ざる**（`o1-deletion-ledger.md` §5b の警告と同じ形）。
→ ★ **名前が最後の防波堤**である。

### 却下した案 b（採番元そのものを O1 の新シートへ移す）

⚠️ 名前の問題ではなく設計変更であり、同時に 3 つを直さないと壊れる:

1. ⚠️ 同じ人に 2 つの P-ID ができる（研究者判断 2026-08-03「1 人の人間に 2 つの識別子を作らない」に反する）
2. ⚠️ 番号空間の衝突 → ★ 分けるなら**接頭辞を変える**のが必須（例 `O1-001`）
3. ⚠️ 削除台帳 §5b の改訂（対応表が 2 か所になる。退会時の「氏名・メールを空にし P-ID は残す」も再定義）

★ 研究者判断: **採らない**。

### 採用した形（案 a）

- `PHASE1_MGMT_SHEET_ID` … **据え置き**。採番元 ＝ P-ID↔個人の対応表 ＝ Phase1 ロスター 1 点。
- `O1_MGMT_SHEET_ID` … ★ **5 本目のキーとして新設**（O1 固有の運用管理シート）。
  ⚠️ **本タスクでは足さない** —— シートがまだ存在せず、★ 空のキーを先に作っても
  fail-closed の検査対象が増えるだけで防波堤にならないため。
  ★ **中身は D-2 で確定した**（**P-ID のみ**・氏名とメールを持たない）。
  → ⚠️ したがって `docs/o1-deletion-ledger.md` §5b の **3 行目は不要**（→ D-2「帰結」）。

### 実装

- `o1Config_()` の `rosterSheetId` に**改名禁止の理由**を書いた
  （★ 誘惑が起きるまさにその場所に置く。⚠️ 理由が無いと「不揃いだから」で戻される）。
- ⚠️ 設定値・検査・テストの**挙動は 1 バイトも変えていない**（コメントのみ）。

## D-2: 新設する O1 運用管理シートは **P-ID のみ**（氏名・メールを持たない）（2026-08-29・研究者判断）

### 問い

★ D-1 で新設が決まった O1 固有の運用管理シートに、**氏名・メールを持たせるか**。
（★ 当初の意向は「持たせる。メールなども送信するので」）

### 判断: ⚠️ **持たせない。P-ID のみにする。**

### 根拠（★ 一次資料で確認）

1. ⚠️★★ **「送るために持つ」は成り立たない。** ★ G1 は自前シートに実名・メールを持たずに
   **受付メールも後日の資料メールも送れている**:
   - 登録直後 … フォーム回答から `MailApp.sendEmail(a.email, …)`（`GSE_G1_Form_Builder.gs:3448`）
   - 後日 … **Phase1 ロスターの C 列から読む** —— `g1EmailForPid_`（`:2840`）が
     `getRange(found.row, 3).getValue()` を返し、★ 呼び出し側（`:2906`）が
     `sendTaskMaterialsEmail`（`:2495`・送信は `:2507`）へ渡す
     （⚠️ 初版は `:1839` と書いていたが、★ そこは `sendThankYouEmail(pid, email)` で
     **email を引数で受け取る**関数だった。cross-review が実測で検出・2026-08-29）
2. ★ **G1 が同じ問いに同じ答えを出している**（`GSE_G1_Form_Builder.gs:124` 逐語）:
   > ★ 同じ理由で、本シートは **実名・メールを持たない**。実名↔P-ID の対応表を 2 か所に作らない (data-privacy)。
3. ⚠️ **複製は削除面を純増させる。** ★ 対応表は現在 2 か所（`docs/o1-deletion-ledger.md` §5b:
   Phase1 ロスター / O1-C 回答シート）。3 つ目を作っても **共用ロスターの PII は消せない**
   （★ tombstone 運用）ので、退会対応は「O1 行の削除」＋「ロスターの PII 列を空に」の**両方**になる。
   ⚠️ どれか 1 つ漏れると同意文書 §7 が履行できない。

### ★ O1 新規参加者のメールはどこで管理されるか（★ 実装済み・確認した）

⚠️ **新シートは不要**。★ `onO1ConsentSubmit`（`GSE_O1_Form_Builder.gs:1375`）が
`roster.appendRow([newPid, a.name, a.email])` で **Phase1 ロスターの A/B/C 列**に書く。

- 既存参加者 … **メール一致**で既存行を見つけ既存 P-ID を再利用（★ C 列が空のときだけ補充）
- 手動登録 `assignO1ParticipantId` … P-ID のみ追記（★ 氏名・メールは研究者が手入力）
- 突合の優先順位は **メール > 申告された P-ID**（⚠️ 自由記入の P-ID は他人を名乗れるため）

### 帰結（★ 台帳は変更不要）

★ 対応表は **2 か所のまま**なので、`docs/o1-deletion-ledger.md` §5b / A-11 の
「**2 か所**」という記述は**そのまま正しい**。⚠️ 3 行目の追記も A-11 の修正も**行わない**。

### ★ 起票（本タスク外）

- **T-22**: O1-C は `a.os` を持っているのに、⚠️ ロスターの **D 列（OS）を埋めていない**
  （★ ログと O1-C 回答シートにのみ残る）。★ 運用上は埋めたほうが楽。⚠️ 挙動変更なので別タスク。

## D-3: ⚠️★★★ 「配備は AI にできない」は**誤りだった**（2026-08-29・実測で覆した）

### 何を訂正したか

★ `deployment-runbook.md` の冒頭は逐語で
「⚠️★★★ ここに書いたものは **AI が実行できない**」
「**Google の独自メニュー項目**と **Apps Script の関数セレクタ**は『実クリックが着弾しても発火しない』」
（2026-08-28 実測）と書いていた。⚠️ **これは誤りである。**

### ★ 真因: **タブが不可視だった**

⚠️ `document.visibilityState === "hidden"`（＝ Chrome が最小化・全画面ターミナルの裏）のとき、
**入力イベントだけが黙って落ちる**。★ スクリーンショットも `javascript_tool` も**通る**ので、
⚠️ 「操作は届いているのに UI が反応しない」と読めてしまう。

★ 切り分けは skill §2.0b の着弾プローブ（`window.__hits` が**空** ＝ 座標でも要素でもない）。
→ ★ **`hidden` を見たら操作せず、ウィンドウを前面に出してもらう**（⚠️ 拡張機能から前面化はできない）。

⚠️★★ **誤った断定のコスト**: 「配備は研究者が手で行うしかない」という**運用の前提**を丸ごと 1 日ぶん
残していた。★ 実際には §3 の 1〜7（貼り付け・プロパティ・4 つの関数実行）が**すべて動いた**。
