# 重要な設計判断

## D1: このタスクを Loop Engineering に載せない

- **判断日時**: 2026-08-01 (セッション開始時・ユーザー承認済み)
- **背景**: ハンドオフ `§0` が「Loop Engineering の初実戦にするか」を最初の判断事項として
  提示していた (`_loop-config.json` 未作成 = 一度も回していない)。
- **選択肢**:
  - A: 載せない・通常の調査タスクとして直列に進める
  - B: 載せる (① を `parallel=1` で基盤検証 → ②③)
  - C: 載せる (3 件フル)
- **採用**: **A**
- **理由** (`docs/loop-engineering.md` の issue-slicing 7 基準に照らして):
  1. **基準 3 (独立性) を構造的に満たせない**。3 件はいずれも `probe_variants.py` /
     `notes.md` / `metrics.json` / `results/` を触るので `## Allowed Files` が全面的に交差し、
     `## Dependencies` で完全直列にするしかない。**並列度の利得がゼロ**。
  2. **基準 4 (検証可能性) が本質的に成立しない**。AC を成果物の状態
     (「`probe_variants.txt` に N 通りの結果がある」) で書くことは*できる*が、それは
     **問いに答えないまま充足できてしまう**。同 doc が警告する「客観に見えて無意味な緑」を
     AC の設計段階で作り込むことになる。調査タスクの Done は「原因が特定できた/総当たりして
     なお不能と確定した」という**意味判断**であり、exit code に落ちない。
  3. **基準 2 (粒度) から見て task 全体が 1 issue 未満**。成果物は新規 1 スクリプト +
     `notes.md` 更新で、目安の「≤5 ファイル / ≤300 行」に task 全体が収まる。
  4. 上記の結果、loop に載せても得られるのは「直列 3 issue = チェックポイント付きの
     通常タスク」であり、worktree・別セッション・`_loop-config.json` のコストだけが残る。
- **トレードオフ**: Loop Engineering の初実戦が先送りになる。
  → **推奨**: 初実戦は **AC を exit code / test 名で言える実装タスク** (例: Epic2 の
  golden 追加、`.steering/20260725-phase1-verdict-and-epic2-prep` の残 C = deep-silence
  fixture) に回す方が、枠組みの検証として意味がある。構造的に合わない題材で回すと
  「枠組みの問題」と「題材の問題」が分離できない。
- **影響範囲**: `.steering/` の記録形式のみ。実験の中身には影響しない。
- **見直しタイミング**: 本タスクの結論が ADR-008/009 起票に進み、そこで複数の
  独立した実装 issue (`engine.rs` / `features.rs` / schema) に割れたとき。
- **loop から持ち込む要素 (載せなくても採用する)**:
  - `acceptance.sh` を書く。`experiments/` を触っても `cargo test` / lint は
    **無条件に緑**になる (Rust に触らないため) ので、これが無いと検証が空になる。
  - 総当たりは本体 `diagnostics.py` に混ぜず `probe_variants.py` に分離する
    (結論が出るまで本体を汚さない)。
  - TASK-POST の `/cross-review` は `/finish-task` で実施する。

## D2: ③ ICC — `.idea` の値は ICC ではなく η² だった。**現行実装を正とする**

- **背景**: 再現値が `.idea` の 1.2〜1.3 倍。しかも 4 特徴量で比がほぼ一定
  (0.750 / 0.753 / 0.779 / 0.780)。前処理差なら特徴量ごとにばらつくはずなので
  **式の違い**を第一候補にして総当たりした。
- **総当たり**: 式 8 種 × 前処理 7 種 × 被験者集合 6 種 = **336 通り** (`probe_variants.py` P3)。
- **原因**: `.idea` の 4 値に 3 桁一致したのは **η² = SSB/SST** (と、数値上ほぼ同一の ω²)、
  前処理は現行と同じ「feat 全件・5 被験者」。最大差 0.0003。
  つまり**前処理は一致していて、式だけが違った**。
- **どちらを正とするか — 採用: 現行実装 (ICC(1))**。まず 2 つは**測っている対象が違う**。
  F = MSB/MSW として `ICC(1) = (F−1)/(F+k0−1)` は**母集団の**分散成分比
  σ²b/(σ²b+σ²w) の推定量、`η² = (k−1)F/((k−1)F+(N−k))` は**この標本で**群が説明する
  平方和の割合 (記述統計)。η² は母集団の分散成分を推定しようとしていないので、
  「η² が ICC の推定に失敗している」のではなく**別の量**である。
  ただし同一データで並べると η² は系統的に小さい値になる (群平方和に自由度 k−1 しか
  与えないため。k=5・N=124,517・k0=22,923.87 の本データで 0.75〜0.78 倍)。
  §1.4 が主張したいのは「**個人差の割合**」= 母集団の分散成分比なので、
  **その量を出す推定量は ICC(1) の方**。
  → **`.idea` の 0.060/0.055/0.159/0.156 は、測っていない量のラベルで報告された
  記述統計**。ADR では引かない。
  (この判断は `/cross-review` で Claude・Codex 双方が独立に再検証し、誤りなしと確認。
  大 N 極限での比が `(k−1)/(k−ICC)` に収束することと実測比 0.75〜0.78 の整合も確認済み。)
- **トレードオフ**: `.idea` の「個人差は 6〜16%」という表現は正しくは「8〜20%」になる。
  **結論の向き (個人差は小さい・個人適応は写像係数側) は変わらない**ので、
  ADR-008/009 の設計判断そのものには影響しない。ただし ADR に `.idea` の数値を
  そのまま引くと**誤った過小値を SSOT に昇格させる**ことになるので、引かない。
- **実装への反映**: `d4_icc` の ICC(1) は**変えない**。代わりに `eta_squared` を
  出力に併記し、`diagnostics.txt` に「η² は `.idea` が ICC と書いていた値。
  k=5 では 0.75-0.78 倍に過小評価する」と刷る。
  **併記しないと将来また「1.2-1.3 倍ずれている」を追跡し直すことになる**ため。
- **影響範囲**: `results/diagnostics.json` (`D4_icc[*].eta_squared` 追加) /
  `metrics.json` (`icc[*].eta_squared` 追加) / `notes.md` §1 表・§2-C・§3。
- **見直しタイミング**: 被験者が増えて群数 k が 10 を超えたとき (η² と ICC(1) の差が縮む)。

## D3: ② r=0.78 — 原因は**自分の実装側**の比較条件の取り違えだった

- **背景**: `.idea` §1.3 の r=0.78 に対し再現は 0.763。前回は「差 0.017 は追跡不能」で
  閉じかけていた。
- **総当たり**: X 候補 4 × 項候補 8 × 相関 2 種 × 集約 3 種 × スコープ 2 = **384 通り**
  (`probe_variants.py` P2)。四捨五入して 0.78 になる φ(F1) 変種は **1 つだけ**。
- **原因**: `.idea` §1.3 は冒頭で「124,517 サンプルで φ を**再計算** (β_writing 基準)」と
  宣言しており、相関の**両辺とも β_writing 基準の再計算値**で取っている。
  前回の再現は φ 項だけ β_writing にして、相手を**記録された `raw_x`**
  (= IME 状態で切り替わる実 β 由来) にしていた。**基準の食い違い**が 0.763 の正体。
  両辺を揃えると **0.7798 → 0.78** で一致する。
- **採用**: `.idea` が正。`d2_d3` に
  `term_correlations_with_recalc_x_beta_writing` を追加して**同条件を再現可能にした**。
- **教訓 (前タスク D5 の再来)**: 前回の paste 96.6 倍と同じく、
  **「先行記述と食い違った」の正体はまた自分の実装だった**。2 件連続。
  「相手が式を書いていないから不明」で閉じる前に、
  **相手の文章が宣言している前提 (ここでは「β_writing 基準で再計算」) を
  自分が守っているか**を先に確かめること。
- **注意**: ただし `.idea` の**結論**「f1 項が支配的」は依然として支持されない。
  同じ条件で φ3=0.8093 が上回り φ6=0.7807 も並ぶ。§2-B の判定は変えない。

## D4: ① 68 件 — 単一候補まで復元したが「✅ 一致」とは書かない

- **総当たり**: 特徴量セット 9 × 被験者集合 6 × ターゲット 3 × 数え方 2 × pooled 2
  = **648 通り** (`probe_variants.py` P1)。
- **結果**: 68 になるのは
  **「17 特徴量 × 4 被験者 × 1 ターゲット・全セル・pooled なし」だけ**。
  17 = `per_feature_cindex.py` の 12 + 収集済み未使用の 5。
  **どの 1 名を除くか / Q1 と Q2 のどちらか は件数では決まらない** (数値的には
  10 通りが等価)。P013 除外と Q1 は**意味論的な根拠**で選ぶ:
  P013 除外は `.idea` §1.1 の表に P013 列が無いことと整合し、
  Q1 は §1.1 が X 軸 (摩擦 = Q1) の節であることと整合する。
  「全セル」で数えるときの件数は集合の中身に依らず `|F|·|S|·|T|` で決まるので、
  この式の整数解が候補の全体になる (`probe_variants.txt` に全解を出力)。
- **傍証**: `.idea` §1.1 の Bonferroni 閾値「p<0.0007」は `0.05/68 = 0.000735` と整合する。
  68 が実際に多重比較の分母として使われたことを示す。
- **採用**: 判定を **「◯ 定義を復元 (単一候補)」**とする。**「✅ 一致」とは書かない**。
  `.idea` 側に定義の記載が無い以上これは復元であって確証ではなく、
  1 つの整数に当てているので偽陽性の余地が残る。
- **却下案**: 「17×4×Q1 で一致した」として ✅ にする案 → 却下。
  1 整数への一致を根拠に ✅ を付けると、後から ADR を読む人が
  「検証済みの事実」として扱ってしまう。
- **ADR への扱いは変えない**: 件数は載せず、結論と本実験の内訳
  (算出可能 103 セル・到達可能 70 セル) を載せる。

## D5: 総当たりを `run.sh` には載せず、`acceptance.sh` から回す

- **背景**: ハンドオフの判断事項「総当たりスクリプトも `run.sh` から再現できるようにするか、
  一度きりの調査として `notes.md` に結果だけ残すか」。
- **選択肢**: A: `run.sh` に組み込む / B: 一度きりの調査として結果だけ残す /
  C: スクリプトは追跡下に置き、`acceptance.sh` から回す
- **採用**: **C**
- **理由**: `run.sh` は「実験を再現する」入口で、その出力 (`diagnostics.json` /
  `metrics.json`) は共有アーティファクト。総当たりは `.idea` という**追跡外の私的メモ**を
  相手にした一度きりの調査であり、実験結果ではないので `run.sh` の成果物に混ぜない。
  一方 B にすると、`diagnostics.py` を直したときに `probe_variants.py` が
  **黙って壊れて誰も気づかない**。`acceptance.sh` から回して exit code と決定性を
  見ておけば、コストは +30 秒で腐敗を防げる。
- **トレードオフ**: `run.sh` だけを回した人には総当たり結果が更新されない。
  → `notes.md` の「再現コマンド」節に `acceptance.sh` を明記して回避。

## D6: `experiments/` の唯一の実質ゲートとして `acceptance.sh` を新設

- **背景**: 本実験は Rust に触らないので `cargo test` / clippy / tsc が**無条件に緑**になる。
  つまり通常の検査は本実験について何も言っていない (`docs/loop-engineering.md` の
  「test/lint が無条件に緑になる issue に `acceptance.sh` を書いたか」と同じ問題)。
- **採用**: `acceptance.sh` に 6 項目 (run.sh exit 0 / 決定性 byte-equal /
  φ 等価性と**閾値が緩められていないこと** / `probe_variants.py` の exit 0 と決定性 /
  `check_notes.py` / `results/` 全体の PII 走査) を集約。
- **`check_notes.py` の設計**: 「`results/diagnostics.json` から導いた文字列が
  `notes.md` の**該当行**に literal で現れる」形式にした (行を特定するアンカー必須)。
  手書きの `notes.md` が本体の変更に追随せず**黙って古い数値を残す**のを止めるため。
  70 項目 + `metrics.json` 8 項目を検査する。
- **空振りしないことを負のテストで確認済み**: `notes.md` の 1 セルを書き換えた場合と
  `metrics.json` の 1 キーを書き換えた場合の両方で exit 1 になることを確認
  (`silent-failure-in-guard-scripts` 型の「広いが何も見ていないゲート」を避けるため)。

## D7: 独立レビューで**ゲート自身の穴が 2 つ実証された**ので設計を変えた

- **背景**: D6 で作った `check_notes.py` を code-reviewer が攻撃したところ、
  **実際に素通りする経路が 2 つ**見つかった (推測でなく実証):
  1. アンカーが複数行にマッチすると `any()` 判定になり、§1 の値を壊しても
     **§3 に同じ数字があるだけで通る**。実証: 「到達可能セルは 70/103」を
     `71/103` に書き換えても exit 0 だった。
  2. `expect in line` の部分文字列一致なので、**桁を足すと通る**。
     実証: ime_shadow `777`→`7770`、残差 max `0.265`→`0.2650` がいずれも exit 0。
- **採用した修正**:
  1. **アンカーが 2 行以上にマッチしたらその場で FAIL** にする。
     「一意なアンカーを書け」を検査側から強制する形にした
     (曖昧なアンカーを許して `all()` にするより、書き手に直させる方が壊れにくい)。
  2. 照合を境界付き正規表現 `(?<![0-9.])EXPECT(?![0-9])` にした。
- **さらに追加した層**: `notes.md` が主張する「総当たり N 通り」「一致は 1 つだけ」を
  `probe_variants.json` と突き合わせる `check_probe()`。これが無いと
  **候補集合を 1 つ足した瞬間に notes の数字が黙って嘘になる** (D5 が防ごうとした
  腐敗が「スクリプトは動くが notes は古い」形で残る)。
- **教訓**: D6 で「ゲートの閾値が緩められていないかまで見る」と書いた同じセッションで、
  そのゲート自身に 2 つの素通り経路を作り込んでいた。
  **ゲートを書いたら必ず攻撃側を独立に立てる**こと。自分で書いた負のテストは
  自分が想定した壊し方しか試さない (今回の負のテストは「値を変える」だけで、
  「桁を足す」「別の行に同じ値がある」は試していなかった)。
