## 1. ★ 設計問い 1 — 送信の実行主体

### 採用案: **`gse-submit` を拡張し、アプリは「起動するだけ」**

```
[Tauri アプリ]  block ended
      │  ① 閉じたばかりの NDJSON パス + 参加者ID + ブロック番号
      ▼
[gse-submit]  --input <path> --participant <ID> --block <N> --auto
      │  ② 匿名化 (packaging.rs) → age 暗号化 → .age をローカルへ
      │  ③ 送信キュー (未送信の .age) を全部 POST
      ▼
[GAS Web App] → 研究者の Drive
```

### なぜこの形か

- ★ **F-4 の隔離方針を壊さない。** `age` も HTTP クライアントも
  **`package` feature の中に閉じたまま**にでき、⚠️ **盲検アプリ本体の依存を 1 つも増やさない**。
- ★ **CSP を 1 文字も触らずに済む**（前セッション実測: CSP は webview しか縛らない）。
  フロントから `fetch` する案は `connect-src` の追加が必要になり、
  ⚠️ **`data-privacy` ルール 5「CSP は外部リソースを禁止」に正面からぶつかる**。
- ★ **D-4（送信を実行時に止められる）が自然に満たせる。** 送信層が別プロセスなので、
  ★ 設定ファイル 1 つで「包むが送らない」に落とせる。⚠️ **再ビルド不要**。
- ★ **ロールバックが容易**（`design.md` のロールバック計画）。
  送信をやめる＝`gse-submit` の送信段だけ止める。**ローカルに `.age` が貯まる状態で成立する。**

### 却下した案

| 案 | 却下理由 |
|---|---|
| (a) Tauri 本体が HTTP を出す | ⚠️ ★ **盲検アプリ本体に HTTP クライアント依存が載る**。F-4 の隔離が崩れ、`.age` を作るために `age` も載せることになる |
| (c) 送信専用の 3 つ目のバイナリ | ★ 「包む」と「送る」を分けると**未送信キューの真実源が 2 つになる**。⚠️ D-3 の再送設計が複雑になる割に、得るものが「関心の分離」だけ |

### ⚠️ この案の弱点（★ 正直に書く）

- ★ **子プロセス起動の失敗を検知して画面に出す経路**が要る。
  ⚠️ 「起動したつもりで動いていない」は `silent-failure-in-guard-scripts` の型そのもの。
  → **F-6 と同じ厳しさ**にする: 起動失敗は握りつぶさず、未送信件数に反映する。
- ⚠️ ★ **ブロック中に走らせない**（`requirement.md`）。ブロック終了直後に起動する。

## 2. ★ 設計問い 2 — ブロック番号の採り方

### 採用案: **`~/.gse/g1_state.json` に永続化し、アプリ起動をまたいで数える**

- ⚠️ ★ **F-3 のとおり、いまのカウンタは再起動で 0 に戻る。**
  P-1 は 1 回の起動で 4 ブロック通したが、★ **それを前提にしてよい根拠は無い**
  （`decisions.md` の未確定 #2 が指摘しているとおり）。
- ★ 参加者 ID とブロック番号を同じファイルに置き、**次回起動で復元**する。
- ⚠️ ★ **番号が衝突したら上書きしない。** 同じ番号の `.age` が既に在るなら
  ★ **`-2` のような接尾辞を付けて別ファイルにし、画面に出す**。
  ⚠️ **黙って上書きするのが最悪**（`preregistration.md §3.6` が事後除外を禁じている以上、
  ブロックの記録は 1 本も失えない）。

### ⚠️ 却下

- 「ファイル名の時刻順で後から研究者が対応づける」→ ★ **O-7（削除要求で特定できること）**を
  満たせるが、⚠️ **実施中に「何本目まで届いたか」が分からない**（M-5 で送信先から追えない）。

## 3. ★ 設計問い 3 — 共有シークレットの置き場所

### 採用案: **配布フォルダ同梱の `submit_config.json`（`pubkey.txt` と同じ扱い）**

```json
{ "endpoint": "https://script.google.com/macros/s/…/exec",
  "shared_secret": "…",
  "send_enabled": true }
```

- ★ **M-3 により、シークレットは本文に入れるしかない**（ヘッダ認証は物理的に不可能）。
  ⚠️ ★ **クエリには入れない**（URL に残る・安全規約「URL にセンシティブな値を置かない」）。
- ★ **`send_enabled: false` が D-4 の停止スイッチ**である。
  ⚠️ ★ **被験者の画面には出さない。** 研究者が配布物を差し替える or 遠隔で指示して書き換える。
- ★ **このシークレットは機密性を守るためのものではない**（D-2 のとおり中身は `.age` で読めない）。
  ⚠️ 守っているのは **可用性**（いたずら投稿）だけである。★ **過大評価しない。**
- ⚠️ ★ **security-checker に必ず掛ける**（`tasklist.md §5`）。

## 4. ⚠️★ 設計問い 5（新規）— `data-privacy` ルール 3 との整合

ルール 3 は外部送信に 3 条件を課す。

| 条件 | 本設計 | 判定 |
|---|---|---|
| ② 匿名化 | `packaging.rs` の `vk` → `category`（★ 既存テスト資産がそのまま効く） | ✅ |
| ③ バッチ送信のみ（リアルタイム禁止） | ★ **ブロック終了後**にだけ走る。⚠️ ブロック中は起動しない | ✅ |
| ① 明示的同意（オプトイン UI・デフォルト OFF） | ⚠️ ★ **形が違う** | ★ 下記 |

★ ①について: 同意は**紙と G1-C（8 項目目）**で取る。アプリ側は
★ **G1 マーカーが無ければ送信経路が存在しない**（通常運用は `submit_config.json` を読まない）
＝ **既定は OFF** である。

⚠️★ **この読み替えを黙って通さない。** `security-checker` に**明示的に問う**:
「紙＋フォームの同意 ＋ モード限定 で、ルール 3-1 を満たしたと言えるか」。
★ 満たさないと判断されたら、**G1 のスタート画面に確認チェックを 1 つ足す**（縮退案）。

## 6. テスト戦略

- ★ **匿名化**: 新経路で作った `.age` を `gse-unpack` で開き、`vk` が無く `category` があること
- ★ **`--input`**: 存在しないパス / 別ディレクトリ / ゼロ引数の既定との共存
- ★ **送信層は差し替え可能にする**（⚠️ 実エンドポイントに投げない）
- ★ **ID 空で開始できない**ことを**赤で実測**
- ★ **エンドポイントを落として**再送の一巡を**赤で実測**
- ★ **マーカー無し起動の非回帰**（画面も挙動も変わらない）
