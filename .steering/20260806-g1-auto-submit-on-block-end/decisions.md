## D-1: 提出物を **ネットワークで自動送信する**（ローカル生成だけで止めない）

- **判断日時**: 2026-08-06
- **背景**: P-1 Windows 回で `.age` が 1 本も作られず、生 NDJSON が平文で研究者に渡った
  (`requirement.md` 背景)。★ **無人在宅の確証実施**（`preregistration.md` 第 9 版）では
  研究者が同席しないので、「被験者が最後に手でアップロードする」経路は
  ⚠️ **P-1 で既に 2 回失敗している**手順に依存し続けることになる。
- **選択肢**:
  - A: ブロック終了ごとに `.age` をローカル固定フォルダへ自動生成するだけ（送信しない）
  - B: **A に加えてネットワークで研究者へ自動送信する**
  - C: 生成はブロックごとに自動、提出は今までどおり手動ボタン
- **採用**: **B**
- **理由**: 研究者判断。★ **回収が被験者の操作に依存しなくなる**のが唯一の本質的な差。
- **トレードオフ**: ⚠️ ★ **`consent.md` に触る**（自動送信は現行の同意文に書かれていない）。
  Tauri の CSP / capabilities、送信失敗時の設計、送信先の運用が新たに必要になる。
  ★ A なら同意文書に触らずに済んだ。**それを承知で B を選んでいる。**
- **影響範囲**: `consent.md` §3 / `participant-guide.md` / `protocol.md §4b.2` /
  `tauri.conf.json` (CSP) / capabilities / `data-privacy` Skill の適用範囲。
- **見直しタイミング**: 倫理審査・研究室の規程で「参加者端末からの自動送信」に条件が付いた場合。
  ★ そのときは A へ縮退できる形にしておく（**送信層を分離する**理由になる）。

## D-2: 送信先は **GAS Web App → 研究者の Drive**

- **判断日時**: 2026-08-06
- **背景**: 送信先が要る。既存基盤で使えるものを優先する。
- **選択肢**:
  - A: **GAS Web App (`doPost`) → 研究者の Drive**
  - B: Dropbox へ直接（現行の提出先と同じ場所）
  - C: 研究者が別途立てる HTTPS エンドポイント
- **採用**: **A**
- **理由**:
  - ★ 既にフォーム / roster / リマインドで Apps Script を運用しており、**基盤を足さない**。
  - ⚠️ ★ **B は配布バイナリに Dropbox のアクセストークンを埋めることになる**。
    抜かれると研究者の Dropbox 全体を触られる。★ **これは配布物に置いてよい秘密ではない。**
  - ★ **送るのは `.age`（研究者の age 公開鍵で暗号化済み）だけ**なので、
    **経路そのものを信頼しなくてよい**。エンドポイントが漏れても中身は読めない。
- **トレードオフ**: GAS Web App は「URL を知っていれば誰でも POST できる」形になりうる
  → ★ **共有シークレットとサイズ上限・拡張子チェックが要る**（いたずら投稿への耐性）。
  ⚠️ ★ ただしそれは **可用性の問題**であって機密性の問題ではない（中身は読めない）。
  GAS の実行時間・POST サイズの上限も確認が要る（★ **未実測**）。
- **影響範囲**: 新規 GAS スクリプト（`.idea/` 側の運用資材）、配布物に入れる URL / シークレット、
  `tauri.conf.json` の CSP `connect-src`。
- **見直しタイミング**: GAS の上限に当たった場合 / 機関のポリシーで Google 経由が使えない場合 → C へ。

## D-3: 失敗時は **ローカルに貯めて自動再送**。送信の単位は **ブロックごとに 1 本**

- **判断日時**: 2026-08-06
- **背景**: 在宅実施では回線が落ちうる。⚠️ ★ `preregistration.md §3.6` は
  **ブロックの事後除外を禁じている**ので、送れなかったブロックを「無かったこと」にできない。
- **選択肢**（失敗時）:
  - A: **ローカルに貯めて自動再送 ＋ 未送信件数を画面に出す**
  - B: その場で数回リトライし、ダメなら警告だけ
  - C: 送信できるまで次のブロックを始めさせない
- **採用**: **A**（送信単位は **ブロック終了ごとに 1 本**）
- **理由**:
  - ★ **`.age` は必ずローカルに残る**ので、送信が全部失敗しても
    「被験者のフォルダから回収する」という**最後の経路が生き残る**。
  - ⚠️ ★ **C は却下**: ブロック間の休憩は `protocol.md §4.4` が 1 分と決めており、
    ★ **回線の都合で手順を壊すのは本末転倒**である。
  - ブロックごとに送るのは、★ **途中でアプリが落ちてもそこまでが届く**ため。
    まとめ送信は「最後まで到達しなかったケースで全損」になる。
- **トレードオフ**: 再送キューという状態を 1 つ増やす。★ 「未送信 N 件」の表示が
  ⚠️ **被験者にとってのノイズ**になりうる（0 件なら何も出さないことで抑える）。
- **影響範囲**: スタート画面の表示、`~/Documents/GSE-submissions/` の扱い、
  アプリ起動時の再送トリガ。
- **見直しタイミング**: 未送信が常態化した場合（＝送信先が不安定）。

## D-4: 送信停止 (O-1) は **入れる。ただしスイッチは研究者側にだけ置く**

- **判断日時**: 2026-08-07（研究者判断・`consent-draft.md` **Q-1**）
- **背景**: `consent-draft.md` §2 の文案が「送信をやめてほしい場合は、その場で言ってください」と
  約束している。★ **文案に書いたなら実装しなければならない** (`consent-draft.md` §4 O-1)。
- **選択肢**:
  - A: **入れる／研究者側のみ**（同意文には「言ってください」と書き、実際のトグルは
    配布物の設定など**研究者しか触れない場所**に置く）
  - B: 入れる／参加者がアプリ画面のトグルで止められる
  - C: 入れない（O-1 を文案から削る）
- **採用**: **A**
- **理由**: ⚠️ ★ **B は無人在宅で「止めたまま最後まで行く」と回収がゼロになる。**
  D-1 で自動送信を採った理由（回収を被験者の操作に依存させない）を、
  ★ **同じタスクの中で自分から壊すことになる**。A なら倫理的な停止権は担保しつつ、
  誤操作による全損を防げる。
- **トレードオフ**: ⚠️ ★ **停止は即時ではない**（参加者が申し出 → 研究者が対応する非同期経路）。
  ★ 同意文にはこの非同期性が伝わる書き方をする（「その場で言ってください」＋研究者が止める）。
- **影響範囲**: 送信層を**実行時に無効化できる**必要がある（ビルドし直しでは約束を守れない）。
  → ★ **設計問い 1（送信の実行主体）への強い入力**。設定の読み取り場所は設計で決める。
- **見直しタイミング**: 倫理審査で「参加者本人が即時に止められること」を要求された場合 → B。

## D-5: 同意文の送信先表記は **「Google のサービス経由」＋保存先を明記**

- **判断日時**: 2026-08-07（研究者判断・`consent-draft.md` **Q-2**）
- **選択肢**: A: 「Google のサービスを経由」＋「研究者が管理する Google ドライブに保存」 /
  B: 具体名（Google Apps Script / Drive）を書く / C: 「研究者が管理する保管場所」のみ
- **採用**: **A**
- **理由**: ★ 参加者にとって実質的な情報は「**Google のサーバを通る**」ことと
  「**最終的にどこに置かれるか**」の 2 点。⚠️ 「Apps Script」と書いても一般参加者には伝わらず、
  ★ **情報量が増えない割に読み手の負担だけ増える**。C は第三者クラウド経由の事実が落ちるので
  開示として不十分。
- **影響範囲**: `consent.md` §3 の文面のみ。実装には影響しない。

## D-6: 「以前の試行で記録が失われた」ことを **書く（表現は中立に）**

- **判断日時**: 2026-08-07（研究者判断・`consent-draft.md` **Q-4**）
- **選択肢**: A: 書く／中立表現 / B: 書く／`consent-draft.md` §1-2 の文面のまま /
  C: 書かない（「確実に残すため」とだけ書く）
- **採用**: **A**
- **理由**: ★ `consent.md` 冒頭の**欺瞞を用いない方針**と整合させる。
  ⚠️ ただし「2 回失われた」と数えて書くと **「この研究は失敗している」という印象**を与え、

- **文面の方針**: 「予備実施で記録が一部失われたことがあったため、確実に残す目的で

## D-7: 収束器は `gse-submit --reconcile`。アプリは **起こすだけ**

- **判断日時**: 2026-08-08（実装）
- **背景**: 未確定 #1（送信の実行主体）の決着。`design.md` §2 の方針を実装に落とした。
- **採用**: `bin/submit.rs --reconcile` に収束器を置き、`lib.rs` は子プロセスとして起こす。
  HTTP クライアント (`reqwest`) は **`package` feature の中**に入れた。
- **理由**:
  - ★ `age` も HTTP も **盲検アプリ本体に載らない**（decisions D3 の隔離を壊さない）。
  - ★ 送信が Rust の別プロセスなので **Tauri CSP を 1 文字も触らない**
    （フロントから `fetch` すると `connect-src` の追加が要り `data-privacy` ルール 5 と衝突する）。
  - `reqwest` は **`tauri` が既に依存しているクレート**なので、供給元を新たに増やさない。
    ⚠️ ★ 実測 M-1（302 が返る・メソッド強制で 405）に対し、reqwest の既定リダイレクト方針は
    302 で POST → GET に変える = **実測で 200 が返った curl の既定と同じ形**である。
- **トレードオフ**: ⚠️ 「起こしたつもりで動いていない」が起こりうる
  （`silent-failure-in-guard-scripts` の型）。→ ★ 子プロセスの exit code と
  `GSE_RECONCILE {...}` 要約行を読み、**失敗はログではなく画面に出す**（`get_submission_status`）。

## D-8: ブロック番号は **台帳と `.age` の名前の両方**から復元する

- **判断日時**: 2026-08-08（実装）
- **背景**: 未確定 #2。`design.md` §3 は「`.age` を作る時点で台帳の次の番号」と決めた。
- **採用**: `next_block_number = max(台帳の最大値, 既存 .age 名から読めた最大値) + 1`
- **理由**: ★ **どちらか片方が欠けても番号が戻らない**ようにする。
  台帳が消えても `.age` の名前（`P012_block03_gse_….age`）から復元でき、
  研究者が `.age` を手で退避しても台帳から復元できる。
  ⚠️ ★ アプリのメモリ上のカウンタは使わない（`G1_BLOCKS_STARTED` は再起動で 0 に戻る）。
- **トレードオフ**: ファイル名に規約が乗る。→ 規約は `submission.rs` の 1 箇所に閉じ、
  ⚠️ **アプリ側と提出ツール側が同じ関数を呼ぶ**ようにした（feature gate を跨いだ drift の防止）。

## D-9: `LogEntry::BlockEnd` に **完了の合図**を足す（固定 sleep を使わない）

- **判断日時**: 2026-08-08（実装）
- **背景**: 収束器は「`session_end` を持つファイル」しか触らない。`BlockEnd` は channel 越しの
  非同期処理なので、★ **送った直後にはまだ `session_end` が書かれていない**。
- **選択肢**: A: 合図を足す / B: 固定 sleep で待つ / C: 待たない（次の機会に拾う）
- **採用**: **A**（`LogChannel::block_end_rx`）
- **理由**: ⚠️ ★ **C だと最後のブロックが送られない。** `lib.rs` は `overlay` 窓を作るので
  Tauri は × では終了せず（`CloseRequested` / `ExitRequested` の処理が無いことを grep で確認）、
  ★ **「次の起動」が来ないまま終わる**経路が実在する。
  B は `ANALYSIS_IDLE` を入れたときに既に否定した形である（**待つべき時間ではなく状態を観測する**）。
- ⚠️ ★ **この検査が押さえていないこと（実測）**: `try_send` を `flush()` の**前**に動かしても
  テストは **3 回とも緑のまま**だった（2 つの操作が同じスレッドで隣り合っており、
  読み手が窓を掴めない）。★ 押さえられているのは
  **「合図が来る」「その時点で `session_end` が読める」**の 2 点だけである。
  → ★ テスト名とコメントをその通りに直した（「順序を検査している」と書かない）。

## D-10: 「× で閉じてもプロセスが残る」は **本タスクでは直さない**

- **判断日時**: 2026-08-08（実装）
- **背景**: `design.md` §7-1 / 引き継ぎ §3-1 の「実装前に閉じる」1 件。
  ★ 事実確認: `lib.rs` に `CloseRequested` / `ExitRequested` / `on_window_event` は **存在しない**
  （grep で 0 件）。`overlay` 窓が生きている限り Tauri は終了しない。
- **選択肢**: A: 窓を閉じたらプロセスも終える / B: 直さず、依存しない設計にする
- **採用**: **B**
- **理由**:
  - ⚠️ ★ A は **通常運用（Phase1）の終了挙動を変える**。`requirement.md` のスコープは
    「通常運用の画面・挙動を変えない」と明記している。★ 本タスクが要求していない範囲である。
  - ★ 収束型なので **正しさが起動回数に依存しない**。「アプリ起動時」は 2 つあるヒントの
    片方にすぎず、取りこぼしても次のブロック終了で拾われる。
  - ⚠️ ★ 唯一の残り穴（最後のブロック）は **D-9 の合図**で塞いだ。
    ブロック終了のたびに `session_end` を確認してから収束器を起こすので、
    ★ 10 本目も**その場で**送られる。
- **見直しタイミング**: 通常運用側で終了挙動を扱うタスクが立ったとき（★ 別タスクとして起票する）。

## D-11: 受け口は **フォームビルダーと別の Apps Script プロジェクト**にする

- **判断日時**: 2026-08-08（実装）
- **背景**: 2026-08-07 の事故（`incident-20260807-g1c-rebuild.md`）は、関数セレクタの選択が
  反映されないまま既定の `setupG1Forms` を実行し、★ **同意フォームの全設問が消えた**もの。
- **採用**: `Form_G1/GSE_G1_Submit.gs` を **別プロジェクト**として配備する。
- **理由**: ★ 対策は「注意する」ではなく **危険な操作の隣に立たないこと**である。
  受け口はデプロイのたびに実行 UI を触るので、⚠️ 同じプロジェクトに置くと
  **また同意記録を消せる位置**に研究者を立たせることになる。
  ★ 受け口プロジェクトには**破壊的な関数が 1 つも無い**（作るだけ・消さない・上書きしない）。
- **トレードオフ**: プロジェクトが 2 つになり、配備手順が 1 つ増える
  → `Form_G1/README.md` に手順を書き、`.gs` 冒頭にも同じことを書いた。
