## 判断 1: 「収集完了」は config.json の**締めフラグと登録数だけ**で表す

- **判断日時**: 2026-09-27（研究者裁定）
- **背景**: `analyze.py:196-200` は `len(conf) < n_subjects` で無条件 NG（optional stopping の機械化）。
  第 20 版 (ii)(c) は「削除・離脱で解析 n が 1 に縮んでも `§3.9` に従って解析する」と言う。
  → ⚠️ **「まだ集まっていない」と「収集は完了したが縮んだ」を機械的に見分ける必要がある**。
  ⚠️ 同時に第 20 版「公表物の書き方」は『個人別の未完了・削除に関する記録は commit しない・公開しない』と
  要求しており、**`config.json` は追跡されるファイル**である。
- **選択肢**:
  - A: `sample_roster.recruitment_closed: {closed, date, decided_before_seeing_results}` ＋
       `registered_k`（**数だけ**）を足す。外した人の内訳は T3 台帳（研究者手元）のみが持つ
  - B: `sample_roster.removed: [{pid, date}]` を足して `len(conf)+len(removed) >= n` を収集完了とする
  - C: gitignore 対象の別ファイル（`roster-closed.json`）に置く
- **採用**: **A**
- **理由**: B は追跡されるファイルに「この P-ID は外された」という**人単位の事実**を永久化し、
  「公表物の書き方」と衝突する（理由を書かなくても事実は残る）。
  C は事前登録の凍結対象（`config.json` の `revision`）の外に判定の根拠が出るので、
  **後から「いつ締めたか」を第三者が検証できない**。
  A は repo に載るのが「締めた日」と「登録数」という**集計値だけ**で、
  第 20 版が公表を要求している「登録 k 名・解析 m 名」と同じ粒度に収まる。
- **トレードオフ**: `registered_k` と実際に募集した人数の一致は**機械では保証されない**
  （研究者が手で保つ。⚠️ 台帳と config の二重記入になる）。
  → 緩和: `analyze.py` は `registered_k < len(confirmatory)` を**矛盾として NG** にする。
- **影響範囲**: `analyze.py:180-215` の roster 検査 / 出力 JSON に `sample_counts` / `config.json`
- **見直しタイミング**: `n_subjects` を変える改訂（＝新コホートの事前登録）が起きたとき

### ⚠️ 併せて確定したこと（機械の挙動）

- `closed=false`（既定）→ **従来どおり `[NG]`**。⚠️ 既定を緩めない（optional stopping の防止が黙って消えないように）。
- `closed=true` かつ 解析 m ≥ 1 → 続行し、`登録 k / 解析 m` を併記する。
- `closed=true` かつ **m=0** → `[NG]`（第 20 版 (ii)(c) 逐語「完了者が 0 名になったら確証解析は行えない」）。
- ⚠️ **欠員検査（`:187-190`）は緩めない**。名簿にいるのに割付ファイルが無ければ NG のまま。
  → 削除の求めで記録を破棄した人・未実施のまま外した人は、**研究者が `confirmatory` から外す**
  （第 20 版 (i) 例外「研究者が名簿から外せる」）。`registered_k` が k を保つので情報は失われない。

## 判断 2: 未完了/未実施のマーカーは**割付ファイルの status 列**に持たせる

- **判断日時**: 2026-09-27（研究者裁定）
- **背景**: `validate_blocks.py:233-245` は「一部のブロックだけ `file` が埋まっている」を
  **記入漏れとして FAIL** にする。→ 未完了者の割付は現状 FAIL になる（第 20 版が自ら指摘）。
  ⚠️★ **実測**: 「開始していない」の機械判別は**構造的に不可能**である ——
  `preregistration.md §2.13-1b` 逐語「⚠️ ★ **何も保存しないので、閉じて開き直せば元に戻る**」。
  アプリの「開始する」も NDJSON が届かない限り見えない。→ 第 20 版の「実験者の実施記録で確認する」しかない。
  残る分岐は**手入力をどこに置くか**だけだった。
- **選択肢**:
  - A: `blocks/P0xx.json` に `participation_status`（＋記録日）を足す
  - B: `blocks/_participation.json` に分離する（割付は `assign.py` の生成物なので手入力を混ぜない）
  - C: 計器に持たせず T3 台帳だけが持つ（→ 部分記入を無条件 NOTE に降格）
- **採用**: **A**
- **理由**: `blocks/*.json` は **gitignore 対象**（`config.json` の `sample_roster._note` で確認）なので、
  人単位のラベルを置いても repo に載らない＝「公表物の書き方」に触れない。
  C は**転記ミスの検出力を失う**（＝ `validate_blocks.py` の存在理由そのもの）。
  B は突合対象が 1 つ増え、2 ファイルの整合検査という新しい失敗様式を作る。
- **トレードオフ**: `assign.py` の生成物に手入力が混ざる。
  → 緩和: `status` は**別キー**（`blocks[]` の中ではなくトップレベル）に置き、
  `assign.py` の再生成で消えたら「status が無い」＝**従来の FAIL に戻る**（fail-closed の向き）。
- **影響範囲**: `validate_blocks.py::check_files` / `--selftest` / `protocol.md`（記入手順）
- **見直しタイミング**: `assign.py` が割付ファイルの形を変えるとき

### ⚠️ 併せて確定したこと（`§3.6` に触れないための線）

- `validate_blocks.py` は **除外も判定もしない**（`README.md:614` の規約）。
  足すのは「status があればその状態を**報告する**」検査だけで、
  ⚠️ **status を根拠にブロックや被験者を落とさない**。
- status が**無い**割付の部分記入は**従来どおり FAIL**（★ negative control としてテストで固定する）。

## 判断 5: consent.md は**フォームに合わせる。ただし「0 回の分は記録しません」は残す**

- **判断日時**: 2026-09-27（研究者裁定）
- **背景**: consent.md =「30 秒未満・⚠️ **中断が 0 回の分は記録しません**」／
  配布済みフォーム =「30 秒より短いもの・**計測中のみ**」。
  ⚠️ フォーム側に「0 回の分は記録しない」の逐語は**無い**。
- **選択肢**:
  - A: 語（「30 秒より短いもの」「計測中のみ」）を揃え、「0 回の分は記録しません」は**残す**
  - B: フォームに逐語で揃える（＝ md から削る）
  - C: フォーム側に足す（配布済みフォームの書き換え）
- **採用**: **A**
- **理由**: 「0 回の分は記録しません」は**約束の縮小ではなく開示の追加**であり、
  削ると被験者に伝えていた『記録しない』情報が文書から消える（＝ 約束が後退する向き）。
  実装も 0 回の分を記録しない。C は研究者裁定の向き（md をフォームに合わせる）と逆で、
  配布済みフォーム（回答 11 件）の書き換え＝別承認が必要になる。
- **トレードオフ**: md とフォームが**逐語一致ではなくなる**（md 側の開示が広い状態が残る）。
  → 差分案に「一致しないことを意図した」と明記する。
- **影響範囲**: `consent.md §3`（表の行 ＋ 本文の箇条書き）
