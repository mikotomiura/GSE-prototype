# Issue 006: `T1d`（restart — `t0` 後の生成/削除/移動・再停止時間・安定生成時間）
verify_level: parse

## Goal

特徴行に `restart` を足し、**`stall onset`（`t0`）の後**に何が起きたか
—— 生成 / 削除 / 移動、再び止まるまでの時間、安定して生成が続いた時間 —— を載せる。

## Background

★ `ADR-030 D10` の Tier 表:
「`T1d` | restart（pause 後の生成 / 削除 / 移動・再停止時間・安定生成時間）| **中（記述）**
（中断後に navigation を経て編集へ戻る形）| ⚠️ 自己発生 stall 後の安定回復を予測できるか」。

★ D11 で `T1d` は **計器変更が不要**と実測済み。

### ⚠️★★★ 「pause 後」ではなく「`t0` 後」である

★ `ADR-030 D2` が **検出窓（`t0` 以前）と転帰窓（`t0` 以後）を分けた**のは、
`.idea/criterion:66` 逐語「**stall onset の検出窓と転帰判定窓を重ねない。**」を満たすためである。
→ ⚠️★★★ **`restart` は転帰側なので、必ず `t0` を原点にする。**
★ 単純 pause を原点にすると **検出窓と転帰窓が重なる**（＝ leakage）。

⚠️ さらに `ADR-030 D2` は **`t0` 直後の buffer `B`** を置いている。
→ ★ `B` の扱いを `stall_onset` の設定から引く（⚠️ 本 issue で値を決めない）。

### ⚠️ 「回復」と書かない

★ `docs/glossary.md` の禁止用語: 認知リソースの**消耗 / 回復 / 補充**は
**限定資源モデル（ego depletion）の語彙**であり、その枠組みは事前登録された検定で否定されている。
→ ★ フィールド名・コメントに `recovery` / `回復` を使わない。
⚠️ **例外は `打鍵再開 / typing_resumption`** で、これは「停滞エピソードからの自力での前進」の意味である。
