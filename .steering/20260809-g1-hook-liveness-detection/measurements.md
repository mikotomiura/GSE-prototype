## §5 ★ 示唆される次の判断 (実装ではなく判断が要る)

1. ⚠️★★ **`validate_blocks.py` の `alive=false` → FAIL は厳しすぎる可能性がある。**
   実測で通常作業の 63 分に 1 回出た。★ 代案:
   - **FAIL を「そのブロックの打鍵が実際に 0 か」と AND にする**
     (フックが死んでいて **かつ** 記録が空、のときだけ落とす)
   - あるいは FAIL でなく **WARN + 手動確認**にする
2. **閾値 120 秒の再検討**。⚠️ ただし ★ **緩めると本物の silent death を見逃す**。
   8/09 の本物の事故 (5 分 0 打ブロック) を捕まえられる範囲で緩める必要がある
3. ★ **再設置は残してよい** (T-C で無害と確定)。ただし
   ⚠️ 「1 エピソード 1 回」の制限は維持する

## §6 ★ 採用した是正 — **案 A** (2026-08-10)

**決定**: `validate_blocks.py` の FAIL 条件を
**「`alive=false`」から「`alive=false` かつ `key` 行 0」の AND** に変えた。
`alive=false` でも打鍵が在れば **WARN**（★ 黙って通しはしない）。

**根拠**: この AND が捕まえるのは 8/09 の本物の事故（5 分 0 打が正常として提出された）
そのものである。⚠️ 一方、誤検知は打鍵を伴うので落ちない。

### 実データでの効き方（★ 旧規則と新規則を同じログに当てた）

| ログ | key 行 | worst starved | 旧規則 | ★ 新規則 |
|---|---|---|---|---|
| T-A | 1,206 | — | OK | OK |
| T-B/T-C | 40 | 120,002 ms | ⚠️ **FAIL** | **WARN** |
| T-D 通常作業 | 5,742 | 120,000 ms | ⚠️ **FAIL** | **WARN** |
| （8/09 の実事故: 0 打 + `alive=false`） | 0 | — | FAIL | ✅ **FAIL のまま** |

★ 旧規則は **記録が正常な 3 本中 2 本を落としていた**。

### ⚠️★ 検査が空振りでないことの確認（壊して赤を見た）

セルフテストが緑なだけでは足りないので、**2 方向に変異させて赤を確認**した:

| 変異 | 期待 | 実測 |
|---|---|---|
| `if keys == 0` → `if True`（案 A を撤回＝常に FAIL） | 対照 3 が赤 | ✅ 赤（「誤検知で FAIL にしてはならない」＋ WARN 欠落の 2 件） |
| `if keys == 0` → `if False`（0 打でも落とさない） | 本命が赤 | ✅ 赤（「alive=false かつ key 0 は FAIL にすること」） |

→ ★ 追加した 2 本の対照は**どちらも実際に効いている**（緑が空振りではない）。

### ⚠️ 承知の上で残した穴

**ブロックの途中でフックが死ぬと `key` は 0 でないので WARN 止まり**になり、
★ **末尾が欠けたブロックが通る**。機械では「誤検知」と区別できない。
→ WARN の文言に明記し、★ **打鍵数と作業内容が釣り合うかを人が確認する**ことを求めている。
