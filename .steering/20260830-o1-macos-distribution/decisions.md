# decisions — 設計判断と根拠

## 判断 1: 初回セットアップのマーカーを**決め打ちから自動判別へ**

**決定**: `初回セットアップ_mac.sh` は `g1.mode` / `o1.mode` のどちらが隣にあるかを読み、
モードを決めて**モードごとに違う確認文言**を返す。両方あれば NG、片方も無ければ NG。

**理由**:
- ★ 旧版 `MARKER="g1.mode"` は O1 の配布物で**必ず NG**（実測 → `blockers.md` B-1）。
- ⚠️ モードごとに script を 2 本用意する案は却下した。★ このプロジェクトが繰り返している
  「片方だけ直してもう片方に古いものが残る」型を新たに作るため
  (`make-common-app-zip.sh` 冒頭が同じ理由で持ち物表を 1 か所にまとめている)。
- ★ 両方あるときに NG にするのは `lib.rs:3150` が起動を拒否するのと**同じ判定を前倒し**するため。
  ⚠️ 被験者が「アプリが開かない」に到達する前に、理由つきで止める。

**却下案**: `make-common-app-zip.sh` 側で `sed` してモード別に書き換える
→ ⚠️ 配布物と repo の script が別物になり、`--selftest` がさらに実体から離れる。

## 判断 2: ⚠️★★★ ゲートを「**実体に対して**」回す

**決定**: `make-common-app-zip.sh` に、展開したフォルダに対し
**引数なしで**（＝被験者と同じ実行の仕方で）初回セットアップを走らせ、
`OK:` と**モードに合った文言**を要求する検査を足した。

**理由**: ★ 既存の 2 か所は両方 `--selftest` で、**自前 fixture の中でだけ緑**だった。
⚠️ 実測した陽性対照が決定的である:

| 何 | 旧版スクリプト |
|---|---|
| `初回セットアップ_mac.sh --selftest` | ✅ **緑 8/8** |
| 新設の「配布物そのもの」検査 | ❌ **赤**（`build_exit=1`） |

★ 「緑」が「配布物が動く」を意味していなかったことが、同じ機械の上で並べて示せた。

## 判断 3: ⚠️★★★ **タグと実体の両方**で O1 実装の有無を検査する

**決定**: `--mode o1` のとき
(a) `git cat-file -e "$TAG:src-tauri/src/o1.rs"`（ソース）と
(b) `strings` で `o1.mode` / `gse_o1_` / `--o1`（**実体**）の両方を要求する。
★ macOS と Windows の**両方**の実体を見る。

**理由**: → `blockers.md` B-2。★ `v0.1.29` は O1 を 1 行も含まないのに、
旧ゲートは最後まで緑で完走した。
- ⚠️ (a) だけでは足りない: ★ タグにソースがあっても **release 資産がそれより前に作られている**
  ことはある（「タグが正しい」と「配るバイナリが正しい」は別の主張）。
- ⚠️ (b) だけでも足りない: ★ 文字列検査は将来の最適化で当たらなくなりうるので、
  ソース側の対と合わせて二重にする。
- ★ `strings` が無い環境では **O1 では die する**（⚠️ 黙って飛ばすと「O1 を知らないビルド」を
  配れてしまう。memory: `silent-failure-in-guard-scripts`）。

## 判断 4: ★ 既定の `TAG="v0.1.24"` と `--mode g1` は**一切触らない**

**理由**: ★ G1 は実施中。⚠️ 既定を変えると G1 の配布物のビルドが黙って変わる（引き継ぎメモ §1-B）。
★ 実測でも `--mode o1` は G1 の zip を作り直していない（08-23 / 08-27 のまま）。

## 判断 5: ⚠️ O1 を知らないビルドで作った zip は**隔離して repo から出した**

**決定**: `dist/_common/O1_実施用_*` と デスクトップの展開物を
セッションの scratchpad へ `mv` した（★ 削除ではなく隔離）。

**理由**: ⚠️★★★ **見た目は完全に正常な配布物**である（署名有効・実行ビットあり・
`o1.mode` あり・README あり）。★ 残しておくと「もうできている」と誤認して
配布フォルダに置かれる危険がある。⚠️ 本番 secret も入っているので repo 外へ出した。

## 判断 6: ⚠️ `/cross-review` の Codex は **secrets-filter でブロック**された（★ 縮退した理由を残す）

**結果**: `scripts/run-codex-review.sh` → **exit 2 (`BLOCKED: secrets-filter detected sensitive content`)**
→ ★ CLAUDE.md の既定に従い **Claude 単独へ縮退**した。⚠️ `.codex/budget.json` は
`tokens_used=25960` のまま不変（★ 課金前に落ちた）。

**★ 誤検知であることの根拠（⚠️ 語の目視ではなく、値で照合した）**:

```
git diff | grep -cF -- "<実 secret の先頭 12 文字>"      → 0
git diff | grep -cF -- "<実デプロイ ID の先頭 12 文字>"  → 0
```

★ diff 中の `secret` はすべて **識別子**（`secret_leak` / `secret_val_checked` /
`plant_secret` / JSON のキー `"secret":"%s"`）か**散文**（`len(secret) >= 24` 等）である。

⚠️★★ これは memory `cross-review-codex-self-block` の**新しい変種**である:
★ 従来は「フィルタ自身のパターン一覧」「手順書の grep」が引っかかっていたが、
今回は **私が新設した「secret 混入検査」のコードそのもの**が引っかかった。
→ ★ 「秘密を探すコード」は必ず「秘密っぽい語」を含むので、**構造的に自己ブロックする**。

**⚠️ `--ack-filtered` は付けていない。** ★ skill が
「**人が確認し `.steering` に根拠を残した時だけ**・**自動では絶対に付けない**」と定めているため。
→ ★ 上の実測が根拠である。研究者が目視で同意できるなら、次を手動で回して真の第二意見を得られる:

```bash
bash scripts/run-codex-review.sh --ack-filtered
```

| 優先度 | 何 | 対応 |

| HIGH | ⚠️ secret 値混入検査 (d) が設定不在で**黙って skip** し、一括の緑に紛れる。★ **私のコメントは「明示する」と書いていたのに実装が無かった** | 走ったかを持ち、走らなければ画面に出す ＋ 緑の文面自体を変える ＋ 対照 1 件 |
