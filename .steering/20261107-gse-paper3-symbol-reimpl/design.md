# 設計（v2・requirement だけから再生成）—— 記号化の書き直し

## アプローチ

不一致の原因を局所化でき、読者が手元でも一致を確かめられることを主にする。そのために 3 つの層に分け、層ごとに照らす。

1. **データの適合器**（データごと）: 生データ → 共通の「押下の列」の形式（`t_ms`・キーの種類）。CoAuthor と CS1 2021 で 1 つずつ。
2. **記号器**（データに依らない）: 押下の列 → tick ごとの (t, x, y, 経路, 記号)。決定的な状態機械として書く。
3. **定数の表**: 窓・バッファの容量・tick の間隔・β・x と y の重み・経路の閾値と α・罰の閾値・平滑の初期値を 1 つの JSON に置き、記号器はそこから読む。論文の補足資料 S2 の表はこの JSON から生成する（本文と実装の値がずれない）。

言語は Python の標準ライブラリだけ（numpy を使わない）。浮動小数は元の実装と同じ演算の順で書き、x・y の bit の一致まで照らす。

### 適合の検査を公開できる形にする（v2 の要）

- 合成の押下の列（種を固定した乱数で、沈黙の長さ・Backspace の連打・同時刻・押下の少ない列を含む数百本）を作り、元の実装に通した出力（記号と x・y の bit）を「期待の痕跡」として固定する。合成なので、人のデータは含まない。
- 公開 repo に、合成の入力と期待の痕跡と、それを書き直しの実装で照らすスクリプトを置く。読者は元の実装を持たなくても、書き直しが元と同じ記号を出すことを確かめられる。
- 実データ（CoAuthor・CS1）の照合は手元だけで行い、件数だけを残す。

- GSE 本体は変えない。

## テスト戦略

- 層 2 の単体: 経路の分かれ目（沈黙 2・15・25 秒）、罰の保留と消費、f1 が 0 で行が出ない場合、同時刻の tick と出来事の順、を合成の短い列で（期待値は元の実装の出力）。
- 適合の検査: 合成の数百本で記号と x・y の bit が全部一致。
- 変異: 定数の表の 1 つ・tick の順・離しの合成・罰の消費をそれぞれ壊し、適合の検査か単体が赤になるのを見る。変異が当たったこと（出力が変わったこと）も確かめる。
- 実データ: 層 1 の押下の列の一致件数、層 2 の feat 行の数・t・記号・x と y の bit の一致件数。不一致があれば種類と件数を記録して止める。

## リスク

- 合成の列が実データの癖（Unicode の判定・複数文字の挿入・API 起源の出来事）を覆わない → 層 1 は実データで別に照らす。
- 元の実装の浮動小数の順を取り違えると、bin の境界で 1 ULP ずれる → x・y の bit で照らして見つける。
