# 設計判断

## D-1: 【1】は案 A のみ採用。案 B (`session_start` 行を必須にする) は**却下**

**却下の理由** (実コードで確認): `lib.rs:1872` は

```rust
let _ = guard.tx.try_send(LogEntry::SessionStart { timestamp: now });
```

★ **結果を捨てている**。bounded(512) の channel が満杯なら `session_start` 行は
黙って落ちる。⚠️ これを提出の**必須条件**にすると、**本物の 5 分ブロックが
永久に包まれず研究者に届かない**。
→ ★ いま直したい欠陥 (番号がずれる) より**はるかに重い失敗**である。

★ 直上の `Rotate` は `try_send` の失敗を検査して fail-loud にしているのに、
`SessionStart` だけ `let _ =` になっている。⚠️ **これ自体が別の穴**だが、本タスクの範囲外。

## D-2: 除外する行型は「実データで測って」決める

`ime_state` を除外対象に選んだ根拠は実測である (推測ではない):

```
ブロックを回したセッション (gse_20260810_041334.ndjson)
  session_start 行より *前* に出た非 meta 行 : ime_state のみ
  session_start 行より *後* に出た行         : session_start / session_meta / feat(257) / key(2800) / ime_state(66)
ブロック未開始のセッション (gse_20260810_041051.ndjson)
  meta(2) + ime_state(2) だけ
```

→ ★ `ime_state` を落としても、本物のブロックは `feat` / `key` で必ず残る。

⚠️ 除外リスト方式そのものは「診断行を足すたびにここを直す」構造を残す。
★ 許可リストに反転する案も考えたが、**列挙し漏れた行型が本物のセッションを捨てる**方向に
倒れるため採らなかった (失敗の向きが悪い)。

## D-3: 【4】は「要求」と「順序」を別の判断に分ける

★ 壊れていたのは実装ではなく **判断の同居**だった。2 つの純関数に割り、
`should_request_input_monitoring` は **Accessibility を引数に取らない** ようにした。
→ ⚠️ 「AX の状態が要求の有無に影響する」という同じバグを、構造として書けなくした。

## D-4: 【2】は「秒に量子化して等値比較」を**却下**。ms + 許容幅にする

★ 一度「1 秒に量子化して等値比較」で実装し、**自分のテストで赤を見た**:

- 真の最終入力時刻が秒境界の近くにあると、実測 55 ms の揺れがバケツをまたいで
  ⚠️ **離席中に「入力があった」= 誤警告**になる
- ⚠️ ではと「±1 秒の差を無視する」にすると、**連続打鍵 (1 秒 tick ごとに +1 秒)** まで
  無視してしまい、★ **フックが死んでいて被験者が打ち続けている一番検出したい場面**で
  検出器が黙る

→ ★ ms のまま持ち、**250 ms の許容幅**で比べる形にした。
実測の揺れ 55 ms と、連続打鍵の 1000 ms の間に線を引いている。

⚠️ 比較規則は OS ごとに違う (`Windows` = 等値 / `macOS` = 許容幅) ので、
★ 呼び出し側 (`lib.rs`) に `!=` を書かせず `liveness::system_input_seen()` に集約した。

## D-5: ⚠️ 実機確認は「済んでいない」と書く

【4】【2】とも、**判断は単体テスト＋変異テストで固定したが、実機での赤→緑は見ていない**。

- 【4】の再現には `Input Monitoring だけ denied・Accessibility は granted` という
  端末状態が要る (アプリを別パスに置き、AX を手で許可する)
- 【2】は 30 秒 / 120 秒の閾値に達するまで待つ必要がある

★ `CGRequestListenEventAccess()` がシステム設定を開くこと自体は
2026-08-10 04:09:39 のログで実測済み (旧実装の else 経路)。
→ 未検証なのは **分岐の経路**だけであり、そこは単体テストが押さえている。
⚠️ それでも「実機で見た」とは書かない。
