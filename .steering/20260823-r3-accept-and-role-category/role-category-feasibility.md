## §0 ⚠️★★★ 結論を先に — **前調査の結論は Windows について誤っていた**

★ 2026-08-21 のサーヴェイ `§5.2` の逐語:

> ⚠️★★★ **役割カテゴリ**（`editor`/`terminal`/`browser`）
> ★ ADR-009 D2 が「収集開始前に計器へ入れない」と条件を付けている。
> ⚠️ さらに**技術的にも識別子必須**（Win=HWND→PID / mac=`AXObserverCreate(pid_t,...)`）
> → **識別子ゼロと両立しない**

⚠️ **「Win=HWND→PID」が誤りである。** ★ Windows には **PID を経由しない経路**があり、
**本 repo は既にそれを出荷している**（下記 §1）。

| OS | ★ 識別子ゼロで役割カテゴリを出せるか | 根拠 |
|---|---|---|
| **Windows** | ⚠️★★★ **出せる。前例が repo にある** | `ime_windows.rs:320` `class_name_of()` |
| **macOS** | ⚠️★★★ ~~**出せない**~~ → **訂正: 出せる**（追補 A-1 / A-3） | ★ `NSWorkspace`→bundle id / **ユーザー宣言** / AX の focused 要素役割 |

## §1 ★★★ Windows — **`GetClassNameW` 経路は既に出荷済み**

★ `src-tauri/src/input/ime_windows.rs:319-330`（**逐語**）:

```rust
/// ⚠️ ウィンドウタイトル (`GetWindowTextW`) も PID も取得しない。
fn class_name_of(hwnd: HWND) -> Option<String> {
    let mut buf = [0u16; 256];
    let len = unsafe { GetClassNameW(hwnd, &mut buf) };
    if len <= 0 { return None; }
    Some(String::from_utf16_lossy(&buf[..len as usize]))
}
```

★ この関数は **WinEvent が渡した HWND に対してコールバック内で呼ばれ**、返ったクラス名は
`is_ime_cloak_class()` の**判定にだけ使われて捨てられる**（保存されない）。

### 1.1 ★ したがって成立している性質（★ 推測ではなく出荷済みコードの性質）

| 性質 | ★ 成立 |
|---|---|
| **PID を取らない** | ✅ `QueryFullProcessImageName` を呼んでいない |
| **ウィンドウタイトルを取らない** | ✅ `GetWindowTextW` を呼んでいない |
| **HWND をコールバックの外へ出さない** | ✅ `class_name_of` は `hwnd` を消費して `String` を返すだけ |
| **保存されるのは判定結果のみ** | ✅ 現行は `bool`（IME cloak か否か） |
| ⚠️★★★ **静的に監査できる** | ✅ **判定表がソースにあり `grep` で検証できる**（★ これが UIA / AX 経路との決定的な差） |

### 1.2 ⚠️★★★ しかし「IME 判定」と「役割カテゴリ」は**同型ではない**（★ 差を 3 つ書く）

| # | ⚠️ 差 | ★ 何が問題か |
|---|---|---|
| **1** | `is_ime_cloak_class` は **固定の小さな allowlist に対する述語**である。役割カテゴリは **未知アプリを含む全域への写像**である | ⚠️ **`Other` バケットに情報が集中する。** ★ 「`Other` の滞在時間」は「知らないアプリを使っていた時間」であり、⚠️ **カテゴリ数が増えるほど擬似識別子性が上がる**（ADR-012 D4 L-c が「distinct ウィンドウ数も保存しない」と塞いだのと同型） |
| **2** | ⚠️★★★ **クラス名は事実上アプリ指紋である** — `Chrome_WidgetWin_1` / `CASCADIA_HOSTING_WINDOW_CLASS` / `HwndWrapper[DefaultDomain;;…]` | ⚠️ **ADR-012 D3 が禁じた「アプリ識別子」に該当するか**は**解釈が割れる**。★ 保存しないなら D4 L-c の作法（「保存するのは遷移が起きた時刻のみ」）と同じ形に収まるが、⚠️ **`GetWindowTextW` を呼ばない」と並べて「`GetClassNameW` は呼ぶ」と明記する必要がある** |
| **3** | ★ IME 判定は **1 ビット**。役割カテゴリは **区間ごとのラベル列** | ⚠️ **[P117] が precision 0.57 で落ちた穴（アプリ識別子→カテゴリ写像）そのもの**。★ 「取れる」ことは「効く」ことを意味しない |

### 1.3 ⚠️ 調べたが**使えなかった**もの

| 候補 | ⚠️ 結果 |
|---|---|
| **`EVENT_CONSOLE_*`**（コンソール窓だけに発火する WinEvent があれば terminal を識別子ゼロで検出できる） | ⚠️★ **公式の Event Constants ページに `EVENT_CONSOLE_*` は 1 つも掲載されていない**（2026-08-23 に一次確認。掲載は `EVENT_AIA` / `EVENT_MIN,MAX` / `EVENT_OBJECT_*` / `EVENT_OEM_DEFINED` / `EVENT_SYSTEM_*` / `EVENT_UIA_*` のみ）。★ さらに Windows Terminal は ConPTY ホストであり**古典的なコンソール窓ではない**ので、仮に存在しても現代の terminal を捕まえない |
| **UIA の `ControlType` / `ClassName` だけ取る** | ⚠️ **要素参照は HWND から導出される**。★ かつ `survey §5.2` 逐語「**同じハンドルから本文が読める**ため、境界が『能力』ではなく『方針』にしかならず**静的に監査できない**」 |
| **`IVirtualDesktopManager`** | ⚠️ **HWND ＋ デスクトップ GUID が必須**（前調査で確定済み） |

## §2 ⚠️★★★ macOS — **本節は末尾の「2026-08-23 追補」で訂正済み。★ 追補を先に読むこと**

> ⚠️ 以下の表は **`AXUIElementCreateSystemWide()`（引数を取らない）を見落としていた**。
> ★ 訂正は追補 A-1 / A-2、代替案 3 件は A-3。

| 経路 | ⚠️ 何を要求するか |
|---|---|
| `NSWorkspace.didActivateApplicationNotification` | ★ **通知そのものは識別子ゼロで受けられる**（⚠️ **時刻だけ**）。★ しかし役割を知るには `userInfo` の `NSRunningApplication` を読む必要があり、⚠️ **`bundleIdentifier` はアプリ識別子そのもの** |

# ⚠️★★★ 2026-08-23 追補 — **§2（macOS は不可能）を訂正する**

> ★ 研究者の問い（逐語）: 「**macOS の問題に対して、私たちのほうで実装するなどをしたうえで
> 自前で解決できるものではないのかな**」
>
> ⚠️★★★ **問いが正しい。§2 の「識別子ゼロの経路は無い」は強すぎた。**
> ★ 一次で確認した結果、**経路は 2 つある**。

## A-1 ★★★ 見落としていた API — `AXUIElementCreateSystemWide()` は **引数を取らない**

| 事実 | 出所 |
|---|---|
| `AXUIElementCreateSystemWide()` は **pid_t を含め引数を 1 つも取らない**。返るのは system-wide 要素 | Apple Developer Documentation（2026-08-23 確認） |
| その system-wide 要素は **`kAXFocusedUIElementAttribute` と `kAXFocusedApplicationAttribute`** を持つ | 同上 |
| focused 要素から **`kAXRoleAttribute`**（`AXTextArea` / `AXTextField` / `AXWebArea` 等）が読める | 同上 |

→ ⚠️★★★ **§2 の表「Accessibility は `AXObserverCreate` が `pid_t` を第 1 引数に取る」は、
*通知を購読する* 経路の話であって、*いま何にフォーカスがあるかを問い合わせる* 経路には当たらない。**

★ **しかもこの信号は役割カテゴリより筋が良い可能性がある** ——
`editor` / `terminal` / `browser` という**アプリの分類**ではなく、
**「いまユーザーが打ち込んでいる先はどんな種類の入力欄か」**という**要素の分類**だからである。
⚠️ ADR-009 D2 が欲しがっているのは前者だが、`left_observation` の内訳には後者の方が近い場面がある。

### ⚠️ ただし採用の障壁は「取得できるか」ではなく **「同じ handle から本文が読めるか」**

⚠️★★★ **同じ focused 要素から `kAXValueAttribute` を読めば本文が取れる。**
★ これは `survey §5.2` が **Windows の UIA を却下した理由の逐語そのもの**である:

> **同じハンドルから本文が読める**ため、境界が「能力」でなく「**方針**」にしかならず、**静的に監査できない**

⚠️ さらに `AXUIElementGetPid()` は任意の要素から PID を返す。
→ ★ **「引数に pid を取らない」は呼び出し規約の話であって、能力の話ではない。**

### ⚠️ 未確認（★ 実機が要る）

| # | 未確認 | ★ 確認方法 |
|---|---|---|
| 1 | system-wide 要素の `kAXFocusedUIElementAttribute` が **安定して返るか** | ⚠️ `rdar://10969414`（"Accessibility SystemWide object does report the focused application"）が historical に報告されている。★ 実機で連続取得して欠測率を測る |
| 2 | Accessibility TCC 以上の権限が要らないか | ★ GSE は既に **Input Monitoring → Accessibility のフォールバックチェーン**を持つ（技術的制約 6）→ **新しい権限ダイアログは増えない見込み**。⚠️ 要実測 |
| 3 | 主要アプリ（Terminal / Xcode / VS Code / Chrome）で `AXRole` が何を返すか | ★ 実機で列挙する。⚠️ **Electron 系は AX 実装が独自**で、`AXWebArea` を返すとは限らない |

## A-2 ★★★ **より重要な訂正 — 私が作った Windows / macOS の非対称は、実は無い**

⚠️★★★ **§0 の表は「Windows は識別子ゼロで出せる / macOS は出せない」と書いたが、これは誤解を招く。**

| | Windows | macOS |
|---|---|---|
| ★ 読むもの | **ウィンドウクラス名**（`Chrome_WidgetWin_1` / `CASCADIA_HOSTING_WINDOW_CLASS` / `HwndWrapper[...]`） | **bundle identifier**（`com.google.Chrome` / `com.apple.Terminal`） |
| ★ 保存するもの | **カテゴリのみ** | **カテゴリのみ** |
| ⚠️ 読むものの性質 | **アプリ指紋** | **アプリ指紋** |

→ ★★★ **どちらも「アプリ指紋を in-memory で読み、カテゴリだけ残す」である。同じ形である。**
⚠️ **クラス名が「識別子ではない」というのは形式論**であって、
**§1.2 の差 #2 で自分が書いたとおり「事実上アプリ指紋」**である。

→ ⚠️★★★ **したがって本当の論点は「Windows か macOS か」ではなく、
「アプリ指紋を in-memory で読むことを許すか」の一点である。**
★ 許すなら両 OS でできる。許さないなら両 OS でできない。**非対称は私が作った幻である。**

★ ただし **1 つだけ本物の差が残る**: **静的監査可能性**。
- Windows の `GetClassNameW` は **クラス名しか返さない**（★ 同じ呼び出しから本文は取れない）
- macOS の `NSRunningApplication` も **本文は取れない**（★ bundle id とアプリ名だけ）
- ⚠️ **A-1 の AX 経路だけが本文へ到達できる** → ★ **A-1 と「bundle id を読む」は別の危険度**である

## A-3 ★ したがって macOS の自前解決策は **3 つある**（⚠️ 採否は決めない）

| 案 | 中身 | ★ 静的監査 | ⚠️ 代償 |
|---|---|---|---|
| **M-1** | `NSWorkspace.didActivateApplicationNotification` → **bundle id を in-memory で読み**、ローカル写像表でカテゴリ化、**カテゴリだけ保存** | ✅ **可能**（写像表がソースにあり `grep` できる／同じ呼び出しから本文は取れない） | ⚠️ **ADR-012 D4 L-c 逐語「`NSRunningApplication` を呼ばない」を書き換える**ことになる。★ **Windows の R-2 と同じ判断**であり、**セットで裁くべき** |
| **M-2** | **ユーザー宣言** —— 本人が「これは editor」と一度だけ宣言する。ログにはカテゴリのみ | ✅ **可能**（★ **OS API を 1 つも呼ばない**） | ★ **ADR-010 D3「宣言から取る」と完全に整合**・**両 OS で対称**。⚠️ 宣言 UI が要る（**ADR-014 Migration 7-ii で既に別タスクとして立っている**）。⚠️ 写像表は**本人の設定ファイル**に残る（★ ただし**本人が書いたもの**であり、システムが収集したものではない） |
| **M-3** | **A-1 の AX 経路**（focused 要素の `AXRole`） | ⚠️★★★ **不可**（同じ handle から `kAXValueAttribute` で本文が読める） | ⚠️ **Windows の UIA を却下した理由に正面から当たる**。★ 採るなら **Windows の UIA も同時に開ける**のが筋（非対称を作らない） |

### ★ 私見（⚠️ 決定ではない）

★ **M-2（ユーザー宣言）が repo の既決と最も整合する。**
理由: ⚠️ **`task_kind` について既に同じ判断を下している**（ADR-010 D3「観測から推定しない・宣言から取る」）。
→ ★ **役割カテゴリだけ観測から取るのは、同じ問いに 2 つの答えを持つことになる。**
★ かつ **宣言 UI は R3-b の前提としてどのみち作る必要がある**（Migration 7-ii）。

⚠️ ただし **M-2 は「本人が宣言していないアプリ」を `unknown` にする** ——
★ **`Other` バケットの擬似識別子性（§1.2 差 #1）はここでも効く。**
