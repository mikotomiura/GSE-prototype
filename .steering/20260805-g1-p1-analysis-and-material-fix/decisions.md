# 重要な設計判断

## D-1: `topic02_lo` の不整合は「割引券の側」を定額制に合わせて直す

- **判断日時**: 2026-08-05（研究者が選択肢 A を選択）
- **背景**:
  研究者が P-1 の 3 ブロック目（LO 条件・`topic02_lo` 商店街の駐輪場）を書いている最中に
  「文章の整合性が保たれていない」と気づいた。**指摘は実在の不整合だった。**

  ```
  料金表: 最初の二時間は無料、それ以降は一日百円である。      ← 時間に対して非線形な定額制
  割引券: 五百円以上買うと二時間分の追加無料券がもらえる。    ← 時間単位で額面が定義される券
  ```

  ⚠️ **定額制のもとでは「二時間分」に対応する金額が料金表に存在しない。**
  同じ券が、2〜4 時間の駐輪なら 100 円まるごと不要になり、4 時間超なら支払いが 1 円も変わらない。
  ★ **論理的な矛盾というより「額面の単位が料金表と噛み合っていない」**のだが、
  要約しようとすると**その食い違いをどう書くか決めなければならない**点で被験者への負荷は同じである。

- **★ なぜこれが軽微でないか（操作の妥当性の問題である）**:
  `preregistration.md §2.2` は条件をこう定義している。

  | 条件 | 課題 | 認知的な性格 |
  |---|---|---|
  | **LO** | 与えた **1 本**の資料を要約する | knowledge-**telling** |
  | **HI** | 与えた **3 本の相互に矛盾する**資料を統合する | knowledge-**transforming** |

  ★ **「矛盾を統合する仕事」は HI にだけ割り当てられている。**
  LO の資料が内部で食い違っていると、**LO でも transforming が発生し、操作そのものが薄まる**。
  → ⚠️ これは「読みにくい文章」の問題ではなく、**HI/LO のコントラストを削る交絡**である。

- **選択肢**:
  - A: **割引券を「その日の駐輪料金が無料になる券」に変える**（料金表は温存）
  - B: 料金表を「それ以降は一時間五十円」に変える（券の文言は温存）
  - C: 直さない
- **採用**: **A**
- **理由**:
  - 「最初の 2 時間無料＋以降は一日いくら」は**実在の駐輪場に多い形**であり、
    B（時間制）に変えると資料の現実味が落ちる。★ **不整合の原因は券の側の単位**なので、
    直す場所も券の側が素直である。
  - C は `§2.8` が明示的に許している是正機会（下記）を捨てることになる。
- **★ 事前登録に抵触しないことの根拠**:
  `§2.8` の凍結条項が**そのものずばり**を許可している。
  > ★★ **パイロットの結果を見て変えてよいのは「課題文・実施手順・ブロック長・資料の量」だけ。**
  > **§3 の判定基準は変えない。**

  → ★ **課題文の是正は P-1 の本来の産物であり、第 10 版の論証は要らない。**
- **トレードオフ**:
  - 「割引券」という語を落として「券」にしたため、後段の「割引券の利用は約九千枚」を
    「この券の利用は」に直した（★ **語を消したら参照側も数え直す**）。
  - ⚠️ 資料総文字数が 490 → **488 字**に動いた。hi=473 との差は 3.5% → **3.1%**（許容 5% 以内）。
    ★ 一度 494 字（差 4.3%）まで膨らんだ案を、余白が 2 文字しか残らないので採らなかった。
- **影響範囲**:
  - ⚠️ ★ **Drive に置いた `G1_実施用_macOS/block03.html` は本文が古いまま**になった（下記 D-4）。
  - P-1 macOS 回の LO ブロックは**旧版の課題文で取られている**。
    ★ ただし `§2.8` により **P-1 は判定をしない**ので、遡って無効になるものは無い。
- **見直しタイミング**: 確証実施の配布物を作り直すとき（旧版が混ざっていないか確認する）。

## D-5: 「消去して次のブロックへ」は、遷移を足すのではなくラベルを直す

- **判断日時**: 2026-08-05
- **背景**: 研究者の指摘「html の箇所で、『文章を削除してから次のブロックに進む』を押しても

  ```js
    pad.focus();
  });
  ```

  2. `preregistration.md §2.13` = 「**次のブロックのファイルを先に開かない**」。

  ⚠️ ★ **最初に書いた 3 本のうち 2 本は、何を壊しても赤にならなかった。**
  ★ **検査を書いた ≠ 検査したことになる。**
- **影響範囲**: `writing-pad.html` / `protocol.md` の当日チェックリスト /
  `record-sheet-pilot.md` / ★ **配布済みページ**（D-4）。

```
実測 734x750:  footer の下端 = 757px  > viewport 750px   → count_in_viewport: false
```

★ **告知が出るのは「文字数を控えてください」と言う場面そのもの**なので、
これは最悪の壊れ方だった。→ `position: fixed` で層を分け（レイアウトを 1px も動かさない）、
発火時に footer を `scrollIntoView` する。修正後は前後とも `footer_bottom = 706` で不動。

> ★ `browser-verification` skill の主張（**機械検査が全部緑でも実物は動いていないことがある**）を
> そのまま踏んだ実例である。

## D-7: G1 専用化は「**フォルダにマーカーを置く**」で実現する（研究者案・採用）

- **判断日時**: 2026-08-05（研究者案「ディレクトリ直下で G1-app みたいなフォルダを作って、
  そこにアプリのコピーを入れた上で G1 専用のアプリにすればいい」）
- ★ **本セッションでは実装しない**（コンテキストの都合により次セッション）。ここは**設計の確定**である。

### ★ 実測が置き場所を決めた

```
バンドル内に g1.mode を置く → codesign --verify --strict:
  "a sealed resource is missing or invalid"
```

⚠️ ★ **`.app` の中にマーカーを入れる案は使えない**（署名が壊れる）。
→ ★ **置き場所はバンドルの外＝フォルダ側しかない。研究者案がそのまま正解だった。**

⚠️ 検証は `/Applications/gse-next.app` の**複製**に対して行った。実物は無傷
（`codesign --verify --strict` が通ることを事後に再確認した）。

### ★ 新しい仕組みを発明しなくてよい

`lib.rs:846-856` が**既に同じことをしている**——「提出する」が `current_exe()` の隣から
`gse-submit` を解決しており、**mac = `.app/Contents/MacOS/` 内 / Windows = `.exe` と同階層**という
プラットフォーム分岐まで書かれている。★ 先例に倣うだけでよい。

### 形

```
G1-app/                     ← ★ このフォルダに居ることが「G1 専用」の意味になる
├── g1.mode                 ← マーカー（起動時に読む）
├── gse-next.app            ← ★ 署名に触らない（中身は 1 バイトも変えない）
├── block01.html … block10.html
└── README_先に読む.txt
```

マーカーの探索は `current_exe()` から **mac は 4 階層上 / Windows は 1 階層上**
（mac: `…/G1-app/gse-next.app/Contents/MacOS/gse-next` → `G1-app`）。

### ★ なぜこの置き方が効くのか

- ⚠️ ★ **起動時に読む**ので、`lib.rs:1924` のコメントが守っている性質
  （「スレッドごと止めるのは『発火はしたが黙殺した』状態を残さないため」）を**壊さない**。
  ★ **UI の実行時トグルにするとここが崩れる。**
- ★ **コピーごとに効く**ので、`/Applications` の普段の GSE は従来どおり。
  → `§5.4` の「既定（未設定）では従来どおり起動する」が**文字どおり保たれる**。
- ★ **物として見える**ので、事後に人が確認できる。
- ★ ターミナルも env も launcher も要らない。

### ★ `§5.4` の扱い — 「手段の差し替え」ではなく「**引き金を 1 本足す**」

⚠️ ★ **env の経路（`probes_disabled_by_env`）を消さない。** マーカーは第 2 の引き金として足す。

| `§5.4` の主張 | この案での状態 |
|---|---|
| 「G1 の実施時はプローブスケジューラを起動しない」 | ★ **強化される**（忘れられない経路が 1 本増える） |
| `probes_disabled_by_env` の実装 | **無変更** |
| 「既定では従来どおり起動する」 | **無変更**（マーカーが無ければ何も変わらない） |
| `§5.4-2` の客観検証（probe 行 0） | ★ **無変更。絶対に残す** |
| 合格経路が増えていないこと | ★ **増えない**（止める経路が増えるだけ） |

⚠️ それでも `§5.4-1` は実装を名指ししているので **第 10 版として記録する**。
★ ただし論証の向きは「置き換え」より素直になる。

### ⚠️ これでも解決しないもの（★ 期待を持たせない）

1. ★ **初回の Gatekeeper は残る。** `.app` は ad-hoc 署名で未公証。Drive / zip 経由で
   受け取った時点で quarantine が付く。★ **フォルダに入れても署名の問題は消えない。**
   消せるのは案 4（Developer ID ＋ 公証・$99/年）だけである。
2. ⚠️ **再起動 10 回はこれだけでは減らない。** 減らすにはログのローテートが要る
   （`SessionLogger::start` が `run()` から **1 回しか呼ばれていない**のが原因・`lib.rs:1530`）。
   ★ フォルダ案とは独立に効くので、両方入れると「フォルダのアプリを 1 回開くだけ」になる。
3. ⚠️ ★ **二重起動**。普段の GSE（Phase1 第 2 週モード）を動かしたまま G1 アプリを開くと、
   **両方がキーボードを掴んで打鍵が 2 本の NDJSON に割れる**。
   今は launcher の `pgrep` ＋ quit が防いでいる。→ ★ **G1 アプリ側で検出して止める**必要がある。
4. ⚠️ ★ **マーカーが外れると黙って通常モードになる**（アプリをフォルダから出す・マーカーを消す）。
   → ★ **画面に「G1 モード」を出して fail-loud にする**。`meta` 行にも記録して事後検証できるようにする。
   ⚠️ ただし `meta` にフィールドを足すと `schema_dto.rs` / `emit_schema` / gse-dataset の
   parity check に波及する（**追加は加算的だが、schema 再生成は要る**）。
