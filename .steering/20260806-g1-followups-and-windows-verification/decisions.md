## D-2: F-1（二重起動の検査を何回やるか）— ★ **測ってから「非同期で毎ブロック」にした**

- **判断日時**: 2026-08-06
- **背景**: code-review M6「二重起動の検査が**起動 1.5 秒後の 1 回だけ**」。前セッションは
  「`start_session` の先頭で呼べば済むが、★ **子プロセス起動が応答時間に載る**ので**測ってから入れる**」
  として送っていた。
- **★ 実測（2026-08-06・macOS 26.5.2・`other_instance_running()` を 5 回）**:

  ```
  run 0: 28.201709ms (found=false)
  run 1: 19.029416ms
  run 2: 18.815875ms
  run 3: 18.536ms
  run 4: 18.101708ms
  ```

  → ★ `/usr/bin/pgrep` の**子プロセス起動に 18〜28 ms**。
  ⚠️ ★ **Windows の `tasklist.exe` は計測していない**（この環境からは測れない）。
- **選択肢**:
  - A: `start_session` の先頭で**同期**に呼ぶ → ⚠️ 「開始する」の応答に 18〜28 ms（Win は不明）が載る
  - **B**: 応答を先に返し、**別スレッド**で聞いて結果だけ emit する
  - C: 定期ポーリング（例 30 秒ごと）→ 子プロセス起動が実施中ずっと繰り返される
  - D: 入れない（現状維持）
- **採用**: **B**
- **理由**: ★ **測った結果、同期にする理由が無くなった**。非同期なら
  「応答時間に載る」という送り理由そのものが消え、**Windows の `tasklist` が遅くても影響しない**
  （★ 未計測のものに賭けなくて済む）。C は実施中の負荷が読めないので採らない。
- **トレードオフ**: 警告が数十 ms 遅れて出る（人が読む警告なので実害なし）。
  ★ 検査は **`!was_active` のときだけ**走らせる（連打で毎回子プロセスを起こさない）。
- **影響範囲**: `lib.rs` の `spawn_duplicate_instance_check`（`setup()` と `start_session()` が共用）。
- **見直しタイミング**: Windows で `tasklist` の実コストが測れたとき（`windows-verification.md` W-5）。

## D-3: F-3（空 NDJSON）— ★ **順序の問題なので順序で直す**。一次資料で確認した

- **判断日時**: 2026-08-06
- **背景**: `20260805…/decisions.md` R-8 結果 4。★ **私が入れた退行**である。
  single-instance に止められた 2 個目のプロセスが、止められる前に NDJSON を作ってから死ぬ。
  提出側（`packaging::has_any_data_row`）で緩和済みだが、
  ★ **本筋は `SessionLogger::start` を single-instance 判定の後ろへ動かすこと**と書かれていた。
- **★ 一次資料での確認**（★ memory や前回の発言を根拠にしない）:
  - `tauri-plugin-single-instance` 2.4.3 `src/platform_impl/{macos,windows}.rs`:
    2 個目は **プラグインの `setup` フックの中で `std::process::exit(0)`**。
  - `tauri` 2.10.2 `src/app.rs`: プラグイン初期化は **`Builder::build()` の末尾**
    (`initialize_plugins`)、**ユーザーの `.setup()` クロージャは `App::run()` の中**
    (`fn setup()` → 設定ウィンドウ生成 → ユーザー setup)。
  - → ★ **`.setup()` に置けば、2 個目はファイルを作る前に死ぬ。**
- **選択肢**:
  - A: `SessionLogger::start` ごと `.setup()` へ移す → ⚠️ 先に起動する分析/IME/監視スレッドが
    `log_tx` を要求するので、**スレッド起動もろとも `.setup()` へ動かす**大改造になる
  - **B**: **2 段階に割る**。`LogChannel::new()`（channel と共有ハンドルだけ）を `run()` で、
    `start()`（ファイルを開く＋スレッド起動）を `.setup()` で
  - C: 直さない（提出側の緩和だけで済ませる）
- **採用**: **B**
- **理由**:
  - ★ **`.manage()` の順序に触らずに済む**（前セッションが「別タスク」に送った理由がこれだった）。
    `SharedLogTarget` を先に作り、`start()` が**同じ Arc を上書き**する形にした。
  - ★ `SessionLogger::start` のシグネチャを変えないので、**既存テスト 8 か所が無改変**。
  - ⚠️ C を採らないのは、`has_any_data_row` が**提出時にしか効かない**ため。
    空ファイルはセッションフォルダに残り続け、研究者の集計時に紛れる。
- **トレードオフ**:
  - ⚠️ `start()` 前に送られた行は bounded(512) に溜まる（`run()`→`.setup()` は同一スレッドで数 ms）。
  - ⚠️ `LogStatus` の初期値が要る。★ **`Ok` ではなく `Disabled{ LOGGER_NOT_STARTED }`** にした。
    `Dashboard.tsx` は起動時に **1 回だけ**読んでポーリングしないので、
    ★ **偽の緑が貼り付くより、偽の警告が出るほうがまし**（fail-loud の向き）。
    ⚠️ そもそも `.setup()` が返るまで IPC は処理されない（イベントループが動いていない）ので
    観測できないはずだが、★ **「はず」に賭けない側へ倒した**。
- **影響範囲**: `logger.rs` / `lib.rs` / `run.sh §5.1`。
  ★ 提出側の `has_any_data_row` は**残す**（起動直後のクラッシュ・ディスク不足でも空ファイルは出る = 二重化）。
- **見直しタイミング**: Tauri の初期化順序が変わったとき（★ 上の一次資料をもう一度読む）。

## D-5: Windows 検証は「手順書 ＋ 手動発火ビルド」まで（★ **実施はしていない**）

- **判断日時**: 2026-08-06（研究者選択「先に Windows ビルドを CI で作るところから」）
- **背景**: ⚠️ ★ 本セッションの実行環境は macOS であり、**Windows 実機に触れない**。
- **★ 一次資料での確認**（`.github/workflows/ci.yml`）:
  - Windows の portable exe を作るのは `build-windows` ジョブ**だけ**で、
    従来は **タグ push（`v*`）でしか動かない**。
  - タグを切ると (a) `build-macos`（self-hosted `gse-mac` が要る）も走り、
    (b) `release` ジョブが **GitHub Release を作る**。
- **採用**: `workflow_dispatch`（手動発火）を追加し、**`build-windows` だけ**を走らせられるようにする。
  `check` / `frontend-check` は手動発火では走らせない（self-hosted の macOS が offline だと
  ジョブがキューへ滞留するため）。`release` の `if` は**タグ限定のまま**なので Release は作られない。
- **理由**: 検証のためにバージョン番号を 1 つ消費し、Release を作り、self-hosted ランナーを
  要求するのは重すぎる。★ 一方で「開発ビルドを配らない / 検証しない」（`protocol.md §4b.1`）は守る。
- **トレードオフ**: 成果物は Actions の artifact（**7 日で消える**）。
- ⚠️ ★ **確かめていないこと**: **`workflow_dispatch` はまだ 1 回も発火させていない。**
  ★ `actionlint` は通っている（既存の 2 件は HEAD にもある既知の指摘）が、
  **lint が通ることと発火することは別**である。
- **影響範囲**: `.github/workflows/ci.yml` / `windows-verification.md` / `protocol.md §1.1`・`§8`。
