# 判断の記録

## 判断 1（2026-10-09・研究者の問いへの回答）: IME 論文は EH1・EH2 そのものではない

- **問い**（研究者の逐語）: 「EH1, 2 に近いものはすでに IME 論文の paper1 で検証されたのでは?」
- **確かめたこと**（`papers/ime-observation` の README・`experiment/preregistration.md` §1.1〜§1.3・§6.8・§6.10・`kit/logger/manifest.json`）:
  - 論文の問いは 5 つ（検出・区間ごとの一致・テキストごとの一致・テキストの復元可能性・実行コスト）。合成入力で、参照の入力欄と記録係（ロガー）を比べた。推定だけで、合否を出していない（§1.2「The study estimates; it tests no hypothesis」）。
  - ロガーは GSE の入力層（`hook`・`ime_compose`・`ime_cloak`・`ime_mode`・`key_gate`）を逐語で写している。F 系列の計算（`features.rs`）は写していない。
  - 参照の入力欄以外のアプリは範囲外（§1.3）。
- **結論**:
  - EH1（形の生成器の検査）と EH2（壁紙の面）は論文の対象外。
  - 重なるのは (a) 前提の一部（IME を使った日本語入力でキーの種類と時刻が届くか・参照の入力欄・合成入力・2 つの IME の範囲）と、(b) 方法の型（§6.8 の漏れの攻撃 → E1-3、§6.10 の実行コストの計器 `kit/e3` → EH2 の CPU）。
  - EH1 は合成の特徴の記録で回すので (a) に頼らない。(a) が効くのは実際の入力を通す EH2・EH3。
- **影響**: E1-3 は §6.8 に倣い、攻撃者の最大（分類器の良い方）を取る（設計 §3.1・§6）。`kit/e3` は `papers/` の規約（GSE 本体から参照しない）があるので使うなら写す。EH2 は Windows / macOS とも OS の API を直接測る形にした（設計 §4）。

## 判断 2（2026-10-09・研究者・AskUserQuestion 4 問・すべて推奨どおり）: タスクの範囲と EH1 の基準

- **決定**:
  1. タスク名 `portrait-eh1-eh2`。
  2. EH1 の合否の基準は、設計書の値（E1-3: 上乗せの 95% 区間の上限 < 0.03・陽性対照の下限 > 0.10 でなければ判定不能 ／ E1-6: 比の 90% 区間が [0.8, 1.25] の中 ／ 順序の感度: 比 ≥ 3 を全画面と投影の両方で ／ E1-4・E1-7: 違反 0 ／ E1-1・E1-5: コードの検査 ／ E1-2: 記述 ／ E1-8: 候補を描くだけ）で、回す前に固定する。
  3. 生成器は仮の文法を数種並べて因子にする。/reimagine は使わない。
  4. EH2 は機械の部分を自動で回し、仮想デスクトップと画面共有は任意の手の手順にする。Windows 版はこの機械で短く試して元の壁紙に戻す。Mac 版は引き継ぎ先で最初に自己検査を回す。
- **理由**:
  - 判断 8（親）が「許容の値は先に決め、事後に動かさない」を求める。値は同等性の検査の慣例（AUC の差の小さな幅・生物学的同等性の 0.8〜1.25 と 90% 区間）に揃えた。陽性対照が赤にならなければ検査器が働いていないので、合格にしない。
  - 見た目の美しさは EH1 で測らない。生成器を 1 本に絞ると、写像の違い（水準・順序の型・鍵）で漏れ方がどう変わるかが見えない。
  - 壊れたスクリプトを別の機器へ渡さないため、Windows 版はここで試す。
- **却下案**: 値を研究者が別に決める（回すのが遅れる）／合否を置かず記述だけ（親の判断 8 から外れる）／生成器を 1 本に絞って /reimagine（比べられる案が 1 本になる）／ここでは試さない（未検証のスクリプトを渡すことになる）。
- **これで閉じたもの**: `.idea` §8.7-3「EH1 にいつ着手するか」→ 今（O1/G1 の実行中・配布物に入れない）。研究者の逐語「機械のみの検証などであれば実施できる状態であればすぐに行いましょう」。

## 判断 3（2026-10-09・固定の時に Claude が足した細部）: 研究者の承認の後、固定の前に書き足したもの

> ⚠️ 研究者に別に聞いていない。いずれも、承認された基準を**緩めない**向き（合格しにくくなるか、定義の穴を塞ぐだけ）で足した。

| # | 足したもの | 理由 |
|---|---|---|
| 1 | E1-3 の帰無の上乗せの 95 パーセンタイルが 0.03 以上なら、全組を判定不能にする | 帰無は承認の時点で「ラベルの並べ替え」とだけ書いた。手順に偏りがあると、帰無でも上乗せが出る。その場合に緑を出さないための保守側の条件 |
| 2 | E1-3 は 2 つの分類器のうち上乗せの大きい方で判定する | 攻撃者は良い方を選べる（IME 論文 §6.8 の「最大を取る」と同じ考え方） |
| 3 | PC1 は `.idea` §8 の v0 全体（水準の写像 ＋ 止まったら更新）とする | 「止まったら更新」の時刻だけでは、打鍵の有無を条件にした検査で上乗せにならない（時刻が打鍵の有無の関数だから）。その漏れは判断 5 の代償 1 として E1-2 で記述する |
| 4 | E1-4 は「不在の中の最初の更新の直後」と「戻った時点」を比べる | 不在の前の材料が遅れて描かれる分を「不在を写した」と数えないため。時間だけによる変化を取り出す |
| 5 | E1-6 の 0 の扱い（両方 0 なら比 1 など）を固定した | 材料が来たときだけ変わる生成器では、中央値が 0 になりうる。事後に扱いを決めないため |
| 6 | 順序の感度の組では、セッションの鍵を揃える | `keyed` の写像の違いが距離を水増しし、順序の感度を過大に見せないため |
| 7 | 不在 ＝ 60 s 以上の無打鍵（ラベルによらない） | 系から見える定義にする。AWAY と STALL_SILENT は打鍵からは区別できない |

- **限界（固定の時点で書いておく）**: E1-3 はセッションをまたいで学ぶ攻撃者を想定している。本人が 1 セッションの中で自分の写像を覚えることは検査しない（`keyed` の守りはこの想定に頼る）→ EH3 の M-4 で聞く。合成した「停滞」は打鍵の統計の型で、結果はこの生成の仮定に条件づけられる。

## 判断 4（2026-10-09・Claude・事後の是正）: ブランチを `docs/portrait-eh1-eh2` に改名した

- **起きたこと**: ブランチを git-workflow の型どおり `feature/portrait-eh1-eh2` で切り、固定のコミット `abfb2c45` を push した。`ci.yml` は `main` と `feature/*` の push で起動するので、CI が走った（run 37876435457: Mac の self-hosted `gse-mac` の check と build-macos は完了、G-GEAR の self-hosted `gse-win` の check が約 26 分実行中）。計測の run 中は CI を計測機で走らせない、という研究者の指示（2026-10-04・memory）に反した。
- **対応**: 12:17 ごろ run を取り消した（`cancelled`）。ブランチを `docs/portrait-eh1-eh2` に改名して push した（`docs/*` の push では CI は起動しない・`gh run list` で 0 件を確かめた）。以後の push はこの名前だけにする。⚠️ リモートの `feature/portrait-eh1-eh2`（`abfb2c45` を指す）は残っている。消すかは研究者に聞く。
- ⚠️ その時間に計測が走っていたかは確かめていない。走っていたなら、その時間帯（2026-10-09 11:50〜12:17 ごろ）の Mac と G-GEAR の測定は CI と重なった可能性がある。
- **再発防止**: memory `feedback_no_pr_during_measurement` の How to apply に「ブランチを切る時点で `docs/` にする（`experiments/` のコードでも）」を足した。
