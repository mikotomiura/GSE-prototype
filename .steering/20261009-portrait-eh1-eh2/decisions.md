# 判断の記録

## 判断 1（2026-10-09・研究者の問いへの回答）: IME 論文は EH1・EH2 そのものではない

- **問い**（研究者の逐語）: 「EH1, 2 に近いものはすでに IME 論文の paper1 で検証されたのでは?」
- **確かめたこと**（`papers/ime-observation` の README・`experiment/preregistration.md` §1.1〜§1.3・§6.8・§6.10・`kit/logger/manifest.json`）:
  - 論文の問いは 5 つ（検出・区間ごとの一致・テキストごとの一致・テキストの復元可能性・実行コスト）。合成入力で、参照の入力欄と記録係（ロガー）を比べた。推定だけで、合否を出していない（§1.2「The study estimates; it tests no hypothesis」）。
  - ロガーは GSE の入力層（`hook`・`ime_compose`・`ime_cloak`・`ime_mode`・`key_gate`）を逐語で写している。F 系列の計算（`features.rs`）は写していない。
  - 参照の入力欄以外のアプリは範囲外（§1.3）。
- **結論**:
  - EH1（形の生成器の検査）と EH2（壁紙の面）は論文の対象外。
  - 重なるのは (a) 前提の一部（IME を使った日本語入力でキーの種類と時刻が届くか・参照の入力欄・合成入力・2 つの IME の範囲）と、(b) 方法の型（§6.8 の漏れの攻撃 → E1-3、§6.10 の実行コストの計器 `kit/e3` → EH2 の CPU）。
  - EH1 は合成の特徴の記録で回すので (a) に頼らない。(a) が効くのは実際の入力を通す EH2・EH3。
- **影響**: E1-3 は §6.8 に倣い、攻撃者の最大（分類器の良い方）を取る（設計 §3.1・§6）。`kit/e3` は `papers/` の規約（GSE 本体から参照しない）があるので使うなら写す。EH2 は Windows / macOS とも OS の API を直接測る形にした（設計 §4）。

## 判断 2（2026-10-09・研究者・AskUserQuestion 4 問・すべて推奨どおり）: タスクの範囲と EH1 の基準

- **決定**:
  1. タスク名 `portrait-eh1-eh2`。
  2. EH1 の合否の基準は、設計書の値（E1-3: 上乗せの 95% 区間の上限 < 0.03・陽性対照の下限 > 0.10 でなければ判定不能 ／ E1-6: 比の 90% 区間が [0.8, 1.25] の中 ／ 順序の感度: 比 ≥ 3 を全画面と投影の両方で ／ E1-4・E1-7: 違反 0 ／ E1-1・E1-5: コードの検査 ／ E1-2: 記述 ／ E1-8: 候補を描くだけ）で、回す前に固定する。
  3. 生成器は仮の文法を数種並べて因子にする。/reimagine は使わない。
  4. EH2 は機械の部分を自動で回し、仮想デスクトップと画面共有は任意の手の手順にする。Windows 版はこの機械で短く試して元の壁紙に戻す。Mac 版は引き継ぎ先で最初に自己検査を回す。
- **理由**:
  - 判断 8（親）が「許容の値は先に決め、事後に動かさない」を求める。値は同等性の検査の慣例（AUC の差の小さな幅・生物学的同等性の 0.8〜1.25 と 90% 区間）に揃えた。陽性対照が赤にならなければ検査器が働いていないので、合格にしない。
  - 見た目の美しさは EH1 で測らない。生成器を 1 本に絞ると、写像の違い（水準・順序の型・鍵）で漏れ方がどう変わるかが見えない。
  - 壊れたスクリプトを別の機器へ渡さないため、Windows 版はここで試す。
- **却下案**: 値を研究者が別に決める（回すのが遅れる）／合否を置かず記述だけ（親の判断 8 から外れる）／生成器を 1 本に絞って /reimagine（比べられる案が 1 本になる）／ここでは試さない（未検証のスクリプトを渡すことになる）。
- **これで閉じたもの**: `.idea` §8.7-3「EH1 にいつ着手するか」→ 今（O1/G1 の実行中・配布物に入れない）。研究者の逐語「機械のみの検証などであれば実施できる状態であればすぐに行いましょう」。

## 判断 5（2026-10-09・研究者）: EH1 は Windows の機器で回す。Windows は EH1・EH2 の両方、Mac は EH2 だけ

- **決定**: 研究者の逐語「まぁ EH-1 は windows に回す感じにして、windows のみ EH-1, 2 両方回す感じで引継ぎに書くか」。この機械で回していた本番は止めた（design §8・結果は開いていない）。
- **前提の確認**（研究者の問い「EH1, 2 両方とも各機器で回す必要があった感じじゃなかった？」への回答）: EH1 は合成の記録と `gse-replay`（`analysis/`）と Python だけで、OS の API に触れない。`analysis/` は CI のゴールデンの一致で両 OS の同一性が確かめられている。→ 1 台で足りる。OS ごとに別物なのは EH2（壁紙の API・仮想デスクトップ / Spaces）。
- **補記（2026-10-09・研究者の問い「API などで win, mac ごとにロジックが変わるので、mac でも EH1 を回した方がよいことはないか」）**: 一次で確かめた。
  - macOS の入力層は Mac のキーコードを Windows の仮想キーコードに変換して記録する（`input/hook_macos.rs` の `macos_vk_to_vk`）。→ 合成の記録に Windows のキーコードを入れたのは両 OS で正しい形。
  - `analysis/` の中で OS で分かれるのは 1 か所だけ: キーリピートの判定（`analysis/loop_step.rs:238` の `#[cfg(target_os = "windows")]`）。Windows は「同じキーを離す前にもう一度押した」押下をリピートとして F1・F4 から除く。macOS は hook の段で autorepeat を捨てるので、解析は判定しない（`input/hook_macos.rs:525・622`）。→ 合成の記録では、この重なりは押下の **0.069%**（スモークの P の 506,227 押下中 351）。窓ごとの F1（中央値）・F4 への効きは小さく、判定を変えるとは見ていない（確かめてはいない）。
  - EH1 は入力層（OS の API）を通らない（合成のキーの行を `gse-replay` に直接渡す）。→ OS ごとの入力の違い（IME・観測するキー）は、どちらの OS で EH1 を回しても検査できない。それを見るのは実際の入力を通す EH2・EH3。
  - → **Mac で EH1 を回す必要はない**と判断した。EH1 は Windows の解析（リピート判定あり）で回した、と notes の限界に書く。
- **引き継ぎ**: `next-session-portrait-eh2-windows.md` を EH1 ＋ EH2 に書き直し、`next-session-portrait-eh1-eh2-windows.md` に改名した（EH1 と EH2 は同時に回さない —— EH2 は CPU を測る）。Mac は EH2 だけ（最初に `swiftc -typecheck`）。

### 研究者の決定（AskUserQuestion・2026-10-09・4 問・すべて推奨どおり）

1. **U-4（更新の文法）**: 「**不在の中では更新しない**」を**第一候補**にする。⚠️ 確定ではない —— 固定の外の探索なので、EH1 の第 2 回で E1-3・E1-2 を当ててから確定する。

3. **次の段**: **EH1 の第 2 回を新しい固定で**回す。中身の候補（第 2 回の設計で決める）: 既定の scheduler のもとで働く陽性対照（PC2 の作り直し・材料の情報を形に強く写す版）・E1-3 の攻撃者に更新の間隔に揃えた窓を足すか・揺らしに強く経路を写す文法への作り直し・`recent` を E1-3・E1-2・E1-6 の固定の組に入れる・`run.sh` の `.exe` と `--jobs`（判断 W1・W2）。EH3 の事前登録と ADR はその後。
4. リモートの `feature/portrait-eh1-eh2`（`abfb2c45`）を**消した**（`git push origin --delete`・2026-10-09）。

- **理由**（3 の推奨）: 親の判断 8 は「形が停滞を写していないことを、参加者の前に機械で確かめる」を求める。E1-3 が両 world で判定不能のまま EH3 に進むと、未検証の形を人に見せることになる。
