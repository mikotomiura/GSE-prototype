# 設計 —— 背景のステージの机上の検査・6 回のまとめ

## 実装アプローチ

既にある 6 回の判定・読み・限りを写して、研究者の判断の材料を 1 つのファイル（`summary.md`）にまとめる。新しい計算はしない。判定を作り直さない。言い方は各回の固定した読み方（各 design の §3.3 と追加の文）の範囲に留める。

### `summary.md` の節（decisions 判断 2〜4）

0. 冒頭の注: EH0・合成の列だけ・「見つかった／見つからなかった」まで・合成した停滞は打鍵の統計の型・揺れの形は Claude が選んだ一例・「GSE が示した」と書かない。
1. もともと何を確かめたかったか: 親タスクの判断 4（試作を作るか否かを安く決める）・項目 1〜6・測らないこと（`E-14`・状態計として読むか・ゲーム化）・項目 1 の合否の形（A_speed を基準・0.03・攻撃者 4 通り・PC1・PC-stall・土台・帰無）。
2. 6 回の流れ: 各回が何を変え、なぜ次の回へ進んだか（1 段落ずつ・各回の decisions の判断を指す）。
3. 主表（`check_summary.py` が照らす）: 回・world と段・下見 0 の状態・L300 の AUC(A_speed)（hgb / lr）・ラベルごとの判定の数。原因の切り分けは判定を作らないので、読みの数の小さな表を別に置く（照らさない・notes の表を写す）。
4. 分かったこと（各回の notes の読みを写す）。
5. 分からないこと: 読み 1 と読み 2 の別・倍率の成分の効き・人の打鍵での形。
6. 計器の限り: 天井・PC-stall が帯に届かない条件（格子の上端・L60 の λ）・1 つの seed で列が world の間で対にならない・赤を最後の判定まで通す端から端の検査が無い・所要（rank の遅さ）・規則の探索的な出どころ（第 2 回以降）・§4 の逸脱（揺れの world）。
7. 親タスクの判断への材料: 判断 3（秒未満）・判断 4（試作）・判断 5（訂正を読まない）と、項目 2〜4・6 の短い要約。
8. 次に問うなら: 読み 1・2 を分ける案と、背景のステージの次の段の選択肢（得るもの・費用・限り）。Claude の見立ては見出しで分け、「見立て・決定ではない」と書く。
9. 一次への指し示し（6 回の design・notes・decisions と結果の dir）。

### 主表の形（機械で照らす）

- `<!-- main-table:begin -->` と `<!-- main-table:end -->` の間に置く。各行の最初の列は行の鍵（`r1-v4` など）で、`check_summary.py` の `SOURCES` が鍵ごとに一次の JSON の場所を持つ。
- 判定の数の書き方: `緑 N`・`赤・検出 N`・`赤・未確認 N`・`判定不能 N` を `・` でつなぎ、0 の区分は書かない。走っていない段は `走っていない（天井）`。一次の語との対応は `green`→緑、`red_detected`＋`red_detected_stop_path`→赤・検出（`stop_path` はどの回でも 0 本で、検査はそれも確かめる）、`red_unconfirmed`→赤・未確認、`undecidable`→判定不能。
- AUC は小数 3 桁（一次の値を丸めたもの）。本番を回した段は本番の `summary.json` の `_detector.L300.auc_A_speed`、天井で止めた段は `ceiling.json` の L300 の値。

### `check_summary.py`

- 引数: リポジトリの根（既定はこのファイルから 2 つ上）。`summary.md` の主表を読み、`SOURCES` の各鍵について一次の JSON から期待の値（状態・AUC 2 つ・3 ラベルの判定の数）を計算して比べる。
- 落ちる条件: 鍵の欠け・重複・余分、値の違い、数の 24 本の合計の違い、`stop_path` の非 0、一次のファイルの欠け。`bad N` を出し、N > 0 なら終了コード 1。
- 変異（使い捨て）: 数を 1 つ変える・行を消す・ラベルの列を入れ替える・AUC の桁を変える。どれも落ちることを確かめ、decisions に書く。
