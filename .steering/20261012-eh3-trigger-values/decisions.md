| # | 問い | 決定 |

| 1 | 契機に届く回数を数える材料 | **本機の自分の O1 記録**（`Documents/GSE-sessions` の `gse_o1_*` 5 本・10-09〜10-12・HMM 0.5.0 で今の main と同じ）。判断 3 の実機の記録は消してある |

- **推奨の理由（要点）**: #1 は自然な作業の記録で、推定の版が今と同じなので記録の `p_stuck` をそのまま使える。7 月の検証の記録（P010〜P014）は版が古く、他の人の記録をこの目的に使ってよいか（同意の範囲）を先に確かめる必要がある。#2 は配布物ごとに段が決まり、本番に戻し忘れる恐れが無く、記録から段が読める。
- **却下案**: 7 月の記録も使う／Mac の記録を待つ／定数を書き換える。
- **実装で決めたこと（問いにしない）**:
  - 段は `Assignment::canonical` に含めない。段を替えても、数えた稼働日の台帳を捨てない（研究者が試作の段から本番の段へ印を替えたとき、期間の途中で日が数え直しにならない）。
  - 区間の終わり（閾値未満が 60 秒）も段の閾値で決める。始まりと終わりで閾値が違うと、試作の段で 0.50〜0.60 の間を行き来する区間の扱いが 2 つの閾値の組み合わせになるため。
  - `meta.invitation_trigger` は、印に `trigger=` が無くても EH3 なら常に書く（`"main"`）。無いことを本番と読ませる解析を作らない。

## 判断 2（2026-10-12・研究者・AskUserQuestion 1 回・推奨どおり）: 試作の段の値

- 別に Python で（状態機械を通さず）`p_stuck ≥ 0.60` かつ打鍵から 180 秒未満が 30 秒以上続いた区間を数えた: 41 本・長さの中央値 162 秒（最長 483 秒）・区間中の打鍵の中央値 3 回・打鍵なし 12 本・区間中の値がずっと同じ（`feat` の値が据え置かれた）5 本。自然な作業では、打つのを止めた間が停滞と推定されている。
- **読み**: 判断 3（前タスク）で契機を意図して作れなかったのは打ち方のせいで、自然な作業では本番の値でも招待は出る。試作の段で緩めて変わるのは主に、研究者が手を止めて図像を確かめられるかどうか（判断 3 で手を止めたときの頭打ちは 0.54）。研究者 1 人・4 日・Windows だけの数で、一般化はしない。

**研究者に示した問い（逐語の要点）**: 上の数と読みを示し、「試作の段の契機の値をどれにしますか？」。選択肢: 0.50・10 秒（推奨）／0.55・15 秒（0.54 の頭打ちを越えないので、手を止めるだけでは研究者が意図して出せない）／本番と同じ 0.60・30 秒（目印と記録の欄だけを入れる）。

**決定**: **0.50・10 秒**（`Trigger::PROTO`）。

- **推奨の理由**: 0.54 の頭打ちを越えるので、手を止めれば研究者が図像・失効・窓を確かめられる。自然な作業では契機が 34→41 回、提示が 11→12 回と少し増えるだけで、どの契機も窓の中で 0.60 に届いていた（M-4 を濁す時点で出た例はこの記録には無い）。
- **帰結**:
  - 稿 §10.1 F-2 を「本番の値（凍結の前に決め直す）」と「試作の段」の 2 行に分けた。区間の終わりは段の閾値で決まることも書いた。
  - 本番の値は試作の段の記録を根拠に凍結の前に決める（前タスクの判断 4 の Claude の見立てのまま）。この数を見ると、本番の値を緩める必要は今のところ無い。ただし数えた材料は研究者 1 人の 4 日だけ。
  - 停滞の区間の多くが「打鍵が止まった間」であることは、M-4（招待の時点の読み）と Stuck の推定の妥当性に関わる。本タスクの範囲の外なので記録だけ残す。
