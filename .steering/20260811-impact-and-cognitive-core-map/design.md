## §1 ★ まず事実 — 推論が実際に読んでいる入力は 2 種類しかない

**一次資料（コード）で確認した。docs を根拠にしていない。**

`analysis/` に渡る `InputEvent` は 6 フィールドあるが、**特徴量計算が読むのは 4 つだけ**である
（`features.rs:82` `calculate_features`）:

| フィールド | 推論で使われるか | 実体 |
|---|---|---|
| `timestamp` | ★ **使う** | Flight Time・バースト・ポーズの全ての材料 |
| `is_press` | ★ **使う** | 押下/離上の区別 |
| `is_repeat` | ★ **使う** | キーリピート除外（F1/F4 の精度） |
| `is_backspace` | ★ **使う** | F3 修正率・F6 削除後停止率・BS ペナルティ |
| `vk_code` | ✗ **使わない** | `loop_step.rs:197-206` の `pressed_keys` 重複排除にのみ使用。**特徴量には入らない** |
| ★ `is_paste` | ✗ **使わない** | ★★ **`analysis/` 内でどこからも読まれていない**（`features.rs` のテスト初期化のみ）。コメント自身が「**FeatureExtractor は本フラグを読まないため FeatSnapshot に影響しない**」と明記（`features.rs:13`） |

> ★★★ **つまり推論が見ているのは「いつキーが上下したか」と「それが BS/Del か」の 2 種類だけである。**
> **何のキーを打ったかも、貼り付けたかも、推論には 1 バイトも入っていない。**

そこから先の経路（すべてコードで確認）:

```text
InputEvent(時刻 + is_press + is_repeat + is_backspace)
   ↓ features.rs  30 秒ローリングウィンドウ
F1 FT中央値 / F3 修正率 / F4 バースト長 / F5 ポーズ回数 / F6 削除後停止率
   ↓ φ(x,β) = clamp((x−β)/(2β), 0, 1)          ← κ=2.0 固定
X = 0.30φ(F3)+0.25φ(F6)+0.25φ(F1)+0.20φ(F5)   ← engine.rs:336・手決めの重み
Y = 0.40φ(F4)+0.35(1−φ(F1))+0.25(1−φ(F5))
   ↓ 5×5 量子化
obs = x_bin*5 + y_bin (0..24)  ＋  obs=25 (BS streak penalty)   ← 計 26
   ↓ HMM  transitions[f64;9] + emissions[f64;78] = 87 パラメータ・全て手書き定数
p_flow / p_inc / p_stuck
   ↓ intervention.rs   Need(閾値) × Opportunity(小休止/idle/cooldown)
none / defer / nudge / wall
```

★ **IME（`ime_open`）の役割は 2 つだけ**で、特徴量には入らない:
1. **β の選択**（`ime_open ? β_writing : β_coding`・`engine.rs:311`）
2. **BS ペナルティの gate**（`apply_backspace_penalty = pending && !ime_open`・`engine.rs:367`）

> ★★ これは `personalization-and-online-learning.md §1.6-4` の
> 「**特徴量 5 つとも打鍵間隔と BS 回数の派生＝測っているのは実質タイピング流暢性**」を
> **コードで裏取りしたもの**である。しかも実体はそれより狭い——**vk_code すら使っていない。**

### 1.1 ★ ここから直ちに出る帰結

- **「詰まり」は打鍵の変化ではなく「打鍵しないこと」「別行動への切替」として現れうる**が、
  現行の観測空間は**打鍵している間のことしか見ていない**。
- ★ **`paste` は NDJSON に `{"type":"paste"}` として記録されているのに推論に使われていない**——
  実測で **`paste_count`→Q1 = 0.571** は**現行 5 特徴量すべてより上**である。
  **これは新センサーではなく配線の問題**である（Tier 0）。
- 同じく **`keys`（窓内打鍵数）→Q2 = 0.615–0.676** も未配線で、**f4 を上回る**。

## §2 ★ β をタスクごとに変える件 — 直感は正しく、既に採択済み。ただし重要な補正がある

### 2.1 決定は既に存在する（ADR-006・**Accepted**）

> **枠組み = Alternative C「分離」**（研究者採択 2026-07-24）:
> 1. **`task_kind` は「どの domain head を走らせるか」を選ぶ上位ルーティング信号**とし、
>    **β は各 head の所有物に格上げする**（「1 関数内の 2 択 if」から外す）
> 2. **`ime_open` は Writing head 内部の within-writing 信号**として維持（β_writing・日本語 composition・BS gate）
> 3. 実装は Phase1 完了後。**抽出（挙動不変・no bump）と配線（挙動変更・bump）を 2 サブフェーズに分ける**

現状は **`ime_open` の 2 値のみ**で、**`task_kind` は `analysis/` に一切渡っていない**（dead_code）。
→ **「どのドメインの baseline で採点するか」を、宣言された task_kind でなく“その瞬間の IME 状態”が代理している。**

★ **Phase2 でタスクを混在させると代理は破綻する**——
**英字引用を打つ writer は IME off で誤って β_coding**、**日本語コメントを書く coder は IME on で誤って β_writing**。
→ **研究者の直感は、この破綻を先回りしている。**

★ 下位決定も確定済み: **IME off の日本語論述（英字引用・数式・URL）は collapse せず**、
Writing head 内に **`β_writing_latin`**（現 β_coding の値をそのまま改名して流用）を持つ。

### 2.2 ⚠️★★ ただし「β を直せば当たるようになる」ではない

**φ は単調変換なので、順位統計量である C-index をほぼ変えない**（実測差はほぼ **≤0.03**）。
大きく動くのは**飽和がタイを作って情報を壊す方向のみ**である。

| | 実測 |
|---|---|
| φ の故障は本物 | 各項が **6〜9 割の時間レール上**（0 か 1.0 に張り付き） |
| ★ しかし C-index は動かない | P010: f1 0.442→0.435 / f3 0.507→0.530 / f5 0.468→0.472 |
| ★★ 帰結 | **§1.1 の「生特徴量が偶然水準」は β に依存しない結論** |
| ★★ 上限 | β 修正で改善しうるのは**合成 X だけ**（飽和項が非飽和項を洗い流すのを防ぐ効果）で、その上限は概ね**最良の単一特徴量近傍**。P010 の最良は **f4=0.527** → **GATE3 の 0.65 には届かない見込み** |

> ★★★ **したがって β のタスク別化は「衛生管理として正しいが、信号を作らない」。**
> **binding constraint は正規化ではなく観測空間と目的変数である。**
> ⚠️ 実際、当初あった「正規化のオンライン個人適応を先に入れて、正規化が悪いのか信号が悪いのかを切り分ける」
> という段階案は、**この実測により成立しないことが判明して撤回されている**。
> → **β 修正は優先1 ではない。優先1 は G1（統制タスク実験）である。**

★ **さらに個人適応の観点**: 実測では **ICC(1) 概ね 0.05–0.30 で水準の個人差は小さく**、
**写像の符号が人によって反転する**（`keys→Q2` が 3 名 0.60–0.68 に対し P014 だけ 0.368）。
→ **個人適応すべきは β（切片）ではなく写像の係数**である。**β のタスク別化はその前段の衛生に留まる。**

## §3 ★ G1 が答える問い（現状のとおりで正しい）

G1 は **10 ブロック × 5 分**（実働 50 分＋休憩 9 分・約 62 分）:

```text
[1]  copy   5分   positive control ＋ 個人の転写 baseline   ← 位置固定
[2]–[9]     5分 ×8  HI 4 / LO 4（SEED で無作為化・ABBA 釣り合わせ後）
                    ★ ブロック 3〜9 の直後に強制比較を 1 問（計 7 回）
[10] copy   5分   positive control（疲労ドリフト測定を兼ねる）  ← 位置固定
```

**測っているのは**: **打鍵由来の content-free イベントで、同一人物内の高摩擦/低摩擦条件が分離できるか**。

> ★★★ **これが最上流のゲート（G1）であり、本設計の全ての分岐がここに条件づけられている。**
> ★ **軸を `self_directed_recovery_risk` へ書き換えても G1 は免除されない**——
> 「打鍵由来の content-free イベントで作業状態を分離できるか」という**測定可能性の問い自体が未検証**だからである。

### 3.1 G1 の結果による 3 分岐（★ 先に決めておく）

| 結果 | 意味 | 次の一手 |
|---|---|---|
| **(a) 分離できる** | 現行の観測空間に信号はある。Phase1 の failing は**目的変数（主観プローブ Q1）側の問題** | 軸の再定義（`recovery_risk`）＋ Tier 0 配線へ進む。β のタスク別化は衛生として並行 |
| **(b) 打鍵だけでは分離できないが、Tier 0（`keys`/`paste`）を足すと分離できる** | **観測空間の不足**が本体 | Tier 0 → Tier 1（沈黙長の**分布**・focus 喪失/復帰）へ投資。★ 最も可能性が高い |
| **(c) どちらでも分離できない** | **打鍵だけでは読めない**。§8 の「対象モダリティが text work に限定される」より深い制約 | 入力層の再設計（Tier 2）か、★ **MhD を通さない表現（§4 の系統 B）へ寄せる** |

⚠️ **(c) でも研究は死なない**——**GATE2 を満たす十分データ下の真の Kill は「測定法の破綻検出」という貢献**になる。
ただし `DataInsufficient`・課題放棄・計測外移行は**貢献ではなく測定の失敗**であり、**混ぜてはならない**。

## §4 ★★★ 接続設計の核心 — 表現層を `p_stuck` の下流に置かない

### 4.1 いまの鎖は「首」が 1 本しかない

```text
打鍵 → 5特徴量 → φ(β) → X/Y → obs26 → HMM → p_stuck → Need×Opportunity → 介入
                                              ↑
                                    ここに表現層をぶら下げると、
                                    MhD が failing である以上、表現層も一緒に倒れる
```

`.idea` の M1（`ewma_x`/`ewma_y` を写す）も D16（`p_flow/p_inc/p_stuck` を写す）も、
**どちらも MhD の出力に依存している**。
→ ★★ **表現層の妥当性が MhD の妥当性に条件づけられてしまう。**
**MhD は GATE3 に届かない見込みなのだから、これは設計上の欠陥である。**

### 4.2 ★ 提案 — 表現層に 2 系統を分けて入れる

```text
                          ┌── 系統 A（推定経由・外れうる）────────────┐
打鍵(時刻 + BS)  →  5特徴量 → φ(β) → X/Y → HMM → p_flow/p_inc/p_stuck │
     │                                        ewma_x / ewma_y         │
     │                                                                ├──→ 表現層
     └── 系統 B（観測直結・推定を通らない・content-free）─────────────┤
         keys 密度 / 沈黙長の分布 / BS 率 / paste の有無 / focus 復帰  │
                                                                      ┘
                                            ＋ 歩いた/歩かなかった（二値・D10/D11）
```

| | 系統 A（MhD 経由） | 系統 B（観測直結） |
|---|---|---|
| 中身 | `p_flow`/`p_inc`/`p_stuck`・`ewma_x`/`ewma_y` | `keys` 密度・沈黙長の分布・BS 率・`paste` の有無 |
| 性質 | ★ **推定**。意味は豊かだが**外れうる** | ★ **事実**。意味は薄いが**外れない** |
| GATE3 との関係 | ⚠️ **未通過の head で信号を見せると [V75] 放棄理由④（データ品質への懸念）に直撃** | ★ **無関係**（推定していないので当たり外れが無い） |
| MhD が Kill されたら | ✗ 一緒に倒れる | ★ **生き残る** |

> ★★★ **系統 B だけでも「今日の地形」は作れる。**
> 「打鍵が濃かった時間帯」「長い沈黙が入った場所」「書いては消した区間」は、
> **推定を一切通さずに content-free で描ける**。
> → **MhD が Kill でも表現層は独立に立つ。** これが §A の I-1/I-2/I-3 を独立させた話の実装版である。

★ **試作フェーズでやるべきことがこれで確定する**——
**同じ 1Hz 信号を系統 A と系統 B の 2〜3 通りの表現に同時に流して聴き/見比べる**。
これは `design.md`（音トラック）§3 Step 3 と**同一の作業**であり、新しい工程を足さない。

⚠️ **系統 B が「安全だから優れている」ではない**。系統 B は**情報が薄い**——
「濃い/薄い」は写せても「守るべき苦闘か、断つべき停滞か」は写せない。
**その区別こそ GSE の問いなので、系統 A を捨てることは研究の問いを捨てることに等しい。**
→ **2 系統は代替ではなく、倒れ方が違う 2 本である。**

### 4.3 ★★ オンライン学習と表現層の衝突 — 「適応後の値」を写してはいけない

**個人適応が進むと、同じ状態でも表現が変わってしまう。** これは作品としても実験としても壊れる。

> ★★★ **解**: 表現層は **「適応後の値」ではなく「その人の基準からの逸脱」を写す**。
> オンライン学習 Phase A が計算する **`reference_deviation`** が、まさにその量である。
>
> - `reference_deviation` は**個人基準で正規化済み**なので、個人適応が進んでも**意味が保たれる**
> - Phase A は **ラベル不要・O(1) メモリ**（EWMA ＋ robust quantile）で、**最初に入る層**
> - ★ 表現層が要求する量と、オンライン学習が最初に作る量が**一致している**

★ **これは偶然ではない**——[P48] が要求する「**構造ゼロの抽象ではなく『自分の通常』と並置された抽象**」と、
`reference_deviation`（自分の通常からの逸脱）は**同じものを別の語彙で言っている**。

⚠️ **ただし尺度過敏の穴がある**——within-person z は
**同じ |z|=3 が意味する絶対差が被験者間で 6.8 倍違った**という実測がある。
→ ★ **`robust quantile 実装に尺度 floor を置く**（`scale := max(個人scale, コホート尺度 × c)`）。
**これは scope 検出器専用にせず Phase A に置く**——同じ過敏が **`reference_deviation` を含む全ての
within-person z に効く**ためである。

### 4.4 ★ 版の凍結 — オンライン学習と表現層で規律の形が同じ

| | 何を凍結するか | いつ動かしてよいか |
|---|---|---|
| **推定（MhD）** | **潜在状態の意味・構造**（`HMM_VERSION`） | オフライン検証 → version bump → golden 再生成 |
| **表現（マッピング）** | ★ **マッピングの範囲・カーブ・時定数**（`EXPR_VERSION`） | 試作中は自由。**pilot 実施中は絶対に動かさない** |
| **個人適応** | ★ **更新規則**（`update_rule_version`） | 評価期間中は profile を凍結（`past_session_adapted`） |

> ★★ **3 つとも「適応してよいものと、版で凍結するもの」を分ける同じ形である。**
> 統一原則は 1 行で書ける——
> **「値は適応してよい。写し方と意味は版で凍結する。」**
>
> ★ PreReg-5 との両立基準も同じ言い方に落ちる:
> **評価期間のデータが 1 バイトも推定に入らないなら両立、入るなら破る。**

## §6 ★ この設計が壊れる条件（先に書いておく）

| 条件 | 何が壊れるか |
|---|---|
| ★★ **G1 が (c) 分離できない** | 系統 A が空になる。表現層は系統 B のみになり、**「守るべき苦闘の区別」という研究の問い自体が測れなくなる** |
| **Tier 0 を足しても C-index が動かない** | 観測空間の問題ではなく**目的変数（主観プローブ）の問題**が本体だったことになる → L-B 計器の作り直しが先 |
| **`left_observation` の上下界が広すぎる（G2 失格）** | `self_directed_recovery` が目的変数として使えない → 軸の再定義そのものが止まる |
| ★ **`progress_proxy` が対象外作業で最大化する穴が塞がらない** | 写経・タイピング練習を「最高に前進」と判定する。**旧軸と新軸に共通する穴**であり、ADR-010 の `scope_fit` が効かないと Need の計算自体が無意味な区間が残る |
| **個人適応が cold-start を上回らない** | 個人化を入れる理由が消える（`§7.7` の過学習検査で落ちる） |

## §7 テスト戦略

本タスクは**コードを書かない**。Stage 1 以降に進む場合のみ:

- **Stage 1**: `emit_schema` の出力 diff が additive のみであること。`gse-replay --snapshot` が **byte-equal**
  （`HMM_VERSION` を bump しないので golden は不変でなければならない）
- **Stage 1'**: **replay parity が acceptance**（Writing head 抽出は挙動不変）
- **Stage 2**: `HMM_VERSION` bump → ゴールデン再生成 → **差分が意図通りかを `.steering/` に記録**
- **Stage 3**: pinning チェックリスト（初期状態／更新順序／時刻窓／欠損イベント／バージョン移行／
  浮動小数差／途中クラッシュ後再開／**状態スナップショットの schema migration**）
- ★ **Stage 0'（表現層の試作）は GSE 本体に触らないので `cargo test --workspace` への影響ゼロ**。
  影響が出る変更をしたら、それはスコープ逸脱である。
