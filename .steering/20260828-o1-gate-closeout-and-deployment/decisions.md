# 重要な設計判断

## 判断 1: O1 の liveness は「**トレイだけ**」切り離す

- **判断日時**: 2026-08-28（★ 研究者判断）
- **背景**: O1 で「マウスのみ 2 分」→ トレイ「⚠ 計測できていません」＋**生存中フックの再設置**が
  起きることを 2026-08-28 に実機で確認した。★ O1 の宣言 4 択には「デザイン・映像・制作作業」が
  あり、⚠️ そこでは**常態**になる。
  ★ 一次資料で確かめたこと（`lib.rs:4081` 付近）: **トレイ表示と再設置は同じ `HookHealth::Down`
  から発火している**。→ ⚠️ 閾値を伸ばすと**再設置も同じだけ遅れる**。
- **選択肢**:
  - A: O1 の `down_after_ms` を 600 秒にする（★ 実装は最小）
  - B: ★ **トレイの閾値だけ別に取る**（ログ 30 秒 / 再設置 120 秒 / トレイ 1800 秒）
  - C: O1 ではトレイ警告を出さない
- **採用**: **B**
- **理由**: ★ 被験者の目に入る誤警告がいちばん害が大きい一方、⚠️ **復旧力（再設置）と証跡
  （NDJSON の `alive` / `starved_ms`）を 1 つも失わない**のは B だけである。
  A は再設置が 10 分遅れる。C は本当に死んだとき 48 時間が無音で失われうる。
- **トレードオフ**: ⚠️ 本当にフックが死んでいる場合、**被験者が気づくのは 30 分後**になる。
  ★ ただしその 30 分のあいだも再設置は 2 分で試みられ、NDJSON には最初から記録が残る。
- **影響範囲**: `input/liveness.rs`（純関数 `tray_starved` を新設）/ `lib.rs`（配線 ＋ 定数）/
  ゲートの liveness 検査（★ 配線まで見るよう強化）
- **見直しタイミング**: ★ O1 の実データで `starve_window` の分布を見て、30 分でも誤警告が出るなら。

  - A: ★ 検査を「**実測の記録があるか**」に変える

- **トレードオフ**: ★ ゲートは 1 件赤のまま。⚠️ 「配れない」状態は変わらない（★ それが正しい）。
- **影響範囲**: `scripts/check-o1-release-readiness.sh` /

- **見直しタイミング**: B-1 のデプロイ後、実測が取れたとき。

## 判断 3: E-2 / E-3（G1 側の同型欠陥）は**いま直さない**

- **背景**: ★ O1 側で直した 2 つの欠陥（申告 P-ID をメール検証なしで信用する / `last > 1` で
  1 行ロスターを見落とす）が、`GSE_G1_Form_Builder.gs` に**同型で残っている**。
- **選択肢**: A: いま repo を直す / B: ★ **起票して実施の切れ目に回す**
- **採用**: **B**
- **理由**: ⚠️ G1 は**実施中**である。★ repo を直しても**配備済みの Apps Script は変わらない**ので、

  繰り返し踏んでいる事故の型）。→ ★ 貼り直せる切れ目にまとめて行う。
- **トレードオフ**: ⚠️ G1 実施中はその欠陥が残る（★ 実害は「申告した P-ID を信用する」経路）。
- **影響範囲**: `Form_G1/GSE_G1_Form_Builder.gs`
- **見直しタイミング**: ★ G1 の実施が途切れ、Apps Script を貼り直せるとき。

## 判断 4: E-4 は **BOM だけが実体の欠陥**だった（⚠️ 途中の見立てを訂正した）

- **判断日時**: 2026-08-28
- **背景と訂正**: ★ 作業中に「G1 = CRLF / O1 = LF のみ」という差を作業ツリーで実測し、
  ⚠️ 一度は「改行コードも未報告の欠陥だ」と書いた。**これは誤りだったので訂正する。**
  ★ `.gitattributes` に **`*.bat text eol=crlf`** が既にあり
  （逐語コメント:「提出ランチャ: Windows cmd は CRLF 前提。checkout 時に LF 化されると
  cmd のパースが崩れるため CRLF 固定」）、⚠️ **新しく clone すれば CRLF で展開される**。
  ★ 裏づけ: `git show HEAD:…/launch-g1-windows.bat` は **LF で保存**されており、
  `git diff --numstat` は BOM を足した本コミットを **1 行の変更**としか数えない。
  → ★ **作業ツリーに古い LF の写しが残っていただけ**である。
- **採用**: ★ **BOM を足す**（⚠️ BOM は「内容」なので git が保持する = ここだけが実体の差だった）。
  ★ 作業ツリーの改行も CRLF にそろえたが、⚠️ **これは repo の状態を変えていない**。
- **理由**: ★ 実際に配っている G1 launcher と同じバイト形式にする。⚠️ 差が出るとしたら
  **日本語 Windows の実機**である。★ `--selftest` で BOM ＋ CRLF の両方を固定し、
  ⚠️ 将来 `.gitattributes` の行が消えた場合も**配布物の側で**気づけるようにした。
- **トレードオフ**: ⚠️ **実機での表示は依然として未確認**（★ 測ったのはバイト形式だけ）→ 起票 T-7。

## 判断 5: 研究者向けの診断は **モードに依らず「届いていない」を指す**

- **判断日時**: 2026-08-28（★ 判断 1 の実装中に自分で見つけた）
- **背景**: ★ `HOOK_STARVED` の読み手を数えたら **3 つ**あった（一次資料で確認）:
  1. `tray.rs:92` … トレイ（**被験者**が見る）
  2. `lib.rs` の `get_recording_status` → `recording_health` → 画面のバッジと
     「キーボードの記録ができていません。研究者に連絡してください。」（**被験者**が見る）
  3. `lib.rs` の `get_diagnostics` の `hook_starved`（**研究者**が見る）
  ⚠️ 判断 1 をそのまま入れると、★ **3 番の意味が O1 のあいだだけ変わる**。
  ★ 2026-08-09 の判断 **D-6** は逐語で「`hook_starved` … は `get_diagnostics`（研究者向け）に
  出し、被験者側はトレイ表示までに留める」と決めている。→ ⚠️ **その約束を壊す。**
- **採用**: ★ `HOOK_NOT_DELIVERING` を新設し、**常に `health == Down` と同義**にする。
  `get_diagnostics` の `hook_starved` はこちらを出し、
  ★ 参考として `hook_starved_shown`（= 被験者に見えている状態）を**併記**する。
- **理由**: ★ 1 と 2 は**どちらも被験者向けの警告**なので遅らせるのが判断 1 の意図どおりだが、
  ⚠️ 3 は研究者の目である。★ 「被験者に見せる」と「届いていない」を**別の旗にする**のが、
  liveness.rs が最初からやっている「**設置済みと届いているを別概念にする**」の延長である。
- **トレードオフ**: ⚠️ Atomic が 1 つ増える。★ ただし読み手は診断 1 か所だけである。
- **影響範囲**: `input/hook.rs`（旗の新設）/ `lib.rs`（保存 ＋ 診断 2 キー）
