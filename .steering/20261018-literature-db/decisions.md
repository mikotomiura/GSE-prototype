## 判断 5〜8（2026-10-18・研究者・AskUserQuestion・4 問とも推奨どおり）

- **判断 5 読む枝**: 読む枝と、カード → 研究の筋の対応表は repo の設定ファイル `scripts/refdb/config.json` に置く。`--branches` で一時的に上書きできる。枝が main に入ったら設定から外す。どの枝を読んだかが git に残る。
- **判断 6 出力先**: 既定は手元の `~/.cache/gse-refdb/out/<日付>/`。Drive の同期フォルダへは `--out` で渡す。Drive のパスにはメールアドレスが入るので repo に書かない。
- **判断 7 ネット取得**: 抄録と書誌（CSL）は `--fetch` を付けたときだけ取りに行く。既定はキャッシュだけで動き、キャッシュに無い書誌は手元の題・出典・年から最小限に作って、その件数を表示する。
- **判断 8 消えた key**: シートで読んだ・メモがある行の key が正本から消えたら、作り直しを止めて、消えた key とメモを表示する。旧 key → 新 key の対応（`--rekey`）を渡すか、`--keep-orphans` で表の末尾に「正本に無い」として残すかを人が選ぶ。黙って消えることも、黙って残ることもない。

## 判断 9（2026-10-18・メインの判断・2026-10-18 の手作りの版との違い）

`build.py` を 2026-10-18 の commit に固定して作り（README §6）、Drive の `GSE文献DB_v2_2026-10-18.csv` と列ごとに比べた。件数（906・要約 675・カードでの記述 576 件 1,571 行・番号の衝突 48）と、ID・番号の衝突・名前空間・著者と題・研究の筋・要約・特徴・要約の材料・カードでの記述・枝・key は一致した。違いは次のとおりで、どれも手作りの版の誤りを直す向きなので、新しい方に揃える。

- **接地の `<` `>`**: 手作りの版は `<https://…>` の山括弧を外すときに、本文の不等号まで消していた（「d=.43 > schedule」→「d=.43 schedule」・「p<0.001」→「p0.001」・30 件）。URL を囲む山括弧だけを外す。
- **年**: 手作りの版は出典の最初の 4 桁を年にしていたため、頁や論文番号を年にしていた（`e2013097118, 2021` → 2013・`27:1949–1963, 2023` → 1949 など 20 件）。注記（最初の「（」）より前の最後の年を採り、頁の範囲・論文番号・`arXiv:2010.…` を年にしない。年が書かれていない出典は空のまま（`CHI '10, pp.1851–1860` は手作りの版も空・`Journal of Educational Data Mining（arXiv:2010.04124…）` は 2010 → 空）。
- **カードの題の ★**: 手作りの版はカードの題（`_index.md` のトピックの列・60 字まで）に ★ を残していた。外す（記号を多用しない方針）。
- **カード外の引用元**: 手作りの版は 200 字ほどで切れていた（9 件）。切らない。
- **URL が「—」**: 手作りの版は「—」をそのまま URL にしていたものと、DOI から補ったものが混じっていた。「—」は空とみなし、DOI / arXiv から補う。
- **状態の `**`**: 外す（1 件）。
- **CSL**: 人名から Crossref の `affiliation`・`role` を落とす（手作りの版は文字列にして持っていた）。Crossref の型名（`journal-article` など）を CSL の型名に直す（手作りの版は 896 件が `@misc` になっていた。直すと `@article` 494・`@inproceedings` 138・`@inbook` 11）。キャッシュで取れなかった DOI の書誌に DOI を入れる。最小限で作る書誌の型は `document`（手作りの版は `article`）。
- **読んだ の FALSE**: シートの 読んだ はチェックボックスで、付けていない行は `get_values` で `FALSE` が返る（2026-10-18 に実物で確認）。それは書いた内容に数えない（数えると、消えた key のたびに中身の無い行で止まる）。

## 判断 10（2026-10-18・メイン・/literature-review の段を empirical-prompt-tuning で確かめた結果）

- tier は Lite（1 シナリオ × 2 回）。ワークフローのコマンドで、重要度は中・変わる頻度は低いため。
- シナリオ: push 前の枝でラウンドを終え、シートの書き出し（`読んだ` の TRUE / FALSE と、正本に無い key のメモ 1 件を含む偽のもの）を渡して節 3 を実行させる。ネット・Drive・Sheets・Artifact は禁止にし、文で書かせた。
- 要件 6 項目（`[critical]` 2: `--keep` を渡す・push 前の枝をローカル名で `--branches` に入れる）。
- 1 回目（Sonnet・tool_uses 5）: 成功・精度 75%（要件 6 の件数の報告は、正しく止まったため manifest が出ず ×。要件 4 は部分的）。不明瞭点 4 つ（`--branches` が config を丸ごと置き換えること・試しと本番の回数・pandoc が無いとき・消えた key を直す場所）を 1 テーマとして節 3 に足した。
- 2 回目（新しい Sonnet）: 成功・精度 75%（× と部分的の理由は 1 回目と同じで、シナリオの作り）。1 回目の不明瞭点は出ず、全枝を書いて `--branches` に渡し、pandoc を確かめて `--no-bib` を付けず、`--rekey` / `--keep-orphans` を選ばずに研究者に聞いて止まった。新しい不明瞭点のうち直したのは「パイプで終了コードが見えなくなる」の 1 つだけ。残り（`--fetch` と `--out` の読み替え）は禁止事項が生んだもので、節の欠陥ではない。
- Lite の 2 回で止めた。
