## D-16: 打鍵は **キー種別を取る**。⚠️ R3 では **生 VK を書き出さずカテゴリへ量子化する**（研究者指摘 2026-08-21）

### 指摘（逐語）

> 打鍵の内容なども一応とっておいたほうが良いのでは？

### ★ 「内容」は 2 つの意味に割れる。**片方は既に取っており、片方は禁止**である

| 意味 | 状態 |
|---|---|
| (i) **どのキーを押したか** | ★ **既に全打鍵の VK を記録済み**（`logger.rs:1382-1392`・`{"type":"key","t":…,"vk":…,"press":…}`）。対象は英字/数字/テンキー/記号/BS/Enter/Space/Tab/Delete（`hook_windows.rs:76-90`）。⚠️ **修飾キーは記録されない** |
| (ii) **どの文字を書いたか（本文）** | ⚠️★★★ **禁止**。`data-privacy` ルール 1（逐語「入力文字: **絶対禁止**」）/ ADR-012 D3 / `§Layer 2 禁止事項` / ★ **`consent.md` で被験者に約束済み**（「★ **文章の中身は一切記録しません。**」） |

★ **(i) は科学的にも既に格上げ済み**: `boundary keys` は `personalization §5.2 (a)` で
**★★★ 採用（弁別の前提条件）**（2026-08-15）。逐語「**VK コードのみで本文非保存のまま移植可能**」。
⚠️ [P121]（N=475）は「**沈黙を長さの帯域で切る**」を否決し、代わりに「**沈黙の直前に押したイベント**」が
弁別することを実測した（英数キー 57% を占めるのに micro の 27%/long の 15% しか開始しない／
特殊文字は micro と負相関／**Return は弁別に使えない**／run は short/mid/long に集中）。
→ ★★★ **研究者の直感は文献に裏付けられている。R3 でも打鍵のキー種別は取る。**

### ⚠️★★★ ただし R3 では、**既存の生 VK 列そのもの**が新たな問題になる

★ **G1 で成立していた前提が R3 では成立しない**:

| | G1（R1） | ⚠️ R3 |
|---|---|---|
| 入力先 | ★ 専用入力画面・全員同じ課題 | ⚠️ **実業務の全アプリ** |
| 入力方式 | ★ 日本語 **IME** 論述 | ⚠️ **英数直接入力が混ざる**（URL / コマンド / コード / **パスワード**） |
| 期間 | ★ 5 分 × 10 ブロック | ⚠️ **数日〜数週間・連続** |
| VK 列からの復元 | ★ ローマ字の綴り＝**読み**。⚠️ **漢字変換は不可逆** | ⚠️★★★ **英数の綴りはほぼ 1:1 で復元できる**（大文字小文字は Shift 未記録のため不明） |

→ ⚠️★★★ **`consent.md` 逐語「書いた文章から復元することもできません」を成立させていたのは
*G1 の課題設計*（日本語 IME 論述）であって、*記録仕様*ではない。**
★ **R3 に同じ記録仕様を持ち込むとこの約束が破れる。**

### ★ 決定（ADR-014 **D4e**）

1. ★ **R3 では `key` 行（生 VK）を出さず、キー種別カテゴリの行を出す**
   （`alnum` / `symbol` / `punct`＝文境界 / `space`＝語境界 / `return`＝段落境界 / `backspace`・`delete` / `tab`）。
2. ⚠️★★★ **量子化は `logger.rs` の書き出し境界だけ。** ★ `features.rs` / `engine.rs` は**無変更**
   （在メモリの `InputEvent` は `vk_code` を持ったまま）→ **`HMM_VERSION` 不変・ゴールデン不変**。
3. ⚠️ **G1（R1）の `key` 行は 1 文字も変えない。** ★ R3 は別の行種を持ち、`capabilities` で機械判別する。
4. ⚠️ `scan_code` / 修飾キー状態 / Unicode 文字を**新たに足さない**（`data-privacy` ルール 1）。

★ **根拠（すべて既決）**:

## D-19: ⚠️★★★ TSF では解決できない。★ 既存制約の **理由付けが誤っていた**（研究者指示 2026-08-22）

### 指摘（逐語）

> それか TSF だとその macOS, windows の問題は解決できるかな？まだ期間はあるし TSF と格闘してみるのもいいのかもしれない.

### ★ 答え — **No。⚠️ 時間をかけても変わらない**（★ 一次資料の逐語で確定）

1. `ITfThreadMgr::Activate` —「**Activates TSF for the calling thread.**」
2. `ITfSource::AdviseSink` —「**リモート対象を指定する引数が構文上存在しない**」
3. ⚠️★★★ **決定打**: MSDN *IME and TSF Accessibility in Windows XP* ——
   「**To access the composition string managed in TSF, the assistive technology products must create
   the `ITfThreadMgr` in the process of creating the target TSF-enabled applications.**」
4. `GUID_COMPARTMENT_KEYBOARD_OPENCLOSE` —「**specific to a thread manager object**」
   → ⚠️ **IME の on/off ですらグローバルコンパートメントに無い**（★ グローバルなのは音声入力の 2 つだけ）

★ **これは難易度ではなく、API 表面に入口が無いという問題である。**

### ★★★ 既存制約の訂正（⚠️ **禁止の結論は変えない。理由だけを正した**）

★ 旧文（`docs/agent-shared.md` #7）:「**グローバル TSF フック禁止**: **UIPI でブロックされる**」

⚠️ **UIPI の禁止リストは逐語 5 項目**（window handle validation / `SendMessage`・`PostMessage` /
thread hooks / journal hooks / **DLL injection**）で、★ **TSF も COM も WinEvent out-of-context も含まれない。**
⚠️ かつ UIPI は「**at the same privilege (or integrity) level では一切干渉しない**」＝
**同一整合性レベルの通常環境では発動すらしない。**

→ ★ **真の障壁は「in-proc COM ＋ スレッドスコープ」というアーキテクチャ。**
⚠️ **権限を上げても・UIAccess を付けても・管理者で実行しても取得できない。**

★ **ただし旧文が「`WH_GETMESSAGE` / `WH_CALLWNDPROC` で `WM_IME_*` を拾う」の意味なら部分的に正しい**
（★ そちらは DLL 注入を要し **UIPI 第 5 項に直撃**）。⚠️ **旧文は 2 つの別問題を混同していた。**
→ ★ **`docs/agent-shared.md` #7 を両方を分けて書き直した。**

### ★ 副産物 — **TSF より良い手段が見つかった**

★ **`EVENT_OBJECT_TEXTEDIT_CONVERSIONTARGETCHANGED` (0x8030)**:
「**The conversion target within an IME composition has changed.**」
→ ⚠️ 現行の 3 定数は「**IME ウィンドウの表示/非表示/移動**」＝候補窓の UI 挙動しか見ていないが、
★ 0x8030 は **composition 内部の変換対象文節の移動**＝ **「うまく変換できていない＝迷い」の直接的な現れ**。
★ **Cognitive Friction 軸に対して情報量が大きく、content-free が構造的に保証される。**

⚠️★★★ **ただし今回は追加しない**（★ 記録仕様の変更であり、前提 3 件が未確認）。
⚠️ **トレードオフは隠さない**: ★ **いまは収集開始前であり、追加するなら今しかない。
見送れば G1 は 0x8030 を持たないまま確定する。** → ★ **研究者判断へ送る。**

### ⚠️★★★ 非対称は解消できない。★ 「下に合わせる」のは誤り
