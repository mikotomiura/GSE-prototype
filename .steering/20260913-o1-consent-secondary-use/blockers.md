# 詰まりと解決 / 起票

## 解決 1 — heredoc がバックスラッシュを潰し、`.gs` の文字列リテラルを壊した

### 何が起きたか

`Bash` ツール経由の quoted heredoc (`<<'PY'`) に `"…\\n" +` と書いたところ、
Python が受け取った時点で **`\n`（実改行）に化けていた**。★ 結果、生成した `.gs` の
JavaScript 文字列リテラルの中に**生の改行**が入り、⚠️ **構文エラーになる状態**を一度書き出した。

### どう気づいたか

⚠️★★★ **`cat -A` で書き出した中身を目視したから**である。
★ 別の編集で assert が落ち、⚠️「書けていない」と思って確認した副産物で見つかった
（★ 先に落ちていなければ、構文エラーのまま次へ進んでいた）。

### 対処

1. ★ 生成後に必ず **`node -e "new vm.Script(src)"` で構文を通す**（★ 以後 2 回とも実施）。
2. ★ パッチは **scratchpad の `.py` ファイルへ Write してから実行**する
   （⚠️ heredoc を経由しない）。
3. ★ どうしても heredoc を使うときは **`NL = chr(92) + "n"`** を置き、
   本文には `@NL@` と書いて最後に `.replace()` する。

### ⚠️ 教訓

★ **「patch ok と出た」は「正しく書けた」ではない。** ⚠️ 文字列を生成する編集は、
**生成物そのもの**（構文・バイト列）を機械で確かめるまで完了ではない。

## 起票 15 — ⚠️ `check-o1-release-readiness.sh --selftest` の 2 件が **main で既に空回りしている**

### 事実（★ 実測・2026-09-13）

`main`（`beac3ff`）を worktree に出して `--selftest` を実行した結果:

```
  ❌ 壊しても緑のまま: コードだけ直しても赤になる（実測が無い）
  ❌ 壊しても緑のまま: 必須欄が空なら赤になる
  selftest: 通過 44 件 / 失敗 2 件
```

→ ★ **本タスクの変更より前から赤である**（⚠️ 私が入れた検査が原因ではない）。

### 原因（★ 推定。⚠️ 一次確認はしていない）

★ 両者とも `selftest 3`（「片方だけでは緑にしない」）にあり、
**repo 側が未実測・未修正であること**を前提に書かれている:

```bash
build; fix_timeout;   expect_red "未実測"           "コードだけ直しても赤になる（実測が無い）"
build; sed_i '…状態: **実測済み**…' "$fix/w/$MEASURE"; fix_timeout; expect_red "必須欄が埋まっていない" …
```

⚠️ ところが repo は既に緑になっている（★ 本体のゲートで
「✅ 送信 timeout が実測にもとづいて見直されている」が出る）。
→ ★ `build` が**埋まった `$MEASURE`** を写すため、`fix_timeout` を当てると**全部緑**になり、
⚠️ 期待していた ❌ が出ない。

### ★ 本ファイル自身が定めている直し方

同スクリプト逐語:

> ★★ 2026-08-28 に緑になった 3 件。⚠️ **緑になったものは selftest 2 から 1 へ移す**

→ ★ この 2 件も **selftest 3（満たす側）から selftest 1（壊す側）へ移す**のが規約どおりの対処。

### ⚠️ なぜ本タスクで直さなかったか

- ★ **別サブシステム**（送信 timeout の実測記録票 `$MEASURE` / `reconcile.rs`）であり、
  本タスク（同意の任意項目）と 1 行も重ならない。
- ⚠️ **緑に戻す方向の変更**なので、★ 中身を理解しないまま触ると
  「検査を緩めて緑にした」になりうる（⚠️ ハンドオフ §5 が禁じている型）。

→ ★ **研究者判断**: 送信 timeout の担当タスクで拾うか、独立に 1 タスク切るか。
