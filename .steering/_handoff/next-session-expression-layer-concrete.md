## ⚠️★★★ 最初に直す用語（★ これが設計そのものを変える）

**「認知リソース」を表現対象と呼ばない。**

★ 実測: `docs/glossary.md:247` の禁止用語表 ——
**「認知リソースの *消耗* / *回復* / リソースの *補充*」**（Physical Anchor・休憩・自然曝露の文脈で禁止）
→ 代替は **「関与の低下 / 関与の再開」**。
理由は**限定資源モデル（ego depletion）の語彙**であり、その枠組みは
[P199]（RRR k=23・N=2,141 で **d=0.04**）/ [P200]（事前登録 k=36・N=3,531 で **d=0.06**）/
[P201]（PEESE b=0.003）で否定されているため。

⚠️★★★ **これは言葉の問題ではない。**
★ 「リソースを表現する」と考えると必然的に**残量メーター**になり、それは
**`.idea` §0 が明示的に否定した「疲労メーター」**であり、**ADR-021 D3 が禁じた「数値・順位・達成度」**そのものである。

→ ★★★ **表現対象は「作業状態」である**:
**Cognitive Friction（摩擦）/ Productive Engagement（関与）/ `p_stuck`**、＋ 観測品質。
★ 境界を渡るのは **`level`（`stable` / `friction_rising` / `stuck`）＋ `invitation`（`none` / `present`）** だけ（ADR-021 D4）。

## ★★★ 本セッションの目標（★ 研究者判断・2026-09-02。この 2 件に絞る）

### 【第 1】OS 制約・セキュリティ機構の技術調査（★ これを先に閉じる）

> ★ **理由**: ここが閉じないと「どの形がベストか」を議論しても**実装不能な案を選びうる**。
> ★ ADR-021 D1 でロック画面を第一媒体に決めた際、私は
> 「**OS 制約でアニメーションを載せられない場合がある → 実装時に再検査**」と**先送りした**。

**空白は 2 つある。両方を埋める。**

#### (a) 実装可能性 —— iOS / Android がロック画面で実際に何を許すか

★ 調べるべき具体項目（★ **一次 = 公式ドキュメント / API リファレンス / 実機**。⚠️ **ブログ記事を根拠にしない**）:

1. **ロック画面ウィジェット**（iOS 16+ の Lock Screen widgets / Android の
   lock screen 表示可能な面）—— ★ **更新頻度の上限**（★ iOS の WidgetKit は
   タイムライン予算があり、**任意のタイミングで更新できない**可能性が高い）。
2. ⚠️★★★ **アニメーションが載るか** —— ★ **ADR-021 D10 の A-7（振幅 ~1°・1–3 Hz の
   その場振動）が実装できるかどうかの生死問題**。★ ウィジェットが静止画しか許さないなら
   **A-7 は色以外の代替符号を作り直す必要がある**。
3. **Always-On Display** に載せられるか、載せた場合の更新粒度と消費電力。
4. **Live Activities / Dynamic Island**（iOS）—— ★ これは**別の面**であり、
   ⚠️ **通知に近い**ので採るなら ADR-017 D5 / ADR-021 D5 の「注意を強く奪う提示は介入である」に当たる。
5. **背景実行と受信** —— ★ PC → スマホの一方向イベントを受けるために
   **常駐が要るか / push が要るか**。⚠️ **ADR-017 D4 制約 1（PC 側に常設 LAN リスナを置かない）**と
   両立する経路があるか。→ ★ **これは W-1（wire protocol の別 ADR）の前提になる。**
6. **secure lock screen の制限** —— ★ ロック状態で表示できる情報の制限、
   端末が「機密内容を隠す」設定になっている場合の挙動。
7. **ペアリングと失効**（ADR-017 D4 の **S1–S6**）を OS の仕組みでどう満たすか。

#### (b) 曝露量の外的妥当性 —— ⚠️ **層 A の 2–4 秒は Face ID 以前の数字である**

★ 実測: `docs/literature/20260830-smartphone-ambient-surface.md:467` が既に警告している ——
**「カード 6 の 2–4 秒という制約は 2016 年の Android のものである」**。
★ [P240]（SOUPS 2014）も **2014 年・Android のみ**。
→ ⚠️★★★ **顔認証時代（自動解錠）では、ロック画面の滞在時間そのものが変わっている可能性がある。**
★ ただし **[P264]（2021・N=41・78% iOS・一人称ビデオ 200 時間超）が
「平均 4.2 秒・中央値 3 秒」を再現している**ので、**崩れてはいない**。
→ ★ **本調査の仕事は「崩れていないことを確かめて記録する」か「崩れた条件を特定する」かのどちらかである。**

**★ 出口**: ADR-022（媒体の実装制約）を起票するか、ADR-021 D1 / D10 の追補にする。

## ⚠️ 音（研究者の問い 2）—— ★ **本セッションでは開かない。ただし順序を記録する**

★ 研究者の見立て（「おそらくオプトインが有効かな？」）は **ADR-017 D5 の再開条件 1 と一致する**。
⚠️ **ただし条件は 4 つとも必要である**（実測・D5 逐語）:

1. **事前オプトイン**（[P133]: 8/15 が「事前承認なしの proactive 機能は受け入れられない」）
2. ⚠️★★★ **内容ごとの選択的無効化**（[P134]: **33/42 = 78.6% が要求**）
   —— ★ **`.idea` の「次回以降の自動開始を無効化する設定」は粒度が粗すぎる**と名指しで却下されている
3. **開始前 cue**
4. ★ **行動側の対照を持つ評価設計**（ON/OFF の無作為化 ＋ 作業ログの客観指標）

⚠️★★★ **かつ、その手前に PS-Q3（層 0 の音を第 1 版から外すか）が未決のまま立ちはだかっている。**
★ ADR-017 は **「B1 の実施でしか決まらない」**としている（`spec` §9-4）。
→ ★★★ **順序は「PS-Q3 を閉じる → D5 の 4 条件を検討」である。オプトインの議論はその後。**
⚠️ **ADR-021 D3 は「音の有無」を本人の調整項目から外した** —— 実装しないものを設定項目に置けないため。

★ **参考（不利な側）**: 参加者の cue 選好は視覚に有利 —— 逐語
*"Verbal cues were described as most distracting, followed by audible cues.
**Visual cues were described as the least distracting**."* [P133]。
★ GSE は既に視覚チャネルを持つので、**第 3 段との差分は「音を鳴らすこと」だけ**である。
