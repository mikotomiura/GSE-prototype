## §1b ⚠️★★★ T-0 — `starve_window` の陽性対照（★ 最優先・実装より先）

### ★ なぜこれが最優先か

⚠️★★★ **これは ADR-013 が潰そうとした取り違えそのものである。**
`starve_window` は `capabilities.threshold_gated` に属するので、
★ **0 行は「判定不能」としか読めない** —— つまり**計器が壊れていても気づけない**。
→ ⚠️ **一度も発火を見ないまま収集を始めると、新コホートで 0 行だったときに何も言えない。**

### ★ 発火条件（★ 実装から導いた。推測ではない）

`liveness::step` は次で動く:

| 条件 | `starved_ms` |
|---|---|
| `!session_active` または **フックが呼ばれた** | **0 にリセット** |
| **システム入力が無い**（マウスもキーも触っていない） | ★ **凍結**（進まない） |
| システム入力あり **かつ** フック未呼び出し | ★ `+= tick_ms` |

→ ★ **「マウスは動かすが打鍵しない」時間だけが積算される。**

★ **陽性対照の手順**（★ G1 モードで実施する）:

1. セッションを開始し、**数秒ふつうに打鍵**する
2. ★ **打鍵をやめ、マウスだけを 5 秒ほど動かし続ける**（⚠️ 1 Hz サンプリングなので
   **1 秒未満のエピソードは原理的に見えない**・所見 B）
3. ★ **キーを 1 つ打つ** → ここでエピソードが閉じる（`peak < 30 秒` なので micro 帯）
4. ★ 2〜3 を **同じ 60 秒の窓の中で 2〜3 回**繰り返す
5. ⚠️ **窓が閉じるまで待つ**（60 秒）。→ `starve_window` 行が 1 本出るはず

## §2 T-1 — 自動終了 × 押下の競合（⚠️ 本セッションの本命）

### ★ 何が起きるか（`blockers.md` D-1 / code-reviewer MEDIUM）

`lib.rs` の G1 ブロック自動終了スレッドは、この順で進む:

```
1) block_session_active.store(false)      ← 分析スレッドを止める
2) SESSION_START_MS.store(0)
3) ANALYSIS_IDLE を待つ (★ 最大 1500 ms)   ← ⚠️ ここが窓
4) BlockEnd を送る                         ← ここで session_end が書かれる
```

⚠️★★★ **3) の窓の中で「開始する」が押されると 2 通りに壊れる**:

| 交錯 | 何が起きるか |
|---|---|
| **押下が後** | `was_active == false`（1 で false になっている）→ `RotateForNewBlock` → **`Rotate` が先に届く** → 直後の `BlockEnd` が**新しいファイルへ `session_end` を書く**（`logger.rs` が `block_closed` を false に戻すため）。→ ★ 以後の `key` / `feat` が **`session_end` の後ろ**に積まれる |
| **押下が先** | 2) が**始まったばかりのブロックの `SESSION_START_MS` を 0 にする** → ★ 分析が止まり、**自動終了も二度と来ない**（`start == 0` で `continue` するため） |

★ **pre-existing** だが、⚠️ **G-1 修正で「実行中の押下」が想定内の操作になったぶん確率が上がった**。
⚠️★★★ **これはリブートの原因と同じ失敗クラス（ブロック境界の破れ）である。**
走り出したら `§3.6` により**回復不能**なので、**収集開始前に閉じる**。

### ★ 直し方の方針（★ 案は出ているが、実装前に `/reimagine` で潰すこと）

- **案 A**: 自動終了側が**終了権をアトミックに取る** ——
  `SESSION_START_MS.compare_exchange(start, 0)` が**失敗したら中止**する
  （＝ その間に新しいブロックが始まっていた）。★ 加えて **3) のアイドル待ちの直後に
  `SESSION_START_MS == 0` を再確認**してから `BlockEnd` を送る。
- **案 B**: `start_session` と自動終了で**同じ「ブロック遷移 Mutex」**を取る。
  ⚠️ ロック順序（`intervention` → `log` の既存順）を壊さないこと。

⚠️★ **`ANALYSIS_IDLE` の待ちを消してはならない** —— それが無いと分析スレッドの在庫 1 イテレーションが
`session_end` を追い越して `Key`/`Feat` を投げる（過去の code-review HIGH）。

### ★ 併せて閉じる — 事後レビュー所見 C（★ 同じ場所を触るので一緒に直す）

`code-review.md` 所見 C 逐語:

> `RotateForRestart` のときだけエピソードが 1 本、新ブロックへ誤帰属しうる。
> 二度押し経路では `session_active` が `true` のままなので、`is_new_block_epoch` で窓を reset した
> **同じ tick** に、reset 前に貯まっていた `prev_starved_ms` が「正→0」として**新しい窓へ**計上されうる。

⚠️★ **気になるのは実害の大きさ（二度押し 1 回につき 1 本）ではなく一貫性の破れ**である ——
`tick()` の docstring は「**誤帰属より既知の切り捨てを採る**」と方針を明記しているのに、
★ **新設した二度押し経路だけがその例外**になっている。

→ ★ **直し方は 1 行**: `is_new_block_epoch` が真の tick では、
`tick()` に渡す `prev_starved_ms` を **0 にする**（＝ そのティックのエピソード判定を抑止する）。
⚠️ **テストで固定する**こと（★ 通常のブロック境界では発火しないことも対照として置く）。

★ **研究者了承済み（2026-08-21・§0 の決定 1）。確認は不要でそのまま閉じてよい。**
⚠️★★★ **ただし 1 行で終わる範囲に限る。** ★ 構造をいじる必要があると分かった時点で
**捨てて T-2 へ進む**（★ A / B は引き続き**直さない**）。
