## §5 ⚠️★★★ 前セッションの教訓（★ 繰り返さない・「検査の検査」5 点）

★ 起票 23 のセッションは **8 件の欠陥を自分で作って自分で見つけた**。⚠️ うち **3 件はテストが緑のまま潜んでいた**。

1. ⚠️ **`$( )` の中の `die` / `exit` はサブシェルしか抜けない** —— ★ **fail-closed が fail-open に化ける**。
2. ⚠️ **`grep -c … || echo 0` は "0" を 2 行出す** —— ★ `[` が壊れ、**ガードが素通りする**。
3. ⚠️ **変異ガードは「元の形が消えた」だけでは足りない** ——
   ★ 「sed が置換した」と「**そもそも存在しなかった**」を区別できない。→ **src に 1 件 / mut に 0 件**を両方見る。
4. ⚠️★★★ **判定式が常に真になっていないか** —— ★ 「rc が 0 でも非 0 でも ok」と書いた瞬間に**空振り**である。
   → ★ **ok と ng の両枝が実際に取られるか**を変異で確かめる。
5. ⚠️★★★ **語で一致させるときは「その語が別の理由でも出ないか」を確かめる** ——
   ★ 実測: `LOOP_BASE_BRANCH` は provenance 行にも出るので、**関門を外しても緑**だった。
   → ★ **die メッセージの固有の語**で固定する。

★ あわせて:

- ⚠️ **「準備できなかった」が出たら、検査が飛んでいないかを必ず確かめる**
  （★ `make_branch` の失敗で **3 件の検査が 1 件の NG に化けた**）。
- ⚠️★★★ **`/cross-review` の diff 範囲の切り方が指摘の質を決める** ——
  ★ 2 巡目で「新しく足した規則だけ」に絞ったつもりが、**規則の *実装* を範囲外に置いてしまい偽陽性を招いた**。
  → ★ **「規則」と「その実装」を同じ範囲に入れる。**
- ⚠️★★★ **指摘が偽陽性でも、確かめる手順は省略しない** ——
  ★ 偽陽性を潰す作業そのものが、**どちらの系統も直接は指摘していなかった空振り 2 件**を掘り出した。
