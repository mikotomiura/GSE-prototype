## §0 ⚠️★★★ このセッションの問い（★ 研究者本人の発意・2026-08-19）

> ⚠️★★★ **打鍵だけで推論すると、タスクを変えても「また同じ形」になる。**
> ★ 各タスクで **実際に主に行われている操作** を推論の素材にすべきではないか。
> ★★★ **そして「何を入れるか」は dev の推測ではなく、
> そのタスクを普段行っているユーザーからデータを抽出して *実測で* 決めるべきではないか。**

⚠️★★★ **本セッションは「設計だけ」を確定する。`src-tauri/` のコードは 1 バイトも変えない**（§5-1）。

### ★ 発意の逐語（⚠️ 原文のまま。誤字も直さない）

```
以前の私のユーザー検証でのPhase1以降で書くタスクでの適用などをさせたい都市、現在それに関して
の各タスクでの適用の方を作成しているが、打鍵での推論のみではまた同じ形になるため、打鍵以外
(各タスクでは具体的に主に行う操作)の内容などを推論の素材として入力させるとよいのでは？また
その入力させる内容などを決定させるためにその顕著としてでるないようの平均などを求めるためにそ
のタスク(普段の作業)を抽出させるためのそのタスクに適した作業を普段行っているユーザーのデータ
抽出検証を行うべきではないか
```

   ★ 逐語の教訓: **「既存ログにある」は *現行コードが出す* の意味であって、*対象コホートにある* の意味ではない。**

## §3 ⚠️★★★ このセッションで裁くこと

### A. 形成的研究の設計（上流）

1. ⚠️ **「顕著に出る操作」をどう定義し、どう測るか。**
   ★ 発意は「**その顕著として出る内容の平均**」と言っている。→ **何の平均か**を決める
   （頻度 / 占有時間 / 遷移確率 / セッション内シェア…）。⚠️ **ここが曖昧なままだと収集が空回りする。**
2. ⚠️★★★ **content-free をどう保つか**（★ 最大の争点）。
   ★ 「主に行う操作」を識別するには最低限**操作の種別**が要る。
   ⚠️ アプリ識別子を持つと [P117] と同じ穴に落ちる。→ ★ **何を「種別」と呼ぶかの定義が要る**
   （例: OS レベルの汎用イベント種別のみ / 利用者の自己申告で写像 / プラグインが種別だけを返す）。
3. ⚠️ **対象モダリティを何から始めるか。** ★ Adapter C 逐語「**まず一アプリに限定した feasibility study**」。
   ⚠️ 動画編集 / スライド / CAD を一括で始めない。
4. ⚠️ **取得手段**。★ OS フックで足りるか、**プラグイン方式**が要るか（Adapter C が既に警告）。
   ⚠️ **GSE 本体で取るのか、別の計測手段で取るのか**（§5-1 の制約と直結）。
5. ⚠️ **募集・同意・privacy 境界**。★ `data-privacy` Skill の拡張対象。
   ⚠️ **ADR-008 Consequences 逐語「`PersonalizationStore` の永続化にはユーザー同意と削除 UI が要る（未解決・実装前に必須）」**と同じ扱いが要る。
6. ⚠️ **n と期間**。★ 形成的なので確証の検出力設計は要らないが、
   **「何名・何日で『顕著』と言えるか」の下限**は決める。
