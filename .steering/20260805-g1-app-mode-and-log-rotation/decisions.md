## R-1: ローテート案は独自発明ではなく、実験ソフトの標準形だった（★ D-7 の追認）

- **見つけたもの**: PsychoPy の **`psychopy.session` API**。
  「同じフォルダにある複数の実験を **1 プロセスで順に走らせる**」ための公式 API であり、
  **Window と入力デバイスを保持したまま**実験を切り替え、
  `saveCurrentExperimentData()` / `saveExperimentData(key)` で **run ごとに別データ**を保存する。
  文書が挙げる設計理由は「ウィンドウを閉じて開き直さなくて済む（オーバーヘッド削減）」。
- **帰結**: ★ 本タスクの第 1 段（1 プロセス・ブロックごとに NDJSON を切る）は
  **動機まで同型**である。D-7 の「ローテートが要る」は追認された。
- **併せて分かったこと**: PsychoPy の既定出力は「1 セッション 1 ファイル ＋ ループごとに
  シート / サフィックスで分ける」。★ **ブロック分割はするが、ファイルにするかシートにするかは
  実装差**。GSE は NDJSON なので**ファイル分割が自然**であり、`protocol.md §1` が
  (a) を選んだ理由（取り違えの影響範囲がそのブロックに閉じる）とも整合する。
- **出典**: <https://psychopy.org/api/session.html> ／ <https://psychopy.org/general/dataOutputs.html>

## R-3: 二重起動の手段を**自作ポート排他 → Tauri 公式プラグイン**に差し替えた

- **判断日時**: 2026-08-05（研究者選択「公式プラグインに差し替え」）
- **背景**: 調査前に自作 `TcpListener` 排他を選んでいたが、調査で 2 点分かった。
- **選択肢**:
  - A: `tauri-plugin-single-instance`（Tauri 公式・Win / mac / Linux）
  - B: 自作 `TcpListener::bind("127.0.0.1:<固定ポート>")`
  - C: 両方
- **採用**: **A**
- **理由**:
  - ★ **公式実装がある**。自作の誤検出リスク（無関係なアプリが同じポートを掴む）を負う理由が薄い。
  - ★ **macOS は同じ `.app` の 2 個目のインスタンスをそもそも起動しない**（CLI 経由を除く）。
    これは `protocol.md §1.1` が既に実測している「`open -a` は前面に出すだけ」と同じ事象であり、
    ⚠️ **OS ごとに事情が違う**ことを意味する。差異はプラグインに吸収させるほうが素直である。
- **制約**（公式文書が明記）: ★ **プラグインは最初に登録する**こと。
- ⚠️ **公式文書に書かれていないこと**（★ 実装時に自分で確かめる）:
  - Windows / macOS で「同一アプリ」を何で識別しているか（bundle ID / mutex 名 / ウィンドウクラス）
  - ★ **別パスにある同一 bundle ID のコピーを検出するか** — R-4 の中心論点なので**実測する**
- **トレードオフ**: 依存が 1 本増える。
- **出典**: <https://v2.tauri.app/plugin/single-instance/>

## R-4: ⚠️★ D-7 に未計上のリスク — **bundle ID 衝突**（LaunchServices）

- **背景**: D-7 は `/Applications/gse-next.app` と `G1-app/gse-next.app` という
  **同じ bundle ID の 2 コピー**を作る形である。
- **見つけたもの**: macOS の LaunchServices は **bundle identifier が同じアプリを同一視**する。
  同一 identifier の複数登録は「アプリが起動しない / デバッグが困難になる」既知のトラブル源として
  Apple Developer Forums で扱われており、開発版と製品版は **bundle ID を分けること**が推奨されている。
  ⚠️ ★ **2 コピーはバージョンも同じ**なので、どちらが選ばれるかの決定規則（高いバージョンを選ぶ）
  すら効かない。
- ⚠️ ★ **帰結（D-7 が見ていなかった失敗経路）**:
  **「G1-app のアプリを開いたのに `/Applications` の通常アプリが前に出る」**が起こりうる。
  D-7 が fail-loud の対象にしたのは「マーカーが外れる / アプリをフォルダから出す」だったが、
  ★ **こちらのほうが確率が高く、被験者の操作ミスですらない**。
- **状態**: ★ **未実測**。R-6 で測る。
- **出典**: <https://developer.apple.com/forums/thread/65764> ／
  <https://lapcatsoftware.com/articles/2024/12/2.html>

## R-5: ⚠️★ D-7 に未計上のコスト — **TCC 再許可**（Input Monitoring）と、配布の第 3 の道

### 5-1. TCC

- **見つけたもの**（★ **一次資料ではない**・複数の二次情報が一致している段階）:
  TCC の許可は **code signature ＋ bundle ID ＋ on-disk path** に紐づき、どれかが変わると
  別アプリ扱いになる。ad-hoc 署名は TeamIdentifier を持たないため **CDHash だけで識別される**。
- **実測（本セッション）**:

  ```
  codesign -dv --verbose=4 /Applications/gse-next.app
    Identifier      = com.johnd.gse-next
    Signature       = adhoc
    TeamIdentifier  = not set
    CDHash          = 998eb73f788c1d45c1291eb015c4c8bbf68ed115
  ```

- ⚠️ ★ **確かめられていない**: `~/Library/Application Support/com.apple.TCC/TCC.db` は
  `authorization denied` で読めなかった。★ **コピーしても CDHash は変わらない**ので
  carry over する可能性もあり、**どちらとも言えない**。→ R-6 で測る。
- **もし再許可が要るなら**: D-7 は被験者に「Input Monitoring をもう一度許可 → アプリ再起動」を課す。
  ★ **ターミナルを消すために別の関門を増やす**ことになり、D-7 の主目的と正面から衝突する。
- **出典**: <https://hacktricks.wiki/en/macos-hardening/macos-security-and-privilege-escalation/macos-security-protections/macos-input-monitoring-screen-capture-accessibility.html>

### 5-2. 配布 — ★ D-7 は選択肢を 1 つ落としている

- D-7 は「Gatekeeper を消せるのは案 4（Developer ID ＋ 公証・**$99/年**）だけ」と書いている。
- ★ **大学が機関の Apple Developer アカウントで研究者のアプリを公証するサービス**の実例がある
  （University of Manchester Research IT。標準の申請は**無料**、優遇処理が £125）。
- ★ **副次効果が大きい**: Developer ID で署名すると **TeamIdentifier が付く**ので、
  TCC の許可が**ビルド間で保持される**。⚠️ 今の ad-hoc 署名は毎ビルドで CDHash が変わるため、
  ★ **被験者はアプリを更新するたびに Input Monitoring を許可し直しているはず**である
  （⚠️ **これも未確認**。Phase1 の被験者に起きていた可能性がある）。
- **本タスクではやらない**（研究者の所属機関に同種のサービスがあるかの確認が先）。
  ★ ただし `debrief` ではなく**運用の課題として記録**する。
- **出典**: <https://research-it.manchester.ac.uk/services/macos-notarization-service/> ／
  <https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution>

## R-7: ★★ 実測結果（2026-08-05・macOS 26.5.2・研究者端末）— **D-7 は維持。ただし launcher は捨てる**

### 測り方（★ 再現できるように書く）

```bash
ditto /Applications/gse-next.app ~/G1-app-test/gse-next.app   # ★ 実物には触らない
codesign -dv --verbose=4 ~/G1-app-test/gse-next.app
codesign --verify --strict ~/G1-app-test/gse-next.app          # rc=0
codesign --verify --strict /Applications/gse-next.app          # rc=0 (実物が無傷であることの再確認)

open ~/G1-app-test/gse-next.app        # ②-b
open -a gse-next                        # ②-c  ← launcher と同じ形
open ~/G1-app-test/gse-next.app        # ②-d  ← /Applications 動作中に G1 を開く
for p in $(pgrep -x gse-next); do echo "$p -> $(ps -o comm= -p $p)"; done

/usr/bin/log show --last 6m --predicate 'process == "tccd"' --style compact | grep AUTHREQ_RESULT
```

> ### ⚠️★ ここでも「検査が走っていない偽の緑」を踏んだ
> 最初 `log show …` を **`log`** で呼んだところ **0 件・rc=0** が返り、
> 「TCC のログは出ていない」と結論しかけた。⚠️ ★ **zsh には `log` ビルトインがある**。
> `/usr/bin/log` に直したら **695 行**取れた。
> ★ **0 件を「無い」と読む前に、検査自体が動いているかを数字で確かめる**
> （前タスクの教訓「`grep -c` は 0 件でも 0 を出す。何も出ないではなく数字を読む」と同型）。

### 結果 1: ★ **TCC の再許可は不要だった**（R-5 の懸念は棄却）

| 何 | PID | service | authValue | authReason |
|---|---|---|---|---|
| ★ `~/G1-app-test` のコピー | 60432 | `kTCCServiceListenEvent` | **2 = 許可** | 4 = 既存設定 |
| `/Applications` の実物 | 60521 | `kTCCServiceListenEvent` | **2 = 許可** | 4 = 既存設定 |

- ★ **完全に同じ結果**。**プロンプトは出ていない**（`Prompt` 行 0・`authReason` が 2=User Consent でない）。
- 理由と整合する事実: **コピーは CDHash も bundle ID も同一**
  （`CDHash=998eb73f788c1d45c1291eb015c4c8bbf68ed115` / `com.johnd.gse-next`）。
  tccd のログも `identifier=com.johnd.gse-next … at ~/G1-app-test/gse-next.app` と、
  ★ **パスが違っても同一の identity として扱っている**。
- ⚠️ ★ **測っていないこと**: (a) `/Applications` に**一度も許可していない新品の端末**での初回挙動、
  (b) macOS 26.5.2 以外、(c) Windows 側（そもそも TCC が無い）。
  → ★ **「新品の端末でも要らない」とは言えない。** 言えるのは「**許可済みの端末でコピーを足しても再許可は要らない**」だけ。

### 結果 2: ⚠️★★ **二重起動は実測で再現した**（§2-3 の懸念は現実）

| # | 操作 | 起動していたもの | 結果 |
|---|---|---|---|
| ②-b | `open <コピーのパス>` | なし | ★ **コピーが起動**（パス指定は確実） |
| ②-c | ★ `open -a gse-next` | コピー | ⚠️ ★ **`/Applications` が別プロセスで新規起動 → 2 プロセス共存** |
| ②-d | `open <コピーのパス>` | `/Applications` | ⚠️ ★ **コピーが別プロセスで起動 → 2 プロセス共存** |

- ★ **NDJSON も 1 プロセス 1 本ずつ、計 3 本できた。**
  = `protocol.md §2-3` が言う「打鍵が 2 本の NDJSON に割れる」機構そのものである。
- ⚠️ ★ **R-3 で引いた「macOS は 2 個目のインスタンスを起動しない」は、D-7 の形では成立しない。**
  ★ **同じ bundle ID でもパスが違えば別プロセスとして平然と共存する。**
  → ★ **二重起動検出は「あれば安心」ではなく必須**である。

### 結果 3: ★ R-4（bundle ID 衝突で通常アプリが前に出る）は**起きなかった。ただし条件つき**

- **パス指定（＝ダブルクリック）なら必ずそのコピーが起動する。** R-4 の心配は当たらなかった。
- ⚠️ ★ **ところが `open -a gse-next`（名前形）は `/Applications` を選んだ。**
  これは **launcher が使っている形そのもの**である（`launch-g1-macos.command:102`）。
  → ★★ **launcher と G1 フォルダ運用は併用できない。**
  併用すると **G1-app のマーカーが効かない通常アプリが起動し、プローブが復活する**。
  ⚠️ ★ **`§5.4-2` の客観検証（probe 行 0）が赤になって初めて気づく = 実施後まで気づけない。**

### ★ この実測が第 2 段の形に与える帰結（**D-7 は作り直さない。付け足す**）

1. ★ **D-7 の形（フォルダにコピー ＋ マーカー）はそのまま維持できる。** TCC のコストは無かった。
2. ★★ **第 2 段では macOS の launcher を廃止する**（`open -a` が通常アプリを起こすため）。
   ⚠️ ★ これは D-7 の狙い（「ターミナルも env も launcher も要らない」）と**同じ方向**である。
   → **launcher を残したまま第 2 段を配ると、かえって危険**になる。
3. ★ **二重起動検出（R-3 の公式プラグイン）は必須**。⚠️ ただし
   **プラグインがこの 2 プロセス共存を実際に止められるかは未確認** →
   ★ **実装後に同じ手順（②-c / ②-d）で再測する**。止められなければ手段を見直す。
4. ⚠️ **Windows は未測定。** `open -a` 相当の曖昧さは無い（`.exe` のパスを直接叩く）が、
   ★ **二重起動そのものは Windows でも起きる**（`taskkill` で防いでいる現状がその証拠）。

## R-8: ★★ 実装後の再測（2026-08-05）— **プラグインには穴があり、私は退行を 1 つ入れていた**

R-7 が「実装後に同じ手順で再測する」としたので、新ビルドで測り直した。
⚠️ ★ **測って初めて分かったことが 2 つある。設計時には見えていなかった。**

### 測り方

```bash
npm run tauri build -- --target aarch64-apple-darwin --bundles app
# ⚠️ sidecar (package feature) が無いので bundling は失敗するが .app 自体は作られる。
#    本体バイナリを手で入れて ad-hoc 署名し直して使った。
G1-app/{g1.mode, gse-next.app}  と  plain/{gse-next.app}  の 2 つを作り、順に open する。
```

### 結果 1: ★ マーカーと fail-loud は**実機で動いた**

```
新ビルドを G1-app（マーカーあり）から起動したときの NDJSON 1 行目:
{"type":"meta","session_start":…,"hmm_version":"0.3.0","g1_mode":"marker"}
```

★ `current_exe()` から **4 階層上**の探索が実機で当たっている。

### 結果 2: ★ プラグインは**同一ビルド同士なら**止める

`G1-app` 起動中に `plain` を開いても **プロセスは 1 個のまま**だった。

### 結果 3: ⚠️★★ **ところが旧ビルドとは共存する**（穴）

`/Applications` の**プラグインを持たない旧ビルド**（Phase1 用 `v0.1.22`）を先に起動してから
新ビルドを開くと、★ **2 プロセスが同時に走った**。

⚠️ ★ **これは被験者の実環境そのものである**（Phase1 で入れた旧アプリが残っている）。
→ ★ **G1 モード限定でプロセス名の検査を足した**（`pgrep -x` / `tasklist`）。
★ **止めずに画面へ出す**（列挙の失敗や名前の一致ミスで実施を潰さないため。判断は人に返す）。

### 結果 4: ⚠️★★ **私が退行を 1 つ入れていた**

★ **止められた 2 個目のプロセスは、止められる前に NDJSON を作ってから死ぬ**
（`SessionLogger::start` が Tauri builder より先に走るため）。実測で **0 行のファイル**ができた。

⚠️ ★ `gse-submit` は `find_latest_session_ndjson` で**最新 1 本**を選ぶので、
★ **被験者が「提出する」を押すと空の `.age` が出る。**
⚠️ ★ **プラグインを入れる前には無かった失敗**であり、**私が作った**。

→ `find_latest_session_ndjson` が **`meta` 行しか無いセッションを候補にしない**ようにした。
★ 起動直後のクラッシュ・ディスク不足など**原因を問わず同じ形で守れる**ので、

## R-9: `/cross-review`（Claude + Codex）の結果と、**直さなかったものの根拠**

Codex 消費 **41,631 トークン**（`.codex/budget.json`: 137,035 → 178,666 / 200,000・invocations 2 → 3）。
対象はコード差分のみ（1,266 insertions・`manual_approval_threshold` 2,000 内）。

### 両者一致 HIGH（★ **修正した**）

⚠️★★ **`Rotate` の送信に失敗しても `SessionStart` を無条件に送っていた。**
`try_send` は bounded(512) が満杯だと落ちるので、ローテートされないまま
**既に `session_end` を書き終えた旧ファイル**に次ブロックが積まれる。
★ `protocol.md §1` が (b) を却下した「沈黙して間違った結果を出す」失敗そのものである。

→ **触った状態を全部巻き戻して `Err` を返す**（`start_session` を `Result` 化）。
フロントは既に失敗を「開始に失敗しました」と表示する経路を持っている。

★ Codex は別の引き金で同じ設計ギャップに到達した（同一パス skip による**ブロックの
サイレントなマージ**）。→ **一意化を `Rotate` 処理の先頭へ移し**、同一パスになりえなくした。

### ⚠️★★ ここでも「発火しない検査」を書いていた

同一パスガード（`current_same` → `continue`）を足したが、
★ **わざと壊しても赤にならなかった**。一意化を先に行うと、書きかけのファイルは必ず存在するので
`unique_path_from` が別名を返し、★ **同一パスには到達しない**。
→ ★ **ガードを消した。** 発火しない検査を残すと「守られているつもり」を作る。
（本タスクで**3 回目**。1 回目は Python の検査 2 本、2 回目は 200ms sleep の根拠、今回がこれ。）

### ⚠️ H2: 他の producer が session ゲートを見ていない — **直さない。根拠を書く**

`record_user_label`（ホットキー）／`record_self_marker`／`record_intervention_dismiss`／
`vignette_response`／`wall_server` の `InterventionResponse` は `session_active` を見ずに `try_send` する。
→ ブロックを閉じた後に押されると `session_end` の**後ろ**に行が付きうる。

★ **それでも止めない。理由は 2 つある**:

1. ⚠️★ **止めると `§5.4-2 / -3` の検出が効かなくなる。**
   `§5.4-3` は「自己マーカーが押されたら `realtime_label` 行として検査が捕まえる」と
   **凍結している**。★ アプリ側で握り潰すと、**禁止事項の違反が見えなくなる**。
   ★ 記録が汚れることより、**違反が検出できることのほうが重い**（`§3.6` は事後除外を禁じており、
   検出できなければ報告もできない）。
2. G1 は**第 1 週モード**で回すので `INTERVENTION_ENABLED=false`。
   Wall / Nudge は発火せず、`intervention_response` 系は**そもそも出ない**。
   プローブも止めているので `realtime_label` は自己マーカーだけである。

⚠️ ★ **例外は `emit_ime_shadow` だけ**で、これは**ユーザー操作ではなく IME の後始末**が
勝手に飛んでくる経路なので、G1 モードのときだけ止めた（違反の検出とは無関係）。
