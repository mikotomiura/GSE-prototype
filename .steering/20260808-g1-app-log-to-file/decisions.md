# 設計判断

## D-1: ログの出力先は「セッション NDJSON と同じフォルダ」

**決定**: `~/Documents/GSE-sessions/gse-app.log`（`GSE_DATASET` 有りなら `raw/<PID>/`）。

**理由**:
- 研究者が NDJSON を見に行く場所と同じ。探す場所を増やさない。
- 収束器 (`reconcile.rs:189`) は `*.ndjson` だけを拾うので、⚠️ **提出物には混ざらない**
  （実装で確認 → `app_log_is_not_picked_up_as_a_session_file` テストで固定）。

**却下案**: `~/.gse/` に置く
→ ★ 被験者にも研究者にも見えない隠しフォルダ。取り寄せの説明が増える。

**⚠️ 積み残し**: 被験者向け `README_先に読む.txt` は **このフォルダに触れていない**
（`dist-readme-macos.txt` を grep して確認）。★ ログを取り寄せるときは場所を伝える必要がある。

## D-2: 同期 I/O にしない（bounded channel + 書き込みスレッド）

**決定**: `impl MakeWriter for std::fs::File`（3 行で済む）を**使わない**。
`crossbeam-channel` の bounded(256) + `try_send` + 専用スレッド。

**理由**: `hook_macos.rs:428` の `tracing::warn!("InputEvent dropped (channel full)")` は
**CGEventTap のコールバックの中**にある。channel が詰まると打鍵ごとに発火しうるので、
そこでファイル I/O をすると `hook-constraints`（コールバック内ブロッキング禁止）を破る。

**却下案**: `tracing-appender` を足す
→ Cargo.lock にも registry cache にも無い。配布ビルドの依存を増やす。
`crossbeam-channel` は既存依存で、`logger.rs` の `LogChannel` と同じ形にできる。

**⚠️ 代償**: 溢れたら**捨てる**。★ 黙って捨てないよう、捨てた件数を次の行に出す。

## D-3: ファイル側の閾値を INFO に固定する

**決定**: `.with_max_level(Level::INFO)` をファイル側 writer に付ける。

**理由**: いま `env-filter` feature は入っておらず既定閾値も INFO
（`tracing-subscriber` の `Subscriber::DEFAULT_MAX_LEVEL` を一次資料で確認）なので**冗長**である。
それでも書くのは、⚠️ 将来 `RUST_LOG` を効くようにした誰かが
`hook_macos.rs:518` のキーコード (`VK=0x..`) を `debug!` 経由でディスクへ落とすのを
**構造で止める**ため（`data-privacy` ルール 1 を運用の注意に頼らない）。

★ この防波堤は統合テストで**壊して赤を見た**（`with_max_level` を外すと `VK=0x41` が
ファイルに現れて赤くなる）。

## D-4: `app_log_path()` は参加者 ID を解決しない（`GSE_DATASET` 無しのとき）

**決定**: `GSE_DATASET` が無い経路では `fallback_log_dir()` を直接使い、
`resolve_participant_id()` を**呼ばない**。

**理由**: この関数は **`tracing` の購読者を設置する前**に呼ばれる。
`resolve_participant_id()` には「新しい ID を生成 → `~/.gse/participant_id` へ永続化 →
`info!` で記録」という副作用があり、★ **先に呼ぶとその 1 行がどこにも出ないまま消える**。
`GSE_DATASET` 無しでは保存先が ID に依存しないので、副作用ごと後続の
`default_log_path()`（購読者の設置後）に任せる。

⚠️ `GSE_DATASET` 有り（開発機）では初回の `info!` が失われるが、開発機には端末がある。

## D-5: ログの外部送信はしない

**決定**: ローカル保存のみ。`data-privacy` ルール 2 の判断が要るので今回はやらない。

**⚠️ 帰結**: 研究者がログを見るには**被験者に送ってもらう**必要がある。
★ ログには `resolved_log_dir` などでホームパス（= 実名を含みうる）が入る。
`redact_home_path` は自動提出の詳細行にしか掛かっていない。取り寄せ運用を決めるときに再検討する。

## D-6: 後片付けで見つけた「残ったプロセス」は止めた

**決定**: `~/Desktop/G1_実施用_macOS` の削除承認に含まれるものとして、そこから動いていた
`gse-next`（PID 84943・3 時間・CPU 157 分）を SIGTERM で止めた。

**理由**: プロセスが動いたままフォルダを消しても、⚠️ 実体は unlink されたまま動き続けて
記録を書き続ける（消したことにならない）。

**⚠️ 消していないもの**: `~/Documents/GSE-sessions/*.ndjson` 3 本（承認外）。
★ うち `gse_20260808_060459.ndjson` は被験者の実施ではなく**研究者の通常作業 3 時間ぶん**である。
詳細は `cleanup-record.md`。

**★ 副産物の発見**: `windows-verification.md §4-1`（× で閉じてもプロセスが残る）は
Windows でしか観測されていなかったが、**macOS でも起きる**ことが実例で分かった。
原因（overlay 窓が残る限り Tauri は終了しない）はプラットフォーム非依存である。

## D-7: Codex レビューの判定 (2026-08-08)

| 指摘 | 判定 | 対応 |
|---|---|---|
| **HIGH** 開いたままの `rename` は Windows で失敗する → 上限が破れる | ⚠️ ★ **この形では成立しない**。Rust std は Windows で `FILE_SHARE_DELETE` を含む share mode で開く (`library/std/src/sys/fs/windows.rs:206` を一次資料で確認)。自分が開いているファイルの rename は通る | ★ ただし**帰結は実在する**ので、rename 失敗を数えて次の行に出すようにした |
| **MEDIUM** 書き込み失敗が完全に不可視 | ★ **正しい**。自己レビューでも同じ穴を挙げていた | 失敗を数え、書けたときに 1 行残す。⚠️ ★ ここで `tracing::warn!` を使わない (購読者の書き込み先そのものなので、warn がまた chunk になって戻ってくる) |
| **MEDIUM** フック側に allocation が残る | ★ 事実だが**悪化はしていない**。従来も stdout への write syscall が同じ経路で起きており、Tee にした今もそれは残る。⚠️ ブロッキング I/O をこれ以上増やしていないことがここでの要件である | 対応せず (理由を記録) |
| **LOW** ローテーション失敗経路が未検証 | ★ 正しい | T7 を追加 (`.1` をディレクトリにして rename を必ず失敗させる)。★ 変異で赤を確認 |
| **LOW** selftest が実装文字列に強結合 | ★ 事実。ただし本プロジェクトは「完全一致 + 変異で空回りを確認」を型にしている | 対応せず |

### ★★ Codex も私も見落としていたもの (T6 を書いて実測で判明)

⚠️ **Unix では unlink されたファイルに書いても成功する。**
「書き込みエラーで気づいて開き直す」設計は**赤のままだった** — エラーが起きないからである。
→ 書く前に `path.exists()` を見る形に変えた。★ ログの置き場はセッション NDJSON と
同じフォルダなので、被験者が「古いものを片付ける」つもりで消しうる。
黙って以後 0 行になる経路を潰した (作り直した回数もファイルに残す)。

## D-8: セッション提出トラッキングは Phase1 を写さず、自動集計にした

**決定**: タブ名は Phase1 に合わせて「セッション提出トラッキング」。
中身は **P-ID × ブロック 01〜10 のマトリクス**で、**手入力の列を 1 つも作らない**。

**理由**:
- ⚠️ ★ Phase1 の `buildSubmissionTab_` (`:1172-1183`) は **ヘッダ + ダミー 1 行だけ**で、
  埋めるコードがどこにも無い（手書き用の空タブ）。★ 無人・在宅（第 13 版）で
  「誰も埋めないタブ」を増やすのは無いより悪い（空を見て「提出ゼロ」と読み違える）。
- ★ G1 には材料が既にある: `g1CollectSubmittedBlocks_()`（`.age` をブロック単位で拾う）と
  `g1CountResponsesByPid_(FORM_ID_MCHECK, Q_BLOCK_NO)`（どのブロックの G1-M に答えたか）。
- ★★ **これが答えるのは 19 列が答えられないこと**: 「完了ブロック数 = 7」の
  **どの 3 つが欠けているか**。⚠️ 在宅では研究者が見ていないので、
  これが分からないと被験者への問い合わせ文が書けない。

**却下案 1**: 参加者ロスタータブも足す
→ ⚠️ ★ `:930-937` の**明文の設計判断**に反する。P-ID の採番元は Phase1 のロスターただ 1 つ
（`:1492`）。2 か所に持つと必ずずれ、PII の複製も増える。
★ そして「G1 実施トラッキング」19 列が実質の G1 ロスターである。

**却下案 2**: 進捗ダッシュボードも足す
→ 明文の根拠（「G1 は 1 人 1 回の実施機会で完結する」）は**今も有効**。
`protocol.md:718` が **10 ブロックを分けない（連続 70 分）** と定めているので、
Phase1 の平均セッション数・継続率にあたる概念が G1 には無い。

**行の真実源**: ★ 「G1 実施トラッキング」の P-ID 列（受け口フォルダではない）。
⚠️ フォルダを真実源にすると、**打ち間違えた P-ID がそのまま被験者として並ぶ**。
→ 代わりに「シートに無い P-ID の `.age`」は**別枠の警告**として出す（黙って捨てない）。

**トリガー**: 新しい毎時トリガーを**作らない**。`refreshG1RunSheet` の末尾で呼ぶ。
⚠️ 毎時トリガーが増えると互いに待って遅くなる（2026-08-08 に実測）。
★ 派生タブの失敗で本体の集計を巻き添えにしないよう try/catch で囲う。

**検証**: ★ 純関数を `.gs` から切り出して **node で実際に動かした**
(`scripts/tests/test_g1_submission_tab.py`・10 件)。
⚠️ うち 3 件は**変異テスト**（欠けブロックを出さない / G1-M を見ない / 孤児を捨てる
に壊すと赤になる）。★ grep で「関数がある」ことを見るだけの検査にしていない。

**⚠️ 未実施**: 実シートへのデプロイと目視確認（研究者判断）。
★ `gas-live-state-vs-code` の教訓どおり、**偽物が緑でも実物で落ちうる**
（`setFrozenColumns(1)` × 結合セルで実際に落ちた）。今回はその罠を先回りして
A1 を結合から外してあるが、⚠️ **実物で確かめるまでは「動く」と書かない**。
