# Form_G1 — G1 統制タスク実験の Google Form 一式

`GSE_G1_Form_Builder.gs` が **3 つのフォーム ＋ 運用管理シート**を構築する。文面の真実源は
`experiments/20260801-controlled-friction-task/consent.md` と `preregistration.md` であり、
**このディレクトリは配布と記録の手段**である（`materials/*.md` → `.docx` と同じ関係）。

| キー | 何 | いつ | PII |
|---|---|---|---|
| `G1-C` | ★ **説明・同意 ＝ 参加登録**（提出で P-ID 自動採番 ＋ 受付メール） | **募集時**（当日その場でも可）・**1 回** | 氏名・メール（＋任意で P-ID） |
| `G1-M` | 強制比較（操作チェック） | ブロック 3〜9 の直後・**計 7 回** | ★ 被験者 ID のみ |
| `G1-S` | 終了後アンケート | 最後の copy ブロックの後・**1 回** | ★ 被験者 ID のみ |

管理シート（`buildManagementSheet()`）は **2 タブだけ**:

| タブ | 中身 |
|---|---|
| **リンク集** | 各フォームの URL ＋ 記入パッドの置き場 ＋ 送付先（手動セルは再実行しても保持される） |
| **G1 実施トラッキング** | 1 被験者 1 行。同意 / 実施日 / OS / ビルド / `GSE_DISABLE_PROBES` / `HMM_VERSION` / 配置 / 完了ブロック数 / 各検査の実施 |

★ Phase1 にある **参加者ロスターと進捗ダッシュボードは作らない**（理由は下記）。

---

## ★★ P-ID は Phase1 と共有する（研究者判断 2026-08-03）

**同じ人には同じ P-ID を使う。** 1 人の人間に 2 つの識別子を作らない。

- ★ **採番元は Phase1 の運用管理シート「参加者ロスター」ただ 1 つ。** G1 側では採番しない。
  ⚠️ **2 か所で採番すると必ず衝突する**（別シートを走査しても相手の最大値が見えないため）。
  初参加の被験者は **Phase1 側で採番してから** G1 を回す。
- ★ 同じ理由で **G1 側に参加者ロスターを作らない**。実名↔P-ID の対応表を 2 か所に持たない
  （`data-privacy`）。実名は Phase1 のロスターと G1-C の回答シートにある。
- G1-C に「参加者ID（お持ちの方のみ）」欄を置いた。以前ご参加の方は自分の P-ID を知っているため。
  **必須にしていない**（初参加の方は持っていない）。

### ⚠️⚠️ ID 共有の帰結（必ず読む）

G1 は**第 1 週（blind 較正）モード**で回すので、`session_meta` に
`condition=blind_calibration` / `label_pool=calibration_blind` が刻まれる。
これは **Phase1 の較正セッションとまったく同じラベル**である（`data.md` の B-4）。

★ **ID まで共有すると、被験者 ID による分離が使えなくなる。** 残る分離手段は 2 つだけ:

1. `blocks/P0xx.json` の `file` 列（どの NDJSON が G1 のブロックかを列挙している）
2. ★ **gse-dataset への送付時に G1 であることを明示する** ← **弱い側。省略しない**

（最後の保険として、管理シートに **G1 実施日**を残す。⚠️ ただし日付は成果物には出さない。）

## ★★ 配備手順（コピペから実施まで・通し）

> ★ **固定 ID 方式**である。`FormApp.create` を使わない。
> ⚠️ Phase1 では `FormApp.create` が実行のたびに別フォームを量産し、配った URL と集計が読む
> フォームがズレて「**回答が記録されない**」不具合を起こした。

### STEP 1 — ★ **新しく作るフォームは無い**

3 本とも **2026-08-03 に作成済みで、ID も `.gs` に記入済み**である（実測で一致を確認）。

| 定数 | 役割 | 状態 |
|---|---|---|
| `FORM_ID_CONSENT` | ★ **G1-C 説明・同意 ＝ 参加登録**（form1） | ✅ 作成済み・記入済み |
| `FORM_ID_MCHECK` | G1-M 強制比較（form2） | ✅ 作成済み・記入済み |
| `FORM_ID_SURVEY` | G1-S 終了後アンケート（form3） | ✅ 作成済み・記入済み |

> ### ★★ G1-C がそのまま参加登録である（研究者判断 2026-08-03）
>
> G1-C は説明文に `consent.md` の内容を**全部載せ**、**同意 7 項目・氏名・メールアドレス**を
> 取っている。★ **これは参加登録として完全に機能する。**
> ⚠️ 別に「参加登録フォーム」を作るのは**重複**だった（一度作って廃止した）。
> **Phase1 も F1（スクリーニング＋同意）を募集時に使い、それをトリガーにしている**。
>
> - **募集時**に G1-C の URL を配る → 提出で P-ID 採番 ＋ 受付メール（自動）
> - **当日の署名**は別途 `handouts/G1_説明・同意文書.docx`（紙）で取る（`protocol.md §4.1`）
> - 当日その場で G1-C に回答した場合も同じ経路を通る（受付メールが届くだけで害は無い）

### STEP 2 — Apps Script にコピペする

1. `script.google.com` → **新しいプロジェクト**
2. `Form_G1/GSE_G1_Form_Builder.gs` の中身を**全部貼る**（既定の `myFunction` は消す）
3. プロジェクト名を付ける（例: `GSE G1 Forms`）

### STEP 3 — 定数を埋める（★ 空のままだと fail-closed で止まる）

★ **フォーム ID は記入済み**なので、埋めるのは 2 つだけ:

```javascript
var PHASE1_MGMT_SHEET_ID = "★Phase1 の運用管理シートの ID★";  // 参加者ロスターがあるファイル
var G1_CONTACT = "研究責任者 ○○（xxx@example.com）";
```

| 定数 | どこから取るか | 空だとどうなるか |
|---|---|---|
| `PHASE1_MGMT_SHEET_ID` | Phase1 の管理シート URL の `/spreadsheets/d/<ここ>/edit` | ★ **P-ID を採番できない**（採番元は Phase1 のロスターただ 1 つ） |
| `G1_CONTACT` | 研究責任者の連絡先 | ★ **受付メールが送れない** |

⚠️ ★ **日時・場所は定数に持たない。** メールに書かないためである（下記「自動メールは 1 通だけ」）。

### STEP 4 — フォームと管理シートを作る

エディタ上部の関数セレクタで **`setupG1Forms`** を選び ▶ 実行。

- ★ **初回は権限承認**が出る（Forms / Spreadsheet / Gmail）。「詳細」→「安全でないページに移動」で許可する。
- 実行ログ（`Ctrl/Cmd + Enter`）に **管理シートの URL** と各フォームの URL が出る。
- ★ 未設定の定数があれば**ログが警告する**（`G1_CONTACT` / `PHASE1_MGMT_SHEET_ID`）。

> ⚠️ 実行時間・クォータに当たったら、`buildG1RegisterForm()` / `buildConsentForm()` /
> `buildManipulationCheckForm()` / `buildPostSurveyForm()` を**単独実行** → 最後に
> `buildManagementSheet()` を回す（URL は Script Properties に残るので集約は成功する）。

### STEP 5 — 受付メールの文面を確認する（★ 送る前に）

**`previewRegisterAckEmail`** を実行 → ログに本文がそのまま出る。**送信はしない。**

★ `preregistration.md §2.12` の開示範囲と突き合わせる（題材・課題の型・難易度を書かない）。
⚠️ 手元でも機械検査できる:

```bash
python3 scripts/check_g1_emails.py    # run.sh からも走る
```

### STEP 6 — 自動送信を有効にする（★ 判断が要る）

```javascript
var G1_AUTO_SEND = true;   // 既定は false（下書き）
```

⚠️ ★ **`false` のままだと Gmail に下書きが溜まるだけで、被験者には届かない。**
登録直後に受付メールを届けるなら `true` にする。`installG1RegisterTrigger()` が実行時に警告する。

### STEP 7 — 登録トリガを設置する（★ 一度だけ）

**`installG1ConsentTrigger`** を実行。以後、G1-C が提出されるたびに
`onG1ConsentSubmit` が自動で走る（採番 → トラッキング行追加 → 受付メール）。

⚠️ 二重作成を防ぐため、既存の同名トリガは先に全削除される。外すときは `removeG1ConsentTriggers()`。

### STEP 8 — 回答をスプレッドシートに繋ぐ

各フォームの「**回答**」タブ → スプレッドシートアイコン → リンクを作る。
★ **G1-M は必須**（`forms_to_blocks.py` が CSV を読む）。

### STEP 9 — URL を取り出して配る

**`listG1FormUrls`** を実行 → ログに回答 URL / 編集 URL が出る。

- ★ **G1-C** … **募集で配る**（提出で採番＋受付メール）。当日その場で回答する場合は実施端末で開く
- **G1-S** … 実施端末にブックマーク
- **G1-M** … 実施端末とは**別のタブ／端末**で開く（記入画面を切り替えないため）

### STEP 10 — 管理シートの手動セルを埋める

「リンク集」タブの**送付先**などの手動セルを埋める。⚠️ 再実行しても手動セルは保持される。

### （任意）x.gd で回答 URL を短縮する

★ **G1 は対面実施なので必須ではない**（実験者がブックマークから開く）。
同意フォームだけ**事前にメールで送る**ような場合に効く。

1. x.gd の API キーを取得し、Apps Script エディタで **1 回だけ**次を実行する:

   ```javascript
   function setXgdKey() {
     PropertiesService.getScriptProperties().setProperty("XGD_API_KEY", "★ここにキー★");
   }
   ```

   ⚠️ ★ **実行したらこの関数を消すこと**（エディタのソースにキーが残るため）。
   ⚠️ ★ **キーを `.gs` にもこのリポジトリにも書かない。** 本リポジトリは**一時 public にする運用**がある。
   キーは Script Properties にだけ置く（`.gs` のソースには出ない）。

2. `shortenFormUrls()` を実行する（`setupG1Forms()` からも呼ばれる）。
   結果は Script Properties の `SHORTURL_*` に入り、`buildManagementSheet()` が
   **リンク集タブの「回答URL」列**に反映する（短縮が無ければ通常の回答 URL にフォールバック）。

**設計上の約束**:

- ★ **キー未設定なら何もしない**（ログに案内を出して戻る）。壊れない。
- ★ **冪等**: 既に短縮済みのものは作り直さない。
  ⚠️ 毎回叩くと**別の短縮 URL が量産され**、配った URL と集計が読む URL がズレる
  （Phase1 の `FormApp.create` と同じ壊れ方）。作り直すときは `clearShortUrls()` を明示的に実行する。
- ★ **失敗を黙って飛ばさない**: `status !== 200` ならログに残して**保存しない**
  （エラー文字列を短縮 URL として配る事故を防ぐ）。

## ★★ 募集 → 自動採番 → 受付メール（Phase1 の onF1Submit と同型）

> ⚠️ **確証実施のみ。** パイロット P-1 は研究者本人が被験者なので使わない（`preregistration.md §2.12-5`）。

### 全体の流れ

```
被験者が G1-C（説明・同意 ＝ 参加登録）を送信
        ↓ onG1ConsentSubmit が自動で走る
  ① Phase1 の参加者ロスターで重複チェック
     ├─ 既にいる（P-ID 申告 or 同じメール）→ ★ 再発番しない（冪等）
     └─ 新規 → P-ID を採番してロスターに追記
  ② G1 実施トラッキングに行を作る（P-ID のみ）
  ③ ★ 受付メールを自動送信（P-ID ＋ 当日の流れ ＋ 記録の範囲）
        ↓
  研究者が返信して日時・場所を確定する（★ 手書き。自動化しない）
  ⚠️ ★ フォームで希望日時は聞かない（研究者判断 2026-08-03）
```

> ### ★ 自動メールは **受付の 1 通だけ**（研究者判断 2026-08-03）
>
> ⚠️ **リマインドは実装していない**（時間トリガは 1 つも無い）。
> G1 は**対面 1 回で完結**するので「未提出者を追う」という Phase1 の課題が存在しない。
> ★ **日時・場所もメールに書かない。** 対面 1 回きりなら、日程の確定連絡は
> 研究者が普通に返信するほうが早く、自動化する価値が無い。
> → かつてあった `sendPreVisitEmail` / `sendPendingPreVisitEmails` は**廃止した**。

★ 具体的な手順は上の「**配備手順（コピペから実施まで・通し）**」を参照。

### ★ Phase1 から踏襲した 4 点（同じ失敗を繰り返さないため）

| 踏襲 | 何を防ぐか |
|---|---|
| **`LockService`** | 同時提出で**同じ P-ID が 2 人に出る** |
| **メールによる重複チェック** | 再提出しても**再発番しない**（冪等）。Phase1 参加者は既存 ID をそのまま使う |
| ★ **送信失敗を備考列に可視化** | 「発番済みだが通知が消えた」状態。⚠️ 再提出しても冪等スキップされるので**永久に届かない** |
| **`maskEmail`** | Apps Script 実行ログはクラウドに残る。実アドレスを出さない |

⚠️ ★ **適格性の自動判定は入れていない**。`preregistration.md` に募集段階の適格基準が無く、
`§2.9` の適格性ゲート（≥100 打鍵）は**実施後**に見るものだからである。
ここで独自基準を作ると、事前登録に無い除外を持ち込むことになる。

### ★★ メールに書いてよいもの / 書いてはいけないもの

`preregistration.md §2.12`（第 7 版）が凍結している。

| ★ 書いてよい | ⚠️ 書いてはいけない |
|---|---|
| 参加者ID・日時・場所・所要時間 | ★ **課題の題材（分野）** |
| 5 分 × 10 ブロック・1 分休憩 | ★ **課題文の本文** |
| 最初と最後が「書き写し」 | ★ **課題の型**（資料 1 本の要約 / 3 本の統合） |
| 300〜400 字 | ★ **難易度の示唆** |
| 記録する / しないもの | 仮説・判定基準・「摩擦」・HI / LO |

> ⚠️ ★ 第 6 版で一度「分野を書く」と決め、**第 7 版で撤回した**経緯がある
> （課題文は当日その場で画面提示するので事前に教える必要が無い・`§2.13`）。
> **書き戻されたら検査が赤になる**:
>
> ```bash
> python3 scripts/check_g1_emails.py   # run.sh からも走る
> ```
>
> この検査は ★ **node で GAS のグローバルをスタブし、本文生成関数を実際に呼ぶ**。
> ⚠️ `node --check` は構文しか見ないので、未定義参照（実例: `G1_TOPIC_TITLES` の残存）を
> 見逃す。**実行して確かめる**方式にしてある。列名参照（`runCol_` / `apply`）の実在も同時に見る。

### ★ なぜ G1 側で採番しないのか（`§2.0` の再確認）

`assignG1ParticipantId()` は **Phase1 の「参加者ロスター」に対して**採番する。
⚠️ ★ **G1 側にロスターを作って採番すると、2 か所採番になり必ず衝突する**
（別シートを走査しても相手の最大値が見えない）。
既に Phase1 に参加した人は**この関数を通さず、その人の既存 P-ID をそのまま使う**。

> ⚠️ `Form_Phase1` 側にも `nextParticipantId_` があり、**採番規則の実装が 2 つある**。
> 規則を変えるときは両方直すこと（**`Form_Phase1` 側が正**）。

## ★ 3 フォームの制約は正反対である（取り違えると実験が壊れる）

| | G1-C 同意 | G1-M 強制比較 | G1-S 終了後 |
|---|---|---|---|
| 形式 | 必須チェックボックス ＋ 記名 | ★ **二択のみ**（「どちらでもない」なし） | 二択・3 択 ＋ 自由記述 |
| リッカート | — | ★ **1〜5 は禁止**（`§2.6`） | 使わない |
| 絶対に書かない | どのブロックが難しい条件か（`protocol.md §4.3`） | ★ **HI / LO** | ★ **HI / LO** |
| 「もう一度回答」リンク | 出さない | ★ **出す**（7 回答えるため） | 出さない |

- ★ **G1-M の選択肢は相対表現**（「1つ前のブロックのほう」「直前のブロックのほう」）にしてある。
  被験者にブロック番号を計算させると、そこで 1 つずれる。番号への変換は `forms_to_blocks.py` が行う。
- ★ **設問文を変えたら `forms_to_blocks.py` の `HEADER_KEYS` / 選択肢定数も同じ版に直す。**
  このプロジェクトでは「文書だけ改訂して実装が追随しない」事故が 2 回起きている
  （`.steering/20260802-g1-execution-prep/decisions.md` E-6 / E-7）。
