## §1 ⚠️★★★ 「送る前」と「送ったあと」で手順が違う

★ O1 のログは **1 日ごとに閉じ、そこから 48 時間おいて**自動提出される
（`o1.rs:62` `SUBMIT_GRACE_MS = 48h`）。★ この 48 時間が**削除保証を守るための機構**である。

| いつ | 誰が消すか | 何が起きるか |
|---|---|---|
| ★ **提出される前**（その日＋約 2 日） | ★ **被験者が自分の端末で**（アプリの「この時間帯の記録を消す」） | ★ 端末上の `gse_o1_*.ndjson` から該当行が消える。⚠️ **研究者には届かない** |
| ⚠️ **提出されたあと** | ★ **研究者が本手順で** | ⚠️ **被験者の端末操作では消えない。** ★ 本文書 §3 の全経路を回す |

### ⚠️ なぜ端末操作では消えないのか（一次資料）

`delete_time_range`（`lib.rs:1342-1466`）→ `redact_dir`（`redaction.rs:154-183`）は
**`gse_*.ndjson` の通常ファイルだけ**を書き換える。★ 対象の判定は
`is_redactable_session_file`（**`redaction.rs:188-196`**・呼び出しは `redaction.rs:169`）で、
`name.ends_with(".ndjson")` を要求する。

→ ⚠️ **`.age`（提出物）は `.ndjson` で終わらないので構造的に対象外**である。
★ `redaction.rs` に `.age` という語は 1 度も出てこない（除外は帰結であって明示ではない）。

> ⚠️★ **既存文書の行番号がずれている**（2026-08-28 に実測）。
> `.claude/skills/data-privacy/SKILL.md:179` と `docs/adr/ADR-014-…:430` は根拠として
> `redaction.rs:174-181` を挙げるが、そこは `redact_dir` の**ループ本体**であって、
> 除外を決めているのは **`redaction.rs:188-196`** である。★ 主張は正しいが出所がずれている。

## §2 ★ 削除要求の経路（⚠️ 被験者に理由を尋ねない）

1. ★ 被験者が **口頭・メール・フォームのいずれか**で研究者に申し出る
   （宛先: 三浦尊統／ZEN大学／`mmiura.network@gmail.com`）。
   ⚠️★★★ **理由を尋ねない。**（同意文書 §4 逐語「理由を説明する必要はありません」）
   ⚠️ `delete_time_range` は**引数に理由を持たない**（`lib.rs:1347` 逐語
   「⚠️ **引数に理由が無い。★ 追加してはならない**」）。★ 運用でも揃える。
2. ★ 受け取る情報は **P-ID と時間帯（または「全部」）だけ**。
3. ★ **§3 のチェックリストを上から順に全部回す。**
4. ★ 終わったら **§6 の表に 1 行足してコミットする。**
5. ★ 被験者に「消しました」と伝える（⚠️ 何を消したかの内訳は返さない）。

⚠️ ★ **参加の取りやめ**も同じ経路で扱う（同意文書 §4 逐語「やめた時点で、
それまでの記録をすべて削除するよう求めることもできます」）。★ その場合は時間帯＝全期間とする。

### §2b ⚠️★★★ 「使わないでください」は **削除要求とは別の申し出**である（★ 2026-09-13 追加）

★ 2026-09-13 に、同意文書 §3 へ **任意**の二次利用同意（★ 記録から計算した数値を
「かたちにして見せる研究」に使わせていただく）を足した。⚠️ その節は逐語で約束している ——
「★ あとから『**使わないでください**』とお申し出いただけます」。

⚠️★★★ **これを §2 の削除要求と混同しない。** ★ 求められているのは**用途からの除外**であって、
**記録の削除ではない**（⚠️ 逆に、勝手に消すと参加そのものを取りやめたと誤って扱うことになる）。

| ★ 申し出 | 何をするか | ⚠️ しないこと |
|---|---|---|
| 「**記録を消して**」（§2） | ★ §3 のチェックリストを全部回す | — |
| 「**二次利用に使わないで**」（本節） | ★ 下の 3 手だけ | ⚠️ **記録を消さない**（★ 本人は参加を続けている） |
| ★ 「**使ってよい**」（★ 後述） | ★ 同じ 3 手（`granted = true`） | ⚠️ **こちらから誘導しない** |

### ⚠️★★★ 「あとから同意をいただく」場合（★ 任意項目の追加**前**に登録した方）

★ 任意項目をフォームに足す**前**に登録を済ませた方は、**その設問を見ていない**。
→ ⚠️ §5c の規則により **自動的に「同意なし」**として扱われる（★ fail-closed。それでよい）。

⚠️★★★ **黙って同意とみなさない。** ★ 使わせていただきたい場合は:

1. ★ **改めてご説明して、お伺いする**（⚠️ 断られても不利益が無いことを必ず先に伝える）。
2. ★ 同意をいただけたら `recordO1SecondaryUseChange("<P-ID>", true)` を実行する。
3. ★ §6 の表に 1 行足す（★ 備考に「二次利用の追加同意」）。

⚠️ **こちらから繰り返し頼まない**（★ 断りにくくさせない）。

1. ★ **登録ログ**（`O1_MGMT_SHEET_ID` の「O1 登録ログ」）に **1 行追記する**。
   ⚠️★★★ **手で打たない。** ★ Apps Script のエディタで次を実行する:

   ```javascript
   recordO1SecondaryUseChange("P015", false);   // ⚠️ 撤回（「使わないでください」）
   recordO1SecondaryUseChange("P015", true);    // ★ あとから同意をいただいた場合
   ```

   ★ 行の形（種別 `consent-update` / 結果 `ok` / 理由 `2nd-use-withdrawn` / 備考 `2nd-use: no`）は
   **関数が作る**。⚠️ 手入力だと **1 文字の違いで §5c の判定から静かに漏れる**
   （★ 赤にならないので誰も気づかない）。
   ★ P-ID の形が違う / 第 2 引数が `true` `false` でない場合は、⚠️ **1 行も書かずに止まる。**
   ⚠️★★★ **既存の行を書き換えない**（★ 追記ログである。⚠️ 書き換えると「いつ同意していたか」が消える）。
   → ★ **読むときは、同じ P-ID の行のうち「種別が `register` / `consent-update` で、
     かつ `2nd-use:` の印を持つ」最新の 1 行が効く。**
   ⚠️★★★ **「ただの最新行」ではない**（code-reviewer 指摘・2026-09-13）:
   ★ `assign`（研究者の手動採番・`o1LogMgmt_("assign", …)`）や `blocked`（`dup-pid` 等）の行は
   **P-ID を持つのに `2nd-use:` の印を持たない**。⚠️ 「最新行」で読むと、
   **採番をやり直しただけで同意が消える**（★ 安全側に倒れるが**偽陰性**であり、
   しかも研究者には理由が見えない）。
2. ★ **同意の正本**（O1-C 回答シート）の回答は**そのまま残す**
   （⚠️ 消すと「同意があった事実」も消え、★ その後の撤回が何に対する撤回か分からなくなる）。
3. ★ §6 の表に 1 行足す（★ 備考に「二次利用の撤回」と書く）。⚠️ **範囲は `—`**（削除していないため）。

⚠️★★★ **`yes → no` の反転は、撤回とは限らない**（★ security-checker 指摘 2026-09-13）。
★ `register` の行は**提出のたびに印を上書き追記する**ので、⚠️ 受付メールの失敗などで
**同じメールでもう一度提出してもらった**とき（★ その復旧手順は `o1FinishO1Registration_` が案内している）、
被験者が任意項目のチェックを入れ忘れると **`yes` が黙って `no` に倒れる**。
→ ★ 結果は安全側（使わない）だが、⚠️ **研究者からは理由が見えない**。
★ 反転を見つけたら、**撤回の申し出を受けているか**を §6 の表で突き合わせること。

⚠️ ★ **理由を尋ねない**（★ §2 と同じ）。

## §4 ⚠️★★★ gse-dataset に O1 を出すと、削除が git 履歴の書き換えになる

★ 2026-08-28 に**実測で確認した穴**である。

| 実測 | 結果 |
|---|---|
| `scripts/sync-session.sh` / `sync-session.ps1` に O1 を弾く記述はあるか | ⚠️ **`o1` の出現 0 件**＝**弾いていない** |
| gse-dataset の `.gitignore` は `metrics/` を除外しているか | ⚠️ **していない**（除外は `raw/**/*.ndjson` 等の NDJSON だけ） |
| `metrics/` は実際に追跡・push されているか | ⚠️ **されている**（`git ls-files metrics/` = **34 件**） |

→ ⚠️★★★ **O1 のセッションを `sync-session.sh` に通すと、O1 由来の `metrics.json` が
private repo にコミットされ push される。** ★ そうなると削除は
**force push を伴う履歴の書き換え**になり、⚠️ **他の clone には残り続ける**。

### ★ 運用上の規則（⚠️ 守れないなら O1 を dataset に出さない）

1. ⚠️★★★ **O1 のセッションを `sync-session.*` に通さない。**
   ★ O1 の解析は**研究者端末のローカルで完結させる**（`experiments/` に来歴のみ残す）。
2. ★ どうしても dataset に出す必要が生じたら、**先に本文書を改訂して**
   「削除が履歴書き換えになる」ことを同意文書に反映してから行う。
3. ✅ **2026-08-28 に実装した**: `sync-session.sh` / `sync-session.ps1` の**両方**が
   O1 のセッション（ファイル名 `gse_o1_*` または `meta` 行の `o1_mode`）を **exit 4 で弾く**。
   ★ 弾くことを示す検査は `scripts/sync_session_o1_guard_test.sh`（陰性 ＋ 陽性対照）。
   ⚠️ ★ ガードは**入口 1 か所**である。手で `gse-replay --metrics` を回して
   `metrics/` へ置く経路は塞げない。★ そちらは本節 1 の運用規則が担う。
