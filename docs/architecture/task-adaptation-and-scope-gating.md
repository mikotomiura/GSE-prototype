## 0. 要約

1. **T-C（較正プロトコル）**: 検出器を検証できる観測を先に設計する。鍵は
   **セッション内 block 設計**——同一人物・同一セッションの中に in-scope と out-of-scope を
   **設計から両方**入れる。これが「観測全体が偏っている人には within-person のレバレッジが無い」
   という実測の破綻（P011）を構造的に解く唯一の方法である。
2. **T-A（統合設計）**: out-of-scope は **head の 1 つにしない**。**走っている head に対する相対的な
   `scope_fit`** とし、`evidence_quality` を下げ `uncertainty` を上げる。
   既存原則（「未較正 head では強介入を出さない」）が**そのまま発火する**ので、**新しいゲート機構を作らない**。
   宣言と観測が食い違っても **re-route しない**（宣言は routing、観測は割引。役割を混ぜない）。
3. **T-B（検出器の構造）**: `flag := (個人内逸脱 OR コホート逸脱) AND 絶対水準ゲート`＋
   **尺度 floor**＋**中心のコホートへの縮約**＋★**到達不能性（マスキング）を出力に含める**。
   **定数は書かない**。定数は Phase2 の構造化 block データから、**in-scope 側だけを使って**決める
   （＝感度を推定量として残し、既知の 2 点に線を引かない）。

> - **定数**（floor 倍率・縮約強度・絶対ゲート閾値・最小 n）。手続きだけを決める。

## 2. T-C — Phase2 較正プロトコル（**ラベル供給**・検証の律速）

> ★ **順序の理由**: どんな検出器も**正解ラベルが無ければ PLAUSIBLE から動かない**。
> 検出器を先に詰めると「それを検証できる観測が設計されていない」という同じ穴に落ちる。

### 2.1 Phase1 が失敗した構造（繰り返さないために言語化する）

- 被験者への指示は「**いつも通り**文章作成や思考作業をするだけ」（`participant-setup-guide.md:71`）で、
  実際の作業は**自己選択**である。
- 一方 `App.tsx` は `task_kind` を `argumentative` に**ロック**している（`src/App.tsx:12,114`・凍結対象）。
- 帰結: 全セッションが `argumentative` を名乗るが、**その値は観測ではなく設定**である。
  **UI ロックは宣言する能力を奪うだけで、実際の作業を拘束しない。**
  → **交絡は除去されたのではなく不可視化された。**

> ★ したがって Phase2 で最初に直すべきは閾値でも特徴量でもなく、
> **「宣言」を定数から観測に戻すこと**である。ロック解除だけでは足りない（自己申告は当てにならない）。

> ### ★ 2026-08-19 研究者判断 — **宣言は routing のみに使い、正しくさせようとしない**
>
> ★ **決定**: `App.tsx` の argumentative lock を外したあと、`task_kind` の**宣言**は
> **ADR-010 D3 の写し**として扱う ——
> 「**宣言は routing のみ、観測は `scope_fit` のみ。融合して『真の `task_kind`』を作らない**」。
>
> ★ **理由**: **新しい原則を持ち込まない**（既存決定の写しで足りる）。
> ⚠️ 宣言が**外れることを前提**にし、検出は `scope_fit` で `evidence_quality` を下げる形に後置する。
>
> ⚠️★★ **承知している穴**: **lock を外してから `scope_fit` が入るまでの期間は、
> 宣言が外れても検出できない。** ★ その期間のセッションは
> 「**宣言は観測ではない**」と明記して扱うこと。
> ⚠️ `scope_fit` の定数は `§4.5` 経由で較正プロトコルからしか出ず、
> **`§2.8` の相乗りを見送った**ので待ちは短くない。
>
> ★ **G1 中は別**: G1 は論述課題であり、宣言がぶれると**ブロック間で head が変わり
> 比較可能性が壊れる**。→ ⚠️★★★ **lock を外す実装をするときは必ず `g1_mode()` 条件付きにする**
> （2026-08-19 時点では **App.tsx は無変更**＝完全 lock のままリブート後の G1 を回す）。
>
> 記録: `.steering/20260819-g1-reboot-and-instrument-fix/decisions.md` 判断 5 / 6。

### 2.2 設計原理（4 つ）

| # | 原理 | 何を防ぐか |
|---|---|---|
| **C-1** | **正例を設計から作る**（自然発生を待たない） | 38 セッションで外的正解ラベルが 1 件しか無かった状態の再来 |
| **C-2** | **同一セッション内に両クラスを入れる** | 「その人の観測全体が偏っていると within-person にレバレッジが無い」（P011 の破綻 3） |
| **C-3** | **ラベルの単位＝ block**（セッションでも人でもない） | 個人 baseline の汚染（マスキング）を**測定可能**にする |
| **C-4** | **宣言・観測・割当を別チャネルで記録する** | ② と ③ を融合して「真の task_kind」を作る誘惑を断つ（→ §3.3） |

### 2.3 セッション構造 — block 設計

構造化較正セッションは、**境界時刻が既知の block 列**として構成する。

```text
[warm-up]  →  [A: 割当 in-scope]  →  [B: 割当 out-of-scope]  →  [A': 割当 in-scope]
  破棄          （通常の論述作業）      （§2.4 の正例）           （復帰の確認）
```

- **block 境界は `task phase change`**（`personalization…md §3.1` の Decision Episode 境界）として記録する。
  → 新しいイベント種別を作らない。既存の境界定義に載せる。
- **順序は被験者間・セッション間で counterbalance** する（B を常に中央に置かない）。
- **warm-up は解析から破棄**する（開始直後の立ち上がりを block A の分布に混ぜない）。
- **境界をまたぐ窓は検証から除外**する（→ §3.4 の解像度整合。読み出し窓長 ≤ 最短 block 長を制約とする）。

> ### ★ なぜ「セッション内」でなければならないか（本書の中心的な主張）
> within-person 検出器が最大の true positive を取り逃した理由は、**その被験者の 5 セッション全部が
> 対象外寄りだったこと**である（`keys_per_min` の母集団 z=6.19 を個人内 z=+1.00 に潰した）。
> **セッション間**の within-person 対比では、この人からレバレッジを取り出せない。
> **block 設計は、全員が定義上両クラスを持つ**ことを保証する。
> これは閾値調整では得られない、**観測設計でしか得られない性質**である。

### 2.4 out-of-scope の正例をどう作るか

- 候補は **`progress_proxy` を最大化する反復的打鍵作業**——写経・書き写し・タイピング練習の類。
  `personalization…md §3.2` が「対象外作業で最大化する」と名指しした失敗モードそのものを、**意図的に作る**。
- ★★ **自前で設計しない。writing research の標準計測器である copy task を採用する** [P38]。
  Inputlog に多言語版が実装され、**転写・運動技能の baseline として打鍵ログ解析に含めることが推奨**されている。
  ★ **副産物が大きい**: copy task ブロックは正例であると同時に、**その人の「純転写」の下限**を直接与える。
  → §4.1 の個人 baseline が汚染される問題（マスキング）に、**外から参照点を 1 つ持ち込める**。
- **欺瞞は不要**。「短い書き写しの区間を挟みます」と事前に伝えてよい（同意手続きを増やさない）。
- ⚠️ **限界（必ず明記して報告する）**: 割り当てられた書き写しは、
  **自然発生する対象外作業（気が散って別の作業に流れる等）と同じではない**。
  demand characteristics により署名が誇張されうる。
  → **割当正例で推定できるのは検出可能性の上界**である。感度の一般化はしない。
- ⚠️ 正例は **1 種類に固定しない**（書き写しだけで閾値を決めると、その 1 種類の検出器になる）。
  最低 2 種類（例: 書き写し／機械的な定型入力）を用意し、**種類別に感度を報告**する。

### 2.5 ラベルの 3 供給層

| 層 | 得られるもの | 使ってよい用途 | 使ってはいけない用途 |

### 2.6 除外基準にタスク内容を含める（対処案 ④）

- 現行 inclusion criteria は**タスク内容に一切触れていない**（`preregistration-v0.3.md` に該当規定なし）。
- Phase2 では **block 単位の除外基準**を事前に書く。セッション単位にしない
  （1 block の逸脱でセッション全体を捨てるのは情報の浪費であり、逆に黙認は Phase1 の再演になる）。

## 3. T-A — out-of-scope を含むタスク適応の統合設計

### 3.1 決定 1: out-of-scope は **head ではなくフラグ**

> **`NullHead` / `UnknownHead` を作らない。** `scope_fit` を `WorkStateEstimate` の
> `evidence_quality` / `uncertainty` に接続する。

**根拠**:

1. **head 選択と scope 判定は問いが違う**。routing は「どのモデルが適用対象か」、
   scope は「**この証拠にモデルが適用できるか**」を問う。後者は**証拠の性質**であり、
   `evidence_quality` は定義上まさにそれを表す欄である。新しい欄も新しい enum も要らない。
2. **NullHead は routing を要求する**。head にすると「NullHead へ切り替える」判断が必要になり、
   それは**確信のある分類**を前提とする。だが検出器は本質的に低確信であり
   （外的正解ラベル 1 件・感度も偽陽性率も未推定）、確信を要求する場所に置いてはいけない。
3. **hard switch は情報を捨てる**。head を差し替えると走っていた head の推定が**消える**。
   フラグなら「推定は出るが弱く扱う」という**連続的な縮退**ができる。
4. ★ **新機構が不要**という §11-11 の性質を保存できる。
   `evidence_quality` が低い → `none`/`defer`（`intervention-decision-engine.md:82`）、
   未較正 head → 強介入禁止（`domain-adapter-boundary.md §原則`）。**どちらも既に書かれている。**
5. ★ **文献の分類と一致する** [V73][V74]。棄権には **ambiguity rejection**（境界近傍で誤りやすいから棄権）と
   **novelty rejection**（訓練分布から乖離しているから棄権）の 2 種があり、**別の量**として区別される。
   GSE の `uncertainty`（head 内部の曖昧さ）＝ ambiguity、`evidence_quality`（証拠が較正分布に合うか）＝ novelty。
   → ★ **`scope_fit` を `uncertainty` に足し込んで 1 本にまとめてはならない**（文献が区別する 2 量を潰す操作）。
   `scope_fit` の**主たる接続先は `evidence_quality` 側**である。
6. 「不確実なら自動化を弱める」は mixed-initiative の確立した原理 [P42] であり、**新規の発明として書かない**。

### 3.2 決定 2: scope は **head 相対**（絶対的な「対象外」を定義しない）

`scope_fit` は「**走っている head が較正された分布と、いま観測している証拠がどれだけ整合するか**」である。
絶対的な「対象作業/対象外作業」は定義しない（content-free では原理的に定義できない）。

> ★ **この定義の副産物が、routing 誤りへの fallback になる**。
> 宣言が `argumentative` なのに実際は coding をしている場合、Writing head の `scope_fit` が下がり、
> `evidence_quality` が下がり、強介入が出なくなる。
> **「誤った head で黙って処理される」（§11-11 の穴の本体）が、ルーティングを直さずに塞がる。**
> 逆に言えば、head ごとに **判別特徴も定数も別物**である（Writing の「推敲の不在」は Coding では意味が違う）。
> → **scope 判定機構は共有し、特徴集合と定数は head が所有する**（ADR-006 の「β は head 所有」と同じ所有規則）。

### ★★ 参照分布の鍵は head 単位ではなく `head × task_kind` 単位である（2026-08-02 追加）

ADR-006 の分岐は `Argumentative | Correspondence => WritingHead` であり、**論述と通信文は同じ head** に入る。
ところが両者は **knowledge-transforming と knowledge-telling** で停滞の質が構造的に違い（[P17]・
`docs/literature/20260629-task-type-writing-struggle.md`）、打鍵特徴は **課題の小さな違いにも感度がある**（[P36]）。

> ★ **したがって「論述で較正した Writing head に通信文を流すと `scope_fit` が下がる」という
> 偽陽性モードが構造的に存在する。** ジャンルの違いを対象外と取り違える——[P36] が名指しした失敗そのものである。

**対処（新機構を作らない範囲で閉じる）**: `scope_fit` の**参照分布を `head × task_kind`（宣言値）で鍵づける**。
個人 baseline が既に `user × task_kind × phase` で鍵づけられている（`§5.3 ContextSnapshot`）のと**同じ規則**であり、
鍵を 1 つ揃えるだけで済む。`phase` は §3.6 により Phase2 では `unspecified` に collapse する。

⚠️ **前提の弱さを明記する**: この鍵づけは `task_kind` enum が意味のある分割であることに依存するが、
**現行の 4 変種は ad-hoc であり理論的裏づけが無い**（`research-positioning §8`・
`20260629` カードが telling↔transforming 軸での**再定義と経験的検証**を「やり残し」として名指し済み）。
→ **enum の再定義は本設計の前提条件**であり、§6 の未解決に挙げる。
⚠️ 鍵を増やすと**鍵あたりのデータが減る**（§3.6 と同じトレードオフ）。task_kind は 4 変種を超えて増やさない
（`ADR-006 Migration 5`: schema は additive のみ・enum は 4 変種維持）。
⚠️ **2026-10-02 追記**: ADR-037 が O1 の宣言に 5 つ目の値 `other`（「その他・細切れの作業」）を足した。
★ ただし **`other` は鍵にしない**（ADR-037 D3）—— 個人ベースラインの推定から外すか、未宣言と同じ扱いにする。
→ ★ **鍵の数は 4 のまま**であり、本節の制約は実質的に維持される。

### 3.3 決定 3: 宣言と観測が食い違ったら — **re-route しない**

| 信号 | 役割 | 役割**でない**もの |
|---|---|---|
| 宣言 `task_kind`（②） | **routing のみ**（どの head を走らせるか） | 較正の正解ラベル |
| 観測署名（③） | **`scope_fit` のみ**（走っている head の証拠を割り引く） | routing の入力 |

**衝突時の規則: 宣言された head を走らせ続け、`evidence_quality` を下げる。**

**根拠**:
- ② は単独では無力（Phase1 の宣言値は分散ゼロで教師に使えなかった）。
  ③ は**何をしていたかを言えない**（content-free の直接の帰結）。
  **どちらも相手の役割を果たせない。** 役割を分けることは妥協ではなく、各信号が実際に供給できるものの上限である。
- ★ **観測で re-route すると閉ループになる**。head を切り替えると参照する baseline が変わり、
  その baseline が次の scope 判定の入力になる。**検出器の誤りが自分の入力を書き換える。**
  外的正解ラベルが無い状態でこのループを本番に載せてはいけない。
- **失敗のコストが非対称**。割り引く側の最悪ケースは「介入が減る」。
  re-route の最悪ケースは「**別の baseline で自信を持って誤採点する**」。

**昇格ゲート（自動 re-route を将来許すなら、先にこれを満たす）**:
1. §2 の S 層で **block 単位の precision/recall が推定されている**こと（点推定と区間の両方）。
2. 誤 route 時の**復帰規則**（元の head へ戻る条件）が事前に定義され、振動しないことが replay で確認済みであること。
3. re-route の有無で介入判断が反転する割合が報告されていること（`§8.2 G2` と同じ「決定に効くか」の形式）。

### 3.4 決定 4: 時間解像度 — **推定は streaming・読み出しは Decision Episode**

| 層 | 単位 | 理由 |
|---|---|---|
| 統計の更新 | **セッション内の trailing 窓**（streaming） | `bs_rate` のような率は短時間では雑音。§4.4 Phase A の EWMA / robust quantile 機構に**そのまま乗る**（新機構不要） |
| `scope_fit` の読み出し | ★ **Decision Episode ごと** | 介入判断が起きる粒度。`ContextSnapshot` は既に `evidence_quality` を持つ（§5.3）ので**配線先が既にある** |
| セッション単位 | **研究解析のみ** | 事後にしか出ないので介入に使えない。これまでの実験がセッション単位だったのは**オフライン解析だったから**である |

> ⚠️ **推定量が変わることを明示する**: これまでの 2 実験は**セッション**を採点した。
> Phase2 の検証は **block**、本番の読み出しは **窓/episode** である。
> **block 単位のラベルで検証できるのは、窓が block の内側に収まる場合だけ**である。
> → 読み出し窓長 ≤ 最短 block 長 を制約とし、**境界をまたぐ窓は検証集合から除外**する（§2.3）。

### 3.5 「新しい機構を作らない」制約（allow-list 方式で守る）

**許される変更（これだけ）**:
1. head が `scope_fit` を計算する（head 内部・Layer 3-4）。
2. `evidence_quality` に**単調な減衰**を掛け、`uncertainty` を対応して上げる。
3. `ContextSnapshot` / ログに `scope_fit` と到達不能フラグを **additive に記録**する（`ADR-005`）。

**禁止（これをやったら設計が壊れている）**:
- Decision Engine に「scope ゲート」を新設する。
- 新しい介入レベル・新しい UI 状態・新しい通知を足す。
- `scope_fit` が低いときに**推定を出さない**（hard mute）。減衰には下限を置き、ゼロにしない。
- `scope_fit` を Layer 5-7（Opportunity/Receptivity/Decision）が**直接**読む。読むのは `evidence_quality` のみ。

### 3.6 `phase` の暫定決定（`§11-1` 未解決 1）

**提案（研究者判断待ち）**: Phase2 では `phase` を**意味づけしない**。

- `phase` := 直前の `task phase change` 境界からの区間（**構造的定義のみ**）。
- **N 層（自然セッション）では `phase = unspecified` に collapse する**。
- **S 層（構造化セッション）でのみ、割り当てた block id を `phase` とする**。

**根拠**: 個人 baseline は `user × task_kind × phase` で鍵づけられる（§5.3）。
`phase` に意味的な値（計画/起草/推敲…）を入れると**鍵の濃度が増え、鍵あたりのデータが減る**。
その意味的分割を検証する正解ラベルは**現時点で存在しない**。
→ **正解ラベルの供給が phase の細分化を律速する**（本書の他の判断と同じ規律）。
head 推定の `phase` は、S 層で「割当 block を当てられるか」が確認できてから検討する。

## 4. T-B — 検出器の**構造**を凍結する（定数は凍結しない）

### 4.1 構造

head `h`・個人 `u`・特徴 `m ∈ M_h`（`M_h` は head 所有・§3.2）。窓統計 `x_m` に対し:

```text
center_{u,m} = λ_{u,m} · median_personal + (1 − λ_{u,m}) · median_cohort      # 縮約 (partial pooling)
scale_{u,m}  = max( robust_scale_personal , c_m · robust_scale_cohort )       # ★ floor
z_person     = ( x_m − center_{u,m} ) / scale_{u,m}
z_cohort     = ( x_m − median_cohort ) / robust_scale_cohort

deviation_m  = ( z_person · s_m < −k_p )  OR  ( z_cohort · s_m < −k_c )        # s_m = 事前宣言した符号
absolute_m   = ( x_m · s_m < a_m )                                            # ★ 絶対水準ゲート
flag_m       = deviation_m AND absolute_m
scope_fit    = g( { flag_m, margin_m } )        # 単調・(0,1] 有界・§4.4
```

**凍結する構造的コミットメント**:

| # | コミットメント | なぜ |
|---|---|---|
| **B-1** | **絶対ゲートとの連言**（`AND`。和や加重和にしない） | 相対基準単独が生んだ偽陽性（`bs_rate` 5〜6% ＝普通の文章作成）を**絶対項だけで消せる**ことが実測された |
| **B-2** | **相対項は個人とコホートの選言**（`OR`） | 両者は**盲点が相補的**（下表）。片方だけにすると必ずどちらかの取り逃しが残る |
| **B-3** | **尺度 floor** `max(personal, c·cohort)` | 一貫した人で z が発散した（実測 z=+25.8 / +12.9）。★ **この floor は scope 検出器専用にせず、`§4.4 Phase A` の robust quantile 実装に置く**——同じ病理は `reference_deviation` など**全ての within-person z** に効くため。⚠️ **この現象は文献に接地していない**（結果は swamping に似るが機序が違う・[V70] 参照の否決 R-3） |
| **B-4** | **中心のコホートへの縮約** | 個人 baseline の汚染（**masking** [V70]・median/MAD の破綻点 50% を混入率 44% が突破した）を緩和する。⚠️ 「in-scope と判定済みのセッションだけで baseline を作る」は**鶏卵問題なので採らない**。★ **copy task ブロック（§2.4）は「純転写の下限」という外部参照点を供給する** [P38] |
| **B-5** | ★ **到達不能性を出力する**（§4.3） | 「検出できなかった」と「**そもそも検出できない**」を区別する |

| 枠組み | 捉えるもの | 盲点 |
|---|---|---|
| 個人基準 | そのセッションが**その人の普段と違う** | 逸脱が常態化している人（マスキング）／観測全体が偏っている人 |
| コホート基準 | その人が**対象作業をしている人々と違う** | 個人差そのもの |
| 絶対基準 | **実質的な深刻さ** | 個人差 |

### 4.2 3 項構造の根拠 — ★ これは **retrodiction であって証拠ではない**

既知の 4 例に当てはめると 3 項構造だけが全部を説明する:

| 事例 | 個人基準 | コホート基準 | 絶対ゲート | 3 項の結論 | 望ましい結論 |
|---|---|---|---|---|---|
| `P013-s08`（打鍵 約1,400 に修正 1 回） | ✗ 取り逃し（z=−0.96・マスキング） | ✓ 発火 | ✓ 通過 | **flag** | flag |
| `P011-s01`（自己申告で裏づけ） | ✗ 取り逃し（`bs_rate` z=−2.21） | ✓ 発火（`keys_per_min` z=6.19） | 要検証 | **flag** | flag |
| `P012-s04`（`bs_rate` 0.0533） | ✓ 発火（z=−5.83） | ✗ | ✗ **阻止** | **no flag** | no flag |
| `P012-s02`（`bs_rate` 0.0572） | ✓ 発火（z=−4.30） | ✗ | ✗ **阻止** | **no flag** | no flag |

> ### ⚠️ この表を性能の証拠として読まないこと
> 4 例すべてが**この構造を導出した当のデータ**である。**導出集合 = 検定集合**であり、循環している。
> 外的正解ラベルは依然 **1 件**しかなく、**感度も偽陽性率も推定できない**。
> この表が支持するのは「**3 項のうち 1 つでも欠くと既知の失敗が再現する**」という**必要性**だけであり、
> 十分性ではない。検証は §2 の新規データで行う。
>
> ### ★ 2026-08-02 追記 — 判別特徴の選択は**独立に裏づけられた**（ただし数値は移らない）
> `bs_rate`（削除・修正の率）を第一候補にしたのは本プロジェクトの導出データ由来の仮説だったが、
> **writing research と test security が独立に同じ特徴を主要判別子として報告している**:
> 自然な執筆は転写より**語と文字をより多く削除し、修正が多い**（[P37]・RF **99%**）、
> **revisions は課題間で頑健に動く一方、平均打鍵間隔は課題間で安定**（[P36]）。
> → ★ **F1（平均打鍵間隔系）・F4（平均バースト長）を scope 判別特徴に入れない**根拠になった（§4.6）。
> ⚠️ ★★ **99% を GSE へ移送しない**——[P37] は**教師あり・クラス均衡・事後解析**であり、
> GSE は**ラベル無し・低頻度・実時間**である。低頻度下では precision が崩れる（base-rate fallacy [V72]）。
> ⚠️ [P36] の結論後半は**逆風**である: *打鍵特徴は手元の書字課題の小さな違いにも感度がある*。
> → 「対象外」と「別の（正当な）書字課題」を打鍵特徴は区別しない。**§3.2 の head 相対定義と §3.3 の
> 「断定せず割り引く」がこれで支持される**（否決 R-4）。
>
> ⚠️ ★ **B-2（コホート項の選言）は `§11-11` に記録された処方箋（連言のみ）を一歩越えている。**
> 越えた理由は上表の 2 行目——**唯一の外的 true positive を当てたのはコホート基準の方**だったこと。
> 代償は偽陽性の露出増であり、それを吸収するのが絶対ゲート（B-1）である。
> **これは仮説であって実測ではない。** Phase2 で B-2 の有無を比較して報告すること。

### 4.3 到達不能性（マスキング）を出力に含める

各 `(u, m)` について、**フラグに必要な `x_m` の値**を逆算する（実測例: ある被験者は
必要 `bs_rate` が **負値**＝`bs_rate ≥ 0` なので**数学的に到達不能**だった）。

- 到達不能なら `(u, m)` を **`unreachable`** と判定し、**その特徴の個人項を無効化**する。
- **`unreachable` は「in-scope」ではない。** `scope_fit` を 1.0 にしない。
  その `(u, m)` は**コホート項＋絶対ゲートだけ**で評価する（＝母集団基準へ縮退）。
  これは「観測全体が偏っている人に個人基準はレバレッジを持たない」という実測に対する直接の対処である。
- 個人 `n` が最小件数に満たない間も同じ扱い（個人項を有効化しない）。
- **報告要件**: `unreachable` の件数・被験者別内訳・reachability 表を、**性能数値と必ず同時に**出す。
  これが無い報告は「フラグ 0 件 ＝ 異常なし」と誤読される。

### 4.4 `scope_fit` → `evidence_quality` の写像

- `g` は **単調非増加**・値域 `(0, 1]`・**下限を持つ**（0 にしない＝ hard mute の禁止・§3.5）。
- `evidence_quality ← evidence_quality × g(scope_fit)`、`uncertainty` は対応して単調に増やす。
- **他の消費者を作らない**（§3.5 の allow-list）。
- ★ **旧 X 軸との関係（2026-08-02 追加）**: `evidence_quality` は新軸専用の欄ではない。
  ADR-009 D1b で旧 X 軸は**降格**したが、`p_stuck` → Need は **Phase 2b までは現行のまま**介入を駆動する
  （`personalization…md §2.5`）。したがって **`scope_fit` は当面、降格した旧軸の側にこそ効く**。
  これは意図どおりである——`progress_proxy` の穴は `§11-11` が明記するとおり
  **旧軸と新軸に共通する穴**であり、scope ゲーティングは両方を同時に守る。
- **ヒステリシス**を持たせる（窓ごとに評価が振動して介入可否がちらつくのを防ぐ）。
  形式は既存の EMA ヒステリシス（`hmm-analysis`）と同型にし、新しい平滑化機構を発明しない。

### 4.5 定数の**推定手続き**（値はここに書かない）

> ★ **鉄則: 定数は正例を使わずに決める。** そうすれば感度が**推定量として残る**。
> いま在る 38 セッションで閾値を決めると、**既知の 2 点に線を引くだけ**になる。

> ### ★★ この手続きは自前ではない — conformal outlier testing の特殊形である [V66][V67]
> 「参照データ（in-scope）のスコア分位点として閾値を置き、**正常標本を外れ値と呼ぶ確率を α 以下に抑える**」は
> conformal outlier detection の標準形であり、Annals of Statistics 水準の保証が付いている。
> **自前の工夫として書かず、この語彙と保証に載せる。** 得られるもの:
> 1. 「specificity を設計で固定する」が**定理として言える**（モデルの当たり外れに依存しない）。
> 2. ★ **較正集合の大きさが達成可能な α の下限を決める**（conformal の有限標本性質。⚠️ 逐語未確認）
>    → **§2 の block 数を統計的要求から逆算できる**。
>
> #### ★★ ただし 3 つの制約が付く（すべて GSE に不利な側）
> | 制約 | 出典 | 設計への帰結 |
> |---|---|---|
> | ★ **被験者ごとの保証は分布非依存には不可能** | [V68] | **固定できるのは marginal FPR のみ**。「この人の偽陽性率は α 以下」とは**書かない**。個人別に欲しければ個人較正集合が要り、その n が α の下限を作る。★ §4.3 の「個人項が使えないときコホート項へ縮退する」は、**この不可能性の下で唯一可能な形**である |
> | 交換可能性が要る。窓は同一セッション内で強く相関する | [V69] | ★ **較正単位は block（またはセッション）とし、窓を独立標本として数えない**。読み出しが窓/episode 単位であること（§3.4）とは矛盾しない——**較正の単位と読み出しの頻度は別物**である |
> | conformal p 値は test point 間で**相互依存**する | [V66] | 窓ごとの flag を集計する運用では多重性・依存を扱う。**「flag 件数」を素朴に率として報告しない** |

| 定数 | 推定手続き | データ |
|---|---|---|
| 絶対ゲート `a_m` | **in-scope block の分布の宣言済み分位点**に置く（specificity を設計で固定する）。out-of-scope block は**一切見ない** | S 層 in-scope のみ |
| 尺度 floor 倍率 `c_m` | in-scope block での `|z|` の**上側分位点が宣言値を超えないように**選ぶ（＝尺度発散を抑える基準であって、検出を最適化する基準ではない） | S 層 in-scope のみ |
| 縮約強度 `λ` | **人単位分割の交差検証**（`§4.4` の既存規定「縮約強度は交差検証で選ぶ・ICC の点推定に紐づけない」に従う） | S+N 層 |
| 逸脱閾値 `k_p` / `k_c` | 同上（in-scope 側の偽陽性率を宣言して逆算） | S 層 in-scope のみ |
| 個人項の最小 `n` | 事前に規則として宣言（データから選ばない） | — |
| 特徴集合 `M_h` と符号 `s_m` | **事前登録**する。現在の第一候補（`bs_rate` 低方向・`keys_per_min` 高方向）は導出データ由来の仮説だが、★ **削除・修正の率が判別子であることは独立の文献で支持されている** [P37][P36]。★ **平均系（F1/F4）は課題間で安定なので入れない** [P36] | — |

**禁止事項**:
- Phase1 の 38 セッションで**いかなる定数も**決めない（導出集合と同一で循環する）。
- Phase2 の結果を見てから特徴・符号・主指標を選び直さない
  （前ラウンドで「無効な検定を凍結してしまった」実例がある。**無効だったと記録し、修正版は探索的として併記する**）。
- `a_m` を決めるのに使った block で感度を報告しない（分割を明示する）。

**報告要件**: 感度・偽陽性率（区間つき）／正例の**種類別**内訳（§2.4）／`unreachable` 表（§4.3）／
除外 block 率（§2.6）／B-2 の有無の比較／
★ **base rate（正例の事前確率）と precision の併記**——**accuracy・感度のみの報告を禁止する**。
低頻度事象では高い検出率が実用的な精度を意味しない（base-rate fallacy [V72]）。
本コホートで外的根拠のあるセッションは 38 中 1〜2 件であり、**運用時の事前確率は低い**と想定される。

### 4.6 オフライン側の消費（本番経路とは別）

`scope_fit` は person-period 行（`§4.4 Phase C`）にも記録し、**recovery model の感度解析の共変量**として使う。
`progress_proxy` は対象外作業で最大化するため（§3.2）、`scope_fit` が低い期を含む/除く両方で
`CIF_rec(H)` を推定し、**結論が反転しないか**を見る（`§8.2 G2` と同じ「決定に効くか」の形式）。
→ これはフィールドを 1 つ記録するだけであり、新機構ではない。

## 5. 主張しないこと（過大主張の禁止・`gse-v2-overview.md §5`）

1. **外れ値であること ≠ 対象外作業をしていたこと。**
2. ★ **フラグされないこと ≠ 対象作業だったこと。** §4.3 の `unreachable` はその機械的な実例である。
3. 本書の構造で**検出器が働くことは示していない**。示したのは「これらを欠くと既知の失敗が再現する」ことだけ。
4. content-free である限り「**何をしていたか**」は原理的に分からない。個別の解釈には本人確認か外形的記録が要る。
5. ★ **マスキングは接地した [V70] が、尺度過敏（swamping）は接地していない**——結果は似るが機序が違う。
6. ★★ **「content-free で対象外作業を判別する」こと自体は新規ではない。**
   写経 vs 自然な執筆は打鍵ログのみで高精度に判別されており [P37][P39][P40]、
   デスクトップのタスク切替検出にも先行研究がある [P41]（ただし**リソース識別子依存**）。
   GSE に残る差分は **(i) ラベル無しで運用時に判定する / (ii) 判定を分類の出力でなく介入の抑制
   （`evidence_quality`）に接続する / (iii) 低頻度・個人内**という条件の**組合せ**だけである。
   → `research-positioning §3 / §4` に還元済み。
7. ★ **本ラウンドの文献確認は一次全文まで降りていない**（abstract / 要旨水準）。「文献で確定した」と書かない。
