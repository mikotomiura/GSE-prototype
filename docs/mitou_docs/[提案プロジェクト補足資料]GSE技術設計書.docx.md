# **0\. 本書の読み方 —— 何を主張し、何を主張しないか**

**本書は2026年度提出版の全面改訂である。** 改訂は誤字の修正ではなく、**主張・実装・ロードマップの全面的な置き換え**である。2026年度版から降ろした主張と、その理由を最初に列挙する。査読者が最初に疑うであろう点を、こちらから先に開示するためである。

| # | 2026年度版の記述 | 本版での扱い | 理由 |
| :---- | :---- | :---- | :---- |
| 1 | **4段階介入**（Nudge → Ambient Fade → Thought Scaffold → Wall）／ **Monk Mode** | **削除** | 画面を塞ぐ介入は「答えの受領」だけを狙えず、AI依存も助けを求める行為も作業そのものも一律に止める。Monk Mode は Wall 専用だったため定義上デッドになった（§5.3） |
| 2 | **6特徴量** | **5特徴量**（F2 を除外） | F2（Flight Time 分散）は単一のタイポや長押しへのノイズ感度が高く、少データ下のHMMを不安定化させる（§3.1） |

| 5 | **8分間の歩行で発散的思考が60%向上** | **取り下げ** | micro-breakのメタ分析（22標本 / N=2,335）で成績は全体null（d=.16, p=.116）、認知負荷の高い課題では d=−.09。かつ**歩行に特化した推定値は存在しない**（§5.4） |
| 6 | **3クラス Macro F1 ≥ 0.5** をフォールバック発動条件とする | **事前登録の語彙へ置換** | 凍結された合否契約は GATE1–3 / PreReg-1〜8 である（§7.1） |

**本書の全体を貫く規約**: 主張のたびに **(a) 何を主張するか (b) 何を主張しないか (c) 反証側の一次証拠** を並べる。特に、**「先行研究が無いこと」を「有望であること」の根拠として使わない。**

# **1\. 設計哲学: Keystroke-First / Content-Free**

## **1.1 芯となる技術的仮説**

| 【要約】 「同じ5秒の沈黙でも、深く考えている沈黙と固まっている沈黙では打鍵パターンが違う」という仮説に基づき、キーボード操作だけで作業状態を推定します。 |
| :---- |

GSEは「答えを与えるAI」の対極に位置する。生成AIが効率を最大化するのに対し、GSEはユーザー自身が答えに辿り着く「苦闘のプロセス」を守る。この設計思想は不便益研究[3][4][5]とProductive Failure[1]に理論的基盤を持つ。

核心仮説:

**「同じ5秒間の沈黙でも、深く考え込む沈黙と固まる沈黙では打鍵パターンが異なる」**

| 【具体例】 論文執筆中のユーザーが5秒間手を止めた場合。従来のツールは「5秒止まった＝サボり」と判定し警告を出します。GSEは直前まで高速でタイプしていた（滑らかな出力が続いていた）ことを記憶しているため、「これは次の文を練っている沈黙だ」と扱い、介入しません。一方、書いては消し、消しては止まるを繰り返している場合は「詰まっていそうだ」と扱い、**かつ割り込んでよい瞬間が来たときにだけ**介入します。 |
| :---- |

**学術的根拠**

① **キーストロークと認知機能の相関**: Park（2024）[11]はスマートフォンのキーストロークダイナミクスで軽度認知障害をAUC 0.88で判別し、特にFlight Timeが認知機能と有意な相関（r=−0.491, p<.001）を示した。

② **本文を保存せずに「どう書いたか」から推定できること**: Mehtaら（2025）[12]は打鍵の仕方だけからLLM支援の有無を検出した。GSEの content-free 制約はこの系譜に乗る。

③ **打鍵動態は「机を離れていた間の身体状態」まで含む**: Giancardoら（2015）[13]は睡眠慣性を誘発した統制実験で **AUC 0.93 / 0.91** を報告し、逐語で「**タイプされたテキストの内容や言語によらず**」と述べている。**これは日本語話者を対象とするGSEにとって重要な接地である**（言語依存の心配が要らない）。

④ **ポーズパターンには認知的意味がある**: Hall, Baaijen & Galbraith（2024）はライティング中のポーズ分布が多峰性を示すことを実証した。

**ただし、②③④から「沈黙の中身を割れる」は導けない。§1.2 でその天井を書く。**

## **1.2 なぜキーストローク単独か —— そして、その天井**

**採用の理由（3点）**

**汎用性**: 特別なハードウェアなしにあらゆるテキスト入力環境に組み込める。
**実現可能性**: マルチモーダル融合は同期・ノイズ・較正・個人差吸収の全てを要し、9ヶ月の開発期間では非現実的である。
**プライバシー**: 本文・クリップボード内容・ウィンドウタイトルを一切保存せずに済む。**これは制約ではなく設計上の資産である**——Phase1の事後アンケートで**被験者4名全員が「プライバシー不安はなかった」**と回答した（§10）。

**そして、この設計の天井を隠さずに書く**

**天井①: 打鍵を伴わない作業は原理的に測れない。** 5特徴量はすべて打鍵動態から算出されるため、動画編集・スライド作成・図面/CAD等では特徴量が縮退し、**無音と離席が区別できない**。これは特徴量の調整では解けず、入力層の再設計を要する別課題である。**外的妥当性の主張は text-based knowledge work に限定する。**

**天井②: 「デスク上の行動を足せば当たるようになる」は一次証拠が否定する側にある。** GSEと同条件（個人ごとのモデル・実地・自己申告 criterion）で得られている実測は、**4社・開発者20名・平均11営業日で precision 0.57 / recall 0.48**[15]である。中央値分割のため base rate ≈ 0.5、すなわち**偶然 +0.07** に過ぎない。**しかもその特徴量はアプリ識別子→カテゴリ写像に依存している。GSEが自ら禁じた情報に支えられて、なお0.57である。**

独立に同じ帯域が2本目もある（マウス軌跡からのmind wandering検出は F1 が無作為基線 +15% 止まり）。さらに**この系の基礎研究は外的再現に失敗しており**、逐語で「**多数派分類器のベースラインを有意に上回るモデルを再現できなかった**」[46]と報告されている。同論文が名指しした3つの脅威（小標本 / 強い不均衡 / 尺度の場当たり的変換）は、**Phase1の条件と3つとも一致した**。

→ **したがって本書は、観測空間の拡張を「精度を上げる」ためではなく「打鍵が沈黙した区間を、停滞 / 熟考 / 離席に割る」ためのものとして位置づける。** そして勝ち幅は、**(a) 多数派分類器 と (b) 現行5特徴量ベースライン の2つに対して報告する。**

**天井③: 被験者横断の universal marker は存在しない。** 個人内分類 89.5% に対し被験者横断は深層学習を含む全器で <60%、116名で共有マーカー群なし[41]。これは**個人内較正というGSEの方針を最も強く支持する**一方で、**新規ユーザーは較正セッションを経ないと「その人にとって妥当な」推定にならない**ことを意味する。**これは正しい設計選択の代償であって、実装改善で消せる欠陥ではない。**

**ここで「動かない」と「介入してよい」を分けて書く**（混同すると、未較正のまま介入する設計に読める）:

| 較正の状態 | 推定 | 介入 | 妥当性の主張 |
| :---- | :---- | :---- | :---- |
| **較正前**（母集団ベースライン） | **動く**（Stage 1 はゼロデータで走る・§2.2） | **強い介入を出さない**（可視化と `defer` の記録に留める） | **しない** |
| **較正後**（個人ベースラインを凍結） | 動く | Need × Opportunity に従って発火 | **GATE3 を通った範囲でのみ主張する** |

**原則**: **較正が済んでいないヘッドでは強い介入を出さない。****不確実性が高いときは自動化を弱める**という mixed-initiative の原理の実装であって、GSE の発明ではない。

## **1.3 主張の層構造 —— 何をどの層で計算し、何で検証するか**

**2026年度版の最大の問題は「3状態を推定する」という1つの文で、性質の異なる4つの計算を束ねていたことである。** 本版では層を分ける。

| 層 | 何を計算するか | 実装 | 何で検証するか | 確証 / 探索 |
| :---- | :---- | :---- | :---- | :---- |
| **L0: 潜在二軸** | 5特徴量 → **X（Cognitive Friction）/ Y（Productive Engagement）** | HMM前段（軸射影） | 主観プローブ Q1（摩擦）/ Q2（前進）との**個人内の順序一致**（C-index） | **確証（GATE3）** |
| **L1: Stuck** | X/Y → **`p_stuck`** | HMM（Forward Algorithm） | 独立な主観 Stuck 申告、行動アウトカム | 探索 |
| **L2: Need** | `p_stuck` に閾値＋抑制を当てた**介入要否の決定** | 介入判断 | 混同行列・**HIR**・Precision・STALL-recall | 探索 |
| **L2': Opportunity** | 小休止・cooldown 等の**タイミング判定** | 介入判断 | 近接アウトカム（micro-randomization） | 探索 |

**`p_stuck` は「介入判断が焚く」値ではなく「推論層が計算する」値である。** 介入判断（L2）は `p_stuck` を閾値で消費する**別計算**であり、その判断性能はL0/L1とは独立に評価される。

**そして確証するのは L0 だけである。** L0のC-indexが検証するのは「**システム内部の軸を、同種の自己申告と照合する収束的妥当性**」であって、Stuck（L1）やNeed（L2）の独立・客観的なGround Truthではない。**「認知状態を捉えた」とは書かない。**

**検証記号との対応**

| 記号 | 何を問うか | 対応する層 |
| :---- | :---- | :---- |
| **X1** | 推論妥当性（行動プロキシは主観と順序一致するか） | L0（確証） |
| **X2** | 介入機会妥当性（good timing で発火できるか） | L2 / L2'（探索） |
| **Y** | システム価値（AI依存が下がり自力解決が上がるか） | 行動アウトカム |

## **1.4 既存システムとの比較**

**2026年度版の比較表を全面的に書き換えた。** 変更点は3つ:「認知状態推定: 3状態」→ 降ろした主張／「適応的介入: ○ 4段階」→ 削除済み／**FlowLightを比較対象に追加**（この系が実配備まで到達しており、GSEの位置づけを最も鋭く問うため）。

| 観点 | **GSE（本提案）** | RescueTime / Centered | BiAffect | **FlowLight**[14] |
| :---- | :---- | :---- | :---- | :---- |
| 入力ソース | 打鍵（キーレベル・**本文非保存**） | アプリ使用時間 | スマホKB | 打鍵＋マウスの**量** |
| 出力 | **`p_stuck`（連続信号）** | 時間集計 | 気分の2値 | 「忙しいか」の2〜4値 |
| 沈黙の扱い | **中身の弁別を問いに据える** | ✗ | ✗ | **要求されていない**（少ない側の弁別が不要） |
| 割り込み判断 | **Need × Opportunity 分離・`defer` を記録** | 通知のみ | ✗ | 中断可否のみ |
| 日本語IME対応 | ○（未確定文字列の解析） | ✗ | ✗ | ✗ |
| 識別子の使用 | **一切使わない** | アプリ識別子 | — | **使わない**（個人分位のみ） |
| 実配備の実績 | **無い**（Phase1は判定に届かず） | 商用 | 研究 | **12か国・449名・中断−46%** |

**正直に書く: 実配備の実績という一点で、GSEはFlowLightに完全に負けている。** そしてFlowLightは**アプリ識別子もウィンドウタイトルも1つも使わず、「直近3分の打鍵＋マウスを重み付き合計し、その利用者自身の過去数日の上位9%/4%分位で閾値化する」だけ**でそこに到達した。

**したがってGSEの差分は「識別子を使わないこと」ではない**（その経路は既に1本ある）。**差分は「操作量が少ない側——停滞 / 熟考 / 離席——を弁別すること」である。** FlowLightはそれを一度も要求されていない。

# **2\. アーキテクチャ全体図**

## **2.1 4層パイプラインとモジュール境界**

```
【1】Sensing Layer         【2】Inference Layer      【3】Decision Layer       【4】Physical Anchor
    (input/)                   (analysis/)               (analysis/)               (未実装)
 ─────────────────         ────────────────────      ───────────────────      ──────────────────
 OS固有のKBフック           5特徴量 → 2軸射影          Need  = p_stuck 閾値      一定時間の離席と
 Win: WH_KEYBOARD_LL        → HMM → p_stuck           Opportunity = 小休止      作業への復帰
 mac: CGEventTap (30秒ローリング窓) → none/nudge/defer センサを使わない
 IME状態検出                1Hz ゲート                 cooldown/daily cap
 Atomic + channel           プラットフォーム非依存      HIR を評価指標に持つ
        │                          │                         │                        │
        └──────────────────────────┴─────────────────────────┴────────────────────────┘
                                   │
                        【5】Expression Channel（第2の柱・§6）
                            4値の抽象イベントを PC → スマホへ一方向送信
```

**この境界は「図の上の話」ではなく、実装のモジュール境界と一致している。**

- `analysis/` は**プラットフォーム非依存**であり、OS APIを直接呼ばない。OS依存は `input/` と `sensors*.rs` に隔離されている。この分離により、**同じ解析テストが Windows / macOS の両方で走る**。
- **回帰保護**: ゴールデンセッションのNDJSONをCLIで再実行し、出力の **byte-equal 一致**で回帰を検出する。推論の挙動を変えたら推論バージョンを上げ、ゴールデンを再生成し、差分が意図どおりかを作業記録に残す規約になっている。
- **スキーマドリフト検知**: NDJSONスキーマはRustの型定義から機械生成し、CIが差分を検知する。データリポジトリ側との整合が自動で保たれる。
- **本書で「実装済み」と書いた主張が、何によって守られているかを対応させる**（守られていないものは「未実装」と書く）:

| 「実装済み」と書いた主張 | 何が守っているか |
| :---- | :---- |
| 推論パイプライン（§4） | **ゴールデン再実行の byte-equal 一致**。推論を変えたらバージョンを上げ、ゴールデンを再生成する規約 |
| 介入判断の閾値（§5.1） | **既定閾値がコード定数と一致することを検査するテスト**（誰かが別値をハードコードしたら落ちる） |
| NDJSON スキーマ（§3.4） | **CI のドリフト検知**（型定義から機械生成し差分を比較） |
| OSごとに規則が違うロジック | **両OSに対のテストを置く規約**（§9-5。片OS前提のテストが他方のCIで落ちた実測がある） |
| Phase1 の判定パイプライン（§10.3） | **反証方向のテスト**（未実施を不合格と出さない／1名でも施行済みなら従来どおり未達を出す） |
| **表現チャネル（§6）** | **未実装。** 受け入れ観点だけを先に固定してある |
| **Physical Anchor（§5.4）** | **未実装。** |
| **セキュア入力欄での記録抑止（§3.4）** | **スキーマ項目はあるが送出元が無い。** Gate S の判定対象 |

**ユーザー体験フロー例**

| 【具体例】 シナリオ: 学生がレポートを執筆中 【0:00〜5:00】 高速でタイプ中。Sensing Layerが「短い打鍵間隔・修正なし」を検出 → 低Friction × 高Engagement → `p_stuck` は低い → **介入なし**。 【5:00】 手が止まる。3秒の沈黙の後に一気に打ち始める → 直前の状態の慣性により `p_stuck` は上がりきらない → **介入なし**（良質な沈黙を壊さない）。 【5:30】 「書いては消し」を繰り返す。F3/F6 が高騰 → `p_stuck` が上昇し **Need が立つ**。**しかしこの瞬間は能動的にタイプしている（打鍵間隔 < 2秒）ので `defer`（見送り）** —— 進行中の苦闘には割り込まない。 【5:45】 打鍵が止まり、小休止（2〜8秒）が訪れる → **Opportunity が立つ** → Nudge を右端に小さく表示。クリックは遮らず、一定時間で自動的に消える。 |

## **2.2 MhD Core: 段階的設計と、Stage 3/4 を主目標から外した理由**

| Stage | モデル | 入力 | 出力 | 必要データ | 昇格の Go/No-Go | 本提案での位置 |
| :---- | :---- | :---- | :---- | :---- | :---- | :---- |
| **1** | ルールベース ＋ HMM | 5特徴量 → 2軸（26観測ビン） | `p_stuck` 等 | **不要** | — | **現在地。正（デフォルト）** |
| **2** | ロジスティック回帰（L2正則化） | 5特徴量 ＋ 交差項 | P(Stuck) | 約50セッション | Stage 1 比 **+3%** | **データ未達。Phase C で判断** |
| 3 | 勾配ブースティング | ＋ラグ特徴 | — | 約100セッション | Stage 1 比 +5% | **本提案の主目標から外す** |
| 4 | 1D-CNN / TCN | 生イベント列 | — | 約200–500セッション | Stage 3 比 +5% | **同上** |

**Stage 3/4 を主目標から外した理由を明記する。** 2026年度版はStage 4までのロードマップを主要な技術的売りとして書いていたが、**較正が打ち切られたため昇格判定に必要なデータが存在しない**（§10）。**「データが無いのに段を上げる」ことは、この分野で最も再現性を壊す行為である**——実際、外的再現に失敗した先行研究[46]が名指しした3脅威のうち2つは小標本と強い不均衡だった。

**オッカムの剃刀を明示的な規約として置く**: **より複雑なモデルを採用するには、計算コストの増大を正当化できる明確な改善（事前宣言した閾値）が必須である。** 未達なら軽量モデルを正とする。

**Stage 1 がゼロデータで動くことは、この設計の資産である。** 開発初日から動作し、他の全モデルの比較基準になり、**新規ユーザーが較正を終える前でも「画面に何も出ない」状態を避けられる。**

**ただし「動く」と「介入してよい」は別である。** 較正前に出してよいのは**可視化と `defer` の記録**までであり、**強い介入は個人ベースラインの凍結後に限る**（§1.2 の表）。

# **3\. Sensing Layer: キーストローク解析**

## **3.1 5特徴量（30秒ローリングウィンドウ）**

**2026年度版の「6特徴量」を「5特徴量」に訂正する。** ウィンドウ幅30秒は、CS1課題でポーズ頻度と認知負荷の相関を20〜60秒のセグメントで分析した知見、およびライティング中のポーズ分布を30秒ウィンドウで解析した手法に基づく。

| # | 特徴量 | 定義 | 認知的意味 | 学術的背景 |
| :---- | :---- | :---- | :---- | :---- |
| **F1** | Flight Time 中央値 | 連続キー間隔の中央値（ms） | 思考の速度。長いほど迷いが生じている | Park (2024)[11]: r=−0.491 |
| **F3** | Correction Rate | (BS + Del) / 全キー押下数 | 「書いては消す」頻度 | Leinonen (2016): 修正率と成績が負相関 |
| **F4** | Burst Length | 連続入力（FT<200ms）の平均文字数 | 滑らかな出力の正の指標 | Flow研究の系譜 |
| **F5** | Pause Count | 2秒以上の無入力の回数 | 停滞の頻度 | Stone (2024) |
| **F6** | Pause-after-Delete率 | 削除直後に2秒以上停止する割合 | 「消した後に固まる」= 詰まりのループ | **本研究が提案する特徴量** |

**F2（Flight Time 分散）を外した理由**

F2はリズム安定性の指標として重要だが、**単一のタイポや偶発的な長押しに対するノイズ感度が他の特徴量より高い**。少データ環境のHMMではこのノイズが状態推定を不安定化させるため、軸射影の重み付けから意図的に除外している。**これは「不要だから外した」のではなく「この段では害の方が大きいから外した」である。** Stage 2 以降で交差項として導入し、除外実験（ablation）で判別力への寄与を検証する。

**「2秒閾値」は検証されたものではない**

F5 / F6 が使う2秒という閾値について、正直に書く。この閾値はライティング研究の慣習に由来するものであり、一次資料の逐語は「**主に伝統に基づく**」「**恣意的な2秒の下限**」である。**したがって本提案では、閾値の個人相対化を検証項目として明示する**（後述 §7.3）。この方向は3つの分野が独立に収束している——実配備での個人分位[14]、固定帯域では分離しなかったという実測[16]、執筆研究の「個人の中央値×2」。

**そして最も重要な反証を書く: 「沈黙を長さの帯域で切れば分かれる」は実測で否定されている**

米国/Python 231名 ＋ 欧州/Java 244名 = **475名の2つの独立文脈**で、micro（2–15秒）/ short（15–180秒）/ mid（3–10分）/ long（>10分）という**4帯域を事前宣言してから**検定した結果、逐語で「**あらゆる長さのポーズの頻度が成績と負相関する**」[16]。**著者自身の事前予測（microは正相関するはず）が外れている。** しかも mid 帯域は結論でも「**気が散っているのかもしれないし、外部資源を使って助けを求めているのかもしれない**」と割れたままである——**これはGSEが最も分けたい2つ（離脱 vs 外部化して解決）そのものである。**

**代わりに弁別しているのは「沈黙の直前に何を押したか」である。** 同論文で、英数キーは全イベントの57%を占めるのに micro の27% / long の15% しか開始せず、特殊文字は micro ポーズと負相関（著者の解釈は「構文への習熟不足とためらいの信号」）、Return は全帯域でほぼ一定＝弁別に使えない。→ **「ポーズの長さではなく位置（直前イベント種別）を分類する」という方針が、実測に裏づけられた。**

**アーキテクチャ上の性質**

**計算コスト**: 全特徴量が O(n) で算出可能。リングバッファによりメモリ使用量は固定（600イベント × 16バイト ≈ 10KB）。
**リアルタイム性**: 1秒ステップでウィンドウをスライドし、状態変化を約1秒の遅延で捕捉する。
**長期沈黙の扱い**: 打鍵が完全に止まった区間では、直前のF3/F6を基準に**合成摩擦**を時間とともに緩やかに注入する（§4.3④）。

## **3.2 入力モード別ベースラインと変換候補の抑制**

**【設計課題】** 日本語IME入力（あ/カモード）と英字直接入力（Aモード）ではキーストロークの統計的性質が構造的に異なる。日本語入力ではローマ字の高速連打の後に変換候補選択のポーズが入るため、F1のベースラインが英字入力時より短く、F5のベースラインは高くなる。この差を無視して単一のベースラインで正規化すると、**日本語入力中の正常な変換操作が系統的に「詰まり」方向へ誤分類される。**

**【実装: Dual Baseline】** 正規化関数のベースライン β を入力モード別に2系統管理する。

| コンテキスト | IME状態 | β_F1(ms) | β_F3 | β_F4 | β_F5 | β_F6 |
| :---- | :---- | :---- | :---- | :---- | :---- | :---- |
| **β_writing**（日本語composition） | ON | 100 | 0.10 | 2.5 | 1.0 | 0.12 |
| **β_writing_latin**（英字直接入力） | OFF | 150 | 0.06 | 5.0 | 2.0 | 0.08 |

**β_writing の設計根拠**: F1=100msは、日本語ローマ字入力時の高速連打（例: "toukyou" = 7打鍵を約700msで入力）の実測値に基づく。**旧値220msはIME変換待ちを含む想定だったが、実セッション分析で実際の中央値が約100msであることが判明し再較正した。** F3=0.10は変換操作に伴うBackspace頻度が英字入力時より高いことを反映。F4=2.5はローマ字列が短いバーストとして記録される特性に対応。F5=1.0は旧値4.0が寛容すぎた（4回のポーズまで摩擦に寄与しない）ため引き下げた。

**β_writing_latin の出所**は、136万打鍵の大規模タイピング調査[51]が報告した母集団中央値をもとにしている。**母集団中央値であって、その被験者の値ではない**——個人差の吸収は較正で行う（§1.2 天井③）。

**2026年度版から名称を変更した**: 旧「β_coding」は、**「日本語論述の中の英字引用・数式・URL」のベースライン**であって、コーディングのベースラインではない。この概念的分離を反映して `β_writing_latin` へ改名した（**数値変更は伴わない**）。コーディング用のベースラインは別途独立に所有している（§3.5）。

**【入力モード検出: 3層アーキテクチャ（Windows）】** 実機テストで発見した3つの障害モード（同一ミリ秒でのフラッピング、`ImmGetContext` のNULL返却、key-UP/DOWN の非対称性）への対処として、以下の3層検出を実装した。

- **Layer 1（プライマリ）**: IMEオープン状態のポーリング（自プロセスウィンドウのみ有効）
- **Layer 2（フォールバック）**: 低レベルキーボードフックでIME切替キーのkey-DOWN/UP両方を監視し、Atomicフラグを更新。一部キーボードでのkey-UP単独発火に対応
- **Layer 3（推論）**: WinEventからComposition開始を検出し、日本語モードを推論

モード切替のログ出力はポーリングスレッドに一元化し、フックコールバックからの直接出力を禁止することで同一ミリ秒フラッピングを防止した。

**【変換候補ウィンドウ表示中の特徴量抑制】** 候補リスト表示中は、矢印キー・Enterキーによる候補選択操作が特徴量を汚染するため、表示状態を検出して**推論を一時停止し、確率ベクトルとEWMAを凍結保持する**。候補ウィンドウ終了後は保持された状態から再開する。TSF言語バーの常駐インジケータのウィンドウクラスは明示的に除外する——日本語IMEロード中に常時表示されるため、含めると**永続的な偽陽性**になる。

**【macOS版】** JISキー（英数/かな）をイベントタップ内で検出してAtomicフラグを即時更新（遅延5ms未満）し、併せて入力ソースを100msごとにポーリングする。ANSIキーボード（JISキーなし）ではポーリングが唯一の検出パスとなる。

**候補ウィンドウ検出**: **macOS 26 では、Windows版で使った2つのAPIが共に動作しないことを実測した。** (a) ウィンドウリストAPIは、日本語IMEプロセスが候補ポップアップにウィンドウオブジェクトを生成せずプライベートな描画機構を使うため不可視。(b) Accessibility API はバックグラウンドスレッドからエラー −25204 を返す（プロセスが信頼済みでも発生する）。

**そこで第3のアプローチとして、キーストローク状態機械を設計した**:

```
IDLE →(文字キー)→ COMPOSING →(Space)→ CANDIDATING →(Enter/Esc)→ IDLE
```

CANDIDATING状態を検出した時点で推論を一時停止する。**ゼロ権限（Input Monitoring 以外不要）・ゼロ遅延・macOSバージョン非依存**であり、実セッションで候補ウィンドウ検出率5/5を確認済みである。

**【クロスプラットフォーム設計の含意】** Windows版とmacOS版で異なるのは**候補ウィンドウ検出のOS API依存部分のみ**であり、Dual Baseline・正規化・HMM推論以降のパイプラインは完全に共通である。**これは §2.1 のレイヤー分離が実際に機能していることの実証でもある。**

## **3.3 IME Composition Analysis と、2026年度版の技術的訂正**

**2026年度版に書いた技術的説明のうち1点を訂正する。**

**旧記述**: 「TSFのグローバルフック（`ITfThreadMgr`）がUIPI（User Interface Privilege Isolation）により異プロセス間でブロックされることを確認した」

**訂正**: **理由が誤っていた。** 一次資料（*Windows Integrity Mechanism Design*）に当たり直した結果、UIPIが禁止するのは以下の5項目である——window handle validation / `SendMessage`・`PostMessage` / thread hooks / journal hooks / **DLL injection**。**TSFもCOMもWinEventのout-of-contextも含まれていない。** かつUIPIは「**同一の権限（整合性）レベルでは一切干渉しない**」ため、通常環境では**発動すらしない**。

**真の障壁はアーキテクチャそのものである。** `ITfThreadMgr::Activate` は逐語で「**呼び出しスレッドに対してTSFを有効化する**」であり、シンク登録API（`ITfSource::AdviseSink`）に**リモート対象を指定する引数が構文上存在しない**。Microsoft自身が「**TSFが管理する変換文字列にアクセスするには、支援技術製品は対象のTSF対応アプリケーションのプロセス内で `ITfThreadMgr` を生成しなければならない**」と明記している[53]。**権限を上げても、UIAccessを付けても、管理者で実行しても取得できない**（そういうAPIが無い）。

**唯一の迂回は、自前のIME（in-proc COM DLL）を全プロセスに常駐させることである**が、仮名漢字変換エンジンの自作・32/64bit の二重配布（**片方欠けると無音で失敗する**）・コード署名・EDRの誤検知・被験者の入力方式の置換という代償があり、**採用しない**。

**DLL注入を伴うグローバルフックで `WM_IME_*` を拾うことも、別途禁止する** —— こちらは**UIPI第5項（DLL injection）に直撃する**（旧記述が部分的に指していたのはこれである）。

**採用する手段は WinEvent（`WINEVENT_OUTOFCONTEXT`）である。** DLL注入が不要で、プロセスを跨げて、**コールバック引数に文字列が1つも無いため content-free 制約が構造的に保証される。**

**結論（グローバルなTSFフックは行わない）は2026年度版から変わらない。理由を正しく置き直したことを記録する。**

**追加特徴量（Phase B以降で統合）**

| 追加特徴量 | 定義 | 取得手段 |
| :---- | :---- | :---- |
| Composition Dwell Time | 未確定文字列の滞留時間（変換の迷い） | Win: WinEvent＋UIA / mac: 状態機械のCOMPOSING滞留 |
| Candidate Retry Count | 変換候補の選び直し回数 | Win: 候補ウィンドウ表示中の操作 / mac: CANDIDATING→COMPOSING の再遷移数 |
| Abandon Rate | 未確定文字列の全削除率 | Win: Composition終了の監視 / mac: Esc/全削除によるIDLE復帰の検出 |

**フェイルセーフ**: IME解析は精度を向上させうる追加要素だが、**万一API統合が困難な環境に直面しても、5特徴量のみでコアの推定が成立する**設計とする。

## **3.4 content-free 制約 —— 何を記録し、何を記録しないか**

**これはプライバシーポリシーではなく、アーキテクチャ上の制約である。**

| ✅ 記録するもの | ❌ 記録しないもの |
| :---- | :---- |
| キーの**カテゴリ**（英数 / 記号 / 削除 / 空白 / 制御） | **キーの文字内容・仮想キーコードの生値** |
| 打鍵の**タイミング**（セッション相対時刻） | **絶対時刻**（匿名化で相対値に変換） |
| 貼り付けの**回数と文字数** | **クリップボードの本文** |
| IMEの**状態遷移**と滞留時間 | **未確定文字列そのもの** |
| フォーカスの**喪失・復帰** | **ウィンドウタイトル・プロセス名・アプリ識別子** |

**提出前にローカルで公開鍵暗号により匿名化する運用を実装済みである。** 氏名とログを同一の場所に置かず、参加者IDのみで結合する。**Phase1では、匿名化健全性を復号後に機械監査した**——生の仮想キーコード0件 / 禁止フィールド0件 / 絶対時刻0件（§10）。

**それでも残るサイドチャネルを、隠さずに書く**

本文を保存しなくても、**貼付の文字数・キーのカテゴリ列・打鍵の相対時刻・IMEの状態遷移**は、状況によっては作業内容を推測させうる。**特にパスワード欄・認証コード・個人情報フォームでは「長さ」だけでも情報になる。**

**現在ある緩和（実装済み）**:

1. **即時の一時停止** —— 稼働中インジケータから、いつでも記録を止められる。
2. **事後の区間指定削除** —— 「昨日の 14:00〜15:00 を消す」形で、提出前に本人が区間ごと削除できる。
3. **貼付は回数と文字数のみ**（本文もアプリ識別子も持たない）。
4. **キーは個別の値ではなくカテゴリ**（英数 / 記号 / 削除 / 空白 / 制御）に落としてから記録する。

**そして、閉じていない穴を明記する**: セキュア入力欄（パスワード入力中）を検出して記録を抑止する経路は、**スキーマ上の項目としては用意してあるが、送出元がまだ実装されていない**（実測: 当該イベントの emitter が Windows / macOS のどちらにも無い）。**すなわち現時点では「パスワード欄では打鍵の存在すら記録しない」という保証は無い。**

→ **本提案では、これを Gate S（センシング・§7.3）の判定項目に含める**（「内容漏洩ゼロ」を実測で確認する対象に、この経路を明示的に入れる）。**「本文を保存していないから安全」で止めない。**

## **3.5 ドメイン別ヘッド（Domain Inference Head）**

**2026年度版には無かった構造である。** 「論述」と「コーディング」では打鍵の統計的性質が違うため、**単一のベースラインで両方を採点すると系統的な誤分類が生じる**。そこで推論ヘッドを分離した。

| ヘッド | 対象タスク | ベースライン |
| :---- | :---- | :---- |
| **Writing** | 論述 / 文通 | β_writing（IME on）/ β_writing_latin（IME off）の切替 |
| **WritingFallback** | 創作 | **数値挙動は Writing と完全に同一。識別子だけが違う** |
| **CodingV0** | コーディング | β_coding（独立に所有） |

**`WritingFallback` を設けた理由を正直に書く。** 設計判断としては「創作には打鍵ベースラインを持たせない」と決めていたが、**代替ヘッドがまだ存在しないため Writing ヘッドへ流している。これは決定からの意図的な逸脱である。** この識別子をセッションメタデータに刻んでおくことで「**適合していないヘッドで採点されたセッション**」を事後に分離でき、後段で創作領域の実現可能性を評価するときの一次データになる。

# **4\. Inference Layer: MhD Core**

## **4.1 潜在二軸への射影**

| 【要約】 5つの数値をそのまま使うのではなく、「どれくらい摩擦を感じているか（X）」と「どれくらい前に進んでいるか（Y）」の2軸に要約してから推論します。 |
| :---- |

**正規化関数 φ**

```
φ(x, β) = clamp((x − β) / (k · β), 0.0, 1.0)     where k = 2.0
```

ベースライン β を基準とした片側正規化であり、β以下の値は φ=0.0、3β で φ=1.0 となる。βは入力モード別に切り替わる（§3.2）。例えば英字入力時（β_F1=150ms）に300msなら φ=0.50 だが、日本語入力時（β_F1=100ms）では同じ300msで φ=1.0 となる。

**軸1: Cognitive Friction（認知的摩擦）**

```
X = 0.30·φ(F3) + 0.25·φ(F6) + 0.25·φ(F1) + 0.20·φ(F5)     （重み合計 = 1.0）
```

**軸2: Productive Engagement（生産的な前進）**

```
Y = 0.40·φ(F4) + 0.35·(1 − φ(F1)) + 0.25·(1 − φ(F5))       （重み合計 = 1.0）
```

**なぜ2軸に圧縮するのか（4つの理由）**

**理由①: 次元の呪いによる放出確率の推定破綻。** 6次元の連続値を直接扱う場合、各状態につき共分散行列（21パラメータ）＋平均（6）＝27、3状態で計81パラメータの推定が必要になる。本プロジェクトの初期データは開発者自身のn=1であり、100ウィンドウを集めても81パラメータの安定推定は統計的に不可能である。2軸なら 5パラメータ × 3状態 = 15 に収まる。

**理由②: 離散化の組合せ爆発。** 6次元を各3ビンに離散化すると 3⁶ = 729 ビンとなり、ほとんどのビンにデータが存在しない疎な状態に陥る。2軸×5ビン = 25ビン（＋ペナルティビン1 = 26）であれば、各ビンに十分な観測頻度が期待できる。

**理由③: 解釈可能性とドメイン知識の注入。** 2軸には明確な意味がある——X は「どれだけ摩擦を感じているか」、Y は「どれだけ前に進んでいるか」。この座標系は、介入トリガーの設計・デバッグ・ユーザーへの説明において6次元空間では得られない透明性を提供する。

**理由④: 正則化効果。** 2軸への射影は複数特徴量の加重平均であるため、個別のノイズが相殺される自然な正則化として機能する（§3.1 の F2 除外と同じ設計思想）。

**ただし、2026年度版が書いていなかった限界を追記する。** **重み係数（0.30 / 0.25 / …）はドメイン知識に基づく初期値であって、データから推定したものではない。** 本提案では、統制タスク実験（§7.2）において**現行5特徴量セットと、観測空間を広げたセットを、事前固定した罰則つき回帰で比較する**——重みを事後に調整して有利な結果を作れないよう、**判定基準をデータを見る前に凍結してある。**

## **4.2 HMM と `p_stuck`**

**離散化**: (X, Y) ∈ [0,1]² を **5×5のグリッド（25ビン）**に離散化し、**ペナルティビン（obs=25）**を加えた **26観測**で扱う。ペナルティビンは **Backspace連続14回以上**で発火する。**14という閾値は、IMEの正常な変換修正操作（通常8〜12連打）を超える値として設定している。** かつ **IMEが開いている間はペナルティを無効化する**——変換修正の連打は認知的な詰まりではなく正常操作だからである。

**状態遷移確率行列**

| From \ To | Flow | Incubation | Stuck |
| :---- | :---- | :---- | :---- |
| **Flow** | 0.75 | 0.17 | 0.08 |
| **Incubation** | 0.12 | 0.80 | 0.08 |
| **Stuck** | 0.06 | 0.18 | 0.76 |

対角要素が高いのは「いまの状態が続きやすい」ことを表し、判定の振動を確率的に抑制する。Flow自己遷移0.75は平均滞留 ≈ 4秒（1/(1−0.75)）に対応する（**旧値0.80から下げた**——Flowへの過度な引力を緩和するため）。

**初期確率ベクトル**: π₀ = [0.80, 0.15, 0.05]（Flow偏重）。セッション開始時の典型的な分布に合わせ、開始直後の確率振動を防止する。軸EWMAの初期位置は (0.1, 0.8)（低Friction・高Engagement）。

**前向きアルゴリズム**（標準的な HMM の推論手続き[52]）:

```
π'_j = ( Σ_i π_i · A[i,j] ) · B[j, obs]
π'  ← π' / Σ_j π'_j
```

**放出確率テーブルには静的最小値 0.01 をベイクインしてある**（確率吸収の防止・§4.3③）。

**状態名（Flow / Incubation / Stuck）は行動パターンの説明語であって、脳内状態のラベルではない。** 実運用で消費するのは `p_stuck`（Stuck likelihood）という**1次元の連続信号**である。**3値の離散ラベルを出力として使わない。**

## **4.3 プロトタイプ実装で解決した課題**

**以下はすべて「セッションログの定量分析 → 問題発見 → 設計変更 → ログ再検証」というサイクルで発見・解決したものである。**

**① 滞留時間のモデリング: HSMM の回避と O(1) の解決**

**課題**: 標準的なHMMはマルコフ性の制約上、各状態の滞留時間が幾何分布に従うと仮定してしまう。しかし実際の熟考（短い）と停滞（長い）は明確な持続時間依存性を持ち、理論上の最適解は滞留時間を明示的にモデル化する Hidden Semi-Markov Model (HSMM) である。

**トレードオフと解決策**: HSMMは計算量の増大を招き、一般的なノートPC上でのリアルタイム推論を困難にする。さらに滞留時間分布のパラメータ推定には大量のデータが必要で、n=1環境では過学習が不可避である。**そこで標準HMMの出力の背後に、計算量 O(1) の遅いEMAによるヒステリシス層を直列配置した。** これによりHSMMの計算コストを払わずに、疑似的に「状態遷移に必要な最低滞留時間（約4秒の慣性）」を強制できる。

**② 確率スパイクの抑制**

**課題**: スライディングウィンドウの更新時（大量のBackspace履歴が窓から外れた瞬間など）に、生のHMM出力が1ms未満で急激に変動するスパイクが発生した。実測で `p_stuck=0.994 → p_flow=0.48` という急変が記録された。根本原因は、表示・判断に使う値が時間的慣性を持たない生の信念を返していたことだった。

**解決策**: 遅いEMAによるヒステリシス層を導入し、α を状況別に使い分ける（通常更新 α=0.40、アクティブタイピング中のペナルティ発火 α=0.60、沈黙中のペナルティ発火 α=0.50）。状態遷移が約2.5秒かけて緩やかに反映されるようになった。

**③ 放出確率の方式変更**

**課題**: 実行時に全ビンへ加算的に ε=0.05 を付与していたところ、`p_flow` が 0.9734 に39.1%のフレームでクラスタリングする等、極端な確率偏りが発生した。かつ ε=0.05 では**ペナルティビンの Stuck:Flow 放出確率比が約20倍に留まり**、Backspaceストリークという強い信号が大幅に鈍化していた。

**解決策**: 実行時の加算的な下限を廃止し、**放出テーブル自体に静的最小値 0.01 をベイクインする**方式に変更した。ペナルティビンの比が **約20倍 → 約99倍** に改善され、同時に全状態-観測ペアで非ゼロ確率が保証されるため確率吸収も防止される。

**④ 長期沈黙の論理的補正（合成摩擦）**

**課題**: 50秒以上キーボードに触れない長期の沈黙が、単なる熟考として判定され続けた。ポーズ回数（F5）だけでは Friction が Stuck領域に到達できなかった。

**解決策**: 沈黙区間に**合成摩擦**を注入する。注入の仕方は **2 系統**あり、**直前の打鍵の文脈が取れるかどうかで分岐する**。

| 経路 | 条件 | 何を注入するか |
| :---- | :---- | :---- |
| **① 文脈ベース（既定）** | 沈黙の直前に打鍵があり、その F3 / F6 が取れる | **直前の F3 / F6 を起点に、沈黙 2〜32 秒で時間スケールを掛けて緩やかに増幅する**（**文脈が低ければ低いまま**——きれいに書けていた後の沈黙を「詰まり」に押し上げない） |
| **② 時間ランプ（フォールバック）** | **直前の文脈が無い**（セッション冒頭など） | F6相当は10秒で開始し40秒かけて上限へ、F3相当は15秒で開始し50秒かけて上限へ。**沈黙が10秒を超えている間は、それぞれ下限 0.15 / 0.20 を割らない** |

**2026年度版はこのうち②だけを書いていた。** ①が既定であり、②は文脈が取れないときの退避路である。

**初期実装では上限を0.45/0.35に制限していたため Stuck領域に到達不可能であり、`p_stuck` が構造的に約5%で天井に達して介入が発火しない問題が判明した。** 上限を1.0に解放し勾配を急峻化することで解決した。

**設計上のトレードオフを明記する**: 合成摩擦は、30秒を超える深い熟考を一時的に「詰まり」方向へ押す可能性がある。現設計では離席の誤検知防止を優先してこれを許容しているが、**入力再開時にバーストが観測されればヒステリシス層により約8秒で戻る**。かつ合成摩擦が作用する時間帯での介入は **Nudge（自動消失）に留まる**ため、深い熟考が不適切に中断されるリスクは限定的である。

**⑤ Backspaceペナルティのレースコンディション**

**課題**: 高速タイピスト（10打鍵/秒以上）が「BS×14 → Enter」と入力した場合、非BSキーが連続カウントを即座に0にリセットするため、**1Hzの分析スレッドが閾値を読み取る前にカウントが消失し、ペナルティが発火しない**競合が発生した。またカウンタをMutexで管理していたため、毎打鍵でのロック取得がホットパスのオーバーヘッドになっていた。

**解決策**: カウンタをアトミック変数に変更してMutexを排除し、さらに**「閾値に達した瞬間にフラグを立て、分析スレッドがアトミックなswapでフラグを消費する」**方式に変更した。リセットとの競合を完全に回避している。**フックコールバック上のMutexを全廃した**——コールバック内でブロッキングしてはならないという制約（§9）を守るためである。

## **4.4 Stage 2 昇格判定 —— なぜ未達か**

**Go/No-Go 基準（事前宣言）**: 約50セッション ＋ Stage 1 比 **+3%** の改善。未達なら Stage 1 を正とする。

**現状は未達である。** 較正（Phase1）が `DataInsufficient` で打ち切られたため（§10）、昇格判定に必要なデータが存在しない。**本提案では、Stage 2 の昇格判断を Phase C 以降に置く。** **データが揃わなければ、9ヶ月の終わりでも Stage 1 のままで報告する。それが正しい結論だからである。**

# **5\. Decision Layer: Need / Opportunity 分離と介入**

## **5.1 Need と Opportunity を分ける**

**これが2026年度版から最も大きく変わった部分である。** 旧版は「STUCK判定 → 介入開始」という単線だったが、**推定が当たっていても、いま割り込んでよいとは限らない。**

| 層 | 問い | 使う信号 | 実装上の閾値 |
| :---- | :---- | :---- | :---- |
| **Need** | いま介入が要りそうか | `p_stuck` | **≥ 0.60** |
| **Opportunity** | いま割り込んでよい瞬間か | 小休止（2〜8秒）/ 中休止（〜30秒）/ cooldown / daily cap / 直近dismiss | **≥ 0.35** |

**両方が揃ったときだけ介入する。**

**抑制条件（実装済み）**

| 条件 | 値 | 理由 |
| :---- | :---- | :---- |
| Nudge cooldown | 10分 | 連続的な介入を防ぐ |
| Nudge daily cap | 6回/日 | 累積的な負担の上限 |
| 直近dismissの抑制 | 20分 | 拒否された直後に再提示しない |
| 離席判定 | 無入力180秒以上 | **介入を全停止する**（居ない人に出さない） |
| 能動タイプ中 | 打鍵間隔 < 2秒 | **`defer`（見送り）—— 進行中の苦闘に割り込まない** |

**`defer` は「何もしなかった」ではなく「意図的に見送った」という第一級の判断としてログに記録される。** これにより、後から「介入しなかったこと」の妥当性も評価できる。**これは2026年度版に無かった設計であり、介入の評価において決定的に重要である**——介入した回だけを見ると、見送りの誤りが評価から消えるからである。

## **5.2 現行の介入レパートリー**

| Lv | 名称 | 状態 | 内容 |
| :---- | :---- | :---- | :---- |
| **1** | **Nudge** | **稼働中** | 画面右端から小さく現れるサイドカード。**クリックを遮らず**、一定時間で自動的に消える。答えを与えず、メタ認知的な問いかけの形をとる |
| 3 | **Physical Anchor（屋内）** | **未実装** | 一定時間の離席と、作業への復帰 |
| 4 | **Physical Anchor（屋外）** | **未実装** | 同上（夜間 22:00–6:00 は無効化し屋内へ縮退） |

**現時点で稼働している介入は Nudge のみである。** そして **Nudge は非ブロックで自動消失するため、労力を課さない**——すなわち**不便益の認定条件①（益は不便だからこそ得られる）を満たさない**[3]。**実際に不便を担うのは Physical Anchor であり、それは未実装である。** 本提案が「不便益を設計思想として引く」までしか書かない理由がこれである。

## **5.3 削除した介入とその理由**

**2026年度提案で技術的な売りの一つだった Ambient Fade / Wall / Monk Mode / Zen Timer / Early Unlock を、2026年8月に全て削除した。**

**削除したもの**: 全画面ブロックUI / QRコード表示とスマートフォンからの解除サーバ / 判定・ログ・スキーマ上の該当バリアント / フロントエンドの該当UI / 依存ライブラリ2つ。

**理由①（履行されていなかった決定）**: 2026年6月に「ハードな全画面ブロックは残さない。強制力はコミットと画面端の視覚的変化に限定し、**クリック遮断なし**」と決定していたが、**実装は逆になっていた**（全画面＋クリックブロック）。**決定と実装の乖離を、実装側ではなく決定側に合わせて解消した。**

**理由②（設計上の粒度）**: **画面全体を塞ぐ介入は、AI依存も、助けを求める行為も、作業そのものも、一律に止める。** しかし本提案が抑えたい対象は「**答えをそのまま受け取ること**」に絞られている——事前登録つき現場RCTで **答えを出すAIは学習成果を下げた（−0.054\*）がヒントに変えたAIは害ゼロ（−0.004）**[8]、独立研究でも**害は「直接的な解の提示」の層に集中する**[9]。**全画面ブロックはこの区別を構造的に持てない。**

**理由③（Monk Mode は定義上デッドになる）**: Monk Mode の作用は「Wallを無効化する」ことだけだった。**Wallを消すと、何もしないトグルになる。** UIに何もしないトグルを残さないために一緒に削除した。

**削除に伴う損失（隠さずに書く）**: **Physical Anchor が運搬路を失った。** Wall解除に使っていたQR＋1ビットのPC↔スマホ経路を、Physical Anchor が再利用する前提だった。→ この穴は §6 の表現チャネルの設計で塞いだ。

**保持したもの**: **HIR（有害介入率）** は残した——指標そのものは最重要の安全指標であり、変わったのは対象から Wall が消えたことだけである。

**凍結文書は書き換えない**: 統制タスク実験の事前登録は凍結中であり、記述が実装とずれるが、**ずれを記録として残す**（凍結の意味を守るため）。

## **5.4 Physical Anchor —— 計測なき身体回帰（未実装・第2の柱）**

**Physical Anchor が提示するのは「いま画面から離れる」という方向づけであり、系は離席の開始も完了も判定しない。** 時間の長さも往復の回数も、系の側の閾値を置かない。どれだけ離れるか、いつ戻るかは本人が決める。

**2026年8月30日に、完了条件そのものを取り下げた。** 旧版は完了条件を「歩数・距離」ではなく「時間＋往復」と定めることで、量で解放を決める設計を避けたつもりだった。**しかしこれは避けきれていない。**「1万歩で解除」と「10分離れたら完了」は、閾値の単位が違うだけで、**届かなかった状態を作る点では同型である。** 取り下げの理由は3つある。

1. **単位を量から時間へ替えても、届かなかった側のセルは残る。** Deciら（1999）の128研究のメタ分析[32]が報告する最大の毀損は、performance-contingent 条件で**最大報酬に届かなかった群の d = −0.88** であり、これは**達成判定が存在すること自体**が作るセルである。同メタ分析はさらに、逐語で「**肯定的なフィードバックが後続する場合であっても、予期される評価は自由選択行動を有意に損なう（d = −0.40, CI = −0.71, −0.09）**」と述べている。すなわち「完了しました」という肯定的な表示も、この記述の射程に入る。
2. **完了を宣告することは、技術をユーザーの行為についての最終権威に置く行為である。** Sengersら（2005）のReflective Design 原則4は逐語で「**技術が、ユーザーではなく技術の側を、ユーザーが何をしているかについての最終的な権威にしてしまわないよう設計せよ**」と述べる[23]。GSEは表現層で既にこの原則を採用し、「あなたは歩いた」と断定しないことにしていた。**表現層で禁じた断定を、介入層の完了判定が裏口から行っていた。**
3. **完了条件は、計測反応性の機序を系の側から作り出す。** Königら（2022）の系統的レビュー（11,723件スクリーニング → 30論文 / 31研究）は反応性を増幅する機序として逐語で「**(3) 実際の行動と望ましい行動との乖離を自己調整によって解消すること**」を挙げている。**完了条件とは、その「望ましい行動」を系の側が定義する行為そのものである。**

**観測は続ける。**「一定時間の打鍵の不在があり、その後に打鍵が再開した」という**時計の事実**は、本文を保存しないまま記録してよい。**ただしこれを「完了した」と解釈しない。**記録に残るのは観測であって判定ではなく、`completed` / `達成` に相当する語をUI・表現層・ログのいずれにも置かない。

**評価は達成率で行わない。** Physical Anchor を評価する量は「離席したか」ではなく、**招待の受容と、その後の機会保存の行動指標**（`paste_after_stuck_rate` / `self_recovery_without_paste` / `manual_contribution_ratio`）である。これは主張範囲（機会保存）と評価量を一致させる変更でもある。

**2026年度版から全面的に変更した点: 身体活動のセンシングを本体から恒久的に外した**

旧版の Outdoor 条件は「**GPS変位 ≥ 100m AND 加速度FFT歩行周波数(1.5–2.0Hz)が5分継続**」だった。**これを恒久的に取り下げる。** 理由は4つある。

1. **センサが寄与しうる判定が、そもそも存在しない。** 上記のとおり完了判定を置かないため、センサの量が入り込む先が構造的に無い。かつ観測として必要なビットは「一定時間の離席があり、作業へ戻った」だけであり、**PCが既にそれを content-free に観測している**（打鍵の不在と再開という構造的事実）。旧版の理由は「完了条件が時間＋復帰だから量が要らない」だったが、これは**完了条件が変われば再燃する形**であった。現在の理由は構造的であり、再燃しない。
2. **計測それ自体が持つ害を、経路ごと消せる。** Etkin（2016）[31]は逐語で「**明示的な外的インセンティブが無くても、計測それ自体が同様の効果を持ちうる**」と述べている。**「報酬ではないから安全」は防御にならない。測らなければ、このリスクは減るのではなく無くなる。**
3. **プライバシー境界が閉じたままになる。** 位置情報が境界を渡らないため、位置情報の取り扱い規定を実装前に整える必要が無くなる。
4. **「計測なき身体回帰」という概念と実装が一致する。**

**これは証拠に基づく判断ではなく、設計判断である。正直に書く。** Consolvoら（2008）のUbiFit[27]は「**測って・抽象的に見せて・量は見せず・達成しなくても罰しない**」設計で成功した、**この分野で唯一の統制つき成功例**である。**証拠の上では「測る側」の方が強い。** 私は**害とプライバシー境界と概念整合を優先して、証拠で劣る側を選んだ。**

**量で解放を決めない理由（一次証拠）**

Deciら（1999）の128研究のメタ分析[32]は、**最大報酬に届かなかった群の内発的動機の毀損が全群中最大（d = −0.88）**であり、さらに「**肯定的フィードバックが後続する場合の予期される評価**」でも **d = −0.40 [−0.71, −0.09]** であることを報告している。**「1万歩でロック解除」型の設計は、この危険側に入る。**

**「散歩が認知作業を回復させる」を主張しない理由（一次証拠）**

micro-breakのメタ分析（**22標本 / 19論文 / N = 2,335**）[30]:

| アウトカム | 効果量 | 判定 |
| :---- | :---- | :---- |
| 活力（vigor） | **d = .36 [.16, .55]**, k=9, p<.001 | 支持 |
| 疲労（fatigue） | **d = .35 [.19, .50]**, k=9, p<.001 | 支持 |
| **成績（performance）** | **d = .16 [−.04, .37]**, k=15, **p = .116** | **null** |
| └ 認知的に負荷の高い課題 | **d = −.09**（非有意） | **符号が逆** |
| └ 創造的課題 | d = .38, p = .006 | 執筆はこちら側の可能性 |

**さらに決定的な点: 著者は「休憩の活動種別（歩くか座るか）は異質性のため moderator にできなかった」と明記している。すなわち「歩行」に特化した推定値は存在しない。**

**GSEが「機会の保存」に主張を限定している設計は、この反証を最初から避けている。** **逆に「歩けば作業が良くなる」を表現で暗示すると、文献に反する暗示を与えることになる。**

**代償を隠さない**: 身体活動を測らないため、「**実際に歩いたか**」の客観的確認手段が本体から消える。**Physical Anchor の実行率と受容の検証は自己申告に依存する。** これは「**害は自己申告に現れない**」[8]「**本人の希望は根拠にならない**」[31]型の批判に弱い。→ **その一点にだけ、本体とは別プロセスの計測器を使う形成的調査で一度だけ答える**（**利得は主張しない**）。

## **5.5 介入判断の評価設計**

**介入は「出したかどうか」ではなく「判断が正しかったか」で評価する。**

| 指標 | 定義 | 位置づけ |
| :---- | :---- | :---- |
| **HIR（有害介入率）** | 守るべき状態（Flow / 熟考）に介入してしまった割合 | **最重要の安全指標** |
| Precision | 介入した回のうち、実際に停滞していた割合 | |
| STALL-recall | 停滞していた回のうち、介入できた割合 | |
| dismiss理由の層別 | 「詰まってない」＝ Need の過検出 / 「いまはもがきたい」＝ Opportunity の誤り | **2種類の誤りを分離する** |

**判断性能は閾値のsweepで動作点を点検する**——単一の閾値での成績ではなく、閾値を動かしたときの挙動を報告する。

**そして安全性の判定を自己申告だけで行わない。** Netflixのautoplayを無効化したRCT（N=76・10–17日・6か月の履歴をベースライン）[49]は、**1日の視聴が −21.0分（p=0.003）／セッション長が −17.6分（p=0.013）動いたにもかかわらず、事前に95%が「自分は視聴時間を制御できている」と回答していた**ことを示している。→ **HIRを dismiss率と自己申告だけで測る設計は、自動的に発動する介入に合格判定を出してしまう。行動側の客観指標（作業ログ・完了率・放棄率・時間超過）を必ず併報する。**

# **6\. Expression Channel: 表現チャネル（第2の柱）**

**2026年度版に存在しなかった構成要素である。そして、この章全体が「効果を主張しない」温度で書かれている。**

## **6.1 なぜ表現チャネルが要るのか**

GSEの介入レパートリーは現在、**Nudge（柔らかい・容易に無視できる）に張り付いている。** 削除した Wall（硬い・自律性を脅かす）との間の帯域を持っていない。

Lyngsら（2019）が367アプリを二重過程モデルで整理したレビュー[18]は、ユーザーが評価するのは「**強制的（coercive）ではないが、簡単に無視・上書きできない**」支援であると結論している。**この中間帯域を占める手段を、GSEは1つも持っていない。**

**ただし[18]は効果検証を伴わないレビューであり、「帯域が空白だから埋めれば効く」は導けない。**

## **6.2 チャネル（抽象）と媒体（実装）を分離する**

```
Expression Channel  ← 抽象。状態 → 表現の対応と、境界の契約を持つ
  ├─ PC画面内の表現              （既存）
  ├─ スマートフォンの常在面      （第1版で追加する媒体）
  └─ 専用オブジェクト            （将来候補・未着手）
```

**「スマホを媒体にすること」は新規性ではない。** Consolvoら（2008）のUbiFit[27]の glanceable display は、一次資料の逐語で「**個人の携帯電話の背景画面、すなわち『壁紙』に置かれる**」ものであった。**すなわちGSEのアンビエント表現の接地は、当初からスマホ表示面の上にあった。**

**かつ「常在面に置くこと自体」に効能は無い。** 事前登録・被験者内クロスオーバー・順序カウンターバランス・ベイズ併用（**N=60・3種の壁紙 × 各1週**）で、**確証アウトカム6つすべてが null**（全 p ≥ 0.098、**BF₁₀ = 0.066–0.433 ＝ 帰無仮説が 2.3〜15.2倍尤もらしい**）[28]。**著者の処方は「受動的表示に能動的プロンプトを混ぜよ」であり、表現層で介入を減らすという向きとは正反対である。**

→ **したがって媒体は交換可能な実装詳細として扱い、主張の所在に置かない。差分は「推定された内的状態を、常在面に非断定的に写すこと」という結合の一点に絞る。**（**これは新規性の縮小ではなく焦点化である**——媒体側は先行だらけ、結合側は該当研究ゼロ。**ただし「空白は有望を意味しない」。**）

## **6.3 境界クラスの契約**

**契約（これ以外を載せない）**:

| フィールド | 値域 | 備考 |
| :---- | :---- | :---- |
| `level` | `stable` / `friction_rising` / `stuck` / `intervention_active` | **4値のみ。`p_stuck` 等の連続値を載せない** |
| `seq` | 単調増加整数 | 欠落検出用 |
| `emitted_at` | 秒粒度 | ミリ秒粒度にしない |
| `epoch` | 不透明な識別子 | チャネルの世代。**本人の識別子・端末名・セッションIDを流用しない** |

**発火条件: `level` が変わったときだけ。** **1Hzのストリームを流さない。**

**常時ストリームにしない理由（3本）**

1. **状態を常時流し続けることは、1ビットのイベントを1発送ることとは別種の設計判断である**（境界の粒度が一段大きい）。
2. **消費者側に予算が無い。** ロック画面の準備時間は**中央値 3.4秒・大半は4秒未満**（N=134・1か月の実端末ログ）[29]。**常時流しても受け手がいない。**
3. 表現の更新回数を制限しないと、**表現の変化そのものが新しい注意散漫になる。**

**再接続の意味論（契約に含める）**: ① `epoch` が変わったら `seq` の比較を打ち切り初期同期からやり直す ② 同一 `epoch` 内で `seq` が戻ったらそのイベントを捨てる（リプレイ扱い）③ 再接続直後は「現在の `level`」を1発だけ送る——**履歴を再送しない**（本人が居ない時間の表現を捏造しないため）④ 一定時間 `epoch` が更新されなければチャネルを失効させ、状態に応答しない基層へ縮退する。

**方向は PC → スマホの一方向とし、「歩いた」という逆方向の経路を作らない。**

1. **完了判定を置かないため、センサの量が入り込む判定が存在しない**（§5.4）。
2. **PCが既に同じものを content-free に観測している**（離席候補区間と復帰）。
3. **逆方向を作ると、位置情報の取り扱い規定の不在が即座にブロッカーになる。**

**帰結として、この設計が持てるビットは「歩いた」ではなく「離席候補区間があり、復帰した」である。** → **表現層は「あなたは歩いた」と断定してはならない。** 根拠はReflective Design 原則4の逐語[23]——「**技術が、ユーザーではなく技術の側を、ユーザーが何をしているかについての最終的な権威にしてしまわないよう設計せよ**」。

## **6.4 曝露予算 —— 表現を2層に割る**

実端末ログ（N=134・1か月）[29]によれば、ロック画面には **1日あたり約40回の 2〜4秒の強制的な曝露** と **約30回の数十秒の任意閲覧** がある。

→ **層A（強制曝露・4秒以内で読み取れる）と 層B（任意閲覧・数十秒）を別に設計する。** **同じ表現を両方に流用しない。**

**「30秒ローリングウィンドウの状態を地形として味わう」型の表現は、層Aの窓に入らない。**

## **6.5 復帰後の差分をどう扱うか**

打鍵動態だけから「机を離れていた間の身体状態」を事後推定することは、**既に可能である**（AUC 0.93 / 0.91、逐語「**タイプされたテキストの内容や言語によらず**」）[13]。**しかしその推定をアンビエントな表現へ結合し常在させた系は、7つの探索角度で依然ゼロである。**

**ただし、そのまま結合すると自己言及が戻る。** 「歩いたか否か」を復帰後の打鍵から推定すると、`p_stuck` と同じソースを共有し、「**回復したのか、歩いたから推定が下がったのか**」が区別できなくなる。

→ **入力の割り方を固定する**:

| 入力 | 何か | なぜ独立か |
| :---- | :---- | :---- |
| **入力1** | **離席候補区間があり、復帰した**（時計の事実。長さと復帰の有無だけ） | **推論ではない。** 打鍵の*不在*と再開という構造的事実であり、`p_stuck` の特徴量ではない |
| **入力2** | `p_stuck`（推論層の出力） | 既存 |

**「個人ベースラインからの逸脱」は第3の独立入力ではなく、入力1の精緻化である。第3の入力として数えてはならない。**

**表現の向き**: 摩擦の信号が下がったら表現は静かに基層寄りへ戻る。**下がらなければ表現は変わらない**（**罰しない・催促しない**）。

**「回復した」と断定しない。** (a) 側の一次証拠は例外なく**臨床スクリーニング＝悪化の検出**であり、「回復の検出」を目的にした系は存在しない。**表現が言えるのは「摩擦の信号が下がった」までである。**

**表現層は介入判断を行わない。** 状態を写すだけであり、推論層にも推論バージョンにも触らない。

## **6.6 セキュリティ最小要件**

**具体的な通信プロトコル（トランスポート・暗号方式・ペアリング手順・鍵の保管）は実装着手時に別途決定する。**本書がここで決めないのは、**決めるべき論点を実装前に固定すると、実装時に分かることを捨てることになる**からである。**ただし「後で決める」に逃がすと将来忘れられる**ので、**どの実装も満たさなければならない最小要件**をここで列挙して先に凍結する。

| # | 要件 |
| :---- | :---- |
| S1 | **明示的なペアリング**（本人の操作で開始する）。自動発見・自動接続を作らない |
| S2 | **イベント送信元の認証** —— 最低限、**ペアリング時に確立した秘密を使って各イベントにメッセージ認証を付ける**こと。**「同一 LAN にいること」を認証の代わりにしない**（削除した解除サーバもランダムトークンを持っていた——先例を落とさない） |
| S3 | **偽造・リプレイ対策** —— `epoch` ＋ 単調 `seq` ＋ 受信側の巻き戻り破棄（§6.3）。**これは順序の健全性であって、偽造対策ではない。** 偽造を防ぐのは S2 のメッセージ認証であり、**S3 単独で十分と決めつけない** |
| S4 | **端末紐付けと失効**（本人がいつでもチャネルを失効できる。失効後は基層へ縮退） |
| S5 | **LAN露出の明示**（露出があるなら「いつ・どのポートが・どれだけの間」開くかを文書化する） |
| S6 | **ペイロードに本人性を載せない**（契約は §6.3 の4フィールドのみ） |

**加えて、PC側に常設のLANリスナを置かない。** オンデマンドで起動し、停止時にファイアウォールルールを撤去する形とする。**常設化は、削除した解除サーバより大きな設計変更である。**

**本節は「実装済み」ではなく「実装前に凍結した制約」である。** 表現チャネルは Phase C の実装対象であり、**S1–S6 を満たすことが着手の前提条件になる。**

## **6.7 第1版の範囲外にしたもの —— 音声の自動開始**

**表現層の範囲は「常在する基層」と「介入候補の視覚的な優先化」の2段までとする。音声の自動開始は実装も評価も行わない。**

**「有害だから」ではない。準備条件を閉じる手段も、害を測る手段も無いからである。**

1. **「装着している」を安全条件として閉じる手段が存在しない。** イヤホンの接続と装着を区別した研究は該当ゼロ。近傍のアナロジー（加速度計の非装着自動判定・N=606・2コホート）では**60分アルゴリズムの特異度が 0.00 / 0.08 まで落ちる**。製品側も**有線接続では装着検出が動作せず、無線対応機種のみの任意機能**と明記している。
2. **決定時点最適化の天井が低い。** マイクロランダム化試験（N=1,255・534決定点）で通知の近接効果は **RR 1.039 [1.01, 1.08]**[47]。既存の帯域（ナッジ補正後 d≈0.01[19] / 実配備 precision 0.57[15]）と**同じ桁**である。
3. **参加者の選好が視覚に有利。** 逐語で「**言語的な合図が最も気が散ると評され、次いで音声。視覚的な合図が最も気が散らないと評された**」。GSEは既に視覚チャネルを持つため、**音声段との差分は「音を鳴らすこと」だけである。**

**将来の再開に必要な条件（4つとも要る）**: ① 事前オプトイン ② **内容ごとの**選択的無効化 ③ 開始前の合図 ④ 行動側の対照を持つ評価設計（ON/OFFの無作為化＋作業ログの客観指標）。

**「駄目」ではないので恒久否決にはしない。**

# **7\. 検証設計**

## **7.1 事前登録された合否契約（凍結済み）**

**本プロジェクトは、判定基準をデータを見る前に凍結する運用を既に実装・実施している。** これは提案上の宣言ではなく、**既に一度回した契約**である（§10）。

| ゲート | 問い | 通過基準（事前凍結） | 不合格時 |
| :---- | :---- | :---- | :---- |
| **GATE1 尺度理解** | 主観申告の尺度を正しく取れるか | 例題8問中6問以上 かつ被験者の8割以上 | 教示を作り直して再施行（本番データを取らない） |
| **GATE2 測定法** | 回答が集まるか | 回答率 ≥80% / 回答時間中央値 ≤10秒 / 有効プローブ ≥20件/人 | ラベル方式を再設計 |
| **GATE3 モデル** | 推定が申告の順序に沿うか | **方向付き順序C-index 中央値 ≥0.65 かつ全員 >0.55** | 特徴・モデルを差し戻し |

**併走する報告要件（PreReg-5〜8）**

- **前向き固定 holdout**: 各人の**最初の2セッションでベースラインを較正し凍結**、残りで前向きに評価する。**評価期間中の閾値・パラメータ調整は禁止。**
- **Recall の抑制**: 独立した陽性エピソードが30件未満なら**点推定を出さない**（定性所見のみ）。
- **欠測（MNAR）**: 未回答を「全て高摩擦」「全て低摩擦」と置いた**上下限を併報**する。**高欠測者を除外しない**——落とすと「難しい状態の人」だけ消えて欠測の偏りを強化するため。
- **二軸性**: 非対角象限の出現が <10% なら「**二軸性は検証不能**」と報告する。**単軸とも二軸とも結論しない。**

**「情報を持つ Kill」と「情報を持たない不足」を区別する規約**

「推論妥当性がKillでも、測定法の破綻検出という貢献が残る」が成り立つのは、**GATE2 を満たす十分なデータの下でC-indexが偶然以下だった真のKillに限る。** **主指標被験者ゼロ・提示プローブゼロ・最低要件未達は Kill ではなく `DataInsufficient`（データ拡充）であり、課題放棄や計測外への移行による空振りは反証ではなく「測定の失敗」として切り分ける。**

**この規約は既に一度、自分に対して適用した**（§10）。

## **7.2 Phase A: 統制タスク実験（G1）**

**2026年度版に無かった段である。そして本提案の入口である。**

**何を問うのか**: **打鍵由来の content-free な特徴量だけで、実験的に操作した高摩擦条件と低摩擦条件を、個人内で分離できるか。**

**これは較正（X1）とは違う。** criterion を主観プローブではなく**実験者が課題設計で与えた条件ラベル**にする。**較正が死んだラベル供給の問題を、統制実験では設計で回避できる。**

**かつ、この問いは軸の定義を書き換えても免除されない。** 分離できないなら、どの軸に書き換えても観測空間が足りていないことになる。

**判定（データを見る前に凍結済み）**

| 項目 | 内容 |
| :---- | :---- |
| 単位 | ブロック（＝無作為化の単位） |
| モデル | **L2罰則つきロジスティック回帰。λ = 1.0（z標準化後）を事前固定しチューニングしない** |
| 標準化 | **学習fold のみ**を使って z 標準化 |
| 交差検証 | **被験者内 leave-one-block-pair-out。被験者を跨いで学習しない**（universal marker 不在[41]） |
| 指標 | 個人内の out-of-fold AUC |

**なぜ罰則を事前宣言するか**: 1人8ブロック（各foldの学習は約6ブロック）に対して特徴量は最大14個。無正則化では**完全分離**が起き、係数が発散してAUCが人工的に1.0近くまで上がる。**λ=1.0 は最適値ではなく慣例値である。結果に有利な値を後から選べないように凍結することに意味がある。**

**特徴量セットは2本だけ（3本目を作らない）**

| セット | 内容 | 何を答えるか |
| :---- | :---- | :---- |
| **FS-A** | 現行5特徴量（F1 / F3 / F4 / F5 / F6） | **現行の観測空間**で分離できるか |
| **FS-B** | FS-A ＋ 打鍵近傍のイベント（打鍵数 / BS率 / 外部貼付文字数 / IME滞留中央値 / 沈黙長のp50・p90・max / バースト長のp50・p90）= 14特徴量 | **観測空間を広げれば**分離できるか |

**勝ち幅は2つの基線に対して報告する**: **(a) 多数派分類器** と **(b) FS-A ベースライン**。**多数派基線に対する勝ち幅を併記しないと、「偶然 +0.07」を「有望」と読む誤り[46][15]が再発する。**

**実施上の制約**: FS-A は**実行時にGSEが出力している5特徴量そのもの**から取り、打鍵ログからオフラインで再計算しない。理由は「現行の観測空間」とは実行時に実際に計算されている値だからである（特徴量計算にはオートリピート除外などログに現れない処理がある）。→ **この制約により、G1 は GSE 本体が動いている環境でしか実施できない。**

**現況**: 事前登録は凍結済み、課題文（8題材×2版）・割付スクリプト・解析スクリプト・検証スクリプトはすべて完成し、検証コマンドが緑である。確証標本のn（3名）も**データを見る前に凍結してある。**

## **7.3 Phase B〜D: 新規ゲートと実験**

**事前登録された合否基準（PreReg-1〜8 / GATE1–3）そのものは変更しない。** 追加するのは **Phase B 以降にのみ発効する新規ゲート**であり、Phase A / 較正には遡及しない。

| ゲート | 何を見るか | 閾値の置き方 |
| :---- | :---- | :---- |
| **Gate D（需要・新規）** | 自発的な初回利用 / 7日以内の再利用 / 研究参加外での利用意向 | **実配備ベンチ（30日継続率の中央値 3.3%）を桁のpriorとして置く。** 試験由来のコンプライアンスを前提に高く置かない |
| **Gate S（センシング・新規）** | イベント取得成功率 / 欠損率 / OS・アプリ差 / 遅延 / CPU・メモリ / **内容漏洩ゼロ** / 再実行可否 | 実測値で判定 |
| **Gate H（有害性・新規・拒否権付き）** | annoyance / tension / **自律性の毀損** / 偽陽性のコスト / 中断 / 早期離脱 / 監視されている感覚 | **悪化した場合、GATE3 が Go でも介入機能は Go としない** |

**Gate H の測定について、2点を明記する**

1. **自律性の測定尺度を「選択肢の多さ」で代用しない。** 自己決定理論の原典[20]は autonomy を「**自己による調整**」と定義し、逐語で「**多くの選択肢を持つことは基本的欲求ではない**」「**選択肢が1つしか無くても、本人が真にそれを是認しているなら十分に自律的だと感じうる**」と述べている。→ **正しい根拠は「選べるから」ではなく「本人が事前に是認しているから」である。**
2. **計器は METUX[21] の autonomy 下位尺度を第一候補とする。** **著者自身が「初期版であり、より徹底した検証と洗練を要する」と留保している**ため、**確証には使わずゲートの運用指標として使う。** 併せて反証[22]（k=99研究のメタ分析レビューが「基本的心理欲求が説明する分散は統計的には有意だが実務的には無視できる」と報告）も併記する。一方、同レビューの方法論的警告「**横断的な自己申告研究は推奨しない**」は、**GSEの個人内・縦断・日次デザインに有利である。**

**Phase C（較正 X1 と介入価値 Y）**: 個人適応した較正プローブでC-indexを算出し GATE2 → GATE3 を判定する。not-kill なら AB/BA クロスオーバーで介入の受容と効果を測定する。

**「AI依存が下がった」を「自力解決」と取り違えないための追加アウトカム**: 完了率 / 放棄率 / 時間超過 / 外部支援の自己申告（計測外への移行の捕捉）を併報する。**`paste_after_stuck_rate` の低下が「自力解決」ではなく「諦め」である可能性を、直接は棄却できない。**

**交絡の統制**: 「ツールを起動したこと自体」の効果（儀式効果）が実在するなら、アウトカムは介入内容ではなくそれに帰属しうる。**較正期（介入なし）と介入期の個人内対比が、この分離の既存の統制として機能する。**

**Phase D（介入機会 X2）**: 介入候補時点で nudge / defer をマイクロランダム化し、近接アウトカム（2〜5分後の手動復帰・外部貼付の回避・dismiss）の差を推定する[42][47]。**cutoff と近接アウトカムの向きは事前登録して凍結し、データを見てから方向を変えない。**

# **10\. Phase1（較正データ収集）の実測 —— 判定に届かなかったこと**

**本章は、本書で最も重要な章である。**

## **10.1 何が起きたか**

2026年6月〜7月、被験者5名・**63セッション**を収集した。うち**主分析に使えるのは40セッション**である（残り23セッションは介入ONの条件で、較正の前提である「推定結果を被験者に見せない」を満たさないため除外した）。

| ゲート | 結果 |
| :---- | :---- |
| **GATE2（測定法）** | **pass**（コホート全体の回答率 **0.926** ≥ 0.80。回答率 <0.70 は1名のみで、Kill 条件の「2名以上」に該当せず） |
| **GATE3（モデル）** | **DataInsufficient** —— 母数を満たしたのは **5名中1名のみ** |
| overall | **inconclusive** |

**被験者別の内訳**

| 被験者 | 評価セッション | 提示 | 回答 | 回答率 | latency中央値 | 有効件数 | X→Q1 C-index | GATE3母数 |
| :---- | :---- | :---- | :---- | :---- | :---- | :---- | :---- | :---- |
| P010 | 10 | 104 | 103 | 0.990 | 6.5s | 103 | **0.45** | ✅ |
| P011 | 3 | 21 | 21 | 1.000 | 8.4s | 21 | 0.40 | ❌ 評価セッション不足 |
| P012 | 5 | 36 | 35 | 0.972 | 4.0s | 35 | **算出不能** | ❌ |
| P013 | 8 | 21 | 7 | **0.333** | 19.3s | 7 | **算出不能** | ❌ |
| P014 | 4 | 34 | 34 | 1.000 | 14.2s | 34 | **算出不能** | ❌ |

**判定パイプラインの `model.verdict` は機械的に `kill` を出した。私はそれを採用しなかった。** 凍結ルールは「**有効プローブ <20件/人 や人数不足は Kill ではなく DataInsufficient**」と事前に定めており、**母数1名の中央値は確証エビデンスにならない**からである。→ **結論: GATE2 = pass、GATE3 = DataInsufficient。**

## **10.2 なぜ起きたか —— 原因は HMM ではなく測定設計にあった**

**C-indexが「低い」のではなく「算出不能」な被験者が2名いた。** 原因は推論側ではなく、**主観申告（Q1）の回答分散の枯渇**である。

| 被験者 | 有効回答 | Q1 の分布 | 相異なる値 |
| :---- | :---- | :---- | :---- |
| P010 | 103 | 2:2　**3:59　4:41**　5:1 | 4（中央2値に97%） |
| P011 | 21 | 1:3　2:7　3:2　4:7　5:2 | 5（良好） |
| P012 | 35 | 1:1　**3:34** | **2**（97%が「3」） |
| P013 | 7 | **1:7** | **1**（完全に一定） |
| P014 | 34 | **1:16　3:18** | **2**（中間値なし） |

順序C-indexは「値が異なるペア」でしか定義されない。**P013 は Q1 が全て 1 ＝ 比較可能ペアがゼロ → 数学的に算出不能**である。

**そして、これは被験者の不誠実さではなかった。** 運用管理シートの主観データと突合した結果:

- **過多側（P012）**: プローブ頻度を **11件中10件で「多すぎた」**と回答。セッション毎アンケートの「集中」項目は5名中最低（2.91）。**その状態で Q1 を35件中34件「3」と回答した。** 事前・事後アンケートの**両方に未回答**であり、離脱していたと解釈するのが自然である。→ **定数化は測定器の過負荷が生んだものである。**
- **過少側（P011）**: 後半4セッション連続で「**少なすぎた**」と回答。有効プローブは21件と閾値ギリギリ。さらに**介入が全10セッションで一度も発火しなかった**（自由記述でも2回言及）。
- **過多側と過少側の両端で同時に外していたことが、律速が測定設計にあることの最も強い証拠である。**

**最も痛い所見**: **P013 は事前アンケートで AI依存「ほぼ毎回」・生成物のコピペ「1日複数回」と回答していた——すなわち GSE が最も狙うべき層である。その被験者が回答率 0.333 で最も早く脱落した。**

**併せて得られた肯定的所見**: 事後アンケート（4名）で「GSEを使う中で詰まったとき考え直す感覚が戻った」は4名中3名が5段階中4–5、フラストレーションは全員1–2。**プライバシー不安は4名全員が「なかった」**——content-free 設計の受容性は支持された。**ただし最も負荷の高かった被験者が欠測しているため、満足度は生存者バイアスで上振れしている。欠測の議論はプローブだけでなくアンケート回答自体にも当てはまる。**

## **10.3 何を直したか**

**① 判定パイプラインの欠陥を修正した。** 尺度理解テストが**未実施**であるにもかかわらず、機械的に「通過率 0.00 ＝ 不合格」と出力される経路があった。**実際にこの出力が引き継ぎに転記され、「1人も通っていない」と誤読された。** → 「未実施」と「不合格」を区別するフィールドを追加し、**未実施のまま Go へ昇格しないことを反証方向のテストで固定した。**

**② 収集仕様の自己記述性を実装した。** 「**信号が無い**」のか「**計器が無い**」のかを、ログだけから機械判定できる形にした。**これは実際に起きた失敗への対処である**——後から沈黙区間を分解しようとしたとき、**必要な行が Phase1 の63ファイル中1行も存在しなかった**（計器の追加が収集の16日後だった）。**計器がコホートを跨げなかった失敗は既に2件あり、3件目を防ぐためである。**

**③ 較正解析パイプラインの穴を起票した。** 介入ONのセッションを混ぜても警告が出ない（配置段階の手作業で防いでいた＝再現性の穴）／時刻の単調性ガードが匿名化データに対して何も守っていない／未匿名化ログが提出される導線がある——**これらは実際にPhase1で顕在化した。**

**④ 次の実験を「設計で回避する」形に切り替えた。** 統制タスク実験（§7.2）では criterion を主観プローブではなく**実験者が与えた条件ラベル**にする。**Phase1 が死んだラベル供給の問題は、統制実験では設計で回避できる。**

## **10.4 プロトタイプ分析の予備的知見（n=1）**

参考として、開発者自身のセッションログによる予備分析を記す。**n=1 であり、汎化性は未検証である。**

- **F6（Pause-after-Delete率）** は Stuck 優勢ウィンドウで平均 **0.469** を示し、Flow優勢ウィンドウ（0.088）の約 **5.4倍**。
- F6 と `p_stuck` の相関は **r = 0.743**、F3（Correction Rate）は **r = 0.678**。
- 設計改善（ヒステリシス層・放出確率の方式変更・合成摩擦）により、Flow優勢率が **97.2% → 79.2%** に正常化し、状態遷移が観測可能になった。

**これらは「モデルの内部で相関している」という記述であって、外部の criterion に対する妥当性ではない。** 外部criterionに対する結果は §10.1 のとおりであり、**X→Q1 の C-index は5名全員で 0.52 以下（偶然水準以下）だった。** **ただしラベル分散が枯渇した状態のC-indexは交絡しており、これを「モデルが外れている証拠」と即断してはならない。** **その切り分けこそが Phase A（統制タスク実験）の目的である。**
