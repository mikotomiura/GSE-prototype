## 6. v1.2 で足したもの（2026-10-08）

> 冒頭の v1.2 改訂宣言の本体である。§0〜§5 は書き換えていない。§1 / §2.1 の表と本節の表は、
> `scripts/check_prereg_parity.py` が**両方**読み、合わせて凍結 JSON と照合する（同じキーが 2 か所にあれば drift とする）。

### 6.1 前処理（観測区間を作る前に `feat` 行を落とす）

`gse-replay --features` は、`feat` 行の時刻列を作った直後に 1 回だけ次の規則を掛け、以後の計算
（観測区間・onset・品質のマスク・`T1a` の窓・tick の右端・封筒の `observed_intervals`）は**落とした後の列だけ**を使う。
落とした行は「入力ファイルに無かった」のと同じに扱う。実装は `src-tauri/src/analysis/feat_offline/idle_trim.rs`。

1. **終わりの点 `h`**: 次の `feat` 行との時刻差が `idle_trim_min_gap_ms` **以上**ある `feat` 行（長い穴の直前）と、時刻が最大の `feat` 行（ファイルの最後。時刻で並べ替えた後の最後であり、ファイルの行順ではない）。
2. **`L`**: `h` 以下で最後の**入力**の時刻。入力は **`key` 行（押下・解放とも・キーの種類を問わない）と `pointer_bin` 行**だけ。
   `ime_state` / `ime_shadow` / `focus_transition` などは数えない（システムが出しうる。2026-10-08 の実記録では、寝た 11 秒後に `ime_state` が 1 行出ていた）。
3. **`R`** = `L` 以上で最初の `feat` 行（最後の入力を含む秒の行。`h` 自身が候補なので必ずある）。
   **`cut = max(R, h − idle_trim_max_ms)`**。
   `L` が無い（`h` 以下に入力が 1 本も無い）ときは **`cut = h − idle_trim_max_ms`**、それが負なら下限なし（`h` 以下の行をすべて落とす）。
   `R` まで残すので、最後の入力は観測区間の内側に入る（判断 6。ただし最後の入力が `feat` 行の穴〔`hole_gap_ms` を超える間隔〕の中にあるときは、`R` は穴の後ろの行になり、入力はどの区間にも入らない。穴の中は前処理が無くても観測区間の外である。`feat` 行は約 1 秒ごとなので、`L` より後を全部落とすと最後の入力が区間の外に出る。2026-10-08 の実記録で確かめた）。
4. **`cut < t ≤ h` の `feat` 行を落とす。** `idle_trim_max_ms = 0` なら（`L` の有無によらず `cut = h` なので）何も落ちない（前処理なしの実行）。

- 入力の時刻: `gse-replay` は行の種類と時刻 `t` だけを読む（`press` などが欠けた `key` 行も入力に数える）。種類が `key` / `pointer_bin` なのに `t` を非負の整数として読めない行があれば、**前処理をせずに止まる**（exit 1・入力の時刻が分からないまま削らない）。

- 原因のラベルは作らない（ADR-030 D8 (b-2) のまま）。規則は穴の長さと入力の有無だけで書いてある。
- 封筒には、`config` に 2 値、`provenance.idle_trim` に落とした `feat` 行の数（`dropped_feat_rows`）と、落とした行のつながり（`spans`・1 本 = 1 つの終わりの点で落とした行。短い穴をまたいでも同じ終わりの点なら 1 本、長い穴をまたげば別の本。本数 = 行を落とした終わりの点の数・`{a_ms, b_ms}` の列）を出す。
- 検査: `idle_trim_min_gap_ms > hole_gap_ms`（穴にならない間隔では削らない）。`idle_trim_min_gap_ms` と `idle_trim_max_ms` は 24 時間以下。
  - 上限が止めるのは **24 時間を超える値（明らかな桁の誤り）だけ**である。たとえば凍結値 60000 の 1000 倍（16.7 時間）は止まらない。凍結値から外れた値は、どれも封筒の `config.overrides` に残る（研究者裁定 2026-10-09・上限を締めない）。
  - 外れた値の向き: `idle_trim_min_gap_ms` が大きすぎると長い穴の前で削らなくなり（ファイルの最後だけ削る）、`idle_trim_max_ms` が大きすぎると削りすぎる。

### 6.4 読み方（§3 に足す規律 7）

7. **前処理あり（運用値）の結果が主**である。**前処理なし（`--set idle_trim_max_ms=0`）の結果を必ず並べて報告する。**
   - 2 本は誤差の向きが逆である。ただし**真の値を挟む上下界ではない**（2026-10-09・研究者裁定。Codex の指摘）。前処理ありでも 30 分を超えて寝た後の `feat` 行は残り、また観測区間が変わると窓・品質のマスク・リスク集合も動くので、率や推定量が 2 本の間に入るとは限らない:
     - 前処理なし: 寝ている間の onset が混ざりうる（電源につないだ Windows のモダンスタンバイ。寝た後も `feat` 行が続くため）。
     - 前処理あり: 寝る直前の本物の onset（画面が点いたまま止まって離れたもの）を落としうる（電源や OS によらない）。
   - 前処理ありを「補正済み」「正しい」と呼ばない。差は「スリープの扱いで動く量」として報告する。
   - あわせて、セッションごとに `provenance.idle_trim` の `dropped_feat_rows` と `spans` の本数（＝ 行を落とした終わりの点の数）を報告する。⚠️ `spans` の `b_ms − a_ms` は短い穴を含みうるので、削った時間としては `dropped_feat_rows`（公称 1 Hz の行数・約 1 秒 × 行数の**概算**。処理の遅れで行の間隔は 1 秒からずれる）を使う。
