## Context

### 1. ★ 何を裁くか

- ADR-014 は、R3（O1）と G1 の募集の競合を**時間軸で解いた**:
  - 判断 1 逐語「⚠️ **G1 の 3 名と募集リソースが正面から競合する** → ★ **判断 4（開始時期）でこの競合を時間軸で解く**（同時に募集しない）」
  - 判断 4 逐語「開始時期 = ★ **G1 の *収集完了* 直後**」。理由は「**R3 は G1 と同じ計器（GSE 本体）を使う**ので、G1 収集中に記録仕様を変えると `preregistration.md §3.6`（ブロックの事後除外の禁止）により**回復不能**になる」。
- ★ 判断 4 の追補（2026-08-23）は、実際に効いている制約を 2 つに絞った: **(1) 収集途中で G1 被験者へ新ビルドを配らない**・**(2) 変更が特徴量経路に触れない**。⚠️ ただし追補は**実施の順序を撤回していない**（理論レビューの衝突 C-C1）。
- ★ **研究者判断（2026-09-18・J-5）**: 「**並行実施へ変える**」（★ レビュー担当の推奨〔判断 4 を維持〕と異なる回答）。
  → 判断 1 と判断 4 を上書きする本 ADR が要る。理論レビューは、新 ADR が扱うべき論点を 5 つ挙げた:
  (i) 募集競合の受け入れ、(ii) 追補の制約 1 との両立、(iii) P-ID の単一採番、(iv) プール分離、(v) ADR-031 M9 による律速。

## Decision

### D1. ★ 開始時期 —— O1 の開始は G1 の収集完了を待たない（判断 4 の開始時期を上書き）

- ★ O1 は、G1 の進み（0/3 名）に関係なく始めてよい。
- ⚠️ ただし O1 の配布を律速するものは**残る**（本 ADR はどれも外さない）:
  1. ADR-031 M9 の追補 —— O1 の配布は **ADR-032 の Accepted と同じリリース**
  2. `scripts/check-o1-release-readiness.sh` が**緑**であること
  3. **本 ADR の Accepted**（研究者）
  4. D6 の運用（案内日の分離）が G1 と O1 の両方の募集に入っていること
- ★ 判断 4 が「GATE3 の verdict を待たない」とした理由（D2 が R3 を確証から外している）は、そのまま本 ADR の理由にもなる —— ★ **O1 の問い（`left_observation` の内訳）は G1 の進みに依存しない**。

### D2. ★ 募集 —— 同時募集を認める（判断 1 の「時間軸で解く」を上書き）

- ★ G1 と O1 の募集が同じ期間に重なることを受け入れる（研究者判断 J-5）。
- ★ **人数は変えない**（段 3 判断 2 #2）: G1 = 3 名（凍結済みの事前登録のまま）、O1 = **3〜5 名**（ADR-014 判断 1）。
- ★ **O1 の上限 5 名の理由を据え直す**: 判断 1 の理由「G1 の 3 名を先に取り切るので募集の総量を抑える」は、並行実施で前提が崩れる。
  → ★ 上限の理由は **「形成的サブコホートであり、研究者が直接説明できる範囲」**（★ ADR-014 判断 3 の根拠 4「一般公募をしない」）とする。
- ⚠️ **判断 3（倫理審査を不要とした根拠 4 件）は 1 つも崩さない** —— ★ 並行実施は一般公募ではない。⚠️ 一般公募へ広げた時点で判断 3 は再判断になる（判断 3 の表のまま）。

### D3. ⚠️★★★ G1 の計器を凍結する —— 追補の制約 1 を「配布物のタグ」で具体化する

- ★ **G1 の被験者へ配る配布物は、G1 の最初の配布に使ったリリースタグで固定する。G1 の収集完了まで、別のタグで作り直さない。**
  （★ `make-common-app-zip.sh --mode g1` と `make-distribution.sh` の両方。）
- ★ **O1 の配布物は、別のタグで作ってよい**（`--mode o1`）。★ ADR-031 M9 により、そのタグは ADR-032 の Accepted と同じリリースになる。
- → ★ 判断 4 の追補の「着手にあたって同時に効き続ける条件」**1 の括弧書き**（逐語「`scripts/make-distribution.sh` / `make-common-app-zip.sh` を **G1 の収集完了まで走らせない**」）を、次へ置き換える:
  > ★ **`--mode g1` の配布物を、G1 の最初の配布と別のタグで作らない。**（★ `--mode o1` の配布物を作るために走らせることは許す。）
- ⚠️ **条件 2〜4 は緩めない**（`HMM_VERSION` を動かさない ／ ゴールデンの差分は新フィールドの追加のみ ／ R3 の段 1 に 1 本も足さない）。
  ★ 理由: G1 の解析は `gse-replay` で再現する（Replay-as-Truth）。O1 のリリースが G1 の特徴量経路を変えると、G1 のログを同じ版で読めなくなる。
- ★ **ログの側で区別できる**: `meta` 行の `g1_mode` / `o1_mode` / `app_version`（出所は Context 2）。→ ★ **G1 の解析は `g1_mode` と G1 のタグの `app_version` を持つファイルだけを使う**。
- ⚠️ **限界**: 配布物の取り違え（G1 の被験者が別のタグの配布物を入れた等）は、**配る前には検知できず、解析のときに `app_version` で除いて初めて分かる**（★ 事後の検知である。除いた件数は除外率として報告する）。

### D4. ★ 同じ人物が両方に入るとき（段 3 判断 1 #8）

| # | 規則 |
|---|---|
| 1 | ★ 両方へ募集してよい |
| 2 | ★ **G1 を先に完了する**。⚠️ G1 の途中で O1 を始めない（★ 追補の制約 1 ＝ 収集途中の G1 被験者へ新ビルドを配らない）。★ G1 を途中でやめた人は、やめた時点を「完了」とみなす（→ 2c） |
| 2b | ⚠️ **O1 に先に参加した人を G1 に入れない**（★ 2 の裏側。★ 理由: 長期の自然作業の記録を経た人は、確証研究である G1 に O1 の経験を持ち越す。⚠️ 持ち越しが効く向きは G1 → O1 より O1 → G1 のほうが重い） |
| 2c | ★ **G1 を途中でやめた人にも O1 を案内してよい**（2026-09-19 追加・段 3 判断 3 #3・研究者判断）。★ やめた時点をその人の G1 の終わりとみなし、3〜5 の手順（翌日以降・別の同意・G1 の配布物を外す・同じ P-ID）で案内する。★ 6 と 7 もそのまま当てる（★ 独立標本として数えない・G1 の途中までの記録と O1 の記録を結合しない）。★ G1 の途中までのデータの扱いは G1 の規則のまま —— G1 の事前登録 `experiments/20260801-controlled-friction-task/preregistration.md` §3.6（被験者の除外は事前に宣言した同意撤回のみ・ブロックの除外は技術的なログ欠損・切断のみ）と、同意文書 `consent.md` §5（削除を求められたら解析から外して破棄する）。本 ADR は変えない。⚠️ G1 を途中でやめることも O1 に参加することも、それ自体は G1 の記録の削除の求めではない（★ `consent.md` §5 は「途中でやめられます」と「後からデータの削除を求められます」を別の項に分けている） |
| 3 | ★ **O1 は G1 の翌日以降に、別の同意で始める**（★ O1 の同意文書は G1 の `consent.md` と別のものである・ADR-014 Migration 5「説明・同意文書（O1 普段の作業の長期記録）」） |
| 4 | ★ 同じ端末では、**G1 の配布物を外してから** O1 の配布物を入れる（★ 2 つの版が同じ端末に並ばないようにする） |
| 5 | ★ **P-ID は同じものを使う**（★ ロスター共用・メール一致で再利用する現行の動作のまま）。⚠️ 新しい P-ID を振らない（★ 1 人に 2 つの識別子を作らない） |
| 6 | ★ 同じ人物であることを**対の観察として記録し、独立標本として数えない**（★ 研究を横断して人数を数えるとき、同じ人を 2 人と数えない） |
| 7 | ⚠️ **G1 と O1 のデータを結合して解析することは、本 ADR では認めない**。★ 結合するなら、両方の同意文書の範囲を研究者が確かめてから別途決める（★ 被験者向け文書は契約）。★ **「結合」の定義**: G1 と O1 の記録（またはそこから計算した量）を、P-ID をキーにして **1 つの解析表・1 つのモデル・1 つの図**に並べること。⚠️ 6 の「対の観察の記録」は、**両方に参加した P-ID の一覧**（人数の数え方のためだけに使う）であり、結合ではない。⚠️ **その一覧に置く列は P-ID だけ**にする（★ 日付・属性・指標を付けると解析表に近づく） |

### D5. ★ プールを分ける

- ★ G1 のデータと O1 のデータを**同じ解析プールに入れない**（★ ADR-014 D1 のレジームの区別・D2 の「O1 で確証仮説を判定しない」のまま）。
  - ⚠️ G1 の確証解析（凍結済みの事前登録）に O1 のデータを入れない。
  - ⚠️ O1 の形成的解析に G1 のデータを入れない（★ 課題条件が違う・D4-7）。
- ★ 受け口・保存先はすでに分かれている（Context 2）。★ 本 ADR はそれを**規則として固定する**。
- ★ **構造上の歯止め**: O1 のデータは `sync-session` のガードで `gse-dataset` へ出ない。G1 の解析 DB（`scripts/build_analysis_db.py`）は `gse-dataset` だけを読む → ★ **G1 の解析経路には O1 が入らない**。
  ⚠️ 逆向き（O1 の解析に G1 を読み込まない）は、まだ機械的な歯止めが無い → ★ O1 の解析スクリプトを作るとき（O1 の事前登録・ADR-014 Migration 4）に、G1 の入力を拒む検査を acceptance に入れる（Migration 6）。
  ⚠️ **歯止めの固定の度合い**: O1 を `gse-dataset` へ出さないガードは `scripts/sync_session_o1_guard_test.sh` とリリースゲートで検査されている。⚠️ 「`build_analysis_db.py` が `gse-dataset` だけを読む」ことはテストで固定されていない（★ 現在の実装の事実である）。

### D6. ⚠️★★★ P-ID の同時採番（起票 T-27）—— 案内日を分けて、検出で受ける（段 3 判断 2 #1）

- ★ **運用**: G1 の登録案内と O1 の登録案内を**同じ日に出さない**。★ 同じ人物に両方を案内するときも、O1 の案内は G1 の完了の後（D4-2 / D4-3）なので自然に分かれる。
- ★ **起きたら**: 両側の検出で止め、研究者が裁く（★ O1 = 予約トークンで自己修復・直せなければ配らない ／ G1 = 採番直後に数えて 2 行以上ならシートへ出す）。⚠️ **自動で消したり振り直したりしない**（`g1CountPidRows_` の doc のまま）。
- ⚠️★★★ **限界を隠さない**:
  - ★ 本規則は**機械的に強制されない**（★ `docs/o1-roster-operations.md` の T-28 と同じ「運用で回避」の代償）。
  - ⚠️ G1 側の検出は TOCTOU を捕まえられない（逐語「『G1 が書く → G1 が数える(=1) → **O1 が書く**』の順序は**捕まえられない**」）。→ ★ **検知ゼロを衝突ゼロと読まない**。
  - ★ 機械的に塞ぐ手段（採番を 1 か所の Web App へ集約する）は**原理的に可能**だが、今回は採らない（研究者判断・コード変更ゼロを優先）。
- ★ **軽い監査**（コード変更ゼロ）: 登録案内を出した**翌日**に、ロスターの A 列で同じ P-ID が 2 行以上ないかをシート上で確かめる（⚠️ 既存の `checkO1RosterShape()` は重複を数えない）。
- ★ **止める条件**: 重複が見つかった P-ID のデータは、研究者が裁くまで**解析に使わない**（⚠️ O1 の提出は 48 時間の猶予後に自動で進むので、止めるのは解析の側である）。
- ★ 運用規則の SSOT は `docs/o1-roster-operations.md` に置く（→ Migration 2）。

## Alternatives

### A1. ⚠️ ADR-014 判断 4 を維持する（G1 の収集完了 → O1）

★ 計器の取り違えが原理的に起きない。⚠️ **却下**（研究者判断 J-5・2026-09-18）。★ G1 が 0/3 名のまま O1 が止まり続ける（★ ADR-011 §Context-6「待つと止まる」の形）。⚠️ ただし判断 4 は、GATE3 の verdict を待つことは退けつつ、**収集完了を待つことは計器の理由で正当とした**。★ 本 ADR はその理由（計器）を捨てず、D3 のタグの固定で受ける。

### A2. ⚠️ 同じ人物を両方に入れない（人でプールを分ける）

★ 対の扱いが要らない。⚠️ **却下**（段 3 判断 1 #8）—— ★ 募集の総量が増える。

### A3. ⚠️ 採番を 1 か所（Web App）へ集約して T-27 を原理的に塞ぐ

★ 機械的に強制できる。⚠️ **却下**（段 3 判断 2 #1）—— G1 / O1 両方の GAS の改修と再配備が要る。★ n が小さく（G1 3 名 ＋ O1 3〜5 名）、案内日を分ければ同時提出は起きにくい。⚠️ **将来 n が増えたら再検討する**（Consequences 2）。

### A4. ⚠️ G1 も O1 と同じ新しいタグで配る（配布物を 1 系統にする）

★ 配布物の管理が単純になる。⚠️ **却下** —— ★ G1 の計器が、G1 の被験者の間で変わりうる（★ `preregistration.md §3.6`「ブロックの事後除外の禁止」で回復不能・判断 4 の理由そのもの）。
