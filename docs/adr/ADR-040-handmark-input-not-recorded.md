## Context

### 1. 何を決めるか

手跡（glossary「手跡」）の見本の自然世界の版は、打鍵に加えて、カーソルの位置と動き・クリック・ホイールを
表現の入力に使う形で固まった（`20261020-handmark-multi-input` 判断 2・10〜12。見本は Version 5）。

| 入力 | 表現 |
|---|---|
| カーソルの位置と動き | 近くの草だけがなびく。動かしている間だけ近くの粒が寄り、止めると数秒でほどける |
| クリック | その場に一回きりの波紋が立ち、1.6 秒で消える |
| ホイール | 粒全体の描く位置を縦にずらし、1 秒で半分に戻る |

背景の層の窓はマウスを受けない作りである（背後のデスクトップのクリックを奪わないため。
`spike/handmark-stage` の `src-tauri/src/handmark_stage_spike.rs` 冒頭）。実物では Rust の側で入力を読み、
表現の窓へ渡すことになる。

### 2. なぜ ADR が要るか

ADR-014 D4 の「R3 でも入れないもの」の表は、次の 2 行を名指ししている（`ADR-014` の表・199〜200 行）。

| 入れないもの | 理由（逐語・記号と太字を除く） |
|---|---|
| 符号付き `dx` / `dy`（イベント単位）/ 絶対座標 / 解像度 / マルチモニタ配置 | 累積すれば軌跡が復元でき画面内容の代理になる（ADR-012 D4 L-b） |
| イベント単位の移動量＋時刻の列 | mouse dynamics は個人識別可能な生体特徴（同上） |

理由はどちらも **記録したときの害**である（累積すると軌跡が戻る・列が個人を識別する）。D4 は O1 の収集の決まりで、
表現の側のことは決めていない（v3-grading 判断 8 の根拠）。しかし、表現の側のコードが絶対座標を読むのを見た人には
D4 に反するように見える。持ち込む前に、使ってよい範囲と、記録へ流れないことを保つ仕組みを決めておく（判断 7）。

### 3. 確かめたこと（`20261020-handmark-multi-input` design.md §1・§2・§2b）

| 入力 | macOS | Windows |
|---|---|---|
| 位置 | `NSEvent.mouseLocation` を描画のたびに読む。**権限なしで読めた**（実測。権限を持たない ad-hoc 署名の .app で `AXIsProcessTrusted()=false`・`CGPreflightListenEventAccess()=false`。置いた位置を追った。macOS 27.0.1） | `GetCursorPos` を描画のたびに読む（実測していない） |
| クリック | `NSEvent.pressedMouseButtons` を繰り返し読む。**権限なしで 3 回とも数えた**（実測・研究者の手のクリック・50ms ごとの読み）。50ms より短い押下は取りこぼしうる（率は測っていない） | `GetAsyncKeyState(VK_LBUTTON)` などを描画のたびに読む（実測していない） |
| ホイール | 繰り返し読む方法がない。CGEventTap が要る。権限なしの tap では押下も 0 件だったが、権限ありの対照が無いので「権限なしでは届かない」は見込み | 繰り返し読む方法がない。Raw Input は受け先が 1 プロセスで装置の種類ごとに 1 つの窓で（一次資料の逐語「Only one window per raw input device class may be registered to receive raw input within a process」・survey §6.5）、O1 の `observe_windows.rs` がすでに使っている |

位置とクリックは、両 OS とも、フックも（macOS では）権限も要らない読み方がある。読むのは「いまの一点」で、
列を作らない。ホイールは両 OS とも、イベントを取る仕組みを表現の側にも持たせることになる。

## Decision

### D1. 手跡の背景の層は、カーソル・クリック・ホイールを表現の入力に使ってよい

- 使ってよい入力: カーソルの位置と動き（前の一点との差）・マウスボタンの押下・ホイール。
- 射程は **手跡の背景の層だけ**（判断 5）。層 A・肖像（EH3 の壁紙を含む）など別の表現で使うときは、
  本 ADR を先例として改めて決める。
- 打鍵の扱いは本 ADR の外である（打鍵はすでに記録の対象で、表現が打鍵から何を受け取るかは
  `.steering/20261015-tangibility-design/` 以降の手跡の決まりのまま）。

### D2. 記録しない・送らない・推定に流さない

表現の入力から得た値（座標・差・押下・ホイールの量、およびそこから計算した値）は、次のどこにも入れない。
入力から計算していなくても入力で動く値（描画の回数・負荷など）も、入力の代わりの値として同じに扱う
（背景の層の試作の計測の CSV は毎秒の描画の回数を書いており、試作自身が「その秒に打っていたか」の粗い代わりになると認めている。
ポインタで描画が回るようになると、これは ADR-012 D4 L-b の 1 秒ビンと同じ種類の量を、L-b の仕様の外で残すことになる）。
したがって、ポインタを入れた版では、人の手で動かした描画の量を計測に書かない。負荷は、決まった動きを流す合成の入力か、
ポインタを切った条件で測る（判断 7）。D2 に例外は作らない。

- NDJSON（`LogEntry`）・applog・`tracing` の出力・提出物（`submission` / `packaging`）
- 開発や試作の計測のファイル（CSV など）
- ネットワーク
- 表現の窓の保存先（`localStorage`・`sessionStorage`・IndexedDB など）と、窓から Rust への返送（`invoke` など）
- 推定（`analysis/` の `engine`・特徴量・介入の判定）

**ADR-014 D4 と ADR-012 D4 L-b は O1 の記録の決まりであり、本 ADR はその本文を変えず、O1 の収集も広げない。**
O1 の `input/observe*.rs` と `analysis/pointer_bin.rs`、ADR-014 D4 の mac 側のマスク（クリックを含まない）には
手を入れない。

### D3. 記録へ流れないことを、型・境界・振る舞いの 3 層で保つ（判断 9 の具体）

| 層 | 決めること | 止められないもの |
|---|---|---|
| 型 | 表現の入力の型に `serde::Serialize`・`Debug`・`Display` を付けない。窓へは専用の関数で、描画に要る値だけを渡す。`LogEntry` は `Debug` を derive している（`logger.rs` の定義）ので、この型をそのフィールドに入れるとコンパイルが通らない。`schema_dto.rs` の `Serialize` の型に入れることも、`serde_json::json!` に渡すことも、`tracing` の `{:?}` で出すこともできない | 値をふつうの数に取り出した後の漏れ（`LogEntry` の行は `format!` と `json!` で手で組み立てるので、数に取り出せば型は効かない）。窓へ送る payload（Tauri の `emit` は `Serialize` を要るので、必ず数の型を経由する）。エラーの文（`anyhow!` や `expect` に値を入れると、呼び出し側で `tracing` に出うる） |
| 境界 | 入力を読むコードを、記録の側と別のモジュールに置く。OS の API を呼ぶファイルは、技術的制約 11（`docs/agent-shared.md`）が許す `input/` に、O1 の `observe*.rs` とは別のファイルとして置く（制約 11 の列挙を増やさない）。`analysis/` には置かない。ソース検査は下の対応表のとおり | 別名の関数を経由した漏れ（文字列検査は補助） |
| 振る舞い | 入力を与えて表現の側を回し、記録（NDJSON の行・applog・計測のファイル）が 1 行も増えないことをテストする | 送信や推定への流入（行数を数えるテストには見えない。ソース検査に頼る） |

D2 の行き先ごとに、どの層で止めるかを次に置く。語の細部（どの語を見るか）は実物のタスクで詰めるが、行き先を落とさない。

| D2 の行き先 | 止め方 | 止められないもの |
|---|---|---|
| NDJSON（`LogEntry`）・applog・`tracing` | 型（`Debug`・`Display` なし）・ソース検査（`LogEntry`・`tracing::`・`log_tx`・`POINTER_TX`）・振る舞い | 数に取り出した後に記録の側の関数へ渡すこと |
| 提出物 | 逆向きのソース検査: `logger.rs`・`schema_dto.rs`・`submission.rs`・`packaging.rs` が表現の入力の型と payload の型の名前を含まない | 同上 |
| 計測のファイル | ソース検査（`std::fs`・`File` を含まない）・振る舞い | 計測を別のモジュールに置いて値を渡すこと |
| ネットワーク | ソース検査（Rust 側と窓の側の通信の API を含まない） | 通信を持つ共通の関数へ数を渡すこと・別名での参照 |
| 窓の保存と返送 | 窓の側のソース検査（ブラウザの保存先・`invoke`・`fetch` を含まない）。⚠️ 窓の capability は、いまの作りではアプリのコマンドを窓ごとに止められない（spike の `capabilities/handmark-stage.json` の記述: AppManifest がない）。窓ごとに止めるかは実物のタスクで決める | 窓ごとに止めない間は、記録のコマンドを窓から呼べること自体は残る |
| 他の窓への配送 | 配信を手跡の窓に限る（`emit_to`）。全窓へ流す `emit` を使わない。⚠️ `emit_to` だけでは足りない: tauri 2.10.2 は target が `Any` の受け手には絞り込みを掛けない（`event/listener.rs` の `match_any_or_filter`）ので、主窓のコードが同じイベント名を target なしの `listen()` で受ければ届く。→ 手跡の窓専用のイベント名にし、他の窓のコードがその名前を `listen` しないことをソース検査で固定する | target が `Any` の受け手を別名や動的な名前で作ること |
| 推定 | ソース検査（`crate::analysis` を参照しない） | 推定へつながる共通の関数へ数を渡すこと・別名での参照 |
| 列（D4） | Rust の側: 列を持たない（最後の一点と戻る値だけ）。窓の側: 許す枠を入力ごとに名前で決め、長さは定数で上限を置く。検査は許す名前の一覧で見て、それ以外の配列・表・リングバッファを赤にする | 許した名前の枠に、寿命を過ぎた値を残す実装（→ 振る舞いのテスト。D4） |

- 前例は壁紙の層の R-P9（`src-tauri/src/wallpaper.rs` の `person_operations_leave_no_trace_in_the_applog` と
  `the_wallpaper_layer_cannot_write_records`）。
- どの検査にも **陽性対照**を付ける。文字列検査は、検査する文字列を足した版で赤になることを確かめる
  （対照の文字列は実行時に組み立て、検査対象のファイルに書かない）。振る舞いの検査は、わざと記録する版で増えることを確かめる。
- 表の「止められないもの」は、この ADR が保証しない範囲である。文字列検査は関数を経由した漏れを見つけられないので、
  レビューで「表現の入力の値を引数に取る関数がどこへつながるか」を見る。
- Windows で `GetAsyncKeyState` を使うときは、**マウスボタンの仮想キーだけ**を読む。キーボードの仮想キーを読まないことも
  境界の検査に入れる（同じ関数でキーの押下も読めるため）。

### D4. 溜めない

- Rust の側が持つのは **最後の一点**と、数秒で戻る値だけ。位置や押下の列を作らない。
- 画面の上の跡も数秒で消える一時のものに限る（`20261017-handmark-why-interesting` 判断 6 の制約 1「育たない・溜まらない」）。
- 描画の状態として許すのは、次の形だけである。
  - 跡を描く枠（窓の側だけ）: 入力ごとに名前を決めた固定の少ない数の枠（見本の波紋は 6）で、古いものから上書きする。
    枠は位置と始まりの時刻を持つので、直近の数回の押下の位置と時刻の短い列になる。これを許す条件は、
    寿命（見本は 1.6 秒・数秒まで）を過ぎた枠と入力を切ったときの枠から位置と時刻を消すこと（描かないだけでは足りない。
    見本は始まりの時刻で描くかを決めるだけで、位置が残る）、読む口を持たないこと。入力が来ない間にも消えることをテストで確かめる。
  - 戻っていく値: 草の押し・粒のずれ・縦のずれなど、時間とともに 0 へ戻る値。
  - 寿命のない列、上限のない列、跡を描かない履歴は持たない。D3 の列の検査は、この区別で見る。
- 本人がある入力を切ったら、その入力の跡はすぐ消し、入れ直したときに前の跡を出さない。切ったときは取得も止め、
  配送待ちの値と切る前の時刻の値を捨てる（遅れて届いた値で跡が戻らないようにする）。これもテストで固定する。
- 窓の側は、受け取った値の時刻を見て、古いもの（描画が止まっていた間に溜まったもの）を描かずに捨てる。

### D5. 数で返さない（ADR-025 D1 を手跡の入力に当てる・判断 3）

- 手跡の入力から出た値を、本人が読む面に量として出さない（量の定義は ADR-025 D1 のまま:
  数値・順位・達成度・連続日数・経過時間・残り時間・累計）。動かした量・押した回数・回した回数を数字・目盛り・
  累計の形にしない。
- これは ADR-025 の射程（層 A）を **手跡の背景の層の入力に限って**広げるもので、`expression-channel.md` §8 の
  `E-11` のうち **PC 側 UI の一部（手跡の背景の層のポインタの入力）だけを閉じる提案**である。ADR-026 D4・ADR-035 D6 は面を丸ごと閉じたが、
  本 ADR は面ではなく入力で切る。手跡の背景の層のうち打鍵の表現は本 ADR の外（D1）で、`E-11` に残る。
  `E-11` に残る `Dashboard.tsx`・オンボーディング・OS 通知・層 B・結果返却は閉じない。
  本 ADR が Accepted になったとき、`E-11` の行に追記する（本文は書き換えない・Migration）。

### D6. 読み方と OS の差

- 位置とクリックは **描画のたびに一点を読む**（macOS は `NSEvent.mouseLocation`・`pressedMouseButtons`、
  Windows は `GetCursorPos`・`GetAsyncKeyState`）。フックを使わない。
- macOS の位置とクリックは権限なしで読めることを実測した（Context 3）。Windows は実測していない。
  実物へ入れる前に、Windows 機で収集だけを頼む形で確かめる。
- 描画のたびの読みは、読みの間隔より短い押下を取りこぼしうる。表現の入力なので取りこぼしは許すが、
  どれくらい取りこぼすかは実物で測る。
- 使うボタン（左だけか、どのボタンも数えるか）は実物で決める。

### D7. ホイールは範囲に含める。O1 の記録の経路を通さずに取れない OS では使わない（判断 4・判断 12）

- ホイールは本 ADR の範囲に含める（入れると決めたときに ADR を起こし直さずに済む）。
- 実物へ入れる条件: **O1 の受け先を奪わず、O1 の記録の経路と同じ場所を通らずに取れること。**
  満たせない OS ではホイールを使わない。
- Windows では、表現の側が Raw Input のマウスを別に登録すると O1 の受け先を奪う（Context 3）。
  `WH_MOUSE_LL` は ADR-014 D4 が O1 で採らなかった理由（システム全体のマウス入力を直列化する・
  通知なく外される）が表現の側にもそのまま当たる。この 2 つは条件を満たさない。
- macOS では権限ありの対照をまだ取っていない。取れるかは実物のタスクで確かめる。

### D8. アプリの切り替えは使わない（`20261020-handmark-multi-input` 判断 3）

切り替えの回数は「注意が散っている」という評価に読まれやすく、`20261017` 判断 6 の制約 2（状態を表さない）と
ADR-025 に近づく。

## Alternatives

| # | 案 | 採否 | 理由 |
|---|---|---|---|
| A1 | 表現にもポインタを使わない（打鍵だけ） | 却下 | 研究者が多入力を取り入れると決めた（v3-grading 判断 8）。D4 が禁じる理由は記録したときの害で、記録しなければ当たらない |
| A2 | O1 の記録の値（1 秒ビンの量）を表現にも使う | 却下 | 位置がなく近くの草・粒を動かせない。記録と表現が同じ経路を通り、境界が崩れる |
| A3 | 型に頼らず、境界と振る舞いだけで止める | 却下 | 判断 9。型でコンパイル時に止められる分は止める |
| A4 | 型だけで止める | 却下 | 数に取り出した後の漏れを止められない（Codex の指摘・判断 9） |
| A5 | ホイールを O1 の受け先から分けて受ける | 却下 | 判断 4。記録と表現が同じ場所を通り、境界の検査を O1 のコードにも広げることになる |
| A6 | ADR-025 を参照するだけにする | 却下 | 判断 3。射程が層 A なので、手跡には決定として効かない |
| A7 | GSE の表現全般に広げる | 却下 | 判断 5。確かめていない面まで広がる |

## Consequences

- 表現の側のコードが座標を読むことは、本 ADR の範囲では D4 に反しない。範囲は「手跡の背景の層・記録しない・溜めない・数で返さない」で、
  どれかが崩れたら本 ADR の外になる。
- 実物には、記録の側とは別のモジュールと、D3 の検査（陽性対照つき）が増える。
- 入力はメモリの中では読んでいる。記録しないことはプロセスの外へ出さないことまでを保ち、プロセスの中で読んでいないことは保たない。
- 本人や他人が画面を撮れば、跡は数秒ぶん写る。これは表現であって記録ではないとし、本 ADR は画面の取り込みを扱わない
  （背景の層が取り込みに写るかは `spike/handmark-stage` で測っている）。
- 入力を足すほど「自分の作業が一緒にいる」に寄るか騒がしさに寄るかは、研究者の「大まかによい」以上には確かめていない
  （判断 12）。多入力の伏せた見比べは別に残る。

## Migration

1. 実物（背景の層の試作 `spike/handmark-stage`）へ持ち込むタスクの最初に本 ADR を読み、D3 の検査から書く。
2. Windows 機で `GetCursorPos`・`GetAsyncKeyState` を収集だけの依頼で確かめる（D6）。
3. ホイールは、各 OS で D7 の条件を満たせるかを確かめてから入れる。macOS は権限ありの対照を取る。
4. 持ち込みのタスクで、本 ADR を見直す（Accepted にするか・D6 の未決を閉じるか・窓ごとにコマンドを止めるか）。
5. Accepted になったら、`expression-channel.md` §8 の `E-11` の行に「手跡の背景の層のポインタの入力は ADR-040 D5 で閉じた」と追記する。

## 見直しのきっかけ

- 実物へ持ち込むとき。
- Windows の実測が出たとき。
- 手跡の背景の層以外で、ポインタを表現に使いたくなったとき（D1 の射程）。

### 項目 1. 読みの間隔（判断 7）

- 背景の窓は Rust へ問い合わせる口（`invoke`）を持たない（判断 4）。窓の描画に合わせて読めないので、Rust の側の読みのスレッドが
  16ms ごと（1 秒に約 60 回）に読む。止めている間は何も送らない。
- 送り先は背景の窓だけで、専用のイベント名（`handmark-stage-pointer`）を `emit_to` で送る（D3 の表の `emit_to` の行のまま）。
- 16ms より短い押下は取りこぼしうる。どれくらい取りこぼすかは測っていない（D6 の 3 つめの点は未決のまま）。

### 項目 2. 左ボタンだけ（判断 6）

- macOS は `pressedMouseButtons` の最下位のビットだけを読む。右ボタン・中ボタンは読まない。

### 項目 3. macOS のホイール（判断 9）

- 材料（results.md §4）: 権限のない .app では、聞くだけの tap は作れたが無効にされ、合成のスクロール 10 回のうち 0 回。
  入力監視の許可を引き継いだ対照では 10 回とも届いた。macOS でホイールを繰り返し読む方法は無く、許可と tap が要る。
- D7 の条件（O1 の受け先を奪わず、O1 の記録の経路を通らない）を、macOS では次の形で満たすとする。
  - O1 のポインタの tap（`input/observe_macos.rs`）とは別のファイル（`input/handmark_wheel_macos.rs`）・別のスレッドに置く。
  - 聞くだけ（ListenOnly）で、ScrollWheel だけを受ける。イベントを止めも変えもしない。
  - 持つのは前に読まれてからの回した量の和 1 つだけ。位置も時刻も読まない（D4）。
  - トレイの「背景: ホイール」を入れている間だけ tap を作る。切ったら tap ごとスレッドを終え、溜まった量を捨てる。
- これは D6「フックを使わない」の、macOS のホイールに限った例外である。位置とクリックは今もフックを使わない。
- Windows は D7 のとおり、ホイールを使わない。

### 項目 4. 打鍵の tap の失効（results.md §5.1）

- 研究者の試視の間（5 回の起動・合わせて約 23 時間）、本体の打鍵の tap が macOS に無効にされたことが 11 回あった
  （最も長い起動は約 21 時間で 7 回）。どれも 1〜2 秒で作り直され、数秒〜数分で記録は戻った。
- ホイールの tap を持たない条件と同じ長さで比べていないので、ホイールの tap のせいかは分からない。
  研究者は、O1 の収集をこれ以上欠かさないため、いまは切り分けないとした（2026-10-23）。
- ホイールの tap が本体の打鍵の tap の失効を増やすなら、本体の記録を欠かす方向に効き、D7 の条件に触れうる。
  実物（本線）へ入れる前に、ホイールを切った条件と比べる。

### 項目 5. D3 の検査（results.md §1）

- 検査は `src-tauri/src/handmark_stage_guard.rs`（テストだけ）に置き、D3 の行き先ごとに陽性対照を付けた。
  型の検査は `const` の評価で、`Debug` などを付けるとテストのビルドが止まる。
- 検査の中の対照に加えて、実物を壊して赤を見た: 配送に `tracing::debug!` を足す（ソースの検査と振る舞いのテストの 2 件が赤）、
  窓の側に名前の一覧の外の配列を足す（列の検査が赤）、`PointerSample` に `Debug` を足す（ビルドが止まる）。戻すと緑。

### 項目 6. 窓の側の枠と捨て方（D4）

- 波紋の枠は 6 つ・寿命 1.6 秒。寿命を過ぎた枠と切ったときの枠から位置と時刻を消す。
- 受け取りは、切る前の世代の値と、送られてから 250ms を超えて届いた値を捨てる。切った知らせは遅れて届いても効く。
- これらは `scripts/handmark-stage-trace.test.mjs`（`node --test`・7 件）で固定し、消去と世代の判定を壊すと赤になることを確かめた。

### 項目 7. 計測（D2・判断 4）

- 試作から、描画の回数などの計測の CSV と、窓から Rust へ問い合わせる口を外した。CPU は外からプロセスの累積の秒で測り、
  人の手の入力は使わず合成の入力とポインタを切った条件で測った（results.md §3）。

### 見直しのきっかけ（足す）

- ホイールを切った条件と比べて、打鍵の tap の失効が増えると分かったとき（項目 4）。
