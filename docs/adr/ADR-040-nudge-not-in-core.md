# ADR-040: Nudge を GSE 本体の介入として出さない —— 判断のロジックは時機の評価に残し、本体の介入は招待にする

## Context

1. 研究者は 2026-10-31 に GSE の位置づけを改めた（判断 10・15）: **打鍵の時刻と種類から作業上の認知状態を推定し（本文は保存しない）、詰まる前に介入を促して、身体回帰の機会を差し出す**。身体回帰は採点しない招待で、開始・継続・完了を系は測らない（ADR-018）。
2. 研究者の言（判断 11）: 「nudge などもおそらく不要じゃないかな？ 割と邪魔くさいかも。存在しても良いとしても、ユーザー検証の際にラベル付の意味合いで作成したし、GSE 本体では不要な気がする」。
3. 実装の現状（2026-10-31 に一次で確認）:
   - Nudge は `analysis/intervention.rs` の `InterventionAction{None, Nudge, Defer}` で判断し、overlay のサイドカードで表示する。条件は `p_stuck ≥ 0.60` と小休止、クールダウン 10 分、1 日 6 回まで。
   - 介入の有効・無効は `lib.rs` の `INTERVENTION_ENABLED`（初期値は有効・`lib.rs:122`。セッションの宣言で上書きされる・`lib.rs:3081`）。O1 と EH3 では無効にしている（`lib.rs:4003`）。無効のときは判断そのものを計算せず記録もしない（`lib.rs:1286`）。
   - 判断は記録からオフラインで計算し直せる（`gse-replay --intervention`・`analysis/intervention_eval.rs` の HIR・Precision）。
   - 招待は EH3 モードで実装済み（`analysis/invitation.rs`・40 px の文字のない図像・60 秒で閉じる・応答のボタンなし・上限と時間帯は本人が選ぶ）。
4. Nudge が検証で担っていた役割は 3 つある: ラベルを取ること、出す時機が正しいかを見ること、出したら何が変わるかを見ること（判断 12）。

## Decision

### D1. Nudge を GSE 本体の介入として出さない

- 本体の既定で Nudge を表示しない（`INTERVENTION_ENABLED` の既定を無効にする、または同等の変更）。変更は別タスクで行い、ゴールデンのテストと `meta` 行の非回帰を確かめる。
- 本体の介入は招待（身体回帰の機会・ADR-026 の PC 面）にする。

### D2. 判断のロジックは消さず、時機の評価に使う

- `intervention.rs` の判断（Need と Opportunity の分離・defer・抑制）は残す。画面に出さず、記録から `gse-replay --intervention` で判断の時刻を計算し、`intervention_eval.rs` で評価する。
- 表示の部品（overlay のサイドカード）の削除は、本 ADR では決めない。

### D3. Nudge の検証での役割を、今あるもので受け持つ

| 役割 | 受け持つもの |
|---|---|
| ラベルを取る | ランダムな時刻のプローブ（盲検の較正）と O1 の 6 択の自己申告（ADR-031） |
| 出す時機が正しいかを見る | D2 のオフライン評価（画面に出さない） |
| 出したら何が変わるかを見る | 招待の図像（検証で操作するものと本体の介入が同じになる） |

### D4. 招待の契機と検証の条件（方向だけを決め、値は事前登録で決める）

- 「詰まる前」は、境界の `level` の `friction_rising`（ADR-021 D4）を、今の推定の出力から定義して招待の契機にする。将来は criterion 直結の段（ADR-019 D1・ADR-009）のハザードへ中身を差し替える。境界の契約は変えない。上げる条件は ADR-019 D3 と約 50 セッションで、事前に登録する。値は事前登録の前に決める（判断 13）。
- 統制課題の 1 段目では、招待の出し方を {推定器 / 頻度を合わせた無作為 / なし} に、各人の中でセッション（またはブロック）ごとに無作為に割り付け、1 人あたり多数のセッションを取る（判断 6 の案 B・判断 14）。割付の単位・反復数・順序と持ち越しの扱いは事前登録で決める。無作為の時刻の条件を `invitation.rs` に足す（別タスク）。
- 1 人の検証期間の途中で推定器の中身を切り替えない。推定器の版を分けて記録する。

## Alternatives

| 案 | 採らなかった理由 |
|---|---|
| Nudge を本体に残す | 研究者の判断で本体には不要（邪魔になりうる・検証の道具として作った）。招待と二重の介入になる |
| Nudge の表示ごと削除する（ADR-015 と同じ型） | 研究者は「既定で止めて残す」を選んだ（判断 14）。コードとゴールデンのテストを壊さずに外せる |
| 実験の中に AI の相談窓を置いて受領を観測する | 研究者が不要と判断した（判断 9）。フォーカスの遷移は既に記録されている |

## Consequences

### 良くなること

- 本体の介入が 1 つ（招待）になり、位置づけ（身体回帰の機会）と実装が一致する。
- 検証で操作するもの（招待）と本体の介入が同じなので、検証の結果がそのまま本体の主張になる。
- 時機の評価は画面に何も出さずにできる。

### 代償

- 主要アウトカム（ADR-024 D1）の構造は、トリガー = Stuck エピソード（`p_stuck ≥ 0.60`・推定器。ADR-024 は許容すると明記）、イベント = 離席候補ギャップ（180 秒以上）明けの初打鍵、アウトカム = その後の受領（外からの paste）の有無である。ADR-024 は分母を離席候補にすると、離席を誘う介入（Physical Anchor）の効果推定で選択バイアスになると述べる。招待を 3 条件で動かすと、腕ごとにトリガーと分母がどう決まるか（とくに無作為の腕で `p_stuck` のトリガーを使うと処置後の条件付けが腕ごとに違って入る）が問題になる。腕ごとのトリガー・分母・時刻の原点を、事前登録の前に決める（判断 14 で副のアウトカム「ウィンドウを離れずに再開したか」を足した）。
- 統制課題で AI の答えをどの経路で得られるようにするか（相談窓は採らない・判断 9）は未決。受領は外からの paste でしか見えないので、課題の設計で決める。
- D2 のオフライン評価は `intervention.rs` の旧閾値と抑制の評価であり、`friction_rising` を契機にする新しい招待の時機の評価にはそのままでは使えない。新しい契機も `gse-replay` で記録から再現できるようにする（Migration 2）。
- 招待の契機を `friction_rising` に替えるまで、招待は「詰まってから」側（`p_stuck ≥ 0.60` が 30 秒）で動く。
- 既存の docs のうち「現行で稼働する介入は Nudge のみ」と書く箇所は、既定の変更が入るまで事実として正しい。既定の変更のタスクで併せて直す。

## Migration

1. 別タスク（`/start-task`）: Nudge の既定を無効にする。ゴールデンと `meta` の非回帰を確かめる。
2. 別タスク: 招待に `friction_rising` の契機と、無作為の時刻の条件を足す。通常のモード・O1・EH3 のそれぞれで招待を出すか出さないかを定め、通常のモードで招待が出る配線を足す（今は EH3 モードでだけ動く。D1 の後に本体の介入が何も出ない状態を作らない）。新しい契機を `gse-replay` で記録から再現できるようにし、時機のオフライン評価に使う。
3. 事前登録: `friction_rising` の値・腕ごとのトリガーと分母と時刻の原点・副のアウトカムの限界・割付の単位と反復数・2 段目へ進む人の選び方・感度分析を、データを見る前に書く。
